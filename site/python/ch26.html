PREFLIGHT CHECKLIST

Picture: Pip points at a clipboard checklist with four ticks and one red cross. Beside Pip stands an orange flight recorder whose dial points at INFO. Sneak the quiet bug peeks in from the side, hoping nobody reads the list.

Pilots never skip the checklist, however many times they've flown. Today Pip gets one for code: tests with tables and a ground crew, a flight simulator for the outside world, a walkaround checker that reads your code, a flight recorder you can turn up or down, and crash investigators who look at the wreck instead of guessing. About 100 minutes, with 32 hands-on checks.

Part 1 · The checklist and its tablestests as checklist lines, and one test that checks a whole table of cases

1

Pip is in the cockpit for the first time. Before the engines start, the Professor hands over a clipboard.

Pip says: A checklist? I know how to fly! Well. I know how to fly in my head.

The Professor says: Pilots with thirty years of flying still read it, line by line, before every takeoff. Not because they're forgetful: because the list never is. In code, your takeoff is every time you save a change for good: a commit.

Chapter 14 built the first checklist lines: pytest, assert, edge cases, pytest.raises, approx, red-green-refactor and breakpoint(). This chapter turns them into a full preflight routine, then adds the tools real teams run around it.

    20
    
    A mechanic tests one instrument on the bench. Then the whole engine on a test stand. Then a real test flight. Tests come in the same sizes.
    
    
    
      
    END-TO-ENDthe whole program, run like a user would. Few, slow.
    
      
    INTEGRATIONseveral parts together: real files, a real database, modules calling modules.
    
      
    UNITone function or class on its own, often with fakes for the rest. Many, fast.
    
    
    
    
    
      
    test_trip.py
    
      
    
        
    test_parse_one_leg is a unit test: one function, one value. test_total_from_a_real_file is a small integration test: a real file, read and added up by two functions working together. (flightlog.py is Part 7's project.)
    
    
    
  
    

  
    
  

  
    
    21
    
    Which lines did your checks actually reach? That's coverage. Real projects use the third-party package coverage.py; the standard library's trace module shows the same idea with no install.
    
    
    
      
    fare.py
    
      
    
    
    
    
    
      
      
    Sneak whispers: The numbers count how often each line ran. >>>>>> marks a line that never ran: nobody tried a baby's fare. If that line had a bug, no check would ever see it.

    Part 5 · The walkaround inspectiona linter that reads for likely bugs, a formatter that tidies, docstrings that explain
    

  
    
    23
    
    Before boarding, someone walks around the plane looking for anything odd. Code gets the same walkaround, without running it. (This checker reads code habits; Chapter 21's Inspector, in the blue cap, checks type labels.)
    
    
    
      
    THE WALKAROUND CHECKERa linter: ruff check, flake8
    Reads your code and points at likely bugs and style slips: unused imports, a variable set but never used, == None, a list as a default argument. Like a spell-checker for code. It only reports.
    
      
    THE TIDY CREWa formatter: ruff format, black
    Rewrites the layout in one standard style: spaces, line breaks, quotes, blank lines. It never changes what the code does, and it never argues. Nobody has to debate commas again.
    
    
    
    
    Two cards. The walkaround checker is a proof-reading critter with big glasses. The tidy crew is a little robot with a broom.
    
    
    
      
      
    The Proofreader says: I only stop code Python can't read (Chapter 1). Code can pass me and still be untidy, or quietly wrong. PEP 8 (Chapter 14) is the style these tools enforce for you.
    
    
    
    
    This book uses ruff, one fast tool that does both jobs. flake8 (a linter) and black (a formatter) are older, popular choices that work the same way. Your editor can run them every time you save, and your type checker (Chapter 21) can sit beside them.

        •

    33
    
      A cousin of logging: the warnings module. Libraries use it to tell programmers (not users) that something should change, such as a function on its way out.
      
    
      
      
      warn_demo.py
      
      
      
    
      
    
        
      
      • A warning names its file, line and category: DeprecationWarning ("this will be removed"), UserWarning (the default), and others.
        • 
      
      • stacklevel=2 blames the line that called old_fuel_check (line 11), which is where the fix belongs.
        • 
      
      • The function ran three times, but the warning printed once: by default each warning is shown once per place in the code.
        • 
      
      • python3 -W error turns warnings into exceptions. Tests often run that way, so nothing deprecated slips through; pytest also lists warnings in a "warnings summary".
        • 
    
      
    
      Why are both warnings above 80 True? This run went through a pipe, and then Python holds ordinary output back until the program ends, while warnings (on the error stream) go out at once. In your own terminal the 80, 60 and 40 lines would appear between the two warnings. Chapter 14's SyntaxWarning about an always-true assert was a warning too, from the Proofreader.

    Under the hood: how pytest finds, injects and rewrites
    
        
      
      
        Collection, then running
        
      
        pytest works in two phases. Collection imports every test file and builds a list of test items: one per test function, one per parametrize row, one per TestCase method. Then it runs each item: it works out which fixtures the item needs (by parameter name, recursively, because fixtures can ask for other fixtures), sets them up, calls the test, and tears the fixtures down in the reverse order.
        
      
        Fixture scope
        
      
        A fixture is made fresh for every test by default (scope="function"). @pytest.fixture(scope="module") makes one per file and scope="session" one per whole run: useful for something slow, like starting a test database, but shared state is exactly how Panel 18's leftovers happen. Fixtures that every file needs go in a file called conftest.py; pytest finds them without any import. autouse=True makes a fixture apply to every test without being asked for.
        
      
        Why assert a == b shows both values
        
      
        A plain assert in Python just raises AssertionError. pytest rewrites the assert statements in test files as it imports them, adding code that records each side's value, which is how its reports can say assert 'B' == 'A' and draw diffs. That's also why pytest stores compiled test files in __pycache__ with its own tag.
        
      
        What a Mock is
        
      
        unittest.mock.Mock creates an object that accepts any attribute and any call, and remembers them all. MagicMock (what patch uses by default) also supports dunder methods such as len() and iteration (Chapter 20). mock.patch("tower.wind_speed") imports tower, saves the current value of its wind_speed attribute, sets a MagicMock in its place, and puts the original back when the with block (or decorated test) ends. Pass autospec=True and the fake also refuses calls with the wrong arguments, which catches tests that drifted away from the real function.
        
      
        How a logger decides
        
      
        Loggers form a tree by name: "pip.engine" is a child of "pip", which is a child of the root logger. A message is first checked against its own logger's level (or the nearest ancestor's that has one set). If it passes, it travels up the tree to every handler on the way; each handler can have its own level and format. basicConfig just adds one handler to the root logger. That's why Boss question 2's radio.debug was printed by root's handler, though root's own level was WARNING.
        
      
        How python -m pdb gets a post-mortem
        
      
        pdb runs your script inside a try. When an exception escapes, it prints the traceback and calls pdb.post_mortem() on the exception's traceback object, which still holds every frame and its local variables. You can do the same from your own code with pdb.post_mortem() inside an except block, or after a crash in the interactive prompt with import pdb; pdb.pm().
        
    
        
  
        

  
        
    In real programs: how teams run the preflight
    
        
      
          
        
        • A tests/ folder and one command. Real projects keep tests in tests/, with shared fixtures in tests/conftest.py, and configure pytest in pyproject.toml under [tool.pytest.ini_options] (this chapter's folder uses a tiny pytest.ini instead).
          • 
        
        • Markers. @pytest.mark.skip, @pytest.mark.skipif(sys.platform == "win32", reason=...) and @pytest.mark.xfail (expected to fail, for a known bug) show up as s and x in the marks. Teams also tag slow tests and run pytest -m "not slow" while working.
          • 
        
        • Readable ids. @pytest.mark.parametrize(..., ids=["short hop", "long haul"]) replaces the ids pytest makes from the values, like [5-A] in Panel 6, with names you choose. Two parametrize decorators stacked on one test run every combination.
          • 
        
        • Handy flags. -x stops at the first failure, -k fuel runs only tests whose names contain "fuel", --lf re-runs only the last failures, -v lists each test as it runs, --pdb opens pdb at every failure, and -W error turns warnings into failures.
          • 
        
        • Coverage in CI. Continuous-integration servers run coverage run -m pytest and often fail the build if coverage drops below a chosen percentage.
          • 
        
        • Linters and formatters in the editor. Most editors can run ruff on save; the ruff settings usually live in pyproject.toml under [tool.ruff]. A project picks one style and never discusses it again.
          • 
        
        • Logging configuration. Bigger programs configure logging from a dict or file with logging.config.dictConfig: several handlers (screen, file, a log server), different levels per module, timestamps on every line. Libraries add only logging.NullHandler() to their top logger, so they stay silent unless the program asks.
          • 
        
        • Debugging a running program. Since Python 3.14, python -m pdb -p PID can attach pdb to a Python process that's already running (with the right operating-system permissions).
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "Fixtures run once for the whole file." By default they run again for every test (Panel 8). Module and session scopes are opt-in.
          • 
        
        • "If a test fails, the teardown is skipped." Teardown after yield runs even when the test fails (Panel 9). Only a crash during setup skips it, because the fixture never reached yield.
          • 
        
        • "Patching a function patches it everywhere." A patch moves one name tag in one module. Other modules' tags, made by from ... import, still point at the original (Panel 16).
          • 
        
        • "A test that passes alone is fine." It must pass in the suite too, in any order (Panel 18).
          • 
        
        • "Mock everything." A test full of fakes can pass while the real pieces don't fit together. Fake the slow, random or outside parts; keep some integration tests with the real thing.
          • 
        
        • "100% coverage means no bugs." It means every line ran (Panel 21).
          • 
        
        • "A linter warning is just style." Some are real bugs, like the shared default list in Panel 24.
          • 
        
        • "logging.info is broken: nothing prints." The default dial is WARNING (Panel 28).
          • 
        
        • "I can call basicConfig whenever I like." Only before any other logging call, or with force=True (Panel 31).
          • 
        
        • "Log messages should be f-strings." Pass the values as arguments: log.info("saved %s files", n). The text is only built when the message is written, and log tools can group messages by their template.
          • 
        
        • "After a crash, c carries on." In post-mortem, c restarts the program from the top.

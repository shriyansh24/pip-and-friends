CHAPTER 21

LABELS AND SORTING CHUTES

Picture: two cardboard parcels with paper labels tied on, one labelled int and one labelled list[str]. Between them stands the Inspector, a new character in a blue peaked cap marked mypy, with round glasses, a magnifying glass and a clipboard.

Pip gets a job at the parcel depot. First: labels that say what each name should hold, so a sharp-eyed Inspector can catch mistakes before anything ships. Then: the sorting office, where each parcel is held up against a wall of shapes and slides down the chute of the first shape it fits. About 80 minutes, with 27 hands-on checks.

1

Pip's first day at the parcel depot. Every name tag gets a paper label saying what kind of parcel it should be tied to.

Pip says: This tag's label says int, so it should be tied to a whole number. That one says str: text. Easy!

The Professor says: Here's the twist. The label is on the tag, not the object, and Python never reads it. Tie the int-labelled tag to a sock and nothing complains. Labels are for people, and for the Inspector at the door.

2

Two different moments. Checking time: before anything ships, the Inspector reads every label and looks for mismatches. Running time: the delivery van (Python itself) moves parcels along and never looks at a label.

The Inspector says: I'm the Inspector. I read your whole program without running it and compare every label with what you actually put in. The best-known inspector for Python is a free tool called mypy.

Read mypy's report like a detective, just like a traceback. Each problem is one line with four parts, separated by colons.

    

      
WHEREdouble.py:5
File name, then line number. No running happened, so there is no "Traceback": just the spot.

      
HOW BADerror
error is a real problem. note lines add extra detail about the line above.

      
WHATthe sentence
Which argument (number 1), which function, what it got ("str") and what the label expected ("int").

      
WHICH RULE[arg-type]
The name of the check, in square brackets. Search it in mypy's docs for a longer explanation.

    

    
The last line is the summary: how many errors, in how many files. When everything matches, mypy says Success instead, as you'll see in Panel 12. The exact wording of messages changes a little between mypy versions; the four parts stay.

    Under the hood: lazy labels, how a pattern is checked, and the older spellings
    
      
      
      
      Labels are worked out lazily (Python 3.14 and newer)
      
      
      Since 3.14 (PEP 649 and PEP 749), the def line doesn't evaluate its labels. Python stores a small hidden function, __annotate__, and only runs it when someone asks for __annotations__. The new annotationlib module can even fetch labels as plain strings, without evaluating them. Below, Parcel doesn't exist anywhere. Defining the function is fine; only asking for the real values fails:
      
      nb_annotationlib.py
      
      
      
        
      CPython 3.15.2
      
        
      CPython 3.13.18
      
      
      
      
      Notice the frame called __annotate__ in the 3.15 traceback: that is the hidden function running at last. On 3.13 the module doesn't exist yet. Before 3.14 the usual way to delay labels was from __future__ import annotations, which turns every label into a string. It works on every version, and the strings show:
      
      
      
      
      How a pattern is checked
      
      
      Each pattern kind is a short list of tests, run in order until one fails:
      
      
        
        
      • Literal: subject == literal. The three special literals None, True and False are compared with is instead.
        • 
        
      • Value (a dotted name such as Color.RED): subject == Color.RED.
        • 
        
      • Sequence: is it a sequence (a list, tuple, range…, but not a str, bytes or bytearray)? Is its length right? Then each item against each sub-pattern.
        • 
        
      • Mapping: is it a mapping (such as a dict)? Does it have every named key? Then each value against its sub-pattern. Other keys are ignored unless you collect them with **rest.
        • 
        
      • Class: isinstance(subject, Cls), then each keyword attribute. Positional sub-patterns are translated to keywords using the class's __match_args__, a tuple of attribute names that dataclasses write for you. A plain class has none, so only keywords work:
        • 
      
      
      
      
      
      Why refuse strings in sequence patterns? Because a string is a sequence of characters, and case [a, b]: silently matching the two-letter word "go" would cause far more bugs than it saves:

      pyright is another free type checker (the same engine runs inside Pylance, the Python language support in VS Code). Same idea, different wording and a column number:

      Checkers don't always agree on the finer points, so a project picks one and runs it the same way every time. (Chapter 26's preflight checklist runs a linter and the tests that way; a type checker can join the list.)
      
    
      
  
      

  
      
    In real programs: where labels and match show up
    
      
      
        
        
      • Big codebases label almost every function and run a checker on every change. The checker finds the "this might be None" bugs that tests miss, and makes renaming things much safer.
        • 
        
      • Libraries ship labels so your editor can autocomplete. When a library has none, people publish separate label files called stubs (packages named types-…, such as types-requests).
        • 
        
      • Frameworks read labels at run time: @dataclass (Chapter 20) finds its fields in __annotations__, and web frameworks use labels to check and convert incoming data, often through Pydantic.
        • 
        
      • match shines when parsing commands (text adventures, chat bots, command-line tools), handling JSON messages from web services, and walking tree-shaped data such as the syntax trees of a compiler.
        • 
        
      • Protocols describe plug-in points without forcing a family tree: "anything with a write method" is how many standard-library functions think about files.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "Type hints make Python check types." Python stores them and moves on (Panels 5, 7 and 20). Only a separate tool checks them.
        • 
        
      • "If mypy says Success, my program has no bugs." mypy checks labels, not logic, and it skips anything labelled Any or left unlabelled (Panel 14).
        • 
        
      • "Optional[int] means the argument can be left out." It only means "int or None". Leaving an argument out needs a default value.
        • 
        
      • "case RED: compares with my variable RED." A bare name always captures (Panels 35–36). Use a dotted name or a literal.
        • 
        
      • "A match with no fitting case raises an error." Nothing happens: no case runs and the program carries on. Add case _: if you want to handle "anything else".
        • 
        
      • "case [a, b]: works on strings too." Sequence patterns refuse str, bytes and bytearray.
        • 
        
      • "A mapping pattern needs the exact same keys." Extra keys are ignored. A sequence pattern, by contrast, needs the exact length (unless it has a *star).
        • 
        
      • "Capture names only exist inside their case." They are ordinary variables, still there after the match, but only if their case fitted (boss level, last check).
        • 
        
      • "match is Python's switch." Other languages' switch statements compare values; match compares shapes and unpacks them. And there's no falling through.
        •

      • Type hints on functions: Python 3.0 (PEP 3107, PEP 484 in 3.5 gave them their meaning). On variables: 3.6 (PEP 526).
        • 
        
      • list[int] with built-in names: 3.9 (PEP 585). int | None: 3.10 (PEP 604).
        • 
        
      • match/case: 3.10 (PEPs 634, 635 and 636). Unary plus in literal patterns: 3.15 (Panel 39).
        • 
        
      • def first[T] and the type statement for aliases: 3.12 (PEP 695). Protocol and TypedDict: 3.8.
        • 
        
      • Lazy (deferred) annotations and the annotationlib module: 3.14 (PEPs 649 and 749).
        • 
        
      • The mypy versions here: 2.4.1 beside CPython 3.15.2 and 2.3.1 beside 3.13.18. Both printed identical reports for every program in this chapter. pyright 1.1.414 ran once, in the notebook.

    Words from this chapter
    
      
      
      
        
      type hint / annotation
      A label after a name (x: int) or after a function's brackets (-> str) saying what type should go there.
      
        
      return hint
      The -> type part: what a function gives back.
      
        
      static type checker
      A tool, such as mypy or pyright, that reads code without running it and compares values with labels. The Inspector.
      
        
      run time / check time
      While the program runs (Python, the conveyor) / before it runs (the Inspector).
      
        
      generic type
      A label with a slot for what's inside, such as list[int] or dict[str, int].
      
        
      union type
      "Either of these": int | str, or the older Union[int, str].
      
        
      optional (X | None)
      A value that might be None; older spelling Optional[X].
      
        
      narrowing
      A checker working out a more exact type inside a branch, for example after if x is None:.
      
        
      Any
      A label that switches checking off for that value.
      
        
      Callable
      The label for a function: Callable[[in types], out type].
      
        
      TypedDict
      A label for a dict with fixed keys, each with its own type.
      
        
      Protocol
      A label describing a shape ("has these methods"), checked without inheritance. Structural typing.
      
        
      type variable (T)
      A blank in a label that the checker fills in from how the function is used.
      
        
      forward reference
      A label naming something not defined yet, such as a class inside its own body. Quoted before 3.14.
      
        
      deferred evaluation
      Working out labels only when asked for (3.14 and newer).
      
        
      match / subject
      The statement that tries patterns against one value, the subject.
      
        
      case / pattern
      One shape to try, and the code to run when it fits.
      
        
      literal pattern
      A number, string, None, True or False; fits if equal.
      
        
      capture pattern
      A bare name; fits anything and ties the name to it.
      
        
      wildcard _
      Fits anything and ties no name.
      
        
      value pattern
      A dotted name such as Color.RED; fits if equal to that value.
      
        
      sequence pattern
      [a, b] or [first, *rest]: fits lists and tuples of the right length (never strings).
      
        
      mapping pattern
      {"key": pattern}: fits dicts that have those keys.
      
        
      class pattern
      Point(x=0) or int(): fits objects of that class with matching attributes.
      
        
      OR pattern
      p1 | p2: fits if any alternative fits.
      
        
      guard
      if condition after a pattern; the case runs only if it's True.
      
        
      as pattern
      pattern as name: ties a name to whatever fitted.
      
        
      __match_args__
      The attribute names a class pattern uses for positional sub-patterns.

New word: a test is a small piece of code that runs your code on an example whose answer you already know, and complains loudly if the answer is wrong.

        • 4 spaces per indent level.
          •

          •

          •

          •

          • 
      
        • lower_case_with_underscores for functions and variables (Chapter 2), ALL_CAPS for constants.
          •

          •

    Under the hood: how pytest finds, runs and explains tests
    
        
      
        Finding tests
        
      
        Given a folder (or nothing, meaning the current folder), pytest looks for files named test_*.py or *_test.py, in subfolders too. Inside them it collects functions whose names start with test, and classes whose names start with Test (Chapter 15 introduces classes; Chapter 26 uses them for tests). Giving a file name, as this chapter does, runs only that file.
        
      
        Running each test on its own
        
      
        pytest calls each test function inside its own safety net. An AssertionError, or any other exception, is caught, recorded as a failure for that test, and pytest moves on to the next one. That's why one failing test can't hide the others, unlike script_tests.py in Panel 3.
        
      
        Why pytest can show the values
        
      
        A plain assert that fails raises an AssertionError with no details (Panel 3 showed a bare AssertionError). When pytest imports a test file, it rewrites every assert in it so that, on failure, it reports the values on both sides of the comparison and the where lines. Your code doesn't change; pytest does the extra work.
        
      
        Exit codes
        
      
        pytest's exit code says how the run went: 0 all passed, 1 some failed, 2 interrupted, 3 internal error, 4 command-line mistake, 5 no tests collected. Code 5 is a classic surprise: here the only function is called check_clock, so pytest finds nothing to run.
        
      no_tests.py
        One possible run: the time on the last line changes every run
        
      
        python -m pytest or just pytest?
        
      
        Both run pytest. python -m pytest guarantees you get the pytest installed for that Python, for the same reason Chapter 13 typed python3 -m pip. Either way, test_scores.py can import scores, because pytest puts each test file's own folder on the import search path.     In real programs
    
        
      
        Tests live in their own folder
        
      
        Real projects keep tests in a tests/ folder and run all of them with one python -m pytest. Chapter 23 shows a full project layout, and Chapter 26 adds its tests/ folder.
        
      
        Robots run the tests
        
      
        Most teams use continuous integration (CI): every time someone sends a change, a server runs the whole test suite automatically. A red run blocks the change from being merged. Your exit code 0 or 1 is exactly what those robots read.
        
      
        Every bug gets a test
        
      
        When a bug is reported, the first step is a test that reproduces it (the boss level's last question). Fixed bugs then stay fixed: such a test is called a regression test.
        
      
        Docs that test themselves: doctest
        
      
        Python ships a module called doctest. It finds examples written like a Python prompt session inside docstrings, runs them, and checks the output. Here the docstring's second example catches the race-clock bug:
        
      doc_demo.py
        
      
        Silence would mean every example passed. doctest is great for keeping examples in docs honest; for real test suites, people use pytest (or the built-in unittest, Chapter 26).
        
      
        The Zen of Python
        
      
        PEP 20 is a short poem about Python's design taste. It's hidden inside Python itself:
        
      zen.py
        
      
        "Readability counts" is PEP 8 in two words. "Errors should never pass silently" is why alarms must ring.
        
      
        Tools that check style for you
        
      
        Nobody checks PEP 8 by eye. Formatters rewrite code into a standard style, and linters point out style problems and likely bugs. Chapter 26 sets them up.
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "My tests pass, so my code has no bugs." Tests only check the examples you wrote. Sneak hides in the cases nobody tested, like the empty list (Panel 11).
          • 
        
        • "A test that passes the first time is great news." Maybe. But a test you've never seen fail might not test anything (the stub's lucky green in Panel 33). Red first.
          • 
        
        • "assert (x == 1, "msg") checks x." It asserts a tuple, which is always true. Python warns with a SyntaxWarning (Panel 14).
          • 
        
        • "Floats can be compared with == in tests." 0.1 + 0.2 isn't exactly 0.3. Use pytest.approx or math.isclose.
          • 
        
        • "I can copy the expected value from what my function prints." Then the test just agrees with the bug. Work expected values out by hand.
          • 
        
        • "Testing means running the program and typing things in." That's manual testing: slow, boring and easy to forget. Automated tests repeat every check in a second.
          • 
        
        • "The debugger is for experts." Five commands (n s p c q) cover most debugging.
          • 
        
        • "sorted(nums) sorts nums." It returns a new list (Panel 31). nums.sort() sorts in place and returns None.
          • 
        
        • "PEP 8 is enforced by Python." Python happily runs messy.py. PEP 8 is for people.
          • 
        
        • "If the AI's code runs, it's right." Running and being right are different things. Test it like any other code.

    Words from this chapter
    
        
      
        
        
        test
        Code that runs your code on an example with a known answer, and fails loudly if the answer is wrong.
        
        
        pytest
        A popular package that finds and runs test functions and explains failures.
        
        
        test function
        A function whose name starts with test, in a file named test_*.py.
        
        
        arrange, act, assert
        The shape of a good test: set up, do one thing, check it.
        
        
        happy path
        The ordinary, expected example.
        
        
        edge case
        An unusual example at the border: empty, zero, negative, huge, exactly on a limit.
        
        
        pytest.raises
        with pytest.raises(ValueError): fails the test unless the block raises that exception.
        
        
        pytest.approx
        Compares floats "close enough": x == pytest.approx(0.3).
        
        
        math.isclose
        The standard library's "close enough" check for floats.
        
        
        diff
        A view of two texts showing what was removed (-) and added (+).
        
        
        stub
        A placeholder function that runs but doesn't do the real job yet.
        
        
        red, green, refactor
        Write a failing test, make it pass simply, then tidy the code with the tests still passing.
        
        
        refactor
        Change how code is written without changing what it does.
        
        
        regression test
        A test written for a fixed bug, so it can never come back unnoticed.
        
        
        debugger
        A tool that pauses a running program so you can look at values and run it a line at a time.
        
        
        breakpoint
        A place where the debugger pauses: breakpoint() in code, or a red dot in an editor.
        
        
        pdb
        Python's built-in debugger. Commands: n, s, p, c, q, and more.
        
        
        step over / into / out
        Run a line including its calls / go inside a call / finish the current function.
        
        
        signature
        A function's name and parameters, as the docs show them.
        
        
        / and * in a signature
        Markers: before /, arguments go by position only; after *, by name only.
        
        
        iterable
        Anything a for loop can walk through.
        
        
        PEP
        Python Enhancement Proposal: a design document for Python.
        
        
        PEP 8
        The style guide for Python code.
        
        
        pseudocode
        A plan written in code-shaped plain language.
        
        
        decomposition
        Splitting a problem into smaller problems, each one a function.
        
        
        incremental development
        Write a little, run, check, repeat.
        
        
        doctest
        A module that runs the examples inside docstrings and checks their output.

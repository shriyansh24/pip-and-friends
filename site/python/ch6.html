    Under the hood: objects, frames and UnboundLocalError
    
          
      
          def is an assignment
          
      
          def greet(): does two things: it builds a function object, and it ties the name greet to it, just like x = 5 ties x to an int. That's why the tracers draw greet as a name tag pointing at an object. It's also why a call before the def line is a NameError: the tag doesn't exist yet.
          
      
          Every call gets a fresh frame
          
      
          When you call a function, Python creates a new frame: a small table of local names. First it binds each parameter to its argument, exactly as if it ran name = "Ada". The parameter and the argument then point at the same object (Chapter 2's name tags). When the call ends, the frame is thrown away. The call expression is replaced by the returned object, or by None.
          
      
          Where Python looks for a name
          
      
          Inside a function, Python looks for a name in this order: the Local frame, any Enclosing function (for functions defined inside functions), the Global names of the file, then the Built-in names such as len and print. People call this the LEGB rule. It's also why naming your own variable len or max hides the built-in machine.
          
      
          UnboundLocalError: decided before the first line runs
          
      
          Python decides which names are local when it builds the function, not line by line. If a name is assigned anywhere in the body, it is local everywhere in the body. So this fails, even though a global count exists:
          
      
          
        
          unbound.py
          
        
          
      
          
      
          count = count + 1 makes count local, so the right-hand side reads the local count, which has no value yet. The traceback has two frames: line 8 in <module> made the call, and line 5 in add_one broke. Better fix than global: pass the value in and return the new one, count = add_one(count).
          
    
          
  
          

  
          
    In real programs: global, pure functions and main()
    
          
      
          The global statement, and why to avoid it
          
      
          global count inside a function says "assignments to count here change the global name". It works:
          
      
          
        
          global_kw.py
          
        
          
      
          
      
          But now any function anywhere can change count. When it has a wrong value, you have to search the whole program for the culprit. Real codebases use global rarely. Pass values in as arguments, and hand results back with return.
          
      
          Pure functions
          
      
          A pure function only uses its arguments and only gives back through return: same inputs, same output, every time, and nothing outside changes. Compare:
          
      
          
        
          pure.py
          
        
          
      
          
      
          add_to_total(5) gave two different answers for the same input, because it changes a global. add(0, 5) always gives 5. Pure functions are easy to test, easy to reuse, and safe to call in any order. Printing, reading input and changing globals are called side effects. Programs need some, but keep them in a few clearly named places.
          
      
          The main() habit
          
      
          Bigger scripts often put their top-level steps in a function called main and finish the file with if __name__ == "__main__": followed by an indented main() call. The if line means "only when this file is run directly, not when another file imports it". You'll meet imports later. For now, know the pattern when you see it.
          
      
          Small machines, good names
          
      
          Name a function after what it does, often with a verb: show_fahrenheit, is_even, count_vowels. If you can't name it in a few words, it probably does too much. Split it into smaller machines.
          
    
          
  
          

  
          
    Common wrong ideas
    
          
      
            
        
          • "def runs the code." It only builds the machine. Nothing in the body runs until a call.
            • 
        
          • "return prints the value." It doesn't. It hands the value back to the caller. In the interactive >>> prompt a bare call shows its value, which adds to the confusion. A script shows nothing unless you print it.
            • 
        
          • "A function without return gives back nothing." It gives back None, which is a real object you can store and print.
            • 
        
          • "The argument's name must match the parameter's name." No. greet(friend) works fine with def greet(name).
            • 
        
          • "Assigning to a name inside a function changes the outside one." It makes a new local name instead (see shadow.py in the exercises).
            • 
        
          • "round always rounds .5 up." Python rounds an exact half to the even neighbour: round(2.5) is 2.
            • 
        
          • "Code after return still runs." return leaves the function at once.
            • 
        
          • "Presets can go anywhere." A slot without a preset can't come after one with a preset, and in a call a positional argument can't come after a keyword one. Both are caught before anything runs:
            • 
      
          
      
          
        
          default_order.py
          
        
          keyword_first.py
          
      
          
      
          One more for later, when you meet lists: a preset is built once, when the def runs, and not again on every call. With a changeable preset like a list, every call shares the same one. The official tutorial calls this an "important warning". Use None as the preset and build the list inside.

    Words from this chapter
    
          
      
          
        
          function
          A named, reusable block of code: Pip's "machine".
          
        
          def
          The keyword that defines (builds) a function. It doesn't run the body.
          
        
          call
          Running a function by writing its name followed by parentheses: greet("Ada").
          
        
          body
          The indented lines under the def line.
          
        
          parameter
          A name in the def line's parentheses: the label on an input slot.
          
        
          argument
          A value passed in a call, which fills a parameter.
          
        
          positional argument
          An argument matched to a slot by its position.
          
        
          keyword argument
          An argument matched to a slot by name: greeting="Hi".
          
        
          default (preset)
          A value given to a parameter in the def, used when the call leaves it out.
          
        
          return value
          The value a call hands back. None if there is no return.
          
        
          None
          Python's "nothing here" value, the only value of type NoneType.
          
        
          docstring
          A string on the first line of a function's body that describes it. Python keeps it for help().
          
        
          frame
          The private workspace of one running call, holding its local names.
          
        
          call stack
          The pile of frames for all calls currently running. The newest is the one running now.
          
        
          local name
          A name created inside a function, parameters included. It exists only during the call.
          
        
          global name
          A name created at the top level of a file.
          
        
          scope
          The part of a program where a name can be used.
          
        
          built-in function
          A function that comes with Python: print, len, round, max, abs…
          
        
          refactoring
          Changing how code is organised without changing what it does.
          
        
          DRY
          "Don't Repeat Yourself": put each piece of knowledge in one place.
          
        
          pure function
          A function whose result depends only on its arguments and that changes nothing outside itself.
          
        
          side effect
          Anything a function does besides returning a value: printing, changing a global, writing a file.
          
        
          TypeError
          A value of the wrong kind for an operation, or the wrong number of arguments for a function.
          
        
          UnboundLocalError
          A local name was read before the function gave it a value.

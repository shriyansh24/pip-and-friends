CHAPTER 26 · INTERMEDIATE

WALKIE-TALKIES AND WAITERS

Picture: Scoot, the bike courier in a red cap and green jacket, cheers between a yellow walkie-talkie labelled HQ and Wes the waiter, who holds up a covered plate.

Your goroutines can now work side by side. Today they get walkie-talkies: Go's context package, which lets one part of a program tell every helper it started to stop, and which gives slow jobs a time limit. Then we open a restaurant: you'll write a web server whose host reads each order and seats it with the right waiter, test it without any network, and visit it as a customer with a timeout of your own. Along the way: context deadline exceeded, 405 Method Not Allowed, and the one-word bug that serves a customer two answers at once. About 150 minutes, with 25 hands-on checks.

  1. HQ calls it off: context and cancel
  2. Running out of time: timeouts, deadlines and the family tree
  3. Radio discipline: the mistakes the Compiler and vet catch
  4. The restaurant: handlers, the host and the waiters
  5. Eating out: clients, timeouts and middleware
  6. Boss level and recap

PART 1 · HQ CALLS IT OFFcontext.Background, WithCancel, Done and Err

1

Monday at the depot. Scoot has just sent three couriers across town to collect a big order. Then the phone rings.

The Professor says: The customer cancelled! Call your couriers back before they waste the whole afternoon.

Scoot says: Call them how? They're three streets away, and one of them sent a helper of their own! I can't shout that far.

Picture: the Professor holds a phone and points at the door. Scoot shrugs, worried.

2

The fix: before anyone leaves, HQ hands each courier a walkie-talkie tuned to its channel. Couriers who send helpers hand them a walkie-talkie too, tuned to theirs. When HQ presses the big ABORT button, every radio on the network crackles at once.

THE RADIO

a context.Contextone per job, passed along

A small value you hand to every function doing a piece of the job. It doesn't carry the work; it carries news about the work: “stop now”, and “you have until 9:30”.

THE BUTTON

cancel()only the one who made the radio has it

Pressing it closes the radio's Done channel. Everyone listening hears it, and so does every radio handed out further down the line.

Scoot says: Catchphrase: HQ says abort, and every radio on the channel hears it. In Go, the network is the context package, from the standard library. People just say “ctx” (say “context”).

3

Four new names. context.Background() is the base station: an empty context that is never cancelled. context.WithCancel(parent) makes a new radio tuned to the parent, and returns two values: the new context, and its cancel function. ctx.Done() returns a channel that closes on abort. ctx.Err() says why it closed, or nil if it hasn't.

    7
    
    One rule with no exceptions: every cancel function you get, you call, even when the job finishes normally. A context keeps a little bookkeeping alive (a link from its parent, and for timeouts a running timer) until it is cancelled. The easy way is to write defer cancel() on the very next line.
    
    
    
      
    DOctx, cancel := context.WithTimeout(
    parent, time.Second)
defer cancel()

    DON'Tctx, _ := context.WithTimeout(
    parent, time.Second)

    PART 2 · RUNNING OUT OF TIMEWithTimeout, WithDeadline, ctx first, and the family tree
    

  
    
    8
    
    Most aborts aren't a person pressing a button. They're a clock. The context package has two kinds, and both press the button for you when the time comes.
    
    
    
      
    
        TIMEOUT
        
        
    WithTimeout(parent, 50*time.Millisecond)“give up 50 ms from now”
    
        
    A kitchen timer: a length of time, counted from the moment you make it.
    
      
    
      
    
        DEADLINE
        
        
    WithDeadline(parent, closingTime)“give up at 22:00”
    
        
    A closing time: a moment on the clock, a time.Time. WithTimeout(p, d) is just WithDeadline(p, time.Now().Add(d)).
    
      
    
    
    
    
    When the time comes, Err() gives a different reason from a pressed button: context deadline exceeded, the error value context.DeadlineExceeded. You still get a cancel function, and you still call it: pressing it early, when the job finishes in time, stops the timer.
    
  
    

  
    
    9
    
    The stew takes 2 seconds (time.After from chapter 24 stands in for slow work). Scoot will only wait 50 milliseconds. Whichever door opens first wins the select.
    
    timeout.go
    
    
    
    
    
    
      
      
    Scoot says: After 50 ms the timer closes Done, so that case wins: gave up waiting. Then errors.Is (chapter 19) confirms the reason is context.DeadlineExceeded: true. The 50 ms against 2 s gap is huge on purpose, so the same door wins on every run.
    
    
    
  
    

  
    
    10
    
    The same idea with a clock time. ctx.Deadline() tells a function how long it has: the time, and true, if a deadline is set; false if not.
    
    deadline.go
    
    
    
    
    
    Line 19 waits until closing time; the last line checks that Done closed at the deadline, never before it. Background has no deadline, so its ok is false.
    
  
    

  
    
  

  
    
    11
    
    Real programs don't put the select in main. They write functions that accept a context and respect it. Here cook takes as long as a dish needs, unless its radio says stop. One context gives the whole meal a 300 ms budget.
    
    cook.go
    
    
    
    
    
    
      
      
    Scoot says: Toast fits. The stew needs 2 s, so at 300 ms the budget runs out and cook returns early with the reason wrapped in %w. Tea would take 10 ms, but the budget is already spent, so it fails at once. Catchphrase: ctx goes first.
    
    
    
    
      
      
    1. A function that might be slow takes ctx context.Context as its first parameter, named ctx.
      2. 
      
    2. It passes that same ctx (or a context made from it) to everything it calls.
      3. 
      
    3. It watches ctx.Done() while it waits, and returns ctx.Err() (wrapped is fine) when told to stop.
      4. 
      
    4. It never stores the ctx for later (part 3 shows why).
      5. 
    
    
  
    

  
    
  

  
    
  

  
    
    12
    
    Every context except Background is made from a parent, so contexts form a family tree. Two rules make the whole package work.
    
    
    
    
    
      
      
    The Professor says: Rule 1: cancelling a context cancels all its children, grandchildren and so on, immediately. Rule 2: it never touches its parent or its brothers and sisters. A child can also be stricter than its parent, with a shorter timeout, but never looser: if the parent stops, the child stops too.

    15
    
      Err() only ever says “canceled” or “deadline exceeded”. Since Go 1.20 you can attach your own reason: WithCancelCause gives a button that takes an error, and context.Cause(ctx) reads it back.
      
    cause.go
    
      
    
      
    
      Err() stays the standard value, so code that checks errors.Is(err, context.Canceled) keeps working; Cause gives the detail. For a context with no cause, Cause returns the same as Err(). There are also WithTimeoutCause and WithDeadlineCause. Good to know they exist; most code never needs them.
      
  
      

  
      
    16
    
      A context can also carry a few values along the chain, like an order ticket number pinned to the radio. WithValue(parent, key, value) makes a child holding one; ctx.Value(key) looks it up, asking the parent if the child doesn't have it.
      
    values.go
    
      
    
      
    
      
      
      
      The Professor says: Use values sparingly: only for facts about the request itself that cross many calls, such as a request ID for the logs. Never for ordinary inputs a function needs: those belong in its parameters, where the Compiler checks them. Value returns any (it can be missing: the pie got nil), so you need the comma-ok type assertion of line 11 (chapter 14). The key is a private empty struct type, ticketKey, so no other package can clash with it.
      
    
      
  
      

  
  
      PART 3 · RADIO DISCIPLINEthe forgotten button, the thrown-away button, and the radio in a drawer
      

  
      
    17
    
    
      Mistake one: make a context and forget its button completely.
      
    forgot_cancel.go
    
      
    
      
    
      
      
      
      The Compiler says: Nothing runs until everything checks out. Line 10, column 7: cancel is declared and not used. You asked for the button and never pressed it. Add defer cancel() on line 11.
      
    
      
    
      Go's famous “declared and not used” rule (chapter 3) turns out to be a lifesaver here. Read it like a detective: the file, then line 10, column 7, which is where the name cancel starts.
      
  
      

  
      
    18
    
      Mistake two, the sneaky version: silence the Compiler by throwing the button into the blank identifier _. It compiles. It runs. And it's still a leak. This terminal session runs the program, then go vet (Specs, chapter 2's proof-reader), which checks for mistakes the Compiler allows.
      
    lostcancel.go
    
      
    
      
    
      
      
      
      Specs says: Line 10, column 7: the cancel function returned by context.WithTimeout should be called, not discarded, to avoid a context leak. That's my lostcancel check. go test doesn't run it for you, so run go vet ./... before you commit.
      
    
      
    
      A context leak: the context and its timer stay alive, and its parent keeps it in its list of children, until the timeout fires. With WithCancel, which has no timer, that's for ever. One leak is small; one per web request adds up. go vet exits with status 1 when it finds something; go run was happy.
      
    
      Tests won't save you here either. The same mistake in a tiny package, kitchen, with a test that passes:
      
    kitchen/kitchen.go
    
      
    kitchen/kitchen_test.go
    
      
    
      One possible run: the time at the end of the ok line changes from run to run. -count=1 makes go test really run the test instead of reusing a result it remembers.
      
    
      
    
      go test runs only a few of vet's checks by itself, and lostcancel isn't one of them, so the test passes with no warning. Plain go vet . finds the thrown-away button on line 11.
      
  
      

  
      
  

  
      
    19
    
      Mistake three: storing a context in a struct. The oven below keeps the radio it was given at startup in a field, and uses it for every bake. The fix, PASSED TO EACH CALL, takes a fresh ctx as the first parameter of each call.
      
    
      
      
      STORED IN THE STRUCT
      ctx_struct.go
      
      
      PASSED TO EACH CALL
      ctx_param.go
      
    
      
    
      
      
      
      Scoot says: The cake failed even though it's a brand-new bake! The oven was still listening to a radio from 200 ms ago, whose time had run out. A context belongs to one job, not to an object that lives for many jobs. Don't put the radio in a drawer: ctx goes first, in every call.
      
    
      
    
      No tool flags this one: it compiles, vet is quiet, and the program misbehaves only later. The Go team's guidance in the context documentation says it plainly: do not store contexts inside a struct type; pass a context explicitly to each function that needs it.
      
  
      

  
      
  

  
  
      PART 4 · THE RESTAURANThandlers, status codes, ServeMux patterns and httptest
      

  
      
    20
    
      The depot opens a restaurant next door, and it runs exactly like the web. A client (a browser, an app, another program) is a customer. A server is the restaurant: a program that waits for orders and answers each one. The language they speak is HTTP.
      
    
      
      
      Hana says: I'm Hana, the host. Every order that comes in, I read two things: what kind of order it is, and which table it's for. Then I send it to the right waiter. In Go, I'm a ServeMux.
      
      
    
      
    
      
      
      
      Wes says: And I'm Wes, a waiter. I take one kind of order, get it made in the kitchen, and bring back a plate with a status code on its label. In Go, a waiter is a handler.
      
    
      
    
      
      
      
    
      
    
      Picture: Hana, a host with a dark bob, a purple waistcoat and a bow tie, points to a table, holding a red menu. Wes, a waiter in a black waistcoat with a towel over his arm, writes on a notepad. Behind them two kitchen helpers cook.
      
  
      

  
      
    21
    
      Every visit is one request (the order ticket the customer hands in) and one response (the plate that comes back).
      
    
      
      
      
        
      REQUEST · the order ticket
      
        
      
          
      METHOD
      what kind of order: GET (bring me something), POST (here's something new), PUT, DELETE…
      
          
      PATH
      which table: /hello/gopher, /orders
      
          
      HEADERS
      notes in the margin, like Content-Type: application/json
      
          
      BODY
      optional: the order itself, for example some JSON
      
        
      
      
      
      
      
        
      RESPONSE · the plate
      
        
      
          
      STATUS
      a three-digit code on the plate's label: 200 OK, 404 not found…
      
          
      HEADERS
      labels on the plate, like Content-Type: text/plain
      
          
      BODY
      the food: text, HTML, JSON or a picture
      
        
      
      
      
    
      
    
      The first digit of the status code says who's happy:
      
    
      
      
      2xx ✓it worked: 200 OK, 201 Created
      
      
      3xx ↪look somewhere else: 301 Moved
      
      
      4xx ✎the customer's mistake: 400, 401, 404, 405
      
      
      5xx ✖the kitchen's mistake: 500
      
    
      
  
      

  
      
    22

      PART 5 · EATING OUThttp.Get, closing bodies, timeouts, contexts and middleware
      

  
      
    32
    
      So far a pretend customer ate at a pretend table. Now Scoot visits a real restaurant, over a real network connection. httptest.NewServer(handler) opens one on your own computer, at a random free port (a numbered door on a computer), and gives its address in srv.URL.
      
    
      
      
      
      Scoot says: The address looks like http://127.0.0.1: plus a port number that changes on every run, so this book never prints it. 127.0.0.1 means “this same computer”: no internet needed, and nothing leaves the machine.
      
    
      
    
      
      
      Hana says: Same host, same waiters, a real front door. And always a defer srv.Close() to lock up afterwards.
      
      
    
      
  
      

  
      
    33
    
      http.Get(url) sends a GET and returns a *http.Response and an error. The body is a stream (an io.ReadCloser, chapter 19): you read it, here all at once with io.ReadAll, and then you close it.
      
    client_get.go
    
      
    
      
    
      
      
      
      Scoot says: resp.Status is the code and its name, 200 OK; resp.StatusCode is just the number. Nobody set a Content-Type, so the server sniffed the body and labelled it text/plain; charset=utf-8. Catchphrase: finished your plate? Give it back: defer resp.Body.Close().
      
    
      
    
      Why close? The connection to the server can be reused for your next order, but only once the body is closed. A program that forgets keeps connections and memory tied up, and a long-running one eventually runs out. Close it right after checking the error, with defer. (The response also has a Date header that changes every second; this book never prints it.)
      
  
      

  
      
  

  
      
    34
    
      Mistake: put the defer before the error check. If the request fails, resp is nil, and resp.Body crashes. This session runs go vet first, then the program, aimed at port 0, where no restaurant can ever be.
      
    resp_vet.go
    
      
    
      
    
      
      
      
      go vet says: Line 12: using resp before checking for errors. That's my httpresponse check, and it caught the crash before it happened.
      
    
      
    
      The run proves vet right. Read it like a detective: panic: runtime error: invalid memory address or nil pointer dereference, in goroutine 1, at main.fetch(), resp_vet.go:12. defer evaluates resp.Body immediately, while resp is still nil. The rule: check err first, then defer the close.
      
  
      

  
      
    35
    
      A surprise for many beginners: if the server answers at all, even with 404 or 500, http.Get returns err == nil. An error only means “no answer came back”: no connection, a timeout, a broken reply. This server has an empty host, so every path is 404.
      
    client_404.go
    
      
    
      
    
      
      
      
      Scoot says: The waiter came back and said “we don't have that”. That's an answer, not a lost order. So always check both: err for “did anyone answer?”, and resp.StatusCode for “what did they say?”.
      
    
      
  
      

  
      
    36
    
      http.Get uses http.DefaultClient, and the default client has no timeout at all. If a server accepts the order and never serves it, your program waits for ever. Make your own client with a Timeout. Here the kitchen would take 5 seconds; the customer waits 200 ms.
      
    client_timeout.go
    
      
    
      
    
      
      
      
      Scoot says: Client errors are *url.Error values, so errors.As (chapter 19) can open them: the operation was a Get, it was a timeout, and the reason inside is a context deadline exceeded. The whole error message would include the random port, so the program prints only the parts that never change.
      
    
      
    
      Look at the last line: the server noticed too. Every incoming request carries a context, r.Context(), which is cancelled when the customer goes away. A good handler listens to it (line 18) and stops cooking for nobody. Walkie-talkies, on both sides of the counter. The kitchen's message travels through a channel so it prints in the same place on every run.
      
  
      

  
      
  

  
      
    37
    
      The walkie-talkie way: http.NewRequestWithContext, called with ctx, a method, a URL and a body, builds a request that carries a context, and client.Do(req) sends it. When the context is cancelled or its time runs out, the request is abandoned. Unlike a client's fixed Timeout, the context can come from your caller, so the deadline of the whole job reaches the network call.
      
    client_ctx.go
    
      
    
      
    
      The error Do returns wraps the context's reason, so errors.Is(err, context.DeadlineExceeded) is true. In a server, pass r.Context() (or a context made from it) to the calls a handler makes, and the whole chain stops when the customer leaves.

    Under the hood: how cancellation travels, and what a server does with each order
    
      
      
      What a context really is
      
      
      context.Context is an interface with four methods: Deadline(), Done(), Err() and Value(key). Background is an empty implementation that never closes. WithCancel returns a small struct (the runtime calls it a cancelCtx) holding a pointer to its parent, a lazily made done channel, the error, and a set of its children. WithTimeout and WithDeadline wrap one of those with a timer (timerCtx), and WithValue makes a link that holds one key and value and forwards everything else to its parent (valueCtx). That's why Value lookups walk up the chain one link at a time: fine for a few values, slow for many.
      
      
      How cancellation reaches every child
      
      
      When a child is made, it registers itself in its nearest cancellable ancestor's children set. cancel() takes a lock, sets the error, closes the done channel, then calls cancel on every child, recursively, and finally removes itself from its parent's set. All of that happens inside the call, which is why panel 14's radios all changed at once. Calling cancel is what removes the child from its parent's set; forgetting it is what “context leak” means: the parent keeps the child (and its timer) alive.
      
      
      If a parent isn't one of the standard types, the package starts a goroutine to watch the parent's Done channel instead. Since Go 1.21, context.AfterFunc(ctx, f) runs f in its own goroutine once ctx is done, for cleanup that must happen on cancellation.
      
      
      Closing, not sending
      
      
      Done is closed rather than sent on because a close wakes every receiver, present and future, and costs nothing per listener. A context never needs to know who is listening. The flip side is that the context can't force anything: a goroutine that never looks at Done carries on regardless. Cancellation in Go is always cooperative.
      
      
      What the server does with each order
      
      
      http.Server accepts connections in a loop and runs each connection in its own goroutine (chapter 24's helpers), so one slow customer never holds up the others. For every request it builds an *http.Request whose context is cancelled when the client's connection closes or when ServeHTTP returns (panel 39). Your handler may run on many goroutines at the same time, so any data it shares needs chapter 25's locks.
      
      
      If a handler panics, the server recovers, logs http: panic serving … and closes that connection, rather than crashing the whole program. A ResponseWriter buffers the first few kilobytes; the status line and headers go out when the buffer fills, when you call WriteHeader or Flush, or when the handler returns. After that, a second WriteHeader can only be logged as “superfluous”.
      
      
      How the mux chooses
      
      
      Since Go 1.22 a pattern is [METHOD ][HOST]/[PATH]. If two patterns both match a request, the one that matches a strict subset of the other's requests wins: /dishes/special beats /dishes/{id}. If neither is more specific (say /a/{x} and /{y}/b), registering the second one panics at startup with a message naming both, so conflicts are found before any customer arrives. A pattern ending in a slash, like /static/, matches everything below it; {$} at the end matches only the exact path. A GET pattern also answers HEAD. Setting GODEBUG=httpmuxgo121=1 restores the old, method-less rules.
      
    
      
  
      

  
      
    In real programs: where radios and restaurants show up
    
      
      
        
        
      • Every request has a deadline. Servers set limits on the http.Server itself (ReadHeaderTimeout, ReadTimeout, WriteTimeout, IdleTimeout), and handlers pass r.Context() into database and network calls, so an abandoned request stops costing anything.
        • 
        
      • Graceful shutdown. srv.Shutdown(ctx) stops accepting new customers, lets current orders finish, and gives up when ctx expires. Chapter 27 pairs it with signal.NotifyContext, which turns Ctrl+C into a cancelled context.
        • 
        
      • Database calls. database/sql has QueryContext, ExecContext and friends; many other libraries take a ctx first, exactly like panel 11's cook.
        • 
        
      • Fan-out with a shared deadline. A search page might ask three services at once with one context; when the first error or the deadline arrives, cancelling the context stops the other two. The errgroup package from chapter 25 does this with errgroup.WithContext.
        • 
        
      • Middleware everywhere. Logging, request IDs (often stored with context.WithValue), authentication, panic recovery, compression and rate limiting are usually middleware, stacked like panel 38.
        • 
        
      • Testing handlers. httptest.NewRecorder in unit tests (chapter 23's table-driven style works well: method, path, want status, want body) and httptest.NewServer for testing your HTTP clients against a fake service.
        • 
        
      • Frameworks. Since Go 1.22's patterns, many small and medium services use the standard ServeMux directly; routers such as chi stay close to the same http.Handler interface, so everything in this chapter carries over.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • “Cancelling a context stops the goroutines using it.” It only closes a channel. Each goroutine must watch Done and return.
        • 
        
      • “If the job finished, I don't need to call cancel.” You do: calling it releases the context's place in its parent and its timer. defer cancel().
        • 
        
      • “Cancelling a child tells the parent.” Cancellation flows down only.
        • 
        
      • “A child with a longer timeout outlives its parent.” It stops when its parent stops, whichever comes first.
        • 
        
      • “context.Value is a handy way to pass parameters.” Only for request-scoped facts like an ID. Inputs go in parameters, where types are checked.
        • 
        
      • “I'll keep the context in my struct to save typing.” Panel 19. Pass it to each call.
        • 
        
      • “http.Error ends the handler.” It writes; you still need return.
        • 
        
      • “http.Get returns an error for a 404.” Only for no answer at all. Check StatusCode.
        • 
        
      • “Go's HTTP client times out by itself.” The default client never does.
        • 
        
      • “I only need to close the body if I read it.” Close it whenever err is nil, read or not.
        • 
        
      • “The order I register patterns in decides who wins.” The most specific pattern wins, whatever the order; true conflicts panic at registration.
        • 
        
      • “r.Context() is fine for work that continues after the response.” It's cancelled when the handler returns. Use context.WithoutCancel, with a timeout of its own.

    Words from this chapter
    
      
      
      
        
      context (context.Context)
      A value passed through a program that carries cancellation, a deadline, and a few request-scoped values.
      
        
      context.Background()
      The empty root context: never cancelled, no deadline, no values.
      
        
      cancel function
      The function returned by WithCancel, WithTimeout or WithDeadline that cancels the new context. Always call it, usually with defer.
      
        
      ctx.Done()
      A channel that is closed when the context is cancelled or times out.
      
        
      ctx.Err()
      nil while the context is live; afterwards context.Canceled or context.DeadlineExceeded.
      
        
      timeout, deadline
      A length of time from now, or a moment on the clock, after which a context is cancelled automatically.
      
        
      parent, child context
      A context made from another; cancelling a parent cancels its children, never the reverse.
      
        
      context leak
      A context whose cancel function is never called, so it and its timer stay alive longer than needed.
      
        
      context.Cause
      Reads the error given to a WithCancelCause cancel function (or a timeout's cause).
      
        
      context.WithoutCancel
      Makes a child that keeps its parent's values but is never cancelled by it.
      
        
      HTTP
      The protocol browsers and servers use: a request goes out, a response comes back.
      
        
      client, server
      The program that sends requests (the customer), and the program that answers them (the restaurant).
      
        
      request, response
      The order ticket (method, path, headers, body) and the plate (status code, headers, body).
      
        
      method
      What kind of request: GET, POST, PUT, DELETE, HEAD and others.
      
        
      path
      The part of a web address after the host and port, like /hello/gopher.
      
        
      status code
      A three-digit number saying how a request went: 2xx success, 3xx elsewhere, 4xx client's mistake, 5xx server's mistake.
      
        
      header
      A named note on a request or response, like Content-Type or Allow.
      
        
      handler
      Anything with a ServeHTTP(w, r) method; also a function of that shape, through http.HandlerFunc.
      
        
      ServeMux (mux)
      A request router: it matches each request's method and path against patterns and calls the matching handler.
      
        
      pattern, wildcard
      A routing rule like "GET /hello/{name}"; {name} matches one path segment, {rest...} the remainder.
      
        
      httptest
      The standard package for testing HTTP code: NewRequest, NewRecorder, and NewServer for a real local server.
      
        
      port
      A numbered door on a computer that a server listens on, like 8080.
      
        
      JSON API
      A server whose requests and responses carry JSON for other programs to read.
      
        
      middleware
      A function that wraps a handler with extra work before and after it, returning a new handler.

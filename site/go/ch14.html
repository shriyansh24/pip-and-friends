CHAPTER 14

PLUGS AND STICKY NOTES

Picture: Scoot, the bike courier in a red cap and green jacket, waves hello.

Last chapter, types got their own verbs: methods. This chapter asks a bigger question: what if a function doesn't care what something is, only what it can do? That's an interface, and it works like a wall socket: anything with the right plug fits, no paperwork needed. Then Scoot sticks notes on the door for the way out (defer), reads and writes real files, and learns when a program should panic. About 120 minutes, with 31 hands-on checks.

  1. The wall socket: interfaces
  2. One socket, many plugs: interface values and pointer receivers
  3. Sockets Go already has: Stringer, error and any
  4. Opening the mystery box: type assertions and type switches
  5. Sticky notes on the door: defer
  6. Files, and panicking on purpose
  7. Boss level and recap

PART 1 · THE WALL SOCKETInterfaces: a type described by what it can do

1

Back at the depot, Scoot plugs things into the charging wall: a phone, a bike lamp, the kettle for tea.

Scoot says: Funny thing. The socket never asks "are you a phone?" or "are you a kettle?". It doesn't care what the thing is.

Scoot says: It only cares whether the thing has the right plug. Right plug? It fits. No forms to fill in, no list of approved devices.

Picture: Scoot, focused, points at the wall.

2

Go has sockets too. An interface is a type that lists methods (chapter 13's verbs). Any type that has every method on the list fits, automatically.

  1. 1The socket is the interface type, here called Speaker.
  2. 2Its slots are a method list: here just one, Speak() string.
  3. 3A type whose methods match the list fits. Dog and Robot both have Speak() string.
  4. 4Cat only has Meow(). Wrong plug: it doesn't fit.

Scoot says: Catchphrase: right plug, it fits. No paperwork.

3

    14

    PART 5 · STICKY NOTES ON THE DOORdefer: do this on the way out
    

  
    
    25
    
    Morning at the depot. Scoot unlocks, switches the lights on and lets the cat in. Then a thought: tonight all of that has to be undone, in reverse.
    
    
    
      
      
    
        
    Scoot says: I'll forget by tonight. So each time I start something, I stick a note on the inside of the door: "lock the door". Then "switch off the lights". Then "feed the cat".
    
        
    Scoot says: On the way out I read them from the top. The last note I stuck is the first one I do.
    
      
    
    
    
    
    Picture: Scoot points at the door.
    
  
    

  
    
    26
    
    Go has exactly this. Put the word defer in front of a function call, and the call isn't made now: it's written on a note and stuck on the door of the function you're in. When that function finishes, the notes are done last stuck, first done.
    
    
    
    
      
      
    Scoot says: Catchphrase: last stuck, first done. Programmers call a pile like this a stack: you only ever add to the top, or take from the top.

      2. 
      
    2. Lines 8 and 9 run as usual. Then main reaches its closing brace, and on the way out the note is done: lock the door.
      3.

    32
    
        A function can leave by its closing brace or by any return. The notes are done either way. That's the whole point: stick the note once, and every way out is covered.
        
    defer_return.go

          3.

        PART 6 · FILES, AND PANICKING ON PURPOSEos.WriteFile, os.ReadFile, os.Open with bufio.Scanner, os.Create, panic and a first look at recover
        

  
        
    33
    
        Every program so far forgot everything the moment it ended. Scoot wants a logbook that's still there tomorrow: a file.
        
    
        
      
      
        
        
        Scoot says: A file is a named bundle of bytes on the disk. The os package (short for operating system) is the counter where you ask for one.
        
        
        Scoot says: And asking can fail: no such file, no permission, disk full. So every file function hands back a receipt, an error. Chapter 8's habit, everywhere.
        
      
        
    
        
    
        Picture: Scoot points ahead, smiling.
        
  
        

  
        
    34
    
        The simplest pair: write a whole file in one go, read a whole file in one go.
        
    write_read.go
    
        
    
        
    
          
      
        1. os.WriteFile("hello.txt", []byte(note), 0644) (line 10)
          Creates the file (or empties an old one) and writes the bytes. []byte(note) turns the string into bytes (chapter 11). 0644 sets who may read and write the file on Linux and macOS: you may write, everyone may read. Just copy it for now.
          2. 
      
        2. data, err := os.ReadFile("hello.txt") (line 15)
          The whole file as a []byte, plus a receipt. string(data) turns it back into text.
          3. 
      
        3. 26 bytes
          14 + 1 newline + 10 + 1 newline. And cat hello.txt (a standard Linux and macOS command that prints a file) proves the file really is on the disk after the program ended.
          4. 
      
        4. Where is hello.txt? In the folder you ran the program from. A file name with no folder in it is relative to that folder.
          5. 
    
        
  
        

  
        
    35
    
        Ask for a file that doesn't exist:
        
    read_missing.go
    
        
    
        
    
          
      
        1. open nope.txt: no such file or directory
          No crash: just a receipt that isn't empty. It says what was tried (open), on what (nope.txt), and why it failed. The words after the colon come from the operating system, so Windows words it differently.
          2. 
      
        2. Checking err on line 10 saved us. Without it, data would be empty and the program would quietly print nothing.
          3. 
    
        
    
        
      
      
        Scoot says: The digger critter dug and found nothing. A missing file is an ordinary failure, so it's a receipt, not a panic. Check it, tell the user, carry on.

        A huge file shouldn't be swallowed whole. Open it, and read it line by line with a scanner from package bufio ("buffered input and output"). Here's the delivery list first, printed with cat, then the program.
        
    scan_lines.go
    
        
    
        
    
          
      
        1. f, err := os.Open("deliveries.txt") (line 10)
          Opens the file for reading. f is a *os.File: a handle on the open file, like a ticket the operating system gives you.
          2. 
      
        2. defer f.Close() (line 15)
          An open file must be closed, or the ticket is never handed back. Stick the note right after the open succeeded, and you can't forget it, whatever happens below.
          3.

          Scan reads the next line and returns true, or false at the end. scanner.Text() is that line, without its newline.
          4.

          The loop also stops on a read failure, so ask afterwards whether it ended well. Here it did: no line printed.
          5. 
    
        
  
        

  
        
    37
    
        Every program that opens a file does these four steps, in this order. Learn the order once and you'll write it without thinking.
        
    
          
      
        • 1. Open. f, err := os.Open(name)
          • 
      
        • 2. Check the receipt. if err != nil { ...; return }. If the open failed, there is no file to use or close.
          • 
      
        • 3. Stick the closing note. defer f.Close(), only now that you know f is real.
          • 
      
        • 4. Use it. Scan, read, write.

    Under the hood: interface values, method sets, defer and open files
    
        
      
        
        
        
        The Professor says: Panel 11's two pockets are not just a picture. That is very nearly what the machine stores.
        
      
        
      
        An interface value is two words
        
      
        On a 64-bit computer, an interface value takes two machine words (16 bytes). The first points to a small table describing the dynamic type; for a non-empty interface such as Speaker, that table (the runtime calls it an itab) also lists where that type's Speak method lives. The second word points to the value, or holds it directly when it is pointer-sized. Calling s.Speak() reads the method's address from the table and jumps there: one extra lookup compared with calling Dog.Speak directly. An any needs no method list, so its first word points straight at the type's description.
        
      
        Why the pointer-receiver rule exists
        
      
        The spec gives every type a method set. The method set of Dog contains the methods with value receivers; the method set of *Dog contains those and the pointer-receiver ones. A type satisfies an interface when the interface's methods are all in its method set. When you put a plain Dog into an interface, the interface stores its own copy, and that copy is not addressable, so there would be no original for a pointer method to change. Calling rex.Speak() directly on a variable still works, because Go quietly takes &rex for you (chapter 13); inside an interface there is no variable to take the address of.
        
      
        Satisfaction is checked by the Compiler
        
      
        Assigning a Dog to a Speaker is checked at compile time, which is why panels 6, 7 and 12 fail before anything runs. Type assertions and type switches are checked at run time, because only then is the box's contents known; that's why panel 20 is a panic, not a compile error. A common idiom to make the Compiler check a type you never assign anywhere: var _ Speaker = Dog{}.
        
      
        How defer is done
        
      
        Since Go 1.14, most defer statements are "open-coded": the compiler places the deferred calls directly at each exit of the function, guarded by a small bit mask that records which defer lines actually ran. That makes them nearly free. A defer inside a loop can't be open-coded (the number of notes isn't known in advance), so the runtime keeps a list of records instead, which costs a little more. Either way, the arguments are evaluated when the defer statement executes, as the spec requires.
        
      
        Panics unwind the stack
        
      
        When a function panics, Go runs that function's deferred calls, then returns to its caller and runs its deferred calls, and so on up to the top of the goroutine. If no deferred function calls recover, the runtime prints the panic value and a trace of where each function was, and exits with status 2. A runtime error such as a nil dereference or a failed type assertion is a panic whose value is a runtime.Error, so its message starts with runtime error: or names the problem (interface conversion).
        
      
        What an open file is
        
      
        An *os.File wraps a file descriptor: a small number the operating system hands out for each open file, network connection or pipe. Each program gets a limited number of them (the operating system sets the limit), which is why forgetting Close in a loop that opens thousands of files eventually fails with an error saying too many files are open. As it happens, Close on a nil *os.File doesn't crash; it returns an error:
        
      nil_close.go
      
        
      
        
      
        That is a courtesy of the os package, not a rule of the language; panel 38's locker shows what most types do. When writing, Close can also report a real failure (for example a full disk), so programs that care check its error rather than deferring it blindly. bufio.Scanner reads in chunks and, by default, refuses lines longer than 64 KiB (scanner.Err() then reports that the token is too long); its Buffer method raises the limit.
        
    
        
  
        

  
        
    In real programs: where interfaces, defer and files show up
    
        
      
          
        
        • Small interfaces everywhere. The standard library's most-used interfaces have one or two methods: fmt.Stringer, error, io.Reader (Read), io.Writer (Write), sort.Interface. fmt.Fprintf in panel 40 accepts any io.Writer, which is why it can print to a file, the screen or a network connection alike (chapter 19).
          • 
        
        • Swapping parts. A program that stores data can take a Store interface, so the same code works with a real database or with a simple in-memory version in tests (chapter 23).
          • 
        
        • Custom errors. Libraries define error types carrying details, like panel 16's TooHeavy; callers can check for them with errors.As (chapter 19).
          • 
        
        • Decoding unknown data. JSON read into an any comes back as maps, slices, strings, float64s and bools, and type assertions or a type switch sort them out (chapter 22 opens them with assertions like m["kg"].(float64)). Note Boss 6: every JSON number arrives as float64.
          • 
        
        • Clean-up with defer. defer f.Close(), defer resp.Body.Close() after an HTTP request, defer mu.Unlock() after locking (chapter 25), defer wg.Done() in goroutines.
          • 
        
        • Recover at the edge. Go's web server recovers a panic in one request handler so the rest of the server keeps running, and logs the trace.
          • 
        
        • Files. Configuration files, logs, CSV exports, and reading input line by line with bufio.Scanner (also used on os.Stdin).
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "A type must say which interfaces it implements." No. Having the methods is enough.
          • 
        
        • "Extra methods stop a type from fitting." They don't. Only missing or misshapen methods do.
          • 
        
        • "If a method has a pointer receiver, the plain type still fits." Only *T fits. Plug in &value.
          • 
        
        • "An interface variable changes its type when you assign to it." Its own type stays the interface; the dynamic type in the type pocket changes.
          • 
        
        • "any means Go stops checking types." It checks more strictly: you can't do anything with an any until you assert its type.
          • 
        
        • "v.(int) converts a float64 to an int." An assertion never converts. It only succeeds if the box holds exactly that type.
          • 
        
        • "error is a special built-in thing." It's an ordinary interface with one method, declared for you.
          • 
        
        • "Deferred calls run at the end of the program." At the end of the function that deferred them.
          • 
        
        • "Deferred calls see the latest values of variables." Their arguments were evaluated when the defer line ran (ink, not pencil).
          • 
        
        • "Defers run in the order they're written." Reverse order: last stuck, first done.
          • 
        
        • "I can defer f.Close() straight after os.Open." Check the error first.
          • 
        
        • "Panic is Go's version of exceptions, for any error." Ordinary failures return errors. Panic is for bugs.
          • 
        
        • "A panic skips deferred calls." It runs them on the way up.

    Words from this chapter
    
        
      
        
        
        interface
        A type defined by a list of method signatures. Any type with all of those methods satisfies it.
        
        
        method signature
        A method's name, inputs and results, without its body: Speak() string.
        
        
        satisfy, implement
        A type satisfies (implements) an interface when it has every method on the interface's list. In Go this is implicit: nothing is written down.
        
        
        interface value
        What an interface variable holds: a dynamic type and a value of that type, or nothing (nil).
        
        
        dynamic type
        The type of the value currently inside an interface. %T prints it.
        
        
        polymorphism
        "Many shapes": one piece of code working with values of different types through a shared interface.
        
        
        method set
        The methods that belong to a type. *T's method set includes pointer-receiver methods; T's does not.
        
        
        fmt.Stringer
        The interface { String() string }; fmt uses it to print values.
        
        
        error
        The built-in interface { Error() string }.
        
        
        any, empty interface
        interface{}, with no methods, so every type satisfies it. any is its short name.
        
        
        type assertion
        x.(T): take the value out of an interface, claiming it has type T. Panics if wrong, unless written v, ok := x.(T).
        
        
        type switch
        switch v := x.(type) with types in the cases.
        
        
        defer
        Schedules a function call to run when the surrounding function returns, with its arguments evaluated now.
        
        
        LIFO, stack
        "Last in, first out": the order deferred calls run in, like a pile you only touch from the top.
        
        
        file
        A named sequence of bytes kept on a disk.
        
        
        *os.File, file descriptor
        A handle on an open file, which must be closed; underneath, the operating system's number for it.
        
        
        bufio.Scanner
        Reads input piece by piece, by default one line at a time.
        
        
        relative path
        A file name without a folder, looked up in the folder the program runs in.
        
        
        panic
        Stops normal execution, runs deferred calls on the way up, and crashes the program unless recovered.
        
        
        recover
        Called inside a deferred function, stops a panic and returns its value.

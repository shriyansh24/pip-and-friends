CHAPTER 9

WINDOWS ON A SHELF

Picture: Scoot, the bike courier in a red cap and green jacket, cheers with both arms up.

An egg carton can't grow. Real lists do: today's parcels, a shopping list, every line in a file. Go's answer is the slice, a window looking onto a long shelf. Read and change what's in the window, grow it with append, check how much shelf is left with cap, and slide the window along with s[a:b]. Plus the five classic slice mistakes, read like a detective. About 90 minutes, with 24 hands-on checks.

  1. The shelf and the window: slice literals, len, indexes, range
  2. Growing the list: append
  3. How much shelf is left: make, len and cap
  4. Sliding the window: s[a:b]
  5. Nothing, comparing, and copies: nil, ==, range
  6. Boss level and recap

Picture a long shelf of boxes behind a wall. You look at it through a window. In Go, the window is a slice, and the shelf is an array that Go keeps out of sight.

  1. 1Where the window starts on the shelf (here: at parcel B).
  2. 2len: how many boxes you can see through the window. Here 3.
  3. 3cap (capacity): how much shelf there is from the start of the window to the end of the shelf. Here 6.
  4. 4The shelf itself: the backing array. You never touch it directly; you work through the window.

Scoot says: Three numbers describe every window: where it starts, how wide it is, how much shelf is left. Hold on to this picture. The whole chapter is this picture.

      PART 4 · SLIDING THE WINDOWSlice expressions: s[low:high]
      

  
      
    22
    
      You can make a new, narrower window onto the same shelf with a slice expression: two numbers in the brackets, with a colon between.
      
    
      
      s[1low · in:3high · stops before]
    
      
    
        
      
      1. Low: where the new window starts
        Box 1 is included.
        2. 
      
      2. High: where it stops
        Box 3 is not included. The window shows boxes 1 and 2. Say it as "from 1 up to, but not including, 3".
        3. 
      
      3. Length = high − low
        3 − 1 = 2 boxes. That's the reason for the odd-looking rule: the length is a quick subtraction.
        4. 
      
      4. Leave a number out
        s[:3] means from the start (low 0). s[2:] means to the end (high len(s)). s[:] is the whole window.
        5. 
    
      
    
      
      
      
      Scoot says: Low is in, high is out. Like the [0:3] in chapter 6's Compiler message: from 0 up to, but not including, 3.

    Under the hood: the slice header, and what append really does
    
          
      
          A slice is three words
          
      
          The ticket in panel 16 is real. A slice value is a small struct the Go runtime calls a slice header (the Go Blog's "Go Slices: usage and internals" calls it a descriptor): a pointer to one element of a backing array, a length and a capacity. On a 64-bit computer that's three 8-byte words, 24 bytes, no matter whether the slice shows 3 elements or 3 million. Assigning a slice (t := s) or passing it to a function copies those 24 bytes, not the elements. That is why slices are cheap to pass around, and also why two slices can end up sharing a shelf (chapter 10).
          
      
          What indexing and slicing compile to
          
      
          s[i] means "the element at the pointer plus i times the element size", after a check that 0 <= i < len(s). s[low:high] builds a new header: pointer moved forward by low elements, length high - low, capacity cap(s) - low, after a check that 0 <= low <= high <= cap(s). Nothing is copied. Failing either check is the panic you met in panels 6 and 26. When the Compiler can prove an index is safe (inside for i := range s, for example), it leaves the check out.
          
      
          append, step by step
          
      
            
        
          1. If len(s) + n <= cap(s), there's room: the new values are written into the backing array just past the window, and append returns a header with the same pointer and a bigger length.
            2. 
        
          2. Otherwise the runtime function growslice allocates a new, larger array, copies the old elements across, writes the new ones after them, and returns a header pointing at the new array. Elements beyond the new length are zeroed.
            3. 
      
          
      
          Either way the result is a new header, and the old variable still holds the old one. The Compiler's is not used error exists because throwing that header away is always a mistake.
          
      
          How much bigger?
          
      
          The growth policy lives in the runtime source (runtime/slice.go) and is deliberately not part of the language specification. Roughly: small slices double, big ones grow by a smaller fraction, and the result is rounded up to one of the memory allocator's size classes. It has changed across releases, and so has the compiler's help. The Go 1.25 release notes ("Faster slices") say the compiler can now put a slice's backing array on the stack in more situations, and name a switch that turns this off: -gcflags=all=-d=variablemakehash=n. That starter array is the cap 4 you saw from Go 1.27.3 in panel 19, for a slice that never leaves its function. Checked by hand on this machine (not captured on this page): Go 1.25.1 also starts grow.go at cap 4, and both Go 1.25.1 and Go 1.27.3 built with that switch go back to 1, 2, 4. (Go 1.26 extended the idea to slices that do leave their function; chapter 28 says more.) So treat cap after append as something to read, never something to predict in code.
          
      
          nil inside
          
      
          A nil slice is a header whose pointer is nil and whose length and capacity are 0. An empty non-nil slice such as []int{} has length and capacity 0 but a non-nil pointer. Every built-in treats the two the same way, which is why len(s) == 0 is the right emptiness test.
          
    
          
  
          

  
          
    In real programs: where you'll see slices every day
    
          
      
            
        
          • Everywhere. Slices are Go's everyday list. Reading lines from a file gives you a []string; reading a file's raw contents gives a []byte; the command-line arguments in os.Args (chapter 7) are a []string.
            • 
        
          • The append-in-a-loop pattern, var out []T then out = append(out, …) inside a for, is the standard way to collect results, filter a list or build an answer.
            • 
        
          • Preallocating: when you know roughly how many items are coming, make([]T, 0, n) gives the shelf enough room up front, so append never has to move house. Code reviewers look for this in hot loops; chapter 10 uses it, and chapter 28 measures it.
            • 
        
          • Sub-slices as views: line[:10] for a prefix, args[1:] to skip the program name in os.Args, buf[:n] for "the first n bytes I actually read". You'll see buf[:n] in almost every program that reads from a file or the network.
            • 
        
          • nil vs empty matters at the edges: Go's JSON encoder writes a nil slice as null and an empty one as []. Inside your own code, prefer len(s) == 0 and don't make callers care which one they got.
            • 
        
          • Function inputs: a function that takes []string works for any number of strings. That's why so much of the standard library takes and returns slices.
            • 
      
          
    
          
  
          

  
          
    Common wrong ideas
    
          
      
            
        
          • "A slice is a resizable array." Close, but not quite: it's a view (pointer, len, cap) onto an array. The array never resizes; append moves to a new one when it must.
            • 
        
          • "append(s, x) changes s." It returns a new slice value. Without s =, the Compiler refuses the line.
            • 
        
          • "make([]int, 5) makes an empty slice with room for 5." It makes a slice showing five zeros. Room-without-contents is make([]int, 0, 5).
            • 
        
          • "If the capacity is 5, I can set s[3]." Only if the length is at least 4. Indexes are checked against len.
            • 
        
          • "s[1:3] gives three elements." Two: indexes 1 and 2. High is not included.
            • 
        
          • "Slicing copies the elements." It makes a new window onto the same array. (Chapter 10 shows the consequences.)
            • 
        
          • "s[-1] is the last element." Not in Go: a negative constant index doesn't compile. Use s[len(s)-1].
            • 
        
          • "Capacity always doubles." Panel 19 shows two Go versions giving different capacities for the same program. It's the runtime's choice.
            • 
        
          • "A nil slice prints nil." It prints []. Use %#v or s == nil to tell.
            • 
        
          • "I can compare two slices with ==." Only with nil. Write a loop, or use slices.Equal (chapter 10).
            • 
        
          • "Changing the v in for _, v := range s changes the slice." v is a copy. Write s[i] = ….
            • 
        
          • "A constant index past the end is a compile error, like with arrays." For slices it compiles and panics at run time; only impossible constants, like a negative index or a high below low (panel 24), are caught early.

    Words from this chapter
    
          
      
          
        
          slice
          A window onto part of an array: where it starts, its length and its capacity. Type written []T.
          
        
          backing array
          The array (the shelf) that holds a slice's elements. You reach it only through slices.
          
        
          slice literal
          Writing a slice's values directly: []int{1, 2, 3}.
          
        
          element
          One value in a slice: one box.
          
        
          index
          An element's position in the window, counted from 0.
          
        
          len(s)
          Length: how many elements the slice shows.
          
        
          cap(s)
          Capacity: how many elements from the slice's start to the end of its backing array.
          
        
          append
          Built-in that returns a new slice with values added to the end, moving to a bigger array if the old one is full.
          
        
          make
          Built-in that builds a slice of a chosen length (and optional capacity), filled with zero values.
          
        
          zero value
          The value a new box starts with: 0, "", false, or nil.
          
        
          slice expression
          s[low:high]: a new window from low up to, but not including, high.
          
        
          half-open range
          A range that includes its start and excludes its end, like [1:3].
          
        
          re-slicing
          Slicing a slice, such as w[:4]; the window may stretch up to its capacity.
          
        
          nil slice
          A slice with no backing array: the zero value of a slice type. Prints as [].
          
        
          empty slice
          A slice of length 0. It may be nil or not; len(s) == 0 covers both.
          
        
          slice header
          The three-part value inside a slice variable: pointer, length, capacity.
          
        
          reallocation
          What append does when the array is full: allocate a bigger one and copy everything across.
          
        
          range copy
          The value variable in for _, v := range s: a copy of each element, not the element itself.
          
        
          runtime
          The part of Go that runs alongside your program: it checks indexes, grows slices and reports panics.
          
        
          preallocate
          Give a slice enough capacity up front with make([]T, 0, n).

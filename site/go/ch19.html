CHAPTER 19 · INTERMEDIATE

PIPES AND NESTING DOLLS

Picture: Scoot, the bike courier in a red cap and green jacket, waves hello with a letter in hand.

Chapter 14 showed you plugs: interfaces. Today you meet the two most famous plugs in Go, Reader and Writer, and join them with a pipe. You'll open up an interface value and find two slots inside, which explains Go's sneakiest trap. Then errors grow up: you'll pack one error inside another like nesting dolls, open them to find the one you want, and learn when a program should give up loudly with panic, and how recover catches it. About 120 minutes, with 26 hands-on checks.

  2. The two-slot box and the nil trap
  3. Designing with plugs
  4. Nesting dolls: wrapping errors

PART 1 · ONE-METHOD PLUGSio.Writer, io.Reader and io.Copy

1

Scoot's depot has installed a network of tubes. Letters whoosh from the sorting room to the front desk, to the archive, to the shredder.

Scoot says: Every station has the same little socket. Anything that can take letters plugs in at one end. Anything that can hand out letters plugs in at the other.

Scoot says: The tube doesn't care what's on either end. Desk, archive, shredder: same socket, same tube.

Picture: Scoot points at the new tubes, amazed.

2

Go's standard library has those two sockets. Each is an interface with just one method. They live in the package io (input and output).

TAKES BYTES type Writer interface { Write(p []byte) (n int, err error) }

io.Writeranything you can write to

"Here are some bytes, please take them." It answers how many it took (n) and whether anything went wrong (err). The screen, a file, a buffer in memory and a network connection are all Writers.

HANDS OUT BYTES type Reader interface { Read(p []byte) (n int, err error) }

io.Readeranything you can read from

"Here's an empty bucket p, please fill it." It answers how many bytes it put in (n), and says io.EOF ("end of file") when there are no more. A strings.Reader (made from a string), a file and the keyboard are all Readers.

The two declarations: type Writer interface with one method, Write(p []byte) (n int, err error); and type Reader interface with one method, Read(p []byte) (n int, err error).

Scoot says: A byte is one small number from 0 to 255; text is stored as bytes (chapter 11). Catchphrase: the smaller the plug, the more things fit. One method is easy for anything to have.

    PART 2 · THE TWO-SLOT BOXWhat's inside an interface value, and the nil trap
    

  
    
    9
    
    Chapter 14 said an interface value holds a type tag and a value. Picture it as a box with two slots. A variable of type io.Writer is such a box.
    
    
    
      
    
        
    var w io.Writer
    
        
    TYPE(empty)
    VALUE(empty)
    
        
    w == nil → true
    
      
    
      
    
        
    w = os.Stdout
    
        
    TYPE*os.File
    VALUEthe screen
    
        
    w == nil → false
    
      
    
      
    
        
    w = n  (n is a nil *Note)
    
        
    TYPE*main.Note
    VALUE
    
        
    w == nil → false!
    
      
    
    
    
    
    Three two-slot boxes. First: var w io.Writer, both slots empty, w == nil is true. Second: w = os.Stdout, type slot *os.File, value slot the screen, w == nil is false. Third: w = n where n is a nil pointer to Note: the type slot says *main.Note and the value slot holds the nil ghost; w == nil is still false.
    
    
    
      
      
    Scoot says: An interface is nil only when both slots are empty. A ghost in the value slot doesn't count: the type slot has a label on it. Catchphrase: an empty box has no type and no value.
    
    
    
  
    

  
    
    10
    
    The same three boxes in a real program. %T prints the type slot, and %v the value.
    
    two_slots.go

      Nothing in either slot. Only now is w == nil true.
      2. 
      
    2. *os.File screen nil? false (lines 20 and 21)
      A type and a real value.
      3. 
      
    3. *main.Note <nil> nil? false (lines 23 to 25)
      The value printed is <nil>, yet w == nil is false, because the type slot now says *main.Note. The value slot holds a nil pointer: a ghost with a name tag.

      PART 3 · DESIGNING WITH PLUGSWhere interfaces belong, and when not to make one
      

  
      
    14
    
      Two habits experienced Go programmers share. Accept interfaces: ask for the smallest plug you need. Return structs: hand back the real thing, with all its buttons.
      
    accept_iface.go
    
      
    
      
    
        
      
      1. report(w io.Writer, …) (line 11)
        report only ever calls Write (through Fprintf), so it asks for just that. Lines 32 and 35 hand it the screen and a *Log. Tests can hand it a bytes.Buffer and check what came out. (Chapter 23 uses the same idea with a stub and httptest's recorder.)
        2. 
      
      2. func NewLog() *Log (line 21)
        It returns the concrete *Log, not io.Writer. If it returned io.Writer, line 36 couldn't call log.Count(): the plug only has one button, Write.
        3. 
    
      
  
      

  
      
    15
    
      In Go, the code that uses a plug usually defines it. The dispatcher needs one thing from a courier, so it writes a one-method interface right next to dispatch.
      
    consumer.go
    
      
    
      
    
        
      
      1. type deliverer interface (lines 7 to 9)
        Lower-case name: it's the dispatcher's private business. Bike and Drone never mention it, and they don't need to.
        2. 
      
      2. PumpTyres (line 20)
        A bike has other methods, and that's fine. The plug asks for Deliver only. The smaller the plug, the more things fit.
        3. 
      
      3. Two real types (lines 27 and 28)
        A bike and a drone both deliver. Two implementations are a good sign the interface earns its keep.
        4. 
    
      
  
      

  
      
    16
    
      Three rules to carry around.
      
    
      
      
      
        ACCEPT
        
      ACCEPT INTERFACESask for the smallest plug
      
        
      A parameter typed io.Writer works with the screen, files, buffers and tests. A parameter typed *os.File works with files only.
      
      
      
      
      
        RETURN
        
      RETURN STRUCTShand back the real thing
      
        
      Callers get every method and field. They can always put it in a plug-shaped box themselves. (The big exception: error, which functions return as the interface.)
      
      
      
      
      
        WAIT
        
      DON'T POLLUTEno plug before two devices
      
        
      Making an interface for a type that has only one implementation, "just in case", is called interface pollution. Write the concrete type first; add a plug when a second device turns up.
      
      
      
    
      
    
      
      
      
      Scoot says: Catchphrase: accept plugs, hand back the real thing. Go's own proverb says it shorter: "The bigger the interface, the weaker the abstraction."

          2.

    29
    
        The fix: each function does one of two things. Either it handles the error (logs it, retries, uses a default) and stops, or it returns it with context. Never both.
        
    once.go
    
        
    
        
    
          
      
        1. return fmt.Errorf(…) (lines 10 and 17)
          The lower functions just return, adding what they were doing.
          2. 
      
        2. ERROR: deliver: parcel -1: bad id (line 25)
          One line, at the top, with the whole story read from the outside in.
          3. 
    
        
    
        
      
      
        Scoot says: Catchphrase: handle it once. Log it or return it, never both.
        
    
        
  
        

  
        
  

  
        
    30
    
        How to write good context, and when to hide the doll.
        
    
          
      
        • Say what you were doing, with which input. "loading config %q: %w" beats "error: %w".
          • 
      
        • Skip "failed to" and "error:". Every layer would add it again: failed to deliver: failed to save: …. The text is already an error.
          • 
      
        • Small letter, no full stop (chapter 8), because your words become part of someone else's sentence.
          • 
      
        • Wrap with %w when callers may need to check what's inside: io.EOF, fs.ErrNotExist, your own sentinels and types.
          • 
      
        • Use %v on purpose at the edge of your package to hide an inner detail, such as which database library you use. Anything wrapped with %w becomes something callers can depend on, so it becomes part of your promise to them.
          • 
      
        • Don't wrap a sentinel you document as "returned as is", like io.EOF from a Read: callers compare it with ==.
          •

        PART 6 · PANIC AND RECOVERThe fire alarm, and catching it
        

  
        
    32
    
        Chapter 14 said: bad luck gets an error, only a bug gets panic. Here's how to tell them apart.
        
    
        
      
        
        ERROR VALUE
        
        A RECEIPTexpected bad luck
        
        
          
          
        • The file isn't there.
          • 
          
        • The user typed "ten" instead of 10.
          • 
          
        • The network is down; the parcel is too heavy.
          • 
        
        
        
        Return an error. The caller decides what to do.
        
      
        
      
        
        PANIC
        
        A FIRE ALARMa bug, or "impossible"
        
        
          
          
        • An index past the end of a slice.
          • 
          
        • A nil pointer used.
          • 
          
        • A switch case that can never happen, happened.
          • 
        
        
        
        The program can't sensibly go on. Everyone stops.
        
      
        
    
        
    
        
      
      
        Scoot says: Catchphrase: panic for bugs, errors for bad luck. If a caller could reasonably expect it, it's an error.
        
    
        
  
        

  
        
  

  
        
    33

          2.

          Line 12 panics. On the way out, the deferred function runs; recover() hands back the panic's value and the panic stops.

    Under the hood: the two words of an interface, how io.Copy finds shortcuts, and how errors.Is walks the chain
    
        
      
        An interface value is two machine words
        
      
        In the Go runtime, a non-empty interface such as io.Writer is stored as two pointer-sized words: a pointer to an itab (a small table naming the concrete type and listing the addresses of its methods), and a pointer to the data. An empty interface (any) stores a pointer to the type itself instead of an itab. The "two slots" in panel 9 are exactly these words. w == nil compares both words with zero, which is why a non-nil type word makes the whole value non-nil even when the data word is zero.
        
      
        Why fmt printed <nil> instead of crashing
        
      
        In panel 11, %v called (*CheckErr).Error on a nil pointer, which read e.Reason and panicked. fmt wraps calls to Error and String in its own recover. If the panic came from a nil pointer receiver, it prints <nil>; for any other panic it prints a %!v(PANIC=Error method: …) note. Helpful for logging, but it also hides the bug.
        
      
        How io.Copy picks a route
        
      
        io.Copy first checks whether the source has a WriteTo method (an io.WriterTo), or the destination has a ReadFrom method (an io.ReaderFrom). If so, it lets them do the copy themselves, which can be much faster; for example, copying between two files on Linux can happen inside the kernel. Otherwise it uses a 32 KB buffer and loops: Read, Write, repeat. That's why panel 8's narrow filter really did make three trips: the buffer was big, but rot13Reader.Read only ever filled 5 bytes of it.
        
      
        The Reader contract, exactly
        
      
        Read may return n > 0 together with a non-nil error, including io.EOF. It may return fewer bytes than the buffer holds, even if more are coming. It should not return 0, nil except when the buffer has length 0. So the correct loop is: process buf[:n], then check err. io.ReadAll, io.ReadFull and bufio.Scanner (chapter 21) do that bookkeeping for you.
        
      
        What %w builds
        
      
        fmt.Errorf with one %w returns a value of an unexported type *fmt.wrapError holding the message and the inner error, with an Unwrap() error method. With two or more %w verbs (allowed since Go 1.20) it returns *fmt.wrapErrors, whose Unwrap() []error returns all of them. errors.Join also returns a value with Unwrap() []error; its Error() joins the messages with newlines.
        
      
        How errors.Is walks
        
      
        errors.Is(err, target) checks, at each doll: is it == target (when the type is comparable)? Does it have an Is(error) bool method that says yes? If not, it unwraps: one inner error, or for a Unwrap() []error each inner error in turn, depth first. That's how panel 19 matched: os.Open's innermost doll is a syscall.Errno (ENOENT), whose Is method says "yes, I count as fs.ErrNotExist". errors.As walks the same way but checks the type, or an As(any) bool method.
        
      
        Why the pointer wrap defeated errors.Is
        
      
        In panel 31 the inner doll was a *DiskFull and the target a DiskFull. Interface comparison first compares the type words, which differ, so the answer is false. Go 1.27's vet printf check reports a %w operand whose type is a pointer to a type that already satisfies error.
        
      
        Panics, unwinding and recover
        
      
        A panic stops the current function, then runs its deferred calls, then does the same in the caller, and so on up the goroutine's stack. If a deferred function calls recover() while this is happening, the panic stops, recover returns the value that was passed to panic, and the function that deferred it returns normally to its caller, with whatever its named results now hold. recover returns nil when there is no panic, or when it isn't called directly by a deferred function (so defer recover() doesn't work, as Boss 6 showed). Since Go 1.21, panic(nil) becomes a *runtime.PanicNilError, so recover() never returns nil for a real panic. Some failures cannot be recovered at all: running out of memory, a stack overflow (chapter 17) and concurrent map writes are fatal errors, not panics.
        
    
        
  
        

  
        
    In real programs: where readers, writers and wrapped errors show up
    
        
      
          
        
        • Files and the network. *os.File and every network connection (net.Conn) are both Readers and Writers. An HTTP response body is an io.ReadCloser (Reader plus Close), and a web handler writes its reply to an http.ResponseWriter, which is a Writer (chapter 26).
          • 
        
        • Snap-together pipelines. gzip.NewReader(f) unzips while you read; io.TeeReader copies everything it reads to a Writer; io.MultiWriter writes to several Writers at once; io.LimitReader stops after N bytes; bufio.NewReader adds a buffer (chapter 21 uses its cousins bufio.Scanner and bufio.Writer).
          • 
        
        • Testing output. Pass a bytes.Buffer where real code passes os.Stdout, then compare buf.String() with what you expected. That's "accept interfaces" paying off; chapter 23 uses the same idea with a stub and httptest's recorder.
          • 
        
        • Composed interfaces. io.ReadWriter, io.ReadCloser and io.WriteCloser are small interfaces embedded together (chapter 18's embedding).
          • 
        
        • Sentinels you'll meet. io.EOF, io.ErrUnexpectedEOF, fs.ErrNotExist, fs.ErrPermission, sql.ErrNoRows, http.ErrServerClosed, context.Canceled and context.DeadlineExceeded (those two in chapter 26).
          • 
        
        • Error types you'll meet. *fs.PathError (operation, path and inner error), *strconv.NumError, *json.SyntaxError (with the byte offset; chapter 22) and *net.OpError. Get at them with errors.As or errors.AsType.
          • 
        
        • Servers recover per request. Go's HTTP server recovers a panic in a handler, logs it, and closes that one connection, so one bad request can't take down the whole server.
          • 
        
        • Validation code often collects every problem with errors.Join so a user sees all of them at once.

    Common wrong ideas
    
        
      
          
        
        • "io.EOF means something broke." It's the normal end of input. io.Copy and io.ReadAll even report nil when they reach it.
          • 
        
        • "Read fills the whole buffer." It may fill less. Always use buf[:n].
          • 
        
        • "A nil pointer in an interface is a nil interface." Only when both slots are empty. Return nil explicitly.
          • 
        
        • "If it prints <nil>, it is nil." Panel 11 printed <nil> while err != nil was true.
          • 
        
        • "Every type needs an interface, for testing." Define interfaces where they're used, when they're needed. Implicit satisfaction lets you add them later.
          • 
        
        • "%w changes the message." The text is identical to %v; only what's kept inside differs.
          • 
        
        • "err == ErrNotFound is fine." Only until someone adds context. errors.Is works both before and after.
          • 
        
        • "Always wrap with %w." Wrapping makes the inner error part of your package's promise. Use %v when callers shouldn't depend on it.
          • 
        
        • "Logging an error is handling it, so I should also return it." Do one or the other. Logging and returning gives duplicate reports.
          • 
        
        • "recover() anywhere catches panics." Only when called by a deferred function, during the panic, in the same goroutine.
          • 
        
        • "Panics are Go's exceptions; use them for errors." Go uses error values for expected problems. Panics are for bugs, and recovered panics are rare and local.
          • 
        
        • "errors.As takes the variable." It takes a pointer to it: errors.As(err, &target). Passing the variable itself panics at run time. errors.AsType avoids that mistake entirely.

    Words from this chapter
    
        
      
        
        
        byte
        One small number from 0 to 255. Text, pictures and files are all stored as bytes.
        
        
        io.Writer
        The one-method interface Write(p []byte) (n int, err error): anything you can write bytes to.
        
        
        io.Reader
        The one-method interface Read(p []byte) (n int, err error): anything you can read bytes from.
        
        
        io.EOF
        "End of file": the error value a Reader returns when there's nothing more. The normal way to finish.
        
        
        io.Copy
        Reads from a Reader and writes to a Writer until EOF; returns the byte count and an error.
        
        
        os.Stdout, standard error
        The screen as a Writer, and its second channel used for problems and logs.
        
        
        bytes.Buffer, strings.Builder
        In-memory Writers; a Buffer is also a Reader, and reading drains it.
        
        
        wrapping Reader / Writer
        A Reader or Writer that holds another one and changes the bytes on the way through.
        
        
        interface value
        A two-slot box: the concrete type, and the value. nil only when both are empty.
        
        
        typed nil
        A nil pointer stored in an interface. The interface isn't nil, because its type slot is filled.
        
        
        accept interfaces, return structs
        Ask for the smallest interface you need; hand back concrete types.
        
        
        consumer-side interface
        An interface declared by the code that uses it, listing only what it needs.
        
        
        interface pollution
        Making interfaces before anything needs them, typically with only one implementation.
        
        
        compile-time check
        var _ I = (*T)(nil): a throw-away line that makes the Compiler confirm *T satisfies I.
        
        
        wrap, %w
        Make a new error with context that keeps the old error inside, so it can still be found.
        
        
        error chain
        The nesting dolls: an error, the error it wraps, the one that wraps, and so on.
        
        
        errors.Unwrap
        Opens one doll: returns the wrapped error, or nil.
        
        
        errors.Is
        Is this exact error anywhere in the chain?
        
        
        errors.As, errors.AsType
        Is an error of this type anywhere in the chain? If so, hand it over. AsType (Go 1.26) returns it directly.
        
        
        sentinel error
        A fixed error value in a package variable, named ErrSomething, checked with errors.Is.
        
        
        custom error type
        Your own type with an Error() string method, carrying details; found with errors.As.
        
        
        opaque error
        An error callers should only report, not inspect.
        
        
        errors.Join
        Combines several errors into one; prints one per line; nil if all are nil.
        
        
        handle once
        Each function either deals with an error or returns it with context, never both.
        
        
        unwinding
        During a panic, leaving functions one by one and running their deferred calls.
        
        
        recover
        Built-in function that stops a panic and returns its value, when called by a deferred function.

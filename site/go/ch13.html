CHAPTER 13

ADDRESSES AND VERBS

Picture: Scoot, the bike courier in a red cap and green jacket, cheers with both arms up.

A courier never carries the house. Scoot carries the address, written on a slip. In Go that slip is a pointer: with it, a function can reach your box and change it. Then methods: verbs that belong to a type, like hero.LevelUp(), and why some work on a photocopy while others work on the original. About 110 minutes, with 25 hands-on checks.

Every variable is a box in the computer's memory, and every box has an address, like every house has one. Write one on a slip:

    first_pointer.go
    

    

    
    
      
  1. p := &score (line 7)
    & means "the address of". p now holds score's address: a slip, not a copy of 5.
    2. 
      
  2. 5 (line 8)
    *p means "go to the address on p, and use what's there". That's score's box, holding 5.
    3. 
      
  3. 7 (lines 9 and 10)
    *p = 7 goes to the address and puts 7 in the box. We printed score, never touched by name, and it's 7.
    4. 
      
  4. int *int (line 11)
    score is an int. p is a *int, said "pointer to int": a slip that can only hold the address of an int box.
    5. 
    

  


  

    5
    
Two symbols, three jobs. Read them out loud like this:

    

      

        &x
        
ADDRESS OFan expression

        
"Write x's address on a slip." The result is a pointer. Read it as address of x.

      

      

        *int
        
POINTER TYPEin a type

        
"A slip for an int house." A star in front of a type makes the pointer type. Read it as pointer to int.

      

      

        *p
        
GO THEREan expression

        
"Go to the address on p." A star in front of a pointer reaches the box it points at, to read it or to change it. This is called dereferencing.

      

    

    

      
      
Scoot says: Catchphrase: & writes the address; * goes there. And a star next to a type name is part of the type: *int, *House.

    15
    
      So should every parameter be a pointer? No. Choose on purpose.
      
    
      
      
      
        HAND OVER A COPY
        
      VALUE PARAMETERfunc show(h House)
      
        
        
          
      • The machine only needs to read the value.
        • 
          
      • The value is small: numbers, strings, bools, small structs.
        • 
          
      • You want a guarantee: the caller's box comes back untouched.
        • 
        
      
      
      
      
      
        HAND OVER A SLIP
        
      POINTER PARAMETERfunc paint(h *House)
      
        
        
          
      • The machine must change the caller's value.
        • 
          
      • The struct is big, and copying it on every call would be wasteful.
        • 
          
      • "No value at all" must be possible (a nil slip, part 3).
        • 
        
      
      
      
    
      
    
      
      
      
      Scoot says: When you read *House in a function's parameters, read it as a warning: "this machine may change your house."

    26
    
      Pointers are a tool, not a habit. Skip them when:
      
    
        
      
      1. The value is small and only read. An int, a bool, a short string, a two-field struct: copying is as cheap as copying a slip, and safer.
        2. 
      
      2. It's a slice or a map. Chapters 10 and 12 showed they're already handles: copying one still shares the shelf or the coat check. *[]int and *map[string]int are almost never what you want.
        3. 
      
      3. It's a string. Strings never change (chapter 11), so nobody could paint them through a slip anyway.
        4. 
      
      4. "Maybe nil" isn't a meaning you need. Every slip can be blank, and every blank slip is a possible panic. A plain value can never be nil.
        5. 
    
      
    
      
      
      
      Scoot says: Use a slip when someone must change the real house, or when the house is too big to photocopy. Otherwise, hand over a copy.

    28
    
      The same calculation twice: once as an ordinary function, once as a method of Rect.
      
    method.go
    
      
    
      
    
        
      
      1. func area(r Rect) int (line 9)
        A function. You call it by name and pass the rect in brackets: area(box).
        2. 
      
      2. func (r Rect) Area() int (line 13)
        A method. The extra brackets before the name, (r Rect), are the receiver: the noun this verb belongs to. You call it with a dot: box.Area(), and inside, r is box.
        3. 
      
      3. 12 and 12
        Same answer. A method is a function with its first argument moved in front of the dot.
        4. 
    
      
  
      

  
      
    29
    
      The parts of a method declaration, from left to right:
      
    
      
      
      (r Rect)
      THE RECEIVERwho does it
      A name and a type, in brackets right after func. Go style keeps the name short, often the type's first letter.
      
      
      Area()
      THE VERBname and parameters
      Then the method's name and its ordinary parameters, exactly like a function. Area needs none.
      
      
      int
      THE RESULTwhat comes back
      The result type and the body in { }, just like any function. The method is declared outside the struct, next to it.
      
    
      
    
      
      
      
      Scoot says: Methods are written outside the type … struct, but in the same package. Different types can each have their own Area: box.Area() and yard.Area() don't clash.
      
    
      
  
      

  
      
    30
    
      The receiver is a parameter too, so the rule from part 2 applies: a plain type gets a copy, a star type gets a slip.
      
    
      
      
      
        
        
      VALUE RECEIVERfunc (c Counter) Inc()
      
        
      The method works on a photocopy of the value. It can read everything. Anything it writes is lost when it returns.
      
      
      
      
      
        
        
      POINTER RECEIVERfunc (c *Counter) IncP()
      
        
      The method gets a slip to the original. Whatever it writes, it writes on the real thing.
      
      
      
    
      
    
      
      
      
      Scoot says: Catchphrase: a value receiver works on a photocopy; a pointer receiver works on the original.

        The consistency rule. Earn and Spend must change the wallet, so they need pointer receivers. Coins only reads, but it gets one too.
        
    wallet.go
    
        
    
        
    
        
      
        POINTER RECEIVER
        • The method changes the value (Earn, Spend).
        • The struct is big, so a photocopy per call is wasteful.
        • Any other method of the type already has one: then all do.
        
      
        VALUE RECEIVER
        • The type is small and no method changes it, like Rect or Minutes.
        • Every method only reads.

    Under the hood: what a pointer is, why nil crashes, and what a method really is
    
        
      
        A pointer is one number
        
      
        On a 64-bit computer, every pointer is 8 bytes: the address of the first byte of the box it points at. A *int, a *House and a *[1000]int are all 8 bytes, which is why handing a big struct over by pointer is cheap. The type (*House) isn't stored at run time; it's how the Compiler knows what it will find at the other end, so it can stop you pointing an *int at a string.
        
      
        Why a nil dereference is a SIGSEGV
        
      
        A nil pointer is the address 0. Operating systems deliberately leave the lowest page of memory unmapped, so touching address 0 (or a small offset from it, like a field of a nil struct pointer) makes the processor raise a fault. The operating system sends the program the signal SIGSEGV, and the Go runtime turns that signal into the panic you saw. That's why the report has two parts: Go's own panic: line and the operating system's [signal SIGSEGV …] line. code=0x1 is the operating system's reason code (here: no memory is mapped at that address).
        
      
        Where do the houses live?
        
      
        You never choose. The Compiler decides whether a variable can live in the function's own short-lived frame (the stack) or must live in longer-lived memory (the heap). If a slip to it might outlive the function, as in return &h in panel 21, the variable "escapes" to the heap. The garbage collector frees heap memory once nothing points to it. Chapter 28 shows how to watch the Compiler make that decision (go build -gcflags=-m). This is why returning the address of a local variable is safe in Go, while in C it is a classic bug.
        
      
        The address you printed
        
      
        Since Go 1.26, the runtime on 64-bit systems starts the heap at a randomized address each time a program starts, a security measure. That's why panel 6's address is a large, unfamiliar number; the same program built with Go 1.24.7 printed a smaller address starting 0xc000…. Either way, addresses are not something to rely on.
        
      
        Which values have an address?
        
      
        The specification calls them addressable: variables, fields of addressable structs, elements of slices and of addressable arrays, and anything reached through a pointer (*p). Not addressable: map elements (that's chapter 12's cannot assign to struct field pins["home"].X in map), constants, the result of a function call, and literals like Counter{}. That's why Counter{}.IncP() fails. Composite literals get one special exception: &House{…} is allowed and builds a new house.
        
      
        A method is a function in disguise
        
      
        Go lets you call a method the long way, as a method expression: Counter.Inc(c) and (*Counter).IncP(&c) do exactly what c.Inc() and c.IncP() do. The receiver is simply the first argument, copied like any other. The dot form adds the convenience: picking the right method for the type, and inserting & or *.
        
      
        Method sets, briefly
        
      
        The methods you can call on a Counter value are its value-receiver methods (plus pointer methods if the value is addressable, because Go can take &). A *Counter has both kinds. The specification calls these lists method sets, and chapter 14 shows why they matter when a value is plugged into an interface.
        
      
        How fmt prints pointers
        
      
        fmt prints a pointer to a struct, array, slice or map as & followed by the contents, but only at the top level. A pointer inside a struct or a slice prints as an address number, and a pointer to an int always does. %p prints any pointer as an address.
        
    
        
  
        

  
        
    In real programs: where pointers and methods show up
    
        
      
          
        
        • Constructor functions. Packages often provide NewThing(…) *Thing, which builds a value, fills in sensible defaults and hands back a slip. You've used one: bufio.NewScanner(os.Stdin) in chapter 7 returns a *bufio.Scanner.
          • 
        
        • Types that change hold pointer receivers. strings.Builder's WriteString is declared func (b *Builder) WriteString(s string) (int, error). That's why the documentation warns not to copy a Builder after writing to it.
          • 
        
        • Small value types use value receivers. time.Time's methods mostly take a value, and calling t.Add(time.Hour) returns a new Time instead of changing t.
          • 
        
        • Stringers everywhere. time.Duration prints as 1h30m0s because it has a String method. Giving your own types one makes logs and error messages readable.
          • 
        
        • Optional values. Settings, forms and JSON data often use *int or *string fields so that "not given" (nil) differs from zero, like panel 22's tip. new(value) made these much shorter to fill in.
          • 
        
        • Big records. Programs that pass around large structs (a game's world state, a parsed document) pass *World to avoid copying hundreds of bytes on every call.
          • 
        
        • Values that must never be copied. Locks from the sync package (chapter 25) are always used through pointers; go vet warns if you copy one.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "Go passes structs by reference." Go always copies arguments. Passing &a copies the address; it's still a copy, of a slip.
          • 
        
        • "* means multiply here." Before a type it means "pointer to"; before a pointer it means "go there". Only between two numbers is it multiplication.
          • 
        
        • "Printing p prints the value." For a pointer to an int it prints the address. Use *p. (Struct pointers print as &{…}.)
          • 
        
        • "A value receiver can change the struct if I call it on a pointer." The receiver gets a photocopy whatever you call it on: panel 33's e.Inc() stayed at 0.
          • 
        
        • "I need & to call a pointer method." Not on a variable: Go takes the address for you. You only hit trouble with values that have no address, like Counter{} or a map element.
          • 
        
        • "Returning the address of a local variable is dangerous." That's true in C, not in Go. The house stays standing as long as a slip leads to it.
          • 
        
        • "Pointers make every program faster." Copying small values is very cheap, and pointers can make the garbage collector work harder. Use them for meaning first: to share and change.
          • 
        
        • "Slices and maps need pointers so functions can change them." Changing their elements already works through a copy, because they are handles (chapters 10 and 12). A pointer is only needed if the function must replace the whole slice, and returning the new slice is usually clearer.
          • 
        
        • "A nil pointer is caught by the Compiler." It can't know at compile time. It's a run-time panic.
          • 
        
        • "Methods live inside the struct." They're declared outside, anywhere in the same package, and they can belong to non-struct types too.
          • 
        
        • "String() can print the value with %v." Inside a String method, fmt.Sprintf("%v", p) calls String again, forever. Format the fields one by one, as panel 35 does.
          •

    Words from this chapter
    
        
      
        
        
        address
        The number that says where a box lives in memory, like a house's street address.
        
        
        pointer
        A value that holds an address: a slip of paper that leads to a box.
        
        
        & (address-of)
        &x gives x's address, a pointer to x.
        
        
        pointer type *T
        The type of a pointer to a T, said "pointer to T": *int, *House.
        
        
        dereference (indirect)
        Follow a pointer to the box it points at: *p. "Cannot indirect" means "that isn't a pointer".
        
        
        nil pointer
        A pointer with no address (a blank slip): the zero value of every pointer type.
        
        
        nil pointer dereference
        Following a nil pointer. A run-time panic.
        
        
        SIGSEGV (segmentation violation)
        The operating system's signal for "this program touched memory it may not use".
        
        
        new
        The built-in that builds a new box and returns a pointer to it: new(int) (zero value) or, since Go 1.26, new(42) (that value).
        
        
        composite literal address
        &House{…}: build a struct and get a pointer to it in one step.
        
        
        pointer arithmetic
        Adding to or subtracting from addresses. Go doesn't allow it.
        
        
        garbage collector
        The part of the Go runtime that frees boxes nothing points to any more.
        
        
        escape
        When a variable must outlive its function (for example because its address is returned), it "escapes" to longer-lived memory. Go decides this for you.
        
        
        method
        A function that belongs to a type, called with a dot: box.Area().
        
        
        receiver
        The value a method is called on, declared in brackets before the method name: (r Rect).
        
        
        value receiver
        A receiver of type T: the method works on a copy.
        
        
        pointer receiver
        A receiver of type *T: the method works on the original.
        
        
        Stringer
        A type with a method String() string. fmt uses it to print the value.
        
        
        non-local type
        A type declared in another package, such as int. You can't add methods to it.
        
        
        addressable
        Has a box of its own, so & works on it: variables, slice elements, struct fields of variables. Map elements and literals are not.
        
        
        method set
        The list of methods you can call on a type. Chapter 14 uses it.
        
        
        consistency rule
        If any method of a type needs a pointer receiver, give all its methods pointer receivers.
        
        
        optional field
        A pointer field where nil means "not given", different from the zero value.

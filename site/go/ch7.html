CHAPTER 7

MACHINES AND MAIL SLOTS

Picture: Scoot, the bike courier in a red cap and green jacket, waves hello with a letter in hand.

Build your own functions: little vending machines. Put values in, get a result out, and use the same machine as often as you like. Learn how many results a machine can hand back, why it always works on a copy of what you give it, and how to split a long program into tidy steps. Then let people talk to your programs: everything they type arrives through a mail slot as paper, and a clerk turns it into numbers. About 95 minutes, with 28 hands-on checks.

  1. Machines: your first functions
  2. Jams: the Compiler checks every call
  3. Two drawers: several results, the blank box, named results, doc comments
  4. Your own copy: call by value, scope, and breaking main into steps
  5. The mail slot: Scan, bufio.Scanner, os.Args and TrimSpace
  6. The clerk: strconv turns text into numbers
  7. Boss level and recap

    27
    
        Scoot's rules for building good machines.
        
    
          
      
        1. One job each. If you need "and" to describe it ("works out the fee and prints the receipt"), it's probably two machines.
          2. 
      
        2. A name that says the job. deliveryFee, not doStuff or f2. Go style: start lowercase, join words with capitals.
          3. 
      
        3. Short. If it doesn't fit on your screen, look for a step to pull out into its own function.
          4. 
      
        4. Inputs in, results out. Take what you need as parameters and hand back results. Don't print inside a machine whose job is to work something out; let the caller decide.
          5. 
      
        5. A doc comment that starts with the name: // deliveryFee is free for orders of 20 coins or more.
          6. 
    
        
    
        
      
      
        Scoot says: Small machines, good names. That's how I'd find my way round a city of code!

    Under the hood: frames, copies, and how input really arrives
    
        
      
        The call stack
        
      
        Each running call gets a stack frame: a block of memory holding its parameters and local variables, plus a note of where to go back to when it returns. Frames pile up like plates: main at the bottom, the function it called on top of it, the function that called on top again. A return takes the top plate off and jumps back to the saved spot. That pile is the call stack, and the tracers in panels 18 and 23 draw it with main first and newer frames below.
        
      
        The panic in panel 11's jam lists the stack: main.share(...) on top (where it broke) and main.main() below (who called it). Chapter 8 reads these traces line by line. The (...) and the missing +0x offset on the share line are a sign the Compiler inlined share: it was so small that the Compiler copied its body into main instead of making a real call. The trace still names it, so you can find your way.
        
      
        What exactly is copied?
        
      
        The Go specification says that in a call, the argument values are evaluated and then assigned to the parameters, as if with =. For an int, a string or an array (chapter 6), that copies the whole value. Some types are themselves small "handles" to data stored elsewhere: slices (chapter 9), maps (chapter 12) and pointers (chapter 13). Copying a handle still copies only the handle, but both copies then lead to the same data. That's still call by value; it's the value that is a handle. Those chapters show what that means in practice.
        
      
        Multiple results
        
      
        Go returns several results directly; there is no hidden "tuple" object. A call with several results can be used only where several values fit: on the right of a, b := or a, b =, in a return of a function with the same result types (return strconv.Atoi(s)), or as the only argument list of another call (fmt.Println(divide(17, 5))). Anywhere else, such as divide(17, 5) + 1, the Compiler refuses.
        
      
        Standard input, and why the screen shows your typing
        
      
        Every program starts with three open streams: standard input (os.Stdin), standard output (os.Stdout, where Println writes) and standard error (os.Stderr, where Go's panic reports go). In a terminal, standard input is the keyboard. The terminal, not your program, shows the letters as you type them (that's called echo), and it sends them to the program only when you press Enter. With < file nothing is typed, so nothing is echoed: the panel 33 terminal shows no orders after the command, only the program's output.
        
      
        How Scan and the Scanner read
        
      
        fmt.Scan treats newlines as spaces and reads one space-separated word per box, converting it to the box's type (that's how &parcels, an int, got 3). Words it didn't use stay waiting in the input, which is the Boss 6 surprise. fmt.Scanln is the same but stops at the end of the line and complains if there are more words than boxes (here Lovelace was left over; Scanln's error said expected newline, but panel 31 never printed it). bufio.Scanner reads in chunks into a buffer (hence the package name) and hands out one line at a time; by default a single line may be up to 64 KB long.
        
      
        Inside Atoi
        
      
        strconv.Atoi(s) is the same as strconv.ParseInt(s, 10, 0) converted to int, as go doc showed in panel 21: base 10, and the size of an int, which is 64 bits on today's computers. Out-of-range input gives the biggest (or smallest) value that fits, together with the value out of range error. That's documented behaviour, not chance, but it's still not what was typed. The error value is a *strconv.NumError that remembers the function name, the input and the reason, which is why its message reads so clearly.
        
    
        
  
        

  
        
    In real programs: where you'll see these every day
    
        
      
          
        
        • (value, error) results are everywhere in Go's standard library: opening files, reading the network, parsing numbers, dates and JSON. Once you can read func Atoi(s string) (int, error), you can read most of Go's documentation.
          • 
        
        • Small functions with clear names are the house style. Look at the Go standard library source: most functions fit on one screen and start with a doc comment that begins with the function's name. Linters such as revive check for it on exported (capitalised) names.
          • 
        
        • bufio.Scanner over os.Stdin is how command-line tools that process text work: read a line, do something, print a line. Unix programmers call these filters, and chain them with pipes (cat orders.txt | go run lines.go does the same job as <).
          • 
        
        • os.Args is the raw list. Real tools usually use the flag package (also in the standard library) to read options like -v or --name=Ada; it's built on os.Args.
          • 
        
        • strconv is the fast, strict converter. fmt.Sscan exists too, but strconv.Atoi with its clear error is what you'll see in most code.
          • 
        
        • Naked returns appear in short helpers, and sometimes with defer (chapter 14). Style guides, including Go's own code review comments, suggest avoiding them in anything longer than a few lines.

    Common wrong ideas
    
        
      
          
        
        • "Defining a function runs it." Defining builds the machine. Only a call runs it.
          • 
        
        • "Functions must be written above the code that uses them." Not in Go. The Compiler reads the whole file first (panel 10).
          • 
        
        • "A function can change the caller's variable by changing its parameter." The parameter is a copy. Return the new value and store it.
          • 
        
        • "If a function returns something, Go makes me use it." A call on its own line silently throws the result away (panel 16). Unused variables are errors; unused results are not.
          • 
        
        • "return prints the value." It hands the value back to the caller. Nothing appears on the screen unless someone prints it.
          • 
        
        • "A function can only return one thing." In Go, as many as the signature lists.
          • 
        
        • "Covering every case in a switch is enough to avoid missing return." Not without default; the Compiler doesn't do the maths (panel 15).
          • 
        
        • "Input typed as 5 is a number." Input is always text. Convert it with strconv.Atoi, or let fmt.Scan convert into an int box.
          • 
        
        • "fmt.Scanln(&name) reads the whole line." It reads one word per box. Use bufio.Scanner for whole lines.
          • 
        
        • "os.Args[0] is the first word I typed." It's the program's own path. Your words start at os.Args[1]. With go run, the program is built in a temporary folder, so os.Args[0] is a long temporary path.
          • 
        
        • "When Atoi fails, the number is 0, so I can just use it." 0 is a placeholder; for out-of-range input it isn't even 0. When err isn't nil, ignore the number.
          • 
        
        • "string(65) turns 65 into "65"." It gives "A", the character with code 65, and go vet warns about it. Use strconv.Itoa(65).

    Words from this chapter
    
        
      
        
        
        function
        A named machine: values go in, the body runs, results come out. Defined with func.
        
        
        define / definition
        Writing the function: func name(…) … { … }. Runs nothing by itself.
        
        
        call
        Running a function: name(arguments). The run jumps in, then back.
        
        
        parameter
        A box in the signature, like km int, filled at each call.
        
        
        argument
        The value you pass in a call, like 3 in fee(3). Copied into the parameter.
        
        
        signature
        A function's first line: name, parameters and result types.
        
        
        return
        Ends the function and hands its results back to the caller.
        
        
        result (return value)
        What comes out of the drawer. A Go function may have none, one, or several.
        
        
        named results
        Results given names in the signature, like (each, left int). They start at their zero values.
        
        
        naked return
        A bare return that hands back the named results. Fine in short functions only.
        
        
        blank identifier _
        The blank box: catches a result you don't want.
        
        
        doc comment
        The comment directly above a function, starting with its name. Read by gopls and go doc.
        
        
        call by value
        Arguments are copied into parameters. The function works on its copy.
        
        
        frame (stack frame)
        The room a call gets for its parameters and local boxes. Gone when the call returns.
        
        
        call stack
        The pile of frames for the calls running right now, main at the bottom.
        
        
        local variable
        A box made inside a function; only that function can see it.
        
        
        top level
        Outside every function's braces. Named functions are declared there.
        
        
        decomposition
        Splitting a big job into small named functions.
        
        
        input
        Data that comes into a running program from outside. Always text at first.
        
        
        prompt
        Text that tells the person what to type, usually printed with Print.
        
        
        standard input (os.Stdin)
        The program's mail slot: the keyboard, or a file fed with <.
        
        
        fmt.Scan / fmt.Scanln
        Read space-separated words into boxes; Scanln stops at the end of the line.
        
        
        & (address of)
        For now: "the address of this box", so Scan can deliver into it. Chapter 13.
        
        
        bufio.Scanner
        Reads input one whole line at a time: Scan() fetches, Text() hands it over.
        
        
        redirect <
        Terminal syntax that feeds a file to a program's standard input.
        
        
        os.Args
        The words on the command line. Slot 0 is the program itself.
        
        
        strings.TrimSpace
        Removes spaces (and tabs and newlines) from both ends of a string.
        
        
        strconv.Atoi
        Text to int. Returns (int, error).
        
        
        strconv.Itoa
        int to text.
        
        
        strconv.ParseFloat
        Text to float64. Returns (float64, error).
        
        
        error
        Go's type for the receipt that says what went wrong. nil, a blank receipt, means no error.
        
        
        nil
        "Nothing here". An error that is nil means all went well.

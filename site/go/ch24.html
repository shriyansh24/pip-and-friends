CHAPTER 24 · INTERMEDIATE

HELPERS AND BATONS

Picture: Scoot, the bike courier in a red cap and green jacket, cheers with both arms up.

Until now, every Go program you wrote did one thing at a time. Today the depot kitchen hires helpers: functions that run at the same time as each other, called goroutines. You'll learn how the head chef waits for them with a clipboard, how helpers pass results along a channel like runners passing a relay baton, how a mailbox with slots lets them stop waiting for each other, and how select watches several doors at once. You'll also meet the runtime's most famous message: all goroutines are asleep - deadlock! About 140 minutes, with 26 hands-on checks.

  1. One cook, many hands: goroutines
  2. The clipboard: sync.WaitGroup
  3. The relay baton: unbuffered channels
  4. The mailbox: buffered channels, close and range
  5. Watching several doors: select
  6. Boss level and recap

Two words people mix up. Both are about doing several things, but they're not the same.

    

      

        CONCURRENCY
        
        
Dealing with many jobs at oncehow you organise the work

        
One juggler, three balls. Only one ball is in a hand at any instant, but all three are "in progress". Goroutines let you write a program as several jobs that overlap.

      

      

        PARALLELISM
        
        
Doing many jobs at the same instantneeds several CPU cores

        
Two jugglers, each with a ball in hand at the same moment. That needs real hardware: a computer's processor has several cores, and each can run code at the same time.

      

    

    cores.go
    

    

    
This book's machine has 2 cores; yours probably has more, so your first two lines will differ. GOMAXPROCS is how many goroutines Go lets run at the same instant; it starts out equal to the number of cores. runtime.NumGoroutine() counts goroutines: right now there's only one, main itself. Main is a goroutine too.

    

      
      
The Professor says: Go's scheduler, part of the runtime built into every Go program, shares those cores among all your goroutines. You write concurrent code; on a machine with several cores, Go runs it in parallel when it can.

PART 2 · THE CLIPBOARDsync.WaitGroup: Add, Done, Wait and wg.Go


  

    8
    
The fix for panel 5: before the head chef goes home, he checks a clipboard listing who is still cooking. In Go the clipboard is a sync.WaitGroup, from the standard library's sync package ("sync" is short for synchronisation: making things happen in a safe order).

    

      
ADD
wg.Add(1)before hiring a helper
Write one more name on the clipboard. The hidden counter goes up by one.

      
DONE
wg.Done()the helper's last act
Cross one name off. The counter goes down by one. Usually written defer wg.Done() (chapter 14) so it happens however the helper finishes.

      
WAIT
wg.Wait()the head chef, at the door
Blocks (stands still, doing nothing) until the counter is back to 0. If it's already 0, it returns at once.

  3. helper 3 · pie

      
counter = 2 → Wait keeps waiting

    PART 3 · THE RELAY BATONchannels: make, send, receive, and the handshake
    

  
    
    16
    
    Slots work when main knows in advance where every result goes. But often a helper needs to hand something to another goroutine: a finished dish, a message, a number. Enter Rosa, who runs the depot's mail.
    
    
    
      
    Rosa says: A channel is a delivery route between goroutines. One goroutine sends a value into it, another receives it out. Every channel carries one type of value: a chan string carries strings, a chan int carries ints.
    
      
    
    
    
    
      
      
    Scoot says: My favourite rule: don't share the note. Send it! Instead of two helpers scribbling on the same desk, one passes the note to the other, and then it's theirs.

    18
    
    A channel made with plain make(chan T) is unbuffered: it has no room to store anything. Think of a relay race: the baton never lies on the track. It passes from hand to hand, so both runners must be at the same spot at the same moment.
    
    
    
    
    
      
      
    Scoot says: Catchphrase: I wait at the door until someone takes the letter. A send on an unbuffered channel waits for a receiver; a receive waits for a sender. When they meet, the value changes hands and both carry on. That meeting is a handshake, and it also tells each side exactly where the other one is.

    20
    
    
    What if main sends on an unbuffered channel and no other goroutine exists to receive?
    
    deadlock_send.go
    
    
    
    
    
    
      
      
    Scoot says: Read it like a detective. First line: fatal error: all goroutines are asleep - deadlock! Every goroutine (here just main) is blocked, waiting for something that can never happen. Then: goroutine 1 [chan send], main, stuck in a chan send. Then where: deadlock_send.go:7. Line 7 waits at the door forever, so sent! never prints.
    
    
    
    
    A deadlock is when goroutines wait for each other (or for nothing) and none can ever move. Go's runtime notices when every goroutine is stuck and stops the program with a fatal error. Unlike a panic, a fatal error can't be caught or recovered. The +0x28 at the end is an offset inside the compiled code; it changes between Go versions, so ignore it. As always, go run reports the program's exit code 2 as exit status 2.
    
    
    A burst says ZZZ, for goroutines asleep.

    PART 4 · THE MAILBOXbuffered channels, close, comma-ok, range and one-way channels
    

  
    
    22
    
    Give make a second number and the channel gets a buffer: a mailbox with that many slots. make(chan string, 3) holds up to 3 letters. That number is its capacity.
    
    
    
      
    ROOM LEFT
    send doesn't waitwhile a slot is free
    The sender drops the letter in and walks on. Nobody needs to be receiving.
    
      
    LETTERS IN
    receive doesn't waitwhile a letter is there
    The receiver takes the oldest letter: first in, first out, like a queue.
    
      
    FULL / EMPTY
    then they waitjust like the baton
    Sending to a full box waits for a free slot; receiving from an empty box waits for a letter.
    
    
    
    
    
      
    Rosa says: len(ch) tells you how many letters are in the box right now; cap(ch) how many slots it has. An unbuffered channel is a mailbox with zero slots: cap is 0.

    31
    
    Who should raise the flag? Only the one who knows there's no more mail: the sender.
    
    
    
      
    DO
    • Close from the sending side, after the last send.
    • Close when a receiver is waiting for the end: a range loop, or a comma-ok check.
    • With one sender, that sender closes when it's done.
    
      
    DON'T
    • Close from the receiving side: the sender may still post, and panic.
    • Close twice, or close a channel you're not sure is open.
    • Close "to tidy up": a channel nobody waits on doesn't need closing; it's cleaned up like any other value.
    
    
    
    
    
      
      
    Rosa says: Catchphrase: the sender closes. A receiver who closes is like a reader nailing the mailbox shut while the carrier is still on the way.

    nonblock.go
    
    
    
    
    
    
      
      
    Scoot says: Peek in the box: empty, so default runs and the program keeps going. After line 13 posts a postcard, the same peek finds it. Like checking the mailbox on your way past instead of standing next to it all day.
    
    
    
  
    

  
    
  

  
    
    38
    
    Waiting forever is rarely what you want. time.After(d) (chapter 22's clocks) returns a channel that receives one value after the Duration d. Put it in a select, and whichever happens first wins: the dish or the timer.
    
    timeout.go
    
    
    
    
    
    
      
      
    Scoot says: First order: the stew needs 500 ms but we only wait 50 ms, so the timer's door opens first. Second order: 20 ms of cooking against a 1-second timer, so the stew wins. The gaps are wide on purpose, so the result is the same on every run.
    
    
    
    
    Why does slowCook make its channel with one slot? After the first timeout, nobody will ever receive that stew. With an unbuffered channel, the cook's send would wait forever: a goroutine stuck for the rest of the program, called a goroutine leak. With one slot it drops the stew in and finishes. Chapter 25 is all about stopping goroutines cleanly.

    One last trap. var ch chan int declares a channel but never calls make, so it holds the zero value for channels: nil, a route that leads nowhere.
    
    nilchan.go

Inside a select, a nil channel's case is simply never chosen, which experts use on purpose to switch a case off.

    41
    
    What you learned in Chapter 24
    
    
      
      
    • NEED MORE HANDS? JUST SAY GO!go f() starts f as a goroutine and carries on at once. Goroutines are cheap; Go's scheduler shares the CPU cores among them (GOMAXPROCS at a time). Concurrency is organising overlapping jobs; parallelism is running them at the same instant.
      • 
      
    • WHEN MAIN LEAVES, THE KITCHEN CLOSESThe program ends when main returns, and running goroutines are stopped mid-dish. Wait for them: wg.Add(1) before go, defer wg.Done() inside, wg.Wait() before leaving, or just wg.Go(f) (Go 1.25). One Done too many panics: negative WaitGroup counter.
      • 
      
    • HELPERS FINISH IN ANY ORDERScheduling order isn't promised. For a dependable result, give each helper its own slot, or collect results and combine them in a way where order doesn't matter.
      • 
      
    • I WAIT AT THE DOOR UNTIL SOMEONE TAKES THE LETTERAn unbuffered channel is a handshake: send waits for a receiver and receive waits for a sender. A buffered channel, make(chan T, n), is a mailbox with n slots, first in first out; it waits only when full or empty. When every goroutine waits: all goroutines are asleep - deadlock! with [chan send] or [chan receive].
      • 
      
    • THE SENDER CLOSESclose(ch) raises the no-more-mail flag: letters inside are still delivered, then receives return the zero value with ok == false, and for v := range ch ends.       • 
      
    • SELECT OPENS THE FIRST DOOR THAT'S READYselect waits for whichever case can go ahead, picking at random among several ready ones; default makes it not wait at all; a time.After case gives up after a timeout.

    Under the hood: the scheduler, what a channel is made of, and how deadlocks are spotted
    
    
      
    Goroutines, threads and the scheduler
    
      
    Your operating system runs threads: each has its own stack, often a megabyte or more, and switching between them goes through the OS. Go puts many goroutines on a few threads. The runtime's scheduler is usually described with three letters: G (a goroutine), M (a machine: an OS thread) and P (a processor: a permission to run Go code). There are GOMAXPROCS Ps. Each P has a queue of runnable Gs, and an M must hold a P to run them. A newly started goroutine goes into a special "run next" spot of the current P, which is why tiny programs so often run the last goroutine started first (try panel 10's order_quick.go). Idle Ps steal work from busy ones. Since Go 1.14 a goroutine that runs too long without pausing can be interrupted, so one busy loop can't hog a core forever.
    
      
    Small, growable stacks
    
      
    A goroutine starts with a small stack (a couple of kilobytes) and the runtime grows it, by copying it to a bigger block, when a function call needs more room. That's why ten thousand goroutines (panel 15) cost only a few tens of megabytes at most, and why Go programs can afford a goroutine per network connection.
    
      
    What a channel is made of
    
      
    A channel value is a pointer to a small structure in the runtime: a lock, a ring buffer with cap slots (empty for unbuffered channels), counters for the front and back of the queue, a "closed" flag, and two waiting lines, one of blocked senders and one of blocked receivers. A blocked goroutine is parked: taken off its P and put in the waiting line, costing no CPU at all. On an unbuffered channel the runtime copies the value straight from the sender to the waiting receiver. That's also why passing a channel to a function copies only the pointer: both sides share the same channel.
    
      
    How "all goroutines are asleep" is noticed
    
      
    The runtime declares a deadlock only when every goroutine is blocked and nothing (no timer, no network, no system call) could ever wake one. If even one goroutine is sleeping in time.Sleep or waiting on the network, the runtime can't be sure, so it says nothing. That's why a stuck helper in a long-running server isn't reported: it just sits there forever, a goroutine leak. Go 1.27 made a goroutine leak profile generally available for finding such goroutines; chapter 25 comes back to it.
    
      
    WaitGroups and "happens before"
    
      
    The sync documentation says that the return of a function started with wg.Go "synchronizes before" the return of the Wait call it unblocks. In plain words: everything a helper wrote before finishing is guaranteed to be visible to main after Wait. That's what makes panel 11's slot pattern correct, and not just lucky. Channels give the same guarantee: a send happens before the matching receive completes. The rules are in the Go memory model document.
    
      
    One variable per loop trip (Go 1.22)
    
      
    Before Go 1.22, a for loop had a single i shared by every trip, so goroutines started in the loop often all saw its last value. Since Go 1.22 (decided by the go line in go.mod) each trip gets a fresh variable, which is why this chapter's helpers can use i and d directly. Older tutorials pass the value as an argument, go func(i int) {...}(i), to work around the old rule.
    
      
    GOMAXPROCS
    
      
    The default is the number of CPU cores the program may use. Since Go 1.25 it also respects a container's CPU limit on Linux. You can override it with the environment variable GOMAXPROCS=1 or by calling runtime.GOMAXPROCS(n), but you rarely should. With GOMAXPROCS=1 goroutines are still concurrent, just never parallel.
    
    
    
  
    

  
    
    In real programs: where helpers and batons show up
    
    
      
      
        
    • Web servers. Go's net/http server runs every incoming request in its own goroutine, so a slow visitor never holds up a fast one (chapter 26).
      • 
        
    • Doing many slow things at once. Fetching ten web pages, resizing a folder of photos, querying three databases: start one goroutine per job and collect the results on a channel or into slots, as in panels 11 and 21.
      • 
        
    • Timeouts. Every network call needs a "give up after" rule. select with time.After is the basic form; the context package (chapter 26) builds on it and can cancel a whole tree of goroutines at once.
      • 
        
    • Queues between parts of a program. A buffered channel lets a fast producer get ahead of a slower consumer by a bounded amount, like a print queue or a log writer.
      • 
        
    • Signals. signal.Notify delivers Ctrl+C to your program as a value on a channel, so a server can finish its work and shut down cleanly.
      • 
        
    • Tickers. time.NewTicker (chapter 22) sends on a channel at a steady rate: games, dashboards and health checks use it in a select loop.
      • 
        
    • "Done" signals. A channel that is only ever closed, never sent on, is a cheap way to tell many goroutines at once that it's time to stop: every receive on it returns immediately after close. Chapter 25 uses this.
      • 
      
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "go f() waits for f." It returns at once. Use a WaitGroup or a channel to wait.
      • 
        
    • "The program waits for its goroutines before exiting." It ends the moment main returns.
      • 
        
    • "Goroutines run in the order I start them." No order is promised (panel 10).
      • 
        
    • "Adding time.Sleep makes it wait long enough." It might, on your machine, today. Sleep guesses; WaitGroups and channels know.
      • 
        
    • "wg.Add(1) can go inside the goroutine." Then main might reach Wait before the helper has added itself, and leave early. Add before go, or use wg.Go.
      • 
        
    • "A buffered channel never blocks." It blocks when full (send) or empty (receive).
      • 
        
    • "Closing a channel deletes the values in it." Values already inside are still delivered.
      • 
        
    • "You must close every channel." Only when a receiver needs to know the end has come. Unclosed channels are garbage-collected like anything else.
      • 
        
    • "The receiver should close when it has had enough." The sender closes. A receiver that closes makes the sender panic.
      • 
        
    • "select tries the cases from top to bottom." Among ready cases it picks at random.
      • 
        
    • "A deadlock is always reported." Only when every goroutine is stuck. A partly stuck program just hangs, or leaks.
      • 
        
    • "More goroutines always means faster." Only when there is waiting to overlap or cores to use. A goroutine per tiny addition costs more than the addition.

    Words from this chapter
    
    
      
    
        
    goroutine
    A function call running on its own, alongside the rest of the program, managed by the Go runtime. main is one too.
    
        
    go statement
    go f(x): start f(x) as a new goroutine and continue without waiting.
    
        
    concurrency
    Structuring a program as several jobs whose lifetimes overlap.
    
        
    parallelism
    Running several jobs at the same instant, on different CPU cores.
    
        
    CPU core
    One part of a processor that can run instructions; a processor usually has several.
    
        
    scheduler
    The part of the Go runtime that decides which goroutine runs on which core, and when.
    
        
    GOMAXPROCS
    How many goroutines may run Go code at the same instant; by default, the number of cores available.
    
        
    sync.WaitGroup
    A counter for waiting on a group of tasks: Add, Done, Wait, and Go (Go 1.25).
    
        
    block (verb)
    Not the { } block of chapter 3: to stop and wait until something happens, using no CPU meanwhile.
    
        
    channel
    A typed route for passing values between goroutines; made with make(chan T) or make(chan T, n).
    
        
    send, receive
    ch <- v puts a value into a channel; <-ch takes one out.
    
        
    unbuffered channel
    A channel with capacity 0: every send waits for a matching receive (a handshake).
    
        
    buffered channel, capacity
    A channel with n slots; sends wait only when it's full, receives only when it's empty.
    
        
    close
    Mark a channel as finished: no more sends; receives drain what's left, then get the zero value.
    
        
    comma-ok receive
    v, ok := <-ch: ok is false when the value came from a closed, empty channel.
    
        
    send-only, receive-only
    The one-way channel types chan<- T and <-chan T.
    
        
    nil channel
    A channel variable that was never made; sending or receiving on it blocks forever.
    
        
    select
    Waits until one of several sends or receives can proceed and runs that case; random among ready cases.
    
        
    non-blocking
    An operation that never waits; in Go, a select with a default case.
    
        
    timeout
    A limit on how long to wait; often a time.After case in a select.
    
        
    deadlock
    Goroutines waiting for each other (or for nothing) so that none can ever continue.
    
        
    fatal error
    A runtime failure that stops the program and can't be recovered, unlike a panic.
    
        
    goroutine leak
    A goroutine that stays blocked forever, holding its memory, because nothing will ever wake it.

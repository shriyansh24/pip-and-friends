Picture Go's module system as a library. A module is a book series with a name on its spine. Each version is one printing of that series, and printings never change once they're on the shelf. (These library shelves hold module versions; they aren't chapter 9's slice shelf.)

Scoot says: So Bo can keep borrowing v1.0.0 while I print v1.1.0. Bo's copy never changes under Bo's feet. Catchphrase: a printing never changes; a breaking change gets a new shelf.

3

Go versions follow semantic versioning ("semver"): a v, then three numbers. Each number is a promise to the people borrowing your code.

v1.4.2

MAJOR1

Goes up when old code that uses you might break: a function removed, renamed, or given a new parameter.

MINOR4

Goes up when you add something new and everything old still works.

PATCH2

Goes up for a fix that doesn't change what the code promises.

The version v1.4.2 split into three parts: major 1, minor 4, patch 2, with what each one promises.

The Professor says: Two special cases. Versions starting with v0, like v0.3.1, promise nothing yet: anything may change. And a dash adds a pre-release tag, like v1.5.0-beta.1, which comes before v1.5.0, and @latest skips it while a normal release exists.

Go's answer is one rule, the import compatibility rule: if the new code has the same import path as the old, it must still work for old callers. A breaking version therefore gets a different import path, ending in /v2.

    

      

        SHELF v1
        import "example.com/stamps"
        
v0.x.x and v1.x.xno suffix

        
Every v1 printing keeps the old promises. Fixes and additions only.

      

      

        SHELF v2
        import "example.com/stamps/v2"
        
v2.x.xa /v2 on the end of the path

        
A new shelf, with new promises. To Go it's a different module, so it can't break anyone on shelf v1.

    19
    
    So init is handy. Why do experienced Go programmers avoid it?
    
    
      
      
    1. It's invisible. Nothing in main says it runs. A reader has to search every file of every imported package to know what happened before line 1 of main.
      2. 
      
    2. It can't return an error. If opening a file or reading a setting fails inside init, the only options are to ignore it or to panic, and the program dies before main starts.
      3. 
      
    3. It runs even in tests, every time the package's tests run (tests are chapter 23), whether a test needs it or not.
      4. 
      
    4. It creates hidden global state, package variables that any code can lean on, which makes order bugs hard to find.
      5. 
    
    
    
    
      
      
    The Professor says: Prefer a plain function you call yourself, like cfg, err := loadConfig() at the top of main: visible, testable, and it returns an error. Keep init for small, certain set-up, such as filling a lookup table. You'll still see one common use: import _ "image/png", where the underscore imports a package only for its init, which registers the PNG decoder.

    Under the hood: how Go picks versions, what the proxy really is, and what bufio and os.Exit do
    
      
      
      Minimal version selection
      
      
      A require line means "at least this version". When several modules require different versions of the same module, Go doesn't pick the newest one in existence: it picks the highest version that anyone in the build asked for, and nothing newer. This rule is called minimal version selection (MVS). Its big advantage is that a build is the same tomorrow as today: a new printing on the shelf changes nothing until someone runs go get and writes the new version into a go.mod. That's why a new printing reaches your build only when someone runs go get (with a version or @latest) and writes it into go.mod: @latest is something you ask for, not something that happens.
      
      
      Graph pruning and // indirect
      
      
      Since Go 1.17 (with a go 1.17 or later line), the main module's go.mod lists every module that provides a package your build uses, including ones you only reach through other modules; those carry // indirect. With that full list in hand, the go command doesn't need to read the go.mod file of every module in the whole graph, which keeps builds fast. It's also why panel 5 shows ink in Scoot's go.mod even though no depot file imports it.
      
      
      The proxy protocol
      
      
      A module proxy answers a handful of plain requests: <module>/@v/list (the versions), <module>/@v/<version>.info (its time), .mod (its go.mod) and .zip (its files). Anything that answers those, even a folder read through a file:// address, is a proxy. This chapter's library is exactly that: a folder built from the module sources, with GOPROXY=file:///home/you/go-ch21/.proxy, GOSUMDB=off and a module cache inside the chapter folder. By default GOPROXY is https://proxy.golang.org,direct: ask the public proxy, and if it doesn't have a module, fetch it straight from its repository.
      
      
      go.sum and the checksum database
      
      
      The h1: hash is a SHA-256 over the names and contents of every file in the module (or of its go.mod alone, for the /go.mod line). The first time anyone in the world downloads a version, the public checksum database (sum.golang.org) records its hash, and every later download is checked against it, so even the proxy can't quietly change a printing. This chapter turned that check off (GOSUMDB=off) because its modules are private and offline; go.sum still checked every build. For private company modules, people set GOPRIVATE instead, which skips the proxy and the database for matching paths.
      
      
      The module cache is read-only
      
      
      Downloaded modules live in $GOPATH/pkg/mod (by default go/pkg/mod in your home folder), one folder per version, such as example.com/stamps@v1.1.0. Go marks those files read-only so nobody edits a printing by accident; to change borrowed code, use a local copy with replace or go work, as in part 4. go clean -modcache empties the cache.
      
      
      How a bufio.Writer decides when to write
      
      
      A bufio.Writer is a byte slice (4096 bytes by default) plus a count. Write copies into the slice while there's room. When a write doesn't fit, it tops up the slice, writes the whole slice to the Writer underneath, and starts again; a write bigger than the whole buffer, arriving at an empty buffer, goes straight through. Panel 32's stepper follows exactly those rules, which is why a full bucket poured parcel 1⏎parcel· with half a word at the end. Flush writes whatever is left. If any underlying write fails, the Writer remembers the error and every later call returns it, so checking Flush's error is enough to catch a failure anywhere.
      
      
      bufio.Scanner's limits
      
      
      A Scanner splits its input into tokens, lines by default. sc.Split(bufio.ScanWords) gives words instead, and bufio.ScanRunes one character at a time. A single token may be at most 64 KB by default; a longer line stops the loop and sc.Err() returns bufio.ErrTooLong ("token too long"). sc.Buffer(make([]byte, 1024*1024), 1024*1024) raises the limit. That's one more reason to always check sc.Err().
      
      
      Files are numbers to the operating system
      
      
      When you open a file, the operating system hands back a small number, a file descriptor; *os.File wraps it. 0, 1 and 2 are standard input, output and error. Each process may hold only so many at once (often 1024 by default on Linux, shown by ulimit -n), which is why panel 35's leak matters. Go also attaches a cleanup to each *os.File that closes it eventually if it becomes garbage, but "eventually" may be far too late; close files yourself.
      
      
      os.Exit versus returning from main
      
      
      Returning from main ends the program with code 0 after main's deferred calls have run. os.Exit(n) asks the operating system to end the process immediately: no deferred calls, in any function, and buffered writers are not flushed. A panic that nobody recovers ends with code 2. Codes above 125 have special meanings to shells, so programs normally use small numbers; the flag package uses 2 for "bad command line", which is a common convention.
      
      
      How //go:embed works
      
      
      While building, the go command reads the directive, finds the matching files (relative to the source file's folder, never outside the module, and skipping names starting with . or _ unless you write all: in front of the pattern), and stores their contents in the program file itself. An embed.FS implements fs.FS, so fs.WalkDir, fs.ReadFile and web servers can read from it like a folder.

    Common wrong ideas
    
      
      
        
        
      • "// indirect lines are optional." They're real requirements. Only the comment is a comment.
        • 
        
      • "go get installs programs." Since Go 1.18 it only edits go.mod. Programs are installed with go install path@version.
        • 
        
      • "Go always uses the newest version of a dependency." It uses the highest version that some go.mod asks for, never a newer one by surprise.
        • 
        
      • "I can fix a release by uploading it again." A printing never changes. Publish a new patch version and retract the bad one.
        • 
        
      • "v2 is just a new tag." It's a new tag and a new module path ending in /v2. Without the path change, Go rejects the tag (or treats old modules as +incompatible).
        • 
        
      • "internal is a keyword." It's only a folder name the go command checks. Capitalised names inside an internal package are still exported to the packages allowed in.
        • 
        
      • "A util package keeps things tidy." It becomes a junk drawer that everything imports. Name packages for what they provide.
        • 
        
      • "Committing a replace to a local folder is fine." It breaks everyone else's build, and replace lines are ignored when someone borrows your module anyway.
        • 
        
      • "The bufio.Writer flushes when the program ends." Nothing flushes it but you (panels 31 and 32).
        • 
        
      • "defer f.Close() in a loop closes each file at the end of the lap." Deferred calls wait for the function to return.
        • 
        
      • ""dir" + "/" + name is good enough." It breaks on Windows and when parts already have slashes. Use filepath.Join; use path.Join (forward slashes always) only for URLs and embed.FS paths.
        • 
        
      • "Flags can go anywhere." Go's flag stops at the first non-flag argument.
        • 
        
      • "os.Exit runs my deferred cleanup." It runs nothing. Neither does log.Fatal.
        • 
        
      • "go run's exit code is my program's exit code." It prints exit status N and exits with 1 itself; build the program to pass the code through.

    Words from this chapter
    
      
      
      
        
      module
      A collection of packages with one go.mod, released together under one module path and version.
      
        
      module path
      The module's name, from go.mod's module line; usually where its code lives, like github.com/scoot/stamps.
      
        
      semantic versioning
      vMAJOR.MINOR.PATCH: breaking changes, additions, fixes. v0 promises nothing; a -beta.1 suffix marks a pre-release.
      
        
      dependency
      A module your module borrows. A dependency of a dependency is marked // indirect in go.mod.
      
        
      go get path@version
      Adds or changes a requirement in go.mod. @latest means the newest version that isn't retracted.
      
        
      go.sum
      Checksums (fingerprints) of every module version the build uses, so a changed download is caught.
      
        
      module proxy
      A server (or folder) that hands out module versions; the default is proxy.golang.org.
      
        
      module cache
      The read-only folder where downloaded modules are kept, normally go/pkg/mod.
      
        
      directive
      A keyword line in go.mod (module, go, require, replace…), or a //go: comment that tools read.
      
        
      retract
      An author's go.mod directive saying "don't use this version of mine".
      
        
      major version suffix
      The /v2, /v3… at the end of the module path for versions 2 and later.
      
        
      import compatibility rule
      Code with the same import path must stay compatible with old callers.
      
        
      internal package
      A package under a folder named internal; only code in the folder that holds it may import it.
      
        
      stutter
      Repeating the package name in an exported name, like stamps.StampsStamp.
      
        
      init
      A function Go runs automatically before main, after package-level variables are set.
      
        
      doc comment
      A comment directly before package or an exported name; shown by go doc and pkg.go.dev.
      
        
      replace
      A go.mod directive that uses a different copy of a module, such as a local folder.
      
        
      workspace, go.work
      A file listing several local modules to build together, without editing their go.mod files.
      
        
      vendoring
      Copying the packages a build needs into a vendor/ folder in the project.
      
        
      go install path@version
      Downloads, builds and installs a program into GOBIN.
      
        
      toolchain, GOTOOLCHAIN
      A Go release (compiler and go command); the setting that says whether Go may download a newer one.
      
        
      buffer, bufio.Writer
      A bucket that collects small writes and passes them on in big pieces; emptied by Flush.
      
        
      Flush
      Writes everything still in the buffer to the Writer underneath.
      
        
      bufio.Scanner
      Reads a Reader one line (or word) at a time: Scan, Text, Err.
      
        
      file descriptor
      The small number the operating system uses for an open file; there's a limit per program.
      
        
      flags (open)
      os.O_APPEND, os.O_CREATE, os.O_WRONLY, os.O_TRUNC…: how os.OpenFile opens a file.
      
        
      permissions
      Who may read, write or run a file, like 0o644.
      
        
      path, absolute, relative
      Where a file lives; from the top of the disk, or from the current folder.
      
        
      filepath.Join
      Joins path parts with the system's separator and cleans the result.
      
        
      filepath.WalkDir
      Visits every folder and file under a folder, in lexical order.
      
        
      temporary file or folder
      One made with a random name in the system's temp folder by os.CreateTemp or os.MkdirTemp.
      
        
      command-line arguments, os.Args
      The words typed after a program's name; os.Args[0] is the program.
      
        
      flag (command line)
      An option like -n 3 or -loud, read by the flag package.
      
        
      environment variable
      A name=value setting a program inherits; read with os.Getenv or os.LookupEnv.
      
        
      exit code
      The number a program ends with: 0 for success. $? in a shell shows the last one.
      
        
      os.Exit
      Ends the program at once with a code, skipping every deferred call.
      
        
      //go:embed
      A directive that bakes files into the program as a string, []byte or embed.FS.

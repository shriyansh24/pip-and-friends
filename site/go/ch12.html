CHAPTER 12

COAT CHECKS, CHARACTER SHEETS

Picture: Scoot, the bike courier in a red cap and green jacket, waves hello.

Slices keep things in a row, found by position. This chapter brings two new ways to keep things. A map is a coat check: hand in a ticket, get your coat back. A struct is a character sheet: one card with a labelled box for every fact about a player. You'll meet the empty hanger, the counter that doesn't exist yet, the order that keeps changing and the photocopier that hides inside every =. About 110 minutes, with 30 hands-on checks.

  1. The coat check: maps
  2. Was the hook used? comma-ok, delete, the nil map
  3. Around the counter: order, counting, keys
  4. Character sheets: structs
  5. The photocopier: copies, comparing, the range trap
  6. Struct or map?
  7. Boss level and recap

PART 1 · THE COAT CHECKMaps: look things up by name, not by position

1

Tonight Scoot is helping at the theatre's coat check. Hundreds of coats, one small counter.

Scoot says: With a slice I'd have to say "give me coat number 214" and walk along the row. But guests don't know positions. They know their name.

Scoot says: So every guest writes a name on a ticket, I hang the coat, and later the ticket takes me straight to the right hook. No walking the row.

Picture: Scoot, focused, points ahead, holding a letter.

2

Go has this built in. It's called a map. Each entry pairs a key (the name on the ticket) with a value (what you get back). You find a value by its key, never by a position.

  1. 1A ticket is a key: the name you look things up by.
  2. 2What hangs on the hook is the value. Here: a hook number.
  3. 3The whole counter is the map: every key paired with its value.
  4. 4One ticket per name. A key appears at most once.

Scoot says: Catchphrase: hand in a ticket, get your coat. In this book the cabinet creature, a chest of labelled drawers, always means a map.

Picture: the cabinet creature, with drawers labelled ana, bo and cy.

3

    PART 3 · AROUND THE COUNTERLooping over a map, counting, maps of slices, and which keys are allowed
    

  
    
    16
    
    
    for k := range m visits every key of a map, like range over a slice. So Scoot loops over the same six keys five times in one run...
    
    order.go
    
    
    
    ONE POSSIBLE RUN
    
    
    
    
    
      
      
    Scoot says: Same map, same loop, five rounds. Compare the rows: nothing promises they match, from one round to the next or from one run to the next. Run it yourself and you'll likely see a different set of rows. That's why this page calls it "one possible run".
    
    
    
  
    

  
    
    17
    
    The Go specification says the order of a range over a map "is not specified and is not guaranteed to be the same from one iteration to the next". The counter staff fetch coats in whatever order is fastest for them. Go even picks a random starting hook each time, on purpose, so nobody's program can come to depend on one order.
    
    
      
      
    1. A slice remembers order: box 0, box 1, box 2.
      2. 
      
    2. A map remembers pairs, not order. "Which came first?" has no answer.
      3. 
      
    3. Your program must give the right answer whatever order range picks: totals and counts are fine; "print the first key" is not.
      4. 
    
    
    
    
      
      
    Scoot says: Catchphrase: a map has no order. Sort the keys.
    
    
    
  
    

  
    
    18
    
    One helpful exception: when fmt prints a whole map, it sorts the entries by key first, so the printout is the same every time.
    
    order_print.go
    
    
    
    
    
      
      
    1. map[apple:2 mango:3 zebra:1]
      String keys in dictionary-style order (byte by byte, chapter 5), not the order you typed them.
      2. 
      
    2. map[10:a 20:b 30:c]
      Number keys smallest first.
      3. 
    
    
    
    
      
      
    Scoot says: That's a printing nicety, not the map's order. The map itself still has none; a range loop still hops around.
    
    
    
  
    

  
    
  

  
    
    19
    
    To loop in a fixed order, take the keys out, sort them, and loop over the sorted slice. Modern Go does the first two steps in one line.
    
    sorted_keys.go
    
    
    
    
    
      
      
    1. slices.Sorted(maps.Keys(fruit)) (line 11)
      Read it inside out: maps.Keys hands over the keys (from the standard maps package, line 5), and slices.Sorted collects them into a new, sorted slice. For now treat it as a recipe; chapter 20 shows how it works.
      2. 
      
    2. for _, k := range keys (line 13)
      A slice has an order, so this loop is the same on every run. Inside, fruit[k] looks up each value.
      3. 
    
    
    
    
      
      
    Scoot says: Both packages need Go 1.23 or later for this recipe (the Go 1.23 release notes list slices.Sorted and maps.Keys as new). Older code builds a []string of keys with a loop and calls sort.Strings on it (chapter 10).

    Under the hood: hash tables, swiss tables and struct layout
    
            
      
            
        
        
            The Professor says: A coat check is fast because nobody walks the whole rail. A map is fast for the same reason: the key itself says roughly where to look.
            
      
            
      
            A map is a hash table
            
      
            Go's map is a hash table. A hash function turns each key into a big number, and part of that number picks a small group of slots to look in. Looking up, adding and deleting take about the same time whether the map holds ten entries or ten million (on average; it's not a promise for every single operation). Two different keys can land in the same group; then Go compares them with == to find the right one. That is why keys must be comparable: equality is the final check.
            
      
            Swiss tables, since Go 1.24
            
      
            Since Go 1.24 the runtime implements maps as "Swiss tables", a design that checks a whole group of slots at once using a few bits of each key's hash stored in a control word. The language didn't change; maps just got faster. Earlier versions used buckets of 8 entries with overflow buckets. Both of this page's toolchains (1.27.3 and 1.24.7) use Swiss tables.
            
      
            Why the order changes
            
      
            The specification leaves the order of range over a map unspecified. The runtime goes further: each range starts at a randomly chosen point, so a program that happens to work with one order fails quickly in testing instead of years later. When a map grows, entries also move to new slots. fmt sorts map keys before printing (since Go 1.12), which is why printed maps are stable and testable.
            
      
            What a map variable holds
            
      
            A map value is a pointer to the runtime's map structure. Copying a map variable or passing it to a function copies that pointer, which is panel 23's shared counter. A nil map is a nil pointer: reads see "no entries", and a write panics because there is no structure to put the entry in. make(map[K]V, n) accepts an optional size hint, n, so a map you know will be big can be allocated once.
            
      
            Why m[k].F = v is refused
            
      
            Map entries move around as the table grows, so Go never lets you take the address of a value inside a map. m[k] is therefore not "addressable" (the spec's word): it is a copy of the value. Assigning to a field of that copy would be silently lost, so the Compiler rejects it. Storing pointers to structs, map[string]*Hero, is the other common answer (chapter 13).
            
      
            A struct is its fields, side by side
            
      
            A struct value is one block of memory holding its fields in declaration order, with small gaps (padding) where needed to keep each field aligned for the processor. There is no hidden pointer, which is why assignment copies every field. Two structs of the same type are equal when every field is equal; a struct containing a slice, map or function field is not comparable at all, and so can't be a map key. The empty struct struct{} takes no memory; map[string]struct{} is a common way to write a set.
            
    
            
  
            

  
            
    In real programs: where maps and structs show up
    
            
      
              
        
            • Counting and grouping. Word counts, votes, log lines per error code: counts[k]++. Grouping: groups[k] = append(groups[k], v) (panel 22).
              • 
        
            • Sets. "Have I seen this before?" with map[string]bool or map[string]struct{}, checked with comma-ok.
              • 
        
            • Lookup tables and caches. Country code to name, user ID to user. A cache keeps answers you computed once so you don't compute them again.
              • 
        
            • Configuration and HTTP headers. The standard library's http.Header is a map[string][]string: a map of slices.
              • 
        
            • Records. Almost every program has structs for its main things: User, Order, Config. Chapter 22 turns structs into JSON and back using field names.
              • 
        
            • Table-driven tests. A slice of anonymous structs, one per test case (panel 39), is the standard Go test style (chapter 23).
              • 
        
            • Struct keys. map[Point]bool for "visited squares" on a game board, or map[struct{ Path, Country string }]int for hit counts by two things at once.
              • 
        
            • Maps and goroutines. A map must not be written by one goroutine while another reads or writes it; the runtime may stop the program with concurrent map writes. Chapter 25 shows how to guard one.
              • 
      
            
    
            
  
            

  
            
    Common wrong ideas
    
            
      
              
        
            • "Looking up a missing key is an error." You get the zero value. Use comma-ok to know whether it was there.
              • 
        
            • "A value of 0 means the key is missing." It might be a stored 0 (panel 9).
              • 
        
            • "Looking up a key adds it." Only assignment adds. len doesn't change on a lookup.
              • 
        
            • "var m map[string]int is an empty map." It's nil: you can read it, but writing panics.
              • 
        
            • "delete on a missing key panics." It does nothing.
              • 
        
            • "Maps keep the order I inserted." No order at all. fmt.Println sorts only for display.
              • 
        
            • "Map order is random, so I can use it to shuffle." It's unspecified, not uniformly random. Use math/rand to shuffle.
              • 
        
            • "b := a makes b another name for struct a." It's a full copy. (For maps and slices, it's a shared handle.)
              • 
        
            • "for _, p := range players { p.X = … } changes the players." It changes copies. Use the index.
              • 
        
            • "m[k].Field = v should work." The Compiler refuses: copy out, change, put back.
              • 
        
            • "Positional literals are shorter, so better." They break when the type changes. Name the fields.
              • 
        
            • "Any struct can be compared with ==." Only if every field can be. A slice field rules it out.
              • 
        
            • "A struct's zero value is always ready to use." Mostly, but a map field inside it is a nil map (Boss 6).

    Words from this chapter
    
            
      
            
        
            map
            A built-in type, map[K]V, that pairs keys of type K with values of type V and finds a value by its key.
            
        
            key, value
            The name you look up by (the ticket), and what you get back (the coat).
            
        
            entry
            One key with its value.
            
        
            map literal
            A map written out in code: map[string]int{"ana": 12}.
            
        
            zero value
            The value a type starts with: 0, "", false, nil, or a struct of zero fields. A missing map key gives the value type's zero value.
            
        
            comma-ok
            The two-result form v, ok := m[k]; ok reports whether the key is in the map.
            
        
            delete
            Built-in that removes one key from a map; a missing key is ignored.
            
        
            nil map
            A map variable with no map behind it (var m map[K]V). Reading works; writing panics.
            
        
            iteration order
            The order a range loop visits entries. For maps it is not specified and changes.
            
        
            comparable
            A type whose values can be checked with ==. Map keys must be comparable.
            
        
            hash table
            The data structure behind a map: a hash of the key picks where to look.
            
        
            struct
            A type made of named fields, each with its own type.
            
        
            field
            One named part of a struct, read and written with a dot: p.Name.
            
        
            struct literal
            A struct value written out in code, with field names (Player{Name: "Rin"}) or by position (Player{"Rin", 3, 20}).
            
        
            positional literal
            A struct literal without field names: every field, in order. Fragile.
            
        
            nested struct
            A struct used as a field of another struct.
            
        
            anonymous struct
            A struct type written in place, without a type name.
            
        
            exported, unexported
            A name starting with a capital letter can be used from other packages (exported); a small first letter keeps it private to its package.
            
        
            %+v, %#v, %T
            Printf verbs: values with field names; Go syntax; the type.
            
        
            addressable
            The spec's word for something you can assign into or take the address of. A map entry isn't.

C++ · CHAPTER 26

COOKIE CUTTERS AND BOUNCERS

Picture: Wren, the mechanic in orange coveralls, waves hello. Beside her stands Tin, a gingerbread-shaped tin cookie cutter with a little face and a plate that says template. Beside them, Ida the bouncer, broad-shouldered in a dark suit with an earpiece, holds a clipboard headed "integral" next to a velvet rope.

Wren is tired of writing the same function three times, once for int, once for double, once for std::string. So she cuts a cookie cutter out of tin: one shape, any dough. That's a template, and the Compiler stamps out a fresh cookie for every type you use. Then she hires Ida, a bouncer with a guest list, so that a type that can't do the job is turned away at the door with a short, clear message, instead of wandering in and making a mess deep inside. That's a concept. About 130 minutes, with 25 hands-on checks.

  1. One cutter, many cookies: function templates, deduction, explicit arguments, two type parameters, template or overload
  2. Cutters with settings: non-type parameters, class templates, CTAD, alias templates, specialisation
  3. Where cutters live, and how they jam: templates in headers, typename, reading long template errors
  4. The bouncer at the door: concepts, constraints not satisfied, standard concepts, three spellings
  5. Write your own guest list: concepts with requires expressions, overloading on concepts, over-constraining
  6. Boss level and recap

PART 1 · ONE CUTTER, MANY COOKIESFunction templates, deduction, explicit arguments, two type parameters, template or overload

1

Wren's workshop has a biscuit tin, and every Friday she bakes for the crew. The first week she cut each gingerbread person by hand with a knife: same shape, again and again, a little wonky every time. The second week she bent a strip of tin into that shape once, and pressed it into any dough she liked: ginger, chocolate, oat. Same shape, every time, in seconds.

Wren says: Code has the same problem. "Give me the bigger of two things" is one idea. It works the same for whole numbers, decimals and words. Writing it out once per type is the knife. Today we make the cutter: generic code, written once, for any type that fits.

2

Wren says: T is just a name, like a parameter name. People pick T for "type" by habit; Number or Item would work too. Inside, the body says a > b, so the pattern fits any type that knows how to do >. Remember that "any type that knows how to": it's what the bouncer in Part 4 checks.

    

  


  

    4
    
A cutter is not a cookie. You can't eat it. The template on lines 4 to 7 isn't a function either: on its own, the Compiler makes no machine code for it. Only when main calls bigger(3, 7) does the Compiler press the cutter into int dough and bake a real function, bigger<int>. That's called instantiation, and the function it makes is an instantiation of the template.

The Professor says: How did the Compiler know which dough? It looked at the arguments. 3 and 7 are ints, and the parameters are T a, T b, so T must be int. Working out T from the arguments is template argument deduction. All of it happens while compiling: by the time the program runs, there are just four ordinary functions.

Can we see the cookies? Yes. nm is a tool that lists the functions inside a compiled program, and -C turns their internal names back into C++. cookies.cpp has two templates: bigger, used with three types, and smaller (line 9), never used.

    6
    
Think of the template as a machine factory. Feed it a pair of values and it deduces T, builds a bigger machine for that type (only the first time), and runs it. Each chip is one line of bigger.cpp from panel 3. The last chip, from deduce_conflict.cpp, feeds it an int and a double.

    9
    
What if mixing types is the whole point? Give the template two type parameters: template <typename A, typename B> (line 4). Each is deduced separately. And what type does a + b make? Let the Compiler work it out with an auto return type (line 5).

    two_types.cpp

A template doesn't change the body's normal rules; it just runs them with the types you gave.

The Professor says: So when do you write a template, and when overloads? If the body is the same idea for every type, one template. If each type needs different work (printing a date is nothing like printing a colour), write overloads. And if one type needs a small exception to a general rule, a plain overload or a specialisation (Part 2) can sit beside the template.

    

  


  

  

  

  

  
  
PART 2 · CUTTERS WITH SETTINGSNon-type parameters, class templates, CTAD, alias templates, specialisation


  

    11
    
A template parameter doesn't have to be a type. template <int N> (line 4) takes a value, fixed while compiling: a non-type template parameter. stars<3> and stars<5> are two different stamped functions, each with its own number baked in. Line 12 mixes both kinds: a type T and a size N.

    non_type.cpp
    

      

      

    

    

      
      
Wren says: You've used one of these since Chapter 8: std::array<int, 4> is a class template with a type and a size. Line 26 is the neat part: total(scores) deduces both T = int and N = 4 from the array's type. The value must be known while compiling, so stars<n>() with a variable n read from the keyboard doesn't compile: the value of ‘n’ is not usable in a constant expression (the notebook shows the whole message).

      The Professor says: "But Chapter 10 said a function body in a header gives multiple definition errors when two files include it!" For ordinary functions, yes. That's why the whole standard library, std::vector included, is written in headers.

      PART 4 · THE BOUNCER AT THE DOORConcepts, constraints not satisfied, standard concepts, three spellings
      

  
      
    24
    
      Picture two parties. At the first, anyone can walk in. A guest who can't dance gets all the way to the dance floor, trips over three people and knocks the cake off the table. Nobody knows who let him in. At the second party, Ida stands at the door with a guest list. "Can you dance? No? Sorry, not tonight." No cake on the floor, and you know exactly why you didn't get in.
      
    
      
      
      
      Ida says: Panel 23 was the first party: Point walked straight into bigger and tripped on line 5, deep inside. I'm a concept: a named list of requirements a type must meet. Put me on a template and I check every type at the call, before anything is stamped. Not on the list? You hear it from me, at the door, in your own code.
      
    
      
    
      Picture: Ida the bouncer, stern, holds up her palm. Her clipboard reads "can dance", and the velvet rope beside her is hooked shut.
      
  
      

  
      
    25
    
      C++20 brings concepts, and the standard library ships ready-made ones in <concepts>. std::integral is the guest list "whole-number types": int, long long, short, char, bool and friends. Line 4 puts it where typename used to be: template <std::integral T> means "T is any type, as long as it's integral".

      What you learned in Chapter 26
      
    
        
      
      • THE CUTTER IS NOT A COOKIEA template (template <typename T>) is a pattern. The Compiler stamps a real function or class for each type you use: bigger<int>, Pair<std::string>. Unused templates make no code; each stamp has its own statics.
        • 
      
      • DEDUCTION NEVER CONVERTST is worked out from the arguments by exact match: bigger(3, 4.5) gives deduced conflicting types. Fix with matching arguments, explicit arguments (bigger<double>), or two type parameters. On a tie, a plain function beats a template.
        • 
      
      • CUTTERS CAN HAVE SETTINGSNon-type parameters (template <int N>), class templates with members written as Pair<T>::f, CTAD (Pair p{3, 5}), alias templates (Grid<char>), and template <> for one hand-made cookie.
        • 
      
      • THE WHOLE CUTTER GOES IN THE HEADERA template body hidden in a .cpp gives undefined reference to `int twice<int>(int)'. Inside a template, typename C::const_iterator marks a dependent name as a type. Read long errors from the first line and the required from here in your own file.
        • 
      
      • CHECK AT THE DOOR, NOT DEEP INSIDE THE PARTYA concept (template <std::integral T>, requires, std::integral auto) refuses wrong types at the call: no matching function, then constraints not satisfied and the rule that failed.
        • 
      
      • NAME WHAT THE CODE REALLY NEEDSWrite concepts with ||, && and requires expressions (requires(T x) { x / 2; } checks that lines compile; add requires inside to check truth). The pickiest list that fits wins an overload. Don't ask for more, or less, than the body uses.
        •

    Under the hood: two-phase lookup, mangled names, deduction rules and subsumption
    
      
      
      Two looks at every template
      
      
      The Compiler reads a template body twice. The first time, at its definition, it checks everything that doesn't depend on T: spelling, brackets, names like std::cout. The second time, at each instantiation, it checks everything that does, such as a > b for a Point. That's why panel 21 got an error at line 7 before any type was involved (first look), and then once more per type (second look). It's also why typename exists: during the first look, C::const_iterator can't be looked up yet, so the Compiler needs to be told what kind of name it is. The standard calls this two-phase name lookup.
      
      
      Each cookie has its own name
      
      
      Inside the object file, functions are stored under mangled names that encode their parameter types (and, for templates, the template arguments), so bigger<int> and bigger<double> can't collide. nm without -C shows the raw mangled names (on this toolchain they start with _Z); -C "demangles" them, which is what panel 5 printed. The linker matches these names exactly, which is why panel 18 complains about `int twice<int>(int)' and not about twice in general.
      
      
      What deduction does and doesn't do
      
      
        
        
      • For a parameter written T x (by value), top-level const and references on the argument are dropped, and an array argument decays to a pointer. bigger("fig", "date") therefore deduces T = const char* (the run below asks the Compiler) and compares addresses, not letters. Pass std::strings, as the comic does.
        • 
        
      • No conversions while deducing (panel 7), not even int to long, and no promotions.
        • 
        
      • A return type is never deduced from: with template <typename T> T make(), you must write make<int>(), like panel 5's exercise did with stamp<int>().
        • 
        
      • Explicit arguments fill parameters from left to right, and the rest are deduced: with template <typename To, typename From> To convert(From x) you can write convert<double>(3).
        • 
      
      
      
      How "pickier" is worked out
      
      
      Panel 34's rule is called subsumption. The Compiler breaks each concept down into its basic yes/no pieces (atomic constraints) joined by && and ||. If every way of satisfying list A also satisfies list B, then A subsumes B and wins. std::signed_integral<T> is defined as std::integral<T> && std::is_signed_v<T>, so it subsumes std::integral. Two lists written separately, even with the same words, are different pieces, and a call that fits both is ambiguous. Build stricter concepts out of looser ones and the ordering comes for free.
      
      
      Concepts are checked in order, and stop early
      
      
      In A && B, if A is false, B isn't even checked. That's why panel 27's totally_ordered<Point> reported the == requirements: equality comes first in its definition, failed, and the rest was never looked at. Panel 35's notes show the same thing the other way round: only floating_point<int> is reported, so integral<int> must have passed before it was checked.

    In real programs
    
      
      
        
        
      • The standard library is templates. std::vector<T>, std::map<K, V>, std::unique_ptr<T>, std::optional<T>, std::array<T, N>, std::max, std::sort: every one is a cutter. That's why its headers are so big, and why its errors mention _Tp and __a: those are the library's own template parameter names.
        • 
        
      • Constrained algorithms. The C++20 std::ranges algorithms (Chapter 25) are guarded by concepts such as std::ranges::random_access_range and std::sortable, which is why misuse now produces constraints not satisfied at your call instead of pages of errors from inside std::sort.
        • 
        
      • Header-only libraries. Many popular C++ libraries (JSON parsers, formatting and testing libraries such as the doctest used in Chapter 17) ship as headers only, because they're mostly templates. Adding one to a project is just an #include.
        • 
        
      • Compile times and code size. Every distinct instantiation is real code to compile and store. Big template-heavy programs control this by keeping templates small, moving type-independent work into ordinary functions, and sometimes using extern template (an explicit-instantiation declaration) to say "this cookie is baked in another file, don't bake it here".
        • 
        
      • Specialising library templates for your types. Real code specialises std::hash<MyKey> so MyKey can go in an unordered_map, and std::formatter<MyType> so std::format("{}", x) works for it.
        • 
        
      • Concepts as documentation. Teams write concepts such as Serializable or Shape that name exactly what their templates need, so the requirement is in the signature where users and tools can see it (Core Guideline I.9).
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "A template is a function." It's a pattern for making functions; nothing exists until it's used (panels 4 and 5).
        • 
        
      • "Templates convert arguments like normal functions." Not while deducing T (panel 7). Only with explicit arguments, and then silently (panel 8).
        • 
        
      • "All the stamped copies share one static." Each instantiation has its own (panel 5's exercise).
        • 
        
      • "typename and class mean different things in template <...>." In a template parameter list they're identical. (Outside it, typename also has its dependent-name job, panel 21.)
        • 
        
      • "Template bodies go in a .cpp like everything else." Then nobody can stamp them (panel 18).
        • 
        
      • "A long template error means my code is hopeless." Read the first error line and the required from here in your file; most of the rest is the trail (panel 23).
        • 
        
      • "A concept changes how the template runs." It only decides whether the template may be used, while compiling. The stamped code is exactly the same.
        • 
        
      • "std::integral means 'a number like int'." It also lets in char and bool (panel 28's exercise).
        • 
        
      • "Every line in a requires expression is checked for truth." Only that it compiles; use a nested requires for truth (panel 33).
        • 
        
      • "More constraints are always safer." Unneeded constraints turn away good types, and impossible ones turn away everyone (panel 35).
        • 
      
      
    
      
  
      

  
      
    Choosing: overload, template, concept or specialisation
    
      
      
        
        
      1. Same idea, different types? One template. If different types need different code, overloads.
        2. 
        
      2. Does the body need something of T (a >, a size(), a <<)? Say so with a concept, standard if one fits (T.11), your own if not. Constrain to what the body uses.
        3. 
        
      3. One type needs a different body? For a function, add a plain overload beside the template. For a class template, a specialisation.
        4. 
        
      4. Is a value part of the type (a size, a capacity, a precision)? A non-type parameter.
        5. 
        
      5. Is a template type's name long and common? An alias template.
        6. 
        
      6. Where does it live? The whole template in a header.
        7.

    Words from this chapter
    
      
      
      
        
      generic code
      Code written once that works for many types.
      
        
      template
      A pattern for making functions, classes or aliases, with parameters filled in while compiling.
      
        
      function template
      A pattern for functions: template <typename T> T bigger(T a, T b).
      
        
      type parameter
      A stand-in for a type, introduced with typename T (or class T).
      
        
      instantiation
      The Compiler making a real function or class from a template for particular arguments; also the thing it makes.
      
        
      template argument deduction
      Working out template arguments from the call's argument types, by exact match.
      
        
      explicit template arguments
      Template arguments written in angle brackets at the call: bigger<double>(3, 4.5).
      
        
      non-type template parameter
      A template parameter that is a value known while compiling: template <int N>.
      
        
      class template
      A pattern for classes: template <typename T> class Pair.
      
        
      CTAD
      Class template argument deduction: Pair p{3, 5} becomes a Pair<int>.
      
        
      deduction guide
      A rule saying how constructor arguments decide a class template's arguments; the Compiler makes them from constructors.
      
        
      alias template
      A short name with parameters for a type pattern: template <typename T> using Grid = ....
      
        
      full specialisation
      A hand-written version of a template for one exact set of arguments: template <> void show<bool>(bool).
      
        
      dependent name
      A name inside a template whose meaning depends on a template parameter, like C::const_iterator.
      
        
      typename (in a dependent name)
      Marks a dependent name as a type: typename C::const_iterator.
      
        
      required from here
      The line in a template error that shows which call caused the instantiation.
      
        
      concept
      A named, compile-time yes/no requirement on template arguments: std::integral, or your own.
      
        
      constraint
      A condition a template places on its arguments, written with concepts and requires.
      
        
      constrained template
      A template with a constraint; wrong types are refused at the call.
      
        
      requires clause
      requires condition after a template line: the template may be used only if the condition is true.
      
        
      requires expression
      requires (params) { lines; }: a bool that is true when every line compiles.
      
        
      nested requirement
      requires condition; inside a requires expression: the condition must be true.
      
        
      abbreviated function template
      A function with an auto (or Concept auto) parameter, which makes it a template without a template line.
      
        
      constraints not satisfied
      The compiler note saying a template was refused because a type isn't on its guest list.
      
        
      subsumption
      The rule that makes the more constrained overload win when one concept is built from another.
      
        
      over-constraining
      Demanding more of a type than the template uses, or demanding the impossible.

C++ · CHAPTER 24

REMOTES AND PACKED LUNCHES

Picture: Wren, the mechanic in orange coveralls, waves hello. Next to her stands Zap, a charcoal universal remote with a little screen for a face and a big yellow PLAY button, sending out an infrared beam.

Wren's workshop has a television, a radio and a lamp, and one remote that works them all. Press play and each device decides for itself what "play" means. That's the first half of this chapter: inheritance (one family of classes) and virtual functions (one button, many meanings), plus the traps that come with them: a missing virtual, a photocopy that loses its third dimension, a destructor that only does half the job. The second half packs lunches: lambdas that carry either a copy of the sandwich or a note saying where it is. Notes are light, until the fridge is gone. About 140 minutes, with 26 hands-on checks.

  1. One family of devices: base and derived classes, protected, who is built first
  2. One button, many meanings: virtual, dynamic dispatch, override, final, and slicing
  3. Interfaces and safe disposal: pure virtual, abstract classes, unique_ptr shelves, virtual destructors, the vtable, dynamic_cast, has-a versus is-a
  4. Packed lunches: lambda syntax, capture by value and by reference, mutable, init-capture, generic and immediately invoked lambdas
  5. Callable things and dangling notes: functors, std::function, function pointers, captures that outlive their fridge, and this
  6. Boss level and recap

PART 1 · ONE FAMILY OF DEVICESBase and derived classes, protected, who is built first

1

Wren's sofa used to be covered in remotes: one for the TV, one for the radio, one for the lamp. Then she bought a universal remote. It has one PLAY button. Point it at the TV and a film starts. Point it at the radio and music plays. The remote doesn't need to know how a TV works. It only needs to know that every device has a play button.

Zap says: I'm Zap. I have exactly one idea: play. I don't care what you are. If you're a device, I press, and you decide what happens. In C++, that idea has two halves: a family of classes that all count as devices (Part 1), and a button whose meaning each family member can change (Part 2).

What does a Tv object look like in memory? It's a Device with extra bits bolted on, like a nesting doll: inside every Tv sits a complete Device, called its base-class subobject. That's why a Tv can go anywhere a Device is expected: the Device part is right there.

    Wren says: Foundations first, roof off first. Tv's constructor may use anything in its Device part (like calling name()), so that part has to exist already. And Tv's destructor may still use its Device part, so that part has to survive until Tv's destructor is done. Members follow the same rule: a class's member objects are built after its bases and before its own constructor body runs, and destroyed in exactly the reverse order. "Every bolt you tighten, you loosen later", in reverse.

    virtual_dtor.cpp
    
      
      
      
      
      
    
      
    
      
      
      
      Wren says: A base with a virtual function gets a virtual destructor. Core Guideline C.127 says it exactly: a class with a virtual function should have a virtual or protected destructor. Usually you write virtual ~Device() = default; and nothing else. Every bolt you tighten, you loosen later: all of them, from the top floor down.
      
    
      
  
      

  
      
  

  
      
    21
    
      How does a running program "look at the real object"? g++, clang and Microsoft's compiler all do it the same way. Each class with virtual functions gets one hidden table in the program, the vtable, listing the address of the function to use for each virtual slot. Each object gets one hidden pointer to its class's table, the vptr, set by the constructor.
      
    
      
    
      
      
      
      The Professor says: The standard never says "vtable": it only says what a virtual call must do. But every mainstream compiler uses this design. It explains everything you've seen: a derived class that doesn't override just copies the base's slot (the lamp); a sliced copy is a real Device, so its vptr points at Device's table; and a non-virtual function has no slot, so it's chosen at compile time. The cost is one hidden pointer per object and one extra lookup per call. Next panel, measured.
      
    
      
  
      

  
      
    22
    
      Can we see the vptr? Not directly, but we can weigh objects. sizeof (Chapter 3) gives an object's size in bytes. Three structs, each holding one int:
      
    sizes.cpp
    
      
      
      
      
      
    
      
    
      
      
      
      Wren says: Plain is just its int: 4 bytes. Give it virtual functions (Virtual has two: play and its destructor) and it jumps to 16: 8 for the hidden pointer (a pointer is 8 bytes on this 64-bit machine), 4 for the int, and 4 bytes of padding so the pointer stays lined up on an 8-byte boundary.       PART 4 · PACKED LUNCHESLambda syntax, capture by value and by reference, mutable, init-capture, generic and immediately invoked lambdas
      

  
      
    25
    
      Chapter 14 met lambdas: little functions with no name, written right where they're needed, like the clip-on attachment Chapter 14 handed to std::sort. Their square brackets, the capture list, say what the lambda takes from the surrounding code. Think of a lambda as a lunch box you pack now and open later. There are two ways to pack the sandwich.
      
    
      
    
      
      
      
      Wren says: A copy travels; a note points home. By value, [x], packs a copy of x into the lambda when it's made. By reference, [&x], packs a note that says where x lives. The note always shows today's sandwich, which is handy. But if the fridge is gone when you open the box, the note points at nothing. Part 5 shows the Sanitizer catching exactly that.

    Under the hood: vtables in detail, what a lambda compiles to, how std::function works, and what virtual really costs
    
        
      
        The vtable, a little more precisely
        
      
        g++ and clang follow the Itanium C++ ABI (an agreement on how compiled C++ is laid out, used on Linux and macOS); Microsoft's compiler has its own, similar scheme. For each polymorphic class the compiler emits one vtable: a table holding, among other things, one function address per virtual function, in declaration order, and a pointer to the class's run-time type information (used by dynamic_cast and typeid). Each object stores a vptr, usually as its very first hidden member. Constructors set it: while Device's constructor runs, the vptr points at Device's table, and only when Tv's constructor starts is it switched to Tv's. That's why calling a virtual function from a constructor or destructor runs the version of the class being built or destroyed, not the derived one (Core Guideline C.82). A destructor has two vtable entries in the Itanium ABI (one that only destroys, one that also frees the memory), which is how delete basePtr frees the right number of bytes when the destructor is virtual.
        
      
        What a lambda compiles to
        
      
        For [bonus](int x) { return x + bonus; } the compiler invents a closure type, roughly struct __lambda_12 { int bonus; int operator()(int x) const { return x + bonus; } };, and the lambda expression creates a closure object of that type. By-value captures become ordinary members; by-reference captures become members that refer to the originals (the exact layout is up to the compiler). mutable removes the const from operator(). A lambda with no captures also gets a conversion to a plain function pointer, which is why panel 35's line 15 compiles. A generic lambda's operator() is a member function template. Because every closure type is a different class known at compile time, a call to a lambda passed straight to an algorithm is easy to inline: lambdas are usually as fast as hand-written loops.
        
      
        How std::function holds anything
        
      
        std::function uses type erasure: it stores the callable together with a small set of "how to call it / copy it / destroy it" operations chosen when it's assigned, which works very like a hand-made vtable. Small callables are stored inside the std::function object itself (the small-buffer optimisation; libstdc++'s 32-byte std::function has room for two pointers' worth); larger ones are put on the heap. A call goes through one indirect jump and usually can't be inlined. It must also be copyable, so it can't hold a lambda that owns a unique_ptr; C++23 adds std::move_only_function for exactly that case (it builds with g++ 13 and -std=c++23); this chapter sticks to std::function.
        
      
        What virtual costs, honestly
        
      
          
        
        • Space: one pointer per object (panel 22), one table per class.
          • 
        
        • Time: a virtual call loads the vptr, loads the slot, and jumps. That's a few instructions; the bigger cost is that the compiler usually can't inline it.
          • 
        
        • Devirtualisation: when the compiler can prove the real type (a local Tv tv; tv.play();, or a class or function marked final), it calls the function directly. final is a small performance hint as well as a design statement.
          • 
        
        • For most programs none of this matters. Measure before worrying (Chapter 29).
          • 
      
        
      
        Hiding, in one paragraph
        
      
        Name lookup stops at the first class that declares the name. If D declares any f, every B::f overload is hidden in D, virtual or not (panel 11's warning). To keep the base overloads visible alongside a new one, write using B::f; inside D. This is also how using Device::Device; (panel 18) brings in base constructors.
        
    
        
  
        

  
        
    In real programs
    
        
      
          
        
        • Plug-in interfaces. GUI toolkits (a Widget base with paint()), game engines (Component with update()), audio software (Effect with process()) and compilers (one class per kind of syntax node) are built around abstract base classes and std::vector<std::unique_ptr<Base>>.
          • 
        
        • The standard library itself. std::exception (Chapter 15) is a polymorphic base: catch (const std::exception& e) and e.what() is a virtual call. Streams use virtual functions inside std::streambuf.
          • 
        
        • Testing. Code that talks to a database or the network through an interface can be tested by handing it a fake derived class that records what it was asked.
          • 
        
        • Callbacks everywhere. Button handlers, timers, "on finished" hooks and event systems store std::functions, usually filled with lambdas.
          • 
        
        • Algorithms. std::sort, std::count_if, std::find_if and Chapter 25's views take lambdas directly, by template parameter, with no std::function cost. Capturing by reference is normal there.
          • 
        
        • Initialising const values with immediately invoked lambdas is common in modern code bases, including in constructors' member initialiser lists.
          • 
        
        • Threads (Chapter 29) are started with lambdas, and a reference capture of a local there is a classic way to crash: capture by value or move things in.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "Writing a function with the same name in a derived class overrides it." Only if the base function is virtual and the signature matches exactly. Otherwise it hides it (panels 8 and 12).
          • 
        
        • "override makes a function virtual." virtual in the base does. override asks the Compiler to check (panel 11).
          • 
        
        • "Virtual functions work on any object." They dispatch on the real object only through references and pointers. A by-value copy is a sliced base object (panels 14 and 15).
          • 
        
        • "std::vector<Base> can hold derived objects." It holds base objects; derived ones are sliced on the way in (Boss 2).
          • 
        
        • "The derived constructor runs first, because it's the one I called." The base part is built first, and destroyed last (panel 6).
          • 
        
        • "A derived class can read its base's private members." No. Use public functions or protected (panels 4 and 5).
          • 
        
        • "The destructor doesn't need to be virtual if it does nothing." If anyone deletes through a base pointer, it must be, whatever it does (panel 19).
          • 
        
        • "An abstract class can't have any code." It can have data, constructors and ordinary functions; it just has at least one pure virtual function.
          • 
        
        • "[=] copies everything, so it's always safe." Inside a member function it copies this, a pointer (panel 38). And a copied raw pointer still dangles if its target dies.
          • 
        
        • "mutable changes the original variable." It changes the lambda's own copy (panel 29).
          • 
        
        • "A lambda is a function." It's an object of a class the Compiler writes, with an operator() (panel 33).
          • 
        
        • "Capturing by reference is faster, so always use [&]." For a lambda used on the spot, fine. For one that outlives the scope, it's a dangling note (panels 36 and 37).

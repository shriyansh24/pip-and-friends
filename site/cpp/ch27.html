SIGNPOSTS AND STICKY PRINTERS

Picture: Wren, the mechanic in orange coveralls, waves hello. Next to her: a signpost pointing two ways, value and error, and a printer stuck on BOLD.

Chapter 15 taught you to pull the fire alarm. Today you learn when not to: some trouble deserves a quiet signpost on the normal road (std::optional, std::expected, error codes), some an emergency exit (exceptions), and some a factory test before the car ever ships (assertions). Then the printer half: stream settings that stick until you change them back, the four warning lamps on every stream, the leftover newline that eats a name, binary files, and the std::filesystem toolbox. About 130 minutes, with 25 hands-on checks.

PART 1 · SIGNPOSTS ON THE ROADoptional, expected, error codes, exceptions and assertions: which one, when?

1

Wren is driving the workshop van to a job. Along the way: a road that's closed today, a flat tyre, and a van that left the factory with a loose brake cable. Three problems. Would you deal with all three the same way?

Wren says: A closed road is normal: a sign tells me, I take the other road, no drama. A flat tyre means I can't finish the trip: I pull into the emergency lane and someone else takes over. And a loose brake cable? That should have been caught at the factory, before the van was ever sold. Code has the same three kinds of trouble.

Ember says: And only one of those is my job. If you pull my alarm every time a road is closed, I'll never get any sleep. Not every problem is a fire.

Picture: Wren points ahead, thinking. Ember the fire marshal holds up a hand: stop.

2

Big idea: C++ gives you several ways to report trouble. Each one fits a different kind of problem.

SIGNPOST

std::optional / std::expected

The answer itself says "there's a value" or "there isn't (and here's why)". The caller looks at the sign on the very next line. Normal, expected trouble.

DASHBOARD LAMP

an error code

A small number or code handed back next to the result, the old C way. Cheap, but easy to drive past without looking.

EMERGENCY EXIT

throw

The function can't do its job and the caller can't just carry on. Ember takes over, somewhere further up (Chapter 15).

FACTORY TEST

assert(...)

Checks for programmer mistakes while you build and test. Not for bad user input: that's not a bug in your code.

Four cards. Signpost: optional and expected, for expected trouble the caller checks at once. Dashboard lamp, dotted border: an error code, cheap but easy to ignore. Emergency exit, dashed border: throw, when the job can't be done. Factory test, cream: assert, for programmer mistakes during testing.

The Professor says: For years, people have wanted preconditions written on the function itself, where callers and tools can see them, rather than hidden inside it as an assert. The committee that writes C++ designed exactly that, called contracts, for C++26: a function could say pre(slot >= 0) or post(r: r > 0) in its declaration, and contract_assert(...) would replace assert in the body.

    

    

      
The Professor says: It has been a long argument. The committee finished its C++26 draft and sent it to the national standards bodies for their vote; a committee paper from July 2026 (P4238R0) asked them to vote no because of contracts. As of November 2026 the draft is not an official ISO standard yet, so C++23 is still the current standard. (News reports say the vote failed in October; this book found no official ISO or committee page confirming that, so treat it as unconfirmed.) Neither compiler on this machine understands contracts anyway (the notebook shows both refusing a pre). Until they arrive, assert plus clear comments (Core Guidelines I.5 to I.8) do the job.

PART 3 · PROMISES AND GUARANTEESnoexcept, what happens when it's broken, and the four exception-safety guarantees


  

    18
    
Writing noexcept after a function's parameters is a promise: "no exception will ever come out of this door". Chapter 22 met it on move constructors, where std::vector reads the promise to decide whether moving is safe. The compiler trusts the promise. It doesn't check it.

    

    

      
      
Ember says: So what if an alarm goes off behind that door anyway? I'm not even called. The promise was broken, so the C++ rules say: std::terminate, straight away. A broken promise switches off the whole building.

    21
    
When an exception flies out of a function halfway through, what state is everything left in? There are four possible answers. Every function gives one of them, whether its author thought about it or not.

    

      
NO-THROW
nothing can go wrong
The function always succeeds; marked noexcept. Destructors, swap, moves. These are the building blocks of the other guarantees.

      
STRONG
all or nothing
If it throws, everything is exactly as before, as if it was never called. Like a bank transfer: both accounts change, or neither does.

      
BASIC
valid, but changed
If it throws, nothing leaks and every object still works, but values may have changed partway. The minimum every function should give.

      
NONE
anything goes
A throw can leave leaks or broken objects behind. Never acceptable in code others will use.

    

    

      
      
The Professor says: These names come from work by David Abrahams for the C++ standard library in the 1990s, and the library documents its functions with them. Chapter 22 already met one: push_back gives the strong guarantee. Next: the same function written to give basic, then strong.

    

    
Four cards: no-throw, always succeeds; strong, all or nothing; basic (dashed), valid but changed; none (dotted), anything goes.

      PART 5 · STREAM HEALTHThe four state lamps, recovering, the leftover newline, unformatted reads and binary files
      

  
      
    30
    
      Chapter 15 met the fail flag. Every stream (std::cin, files, string streams) actually has a little dashboard of state flags, and four questions you can ask about them.
      
    
      
      
      good()
      all clear
      True only when none of the three problem flags is up. Note: not the opposite of fail().
      
      
      eof()
      end of input reached
      A read ran into the end. Not a look-ahead: it goes up after touching the end (Chapter 15's last-word-twice bug).
      
      
      fail()
      a read went wrong
      A read couldn't produce a value: letters where a number was wanted, or nothing left. While it's up, every read is refused. Also true when bad is up.
      
      
      bad()
      the stream is broken
      Something failed underneath: a disk error, a lost device. Rare, and usually not fixable by your program.
      
    
      
    
      
      
      
      Wren says: if (in) and while (in >> x) ask "is fail() false?". That's why reading in the condition works so well. Let's watch the lamps change.
      
    
      
    
      Four cards: good, all clear; eof (cream), a read hit the end; fail (dashed), a read went wrong; bad (dotted), the stream is broken.

    Under the hood: what expected holds, how noexcept ends things, what a stream's settings really are
    
      
      
      What a std::expected holds
      
      
      An expected<int, std::string> holds either an int or a std::string, in the same storage, plus a flag saying which. It never holds both and never borrows memory from the heap for itself. *e on an error is undefined (no check), just like * on an empty optional; e.value() checks, and throws std::bad_expected_access if there's no value. e.value_or(0) gives a fallback. In C++23 there are also and_then, transform and or_else for chaining steps that each might fail.
      
      
      Why clang can't see expected here
      
      
      libstdc++ 13's <expected> switches itself on only when the compiler reports full C++20 concepts support through a feature-test macro. clang++ 18 reports an older value of that macro, so the header defines nothing and clang reports no template named 'expected' (panel 6). Here is that macro, printed by each compiler; this machine's <expected> header asks for __cpp_concepts >= 202002L:
      
      concepts_macro.cpp
      
      
      
      
      
      
      
      cppreference lists expected in clang's own library, libc++, from version 16 (not run for this book).
      
      
      Four more claims, checked
      
      
      Without std::unexpected, a message can't become the error arm (the exercise after panel 6):

      What happens when noexcept is broken
      
      
      The rules say std::terminate is called, and it is implementation-defined whether any stack unwinding happens first. In practice g++ compiles a noexcept function so the exception search simply stops at its edge. That's also why noexcept can make code a little smaller: the compiler doesn't have to prepare to unwind through such functions.
      
      
      Where the guarantees come from
      
      
      The basic, strong and no-throw guarantees were described by David Abrahams in the late 1990s while the first C++ standard library was being specified, and the standard still uses the ideas. std::vector::push_back gives the strong guarantee (when the element's move can't throw or it can be copied); destructors and swap of standard containers give no-throw. Core Guideline E.12 says to use noexcept when exiting a function because of a throw is impossible or unacceptable.
      
      
      A stream's settings are just numbers
      
      
      Every stream stores its formatting flags (fixed, hex, left, boolalpha...) as bits in one value, plus a precision, a width and a fill character. Manipulators are tiny functions that change those. std::cout.flags() returns all the flags, so a helper can save them with auto f{std::cout.flags()}; and restore them with std::cout.flags(f);. To save absolutely everything, including fill and precision, make a spare stream to hold them: std::ios saved{nullptr}; saved.copyfmt(std::cout); ... std::cout.copyfmt(saved);.
      
      
      Width resets, but only for most things
      
      
      The width goes back to 0 after each formatted item that uses it (numbers, strings, characters). Manipulators themselves don't print, so std::setw(6) << std::left still applies the width to the next real item.
      
      
      Stream state as bits
      
      
      The flags behind panel 30 are std::ios::goodbit (zero), eofbit, failbit and badbit, stored together; rdstate() returns them. clear() sets them all to goodbit; setstate(failbit) raises one. in.exceptions(std::ios::badbit) makes the stream throw std::ios_base::failure when that flag goes up: sensible for badbit, awkward for eofbit and failbit, which go up during normal reading.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • One style per project. Large code bases write down their error policy. Some (many games, embedded systems, and historically Google's style guide) compile with -fno-exceptions and use return values; others use exceptions throughout. std::expected gives the return-value style a standard shape, and libraries such as tl::expected offered the same before C++23.
        • 
        
      • Exception families at library edges. A library usually throws its own family (for example a JSON library's parse_error, type_error and out_of_range, all built on one base), so users can catch "anything from this library" or one specific problem.
        • 
        
      • Rethrow to add context. Servers often catch, log the request id, and throw;. C++11's std::throw_with_nested wraps the original inside a new exception with more context, and std::rethrow_if_nested unwraps it.
        • 
        
      • noexcept on moves and swaps. Containers check it (Chapter 22), so a class without noexcept moves gets copied when a vector grows.
        • 
        
      • Formatting. New code prefers std::format (and std::print in C++23, not available on this toolchain) because it never changes stream state. Manipulators are still everywhere in older code and in code that writes to files and string streams.
        • 
        
      • Binary formats. Images, audio, save games and network messages are binary, always with a written specification of sizes and byte order. Real code reads them field by field, rather than dumping whole structs, because padding and byte order differ between machines.
        • 
        
      • std::filesystem. Build tools, installers and backup programs walk folders with recursive_directory_iterator, create output folders with create_directories, and use the error_code overloads for "maybe there" files.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "Exceptions are always better than return values" (or the other way round). Each fits a different kind of trouble (panel 11).
        • 
        
      • "assert checks user input." It checks your own code, and vanishes with -DNDEBUG.
        • 
        
      • "noexcept stops exceptions." It turns them into std::terminate.
        • 
        
      • "The compiler checks that a noexcept function can't throw." It warns only about a throw written directly inside (panel 19), never about calls (the predict after panel 20).
        • 
        
      • "throw e; and throw; are the same." throw e; copies and slices.
        • 
        
      • "The compiler picks the best-matching handler." It picks the first one that matches.
        • 
        
      • "setprecision applies to the next number." It applies until changed. Only setw is one-shot.
        • 
        
      • "good() is the opposite of fail()." After reading the last number, good() is false (eof) while fail() is still false.
        • 
        
      • "clear() removes the bad input." It only resets the flags.
        • 
        
      • "getline after >> is broken." It works exactly as specified; the newline was still there.
        • 
        
      • "A binary file looks the same on every computer." Byte order and type sizes can differ.
        • 
        
      • "directory_iterator lists files alphabetically." Its order is unspecified.
        • 
        
      • "p.extension() is txt." It's .txt, dot included.

    Words from this chapter
    
      
      
      
        
      std::expected<T, E>
      C++23: a return value that holds either a T (success) or an E (the error); has_value(), *, value(), error().
      
        
      std::unexpected
      The wrapper that marks a value as the error arm of an expected: return std::unexpected{"empty"};.
      
        
      error code
      A small value returned to report success or which problem happened; std::errc and std::error_code in the standard library.
      
        
      std::from_chars
      C++17 number parser in <charconv>; never throws, reports through an std::errc.
      
        
      [[nodiscard]]
      An attribute asking the compiler to warn if a function's result is ignored.
      
        
      attribute
      A note to the compiler in double square brackets, such as [[nodiscard]].
      
        
      precondition
      What must be true before a function runs, for it to work.
      
        
      postcondition
      What a function promises is true when it returns.
      
        
      invariant
      A rule about an object that must hold for its whole life.
      
        
      contracts
      A planned C++26 feature (pre, post, contract_assert) for writing preconditions and postconditions on functions; not yet in an approved standard or on this toolchain.
      
        
      exception hierarchy
      A family of exception classes built on each other with inheritance, rooted at std::exception.
      
        
      rethrow
      throw; inside a handler: send the same exception on, unchanged.
      
        
      noexcept
      A promise that no exception leaves a function; breaking it calls std::terminate. As noexcept(expr), a compile-time question.
      
        
      exception-safety guarantees
      No-throw (always succeeds), strong (all or nothing), basic (valid but maybe changed), none.
      
        
      copy-and-swap
      Getting the strong guarantee: do the work on a copy, then swap it in with an operation that can't throw.
      
        
      manipulator
      Something sent into a stream that changes its settings instead of printing: std::setprecision, std::fixed, std::hex, std::setw, std::ws.
      
        
      sticky setting
      A stream setting that stays on until changed; all of them except the width.
      
        
      <iomanip>
      The header for manipulators that take an argument (setw, setprecision, setfill).
      
        
      state flags
      A stream's eof, fail and bad bits; asked with good(), eof(), fail(), bad().
      
        
      std::ws
      An input manipulator that skips whitespace, including leftover newlines.
      
        
      formatted / unformatted I/O
      >> and << convert values and (for input) skip whitespace; get, getline, read, write move characters or bytes as they are.
      
        
      binary file
      A file holding raw bytes rather than text; open with std::ios::binary.
      
        
      little-endian
      Storing a number's smallest byte first, as x86-64 processors do.
      
        
      std::filesystem
      C++17 library for paths, files and folders, in <filesystem>.
      
        
      fs::path
      A path that knows its parts: filename(), stem(), extension(), parent_path(), joined with /.
      
        
      directory_iterator
      Visits each entry of one folder, in unspecified order.
      
        
      filesystem_error
      The exception the throwing filesystem functions raise; has code() and path1().
      
        
      std::error_code
      An error value with message(); passing one to a filesystem function makes it report instead of throwing.

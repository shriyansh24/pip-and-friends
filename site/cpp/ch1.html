Here's the catch. A CPU only understands machine code: numbers. People write source code: text with words in it. Same cake, two forms:

cake.cpp · source code (for people) 

      

      

        cake · machine code (for the CPU)

The Professor says: Nobody writes those numbers by hand any more. We write source code, and a program called a compiler translates it. You can open my notebook at the end to see the whole list.

    

  


  

  

  

    6
    
There are two ways to turn source code into action.

    

      

        
COMPILEDtranslate the whole book first

        

        
A translator turns the whole book into the reader's language once. After that, anyone can read the translation quickly, with no translator in the room. C++, C, Rust and Go work like this.

      

      

        
INTERPRETEDtranslate each time it runs

        

        
An interpreter translates and runs the program each time you start it, so there's no separate build step. Easy to start, but usually slower. Python and JavaScript usually work like this.

      

    

    

      
      
Wren says: C++ is compiled. So for us, there's always a build step before the program can run. Today you learn that step inside out.

    

  


  

  

  

    7
    
    
Why do people choose C++? Two reasons, and they're two sides of one coin.

    

      
FASTtranslated ahead, close to the metal
The compiler has time to make tight machine code, and C++ lets you control memory directly. That's why it runs games, web browsers, databases and car software.

      
UNFORGIVINGit trusts you
C++ checks a lot while it builds, but it doesn't babysit the running program. Some mistakes aren't caught at all. You'll learn the safety nets as you go.

    

    

      
      
The Professor says: One scary word for later: undefined behaviour. It means code the C++ rules give no meaning to, so the program might do anything, even seem to work. We'll meet it with proper tools that catch it.

    12
    
So a C++ program lives two lives. Problems can show up in either one.

    

      
COMPILE TIME
While building (preprocess, compile, link).
  • The Compiler checks the rules of C++.
  • The Linker checks every part is there.
  • A problem here means no program at all. Nothing runs.

      
→

      
RUN TIME
While the program runs, possibly much later, on another computer.
  • The program does exactly what the machine code says.
  • Wrong instructions give wrong results, with no warning.
  • A program can also end by reporting a problem.

    

    

      
      
Wren says: Every mistake caught at compile time is one your users never see. That's why C++ people love a fussy compiler. Measure twice, compile once.

    Under the hood: the four stations up close
    

      
Inside g++ there are really four jobs. The comic merges two of them, because one command usually does both:

      
    
        
  1. Preprocess (-E): handle every line that starts with #. #include pastes a file in. Output: plain C++ text (a .ii file if you save it).
    2. 
        
  2. Compile (-S): check the rules and translate C++ into assembly, a text form of machine instructions (a .s file).
    3. 
        
  3. Assemble (-c stops after this): turn the assembly into machine-code bytes, an object file (.o).
    4. 
        
  4. Link (no stopping flag): the linker, ld, joins object files and libraries into an executable.
    5. 
      

      
What's inside an object file?

      
Machine code, plus a list of symbols: names this file provides and names it needs from elsewhere. nm prints that list (-C turns the coded names back into readable C++):

T main: this file provides main (T means it lives in the code section). U std::cout and the long operator<< line: this file uses them but doesn't contain them (U for undefined). The other U line, std::ios_base_library_init(), is a library helper that sets up std::cout. The linker's job is to find a provider for every U. When it can't, you get undefined reference, exactly like the missing main in panel 30. The r lines are small read-only constants that came in with the header.

objdump -d shows the bytes from panel 5 next to their names in assembly. Each row is one CPU instruction: an address, the bytes, then a short name like mov (move), call or ret (return). The three call rows are the three printing lines of cake.cpp:

You will never need to write this. But knowing it's there explains a lot: why a C++ program is fast (the CPU runs these bytes directly), and why a Linux program won't run on Windows or on a phone (different instructions, different file format).

      
Libraries: the bakery's ready-made parts

      
std::cout lives in the C++ standard library (on Linux usually libstdc++). By default it is linked dynamically: the executable holds a note saying "load libstdc++ when you start", and the system loads it at run time. That's one reason cake is only about 16 to 32 kilobytes (panel 24) even though iostream is enormous.

    

  


  

    Standards and compilers: the long story
    

      
C++ was created by Bjarne Stroustrup at Bell Labs, starting from C. The first ISO standard was C++98. Since C++11 the committee (called WG21) has shipped a new edition every three years. The current one is C++23, published as ISO/IEC 14882:2024. The committee completed a C++26 draft in March 2026 and sent it to the national standards bodies for their vote. ISO's page for that draft shows the vote as closed, but as of November 2026 C++26 is not an official ISO standard yet, so C++23 is still the current standard (status as of 8 November 2026; sources in "Go deeper").

      
What __cplusplus says

      
The compiler sets __cplusplus to the year and month of the edition it follows. Values seen on this machine:

      

        

        

      

      

        

        

      

      
g++ 13's 202100 is a placeholder that this version never updated. clang++ 18 reports 202302 and also accepts -std=c++2c (202400, a placeholder for C++26), as panel 32 showed.

      
Defaults change

      
Both compilers here default to C++17 (strictly, gnu++17: C++17 plus some GNU extras; -std=c++17 switches the extras off and -Wpedantic warns when you use them). According to the GCC 16 release notes, GCC 16 switched its default to C++20 (gnu++20). That's the point: a build that depends on the default can change meaning when someone upgrades.

      
Same mistake, different words

      
Compilers word their messages differently. For the missing ; in panel 33, clang++ says expected ';' after expression where g++ says expected ‘;’ before ‘}’ token, and clang++ adds a count of errors at the end. The clues are the same: file, line, column, a copy of the line, a caret. Chapter 2 compares them side by side.

      
Notice the curly quotes in g++'s messages. It uses them when the terminal is set to UTF-8 (most are); in the plain C locale it prints straight quotes. Same message.

      
Undefined behaviour, one more sentence

      
Some mistakes break no checkable rule, so the compiler builds the program anyway, and the C++ standard says nothing about what happens when it runs. The result can change between compilers, flags, or even runs. This book never shows such output as if it were normal; instead it uses tools called sanitizers that catch the mistake and report it.

    

  


  

    In real programs
    

      
    
        
  • Nobody types the full command a hundred times a day. Projects use a build system, such as Make or CMake (Chapter 17), which remembers the flags and rebuilds only the files that changed. An IDE's Build button does the same.
    • 
        
  • Exit codes drive automation. Test runners and build servers check them: 0 means "carry on", anything else stops the line. g++ … && ./tests is the smallest version of that idea.
    • 
        
  • Warnings are taken seriously. Many teams add -Werror, which turns every warning into an error so nothing suspicious slips through. Other common extras: -Wpedantic (stick strictly to the standard), -Wshadow, -Wconversion.
    • 
        
  • Debug and Release. IDEs and build systems keep both builds side by side. Release builds often use -O2 or -O3, plus -DNDEBUG to switch off internal checks.
    • 
        
  • Compiler Explorer is used by professionals daily: to compare compilers, to check what machine code a line produces, and to share small examples by link.
    • 
        
  • Big programs have many source files. Each .cpp is compiled to its own .o, and the linker joins them all. Chapter 10 builds one.
    • 
      

    

  


  

    Common wrong ideas
    

      
    
        
  • "I can run my .cpp file." You can only run what the build produces. Panel 28.
    • 
        
  • "It compiled, so it works." The Compiler checks rules, not intentions. Panel 36 and its exercise.
    • 
        
  • "I saved my change, so the program changed." Not until you build again. Panel 35.
    • 
        
  • "No message means nothing happened." For a build, no message means everything worked.
    • 
        
  • "Warnings don't matter because the program still builds." Warnings point at code that is probably wrong. Fix them while there are few.
    • 
        
  • "Every error comes from the compiler." Three voices: the shell, the Compiler, the Linker. The first word of the message tells you which.
    • 
        
  • "The compiler's default edition is the latest one." Ours defaults to C++17, two editions old. Always pass -std.
    • 
        
  • "a.out is a special file." It's just the default name. Use -o.
    • 
        
  • "C++ and C are the same." C++ grew out of C and can use most C code, but it is a different language with its own standard and its own compiler front end (g++, not gcc, links the C++ library for you).
    •

    Words from this chapter
    

      

        
program
Exact instructions a computer follows, in order.

        
CPU
The part of the computer that carries out machine instructions, one tiny step at a time.

        
source code
The text people write in a programming language. In C++, .cpp files.

        
machine code
The numbers a CPU runs directly.

        
compiler
A program that translates source code into machine code ahead of time. g++ and clang++ are C++ compilers.

        
compiled / interpreted
Translated once, before running (C++) / translated each time it runs, with no separate build step (Python, usually).

        
build
Turning source code into a program: preprocess, compile, link. Also the program you get.

        
preprocessor
The first station. Handles # lines; #include pastes a file in.

        
object file
A .o file: machine code for one source file, not yet runnable.

        
linker
The last station (ld). Joins object files and libraries into an executable.

        
library
Ready-made code you can use, like the C++ standard library that provides std::cout.

        
executable
A program file you can run, like cake (cake.exe on Windows).

        
compile time / run time
While the program is being built / while it runs.

        
terminal
A window where you type commands.

        
shell
The program inside the terminal that reads and starts your commands (here bash).

        
prompt
The text that shows the terminal is waiting, ending in $.

        
flag
An option on a command, starting with -, like -Wall.

        
standard
An official edition of the C++ rules, like C++23. Chosen with -std=.

        
warning
A compiler message about code that is legal but suspicious. The program is still built.

        
Debug / Release build
Built with labels for the debugger (-g) / built optimised (-O2).

        
a.out
The default name for the program when you leave out -o.

        
exit code
The number a program ends with. 0 means success. echo $? shows it.

        
PATH
The list of folders the shell searches for a bare command name.

        
hexadecimal
Writing numbers with sixteen digits, 0 to 9 then a to f.

        
undefined behaviour
Code the C++ rules give no meaning to. Anything can happen when it runs.

        
Compiler Explorer
A website (godbolt.org) that builds code with many compilers and shows the result.

C++ · CHAPTER 18

INSPECTORS AND MAGNIFIERS

Picture: Wren, the mechanic in orange coveralls, waves. Next to her stands Inspector Pike in a yellow high-visibility tabard and a peaked cap, pointing a big magnifying glass at the reader.

Your program compiles. It runs. It prints a number. Is it right? A car that starts isn't a car that's safe to drive, so cars go through an inspection lane: a wash, a mirror check, a checklist, and a run on a rolling road. Code has the very same lane, and today Wren drives through it with Inspector Pike. Then we pick up a magnifying glass and look hard at text: views that don't own their page, a label printer called std::format, quick number parsing, and the surprise that "é" is two bytes. About 130 minutes, with 26 hands-on checks.

  1. The inspection lane: a clean build isn't a right build, and a warnings policy
  2. The car wash and the checklist: clang-format and clang-tidy
  3. The rolling road: sanitizers, library assertions, Valgrind, and which tool catches what
  4. The magnifying glass: std::string_view, and the page that burned
  5. The label printer: std::format specs, checked format strings, from_chars and to_chars
  6. Bytes, not letters: UTF-8, cctype and unsigned char
  7. Boss level and recap

    18
    
Station 4: the rolling road. The same source, built with the sanitizers from Chapter 3: -fsanitize=address,undefined. The compiler adds a check before every memory access, then the program runs for real.

    

    

    
    
      
  1. The headline: heap-buffer-overflow: something read past the end of a block on the heap (Chapter 13's library). READ of size 4: one int.
    2. 
      
  2. Where, in your code: frame #0 ... in main /home/you/cpp-ch18/overrun_san.cpp:8, the total += psi[i] line.
    3. 
      
  3. Whose block: "0 bytes after 16-byte region": the vector's 4 ints are 16 bytes, and the read landed right after them. "allocated by thread T0 here" shows the vector being made on line 5.
    4. 
      
  4. The fine print: ==2== is the program's process id, and the 0x... addresses differ on other machines. The "shadow bytes" map at the end is ASan's own bookkeeping; you can skip it.
    5.

    PART 4 · THE MAGNIFYING GLASSstd::string_view: a cheap, non-owning view, and the page that burned
    

  
    
    27
    
    Big idea: a std::string owns its letters: it keeps them on a page (a heap block), and tears up the page when it's destroyed. A std::string_view (from <string_view>) owns nothing. It's a magnifying glass held over part of someone else's page: just "where the first letter is" and "how many letters". Copying the glass is cheap; it's two numbers. But if the owner burns the page, the glass shows nothing useful.
    
    
    
    
    
      
      
    Inspector Pike says: A view is a look, never a keep. The glass is only as good as the page under it.
    
    
    
  
    

  
    
    28
    
    Why bother? Because a std::string_view parameter (line 5) accepts a std::string, a "literal" or another view, and copies no letters. Cutting a piece off a view, with substr or remove_prefix, just moves the glass.
    
    sv_basics.cpp
    
    
      
    
      
    
    
    
    
      
      
    1. Line 11: a std::string becomes a view of all 22 letters. No copy.
      2. 
      
    2. Line 12: a string literal becomes a view straight onto the literal, which lives for the whole program. A const std::string& parameter would have had to build a temporary std::string here.
      3. 
      
    3. Line 14: view.substr(0, 10) is a new view of the first 10 letters. (On a std::string, substr makes a new string, with its own copy.)
      4. 
      
    4. Line 15: remove_prefix(12) slides the start of the glass 12 letters to the right. The last line proves the owner's text never changed: a view can't change the page.
      5.

      Wren says: The rule of thumb: a string_view is great as a function parameter (the caller's string outlives the call) and dangerous as a variable you keep or a return value. Three more ways to burn the page: returning a view of a local string, viewing a string that's then changed (it may move its letters to a bigger page), and viewing a "text"s temporary.
      
    
      
  
      

  
      
  

  
      
    32
    
      When to use which. The C++ Core Guidelines put it in two rules: SL.str.1 "Use std::string to own character sequences" and SL.str.2 "Use std::string_view ... to refer to character sequences".
      
    
      
      
      You want to...Use
      
      
        
      read some text in a function, and not keep itstd::string_view parameter
      
        
      keep the text: store it in an object, a vector, a mapstd::string
      
        
      return text you built inside the functionstd::string (never a view of a local)
      
        
      change the caller's textstd::string&
      
        
      pass text to an old C function that needs a '\0' at the endconst std::string& and .c_str(): a view of part of a string has no '\0' after it
      
            
    
      
    
      And the two literal suffixes from std::literals (Core Guideline SL.str.12: "Use the s suffix for string literals meant to be standard-library strings"): "oil"s is a std::string, "oil"sv is a std::string_view, and plain "oil" with auto is a const char*, a bare pointer.

        What you learned in Chapter 18
        
    
          
      
        • A CLEAN BUILD ISN'T A RIGHT BUILDThe Compiler checks that code is legal, not that it's what you meant. Run the whole inspection lane: static stations read the code (clang-format, warnings, clang-tidy); dynamic ones watch it run (sanitizers, library assertions, Valgrind). Each catches what the others miss.
          • 
      
        • -WALL ISN'T ALLA warnings policy: -Wall -Wextra -Wpedantic -Wshadow -Wconversion, plus -Werror on the build server so a warning shuts the gate. Every warning names its flag in brackets.
          • 
      
        • LET THE CAR WASH ARGUE ABOUT SPACESclang-format for layout (-i to rewrite, --dry-run --Werror to check); clang-tidy for known bad patterns, by family: modernize-, bugprone-, cppcoreguidelines-, with --fix.
          • 
      
        • ASAN AND UBSAN RIDE TOGETHER; TSAN RIDES ALONE-fsanitize=address,undefined in one build, -fsanitize=thread in another. -D_GLIBCXX_ASSERTIONS is a cheap seatbelt; Valgrind checks an unchanged program, slowly. Here, sanitizer builds use g++.
          • 
      
        • A VIEW IS A LOOK, NEVER A KEEPstd::string_view is a pointer and a length over someone else's page: perfect for parameters, dangerous to store or return. A view of a temporary, a local, or a string that then changes dangles, and g++ 13 says nothing: ASan says heap-use-after-free.
          • 
      
        • BYTES, NOT LETTERSstd::format specs go fill, align, width, precision, type ({:*>8.2f}) and are checked while compiling; from_chars parses fast and reports where it stopped. A std::string holds UTF-8 bytes: "é" has size 2, and <cctype> wants unsigned char.

    Under the hood: how sanitizers and Valgrind see bugs, how std::format checks at compile time, and how UTF-8 is built
    
        
      
        How AddressSanitizer works
        
      
        ASan keeps a shadow memory: for every 8 bytes of your program's memory, one shadow byte says how many of them may be used. The compiler inserts a quick shadow check before every load and store. new and malloc are replaced so that every block gets poisoned redzones on both sides (that's how "0 bytes after 16-byte region" is spotted), and freed blocks go into a quarantine instead of being reused at once (that's how "use after free" is spotted, and why a freed block shows fd in the shadow map). The cost: more memory, and the ASan documentation gives a typical slowdown of about 2×. A use after free can slip through if so much memory has been freed since that the block left quarantine.
        
      
        How UBSan works
        
      
        UBSan adds a small check at each operation that could be undefined: every signed +, - and *, every division, every shift, some casts. If the check fails it prints runtime error: and, with -fno-sanitize-recover=all, stops. It doesn't track memory, which is why ASan and UBSan complement each other so well.
        
      
        How Valgrind works
        
      
        Valgrind doesn't need a rebuild because it never runs your machine code directly. It translates it, a little at a time, into its own instructions with checks added, then runs those on a simulated processor. Memcheck tracks whether every byte is addressable and whether it has been given a value ("Conditional jump or move depends on uninitialised value(s)" is its famous message). Simulating everything is why it's 10 to 50 times slower. It only knows about heap blocks, so an overrun of a local array on the stack goes unnoticed.
        
      
        Static analysis can't be perfect
        
      
        A static tool would have to predict every value a program might ever see, which is impossible in general (computer science proves no program can decide every such question about all other programs). So static tools approximate: they either miss some bugs (false negatives) or report some correct code (false positives). Dynamic tools never report a bug that didn't happen, but only see the roads your test runs actually took. That's the real reason for a lane with both kinds.
        
      
        How std::format checks its string while compiling
        
      
        std::format's first parameter isn't a plain string; it's a std::format_string<Args...> whose constructor is consteval: it must run while compiling. It walks the string, counts the slots and checks each spec against each argument's type. On a problem it calls a function that isn't allowed at compile time, and that failure is the error you saw. When the string is only known at run time, use std::vformat, which checks at run time and throws std::format_error (the label printer's jam). Chapter 19 explains consteval.
        
      
        How UTF-8 is built
        
      
        UTF-8 splits a code point's number into bits and spreads them over 1 to 4 bytes. One byte: 0xxxxxxx (the 128 ASCII characters, unchanged). Two bytes: 110xxxxx 10xxxxxx. Three: 1110xxxx + two 10 bytes. Four: 11110xxx + three. So é, U+00E9 = binary 000 1110 1001, becomes 110 00011 10 101001 = c3 a9. Every "more" byte starts with 10, which is why (byte & 0xC0) != 0x80 finds character starts, and why you can always find the start of a character from the middle of a text.
        
      
        Why string_view has no '\0'
        
      
        C strings end with a zero byte. A view of the middle of a string can't add one without changing the owner's page, so a string_view is just pointer + length. Passing view.data() to a C function that expects a zero at the end may read past your text. Convert to std::string first when you need .c_str().
        
    
        
  
        

  
        
    In real programs
    
        
      
          
        
        • Build servers run the lane. Continuous integration (CI) systems build every change with -Werror, run clang-format --dry-run --Werror and clang-tidy, and run the tests under ASan+UBSan and TSan builds before a change may be merged.
          • 
        
        • Fuzzing. Fuzzers such as libFuzzer and AFL++ feed millions of random inputs into a sanitized build. The sanitizer turns silent memory errors into crashes the fuzzer can notice. Google's OSS-Fuzz project runs this for open-source code continuously.
          • 
        
        • Hardened libraries in production. Some Linux distributions compile their packages with -D_GLIBCXX_ASSERTIONS, because the checks are cheap enough to leave on. Newer libc++ versions have a similar "hardening mode".
          • 
        
        • Editors run the checklist live. The clangd language server shows clang-tidy findings as you type in VS Code, Vim, Emacs and others, and many editors run clang-format when you save.
          • 
        
        • string_view in libraries. Parsers (JSON, configuration files, network protocols) cut their input into views instead of copying, which is a big part of why they are fast. They keep the input buffer alive for as long as the views are used.
          • 
        
        • from_chars in fast parsers. JSON and CSV libraries use from_chars because it ignores the computer's language settings (a German setting writes 3,5 for 3.5) and never allocates.
          • 
        
        • UTF-8 everywhere. The web, Linux, macOS and modern Windows programs all use UTF-8 widely. With Microsoft's compiler, add /utf-8 so source files and string literals are read and stored as UTF-8.

    Common wrong ideas
    
        
      
          
        
        • "No warnings means no bugs." Panels 1 and 17: both built clean. One was wrong, one was undefined behaviour.
          • 
        
        • "-Wall turns on all warnings." It's a set. -Wextra, -Wshadow, -Wconversion and -Wpedantic are all off without asking.
          • 
        
        • "Sanitizers can all go in one build." ASan and UBSan, yes; TSan never with ASan (panel 21).
          • 
        
        • "If the sanitized run is quiet, the program has no bugs." It had no bugs on that run. Other inputs take other roads.
          • 
        
        • "clang-format might break my code." It changes whitespace and layout (and optionally sorts #includes), never meaning. Sorting includes can, rarely, matter for headers that depend on order.
          • 
        
        • "A string_view is a lightweight string." It's a lightweight look at someone else's string. It owns nothing.
          • 
        
        • "Returning a string_view is always faster." Only if what it views outlives the call. A view of a local is a view of ashes.
          • 
        
        • ".size() counts letters." It counts bytes (chars). "café" is 5.
          • 
        
        • "std::toupper(c) is fine on any char." Not for negative chars: cast to unsigned char first. And it still won't upper-case é.
          • 
        
        • "std::format with a wrong spec crashes at run time." With a literal format string it fails to compile. Only std::vformat with a run-time string throws.
          • 
        
        • "from_chars is like stoi." It skips no spaces, accepts no +, throws nothing, and tells you where it stopped.

    Words from this chapter
    
        
      
        
        
        static analysis
        Checking a program by reading its code, without running it: compiler warnings, clang-tidy.
        
        
        dynamic analysis
        Checking a program while it runs: sanitizers, library assertions, Valgrind.
        
        
        warnings policy
        The warning flags a team always builds with, such as -Wall -Wextra -Wpedantic -Wshadow -Wconversion -Werror.
        
        
        -Werror
        A flag that turns every warning into an error, so the build fails.
        
        
        shadowing
        An inner variable with the same name as an outer one, hiding it inside its braces.
        
        
        variable-length array (VLA)
        An array whose size is a run-time variable: allowed in C, not in standard C++; g++ accepts it as an extension.
        
        
        clang-format
        A tool that rewrites code layout to a chosen style, set in a .clang-format file.
        
        
        clang-tidy
        A tool that checks code for known bad patterns ("checks"), chosen in a .clang-tidy file, and can apply fixes with --fix.
        
        
        check family
        The prefix of a clang-tidy check's name: modernize-, bugprone-, cppcoreguidelines- and more.
        
        
        fix-it
        A suggested replacement printed under a warning, which a tool can apply automatically.
        
        
        sanitizer
        A compiler option that adds run-time checks for one kind of bug: ASan (memory), UBSan (undefined behaviour), LSan (leaks), TSan (data races), MSan (uninitialised reads).
        
        
        sanitizer matrix
        Which sanitizers can share a build: ASan + UBSan together, TSan and MSan each alone.
        
        
        _GLIBCXX_ASSERTIONS
        A macro that switches on cheap checks inside libstdc++, such as vector index checks.
        
        
        Valgrind / Memcheck
        A tool that runs an unchanged program on a simulated processor; Memcheck reports bad memory accesses and leaks.
        
        
        Compiler Explorer
        A website (godbolt.org) that compiles code with many compilers side by side.
        
        
        std::string_view
        A non-owning view of characters: a pointer and a length, from <string_view>.
        
        
        dangling
        Describes a view, pointer or reference whose target has been destroyed. Using it is undefined behaviour.
        
        
        temporary
        An unnamed object, such as a function's returned value, destroyed at the end of the full statement that made it.
        
        
        literal suffix
        Letters after a literal that change its type: "oil"s is a std::string, "oil"sv a std::string_view.
        
        
        format spec
        The instructions after the colon in a std::format slot: fill, align, sign, #, width, precision, type.
        
        
        std::vformat
        The version of std::format for format strings known only at run time; it throws std::format_error on a bad spec.
        
        
        std::from_chars / std::to_chars
        Fast conversions between text and numbers, from <charconv>; they report errors with std::errc and never throw.
        
        
        encoding
        A recipe for storing characters as bytes.
        
        
        UTF-8
        The most common encoding: 1 byte for ASCII characters, 2 to 4 bytes for everything else.
        
        
        code point
        A character's number in Unicode, such as U+00E9 for é.
        
        
        char8_t / std::u8string
        C++20's types for UTF-8 bytes, written with u8"..."; std::cout refuses them.

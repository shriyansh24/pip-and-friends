C++ · CHAPTER 11

SMOKE ALARMS, DARK ROOMS

Picture: Wren, the mechanic in orange coveralls, waves hello. Next to her stands the Sanitizer, a figure in a long green coat with big green night-vision goggles and a torch.

"It worked when I tried it" is not the same as "it works". This chapter gives your programs a safety net. First, tests: checks with answers you already know, and smoke alarms (assert) that scream the moment something you assumed turns out false. Then the scariest room in C++: undefined behaviour, where no rules apply at all. You'll meet the Sanitizer, whose night-vision goggles show the furniture in the dark, and learn to read its reports like a detective. About 110 minutes, with 22 hands-on checks and a sorting game.

  1. Expected versus actual: your first tests
  2. The smoke alarm: assert, NDEBUG and static_assert
  3. Good tests: edge cases, regression tests, coverage
  4. The dark room: undefined behaviour
  5. Night-vision goggles: sanitizers and the safety-net build
  6. Boss level and recap

    PART 2 · THE SMOKE ALARMassert, what NDEBUG does to it, and static_assert
    

  
    
    5
    
    A smoke alarm on the kitchen ceiling is silent while everything is fine, and screams the moment something is burning. assert(condition); is a smoke alarm for your code. You write down something you believe must be true at that spot. If it's true, nothing happens at all. If it's false, the program stops immediately and says exactly which belief broke, and where.
    
    
    
    
    
      
    Wren says: An alarm doesn't put out fires. It just makes sure you notice the fire straight away, right next to where it started, instead of three rooms later. Silent when fine, loud when not.

    PART 3 · GOOD TESTSEdge cases, the year 1900, test first, regression tests and coverage
    

  
    
    12
    
    Which inputs should you test? Picture every possible input as an island. In the middle are the ordinary inputs, and most code handles those. Bugs live on the beaches: the edge cases, the smallest, emptiest, most negative and largest inputs.
    
    
    
    
      
    THE USUAL EDGES
    • Empty: no items, an empty string.
    • One: a single item; loops run once.
    • Negative and zero: numbers below or at 0.
    • Biggest: the largest value the type holds.
    
      
    AND ALSO
    • All items the same.
    • The answer is first, or last.
    • Special rules in the problem itself, like the leap year rule coming up.
    • Inputs the function promises not to accept: guard them with an assert instead of a test.

It stays quiet on a pass and only speaks up on a failure, so a clean run is one short line. std::numeric_limits<int>::max(), from <limits>, is the largest int.

    18
    
    Two habits professionals swear by. Test first: when you find a bug, write the test that catches it before you fix anything, and watch it fail. Keep it: after the fix, the test stays in the file for good. A test kept to stop an old bug coming back is a regression test (to regress means to slide backwards).
    
    
    Then the next bug: start again at 1.
    
    
    
      
    Wren says: Why watch it fail first? Because a test that has never failed might not test anything: maybe it calls the wrong function, or checks the wrong thing. Seeing it go from FAIL to PASS proves both the test and the fix. Catch it once, keep the trap forever.

It can't tell you your tests are good: a line can run and still give a wrong answer nobody checked.
    
    
    
  
    

  
  
    PART 4 · THE DARK ROOMUndefined behaviour: what it is, its cousins, and why it can look fine
    

  
    
    20
    
    Tests check answers. But C++ has a deeper danger. The rules of C++ list some things you must never do, such as reading past the end of a vector. If a program does one of them, the rules say nothing at all about what happens next. That's called undefined behaviour, or UB. It's like walking around a dark room: some nights you cross it fine, some nights you break a toe, and it can be different every night.
    
    
    
      
      
    
    
    
    
      
    Wren says: "Anything can happen" really means anything. It might crash. It might print a sensible-looking number. It might work perfectly today and fail tomorrow, on a friend's computer, or after a compiler upgrade. No rules apply, not even "it crashes".
    
      
    
    
  
    

  
    
    21
    
    Why would a language allow that? Speed. Checking every vector index and every addition for overflow costs time. So C++ makes a deal with you: you promise never to break these rules, and in return the Compiler may assume you never do and make your program as fast as it can.
    
    
    
      
      
    The Professor says: That assumption is what makes UB so strange. The Compiler doesn't add a check that "does something bad"; it simply builds the program as if the bad case could never happen. If it does happen, the program is running on a promise that was broken, and the result can be anything. A different compiler, or the same one with -O2 (optimise for speed), may build a different program from the same broken promise.
    
    
    
    
    
      
    Wren says: "Close to the metal. Careful with the wrench." The speed is real, and so is the danger. This book has a strict rule: we never show the output of a program with UB as if it meant something. We only show what the safety tools say about it.
    
      
    
    
  
    

  
    
    22
    
    UB has two milder cousins. Learn to tell all three apart:
    
    
    
      
    IMPLEMENTATION-DEFINEDeach compiler chooses, and says so
    The rules leave a detail open, and each compiler must pick an answer and document it. How many bytes an int takes. Whether plain char can be negative. Safe to rely on for one compiler and machine; check it with static_assert.
    
      
    UNSPECIFIEDthe compiler chooses, quietly
    The rules allow a few outcomes, and the compiler may pick any of them without telling you. The order in which a function's arguments are worked out is the classic case. Your program must work whichever it picks.
    
      
    UNDEFINEDno rules at all
    The rules give no meaning to the program. Not one of a few answers: anything. Reading past the end of a vector, overflowing an int, dividing by zero, reading a variable nobody set.

      The worst part: UB often looks fine. This course's research notes record what happened when an out-of-bounds read and an overflow were run without any safety tools: each printed an ordinary-looking number, with no error at all.       PART 5 · NIGHT-VISION GOGGLESAddressSanitizer, UndefinedBehaviorSanitizer, library checks, .at() and the safety-net build
      

  
      
    29
    
      Warnings read the source. A sanitizer watches the program while it runs. Add -fsanitize=address,undefined when you build, and g++ adds a guard to every memory access and every risky sum. The program runs a little slower and uses more memory, and the moment it breaks a rule, it stops and writes a report.
      
    
      
      
      
      The Sanitizer says: I wear night-vision goggles. In the dark room I see every chair: AddressSanitizer (ASan) sees memory: reads past the end (heap-buffer-overflow), memory that was already given back (heap-use-after-free). UndefinedBehaviorSanitizer (UBSan) sees sums: overflow, dividing by zero. I don't guess. I stop you at the exact line, and I tell you what, where and why.
      
    
      
    
      
      
      Wren says: Two more flags in this book's sanitizer builds: -fno-sanitize-recover=all makes it stop at the first problem instead of carrying on into the dark, and -fno-omit-frame-pointer keeps the "who called whom" trail tidy for the report.

    Under the hood: how assert vanishes, how the goggles see, and why UB changes with -O2
    
          
      
          assert is a macro
          
      
          assert is not a function. It's a macro: a piece of text the preprocessor (Chapter 10's #include helper) swaps in before compiling. Roughly: if NDEBUG is defined, assert(anything) becomes ((void)0), which does nothing; otherwise it becomes "if the condition is false, print the message and call std::abort()". That's why the condition's own text appears in the message (the macro turns it into a string), and why work inside it disappears entirely under -DNDEBUG: the code is never even compiled. It also means NDEBUG must be defined before <cassert> is included, which the -D flag guarantees.
          
      
          How AddressSanitizer sees the furniture
          
      
          ASan keeps a secret second map of memory, the shadow memory: one shadow byte for every 8 bytes of your program's memory, saying how many of those 8 bytes you may touch. Around every block it hands out, it leaves a few bytes of poisoned "no entry" space, called redzones. Every read and write in your program is compiled with a tiny check of the shadow first. In panel 31's folded map, 00 means "all 8 bytes are yours", [04] marks the bad address's group, where only the first 4 bytes are yours (12 bytes = 8 + 4), and fa is a heap redzone. Freed blocks are poisoned too (fd) and kept out of use for a while, which is how heap-use-after-free is caught.
          
      
          A blind spot. ASan only checks code that was compiled with it, and this machine's standard library (libstdc++) wasn't. A std::string also keeps short text in a small buffer inside the string object itself, so a read a few letters past the end can stay inside memory ASan thinks is fine. Some misuse of std::string therefore goes unreported. -D_GLIBCXX_ASSERTIONS and .at() (panel 36) check string indexes too. (This gap comes from the sanitizer and library documentation and from Chapter 8's notes; no program on this page shows it, because a run that ASan misses would be undefined behaviour shown as output.)
          
      
          How UBSan sees sums
          
      
          UBSan wraps each risky operation in a check: before a + b on ints, "would this overflow?"; before a / b, "is b zero?". Most checks are cheap, which is why UBSan is often left on in testing for good.
          
      
          Why UB changes between builds
          
      
          An optimiser is allowed to assume UB never happens. Given for (int i = start; i <= end; ++i), it may assume i never overflows, so the loop must end, and it builds faster code on that basis. If the assumption is broken, the faster code does whatever it does. Different compilers, versions and -O levels make different assumptions, so the same broken program can behave differently under each. Experts call the most surprising cases "time travel": because the compiler reasons about the whole function, code before the UB can be affected too.
          
      
          Unsigned numbers are different
          
      
          Unsigned types never overflow in the UB sense: arithmetic on them is defined to wrap around modulo 2N (for a 32-bit unsigned int, 232). That's why 0u - 1 is 4294967295 and why v.size() - 1 on an empty vector is a huge number (Chapter 9). The sanitizers don't report it, because it isn't against the rules; it's just usually a bug.
          
      
          Two compilers, one library
          
      
          On this machine clang++ uses g++'s standard library (libstdc++), so -D_GLIBCXX_ASSERTIONS works with both; only the wording of the message differs. Here is clang++'s run of the same program:

    In real programs
    
          
      
            
        
          • Test frameworks. Real projects use a framework such as doctest, Catch2 or GoogleTest: each test gets a name, failures show expected and actual side by side, and one command runs thousands of tests. It's the check function from panel 13, grown up. This book meets one in a later chapter.
            • 
        
          • Continuous integration. Many teams make a server build and test every change automatically, often once with sanitizers and once with optimisation, and refuse to accept a change that turns any test red.
            • 
        
          • Fuzzing. A fuzzer feeds a program millions of random or mutated inputs under ASan and UBSan, hunting for edge cases nobody thought of. Big browser and operating-system projects run fuzzers all day.
            • 
        
          • Hardened libraries. Library checks like _GLIBCXX_ASSERTIONS are cheap enough that some Linux distributions build their packages with them switched on. libc++ (used by Apple's clang) has a similar "hardening mode", and Microsoft's library checks indexes in debug builds.
            • 
        
          • Asserts in release builds. Some projects keep certain asserts on even in finished programs, because stopping loudly is safer than carrying on with broken data. Others write their own always-on check macros.
            • 
        
          • Calendars really are hard. Real date code relies on well-tested libraries (C++20's <chrono> has calendar types) rather than hand-written rules.
            • 
      
          
    
          
  
          

  
          
    Common wrong ideas
    
          
      
            
        
          • "It printed the right answer, so it works." For that input, on that day. Test the edges; build with the safety net.
            • 
        
          • "All tests pass, so there are no bugs." The leap-year tests passed with a bug inside (panel 14).
            • 
        
          • "Asserts check user input." They vanish with -DNDEBUG. User input needs real checks.
            • 
        
          • "assert(x = 5) checks x is 5." One = assigns. Use ==, and keep work out of asserts.
            • 
        
          • "UB means the program crashes." It means anything, including working, or printing a believable wrong number.
            • 
        
          • "Exit code 0 means no UB." UB promises nothing, not even an exit code.
            • 
        
          • "Implementation-defined is the same as undefined." Implementation-defined is documented and safe on one compiler; undefined is never safe.
            • 
        
          • "No warnings means no UB." Panels 28 and 30: two compilers, two different holes, and an off-by-one loop with no warning at all.
            • 
        
          • "The sanitizer said nothing, so the program is correct." It only checks the paths that ran, and it doesn't check answers or blank variables.
            • 
        
          • "The report's line number is the bug." It's where the rule broke. The cause may be a line earlier (Boss 2) or in a caller.
            • 
        
          • "Unsigned numbers are safe." They're defined, not safe: 0 − 1 is over four billion.
            • 
        
          • "I'll add the safety net later." The longer you wait, the more places a bug could hide. Lights on from the start.

    Lab: run it yourself (Windows, macOS, Linux)
    
          
      
          1. Asserts and NDEBUG
          
      
          Make a folder cpp-ch11, save alarm.cpp, and build it as the terminal shows: g++ -std=c++23 -Wall -Wextra -g alarm.cpp -o alarm, then ./alarm (Windows PowerShell: .\alarm.exe). Then add -DNDEBUG and run it again. With Microsoft's compiler: cl /std:c++20 /W4 /EHsc alarm.cpp, and /DNDEBUG to switch asserts off. Visual Studio's "Release" configuration defines NDEBUG for you, which surprises many people. (Microsoft's compiler was not run for this course.)
          
      
          2. The safety-net build
          
      
            
        
          • Linux (g++ or clang++): g++ -std=c++23 -Wall -Wextra -g -fsanitize=address,undefined -D_GLIBCXX_ASSERTIONS oob.cpp -o oob, then ./oob. On some distributions clang++ needs its sanitizer runtime package installed first; on this course's machine it isn't, which is why every report here comes from g++.
            • 
        
          • macOS: Apple's clang (also called g++ there) supports -fsanitize=address,undefined. Its library is libc++, so -D_GLIBCXX_ASSERTIONS does nothing; recent versions offer -D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST instead. Reports look the same, with different addresses and paths.
            • 
        
          • Windows (MSVC): cl /std:c++20 /W4 /EHsc /Zi /fsanitize=address oob.cpp gives AddressSanitizer. MSVC has no UndefinedBehaviorSanitizer; its debug builds (/MDd) check vector indexes instead.

    Words from this chapter
    
          
      
          
        
          test
          Running code on an input whose right answer you already know, and comparing.
          
        
          test case
          One input with its expected answer.
          
        
          expected / actual
          The answer you worked out by hand / the answer the code really gave.
          
        
          pass / fail
          Expected and actual match / don't match.
          
        
          edge case
          An input at the limits: empty, one item, negative, zero, the largest value, or an exception in the problem's rules.
          
        
          assert
          A run-time check from <cassert>: does nothing if true; if false, prints the file, line, function and condition, then aborts (exit 134 here).
          
        
          precondition
          A rule a caller must keep before calling a function, such as "the carton is not empty".
          
        
          NDEBUG
          A name that, when defined (-DNDEBUG), turns every assert into nothing.
          
        
          static_assert
          A check the Compiler makes while building; a false condition is a compile error. Not affected by NDEBUG.
          
        
          test-first
          Writing the test that shows a bug (and watching it fail) before fixing the bug.
          
        
          regression test
          A test kept forever so that a fixed bug can't come back unnoticed.
          
        
          code coverage
          A count of which lines (or branches) ran during the tests; gcov reports it for g++ builds made with --coverage.
          
        
          undefined behaviour (UB)
          Something the rules forbid and give no meaning; after it, anything can happen.
          
        
          implementation-defined
          A detail each compiler must choose and document, such as sizeof(int).
          
        
          unspecified
          A detail where the rules allow several outcomes and the compiler may pick any without saying, such as the order arguments are worked out.
          
        
          signed integer overflow
          A result too big or too small for a signed type like int; undefined.
          
        
          dangling reference
          A reference to something that no longer exists, such as a vector cup after the vector moved its items.
          
        
          unsequenced modification
          Changing one variable twice in a single expression with no order between the changes.
          
        
          sanitizer
          A build option that adds checks to a program so it reports rule-breaking while it runs.
          
        
          AddressSanitizer (ASan)
          -fsanitize=address: catches bad memory reads and writes, such as heap-buffer-overflow and heap-use-after-free.
          
        
          UndefinedBehaviorSanitizer (UBSan)
          -fsanitize=undefined: catches overflow, division by zero and other undefined operations.
          
        
          heap
          The memory area where a vector (and other growable things) keep their items.
          
        
          heap-buffer-overflow
          Reading or writing past the end (or before the start) of a block on the heap.
          
        
          heap-use-after-free
          Using heap memory after it was given back.
          
        
          stack trace
          The numbered #0, #1... lines: where it happened, then who called that, and so on.
          
        
          _GLIBCXX_ASSERTIONS
          A flag that switches on cheap checks inside g++'s standard library, such as vector indexes.
          
        
          safety-net build
          This book's habit: -Wall -Wextra -g -fsanitize=address,undefined -D_GLIBCXX_ASSERTIONS.
          
        
          Valgrind
          A Linux tool that runs an unchanged program inside a slow memory checker.

C++ · CHAPTER 19

BAKED BEFORE THE PARTY

Picture: Wren, the mechanic in orange coveralls, waves hello with her wrench.

The workshop is throwing a party, and Wren has a rule for the kitchen: anything that can be done before the guests arrive, gets done before the guests arrive. In C++ that rule has names. const seals a box so nobody can change it. constexpr and consteval ask the Compiler to bake a value while building, so the running program just serves it. static_assert checks the cake before the party starts. Then the second half of the kitchen: auto, a label-maker that reads a box and prints its type (but peels off some stickers), nicknames for long types, and lunchboxes that pack two or three values together: std::pair, std::tuple and structured bindings. About 120 minutes, with 27 hands-on checks.

  1. Sealed boxes: const on variables, parameters, member functions and pointers
  2. Baked before the party: constant expressions, constexpr variables and functions
  3. Checked before the doors open: consteval, static_assert, if constexpr and the map of when things run
  4. The label-maker: auto, auto&, const auto&, decltype and when not to use auto
  5. Nicknames and lunchboxes: using aliases, CTAD, pair, tuple, tie and structured bindings
  6. Boss level and recap

    PART 2 · BAKED BEFORE THE PARTYConstant expressions, constexpr variables, constexpr functions and the as-if rule
    

  
    
    8
    
    
    Every C++ program lives through two times. Compile time is the kitchen before the party: the Compiler reads your code and builds the program file. Run time is the party itself: someone types ./slices and the program does its work. A cake can be baked in either one. The guests eat the same cake, but only one of them makes them wait.
    
    
    
    
    
      
      
    Wren says: constexpr means "this can be worked out at compile time". The Compiler does the sums while building and writes the answer into the program file. At the party there's nothing left to do but serve it. My kitchen motto: bake it before the party.
    
    
    
  
    

  
    
    9
    
    A constant expression is an expression the Compiler can work out completely while building: literals like 12, other constants, and arithmetic on them. A constexpr variable must be given one. Line 7 multiplies two constexpr values, so it's a constant expression too. Line 8 shows why that matters: the size of a std::array must be known while building, and slices is.
    
    bake.cpp
    
    
      
    
      
    
    
    
    
    
      
      
    Wren says: A constexpr variable is also const: sealed, like panel 1. On top of that it's a promise that its value is known before the party, so it can go anywhere C++ demands a compile-time number: array sizes, static_assert, and (Chapter 26) template arguments.

      A secret from the Professor's desk. Here's a plain function, not constexpr. We ask g++ to show the machine instructions it makes for main (-S writes assembly, the human-readable form of machine code; the two greps keep only main's lines). First with no optimising (-O0), then optimising (-O2).
      
    asif.cpp
    
      
    
      
      
      -O0: done at the party
      
      
      -O2: quietly done in the kitchen
      
    
      
    
      How this run was really made: asif_O0.cpp is a byte-for-byte copy of asif.cpp, kept under its own name so each build has its own record. 
      
    
      
      
      
      The Professor says: At -O0, main puts 10 in a register (one of the processor's own tiny storage boxes) and calls the function. (Ignore endbr64, the first instruction in both: it's a security marker this compiler puts at the start of functions.) At -O2, the call is gone: movl $24, %eax just loads the answer, 24. The optimiser may change anything, as if the program ran exactly as written, as long as nobody can tell the difference. That's the as-if rule. So why write constexpr? Because the optimiser's baking is a favour, not a promise. constexpr is a guarantee, checked even at -O0, and usable where C++ demands a constant.

      PART 4 · THE LABEL-MAKERauto and its rules, auto& and const auto&, decltype, the vector<bool> surprise, and when not to use auto
      

  
      
    24
    
      Writing types out gets tiring: std::map<std::string, std::vector<int>>::const_iterator, anyone? auto lets the Compiler work out a variable's type from its starting value. This is called type deduction. Think of auto as a label-maker: it reads the box you give it and prints the label for you.
      
    
      
    
      
      
      
      Wren says: The rule to remember: plain auto makes a brand-new box, a copy. So it peels off the & sticker (a copy isn't a nickname for anything) and the outer const sticker (your copy is yours to change). Want them? Ask: auto&, const auto, const auto&. auto reads the box, but peels the stickers.
      
    
      
  
      

  
      
    25
    
      How can we see what auto picked? C++ has no portable way to print a type's name. Instead, each line 12 to 17 makes a claim and the Compiler checks it. decltype(a) means "the declared type of a", and std::is_same_v<X, Y> (from <type_traits>) is true only when X and Y are exactly the same type. If any claim were wrong, the build would stop, and nothing at all would print.
      
    auto_basics.cpp
    
      
      
      
      
      
    
      
    
      
      
      
      Wren says: Two surprises. "hi" on line 9 is a C-style text literal, so d is a const char*, a pointer to letters, not a std::string. Line 10 says std::string out loud to get one. And 5u (line 11) is unsigned int: the u suffix matters. auto takes the literal's type exactly.

        One famous trap. To save memory, std::vector<bool> packs each bool into a single bit, and you can't make a nickname to one bit. So lit[0] doesn't give a bool&; it gives a small stand-in object, a proxy, that remembers which bit it means. auto faithfully copies the proxy.
        
    vecbool.cpp

Line 8 spelled out bool, so second is a real copy and kept its 1. Line 9 proves it: first is not a bool.
        
    
        
    
          
      
        1. Only std::vector<bool> does this. std::vector<int>, std::vector<char> and every other vector hand out real references.
          2. 
      
        2. The fix: when you want the value, name the type: bool first = lit[0];.
          3. 
      
        3. No error, no warning: both compilers build this silently. A static_assert with std::is_same_v is how you'd catch it.
          4.

    30
    
        auto takes its type from the first value, and only from the first value. Two programs where that bites. First: auto total = 0; makes an int, so every price is chopped to a whole number as it's added (2.5 + 1.25 + 4.75 = 8.5, but the int ends at 7, with no warning). Second: auto i = 0 is an int, compared with size()'s unsigned type.
        
    
        
      
        silent: chopped to whole numbers
        auto_trap.cpp
        
      
        a warning: signed vs unsigned
        auto_sign.cpp
        
    
        
    
          
      
        • Use auto when the type is already on the line or is long and obvious: auto it = ages.find("Ada");, auto p = std::make_unique<Robot>();, auto count = v.size();.
          • 
      
        • Use auto in range-for, always with the right sticker: const auto& or auto&.
          • 
      
        • Spell the type when the exact type is the point: money (double total{0.0};), counters compared with sizes, and values from std::vector<bool>.
          • 
      
        • Spell the type when a reader would have to hunt for it. Code is read far more often than it's written (Core Guideline ES.11 says use auto to avoid repeating type names, not to hide them).
          •

In the second, the loop works here, but the warning is a smell: use a range-for, or std::size_t i. Chapter 20 tells the whole signed-and-unsigned story.

          What you learned in Chapter 19
          
    
            
      
          • SEAL IT UNLESS IT MUST CHANGEconst on variables, on look-only parameters (const T&) and on look-only member functions (int degrees() const). A const object can only call const member functions. Const turns silent slips into compile errors (panel 3's spot).
            • 
      
          • READ IT RIGHT TO LEFTconst int* p: a pointer to a sealed int; it may move but not write. int* const p: a sealed pointer; it may write but not move. The errors say "read-only location" or "read-only variable".
            • 
      
          • BAKE IT BEFORE THE PARTYA constant expression is worked out while building. constexpr variables must be given one; constexpr functions may run at compile time or at run time; consteval functions must run at compile time. Only promises can be baked: a plain variable or an ordinary function call stops the build.
            • 
      
          • CHECK THE CAKE BEFORE THE DOORS OPENstatic_assert(condition, "message") checks while building, prints your message and the worked-out comparison. Test constexpr functions with it: free, every build, and undefined behaviour is refused in the kitchen.

          • AUTO READS THE BOX, BUT PEELS THE STICKERSPlain auto makes a copy and drops the & and the outer const. Want the real thing? Ask for the &: auto&, const auto&. decltype(x) copies a type exactly. Beware vector<bool> proxies, auto total = 0, and {5} versus (5).
            • 
      
          • NAME THE PARTSusing gives long types short names. std::pair and std::tuple pack values; structured bindings unpack them into new names, std::tie into existing ones. For anything that lasts, a struct with good names beats positions.

    Under the hood: what the kitchen may do, top-level and low-level const, and the exact rules of auto
    
          
      
          What a constexpr function may contain
          
      
          C++11's first constexpr functions could hold a single return statement. C++14 allowed local variables, loops and if, which is why make_squares and factorial look like ordinary code. C++20 went further: try blocks, virtual functions, and even new/delete, as long as every allocation is given back before the constant evaluation ends; that's how std::vector and std::string can be used inside a constexpr function. What a constant evaluation may never do: read a variable that isn't a constant, call a non-constexpr function, or do anything with undefined behaviour, such as signed overflow (panel 21), reading past an array's end, or dividing by zero. Compilers also cap the amount of work one constant evaluation may do (g++ has switches like -fconstexpr-ops-limit), so an endless loop in the kitchen ends in a compile error, not a frozen build.
          
      
          Three related keywords
          
      
            
        
          • constexpr on a variable: const, and initialised by a constant expression. On a function: may be evaluated at compile time.
            • 
        
          • consteval (C++20), functions only: every call must produce a constant. Called an immediate function.
            • 
        
          • constinit (C++20), for global and static variables: the starting value must be worked out at compile time, but the variable is not const and may change later. It guards against a problem Chapter 28 meets: globals whose start-up order between files is unpredictable.
            • 
      
          
      
          Top-level and low-level const
          
      
          A top-level const seals the object itself: const int ci, or the pointer in int* const p. A low-level const seals something the object leads to: the int in const int* p, or the int named by const int& r. auto drops top-level const, because the new variable is a separate copy and copying a sealed value into your own box is harmless. It keeps low-level const, because dropping it would let you change a sealed object through the copy (Boss 6). A reference is always "low-level": auto& on a const object gives const T&.
          
      
          The full auto rules, briefly
          
      
            
        
          • auto x = expr; uses the same rules as a function template's by-value parameter: references and top-level const are dropped; arrays and functions turn into pointers.
            • 
        
          • auto& x = expr; keeps const; it can't bind to a temporary (auto& x = 5; is an error). const auto& x = 5; can.
            • 
        
          • auto x{1}; is an int (since C++17), but auto y = {1, 2}; is a std::initializer_list<int>, a light read-only list. Another reason this book writes auto x = 1; when it uses auto.
            • 
        
          • decltype(name) gives the declared type exactly. decltype((name)), with extra parentheses, treats it as an expression and gives a reference, int&. A trap for experts, not for today.
            • 
      
          
      
          How CTAD and structured bindings work
          
      
          CTAD uses the class's constructors (and helper rules the library writes, called deduction guides) to work out the template arguments: std::pair p{1, 2.5}; is a std::pair<int, double>. A structured binding auto [a, b] = t; secretly makes one hidden copy of t and makes a and b names for its parts; with auto& the hidden variable is a reference to t, so the names reach the real parts. That's why the & on the binding matters in Boss 2.
          
      
          Why vector<bool> is different
          
      
          In 1998 the standard gave std::vector<bool> a space-saving special version: one bit per value instead of one byte. Its operator[] returns std::vector<bool>::reference, a small class that holds the address of a word and the position of a bit, and converts to bool when read. Most experts now consider that a mistake, but it can't be removed without breaking old programs. If you need real bools, use std::vector<char>, std::deque<bool>, or for a fixed number of bits, std::bitset (Chapter 20).
          
    
          
  
          

  
          
    In real programs
    
          
      
            
        
          • Named constants instead of macros. Old C code writes #define MAX_GUESTS 40, a text replacement with no type and no scope. Modern C++ writes constexpr int max_guests{40};: typed, scoped and visible in a debugger.
            • 
        
          • Lookup tables. Checksums (CRC tables), colour palettes, sine tables in games and audio code, character-class tables in parsers: all are classic constexpr tables, built while compiling instead of at start-up.
            • 
        
          • Small devices. On microcontrollers, a constexpr table can be placed in read-only flash memory instead of precious RAM, and nothing has to be computed when the device switches on.
            • 
        
          • Checks that travel with the code. Libraries static_assert on the sizes of structs that are sent over a network or written to files, so a change in layout breaks the build instead of corrupting data. The standard library itself guards std::get with one (panel 36).
            • 
        
          • Compile-time format strings. Chapter 18 showed std::format("{} and {}", 1) failing to compile: the format string is checked by a consteval constructor inside the library. That's this chapter's tool, used by the library authors.
            • 
        
          • Inserting into maps. auto [it, inserted] = ages.insert({"Ada", 36}); unpacks the std::pair<iterator, bool> that insert returns: where the item is, and whether it was new.
            • 
        
          • Aliases in big code bases. Projects name their important types once, using UserId = std::int64_t;, so a later change touches one line, and readers see meaning instead of machinery.
            • 
      
          
    
          
  
          

  
          
    Common wrong ideas
    
          
      
            
        
          • "A constexpr function always runs at compile time." Only when its result is needed as a constant and its arguments are constants. Otherwise it's an ordinary function (panel 11). For "always", use consteval.
            • 
        
          • "const and constexpr are the same." Both seal. Only constexpr guarantees the value is known while building (panel 14).
            • 
        
          • "If a variable holds a number that never changes, it's a constant expression." The Compiler looks at promises, not at values (panel 13).
            • 
        
          • "constexpr makes my program faster." It moves work from the party to the kitchen, which can help, but the optimiser often bakes plain code anyway (panel 16). constexpr is first of all a guarantee and a way to use values where C++ demands constants.
            • 
        
          • "const int* and int* const mean the same." Read right to left: the first seals the int, the second seals the pointer (panel 5).
            • 
        
          • "A const reference means the value can't change." It means you can't change it through that name. Someone else may (Boss 1).
            • 
        
          • "auto x = v[0]; gives me the element." It gives you a copy. Ask for the & (panel 27).
            • 
        
          • "auto keeps const." Only low-level const. A plain auto copy of a const int is a changeable int (panel 26).
            • 
        
          • "auto is slower or makes code dynamic." The type is fixed at compile time, exactly as if you'd written it. Nothing changes at run time.
            • 
        
          • "std::vector v{5}; makes five zeros." It makes one 5. Parentheses mean "this many" (panel 33).
            • 
        
          • "A tuple is always better than a struct because it's shorter." Shorter to write, slower to read. Name the parts (panel 37).

    Words from this chapter
    
          
      
          
        
          const correctness
          Marking everything that shouldn't change as const, so the Compiler can enforce it.
          
        
          immutable
          Unchangeable after it's made.
          
        
          read-only
          The Compiler's word for const in error messages: may be read, never written.
          
        
          const member function
          A member function with const after its parameters; it promises not to change the object, so it may be called on const objects.
          
        
          pointer to const
          const int* p: the pointer may move, but may not be used to change what it points at.
          
        
          const pointer
          int* const p: the pointer can't be moved to another address, but may change what it points at.
          
        
          top-level / low-level const
          A const on the object itself, or on something the object points to or names.
          
        
          compile time
          While the Compiler is building the program ("the kitchen").
          
        
          run time
          While the built program is running ("the party").
          
        
          constant expression
          An expression the Compiler can work out completely at compile time.
          
        
          constexpr
          On a variable: const and known at compile time. On a function: may be evaluated at compile time.
          
        
          consteval
          C++20: a function whose every call must be evaluated at compile time (an immediate function).
          
        
          static_assert
          A check the Compiler makes while building; a false condition stops the build with your message.
          
        
          if constexpr
          An if whose condition is a constant expression; the branch not taken is discarded from the program.
          
        
          as-if rule
          The optimiser may change anything about how a program runs, as long as its visible behaviour stays the same.
          
        
          assembly
          A human-readable form of machine instructions, such as movl $24, %eax.
          
        
          register
          One of the processor's own tiny storage boxes, where it keeps the numbers it is working on right now (%eax, %edi in panel 16).
          
        
          type deduction
          The Compiler working out a type from a starting value (auto) or from constructor arguments (CTAD).
          
        
          auto
          "Work out this variable's type from its starting value." Drops references and top-level const.
          
        
          decltype
          decltype(x) is the declared type of x, exactly.
          
        
          std::is_same_v
          From <type_traits>: true when two types are exactly the same.
          
        
          proxy
          A stand-in object that acts on behalf of another, like the bit reference std::vector<bool> hands out.
          
        
          type alias
          A second name for an existing type: using Scores = std::vector<int>; (or the older typedef).
          
        
          CTAD
          Class template argument deduction: std::vector v{1, 2}; works out <int> by itself (C++17).
          
        
          std::pair
          Two values packed together, reached as .first and .second.
          
        
          std::tuple
          Any number of values packed together, reached by position with std::get<N>.
          
        
          structured binding
          auto [a, b] = thing;: new names for the parts of a pair, tuple, struct or array (C++17).
          
        
          std::tie
          Makes a tuple of references to existing variables, so std::tie(a, b) = pair; unpacks into them.

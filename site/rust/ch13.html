Mabel says: Every time Cleo asks for her violin, I start at pocket 0 and check every pair until I find her name. With three readers it's fine. With three thousand, she'll miss her concert.

The Professor says: Then stop searching. Give every locker a label, and walk straight to the one that says "Cleo". Rust's name for a room of labelled lockers is a HashMap.

Picture: Mabel shrugs at a long list. The Professor answers from the right.

2

A HashMap is a room of lockers. Each locker has a label on the door and one thing inside. You never ask for "locker number 2"; you ask for "the locker labelled Ben".

KEYthe label

What you look things up by. Each key appears at most once in a map: two lockers can't share a label.

VALUEthe thing inside

What you get back. Two lockers may hold equal things.

HashMap<K, V>the room

All keys share one type K, all values one type V. A key with its value is a pair (or entry).

    26
    
      For problems that can happen, Rust answers with a parcel. Open it and you find either the gift you asked for, or a note explaining what went wrong. Never both, never neither.
      
    
      
      
      
    
      
    
      Picture: two cardboard parcels with faces. The first, smiling, holds up a wrapped present; its label says Ok of 42. The second, startled, has a folded note marked with an exclamation mark sticking out; its label says Err of note.
      
    
      
      
      It's just another enum from the standard library, like Option:
      

      enum Result<T, E> {
    Ok(T),    // success, carrying a T
    Err(E),   // failure, carrying an E
}
      
    
      
    
      
      
      Option<T>the gift box
      Some(value) or None. "Maybe nothing, and nothing needs explaining": no such locker, an empty Vec.
      
      
      Result<T, E>the parcel
      Ok(value) or Err(reason). "It might fail, and here's why": text that isn't a number, a file that isn't there.

    Under the hood: hash numbers, random seeds, growing tables, and what ? really writes
    
      
      
      
        
        
      The Professor says: Let's open the number machine.
      
      
      
      
      Real hash numbers
      
      hash_numbers.rs
      
      
      A hash function turns any key into a big number, a u64 here (up to about 18 quintillion). The same key always gives the same number, and different keys almost always give very different numbers. The map uses a few bits of that number to pick a slot in its table, so finding a key costs about the same whether the map holds ten pairs or ten million. (DefaultHasher::new() always starts from the same fixed keys, which is why these numbers are the same on every run.)
      
      
      Why the order changes between runs
      
      
      A HashMap doesn't use fixed keys. Each new map gets a RandomState, seeded with random numbers picked while your program runs, so its hash numbers, and therefore its slots, are different every run, and different for each map. That's deliberate. If an attacker could predict where keys land, they could send a web server thousands of keys that all land in the same slot and make it crawl (a "HashDoS" attack). Today's standard hasher is SipHash-1-3, chosen to be hard to predict while still fast; the documentation promises only that it's a good, unpredictable hasher, not which algorithm, so it can change. The Rust book notes you can plug in a faster hasher from crates.io if you have measured that hashing is your bottleneck.
      
      
      The table grows
      
      capacity_map.rs
      
      
      Like a Vec, a map starts with no table at all (capacity 0) and grows when it's nearly full: here 3, then 7, then 14 pairs of room, on Rust 1.99.1. When it grows, every pair is hashed again into the bigger table. That's one more reason never to rely on the order: even one insert can reshuffle everything. HashMap::with_capacity(n) reserves room up front.
      
      
      Sizes
      
      sizes.rs
      
      
      The map itself is 48 bytes on this 64-bit machine: a pointer to its table, some counters, and the 16 bytes of its random seed. The pairs live in the heap table. A Result<u32, ParseIntError> is only 8 bytes: a tag saying Ok or Err plus room for the bigger of the two. And Result<(), String> is 24 bytes, the same as a String: the Compiler hides the Ok/Err tag in a value a String can never have, the same trick that makes Option<&T> free (Chapter 11's notebook).
      
      
      What ? really writes
      
      
      expr? means very nearly the long match from panel 36, with one extra step: Err(e) => return Err(From::from(e)). That From::from converts the note into the error type your function promised. It's why ? can pass a ParseIntError out of a main that promised Box<dyn Error>: every error type can be converted into that box. Chapter 21 uses From to design your own error types.
      
      
      What a panic does on its way out
      
      
      By default a panic unwinds: it walks back up the stack of function calls, dropping every value on the way, as if each function had reached its closing brace. Files get closed, memory is freed, and then the program exits with 101. A project can choose panic = "abort" in its Cargo.toml profile to skip the clean-up and stop at once (smaller programs, no tidy-up). Exit codes, in short: 0 success; 1 main returned an Err; 101 a panic, or cargo failing to compile.

    Common wrong ideas
    
      
      
        
        
      • "A HashMap keeps the order I inserted things." No, and it doesn't sort them either. The order can change between runs and after any insert. Sort the keys or use BTreeMap.
        • 
        
      • "It printed in the same order three times, so it's safe." Small maps can repeat an order by luck. Someone else's run, or tomorrow's, may differ.
        • 
        
      • "map.get(k) gives me the value." It gives an Option<&V>: a box holding a look at the value.
        • 
        
      • "insert won't touch an existing key." It replaces the value (and hands the old one back). Use entry(k).or_insert(v) to insert only when the key is new.
        • 
        
      • "A value of 0 means the key isn't there." Some(0) and None are different answers (panel 7's Ben).
        • 
        
      • "I can use my struct as a key." Only after #[derive(PartialEq, Eq, Hash)] (E0277), and not if it contains an f64.
        • 
        
      • "Result is for exceptions, like in other languages." Rust has no exceptions. A Result is an ordinary value you return, and the type tells every caller that failure is possible.
        • 
        
      • "? ignores the error." It does the opposite: it hands the error to the caller, immediately.
        • 
        
      • "? works anywhere." Only inside a function that returns Result (or Option). In a plain main it's E0277.
        • 
        
      • "expect is safer than unwrap." Both panic on Err. expect just leaves a better message.
        • 
        
      • "A panic and returning Err from main are the same." A panic is "the program has a bug" (exit 101, thread id, backtrace note). An Err from main is a clean "this didn't work" (exit 1).
        • 
        
      • "Warnings don't matter." The unused-Result warning in panel 34 was a real lost loan.

PART 1 · THE SHAPE SORTERwhat a pattern is, the six places patterns live, patterns that might not fit, E0005 and let...else

1

Saturday morning in the children's corner. A toddler pushes a star at the square hole. It won't go. She turns it, tries the star-shaped hole, and clunk: it drops in.

Mabel says: You've been using a shape sorter since Chapter 6! Every arm of a match is a hole with a shape. The value is the piece. Rust tries the holes from top to bottom and drops the piece through the first one it fits.

The Professor says: Rust calls a hole's shape a pattern. Today you'll see that patterns turn up in six places, not just in match, and that some holes have little hands that grab the parts inside the piece.

Picture: Mabel explains with a pointing hand; the Professor answers from the right.

2

A pattern describes the shape of a value. Checking a value against a pattern is called matching. If the value has that shape, the pattern fits (it "matches"), and any names written inside the pattern are filled in with the matching parts. That filling-in is called binding.

  • Literal patterns, like 0 or 'a', fit only that exact value.
  • Name patterns, like w or n, fit anything and grab it.
  • Shape patterns, like Some(w), (x, y) or Book { title, .. }, check the outside and grab the insides.
  • The wildcard _ fits anything and grabs nothing.
3

    4
    
Some holes fit every piece that could possibly arrive. (title, pages) fits every pair. Others fit only some pieces: Some(first) doesn't fit None. Rust has a word for each kind.

    

      

        
IRREFUTABLE = can't fail to fit

        
x, (a, b), Book { title, pages }, _

        
Required by let, for and function parameters. There's no "else" there: the program has nowhere to go if the piece doesn't fit.

      

      

        
REFUTABLE = might not fit

        
Some(x), Ok(n), 0, 1..=5, [first, ..]

        
Allowed in match arms, if let, while let and let…else, because each one says what happens when it doesn't fit.

      

    

    

      
      
Mabel says: "Refute" means "prove wrong". A refutable pattern can be proved wrong by some value. Catchphrase: if it might not fit, say what happens when it doesn't.

A hole can have the shape of a whole struct, with a little hand at every field. Taking a value apart like this is called destructuring. A hand can grab the field under its own name, or under a new name, or reach further in, into a struct inside the struct.

    
    
    
The shorthand title means "the field title, into a name called title"; pages: p means "the field pages, into a name called p".

        What you learned in Chapter 21
        
    
          
      
        • EACH HOLE IS A PATTERN; NAMES ARE LITTLE HANDSPatterns live in let, match, if let, while let, for and function parameters. They check a shape and grab its parts: structs, enums, tuples, slices, nested as deep as you like.

        • IF IT MIGHT NOT FIT, SAY WHAT HAPPENS WHEN IT DOESN'TRefutable patterns need an escape: match, if let, while let or let…else. In a plain let: E0005. Gaps in a match: E0004 (guards don't count). Arms after a catch-all: unreachable.
          • 
      
        • UNDERSCORE ALONE GRABS NOTHING_ moves nothing; _name still grabs. Grabbing a String field moves it (a partial move, E0382); match on a reference or use ref to borrow instead.
          •

          •

    Under the hood: how matching and ? really work
    
        
      
        
        
        
        The Professor says: None of this costs anything when the program runs. Here's what the Compiler does with it.
        
      
        
      
        Exhaustiveness is a compile-time puzzle
        
      
        For every match, the Compiler works out which values no arm covers, using an algorithm based on "usefulness": an arm is useful if some value reaches it, and the match is exhaustive if a final _ arm would be useless. That's how it can print the gaps as ranges, like i32::MIN..=0_i32 in panel 20, and how it finds unreachable arms (panel 21). Guards are left out of this reasoning on purpose: a guard can run any code, and deciding what arbitrary code returns is impossible in general.
        
      
        Matching compiles to plain jumps
        
      
        A match on an enum is compiled into a check of the enum's hidden tag (which variant it is) and a jump, often a jump table. Range patterns become comparisons. There's no "pattern object" at run time. That's why patterns are as fast as hand-written ifs, and often faster.
        
      
        Binding modes ("match ergonomics")
        
      
        When a non-reference pattern meets a reference, as in panel 14, Rust switches the default binding mode to "by reference", so names bind as &T (or &mut T for a &mut). This arrived in 2018; before it, code was full of &Some(ref x). Edition 2024 tightened the rules: inside a pattern that is already binding by reference, writing ref, mut or an explicit & is now an error, because the old meaning surprised people. If you meet such an error in old code, cargo fix --edition rewrites it.
        
      
        What ? expands to
        
      
        On a Result, expr? behaves roughly like match expr { Ok(v) => v, Err(e) => return Err(From::from(e)) }. The From::from call is the customs desk. Every type has a free impl From<T> for T, which is why ? works without any impl when the forms already match. On an Option, ? returns None early instead, and you can't mix the two in one function without converting (ok_or, .ok()).
        
      
        A surprising cousin of E0277
        
      
        Write the same broken line without the turbofish, let days: u32 = text.trim().parse()?;, and you get a different code. The real run of mix_errors_infer.rs:
        
      
        
      
        E0271 is a "type mismatch resolving" error: without ::<u32>, the Compiler is still working out which type parse makes when the ? asks for a LoanError, and it reports the clash in terms of FromStr::Err. Same cause, same fix (a From impl or map_err). If an error message about ? confuses you, adding the turbofish often makes it clearer.
        
      
        Why main prints Debug
        
      
        main may return any type that implements the Termination trait. For Result<(), E> with E: Debug, an Err is printed as Error: {:?} to stderr and the exit code is 1. anyhow's Debug face is written to look like a human report (panel 36), which is why it reads so nicely there.
        
    
        
  
        

  
        
    In real programs: patterns and errors in the wild
    
        
      
          
        
        • Command parsers match on slices of words: match words.as_slice() { ["add", name] => …, ["remove", name] => …, ["list"] => …, _ => help() }. A whole little command language in one match.
          • 
        
        • State machines (a door, a game, a network connection) match on (state, event) pairs: (Closed, Push) => Open. The Compiler checks every pair is handled.
          • 
        
        • Compilers and interpreters, including rustc itself, are mostly enormous matches over nested enums describing code.
          • 
        
        • The standard library's own errors follow this chapter's design: std::io::Error has a kind() you can match on (NotFound, PermissionDenied, …), and std::io::Result<T> is a type alias.
          • 
        
        • thiserror and anyhow are very widely used. Many Rust command-line apps use anyhow (or a relative such as eyre), and many libraries use thiserror.
          • 
        
        • Command-line tools often print errors with the chain on one line, error: card "x": not a number: invalid digit found in string, which is anyhow's {:#} format from the predict check.
          • 
        
        • Clippy (Chapter 15) has lints for this chapter: clippy::unwrap_used and clippy::expect_used can be turned on to forbid unwraps in library code, and clippy::manual_let_else suggests let…else where you wrote a match that returns early.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "A name in a pattern compares with a variable of that name." It always makes a new name (the predict check with Some(y)). Compare with a guard, or use a const, which is matched as a value.
          • 
        
        • "Guards that cover every case make a match exhaustive." Guards never count (Boss 2). Leave the last arm unguarded.
          • 
        
        • "_x and _ are the same." _x binds and moves; _ doesn't bind at all. This also matters for things that do work when dropped: let _ = lock(); drops the value immediately, while let _guard = lock(); keeps it alive to the end of the block.
          • 
        
        • "Destructuring copies the fields." Copy fields are copied; others are moved, leaving a partial move.
          • 
        
        • "Order of match arms doesn't matter." Arms are tried top to bottom; the first that fits wins.
          • 
        
        • "? only passes the error along." It also converts it with From, and that's why E0277 mentions From.
          • 
        
        • "Errors should be Strings." Strings are fine in tiny programs, but callers can't match on them, and you lose the original error.
          • 
        
        • "anyhow is better than thiserror" (or the other way round). They solve different problems: libraries vs applications.
          • 
        
        • "Never use unwrap." It's right for tests, examples, prototypes and broken invariants (with expect and a reason). It's wrong for failures the caller should handle.

    Words from this chapter
    
        
      
        
        
        pattern
        A description of a value's shape, used to check it and take it apart.
        
        
        match / fit
        A value matches (fits) a pattern if it has that shape.
        
        
        binding
        A name in a pattern that receives (grabs) part of the value.
        
        
        destructuring
        Taking a struct, enum, tuple or slice apart with a pattern.
        
        
        irrefutable / refutable
        A pattern that always fits / one that might not. let, for and parameters need irrefutable ones.
        
        
        let…else
        A let with a refutable pattern and an else block that must leave (return, break, continue, panic).
        
        
        wildcard _
        Fits anything, binds nothing.
        
        
        rest pattern ..
        "Any other fields" in a struct pattern; "any number of items" in a slice or tuple pattern.
        
        
        range pattern
        a..=b: any value from a to b, both included. a..: a or more.
        
        
        or-pattern
        A | B: fits if either fits.
        
        
        match guard
        pattern if condition: an extra test after the shape fits. Not counted for exhaustiveness.
        
        
        @ binding
        name @ pattern: check the pattern and bind the whole value.
        
        
        slice pattern
        [a, b], [first, .., last], [first, rest @ ..]: patterns for slices and arrays.
        
        
        partial move
        Moving some fields out of a value; the rest stay usable, the whole doesn't.
        
        
        binding mode / ref
        Whether a name grabs by value or by reference. Matching through a reference binds by reference automatically; ref x asks for it.
        
        
        exhaustive
        A match that covers every possible value (else E0004).
        
        
        unreachable pattern
        An arm no value can reach, because earlier arms cover it.
        
        
        let chain
        if let … && let … && condition, edition 2024 only.
        
        
        custom error type
        Your own type (usually an enum) describing how your code can fail.
        
        
        std::error::Error
        The trait that marks a type as an error; requires Debug and Display; offers source().
        
        
        error source / chain
        The error that caused this one, and the list you get by following sources.
        
        
        combinator
        A method such as map, and_then, or_else, ok_or, map_err that transforms an Option or Result without a match.
        
        
        type alias
        type Result<T> = std::result::Result<T, MyError>;, a short name for a longer type.
        
        
        thiserror / anyhow
        Crates: derive error boilerplate for libraries / one catch-all error with context for apps.
        
        
        context
        A note stapled onto an error saying what was being done, with anyhow's .context().
        
        
        invariant
        A promise your code keeps about its own data; breaking one is a bug, a reason to panic.
        
        
        E0005 / E0004
        A refutable pattern in a let; a match that doesn't cover every value.
        
        
        E0382 / E0277 / E0271
        Use after a (partial) move; ? couldn't convert the error (no From); a type mismatch while resolving parse's error type.

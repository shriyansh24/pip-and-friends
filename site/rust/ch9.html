PART 1 · THE DETECTIVE'S METHODEvery borrow error is a case: read the scene, follow the suspect, pick a known fix

1

Mabel knows the lending rules by heart now. But knowing the rules and fixing a program the Compiler refused are two different skills.

Mabel says: The Compiler says no, I read the message, and then… I start changing things at random until it goes quiet.

The Professor says: Random changes are how detectives arrest the wrong person! Every borrow error is a case. We visit the scene, we follow the suspect, and we open the casebook to see which fixes have worked before.

Picture: Mabel shrugs, unhappy. The Professor, playing detective chief, answers her.

2

The detective board. Every case file has the same three parts, and each part is a piece of the Compiler's message.

SCENE^^^ primary label

The carets mark where the Compiler noticed the clash. It's the line in the --> arrow. Often it's an innocent bystander.

SUSPECT--- secondary labels

The dashes mark the other loan, and where it's later used. That late use is very often the real culprit.

KNOWN FIXEShelp: and the casebook

The help: lines, plus the fixes this chapter collects. Pick the smallest one that tells the truth about your program.

Case file #1. Mabel keeps a queue of readers waiting for Emma. She notes who is next, a new reader joins, and then she announces the next one.

case_queue.rs 

    

    
    
      
  1. error[E0502]: cannot borrow `queue` as mutable because it is also borrowed as immutable
    What: a reader and a writer at once, the Chapter 8 rule.
    2. 
      
  2. ^^^^^^^ mutable borrow occurs here
    The scene, line 4. push writes to the queue, so it needs a writing loan. The push itself is perfectly normal.
    3. 
      
  3. ----- immutable borrow occurs here
    The suspect's loan, line 3: next is a reading pass for slot 0.
    4. 
      
  4. ---- immutable borrow later used here
    The suspect's alibi falls apart, line 5: next is still being used after the push. That one late use stretches the reading loan across the writer.
    5. 
    

    

      
      
The Professor says: The caret points at the push. But nobody would say "never push to a list"! The suspect is the reader on line 3 who is still reading on line 5. Catchphrase: follow the suspect, not the scene.

Before fixing anything, a good detective asks one question: is this program really dangerous, or is the Compiler just being careful? Here it's really dangerous.

SCENE^^^
Line 4, queue.push(...), a writing loan.

        
SUSPECT---

MOTIVEwhy it's unsafe
A push may move the whole queue to a bigger heap block (Chapter 8, panel 19). next would then point at freed memory.

        
KNOWN FIXES
    
          
  1. Shorten the loan: finish with next before pushing.
    2. 
          
  2. Remember a position, not a reference: keep the index 0 and look it up later.
    3. 
          
  3. Clone deliberately: keep your own copy of the name.
    4. 
        

      

    

  


  

    5
    
Three fixes, three real runs. Each one compiles, for a different reason.

    

      
1 · SHORTENfix_queue_shorten.rs

        
Line 4 is next's last use, so its loan ends before the push on line 5. CHEAPEST

      
2 · INDEXfix_queue_index.rs

        
next is just the number 0: no loan at all. Line 5 borrows slot 0 fresh, after the push.

      
3 · CLONEfix_queue_clone.rs

Mabel says: All three are correct. A detective picks the one that fits the story: if I only need the name for a moment, I shorten the loan. If I need it later and the queue keeps changing, I remember the position, or make a copy.

PART 2 · CASE FILE: THE VANISHING LOCALReturning a reference to something a function made: E0106, a trap called E0515, and the owned fix


  

    7
    
A function is a room. Everything made inside it is dropped when the room closes, at its closing brace. What if the room tries to hand out a reading pass to something inside it, on its way out?

    

    

      
      
Mabel says: That's Chapter 8's rule in disguise: bring it back before the owner leaves. Here the owner leaves at the very moment the pass is handed over.

    

  


  

    8
    
    
Case file #2. make_label builds a String and tries to return a reference to it: -> &String.

    case_vanishing.rs
    

    

    
    
      
  1. error[E0106]: missing lifetime specifier
    What: a new word. A lifetime is how long a loan stays valid. A "lifetime specifier" is a way to write that down; you'll learn the notation in Chapter 19. For now, read it as: "this reference has to come from somewhere, and I can't see where."
    2. 
      
  2. ^ expected named lifetime parameter
    The scene: the & in the return type, line 1.
    3. 
      
  3. = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
    The motive, in plain words. The function takes no inputs, so the only thing it could lend is something it made itself, and that is dropped at line 4.
    4.

    Fix suggestion one. Note the word uncommon. Panel 9 shows what happens if you take it.
    5.

    Fix suggestion two, with a - line and a + line: replace &String with String.
    6. 
    

    

      
      
The Compiler says: A reference must point at something that outlives it. Nothing made in that room survives the closing brace, so there's nothing for your & to point at.

    PART 3 · CASE FILE: THE BOOK THAT CAN'T LEAVE THE SHELFMoving out of a vector by index: E0507, and three ways to get a book off the shelf
    

  
    
    13
    
    A Vec is a shelf, and the shelf owns every book on it. If you could just pull Emma out of slot 0 and walk away, the shelf would have a hole that it still thinks holds a book.
    
    
    
    
    
      
      
    Mabel says: When the shelf is dropped, it drops every book in every slot. If Emma had a second owner walking around, she'd be dropped twice. Every book has exactly one owner, and for books on a shelf, that owner is the shelf.

    PART 5 · WINDOWS ONTO THE SHELFSlices: &s[a..b], ranges, &str and &[i32], string literals, and why functions take &str
    

  
    
    25
    
    Mabel has a new kind of loan. Instead of lending the whole shelf, she lays a window frame over part of it. Through the window you see books 2, 3 and 4. You don't own them, and you can't see the rest.
    
    
    
    
    
      
    SLICEa view, not a copy
    A slice is a reference to a run of items that sit next to each other in memory: a window onto part of a String, an array or a vector. It borrows; it never owns.
    
      
    TWO NUMBERSptr + len
    A slice is stored as just two numbers: where the window starts (a pointer) and how many items it shows (its length). Nothing is copied.
    
    
    
  
    

  
    
    26
    
    Two windows onto one String.
    
    slice_basics.rs
    
    
    
    
    
      
      
    1. Line 3: &s[0..5]. The & says "borrow", the [0..5] says which part. 0..5 is a range: start at byte 0, stop before byte 5. So bytes 0, 1, 2, 3 and 4: hello.
      2. 
      
    2. Line 4: &s[6..11]: bytes 6 to 10, world. Byte 5 is the space, left out of both windows.
      3. 
      
    3. The type of hello and world is &str, said "string slice" or "ref str": a window onto text.
      4. 
      
    4. Line 7: s still owns all of it. Windows never take anything.
      5. 
    
    
    
    
      
      
    Mabel says: Start counts, end doesn't: 0..5 is five bytes, and the length is always end minus start. Catchphrase: a slice is a window, not a copy.

    28
    
    Range shorthands, for a String s of length n. They're the same ranges you used in for loops in Chapter 5.
    
    
    
      
    FROM THE START&s[..3]
    Same as &s[0..3]: the first 3 bytes.
    
      
    TO THE END&s[2..]
    Same as &s[2..n]: everything from byte 2 on.
    
      
    EVERYTHING&s[..]
    Same as &s[0..n]: a window over the whole thing.
    
    
    
    
      
      
    • Length = end − start. &s[2..6] is 4 bytes long.
      • 
      
    • a..a is an empty window, length 0. Allowed, and sometimes useful.
      • 
      
    • Past the end is a panic. On an 11-byte String, a window ending at byte 20 stops the program at run time, like the out-of-range index in Chapter 5.
      • 
    
    
    
    See both in a real run
      past_end.rs
    
      
    Line 3's empty window prints as ''. Line 6 asks for bytes 6 up to 20: end byte index 20 is out of bounds for string of length 11. (The end is computed on line 5, while the program runs, so the check happens at run time.) In thread 'main' (1), the (1) is the thread's id number: on your computer it will be a different number.

      2.

      3.

      4.

    sum_slice.rs
    
    
    
    
    
      
      
    1. Line 3: for n in nums walks through the window. Each n is a &i32, a reference to one item, so line 4 writes *n: the star follows the arrow (Chapter 8).
      2.

    A secret you can finally hear: every "text in quotes" you've written since Chapter 1 is a slice.
    
    literal.rs
    
    
    
    
    
      
      
    1. Line 2: the type of a string literal is &'static str. The text is baked into the program itself when it's compiled, and the literal is a window onto it.
      2.

      3. 
      
    3. Line 3: you can take a window of a window. first is another &str, onto the first 5 bytes.
      4.

    Under the hood: fat pointers, UTF-8 and why indexes aren't places
    
      
      
      
        
        
      The Professor says: A slice is the second-simplest thing a computer has: an address, plus a count. Let's measure it.
      
      
      
      
      A slice is a "fat pointer"
      
      
      A plain reference like &String is one address: 8 bytes on a 64-bit machine. A slice reference needs two numbers, the address of its first item and how many items it covers, so &str and &[i32] are 16 bytes. Programmers call that a fat pointer. A String itself is 24 bytes: pointer, length and capacity, as in the stack-and-heap steppers.
      
      sizes.rs
      
      
      (Sizes measured on this 64-bit Linux machine. A slice has no capacity: it can't grow, because it doesn't own the room around it.)
      
      
      The capacities in the steppers, measured
      
      
      Panels 11 and 35 draw each String's len and cap. This program makes the same Strings the same way and prints both, before and after clear().
      
      caps.rs
      
      
      Why &String turns into &str
      
      
      A String knows how to present itself as a window over all of its bytes. When a function wants &str and you pass &my_string, the Compiler quietly inserts that conversion. The same goes for &Vec<i32> to &[i32]. The mechanism is called deref coercion; the trait behind it, Deref, is a Chapter 23 topic. It only works in one direction: a &str can't become a &String, because there may be no String at all (a literal), which is exactly panel 33's error.
      
      
      Bytes, not letters
      
      
      Rust's String and str always hold valid UTF-8: a way of storing every writing system's characters where each character takes 1 to 4 bytes. ASCII (plain English letters, digits, punctuation) takes 1 byte each; é takes 2; many Chinese characters take 3; most emoji take 4. Slicing works in bytes because that's cheap: jumping to byte 1000 is instant, while finding the 1000th character means reading every byte before it. The price is the boundary check you saw in panel 37, which keeps every &str valid UTF-8. Chapter 12 shows the tools for working with characters (chars()) instead of bytes.
      
      
      Why the borrow checker can't see v[0] and v[1] as separate
      
      
      To the borrow checker, pair.0 and pair.1 are different places, with names fixed in the source code. v[i] is a call to the vector's indexing method with a number that may only be known at run time; the method borrows the whole vector to do its work. split_at_mut is written with a small amount of carefully checked low-level code inside the standard library, which is allowed to promise that its two halves never overlap. You get a safe tool; the library's authors carry the proof.
      
      
      Case files the Brown edition keeps
      
      
      This chapter's casebook follows the idea of the Brown University edition of the Rust book, which has a chapter of ownership "case studies" that the official book lacks. Its question, "is this program actually unsafe?", is the heart of step 4 in panel 6's checklist.
      
    
      
  
      

  
      
    In real programs: how professionals use slices and the casebook
    
      
      
        
        
      • Parameters are windows. Experienced Rust programmers write &str and &[T] for parameters almost by reflex. Linters (Clippy, the official one, in a later chapter) even warn when you write &String or &Vec<T> as a parameter type.
        • 
        
      • Returning windows into an input is common: find the first word, trim spaces, pick out a field from a line of text. Returning windows into something the function made is never possible; return an owned String or Vec for that.
        • 
        
      • Windows onto data you already have avoid copying: an average of the last 7 days, the first 3 readings, the weekend.
        • 
      
      
      in_real.rs
      
      
      ({:.1} prints a number with one decimal place, and as f64 turns the count into a decimal number for the division; both came up in Chapter 3.)
      
      
        
        
      • Clones in real code are fine and common for small things, or when two parts of a program need independent copies. Many beginners clone to silence errors; many experts first ask whether a function should be borrowing instead.
        • 
        
      • Indices instead of references is a pattern big programs use deliberately: games store "entity number 7" instead of a reference to it, so the list of entities can change freely.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "The error is on the line with the caret." The caret marks the scene. The fix is usually at the suspect: the "later used here" label, or the signature named in a note:.
        • 
        
      • "Take the first help: suggestion." Read them all. For E0106, the first suggestion ('static) is the uncommon one, and leads to E0515 with a local.
        • 
        
      • ".clone() is always the safe fix." It always compiles, but it's often a sign a function should borrow instead. And changing a clone never changes the original.
        • 
        
      • "A slice is a copy of part of the String." It's a window: a pointer into the same bytes and a length. Nothing is copied.
        • 
        
      • "&s[2..5] is 4 bytes, from 2 to 5." The end is left out: bytes 2, 3, 4, which is 3 bytes. Length is end minus start. Write 2..=5 if you want to include 5.
        • 
        
      • "Slice indexes count letters." They count bytes. In héllo, byte 2 is the middle of é.
        • 
        
      • "A string literal is a String." It's a &'static str: a window onto text baked into the program. String::from("…") copies that text into a new, owned, growable String.
        • 
        
      • "Functions should take &String to borrow text." They can, but &str accepts more: literals and windows too.
        • 
        
      • "Two &mut to different slots of a vector are always fine." They are safe, but the Compiler can't tell slots apart (E0499). Use split_at_mut.
        • 
        
      • "A slice can grow if I push to it." A slice doesn't own its room, so it has no push. To grow something, you need the owner (the String or the Vec).
        •

    Words from this chapter
    
      
      
      
        
      scene / primary label
      The ^^^ label in a compiler message: where the problem was noticed.
      
        
      suspect / secondary label
      The --- labels: the other loan involved and where it's used later.
      
        
      lifetime
      How long a reference stays valid. Writing lifetimes down ('a) is Chapter 19.
      
        
      'static
      The lifetime "valid for the whole run of the program", which text baked into the program has.
      
        
      local variable
      A variable made inside a function; dropped at that function's closing brace unless moved out.
      
        
      E0106 / E0515
      Returning a reference with nothing to borrow from; returning a reference to a local.
      
        
      E0507
      Moving a value out of somewhere you only have access to, such as a vector's slot.
      
        
      remove(i) / swap(i, j)
      Take item i out of a vector, owned, closing the gap; trade two items in place.
      
        
      splitting a borrow
      Lending different parts of one value (such as two fields) to different borrowers at once.
      
        
      slice
      A reference to a run of neighbouring items: a window. Stored as a pointer and a length.
      
        
      range
      a..b: from a up to, but not including, b. a..=b includes b. Shorthands ..b, a.., ...
      
        
      string slice, &str
      A window onto UTF-8 text. String literals are &'static str.
      
        
      &[T]
      A window onto items of type T, from an array or a vector, such as &[i32].
      
        
      deref coercion
      The Compiler turning &String into &str (and &Vec<T> into &[T]) where needed.
      
        
      UTF-8
      The way Rust stores text: 1 to 4 bytes per character.
      
        
      char boundary
      The line between two characters' bytes. Slices must start and end on one.
      
        
      byte literal, b' '
      A single byte, written like a character with a b in front.
      
        
      fat pointer
      A reference that carries extra information beside the address, like a slice's length.
      
        
      split_at_mut(i)
      Cuts a vector or array into two writing windows, ..i and i.., that can't overlap.

Chapter 17 called a trait a badge: a promise that a type has certain methods. The standard library comes with a set of ready-made traits, the standard traits, and its own tools are built to accept any type wearing the right one. Think of a travel adapter kit: the wall sockets are std's tools, each trait is a plug shape, and your type can grow as many plugs as it needs.

    
    
    

      
Derivea plug off the shelf
Some plugs have one obvious shape. Write #[derive(Debug, Clone, PartialEq)] above the struct and the Compiler builds them for you, field by field (Chapter 17 showed that a derive writes the impl for you).

      
Hand-madeyou shape it yourself
Other plugs need a decision only you can make, like what a Card should look like on screen. You write impl Display for Card { … } yourself.

    

    

      
      
Mabel says: So std isn't refusing my card. It's waiting for the right plug. Catchphrase: grow the plug, fit the socket.

    5
    
Debug is for programmers. Display is for people: the words a reader of your program sees. Rust can't guess those, so Display can't be derived. You write it, and it always has the same shape:

    
The Display plug, ready to fill in:
use std::fmt;

impl fmt::Display for Card {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "…your words…", …)
    }
}

    
    
      
  • fmt is the one method the trait asks for. It borrows the card (&self) and writes words into f.
    • 
      
  • f: &mut fmt::Formatter is the page being written: println! hands it over, and you write on it.
    • 
      
  • write!(f, …) works exactly like println!, same placeholders, except it writes onto f instead of the screen, and adds no newline.
    • 
      
  • fmt::Result says whether the writing worked. write! already hands one back, so it can be the last line, with no semicolon (Chapter 4: the last line drops out).
    • 
    

    

      
      
Mabel says: Polite voice for readers, x-ray goggles for programmers. Two plugs, two jobs. Catchphrase: Debug you derive, Display you decide.

Chapter 7 had a rule: flyers are photocopied, keys are cut. Two plugs make that rule work for your own types.

    

      
      
    

    
Picture: first, a photocopied flyer of a key, stamped COPY and tagged Point. Second, a freshly cut spare key with little sparkle lines, tagged Book.

    
    
      
  • Copy needs Clone. You always derive both: #[derive(Clone, Copy)]. Every Copy type can also be cloned; not every Clone type can be copied.

    PART 3 · COMPARING, SORTING AND HASHINGPartialEq and Eq for ==, a hand-written eq, PartialOrd and Ord for < and sort, field and variant order, why floats can't use sort, and Hash for HashMap keys
    

  
    
    11
    
    Four plugs answer two questions. Are these the same? (==, !=) and which comes first? (<, >, sort). Each question comes in a "partial" and a "total" version.
    
    
    
    
      
    PlugGives youThe promise
    
      
        
    PartialEq== and !=Values can be compared for sameness.
    
        
    Eqnothing new to callA marker: every value equals itself. Floats can't promise that, because "not a number" (NaN) isn't equal to itself.
    
        
    PartialOrd< > <= >=, partial_cmpMost pairs have an order; some (NaN again) may not.
    
        
    Ordcmp, sort, max, BTreeMap keysEvery pair has an order, always. Needs Eq and PartialOrd too.

    14
    
    Derive all four plugs and your type can be compared with < and sorted. The derived order follows two rules you can see in the code.
    
    ord_derive.rs
    
    
    
    
    
      
      
    1. Enums: earlier variants are smaller. Small is written first, so Small < Large is true and sorting gives [Small, Medium, Large].
      2. 
      
    2. Line 16: cmp (from Ord) answers with an Ordering, an enum with three variants: Less, Equal, Greater. Medium is Less than Large.
      3. 
      
    3. Structs: fields compared top to bottom. author is declared first, so books sort by author; only two books by the same author look at title. That's why both Austens come first, Emma before Persuasion.
      4. 
      
    4. Text is compared letter by letter, like a dictionary, but by character code: every capital letter comes before every small letter. The next exercise tests that.
      5.

    15
    
    
    Mabel measures three shelves and wants the heights in order. Numbers can be sorted, surely?
    
    
    
      
    WRONG: sort() on floats
    sort_floats.rs
    
      
    RIGHT: sort_by(f64::total_cmp)
    sort_floats_fixed.rs
    
    
    
    
      
      
    1. error[E0277]: the trait bound `{float}: Ord` is not satisfied. {float} is the Compiler's name for "some float, I haven't picked which yet". Where: .sort(), which needs Ord. The help lists types that do have Ord: all integers, no floats.
      2. 
      
    2. Why: floats include a special value, NaN ("not a number", what you get from 0.0 / 0.0). The fixed program shows it: nan == nan is false, and comparing 1.0 with NaN gives None, "no order at all". So floats wear only the partial plugs.
      3.

      4.

    A conversion turns a value of one type into another. Implement From<X> for Card, "a Card can be made from an X", and you get two doors into the same booth.

      •

    PART 5 · OPERATORS AND DEREFevery operator is a trait method: Add, Mul and Neg for a Step type, E0369 without them, Index and IndexMut for shelf[2], and a first look at Deref
    

  
    
    26
    
    Here's a secret: + is not magic. When Rust sees a + b, it calls a method, Add::add(a, b), from the trait std::ops::Add. Numbers wear that plug already. Give it to your own type, and + works on it. This is called operator overloading.
    
    
    
      
    You write → Rust callsPlug (in std::ops)
    
      
        
    a + b
    → a.add(b)    		Add (also Sub for -, Div for /, Rem for %)
    
        
    a * 3
    → a.mul(3)    		Mul<i32>: the right-hand side can be a different type
    
        
    -a
    → a.neg()    		Neg: one value in, one out
    
        
    a += b
    → a.add_assign(b)    		AddAssign: changes a in place
    
        
    shelf[2]
    → *shelf.index(2)    		Index, and IndexMut to change it
    
        
    a == b, a < b
    → a.eq(&b), a.lt(&b)    		PartialEq, PartialOrd (Part 3: they're in std::cmp)
    
          
    
    
    
    
      
      
    Mabel says: An operator is a machine with a nickname. Catchphrase: every operator is a method in disguise.
    
    
    
    
    Picture: a machine labelled Add::add, with an input hopper and an output chute.

    Under the hood: what derive writes, how {} finds your fmt, padding, the prelude, and the Hash promise
    
        
      
        
        
        
        The Professor says: Let's unscrew a few plugs and look at the wiring.
        
      
        
      
        What a derive writes
        
      
        A derive is a macro: code that writes code while compiling. #[derive(PartialEq)] on Book { title, year } writes, in effect, an impl PartialEq for Book whose eq returns self.title == other.title && self.year == other.year. A derived Clone calls .clone() on every field; a derived Debug calls the formatter's struct helper with each field's name and value. That's why every field must already wear the plug: the generated code calls it. The tool cargo expand (a separate install) can show you the exact code.
        
      
        How {} finds your fmt
        
      
        println! is a macro too. For each {} it arranges a call to Display::fmt for that argument, and for each {:?} a call to Debug::fmt, passing a Formatter that writes to the screen. format! passes one that writes into a new String, which is how to_string() works for every Display type.
        
      
        Width and padding
        
      
        Placeholders can ask for a width: {:>8} means "at least 8 characters, pushed right". write! ignores that request; f.pad(…) honours it.
        
      pad.rs
        
      
        Which plugs are always in reach
        
      
        The prelude is the list of names every Rust file can use without a use line. It includes Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Default, Drop, From, Into, AsRef, ToString, and (since the 2021 edition) TryFrom and TryInto. Not in it: fmt::Display, str::FromStr, hash::Hash (derive finds it anyway) and the std::ops operator traits. That's why this chapter's programs import exactly those.
        
      
        The Hash promise
        
      
        A HashMap trusts one rule: if two keys are equal, their hashes are equal. Derive both PartialEq and Hash and it holds automatically. But eq_custom.rs compares only the ISBN; if that type also derived Hash, two "equal" copies would hash their conditions too, get different fingerprints, and land in different lockers. Whenever you hand-write eq, hand-write hash from the same fields.
        
      
        The orphan rule, again
        
      
        You may implement a std trait for your type, or your trait for a std type, but not a std trait for a std type: impl Display for Vec<i32> is Chapter 17's E0117. To give a Vec a Display, wrap it in a struct of your own.
        
      
        Version differences
        
      
        The two compilers word the HashMap error slightly differently: Rust 1.99.1 adds a second label under the key (`CallNumber` doesn't satisfy the trait bound); Rust 1.97.0 has only the first. Here is 1.97.0's run of the same hash_missing.rs:

    In real programs: derive everywhere, Display for errors, From and ?, operators in maths crates, Drop that closes files
    
        
      
          
        
        • Derive is everywhere. Most structs in real Rust code start with #[derive(Debug, Clone, PartialEq)], and many add Eq, Hash or Default. Crates can define derives of their own: the popular serde library adds #[derive(Serialize, Deserialize)] to turn structs into JSON and back.
          • 
        
        • Display for errors. Chapter 21 builds error types that implement Display (the message a person reads) and std::error::Error.
          • 
        
        • From makes ? smarter. When ? passes an error back, it calls From::from on it, so a function returning your own error type can use ? on many kinds of failure, as long as each has a From. Chapter 21 again.
          • 
        
        • Operators in maths and games. Vector and matrix libraries implement Add, Mul, Neg and Index so that formulas look like formulas. Money and time types do the same: std's own Duration can be added to an Instant.
          • 
        
        • Drop that cleans up. A std::fs::File closes itself in its Drop, so you never forget to close a file (Chapter 25). A lock's guard unlocks in its Drop (Chapter 26). This pattern, "acquire in a constructor, release in Drop", is often called RAII.
          • 
        
        • Default for settings. Configuration structs with dozens of fields are built with Config { port: 8080, ..Default::default() }.
          • 
        
        • AsRef for friendly functions. Many std functions take impl AsRef<Path> or AsRef<str>, so callers can pass whatever kind of text they have.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "I can derive Display." No: Display is always hand-written. Only nine std traits derive.
          • 
        
        • "Copy and Clone are the same thing." Copy happens by itself on = and in calls; Clone only when you write .clone(). Copy needs Clone.
          • 
        
        • "I'll make my struct Copy so it stops moving." Only if every field is Copy. A String, Vec or Box inside rules it out (E0204).
          • 
        
        • "A clone shares its data with the original." A clone is independent; changing one doesn't change the other.
          • 
        
        • "Derived == compares whether two variables are the same object." It compares field by field. Two separate Books with the same fields are equal.
          • 
        
        • "Derived order sorts by the most important field." It sorts by the first field written, then the next.
          • 
        
        • "Numbers can always be sorted." Integers, yes. Floats aren't Ord: use sort_by(f64::total_cmp).
          • 
        
        • "Any struct can be a HashMap key." It needs Hash and Eq, so no float fields unless you take special steps.
          • 
        
        • "I must implement Into too." Write From; Into comes free. Writing Into by hand is almost never needed.
          • 
        
        • ".into() figures out the type." Only from context: give it a type on the left, or E0282.
          • 
        
        • "I should call .drop() to clean up early." That's E0040. Call drop(x), or let the scope end.
          • 
        
        • "Values are dropped in the order they were made." The reverse: newest first.
          • 
        
        • "A moved value is dropped where it was moved from." It's dropped wherever its last owner's scope ends.
          • 
        
        • "Operator overloading is slow." a + b is an ordinary method call, which the optimiser usually inlines; it costs the same as calling add yourself.

    Words from this chapter
    
        
      
        
        
        standard trait
        A trait defined by the standard library, which std's own tools accept: the plugs in the adapter kit.
        
        
        derive, #[derive(…)]
        An attribute asking the Compiler to write a trait's implementation from the fields. Nine std traits can be derived.
        
        
        attribute
        A note to the Compiler written in #[…] above an item.
        
        
        Debug / Display
        Printing for programmers ({:?}, {:#?}, derivable) / printing for people ({}, hand-written).
        
        
        fmt::Formatter, write!, fmt::Result
        The page a fmt method writes on; the macro that writes on it; the "did writing work?" answer.
        
        
        Clone / Copy
        An explicit copy with .clone() / an automatic copy by bytes, for plain values with no heap data and no Drop. Copy needs Clone.
        
        
        marker trait
        A trait with no methods, only a promise: Copy, Eq, Sized.
        
        
        PartialEq / Eq
        == and != / the promise that every value equals itself (floats can't make it).
        
        
        PartialOrd / Ord, Ordering
        Comparisons that may have no answer / a total order for sort and cmp; the answer Less, Equal or Greater.
        
        
        NaN
        "Not a number", a special float value that isn't equal to anything, itself included.
        
        
        Hash, hash
        The plug that turns a value into a fingerprint number; HashMap keys need it with Eq.
        
        
        Default
        A sensible starting value, from T::default() or Default::default().
        
        
        From / Into
        A conversion that can't fail, written once as From and usable both ways.
        
        
        TryFrom / TryInto
        A conversion that can fail, handing back a Result with its own Error type.
        
        
        FromStr
        Parsing text into your type, so parse works; its note type is Err.
        
        
        AsRef
        "Can lend you a reference to this": AsRef<str>, AsRef<Path>.
        
        
        operator overloading
        Giving your type an operator by implementing its trait: Add, Sub, Mul, Neg, Index, IndexMut…
        
        
        Deref
        "Treat me as a reference to what's inside"; mainly for smart pointers (Chapter 23).
        
        
        Drop, destructor
        The plug whose drop method runs automatically when a value's owner goes out of scope.
        
        
        drop(x)
        A prelude function that takes ownership of x, so it's dropped right away.
        
        
        Sized
        Having a size known while compiling. str and [T] aren't, so they live behind references.
        
        
        prelude
        The names every Rust file can use without a use line.
        
        
        E0277 / E0204 / E0369 / E0282 / E0040 / E0184
        A missing trait; Copy on a type with a non-Copy field; an operator the type doesn't support; type annotations needed (here, for into); calling .drop() yourself; Copy on a type with Drop.

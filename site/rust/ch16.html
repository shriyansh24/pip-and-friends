PART 2 · OPENING THE BOOKstd::fs::read_to_string, the parcel it hands back, and why a missing file shouldn't be a panic


  

    8
    
A file is text (or other data) kept on the disk under a name, like poem.txt. A path is the name you use to find it: just poem.txt means "in the folder the program was started from". To read one, the robot uses std::fs::read_to_string (fs is short for "file system").

    
    
    
Its signature, as the docs show it (Chapter 15: read the arrow before you call):
pub fn read_to_string<P: AsRef<Path>>(path: P) -> io::Result<String>

    
    
      
  • After the arrow: io::Result<String>, a parcel (Chapter 13). Opening a file can fail even when your program is perfect, so you get Ok(String) or Err(io::Error).
    • 
      
  • The <P: AsRef<Path>> part means "any kind of thing that can act as a path": a &str, a String or a &String all work. Chapter 17 explains how to read signatures like this one, and Chapter 18 meets AsRef itself.
    •

PART 3 · A CLIPBOARD FOR THE SETTINGSa Config struct, Config::build returning a Result, process::exit(1), who owns the Strings, and the two pipes: stdout for data, stderr for trouble


  

    12
    
Look at main in read_file.rs: it collects words, picks them apart, reads the file and prints. Soon it would also check the count, search and report errors. A function that does everything is hard to read and impossible to test. Programmers call the fix separation of concerns: one job per piece.

    

      
The receptionistmain, from now on
Collects the words, hands them to Config::build, hands the result to run, and if anything comes back as an Err, tells the reader and closes the desk. Nothing else.

      
The clipboardstruct Config
One form that keeps the settings together: query (what to look for) and file_path (where). Its build function checks the words before filling the form in.

    PART 5 · TEACHING IT TO SEARCHtest first: a failing test, then just enough code; the lifetime label 'a on search; lines() and contains(); results that are windows onto the file
    

  
    
    21
    
    The robot still can't search. We'll write search the way many professionals do: test first. Write a test that describes the job, watch it fail, then write just enough code to make it pass. This is called test-driven development.
    
    
    
    
    
      
    The Inspector says: Show me the checklist before you build. If my stamp says FAIL first, I know the test can really catch a mistake. Catchphrase: see it fail, then make it pass.
    
      
    
    
    
    Picture: the Inspector, in a yellow hard hat and orange vest, holds up a stamp reading FAIL.
    
  
    

  
    
    22
    
    
    First, the signature. search takes the word and the file's text, and hands back the matching lines as &str windows: no copying. The obvious way to write it doesn't compile.
    
    search_nolife.rs
    
    
    
    
    
      
      
    1. error[E0106]: missing lifetime specifier. You met E0106 in Chapter 9, when a function tried to lend out something it made itself.
      2. 
      
    2. The help: line says the real question: the signature does not say whether it is borrowed from `query` or `contents`. The returned windows look onto something. Onto which input?
      3. 
      
    3. The Compiler's suggestion puts 'a on everything, which is more than we need. We know the answer: the lines come from contents, never from query.
      4. 
    
    
    
    So we label only those two:
    fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str>
    
    
      
      
    • 'a (say "tick a") is a lifetime label, a name for "how long a borrow lasts". <'a> after the name introduces it, like a variable for borrows.
      • 
      
    • &'a str on contents and Vec<&'a str> on the result say: "the windows I hand back look onto contents, so they're good only as long as contents is".
      • 
      
    • The label doesn't change how long anything lives. It's a promise written down, so the Compiler can check every caller. Chapter 19 tells the whole story.
      • 
    
    
    
    
      
      
    Mabel says: It's my oldest rule, written into the signature: the found lines are borrowed from the poem, so bring them back before the owner leaves.

    Under the hood: how the words arrive, words that aren't text, exit codes, and what cargo test ran
    
      
      
      
        
        
      The Professor says: Let's open the antenna and the exit door.
      
      
      
      
      How the words get in
      
      
      When the terminal starts a program, the operating system hands it a list of words (traditionally called argv, "argument vector") and a table of environment variables. Splitting at spaces and removing quotes is the terminal's job, done before your program starts, which is why "night owl" arrived as one word with no quotes. cargo run builds the program, then starts it with the words after --. Word 0 is whatever path was used to start it: target/debug/args here; on Windows something like target\debug\args.exe. Programs shouldn't rely on word 0 being anything in particular.
      
      
      Words that aren't text
      
      
      On Linux and macOS, a command-line word can be any bytes at all, not necessarily valid UTF-8 (Chapter 12). env::args() promises Strings, so if a word isn't valid UTF-8, it panics. Here the bash trick $'\xe9' sends one byte that is not UTF-8:
      
      
      
      
      How this run was really made: as in panel 3, the helper script go.sh set up the cargo project ~/rust-ch16/bad_utf8 from bad_utf8.rs, with poem.txt beside Cargo.toml; then exactly the command shown ran there.
      
      
      The panic points into the standard library's own env.rs, because that's where the conversion failed. (Rust 1.97.0 printed that path with a different folder name, a commit hash, and a different line number; that is the only difference between the two versions here.) Programs that must accept any file name use env::args_os(), which hands out OsStrings: the operating system's own kind of text, which can hold anything.
      
      
      Why build clones: taking a word out of a borrowed list
      
      
      Panel 13's build copies each word with .clone(). Here is what happens without it. This small program fills its list by hand and asks build to keep word 1:
      
      move_out.rs
      
      
      E0508: args is a &[String], a borrowed window onto someone else's list, so a String can't be carried out of it. The two help: lines show the two ways out: borrow the word (&args[1], a window that must go back before the list's owner leaves) or clone it (args[1].clone(), a copy build owns). Config keeps its words, so the robot clones.
      
      
      process::exit and exit codes
      
      exit_flush.rs
      
      
      process::exit(n) ends the whole program at once with exit code n; the code is yours to choose. On this run even the half line without a newline reached the screen. But the documentation warns that nothing on the stack gets its clean-up run (no values are dropped), so the habit is: call it only from main, once the work is done or abandoned. The robot does exactly that. Exit codes in this book so far: 0 success; 1 "it didn't work", from process::exit(1) or a main that returns Err; 101 a panic, or cargo failing to compile. Linux and macOS keep codes from 0 to 255.
      
      
      Display for people, Debug for programmers
      
      
      The same missing-file error printed two ways in this chapter. .expect in panel 10 showed its Debug form, Os { code: 2, kind: NotFound, message: "No such file or directory" }. eprintln!("Application error: {e}") showed its Display form, No such file or directory (os error 2). A Box<dyn Error> can show either; for messages to people, use {}.
      
      
      What cargo test ran
      
      
      For a package with lib.rs and main.rs, cargo test builds three test programs: the library with its #[cfg(test)] code, the binary with its own (we have none), and one that runs the code examples inside the library's /// comments, called doc-tests (Chapter 24). That's why panel 29 shows three running groups. Each test runs on its own thread, which is why a failing test's panic shows its own name and thread id.

    Common wrong ideas
    
      
      
        
        
      • "args[1] is the program's name." That's args[0]. Your first word is args[1].
        • 
        
      • "env::args() gives only the words I typed." It always starts with the program's own path.
        • 
        
      • "The quotes arrive with the word." The terminal removes them and keeps the phrase together.
        • 
        
      • "Words before -- go to my program too." Those belong to cargo. Put your program's words after the gate.
        • 
        
      • "Errors should use println! so people see them." Both pipes reach the screen, but only stderr survives a redirect. Answers to stdout, trouble to stderr.
        • 
        
      • "process::exit is like return." return leaves one function; exit ends the whole program at once, skipping clean-up.
        • 
        
      • "A missing file deserves a panic." A panic says "this program has a bug". A missing file is the world's problem: hand back a Result.
        • 
        
      • "read_to_string returns a String." It returns io::Result<String>: a parcel to open.
        • 
        
      • "lib.rs needs a mod lib; line in main.rs." No: it's a separate crate that cargo finds by itself. main.rs reaches it by the package's name.
        • 
        
      • "contains finds whole words." It finds letters in a row: the matches "there", and owl would match "slowly".
        • 
        
      • "IGNORE_CASE=0 switches it off." With is_ok(), present means on.
        • 
        
      • "The 'a makes contents live longer." It changes nothing at run time. It's a promise the Compiler checks.
        • 
        
      • "A new test should pass the first time." Seeing it fail first proves it can catch a mistake.

      command-line argument
      A word typed after a program's name when starting it.

      Pours a stream of items into a collection; the type you ask for says which kind. (Chapter 20.)
      
        
      --
      In cargo run -- …, the gate: words after it are passed to your program.
      
        
      file, path
      Data stored on disk under a name; the name used to find it, relative to the folder the program runs in unless it starts from the top.
      
        
      std::fs::read_to_string
      Reads a whole file into a String, handing back io::Result<String>.
      
        
      io::Error
      The note inside a failed file operation, with a kind such as NotFound.
      
        
      separation of concerns
      Giving each piece of a program one job.

      std::process::exit(n)
      Ends the program at once with exit code n, skipping clean-up.
      
        
      exit code
      The number a program hands back when it ends: 0 success, 1 failure here, 101 a panic.
      
        
      stdout / stderr
      Standard output and standard error, the two pipes out of every program: answers and trouble.

      Sending stdout (or stderr) into a file instead of the screen.
      
        
      binary crate / library crate
      A program you run (rooted at src/main.rs) / code for other code to use (rooted at src/lib.rs). One package can have both.
      
        
      test-driven development

      stub
      A placeholder body that compiles but doesn't do the job yet.

      Makes a new String with every letter in lowercase.

      Every line of code and every output in this comic comes from a real run: Rust 1.99.1 with edition 2024 (shown) and Rust 1.97.0 (comparison), on 2026-11-08, in /home/you/rust-ch16. Each of the 48 programs was built and run as its own cargo project (the data file also holds the three lib.rs files, recorded as source only) with cargo run -q, a debug build. Runs that need words after --, the poem file, an environment variable, a redirect or cargo test were driven by small command files: a helper script (go.sh) copies each program into src/main.rs (and, for the split projects, its library into src/lib.rs), puts poem.txt next to Cargo.toml, and then exactly the command shown runs there; a note under each of those runs says so. The projects split, split_private and seekbot are cargo packages named seekbot. The four road programs and seek_test.rs are byte-for-byte copies of the finished robot's main.rs, run in its one folder; the badge in panel 29 checks that. args.rs was built in its project's own target folder, as a fresh cargo new project is, so the word 0 it prints is target/debug/args. Test runs used cargo test -q -- --test-threads=1 --format pretty, and their output is shown unchanged: the closing time is a real measurement, so those three runs (panels 23, 24 and 29) are labelled "one possible run" and are never used as answers. The two versions printed the same output for every program. Three runs are listed as differing: in bad_utf8.rs's panic and contains_string.rs's compiler note, only the folder name (a commit hash) and line number of a path into the standard library change; in search_red.rs only the failing test's thread id, which changes from run to run anyway. The thread ids in panics, (1) for main, come from running each program in its own fresh process namespace.
      
  
      The machines, the two memory tracers and the map of roads are teaching models; each checks itself against those runs and shows a badge. The map's four roads are four real runs of the finished robot (seekbot.rs, road_ci.rs, road_noargs.rs, road_nofile.rs). The tracers use small stand-ins (a word list filled in by hand, a three-line text) so they run the same everywhere. The robot, the command-line anatomy, the file machine, the pipes, the building, the test loop, the switch and the teaser are pictures, not output.

PART 1 · THE FRONT DOORa web server is a restaurant; TcpListener::bind opens a door on a port; incoming() is the queue of visitors; an HTTP request is an order card; a response is the plate; read errors like a detective

1

Twenty-eight chapters ago, Mabel's first program printed one line and stopped. Today her program will sit and wait for visitors, and answer each one.

Mabel says: When you type an address into a browser, the browser sends a little order to a program on another computer, and that program sends back a page. That program is a web server. Let's open one!

The Professor says: Everything stays on your own computer today, and we use only Rust's standard library. Real websites use big, well-tested libraries for this. Building a small one by hand is how you see what those libraries do for you.

Picture: Mabel cheers with both arms up. The Professor answers her.

2

Here is the whole idea as a restaurant. Keep this picture: every program in this chapter is a piece of it.

  • The diner is the client: a browser, or any program that asks. The kitchen is the server: a program that waits and answers.
  • The door has an address. 127.0.0.1 is a special address that always means "this same computer" (its nickname is localhost). 7878 is a port: one computer has 65,535 numbered doors, so many servers can run at once. The Rust book picked 7878 because it spells "rust" on a phone keypad.
  • TCP is the corridor between diner and kitchen: a connection that delivers bytes in order, without losing any. HTTP is the language the order card and the plate are written in.

When a browser knocks, it doesn't just stand there. It hands over an order card written in HTTP: plain text, one line after another. (Not Chapter 27's order slip, which was a future waiting to be handed in: this card is what the diner actually wants.)

    

    
    
      
  • The request line says what the diner wants. GET is the method ("please give me"); / is the path, the page asked for (/ means the front page); HTTP/1.1 is the version of the language.
    • 
      
  • Headers add details: which address the diner typed (Host), which browser it is, what it can read.
    • 
      
  • Every line ends with two invisible characters: \r\n, "carriage return, line feed" (Chapter 12's backslash codes), called CRLF. A completely empty line means "that's the whole order". Catchphrase: a blank line ends the order. Remember it; it's the bug in the exercise after panel 10.

PART 3 · HIRE A BRIGADEa thread pool: a fixed crew of workers, a channel as the ticket rail, jobs as boxed closures; build it the way the Rust book does, letting the Compiler tell us what's missing (E0433, E0382, E0277); watch the Arc counter; then race 1, 2 and 4 workers


  

    17
    
Real kitchens solve this with a brigade: a fixed crew of cooks, and a ticket rail where orders wait. The head chef at the pass clips each new order onto the rail; whichever cook is free takes the next ticket. In code, that's called a thread pool.

    

    
    
      
  • ThreadPool: the whole brigade. ThreadPool::new(4) hires four cooks once, at opening time. pool.execute(job) clips a ticket onto the rail.
    • 
      
  • A worker: one cook, a thread that loops forever: take a ticket, cook it, take the next. With 4 workers, at most 4 orders cook at once; the rest wait on the rail. A flood of diners makes the rail longer, not the kitchen bigger.
    • 
      
  • The rail is a channel (Chapter 26): one Sender for the head chef, one Receiver that the cooks must share. The clip is a Mutex, so only one cook pulls a ticket at a time, and every cook holds an Arc key to the same rail. That's the type you're about to build: Arc<Mutex<mpsc::Receiver<Job>>>.
    • 
    

  


  

    18
    
    
The Rust book's trick: first write the code you wish worked, then let the Compiler tell you what's missing, one error at a time. The wish:

    e_no_pool.rs
    

    

    
    
      
  1. error[E0433]: cannot find type `ThreadPool` in this scope, with use of undeclared type `ThreadPool` under it. Of course: it doesn't exist yet. That's the to-do list: a struct called ThreadPool, a function new, and a method execute that takes a closure, just like thread::spawn does.
    2. 
    

    

      
      
The Compiler says: Some people call this compiler-driven development. Fine by me. I'll keep saying what's missing until nothing is.

    

  


  

    19
    
What goes on a ticket? A piece of code to run later: a closure. Different orders are different closures, with different types, but one rail can carry only one type. So every ticket is the same kind of box:

    
type Job = Box<dyn FnOnce() + Send + 'static>;

    

      
Box<dyn …>
A box on the heap holding "something that can do this", whatever its real type is: Chapter 23's universal remote. All boxes are the same size, so one rail fits them all.

      
FnOnce()
The trait for a closure that can be called once, takes nothing and returns nothing (Chapter 20). A ticket is cooked once, and the closure may use up what it owns, like the stream.

      
Send + 'static
Send: allowed to travel to another thread (Chapter 26's badge). 'static: borrows nothing short-lived, so it may wait on the rail as long as it likes (Chapter 19).

    

    
The line starts with type Job =, a type alias: a short nickname for a long type, so the rest of the code can just say Job.

    2. 
      
  2. Line 23's label says why it moved instead of being copied: a Receiver doesn't implement Copy. And you can't clone it either: an mpsc channel is "multiple producer, single consumer" (Chapter 26).
    3. 
      
  3. The note: suggests borrowing instead. That can't work here: each worker's thread may outlive this function (Chapter 26: "a cook might outlive you, so give, don't lend"). We need several owners of one receiver.

    21
    
    
Several owners? That's what Arc is for. Mabel wraps the receiver in an Arc and gives each worker a clone.

    e_arc_only.rs
    

    

    
    
      
  1. error[E0277]: `std::sync::mpsc::Receiver<Box<(dyn FnOnce() + Send + 'static)>>` cannot be shared between threads safely. Long, but it's just our Receiver<Job> with the alias spelled out.
    2. 
      
  2. The two notes are the chain of reasoning: the trait `Sync` is not implemented for the receiver, so Arc<…> can't implement `Send`, and spawn requires Send. An Arc lets several threads look at one value at the same time; two cooks pulling a ticket off the same rail at the same instant would be a data race.
    3. 
    

    

      
      
Mabel says: Chapter 26 again: Arc to share, Mutex to change. Taking a ticket changes the rail, so the rail needs a clip: Arc<Mutex<Receiver<Job>>>.

    Under the hood: sockets, the door's queue, and why the guard lingers
    
    
      
    
        
        
    The Professor says: TcpListener and TcpStream are thin wrappers around the operating system's sockets. Rust adds ownership: a socket closes exactly when its owner drops it.
    
      
    
      
    What bind, incoming and connect really do
    
      
    TcpListener::bind asks the operating system for a listening socket on an address and port. From then on, the system itself accepts connections and parks them in a short queue, the backlog, even while your program is busy. That's why diner 2 in panel 14 wasn't refused: it waited in the backlog. Each turn of incoming() calls accept, which takes the next connection from that queue (or waits for one) and wraps it in a TcpStream. On Unix-like systems, Rust's standard library also sets the SO_REUSEADDR option, so a restarted server can bind the same port right away instead of waiting a minute or two for old connections to clear; a second listener while the first is still open still gets AddrInUse.
    
      
    TCP in one paragraph
    
      
    TCP turns the internet's unreliable little packets into a reliable, ordered stream of bytes: it numbers the pieces, re-sends lost ones and puts them back in order. It knows nothing about lines or messages, which is why HTTP needs its blank line and Content-Length to say where things end. 127.0.0.1 never leaves your computer: the system loops the bytes straight back.
    
      
    HTTP/1.1, keep-alive and what we skipped
    
      
    HTTP/1.1 lets a browser send several requests over one connection ("keep-alive"). Our server answers one request and hangs up, which is allowed: the client simply opens a new connection next time. Real servers also handle request bodies (a POST carries data after the blank line, sized by its own Content-Length), headers that arrive in pieces, very long or malicious requests, timeouts, and HTTP/2 and HTTP/3. That's a lot of careful code, which is why real programs use a library like hyper.
    
      
    Why while let keeps the lock
    
      
    Rust drops a temporary value at the end of the enclosing statement. In let message = receiver.lock().unwrap().recv();, the statement ends at the semicolon, so the MutexGuard is dropped before the next line. In while let Ok(job) = receiver.lock().unwrap().recv() { … }, the condition belongs to the whole while let expression, so its temporaries live until the end of each pass through the loop body. The 2024 edition shortened this for if let (its temporaries are now dropped before the else) but not for while let, and this chapter's captures, made with edition 2024, show the lock really is still held.
    
      
    Why the Receiver isn't Sync
    
      
    Sender is Send (and since Rust 1.72 also Sync), so many threads can send. Receiver is Send but not Sync: only one thread at a time may receive, which is the "single consumer" in mpsc. The Mutex makes the "one at a time" explicit. Crates like crossbeam-channel offer channels with many receivers if you'd rather skip the lock.
    
      
    Threads vs tasks
    
      
    A spawned thread reserves its own stack (2 MiB by default for Rust threads on most platforms) and is scheduled by the operating system. A Tokio task is a state machine (Chapter 27) that is only as big as the variables it keeps across .awaits, scheduled by Tokio onto a few worker threads. That's why tasks scale to many thousands of mostly-idle connections.
    
    
    
  
    

  
    
    In real programs: where this chapter's ideas live
    
    
      
      
        
    • hyper is the HTTP library underneath much of the Rust web world; Axum (from the Tokio project) and actix-web add routing, so your "menu" becomes functions attached to paths, and shared state is often an Arc<AppState>, just like Boss 6.
      • 
        
    • Thread pools are everywhere: rayon keeps one sized to your cores for data-parallel work, and Tokio keeps a separate blocking pool (spawn_blocking) for slow work that would otherwise freeze the waiter.
      • 
        
    • Graceful shutdown in production waits for a signal, such as Ctrl+C (tokio::signal::ctrl_c) or a stop request from the system, then stops accepting, lets in-flight requests finish, and exits: the same closing ritual as panel 28.
      • 
        
    • Backpressure: a bounded rail (sync_channel(n), Chapter 26) makes the head chef wait when too many tickets pile up, instead of letting memory grow without limit. Real servers also cap how many connections they hold at once.
      • 
        
    • Bad input: production servers never unwrap() on what a client sends. A malformed request gets a 400 Bad Request, and the server keeps running.
      • 
        
    • Testing a server the way this chapter's test diners do (start it, connect, check the reply) is called an integration test (Chapter 24). Crates like reqwest act as the diner.
      • 
      
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "incoming() ends when nobody is left." It never ends on its own; only take, a break or stopping the program ends the loop (Exercise "take").
      • 
        
    • "Reading the request means reading until the end." The client keeps the connection open waiting for the plate. Read up to the blank line (and then any body the headers announce).
      • 
        
    • "Content-Length counts characters." It counts bytes. "café" is 5 bytes in UTF-8 (Chapter 12).
      • 
        
    • "More workers is always faster." Only while there's waiting to overlap or cores to use. A pool far larger than the work just costs memory.
      • 
        
    • "The pool runs jobs in the order they were sent, so their output comes out in that order." Jobs start in rail order, but they finish whenever they finish, on whichever worker (panel 25).
      • 
        
    • "The Mutex makes the workers take turns cooking." Only taking a ticket is one at a time. Cooking happens outside the lock, unless you hold the guard too long (panel 26).
      • 
        
    • "Dropping the pool stops the workers." Nothing stops a thread from outside. Dropping the sender asks them to stop; join waits until they have.
      • 
        
    • "Async is always better than threads." Async shines for waiting; for heavy computing, a thread pool is simpler and just as fast.

    web server / client
    A program that waits for requests and answers them / the program that asks (a browser, curl, our test diner).
    
        
    IP address, 127.0.0.1, localhost
    The number that names a computer on a network; 127.0.0.1 (nickname localhost) always means "this computer".
    
        
    port
    A numbered door on one computer (1 to 65535), so many servers can share it. Below 1024 usually needs administrator rights.
    
        
    TCP / connection
    The protocol that delivers a reliable, ordered stream of bytes between two programs / one such open line.
    
        
    TcpListener / TcpStream
    A listening socket bound to a port / one open connection you can read from and write to.
    
        
    socket
    The operating system's handle for one end of network communication.
    
        
    backlog
    The operating system's short queue of accepted connections waiting for the program to call for them.
    
        
    HTTP
    The text language of web requests and responses.
    
        
    request / request line / method / path
    What the client sends / its first line, like GET / HTTP/1.1 / the verb (GET, POST) / which page (/, /sleep).
    
        
    header
    A Name: value line after the first line, adding details.
    
        
    CRLF
    \r\n, the two characters that end every HTTP line; an empty line ends the headers.
    
        
    response / status line / status code
    What the server sends back / its first line / the three-digit verdict: 200 OK, 404 NOT FOUND, 400 Bad Request.
    
        
    body / HTML
    The content after the blank line / the language web pages are written in.
    
        
    Content-Length
    The header that says how many bytes of body follow.
    
        
    router
    The code that picks an answer from the request (here, a match).
    
        
    thread pool / worker
    A fixed set of threads that take jobs from a shared queue / one of those threads.
    
        
    job
    One unit of work on the queue; here Box<dyn FnOnce() + Send + 'static>.
    
        
    type alias
    type Job = …;: a short name for a longer type.
    
        
    compiler-driven development
    Writing the code you wish worked, then fixing what the Compiler says is missing, one error at a time.
    
        
    temporary
    A value made in the middle of an expression without a name, like the guard from lock(); dropped at the end of its statement.
    
        
    graceful shutdown
    Stopping so that work in progress finishes: stop taking orders, let the workers finish, wait for them.
    
        
    Option::take / Vec::drain
    Move the value out and leave None / remove elements and hand each one over by value.
    
        
    assert!
    A macro that panics if its condition is false.
    
        
    curl
    A command-line HTTP client.
    
        
    task (Tokio)
    A lightweight unit of async work; many tasks share a few threads.
    
        
    E0433 / E0599 / E0596
    Cannot find a type (or path) / no such method in scope (often a trait not imported) / cannot borrow as mutable.
    
        
    E0382 / E0277 / E0507
    Use of a moved value ("in previous iteration of loop") / a missing trait, here Send or Sync / cannot move out of something behind a reference.

    Every line of code and every output in this comic comes from a real run: Rust 1.99.1 with edition 2024 (shown) and Rust 1.97.0 (comparison), on 2026-11-08, in /home/you/rust-ch29. Each of the 49 programs was built as its own cargo project and run with cargo run -q on 64-bit Linux, inside a fresh process namespace, which is why the main thread's id is (1). Compile errors are shown exactly as cargo printed them, with their real exit code, 101; panics in main also exit with 101.
    
  
    The servers really listen on 127.0.0.1:7878, and the test diners are real TCP clients running on their own threads in the same program; a server serves a fixed number of visitors (take) so that it ends. Wait times are measured with Instant but printed only rounded to whole seconds, or as a yes/no against a 400 ms threshold, with margins of hundreds of milliseconds, so each run prints the same thing; every program was run twice to check. pool_logs.rs prints worker numbers chosen by the scheduler: it is marked nondeterministic, labelled "one possible run", and never used as an answer key. forget_sender.rs would hang forever; its watchdog thread ends it after 2 seconds with exit code 1. Panel 33 is one real shell session (grand_opening.cmd: the steps run in one bash process, so cd, the background job and kill %1 carry over). Its first step also refreshes the project folder from grand_opening.rs with a small helper script before the cd; curl's \r\n line endings are shown as plain line breaks, as a terminal displays them.
    
  
    Version differences: e_write_scope.rs and e_arc_only.rs differ only in the line that points into the standard library's source (1.99.1 locates Write in library/core/src/io/write.rs, 1.97.0 in library/std/src/io/mod.rs), and e0507.rs also names std::thread::JoinHandle::<T>::join on 1.99.1 where 1.97.0 says JoinHandle::<T>::join. pool_logs.rs is listed too, only because its scheduler-dependent worker lines came out in a different mix; it is never treated as a second run on this page. Every other program printed the same on both versions. The Tokio program uses tokio 1.54.1, pinned exactly.
    
  
    The rush-hour lanes are an extension (assets/ext/rs-ch29.js): it plays the queue (first come, first served; a free worker takes the next ticket) and checks every quick diner's "waited behind a stew?" verdict, and every diner's order, against the matching block of the real rush.rs run; which worker takes which ticket is drawn as one possible assignment. The pool tracer, the router machine and the map of one visit are teaching models that check themselves against the runs and show a badge; the tracer follows worker 1 taking the ticket, one possible order that gives the same screen. The restaurant, order card, plate, brigade and closing-time drawings are pictures, not output. The whole-journey cards were built from the recap panels of chapters 1 to 28 of this book (checked against them on 2026-11-08), written in sentence case.

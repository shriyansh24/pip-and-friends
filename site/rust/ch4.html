RUST · CHAPTER 4

MACHINES AND SWITCHES

Picture: Mabel the librarian waves. Beside her stand a machine with a slot on top and a chute at the bottom, labelled fn, and a signpost pointing two ways, labelled true and false.

Build your own machines (functions): inputs in, one value out. Learn why one tiny semicolon can swallow a result. Then add switches (if and else) so a program can choose. About 80 minutes, with 26 hands-on checks.

  1. Your first machines: fn, calls and parameters
  2. What comes out: return values, expressions and the semicolon shutter
  3. Inside the machine: frames, scope, todo! and assert_eq!
  4. Switches: if, else, bool conditions and logic
  5. Ladders and values: else if, early return, if as a value
  6. Boss level and recap

    PART 2 · WHAT COMES OUTReturn values, expressions and the semicolon shutter
    

  
    
    11
    
    A machine with a chute. -> i32 promises an i32 drops out.
    
    
    
      
    returns.rs
    
      
    
    
    
    
      
      
    1. days * 25 (line 8)
      The last line of the body has no semicolon. Its value is the return value. Rust calls a last line like this the tail expression.
      2. 
      
    2. let fee = late_fee(3); (line 2)
      The call becomes its value: 75 comes out of the chute and is stored in fee.
      3. 
      
    3. println!("…", late_fee(10)) (line 4)
      You can use a call anywhere a value fits, even straight inside println!.
      4. 
    
    
    
    
      
      
    Mabel says: Printing shows a value to people. Returning hands a value to the program, so it can keep working with it.
    
    
    
  
    

  
    
    12
    
    The big idea behind that missing semicolon: Rust code is made of two kinds of pieces.
    
    
    
      
    
        
    STATEMENTSdo something
    
        
    An instruction. It does a job and produces no value. It usually ends with ; (a whole fn definition doesn't need one).
    
        
    • let fee = 75;
    • println!("Hi");
    • fn greet() { … }
    
      
    
      
    
        
    EXPRESSIONSproduce a value
    
        
    Anything that works out to a value. You can store it, print it, or pass it on.
    
        
    • 5 + 6 is 11
    • late_fee(2) is 50
    • a block { … } is the value of its last line
    
      
    
    
    
    
    
      
    expressions.rs
    
      
    Three expressions, three values: a sum, a call, and a block (lines 4–7).
    
    
    
    
    
      
      
    The Professor says: Put a semicolon after an expression and it becomes a statement: the value is thrown away.
    
    
    
  
    

  
    
    13
    
    A pair of curly braces makes a block. A block is an expression: its value is its last line, with no semicolon.
    
    
    
      
    blocks.rs
    
      
    
    
    
    
      
      
    1. Lines 3 and 4 are statements inside the block: they make two names.
      2. 
      
    2. Line 5, fiction + poetry, has no semicolon: it's the block's value, 17.
      3. 
      
    3. The ; on line 6 ends the whole let total = { … }; statement.
      4. 
    
    
    
    A function body is a block too. That's why the last line of late_fee becomes the return value.
    
  
    

  
    
    14
    
    What drops out of a machine with no ->? An empty wrapper.
    
    
    
      
    unit_fn.rs
    
      
    
    
    
    
    
      
      
    Mabel says: () is pronounced "unit". It's Rust's empty wrapper: a value that holds nothing. A function with no -> hands back (). So does a block whose last line ends in ;.
    
    
    
    
    Line 3 uses {result:?}, the X-ray goggles from Chapter 3, because () has no polite {} form. You'll rarely store a () on purpose; this is just to see it.
    
  
    

  
    
  

  
    
    15
    
    
    The classic Rust mistake: one extra semicolon on the last line.
    
    
    
      
    
        
    NO SEMICOLONdays * 25
    
        
        
    The last line is an expression. Its value drops out: an i32, just as -> i32 promised.
    
      
    
      
    
        
    SHUTTER DOWNdays * 25;
    
        
        
    The semicolon turns the last line into a statement and shuts the chute. The 75 is swallowed, and only the empty wrapper () comes out.
    
      
    
    
    
    semicolon_shut.rs
    
    
    
    
      
      
    The Compiler shouts: THE LABEL SAYS i32. OUT CAME AN EMPTY WRAPPER!
    
    
    
    
    Picture: the Compiler, beacon red, gate down. A burst says CLUNK.
    
  
    

  
    
    16
    
    The real message. This one has three labels; read them in this order.
    
    
    
    
      
      
    1. error[E0308]: mismatched types
      What: a type didn't match. You'll meet E0308 again and again; it comes back in Part 4.
      2. 
      
    2. ^^^ expected `i32`, found `()`
      The primary label (the ^^^) sits under the return type on line 6: you promised an i32, but the body gives ().
      3. 
      
    3. -------- implicitly returns `()` …
      A secondary label (the dashes) under the name explains why: the body has no tail expression.
      4. 
      
    4. - help: remove this semicolon to return this value
      The help, on line 7, points at the exact character to delete. Case closed.
      5. 
    
    
    
    
      
      
    Mabel says: Notice the error points at line 6, but the fix is on line 7. When there's a help:, follow it.
    
    
    
    
  
    

  
    
    17
    
    Feed the late_fee() machine. Every result comes from a real run of machine_fee.rs, and the jam from semicolon_shut.rs.

    explicit_return.rs
    
      
    
    
    
    
      
      
    1. days * 25 (line 7): the tail expression. This is the usual Rust style for the last line.
      2.

    PART 3 · INSIDE THE MACHINEFrames, scope, placeholders and quick checks
    

  
    
    19
    
    Each call gets its own little desk to work at. Rust calls it a frame.
    
    
    
      
      
    • A call opens a new desk on top of the pile. The parameter d gets its own copy of the argument, 3.
      • 
      
    • Names made inside the function live on its desk. per_day exists only there.
      • 
      
    • When the call returns, the desk is cleared away. Only the returned value travels back down to the caller.
      • 
    
    
    
    A pile like this is called the call stack. Chapter 7 looks at it closely; for now, just watch desks come and go.

    28
    
      Conditions are usually comparisons. Each one asks a yes-or-no question and gives back a bool.
      
    
      
      The six comparison operators
      
      WriteAsksWatch out
      
      
        
      a == bis a equal to b?Two equals signs. One = means "store", not "compare".
      
        
      a != bis a different from b?Say it "not equal".
      
        
      a < bis a less than b?The open side faces the bigger number.
      
        
      a > bis a greater than b?
      
        
      a <= bless than or equal?Write <=, never =<.
      
        
      a >= bgreater than or equal?Write >=, never =>.
      
            
    
      
    
      
      
      compare.rs
      
      
      
    
      
    
      
      
      
      The lamp says: Remember me from Chapter 3? I'm a bool: on for true, off for false. Every comparison switches me one way or the other.

    31
    
      Join questions together with three logical operators. Think of switches in a light circuit.
      
    
      
      
      
        
      ANDa && b
      
        
        
      True only if both are true. Two switches in a row: both must be closed.
      
      
      
      
      
        
      ORa || b
      
        
        
      True if at least one is true. Two switches side by side: either one will do.
      
      
      
      
      
        
      NOT!a
      
        
        
      Flips one answer: !true is false and !false is true.

    32
    
      A time-saver called short-circuiting: if the left side already decides the answer, the right side is never even asked.
      
    
      
      
      short_circuit.rs
      
      
      
    
      
    
        
      
      1. asks(false) && asks(true)
        The left side is false, so the AND is false no matter what. The right call never happens: only one "asked" line.
        2. 
      
      2. asks(true) || asks(false)
        The left side is true, so the OR is true no matter what. Again, the right call is skipped.
        3.

      What you learned in Chapter 4
      
    
        
      
      • BUILD IT ONCE, USE IT ANYWHEREA function is a named machine: fn name(param: Type) -> ReturnType { … }. Every parameter needs a type. Calls jump in and come back to the line after the call. Names are snake_case.
        • 
      
      • THE LAST LINE DROPS OUTA block is an expression whose value is its last line without a semicolon (the tail expression). That's how functions return. return leaves early.
        • 
      
      • A SEMICOLON SHUTS THE CHUTEPut ; on the last line and the value is swallowed: out comes the empty wrapper (), and E0308 says expected `i32`, found `()`. Follow the help:.
        • 
      
      • WHAT HAPPENS IN THE BLOCK STAYS IN THE BLOCKEach call gets its own frame; names made inside a block or function vanish at its closing brace (E0425). todo!() marks unfinished work, and assert_eq! checks a result.
        • 
      
      • THE SIGNAL MUST BE A BOOLif needs true or false: no truthiness, and == compares while = stores. &&, || and ! combine answers, and the right side is skipped when the left decides.
        • 
      
      • SAME CARGO ON BOTH TRACKSLadders are checked top to bottom, so ask the strictest question first. An if used as a value needs an else, and every arm must give the same type.

    Under the hood: frames, copies, and why types are required
    
      
      
      Where the values really live
      
      
      The tracer in panel 20 draws each value in a box beside its frame, with an arrow, so you can read it easily. In a real Rust program, an i32 sits inside the frame itself: the frame is a small block of memory on the stack, with room for every local name. A call pushes a new frame on top; returning pops it off. That's why it is so fast, and why a function's locals disappear when it returns. Chapter 7 draws the stack properly, next to its partner, the heap.
      
      
      Arguments are copied in
      
      
      When late_fee(days) runs, the parameter d gets a copy of the number in days. Changing d inside the function could never change days in main. Numbers, bools and chars are always copied like this. Bigger values, like text you build at run time, follow Mabel's ownership rules instead (Chapter 7), and lending a value without copying it uses references (Chapter 8).
      
      
      Why every parameter needs a type
      
      
      Inside a function, Rust works out most types for you: let a = 5 + 6; needs no label. But a signature is a promise between the machine and everyone who uses it. Writing the types there means the Compiler can check each function on its own, a mistake inside one machine can't silently change how the rest of the program is understood, and error messages can point at the exact call that broke the promise (as in panel 10 and the spot_argtype.rs exercise).
      
      
      A let is a statement, so it has no value
      
      
      In some languages x = y = 6 sets both names. In Rust a let produces no value at all, so you can't use it where a value is expected:
      
      
      
      
      The note mentions if and while conditions: a special form called if let, which Chapter 11 teaches alongside match. The warning below the error is a separate, smaller point: the brackets themselves are unnecessary. Its suggested line, let x = let y = 6;, still has the error, so fix the error first.
      
      
      Why todo!() fits any return type
      
      
      todo!() never finishes normally: it always panics. A value that can never actually appear can stand in for any type, so the Compiler accepts it as an i32, a bool, or anything else. panic! works the same way. (Its type has a name, "never", written !; you won't need it for a long time.)
      
    
      
  
      

  
      
    In real programs: small machines, guard clauses, checks
    
      
      
        
        
      • Small functions with honest names. A good function does one job, and its name says what: late_fee, is_teen, max_of. Names that answer yes or no often start with is_ or has_ and return bool.
        • 
        
      • Tail expressions are the house style. Rust code almost never ends a function with return x;. The advice tool cargo clippy even has a lint called needless_return that suggests removing it. Early return for special cases is normal.
        • 
        
      • Guard clauses keep code flat. Handling the odd cases first and leaving early (panel 36) avoids deep piles of nested ifs. Reviewers like it because the normal path reads straight down.
        • 
        
      • if as a value replaces the "ternary". Many languages have a special cond ? a : b operator. Rust doesn't need one: if cond { a } else { b } already is an expression.
        • 
        
      • Checks everywhere. assert_eq!, assert_ne! (not equal) and assert! (any bool) are the building blocks of Rust's tests. Real projects keep them in test functions that cargo test runs (Chapter 14). assert! lines in normal code also document "this must be true here".
        • 
        
      • todo!() versus unimplemented!(). Both panic. todo! says "I will write this"; unimplemented! says "this isn't supported". Teams often search for leftover todo!s before a release.
        • 
        
      • Long ladders. When an else if ladder compares one value with many fixed values, Rust programmers usually switch to match (Chapter 11), which the Compiler can check for missing cases.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "Every line needs a semicolon." Statements do. The last line of a block that should produce a value must not have one. Chapter 1's notebook promised this chapter would explain when it matters: it matters whenever the block's value is used.
        • 
        
      • "A function must be written above the code that calls it." Not in Rust. The Compiler reads the whole file first (panel 6 called greet, written below main).
        • 
        
      • "println! inside a function returns the value." Printing shows text to a person. Only the tail expression or return hands a value back to the program.
        • 
        
      • "Changing a parameter changes the caller's variable." The parameter holds a copy. (You'd have to mark it mut even to change the copy.)
        • 
        
      • "if 1 means true." No truthiness in Rust: conditions must be bool.
        • 
        
      • "=< and => work too." Only <= and >= compare. => is a different symbol, used in match.
        • 
        
      • "Every if needs an else." Only an if whose value you use. An if that just does something (panel 29's fix) is fine alone.
        • 
        
      • "The error line is always where the fix goes." The semicolon error points at the return type on the signature line; the fix is the ; further down. Read the help:.
        • 
        
      • "Both sides of && always run." The right side is skipped when the left side already decides (panel 32). That matters when the right side prints something or does real work.
        •

    Words from this chapter
    
      
      
      
        
      function
      A named, reusable list of instructions, written with fn. A machine.
      
        
      define / call
      Defining builds the function (fn name() { … }). Calling runs it (name()).
      
        
      DRY
      "Don't repeat yourself": put repeated code in one place, such as a function.
      
        
      parameter
      A named slot in a function's definition, with a type: days: i32.
      
        
      argument
      The actual value passed in a call: the 3 in late_fee(3).
      
        
      signature
      A function's first line: its name, parameters and return type.
      
        
      return value
      The value a function hands back to its caller.
      
        
      return type
      The type after ->: what kind of value comes back.
      
        
      snake_case
      Lowercase words joined by underscores, the Rust style for function and variable names.
      
        
      warning
      A Compiler note about code that works but looks wrong or unusual. The program is still built.
      
        
      statement
      An instruction that does something and produces no value. Usually ends with ;.
      
        
      expression
      Code that works out to a value: 5 + 6, a call, a block, an if … else.
      
        
      block
      Code between { and }. Its value is its last line without a semicolon.
      
        
      tail expression
      The last line of a block, with no semicolon, whose value becomes the block's value.
      
        
      unit, ()
      The empty value: what a function with no return type, or a block ending in ;, hands back.
      
        
      return
      A keyword that leaves the function at once with a value.
      
        
      frame
      The private workspace a call gets for its parameters and local names. Cleared when the call returns.
      
        
      call stack
      The pile of frames: one for each call that hasn't finished yet.
      
        
      scope
      The part of the code where a name can be used: from its let to the end of its block.
      
        
      binding
      A name made with let (or a parameter).
      
        
      todo!()
      A placeholder macro: it compiles anywhere and panics with not yet implemented if reached.
      
        
      assert_eq!
      A macro that panics unless its two values are equal, showing both.
      
        
      logic bug
      A mistake that compiles and runs but gives the wrong answer.
      
        
      condition
      The bool question an if asks.
      
        
      if / else if / else
      Keywords that choose which block runs, checked top to bottom.
      
        
      comparison operator
      == != < > <= >=: each gives a bool.
      
        
      truthiness
      Treating non-bool values as true or false. Rust doesn't have it.
      
        
      assignment
      Storing a value with a single =. Not a comparison.
      
        
      logical operator
      && (and), || (or), ! (not).
      
        
      short-circuiting
      Skipping the right side of && or || when the left side already decides.
      
        
      guard clause
      An early check with a quick return for a special case.
      
        
      arm
      One of the blocks an if can choose.
      
        
      primary / secondary label
      In a compiler error: ^^^ marks the main problem; --- marks related places.
      
        
      E0061, E0308, E0317, E0425
      Wrong number of arguments; mismatched types; if may be missing an else; name not found in this scope.

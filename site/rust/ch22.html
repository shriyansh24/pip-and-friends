PART 1 · THE DRAWER CHARTVec and HashMap are the everyday drawers; the standard library has five more, each built for one kind of job

1

Mabel keeps everything in accordion folders, the Vec from Chapter 11: the line of readers at the desk, the catalogue, and the pile of books waiting for repair.

Mabel says: Serving the first reader means shuffling everyone else forward. The catalogue has to be sorted again every time I print it. And to find the most urgent repair I check the whole pile, every single time.

The Professor says: A folder can do all of that, slowly. Rust's standard library has a whole chest of drawers in std::collections, and each drawer is shaped for one job. Today we learn to pick the drawer for the job.

Picture: Mabel shrugs beside a heap of folders. The Professor answers from the right.

2

The drawer chart. A collection is a value that holds many values. You've met the first two; the other five are new today. Every drawer except Vec needs a use std::collections::…; line.

Vec<T>the accordion folder (Ch 11)

Items in order, by position. Fast at the end. The default choice.

VecDeque<T>the queue tube

A line you can add to and take from at both ends, fast. A queue.

HashMap<K, V>the locker room (Ch 13)

Find a value by its key, fast. No order at all.

BTreeMap<K, V>the sorted filing cabinet

Like a map, but keys always sorted. Same order every run. Ranges.

HashSet / BTreeSetthe guest book

Keys with no values: each item once. "Have I seen this?"

BinaryHeap<T>the priority line

Always hands you the biggest (most urgent) item next.

[T] slice toolsthe toolkit on every Vec

Sort, search, keep, de-duplicate, slide a window, cut in two.

Mabel says: So the question is never "which collection is best?" It's "what will I do most often: add at the end, serve from the front, look up by key, keep sorted, or grab the biggest?" Catchphrase: pick the drawer for the job.

The chart, as text: Vec, the accordion folder, items in order, fast at the end. VecDeque, a tube open at both ends, a queue. HashMap, lockers found by key, no order. BTreeMap, a sorted filing cabinet, keys always in order. HashSet and BTreeSet, a guest book, each item once. BinaryHeap, a priority line, biggest first. Slice tools, a toolkit that works on every Vec and array.

How can both ends be fast? Inside, a VecDeque is a row of slots used as a ring: when it runs off the right end, it carries on at slot 0. It remembers where the front is (the head). as_slices() lets you see the ring: it hands back the part from the head to the end, and then the part that wrapped round to the start.

    heap_float.rs
    
    
    
    
    
      
      
    1. error[E0277]: the trait bound `{float}: Ord` is not satisfied
      What: the item type is missing a skill. {float} means "some decimal number type, not decided yet", and Ord is the trait for a total order: any two values can always be compared (Chapter 18).
      2.

      3.

    Under the hood: sizes, B-trees, the heap's trick, sorting algorithms and UTF-8
    
      
      
      
        
        
      The Professor says: Let's take the drawers apart.
      
      
      
      
      How big is each drawer itself?
      
      sizes.rs
      
      
      These are the sizes of the handles that live on the stack (Chapter 7) on this 64-bit machine; the items themselves live on the heap. A Vec is pointer, capacity and length: 24 bytes. A VecDeque adds the head index: 32. A BinaryHeap is literally a Vec inside, so it's 24 too, and BTreeMap is a pointer to its root node, a height and a length. HashMap carries its 16-byte random seed (Chapter 13's notebook), hence 48. A &str is a pointer and a length: 16. A char is always 4 bytes, enough for any Unicode scalar value; that's why a Vec<char> takes up to four times the room of the String it came from.
      
      
      Why a B-tree, not a binary tree?
      
      
      Rust's BTreeMap is a B-tree: each node holds up to 11 keys in a sorted little array, with children between them. Searching walks down a few levels and does a short scan in each node. Packing many keys per node means fewer jumps around memory, which modern processors reward far more than they reward saving a comparison. Lookups, inserts and removals all cost about log n steps, versus about 1 for a HashMap, so a HashMap is usually faster when you don't need order. The standard library's collections page has a table of these costs.
      
      
      The heap's trick
      
      
      The tree in panel 16 is never stored as a tree. Slot i's children are always slots 2i + 1 and 2i + 2, and its parent is (i − 1) / 2, so a plain Vec is enough, with no pointers at all. That's why BinaryHeap::from(vec) and into_vec() are cheap. A small detail: when Rust's pop sinks the new top, it actually runs the hole straight down to the bottom along the bigger children and then lets the item climb back up, a trick that saves comparisons on average. For the numbers in panel 16 the result is exactly what the stepper shows, and the stepper checks itself against the real arrays.
      
      
      Two sorting algorithms
      
      
      sort is stable and may borrow some extra memory while it merges runs of already-sorted items; sort_unstable sorts in place. Both take about n log n steps in the worst case, and both are very fast on input that is already nearly sorted. The documentation names the current algorithms but promises only the behaviour (stable or not, the cost limits), so they can be improved in any release without your program changing. sort_by_cached_key is a third cousin: it works out each key once, which helps when the key is expensive (say, to_lowercase()).
      
      
      UTF-8, bit by bit
      
      utf8_bytes.rs
      
      
      The first byte of each char says how many bytes follow: 0… one byte (plain ASCII), 110… two, 1110… three, 11110… four. Every following byte starts with 10. That's how chars() finds where each char starts, and why a byte starting 10 can never begin a valid char: in panel 36, the reversed é started with 169 = 10101001. Notice {b:08b} in line 5: binary, zero-padded to 8 digits, straight from Part 6. U+{:04X} prints the code number in capital hex, at least 4 digits.
      
      
      Floats in sorted drawers
      
      
      Floats have PartialOrd (most pairs compare) but not Ord. To sort a Vec<f64>, use v.sort_by(|a, b| a.total_cmp(b)): total_cmp gives every float, NaN included, a fixed place in line. For a heap or BTreeMap of floats, wrap them in a small struct whose Ord uses total_cmp, or store whole numbers of tenths or pennies.
      
    
      
  
      

  
      
    In real programs: where you'll see these drawers and this formatting
    
      
      
        
        
      • VecDeque: work queues, a breadth-first search through a maze or a web of links (visit the nearest places first), and "the last 100 log lines" buffers (push_back plus pop_front when it's full).
        • 
        
      • BTreeMap: anything printed or saved where the order must be stable: configuration files, reports, test snapshots; and range questions such as "all loans due between the 1st and the 7th".
        • 
        
      • BinaryHeap: schedulers, "next event" timers in games and simulations, the shortest-route algorithm in maps (Dijkstra's), and keeping the top k items of a long stream, below.
        • 
        
      • Formatting: command-line tools print aligned tables with exactly these specs; {:#?} is every Rust programmer's debugging friend; {:08b} and {:#x} appear wherever bits and bytes matter.
        • 
      
      
      
      The top-3 pattern: keep a min-heap of at most 3 items. Each new item goes in, and if there are now 4, the smallest is thrown out. Whatever stays is the three biggest, and memory never grows past 4 items, however long the list.
      
      top_k.rs
      
      
      More formatting you'll meet: pretty Debug, padding a Debug value by formatting it first, and named and numbered arguments.
      
      fmt_more.rs
      
      
      Line 5: many types' Debug output doesn't reliably honour a width, so format it into a String first and pad that, exactly the advice in the std::fmt documentation. Line 6: é is one char, so it gets the same padding as any letter. Line 8: {{ and }} print literal braces, and 99.25 rounds to 99.2, the even neighbour, as in the ruler.
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "BTreeMap is always better because it's sorted." It's sorted, and usually a bit slower. Pick it when you need the order.
        • 
        
      • "Text keys sort like a dictionary." They sort by code number: capitals before small letters, "10" before "9", and é after z.
        • 
        
      • "A BinaryHeap keeps everything sorted." Only the top is guaranteed. Printing it shows a jumble; use into_sorted_vec for a sorted list.
        • 
        
      • "binary_search will tell me if the Vec isn't sorted." It can't; it just gives a meaningless answer.
        • 
        
      • "dedup removes all duplicates." Only neighbouring ones. Sort first, or use a set.
        • 
        
      • "Vec::with_capacity(3) gives me 3 items." It gives an empty Vec with room for 3.
        • 
        
      • "or_insert(make()) only calls make when needed." Arguments are always worked out first; use or_insert_with(make).
        • 
        
      • "len() is the number of letters." It's bytes. chars().count() is chars, and even that can differ from what a reader sees.
        • 
        
      • "Two strings that look the same are equal." Not if one uses é and the other e plus an accent.
        • 
        
      • "Width cuts long values to fit." Width is a minimum. Precision cuts text.
        • 
        
      • "My Display impl gets padding for free." Only if it ends with f.pad (or passes the formatter on to something that pads).
        • 
        
      • "{:.0} rounds 2.5 up to 3." Exact ties round to even: 2. Most real decimals aren't exact ties anyway.
        • 
        
      • "HashSet operations give the same order every time." They follow the set's jumbled order. Sort, or use BTreeSet.

    Words from this chapter
    
      
      
      
        
      collection
      A value that holds many values: Vec, VecDeque, HashMap, BTreeMap, HashSet, BTreeSet, BinaryHeap.
      
        
      VecDeque<T>, deque
      A double-ended queue: fast push/pop at the front and the back.
      
        
      queue / stack
      First in, first out (serve the oldest) / last in, first out (serve the newest).
      
        
      ring buffer
      A row of slots used in a circle, with a head index marking the front. How VecDeque works inside.
      
        
      make_contiguous
      Lays a VecDeque's items out in one run of slots and hands back a slice.
      
        
      BTreeMap / BTreeSet
      A map / set that keeps its keys sorted. Deterministic order.
      
        
      deterministic
      Gives the same output every time for the same input.
      
        
      range
      Walk only the keys between two bounds, in a BTreeMap or BTreeSet.
      
        
      union / intersection / difference / symmetric difference
      In either set / in both / in the first but not the second / in exactly one.
      
        
      BinaryHeap, priority queue
      A collection that always hands back its biggest item next.
      
        
      heap property
      Every parent is at least as big as its children. (Not the same "heap" as the memory heap of Chapter 7.)
      
        
      Reverse, min-heap
      A wrapper that flips comparisons; a heap of Reverse items serves the smallest first.
      
        
      Ord, total order
      Any two values can be compared. Needed by sorted drawers and heaps; floats don't have it.
      
        
      stable sort
      A sort that keeps equal items in their original order (sort, sort_by, sort_by_key).
      
        
      binary search
      Finding an item in sorted data by halving the range each step. Ok(i) or Err(insert_at).
      
        
      retain / dedup
      Keep only items that pass a test / merge neighbouring repeats.
      
        
      windows(n) / chunks(n)
      Overlapping slices of n neighbours / separate slices of n, the last maybe shorter.
      
        
      split_at_mut
      Cut a slice into two non-overlapping &mut slices.
      
        
      capacity / with_capacity
      Room reserved for items / reserve it up front. Not the same as length.
      
        
      or_insert_with / or_default / and_modify
      Entry-API cousins: build a value lazily / use the default / change an existing value.
      
        
      Index / IndexMut
      The traits behind reading and writing with square brackets.
      
        
      UTF-8
      The code that stores each char in 1 to 4 bytes. What a Rust String uses.
      
        
      Unicode scalar value
      One code number from the Unicode list, like U+00E9. One Rust char.
      
        
      grapheme cluster
      What a reader sees as one character: one or more chars glued together.
      
        
      combining character
      A char, like an accent, that attaches to the char before it.
      
        
      normalisation
      Rewriting text so equal-looking text has equal bytes (é as one char, or as e + accent, consistently).
      
        
      to_digit(base)
      A char's value as a digit in that base, in an Option.
      
        
      splitn, rsplit, split_once, split_terminator
      At most n pieces / from the right / exactly one cut / a final separator ends instead of dividing.
      
        
      FromStr
      The trait parse uses to turn text into your type.
      
        
      format spec
      The part after the colon in {…}: fill, align, sign, #, 0, width, precision, type.
      
        
      fill / align / width / precision
      Padding char / where the value sits (< ^ >) / minimum size in chars / decimals, or maximum chars for text.
      
        
      f.pad
      Writes text into a formatter, honouring the caller's width, fill, alignment and precision.
      
        
      write! / writeln!
      Format into a target such as a formatter or a String (needs use std::fmt::Write).
      
        
      Cow<str>
      "Clone on write": either borrowed text or an owned String, whichever was needed.
      
        
      to_owned
      Make an owned copy of borrowed data: &str → String, &[T] → Vec<T>.
      
        
      E0599 / E0499 / E0277
      No such method here (sort on a VecDeque, write! without the trait) / two mutable borrows at once / a missing trait (Ord for floats, LowerHex for text).

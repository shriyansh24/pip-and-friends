RUST · CHAPTER 28

HANDLES, RACE CARS, HARDWARE

Picture: Mabel the librarian waves. Beside her the Trail Guide, a hiker in a wide hat, points ahead next to a trail sign that says CRAFT. The Compiler robot stands with its gate up and a green beacon.

Your programs work. Now let's make them good. Three trips today. First the toolbox: functions and types with handles that are easy to grip the right way and impossible to grip the wrong way (signatures, builders, newtypes, guards, and the Trail Guide's advice from cargo clippy). Then the race track: why the same program is ten times faster with --release, why it also stops checking for overflow, and how a real program counts every trip to the heap. Last, the hardware store: how to pick crates by reputation and fit, turn a struct into JSON and back with serde, and what happens when two versions of one crate end up in your project. About 150 minutes, with 29 hands-on checks.

  1. A good handle: what a function asks for and hands back
  2. Handles that can't slip: newtypes, builders, Default, guards, privacy
  3. Two race cars: debug and release
  4. Pack light: counting trips to the heap
  5. The hardware store: crates, serde, features and versions
  6. Boss level and recap

PART 1 · A GOOD HANDLEborrow what you read (&str, &[T]), return what you make; impl Into<String>; the clone tax; Option<&T>; iterators; and the Trail Guide's advice from cargo clippy

1

Mabel is choosing a new toolbox for the library's repair cupboard. Two boxes, the same tools inside. One handle has a shaped grip that fits every hand. The other is a thin wire that fits one kind of hand and pinches everyone else.

Mabel says: Code has handles too: the first line of every function, the signature, is the handle other code grabs. This chapter's first motto: easy to grip the right way, impossible to grip the wrong way.

The people who'll call your functions include you, next month. A good handle saves them clones, conversions and surprises. The Compiler checks that your code is correct; this chapter is about code that's also pleasant, fast and well-chosen. Words for it: idiomatic code (written the way experienced Rust programmers write it) and API design (an API, "application programming interface", is the set of functions and types others use).

Reading lamps at the library desks. Mabel's rule: a lamp must never be left on. Instead of remembering to switch each one off, she makes the lamp switch itself off when its owner leaves. A value whose Drop (Chapter 18) undoes what its creation did is called a guard. The pattern is called RAII: "resource acquisition is initialization", a clumsy name for "get it when you make the value, give it back when the value is dropped".

    21
    
    Mabel pins a checklist inside the toolbox lid. Before you call a function or type "done", run down the list.
    
    
      
      
    1. Parameters: borrow what you only read (&str, &[T], &T); take ownership (or impl Into<String>) only when you keep the value.
      2. 
      
    2. Results: return owned values you made; return borrows only when they point into an argument; hand out Option<&T>, not &Option<T>.
      3. 
      
    3. Clones: each .clone() of a String or Vec should be a decision, not a way to silence the Compiler.
      4. 
      
    4. Types that carry meaning: a newtype for units and ids; a builder or Default for many settings; a guard for anything that must be undone.
      5. 
      
    5. Privacy: fields private unless there's a reason; pub is a promise you have to keep.
      6. 
      
    6. Imports: name what you use (use std::fmt::Display;) instead of use some_crate::*;. A wildcard (*) import hides where names come from, and two of them can clash (Chapter 24).
      7. 
      
    7. Docs: a /// comment on everything pub, with a short # Examples section.
      8. 
      
    8. Clippy: cargo clippy prints nothing.
      9. 
    
    
    
    
      
    The Professor says: One more idea for later, called typestate: a type for each stage, such as Draft and Sent, where only Draft has a send method. Sending twice then isn't a bug you test for. It's a program that doesn't compile. Panel 15 was a small taste of it.

    27
    
    The Professor's pit-stop rules for speed.
    
    
      
      
    1. Measure first. Most of a program's time is usually spent in a small part of it, and it's rarely the part you'd guess. Find it before changing anything.
      2. 
      
    2. Use the right stopwatch. Instant is fine for a first look. For careful comparisons, the Criterion crate runs a piece of code many times and reports the average and how much it varies (a benchmark). A profiler, such as cargo flamegraph, draws a picture of where all the time went.
      3. 
      
    3. Write clear code first. Iterators, slices and small functions are zero-cost: in release they compile to the same machine code a hand-written loop would get, so clarity isn't the thing slowing you down.
      4. 
      
    4. Look at what the code asks for. Copies and trips to the heap (Part 4) cost more than a few extra lines of code. Removing them usually beats clever tricks.
      5. 
      
    5. unsafe is not a turbo button. It switches off some of the Compiler's checks; it doesn't make anything faster by itself. Code like get_unchecked(i) skips a bounds check that the optimizer usually removes anyway, and a wrong index then reads whatever memory happens to be there, with no panic to tell you. Reach for it only with a measurement in hand, and then usually don't.
      6.

    Chapter 7's two kinds of memory, with real sizes. The stack is the pile of plates: one per function call, set and cleared in no time. The heap is the coat-check room: room for things whose size can change, but every new spot means asking the attendant, waiting, and getting a ticket back. Each ask is an allocation. size_of tells you how many bytes a value takes on its plate.
    
    stack_heap.rs
    
    
    
    
    
      
      
    1. A String is always 24 bytes on the plate, a pointer, a length and a capacity, however long the text. The letters themselves are in the coat-check room. A &str is only 16 bytes, a pointer and a length, and it never asks for anything new.
      2. 
      
    2. A Box puts its whole value on the heap and keeps only an 8-byte ticket on the plate.
      3. 
      
    3. The stack is fast because it's simple: no asking, no waiting. Each heap allocation is a small errand. Programs that run millions of errands spend real time on them. That's what the rest of this part counts.
      4.

    Under the hood: where the speed comes from, and how the tally counter works
    
      
      
      
        
        
      The Professor says: Most of what you saw today is the compiler doing the boring work, either while compiling (derives, generics, optimizing) or not at all (newtypes cost nothing).
      
      
      
      
      What the optimizer does
      
      
      Rust hands your code to LLVM, the same optimizer used by clang for C and C++. At opt-level = 3 it inlines small functions (pastes their body where they're called, so a closure in an iterator chain disappears), removes bounds checks it can prove are never needed, keeps values in CPU registers instead of memory, and often handles several numbers per instruction (vectorization). At opt-level = 0 it does almost none of this, so the debug build keeps every function call, every check and every temporary. That's the gap in panel 26.
      
      
      Why generics and newtypes are free
      
      
      A generic function such as fn total<T: Sum>(...) is compiled once for every type it's used with (monomorphization, Chapter 17), so each copy is as specific as hand-written code. A newtype like struct Meters(f64) has exactly the size and layout of an f64; the type exists only during compiling. The Rust book's chapter 13.4 times an iterator search against a loop over a whole novel and gets results within the margin of error. It quotes Bjarne Stroustrup's "zero-overhead principle": what you don't use, you don't pay for, and what you do use, you couldn't hand-code any better.
      
      
      How a Vec grows
      
      
      Doubling makes pushing cheap on average: each item gets copied at most about once more over the Vec's life, however long it grows (amortized constant time). The first capacity also depends on the item size: the runs here use 4-byte numbers and got room for 4. None of this is promised by the docs, which is why the page shows real runs. shrink_to_fit() gives spare room back; reserve(n) asks for room for n more ahead of a burst of pushes.
      
      
      The tally counter (panel 31)
      
      
      Every Box, Vec and String gets its memory from one place: the global allocator. By default it's the system's (on Linux, the C library's malloc). #[global_allocator] swaps in your own. alloc_count.rs wraps the system allocator: its alloc adds one to an atomic counter (Chapter 26) and then passes the request on. When a Vec grows, its realloc call isn't overridden here, and the default realloc calls alloc for the new block, so every growth is counted too. Implementing GlobalAlloc requires unsafe, because a wrong allocator could break every value in the program; real projects use ready-made, carefully reviewed allocator crates (for example mimalloc or jemallocator) when they want a different one, and crates like dhat to count allocations.
      
      
      How serde's derive works
      
      
      #[derive(Serialize)] runs a procedural macro from the serde_derive crate while compiling. It reads your struct's fields and writes an impl Serialize for Book that hands each field, by name, to a serializer. serde itself knows nothing about JSON: serde_json is one serializer, and the same derive works with crates for TOML, YAML, CSV, MessagePack and many more. That split, one data model with many formats, is why serde is everywhere. Attributes such as #[serde(rename = "pageCount")], #[serde(default)] and #[serde(skip)] adjust the generated code field by field.
      
      
      The error-feeding program from panel 35
      
      serde_errors.rs
      
      
      
      
    
      
  
      

  
      
    In real programs: where these habits show up
    
      
      
        
        
      • The standard library's own handles: fs::read_to_string takes impl AsRef<Path>, so you can pass a &str, a String or a PathBuf; HashMap::get returns Option<&V>; Vec::with_capacity and String::with_capacity exist for exactly the reasons in Part 4.
        • 
        
      • Builders: std::thread::Builder (name and stack size for a thread), std::process::Command (Command::new("ls").arg("-l").output()), and HTTP clients like reqwest's request builder.
        • 
        
      • Guards: MutexGuard, File, TcpStream (closes the connection), and temporary-directory crates that delete their folder on drop.
        • 
        
      • Newtypes: ids in web services (UserId(u64) and OrderId(u64) can't be swapped), validated text (Email), and units in science and games.
        • 
        
      • serde: configuration files, web APIs, saved games. Almost any Rust program that reads or writes structured data uses it.
        • 
        
      • Release profiles: command-line tools often set lto = true and codegen-units = 1 for their published builds; some services keep overflow-checks = true in release because a panic is safer than a silently wrong number.
        • 
        
      • Supply chain: many companies run cargo deny or cargo audit on every change, and review new dependencies before adding them, just like code.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "&String and &str are the same thing." A &String can turn into a &str, but not the other way round. Ask for &str.
        • 
        
      • "Cloning is how you fix borrow errors." Sometimes it is the right fix, but first ask whether a borrow or a move says what you mean.
        • 
        
      • "Iterators are slower than loops." In release builds they compile to about the same machine code. Panel 26 times one run; the Rust book's chapter 13.4 measures it properly.
        • 
        
      • "My program is slow, so Rust is slow." First check that you built it with --release.
        • 
        
      • "Rust always panics on overflow." Only when overflow checks are on: debug builds by default, release builds only if you ask.
        • 
        
      • "unsafe makes code faster." It switches off checks. Speed comes from what the code does, and the optimizer usually removes the checks you'd want to skip.
        • 
        
      • "let _guard and let _ mean the same." The first keeps the value until the end of the block; the second drops it immediately.
        • 
        
      • "More downloads means safe." It means many people use it, which helps, but popular crates can still have bugs. Keep your lock file, update on purpose, and run cargo audit.

    Lab: run it yourself (Windows, macOS, Linux)
    
      
      
      0. Have Rust and Clippy
      
      
      If you haven't installed Rust yet: on Windows, download and run rustup-init.exe from rustup.rs (it may ask you to install the Visual Studio C++ build tools first). On macOS and Linux, run curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh in a terminal. This book used Rust 1.99.1; rustup update gets the newest. Clippy comes with the default install; if cargo clippy says it's missing, run rustup component add clippy.
      
      
      1. Two race cars
      
      
      In a terminal (Windows: PowerShell or Windows Terminal; macOS: Terminal; Linux: any terminal), run cargo new visitors and cd visitors. Paste overflow.rs into src/main.rs. Run cargo run, then cargo run --release. Look in the target folder: there's a debug and a release folder, each with its own program. Add the [profile.release] lines from panel 25 to Cargo.toml and run the release build again.
      
      
      2. Your own stopwatch
      
      
      Paste bench_debug.rs and run it both ways, three times each. How much do your numbers wobble? Change 3_000_000 to 30_000_000 and see whether the ratio stays about the same. For serious measurements, try Criterion: cargo add criterion --dev, then follow the "Getting Started" page of the Criterion book (benchmarks live in a benches/ folder and run with cargo bench).
      
      
      3. Ask the Trail Guide
      
      
      Run cargo clippy on your own programs from earlier chapters. For more opinions, try cargo clippy -- -W clippy::pedantic (a strict, sometimes fussy group). cargo clippy --fix applies the suggestions it's sure about (it refuses to run if you have uncommitted changes in git, unless you add --allow-dirty).
      
      
      4. Add crates the quick way
      
      
      cargo add serde --features derive and cargo add serde_json write the [dependencies] lines for you, with the newest versions. Then paste serde_demo.rs and run it. cargo tree shows what came along; cargo tree -e features also shows which features each crate switched on. Remove --features derive to meet panel 36's error.
      
      
      5. Count your own allocations
      
      
      Paste alloc_count.rs and add your own line: results.push(("collect 1000 numbers", count(|| (0..1000).collect::<Vec<u32>>())));. Guess the number before you run it.
      
      
      6. Check your dependencies
      
      
      cargo install cargo-audit (a few minutes the first time), then cargo audit in any project with a Cargo.lock. It works the same on all three systems.
      
    
      
  
      

  
      
    Words from this chapter
    
      
      
      
        
      idiomatic
      Written the way experienced users of the language usually write it.
      
        
      API (application programming interface)
      The functions, types and methods other code can use; its design is how easy they are to use well.
      
        
      signature
      A function's first line: its name, what it takes and what it returns. The "handle" of the function.
      
        
      deref coercion
      Rust turning &String into &str (or &Vec<T> into &[T]) automatically where needed.
      
        
      impl Into<String>
      A parameter type meaning "anything that can turn into a String".
      
        
      lint / Clippy
      One named check of code style or correctness / the tool (cargo clippy) that runs hundreds of them.
      
        
      zero-cost abstraction
      A convenient way to write code (iterators, generics, newtypes) that compiles to code as fast as the hand-written version.
      
        
      newtype
      A struct with one field that gives a value its own type, such as struct Meters(f64).
      
        
      builder
      A helper value you fill in one named choice at a time before build() makes the real thing.
      
        
      receiver
      The value before the dot in a method call; self inside the method.
      
        
      guard / RAII
      A value whose Drop undoes what its creation did / "resource acquisition is initialization", the pattern behind guards.
      
        
      typestate
      Using a different type for each stage of something, so wrong-stage actions don't compile.
      
        
      wildcard import
      use path::*;, which brings in every public name at once.
      
        
      debug build / release build
      Built quickly with checks and no optimization / built slowly with optimization and (by default) no overflow checks.
      
        
      profile
      A named set of build settings in Cargo.toml: dev and release.
      
        
      overflow / wrap around
      A result too big (or small) for its type / continuing from the other end, like an odometer.
      
        
      optimize / optimizer
      Make a program faster or smaller without changing what it does / the part of the compiler that does it.
      
        
      benchmark / profiler
      A careful, repeated time measurement / a tool that shows where a program spends its time.
      
        
      allocation
      One request to the heap for memory.
      
        
      capacity
      How many items a Vec (or bytes a String) has room for without asking the heap again.
      
        
      buffer
      A piece of memory kept for holding data on its way somewhere, often reused.
      
        
      global allocator
      The one place every heap allocation in a program goes through.
      
        
      crate registry / crates.io / docs.rs
      Where published crates live / Rust's public registry / the site that builds and hosts every published crate's documentation.
      
        
      serialize / deserialize
      Turn a value into text or bytes / turn them back into a value.
      
        
      JSON
      "JavaScript Object Notation": a text format of keys, values, lists and nesting, used by most web services.
      
        
      seed
      The starting number of a random-number generator; the same seed gives the same sequence.
      
        
      regular expression / capture group
      A pattern for matching text / a bracketed part of the pattern you can read back.
      
        
      dependency / dependency graph
      A crate your project uses / every crate involved, and who uses whom (cargo tree prints it).
      
        
      feature
      An optional part of a crate, switched on in Cargo.toml.
      
        
      supply chain / typosquatting
      All the code you depend on and the people behind it / publishing a malicious crate under a name one typo away from a popular one.
      
        
      E0308 / E0382 / E0616 / E0603
      Mismatched types (here: wrong newtype, &Vec vs array, two rand versions) / use of a moved value (the builder used twice) / private field / private item (a tuple struct's constructor).

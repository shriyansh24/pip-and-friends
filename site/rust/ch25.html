PIPES AND EXCHANGE BOOTHS

Picture: Mabel the librarian waves. Beside her, a pipe labelled stdin runs into a yellow box labelled your program; out of the box come two pipes, stdout and stderr, with water flowing out. To the right stands a little wooden exchange booth with a window labelled From and two coins in front.

The library is getting a plumbing room and an exchange office. In the plumbing room, programs take text in through one pipe, send results out through another, keep a third for trouble, read and write files on the shelves, and listen to switches on the command line. In the exchange office, numbers change from one type to another: some booths are fair, some may refuse, and one shortchanges you without a word. At the end, a real line-counting tool. About 150 minutes, with 25 hands-on checks.

  2. Books on the shelf: reading and writing files, paths
  3. Buckets: BufReader, BufWriter and the vanishing report
  4. The switchboard: arguments, environment variables, clap
  5. The exchange booths: as, From, TryFrom, checked maths
  6. Labels that can't be mixed up: newtypes and Default

Picture: Mabel points at a row of tools. The Professor answers from the right.

2

The three standard streams. A stream is a pipe that carries bytes, one after another. The operating system connects all three to your terminal unless you tell it otherwise.

stdinstandard input, number 0

Where a program reads. The keyboard, unless a file or another program is plugged in.

stdoutstandard output, number 1

Where println! writes. The results: the data someone might save or pass on.

stderrstandard error, number 2

Where eprintln! writes. Trouble: warnings, errors, progress notes for a human.

3

Two lines go down the main pipe and one down the spout. On a plain terminal both pipes end on the same screen, so they look alike. The shell can unplug either one.

When a program ends, it raises a little flag for whoever started it: the exit code, a whole number. Scripts and other programs read the flag to decide what to do next. In a terminal, echo $? shows the last one.

    

      
0All went well. The only "success" code.

      
1Something failed: a general "no". ExitCode::FAILURE, and what main gives when it returns Err.

      
2By custom: "you used me wrong" (bad arguments). clap uses it.

      
101Rust's code for a panic, and for a failed cargo build (Chapter 13).

    

    

      
      
Mabel says: Anything that isn't 0 means "not OK". The number says what kind of not-OK, so pick it on purpose.

PART 3 · BUCKETSBufReader and lines() for files; E0599 when BufRead isn't imported; the Read and Write traits; BufWriter's bucket; flush; the report that vanished; errors swallowed on drop


  

    17
    
Every trip to the stack room costs time: the program has to ask the operating system, which is slow compared with anything inside your program. Carrying one teaspoon per trip would take forever. So Rust offers buckets.

    

    

      
BufReadera bucket for reading
Fetches a big scoop (8 KiB by default) in one trip, then hands it out line by line. Gives you .lines().

      
BufWritera bucket for writing
Collects your little writes and pours them out in one trip when it's full, when you flush it, or when it's dropped.

    PART 5 · THE EXCHANGE BOOTHSE0308 between i64 and i32; as casts: truncation, sign change, float saturation, the literal the compiler catches; From and Into; E0277 when no fair exchange exists; TryFrom and TryInto; checked, overflowing, wrapping and saturating maths
    

  
    
    31
    
    Numbers in Rust come in sizes (Chapter 3): a u8 holds 0 to 255, an i32 about ±2 billion, an i64 far more. Rust never changes a number's type behind your back. To change one, you visit an exchange booth, and there are three.
    
    
    
      
    From / Intothe fair booth

    Under the hood: file descriptors, buffering, bits and exit codes
    
    
      
    
        
        
    The Professor says: Let's take the plumbing apart.
    
      
    
      
    The numbers 0, 1 and 2
    
      
    On Linux and macOS, a running program refers to each open pipe or file by a small number, a file descriptor. Every program starts with three already open: 0 (stdin), 1 (stdout) and 2 (stderr). That's why the shell writes 2> for "redirect stderr": it means "descriptor 2". When you open a file, it typically gets the next free number, 3. Windows uses "handles" instead, with the same three standard ones.
    
      
    Rust's own buffering of stdout
    
      
    io::stdout() already has a small bucket that pours at every newline (it's line-buffered), which is why print! without a newline sometimes doesn't appear until later; call io::stdout().flush() after a prompt. stderr has no bucket at all, so warnings appear at once. Each println! also locks stdout for a moment; in a loop that prints thousands of lines, take the lock once with io::stdout().lock() and wrap it in a BufWriter, as linecount does.
    
      
    Why 300 as u8 is 44
    
      
    Integers are stored in binary. 300 is 1 0010 1100: nine bits. A u8 has room for eight, so as keeps the lowest eight, 0010 1100, which is 44. Negative numbers use two's complement: −1 is all ones, so as a u8 it reads 1111 1111 = 255. Casting between signed and unsigned of the same size never changes a bit, only how the bits are read. Float-to-integer casts have saturated (pinned to the nearest end, NaN to 0) since Rust 1.45; before that, out-of-range casts were undefined behaviour.
    
      
    Exit codes have 8 bits on Unix
    
      
    On Linux and macOS, a parent process sees only the lowest 8 bits of an exit code, which is why ExitCode::from takes a u8. process::exit(256) would look like 0 there, and like 256 on Windows; the standard library's documentation gives this very example. Shells also report a program killed by a signal as 128 plus the signal number.
    
      
    What main's Result does
    
      
    When main returns Err(e), Rust prints Error:  and e's Debug form to stderr, and exits with 1. That's why Panel 12 showed Os { code: 2, kind: NotFound, … } instead of the friendlier Display text. Real tools usually match the error in main and print it with {e}, as linecount does. The anyhow crate prints a tidy chain of causes.
    
      
    Newtypes cost nothing
    
      
    In practice a struct with a single field has the same size as that field: Meters(f64) is 8 bytes, like f64, and the wrapper costs nothing at run time. Rust's default layout doesn't promise this; writing #[repr(transparent)] above the struct makes it a guarantee (the Rust Reference, "Type layout"). The safety is free.
    
    
    
  
    

  
    
    In real programs: where you'll meet these pipes and booths
    
    
      
      
        
    • Unix-style tools (grep, wc, sort) read stdin when no file is given, write results to stdout, complain on stderr and use exit codes 0, 1 and 2. A Rust tool that follows the same rules fits straight into any pipeline.
      • 
        
    • clap is the usual choice for argument parsing in Rust command-line tools. Its derive style also does subcommands (tool add, tool list) with an enum, can read defaults from environment variables (its env feature), and generates shell completions. Chapter 28 looks at choosing crates.
      • 
        
    • Reading configuration: settings usually come from three places, in order of priority: command-line flags, then environment variables, then a config file, then defaults. Read them all once at start-up into one settings struct with Default.
      • 
        
    • Testing output: write functions that take &mut impl Write, as in Panel 20. The real program passes stdout; tests pass a Vec<u8> and compare.
      • 
        
    • Newtypes appear wherever a mix-up would be expensive: IDs (UserId, OrderId), money in cents, units, and validated text such as an Email that can only be built by a TryFrom<&str> that checked it.
      • 
        
    • Lints for casts: cargo clippy -- -W clippy::cast_possible_truncation warns at every as that might lose data. Some teams turn it on for the whole project (Chapter 15 introduced clippy).
      • 
      
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "Errors should be printed with println!." Put them on stderr with eprintln!, or they end up inside saved results.
      • 
        
    • "Any exit code is fine; nobody looks." Scripts, &&, build systems and CI all look. 0 must mean success.
      • 
        
    • "process::exit is just a quicker return." It skips every drop: unflushed buckets are lost, and temporary files aren't cleaned up.
      • 
        
    • "fs::write adds to the file." It replaces it. Use OpenOptions::new().append(true).
      • 
        
    • "Dropping a BufWriter is as good as flushing it." It usually writes the data, but any error is thrown away. Flush yourself and check the result.
      • 
        
    • "lines() keeps the newline." It removes it (and a \r before it, for Windows files).
      • 
        
    • "Command-line numbers arrive as numbers." Every argument is a String until you parse it.
      • 
        
    • "as rounds floats." It chops toward zero. Use .round() first.
      • 
        
    • "as will panic if the value doesn't fit." It never panics and never warns (except for a literal the Compiler can see). That's why it's the shady booth.
      • 
        
    • "A type alias makes a new type." It's a nickname. Use a newtype for protection.
      • 
        
    • "A newtype gets its inner type's methods and operators." It gets nothing until you implement or derive it (E0369 for +).
      • 
        
    • "Wrapping set_var in unsafe makes it safe." unsafe is a promise you make. With other threads touching the environment, the promise is false.

    Arithmetic that, on overflow, gives None / wraps and says so / wraps / stops at the end.
    
        
    type alias
    A second name for an existing type (type Meters = f64;). No new checks.
    
        
    newtype
    A one-field tuple struct that makes a distinct type around another (struct Meters(f64);).
    
        
    Default
    The trait for a type's sensible starting value.
    
        
    E0133 / E0308 / E0277 / E0599 / E0369
    Unsafe call outside unsafe / mismatched types / a missing trait (Display for paths, From<i64> for i32) / a trait method used without importing the trait / an operator the type doesn't have.

2

The Professor's map. Every word on it is a real Cargo word, and the whole chapter uses this picture.

cratea building

One unit the Compiler builds at a time. A library crate (src/lib.rs) is used by others; a binary crate (a program with fn main) is run.

packagea plot

One Cargo.toml and the crates it describes: at most one library, and any number of programs.

workspacethe city

Several packages that are built together and share one Cargo.lock and one target/ folder.

dependencya road

A crate your crate uses. Cargo builds the roads' far ends first.

featurean optional room

A named, switch-on-able part of a crate, added at build time only if someone asks for it.

Cargo.toml / .lockdeed and receipt

The deed says what the plot needs and allows; the receipt (Chapter 14) records exactly which versions were used.

The map, as text: a workspace is the whole city. A package is a fenced plot with one Cargo.toml. Inside a plot stand crates, which are buildings: one library building and program buildings, including extra ones in src/bin. Roads are dependencies. A feature is an optional room built only on request. Cargo.toml is the deed and Cargo.lock the receipt.

When you publish a library, its version number is a promise to everyone who uses it. Rust crates follow semantic versioning ("semver"): MAJOR.MINOR.PATCH.

    

    

      
You changed…Bump1.4.2 becomes

      
        
a bug inside, nothing public changedpatch1.4.3

        
added something public (old code still compiles)minor (patch goes to 0)1.5.0

        
changed or removed something publicmajor (the rest go to 0)2.0.0

      
    

    
Before 1.0.0, Cargo treats the first non-zero number as the "major" one: going from 0.3.1 to 0.4.0 is allowed to break things, which is why panel 28 of Chapter 14 said "0.10.3" never accepts 0.11.

  


  

  

  

    17

Chapter 14 called Cargo.lock the receipt: the exact versions a build used. Three more things about it.

    

      
programskeep the receipt
For a program, commit Cargo.lock to version control, so every build everywhere uses the versions you tested.

      
librariestheir receipt is ignored by others
When your library is someone's dependency, only their top-level Cargo.lock counts; yours is skipped. Cargo's own guide doesn't tell library authors to leave it out (cargo new tracks it by default), and many keep it for their own tests and CI.

      
cargo updatea new receipt
Moves every dependency to the newest version its requirement allows, and rewrites Cargo.lock. cargo update -p rand updates just one. Cargo.toml doesn't change.

    Under the hood: what cargo test really builds, fingerprints, features and the resolver
    
      
      
      
        
        
      The Professor says: A city planner's notes on how the town is actually built.
      
      
      
      
      One cargo test, several programs
      
      
      For panel 24 Cargo compiled the library twice: once normally (so tests/checkout.rs and the doc tests can use it as a customer) and once with --test, which turns on cfg(test) and adds a small test runner called libtest with its own main. It did the same for src/main.rs, and compiled each file in tests/ as a crate of its own with the runner added. Each of those is an ordinary program in target/debug/deps/; the Running line shows its path, and you could run it by hand. Everything after -- is handed to each of those programs, which is why --test-threads, --ignored and --show-output go there.
      
      
      The odd letters in overdue-1390698c04b366c2
      
      
      They are a hash of the things that make a build different: the package, its version and source, the profile, the features and the compiler version. Two builds that differ get different file names, so they can sit side by side in target/. The comparison toolchain (Rust 1.97.0) produced different letters for every test program on this page, which is the main reason 25 of the 72 programs are recorded as differing between versions in the data file.
      
      
      Doc tests
      
      
      rustdoc --test pulls every fenced code block out of the library's doc comments, wraps each in a fn main (unless it has one), adds use-free access to your crate by name, compiles and runs it. Since edition 2024 it compiles as many examples as it can into one program ("merged doctests") and runs that, which is far quicker than one program per example. A block marked ```ignore isn't run, ```no_run is compiled but not run, ```should_panic must panic, and ```compile_fail must not compile. Lines starting with #  are compiled but hidden from the rendered docs.
      
      
      How features are switched on
      
      
      Cargo passes each enabled feature to the compiler as --cfg feature="weekend", and it also passes the list of features that exist. That second list is how the Compiler could say expected values for `feature` are: `party` and `weekend` in Boss 2. Within one build, every crate is compiled once with the union of all features anybody asked for (feature unification), which is why features must only add things.
      
      
      The resolver
      
      
      The resolver reads every requirement in the city, picks one version per major line of each crate (two incompatible majors, like rand 0.9 and rand 0.10, can both be in one build), and writes the result in Cargo.lock. Resolver 2 (edition 2021) stopped unifying features between normal dependencies and build-time or dev-only ones. Resolver 3 (edition 2024) adds the MSRV rule from panel 20: by default it falls back to older versions whose rust-version your project can build, when such versions exist.
      
      
      Profiles
      
      
      cargo build uses the dev profile (fast to compile, checks for overflow), cargo build --release the release profile (optimised), and cargo test the test profile, which starts from dev. You can change a profile in Cargo.toml, for example [profile.dev] with opt-level = 1 for faster debug programs. In a workspace, profiles are set once, in the top Cargo.toml. Tuning them for speed is Chapter 28.
      
    
      
  
      

  
      
    In real programs: workspaces, features and tests you'll meet
    
      
      
        
        
      • Workspaces everywhere. Large Rust projects are usually workspaces: a core library, a command-line program, extra tools and test helpers as separate members, so each piece builds and tests on its own and they all share one Cargo.lock.
        • 
        
      • Features in the wild. serde's derive feature turns on #[derive(Serialize, Deserialize)]; tokio (Chapter 27) has features such as macros, rt-multi-thread and full, so you only compile the parts you use. On docs.rs, each crate's page lists its features.
        • 
        
      • default features. A crate can list features that are on unless you say otherwise: [features] default = ["weekend"]. A user can turn them off with default-features = false in their dependency line.
        • 
        
      • Re-exports. Many crates put a pub use signpost or a prelude at the top so you can write short paths, and so they can reorganise their rooms without breaking you.
        • 
        
      • Test layout. Unit tests at the bottom of each file, a tests/ folder for customer-style tests, and examples in /// comments that double as tests. Larger projects add an examples/ folder: each file there is a small program you run with cargo run --example NAME, and cargo test at least builds them, so they can't rot.
        • 
        
      • CI files. Hosting sites run a short file of commands on every change; for Rust it's usually the three steps from panel 37, often on Windows, macOS and Linux at once, and sometimes on the project's MSRV too.

    Common wrong ideas
    
      
      
        
        
      • "main.rs and lib.rs are one crate." Two crates on one plot. main.rs reaches the library by its name and through pub doors.
        • 
        
      • "pub(crate) means anything in my package." Only the same crate. src/main.rs, src/bin/ and tests/ are other crates.
        • 
        
      • "Globs are always fine." Two globs with one name stop the build (E0659), and a new name in a crate you glob-import can break you later.
        • 
        
      • ""1.2" means exactly 1.2." It means ^1.2: anything from 1.2.0 up to 2.0.0. Exactly is "=1.2.0".
        • 
        
      • "A minor version can change a public type." Not honestly. That's a major bump.
        • 
        
      • "My library's Cargo.lock decides my users' versions." Only the top-level project's lock counts.
        • 
        
      • "A feature can switch something off." Features should only add; Cargo unions them across the whole build.
        • 
        
      • "Integration tests can test private functions if they're in my package." They're separate crates: public only.
        • 
        
      • "Doc examples in main.rs are checked." Cargo runs doc tests for libraries only.
        • 
        
      • "Doc examples on private items are skipped." With Rust 1.99.1 they run, as outsiders, and fail to compile if they use the private item (panel 27).
        • 
        
      • "tests/common.rs is just a helper." It's also a test crate with 0 tests. Use tests/common/mod.rs.
        • 
        
      • "cargo test name runs the test called name." It runs every test whose name contains it.
        • 
        
      • "A filter word checks the doc tests too." With a filter word, cargo test leaves the doc tests out entirely (panel 31). Use cargo test --doc word for those.
        • 
        
      • "If cargo test printed no doc tests, they passed." A failure in an earlier section stops the run; use --no-fail-fast to see everything.
        • 
        
      • "A flaky test is bad luck." It's a real bug in the tests, usually something shared.

      4. Install and publish (read-only steps; nothing here was run for this page)
      
      
        
        
      • cargo install builds a program in release mode and copies it to Cargo's bin folder (~/.cargo/bin on macOS and Linux, %USERPROFILE%\.cargo\bin on Windows), which rustup put on your PATH. cargo install ripgrep installs a published tool; cargo install --path . installs the program in the current folder.
        • 
        
      • Custom cargo commands: any program on your PATH named cargo-something can be run as cargo something. That's how tools such as cargo-edit add their commands.
        • 
        
      • Publishing to crates.io: log in on crates.io with a GitHub account, create an API token, run cargo login and paste it. Fill in description and license (and ideally repository) in [package], run cargo publish --dry-run to check, then cargo publish. A published version can never be changed or deleted, only yanked (cargo yank --version 1.5.0) so new projects won't pick it. That permanence is why honest version numbers matter.
        • 
        
      • Git dependencies: name = { git = "https://…", tag = "v1.2.0" } fetches straight from a repository (this needs the internet, which is why this page used path dependencies). crates.io doesn't allow publishing a crate that depends on git or path crates without a version.

      On your machine: panic lines show a thread id like (8); yours will differ. Windows paths use backslashes. The Compiler's wording can shift a little between Rust versions, as the glob example in panel 9 shows.

    Words from this chapter
    
      
      
      
        
      crate
      One unit the Compiler builds: a library crate or a binary crate (program).
      
        
      package
      A Cargo.toml and its crates: at most one library, any number of programs.
      
        
      workspace
      Several packages built together, sharing one Cargo.lock and one target/. Its top Cargo.toml has a [workspace] section.
      
        
      member
      A package listed in a workspace's members.
      
        
      src/bin/
      A folder of extra programs; each .rs file is one, run with --bin NAME.
      
        
      default-run
      A [package] key naming the program cargo run runs when there are several.
      
        
      -p NAME
      Pick one package of a workspace.
      
        
      pub(crate)
      Visible anywhere in the same crate, nowhere else.
      
        
      re-export, pub use
      Make a name available at another address of your crate, for everyone.
      
        
      prelude
      A module that re-exports the most-used names, meant for one glob import.
      
        
      glob import
      use path::*;: every public name in that module.
      
        
      path dependency
      A dependency found in a folder on disk: { path = "../x" }.
      
        
      cargo tree
      Prints the dependency tree; -i NAME inverts it to show who depends on NAME.
      
        
      feature
      A named optional part of a crate, declared in [features], switched on with --features or in a dependency line.
      
        
      #[cfg(...)]
      Compile the next item only if the condition holds: feature = "x", test.
      
        
      optional dependency
      A dependency built only when a feature asks for it (optional = true, "dep:name").
      
        
      semver
      Semantic versioning: MAJOR.MINOR.PATCH, where the number you bump says what kind of change it was.
      
        
      breaking change
      A change that can stop users' code from compiling or working, such as changing a public type.
      
        
      version requirement
      What Cargo.toml accepts: ^1.2 (or 1.2), ~1.2, =1.5.0, ranges.
      
        
      resolver
      Cargo's engine that chooses versions and features; version 3 is the edition-2024 default.
      
        
      cargo update
      Move dependencies to the newest allowed versions and rewrite Cargo.lock.
      
        
      MSRV, rust-version
      The oldest Rust a package promises to build with.
      
        
      unit test
      A small test inside the crate, in #[cfg(test)] mod tests; may test private items.
      
        
      integration test
      A test file in tests/, compiled as a separate crate that uses only the public API.
      
        
      doc test
      A code example in a library's /// comment that cargo test compiles and runs.
      
        
      testing pyramid
      Many fast unit tests, fewer integration tests, a few broad checks at the top.
      
        
      test filter
      A word after cargo test: runs tests whose names contain it.
      
        
      #[ignore]
      Skip a test unless run with --ignored or --include-ignored.
      
        
      captured output
      What passing tests print, hidden unless --show-output or --nocapture.
      
        
      --no-fail-fast
      Keep running the remaining test sections after one fails.
      
        
      matches!
      True if a value fits a pattern; used as assert!(matches!(v, pattern)).
      
        
      fixture
      A helper that builds a fresh setup (data, a file) for one test.
      
        
      flaky test
      A test that passes or fails depending on timing or order, not on the code.
      
        
      CI
      Continuous integration: a server that runs the checks on every change.
      
        
      E0603 / E0659 / E0425 / E0308
      Private item / ambiguous name from two globs / name not found (here: gated behind a feature) / mismatched types.

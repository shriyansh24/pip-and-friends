    10
    
Think of the Compiler as an editor with a red pen, marking up your page. An editor does three things, and so does every Rust error:

    
    
    
      
  1. Circles the mistake. In the message: ^^^^^^^^^ under the code that broke the rule, with a short label. This is the primary label.
    2. 
      
  2. Draws an arrow back to where the trouble started. In the message: ----- under another spot, with its own label. This is a secondary label.
    3. 
      
  3. Writes the fix in the margin. In the message: a help: line, the line rewritten, and +++ under exactly what to add.
    4. 
    

    
And the sticky note? Every kind of error has a catalogue number, like E0384, so you can look up the long story.

    Under the hood: variables, the checks, and two endings
    
        
      
        A variable is a named place in memory
        
      
        When main starts, Rust sets aside space for its variables, which is why the tracers draw a box per variable inside main. A plain let doesn't make the memory read-only; it is a rule the Compiler checks before anything runs. Rust calls a variable a binding, and the rule is that an immutable binding may be initialised (given its first value) exactly once. That is why let x; followed by x = 6; is fine, and why E0384 says "assign twice". If you look into a declared box before it has a value, the Compiler refuses that too:
        
      
        
      
        A real version difference: Rust 1.97.0 words this E0381 message differently ("used binding `answer` is possibly-uninitialized") and has no help: block. Compiler messages keep improving between releases, which is one reason this book names its exact version.
        
      
        Shadowing really makes a second variable
        
      
        After let title = title.len(); there are two variables. The old one can't be named any more, but it still exists until the end of its block (here, the end of main). That's why the tracer keeps it, faded. In optimised builds the Compiler may reuse its space; you can't tell from inside the program.
        
      
        const and static
        
      
        A const has no address of its own: its value is copied into each place that uses it. A static is one value at one fixed address for the whole run. Changing a static needs static mut and unsafe code, and edition 2024 denies taking references to a static mut; you'll almost never need it. Assigning to a constant isn't allowed at all:
        
      
        
      
        E0070 calls MAX_LOANS an invalid "left-hand side": the left of = must be a place, like a variable, and a constant isn't a place.
        
      
        rustc's ending versus cargo's ending
        
      
        Calling the compiler directly (with --edition 2024, never without it: see Chapter 1) ends the letter differently. You get error: aborting due to 1 previous error, the explain line comes last, and the exit code is 1. Cargo hides the aborting line and adds its own summary instead (exit code 101). This program has no println! between the two assignments, so there is also a warning: the 5 is never read.
        
      
        
      
        How this run was really made
        The cd bare step also made the folder bare and copied the program into it as main.rs: mkdir -p bare && cp rustc_abort.rs bare/main.rs && cd bare. Then rustc --edition 2024 main.rs ran exactly as shown.
        
      
        Every message on these pages comes from Rust 1.99.1. A different version on your machine may word some messages slightly differently, as E0381 above shows.
        
    
        
  
        

  
        
    In real programs
    
        
      
          
        
        • Most variables in real Rust code have no mut. Programmers add a lid only when a value truly changes. The "does not need to be mutable" warning keeps it that way.
          • 
        
        • Shadowing is used for step-by-step conversions: text read from a user, then trimmed, then turned into a number, all under one clear name.
          • 
        
        • Constants live at the top of a file (limits, names, sizes), so there is one place to change them.
          • 
        
        • Many teams treat warnings as errors in their automatic build checks, so code with warnings can't be merged. One common way is building with RUSTFLAGS="-D warnings"; -D means "deny".
          • 
        
        • Clippy (cargo clippy) is an extra set of lints, hundreds of them, with the same message layout you learned here.
          • 
        
        • cargo check runs every check without building a program. It's the fastest way to see the red, and it's what editors run in the background.
          • 
        
        • Machines can read messages too. cargo build --message-format json prints each message as data; that is how editors and other tools draw the red pen.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "let makes a constant." It makes an immutable variable. Constants are const: type required, value fixed before the program runs, usable outside functions.
          • 
        
        • "Immutable means it must get its value on the same line." A sealed box may be filled once, later (Panel 5).
          • 
        
        • "Shadowing changes the old variable." It makes a new one. The old one is hidden, not changed.
          • 
        
        • "mut lets a variable hold anything." It lets the value change; the type never does.
          • 
        
        • "Warnings don't matter." They don't stop the build, but an unused variable is often a typo or a forgotten step.
          • 
        
        • "The ^^^ line is always the one to edit." E0384 wanted line 2, the --- line.
          • 
        
        • "help: is always the best fix." It's a good suggestion. For gen it offered r#gen; renaming is clearer.
          • 
        
        • "Five errors means five mistakes." Often it's one mistake and four echoes.
          • 
        
        • "Errors mean I'm bad at this." Professionals see these messages all day. Reading them well is a skill, and you've started it.

    Words from this chapter
    
        
      
        
        
        variable
        A labelled box holding a value. Made with let.
        
        
        binding
        Rust's word for a name tied to a value; a variable.
        
        
        keyword
        A word Rust keeps for itself, like let, mut, fn, const.
        
        
        reserved keyword
        A keyword kept for the future, like gen in edition 2024.
        
        
        identifier
        A name you invent for a variable, constant or function.
        
        
        placeholder
        {} or {name} in println! text: a hole that gets filled with a value.
        
        
        declare
        Make the labelled box: let answer;.
        
        
        assign
        Put a value in a box with =.
        
        
        initialise
        Give a variable its first value.
        
        
        immutable
        Can't be changed. Variables are immutable unless marked mut.
        
        
        mutable, mut
        Changeable: a box with a lid.
        
        
        type
        The shape of a value, which decides what fits: i32, &str, usize.
        
        
        type annotation
        Writing the type yourself: let x: i32 = 5;.
        
        
        type inference
        The Compiler working out the type from the value.
        
        
        shadowing
        A new let with an old name: a new box in front of the old one.
        
        
        constant, const
        A named value fixed before the program runs. Type required, all caps.
        
        
        static
        A value at one fixed place in memory for the whole run.
        
        
        snake_case
        lowercase_words_with_underscores: the style for variables.
        
        
        SCREAMING_SNAKE_CASE
        CAPITALS_WITH_UNDERSCORES: the style for constants.
        
        
        diagnostic
        Any message from the Compiler: an error, a warning, a note or a help.
        
        
        error code
        A catalogue number such as E0384, explained by rustc --explain.
        
        
        primary label
        The ^^^ marker and its text: where the problem was noticed.
        
        
        secondary label
        A --- marker and its text: another place in the story.
        
        
        help
        A suggested fix; +++ marks what to add.
        
        
        note
        An extra fact, not a fix.
        
        
        warning
        A message that doesn't stop the build.
        
        
        lint
        A named check that produces warnings, like unused_mut.
        
        
        echo error
        (This book's term.) A later error caused by an earlier one.
        
        
        scope
        The part of a program where a name can be used.
        
        
        rust-analyzer
        The tool that shows Rust errors and type hints inside your editor.
        
        
        rustfmt, cargo fmt
        The tool that tidies code layout.
        
        
        edition
        A named set of language rules (2015, 2018, 2021, 2024), chosen in Cargo.toml.

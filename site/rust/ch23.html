RUST · CHAPTER 23

KEYS, COUNTERS AND REMOTES

Picture: Mabel the librarian points at three things: a big brass key labelled Box, a two-digit counter showing 03 labelled Rc, and a TV remote with buttons, sending signal waves, labelled dyn.

Three gadgets from the library's back office. A key to a storage unit across the street: that's Box, a value kept on the heap. A member counter on a shared family account: that's Rc, one value with several owners, cleaned up when the last one leaves. And a universal remote that looks up each device's button codes the moment you press: that's dyn Trait, one list holding many different types. PART 1 · THE STORAGE-UNIT KEYBox puts a value on the heap and keeps a key on the stack; big values, the key moving instead of the value, and recursive types (E0072)

1

Monday morning. A delivery of four hundred donated books lands on Mabel's desk. The desk is small, tidy and fast to reach. It is not built for four hundred books.

Mabel says: My desk is the stack from Chapter 7: small, quick, and everything on it has a size I know in advance. The books go to the storage unit across the street. That's the heap. I keep only the key on my desk.

The Professor says: Rust has a type for exactly that key: Box<T>. You met it in Chapter 7. Today you'll see why it matters, and meet its two cousins, Rc and RefCell.

Picture: Mabel, surprised, shrugs at a pile of books. The Professor answers from the right.

2

Box::new(5) rents a space on the heap, puts the 5 in it, and gives you back a key: a pointer that knows where the space is. The key lives on the stack. It owns the space, so when the key's owner leaves, the space is emptied and given back (Chapter 7's drop).

Mabel says: A Box is a smart pointer: a pointer that also owns what it points at and does something extra for you (here: frees the space). Catchphrase: one key on the desk, the value in the unit.

    deref_coercion.rs
    
      
    
      
    
    
        
      
      1. Line 10: greet wants a &str but gets a &String. A String is a smart pointer to its letters, and it says so with the Deref trait (Chapter 18's first look). Rust calls deref for you, once.
        2. 
      
      2. Line 11: a &Box<String>, two keys deep. Rust calls deref as many times as it needs, until the type fits. This is deref coercion: "coercion" means a conversion the Compiler does without being asked.
        3. 
      
      3. Line 12: the same trip written out by hand. *boxed is the String, **boxed is the str inside it, and & borrows that. Nobody writes this; it's here to show what line 11 means.

        5.

        The pattern has a long, odd name: RAII, "Resource Acquisition Is Initialization". It means: getting something (a heap unit, an open file, a lock) is making an owner, and giving it back happens in the owner's Drop. You can't forget to clean up, because the closing brace does it. Box frees its unit this way; Rc, in Part 3, updates its counter this way.
        
  
        

  
        
  

  
        
    12
    
        A smart pointer is a pointer, plus ownership, plus one extra job, done through Deref and Drop. Here's this chapter's key ring. You know the first; the other two come next.
        
    
          
      
        • Box<T>Box::new(v)One owner. The value lives on the heap. Extra job: free the unit at drop.
          • 
      
        • Rc<T>Rc::new(v), Rc::clone(&r)Many owners, read-only. Extra job: count the owners, and free the value when the count reaches 0.
          • 
      
        • RefCell<T>.borrow(), .borrow_mut()One owner, but changes allowed through a shared &. Extra job: check Chapter 8's lending rules while the program runs.
          • 
    
        
    
        The card with the dashed border is the one whose checks happen while the program runs instead of at compile time.

          PART 4 · THE WHITEBOARDRefCell checks the lending rules while the program runs: borrow and borrow_mut, the RefCell machine, the "already borrowed" panic, Cell, Rc<RefCell<T>>, cycles that leak, Weak, and Rc across threads (E0277)
          

  
          
    19
    
          The staff room has a whiteboard. Anyone with a key to the room may use it, but there's a sign-out sheet taped beside it, checked every time: sign in as a reader (any number at once) or as the writer (only if nobody else is signed in). Rust's whiteboard is RefCell<T>.

          For small Copy values like numbers and bools there's a simpler tool, Cell<T>. It never lends anything out. You get a copy, or set a new value, so there's no sheet and nothing to panic about.
          
    cell.rs
    
          
    
          
    
            
      
          1. Line 5: a counter inside the Book, wrapped in a Cell.
            2. 
      
          2. Line 10: open takes &self, yet counts: get() copies the number out, set() puts a new one in. Interior mutability again, with no passes at all.
            3.

            The cure is a key that doesn't count: Weak<T>. Think of a bookmark card that remembers where a book is, but doesn't stop the book going back. Rc::downgrade(&rc) makes one; weak.upgrade() asks "is it still there?" and answers with an Option<Rc<T>>. The usual rule: parents own their children; children point back to their parent weakly.

              2.

    32
    
            How does s.area() know whose area to run? A &dyn Shape is a fat pointer: two addresses instead of one. The first points at the data. The second points at a vtable ("virtual method table"): a small table the Compiler builds once per type and trait, listing where each method's code lives.
            
    
    
    fat_pointer.rs
    
            
    
            
    
            The real sizes on this 64-bit computer: a plain reference or Box is 8 bytes, one address. A dyn one is 16 bytes, two addresses. Looking up a method this way while the program runs is called dynamic dispatch ("dispatch" means sending a call to the right code).

    Under the hood: what Box, Rc, RefCell and dyn really are
    
            
      
            
        
        
            The Professor says: None of these is magic. Each is an ordinary struct in the standard library, plus a few rules the Compiler knows about.
            
      
            
      
            Box
            
      
            A Box<T> is one pointer. Box::new asks the memory allocator for size_of::<T>() bytes and moves the value there; Box's Drop drops the value and hands the bytes back. Option<Box<T>> is also 8 bytes: a Box is never null, so Rust uses the null address to mean None (the "null pointer optimization", which the standard library guarantees for Box). One quirk: Box::new([7u32; 100_000]) may build the array on the stack first and then copy it, so truly huge arrays are usually made with vec! instead.
            
      
            Rc and Weak
            
      
            Rc::new(v) makes one heap allocation holding two counters and the value: the strong count and the weak count. Rc::clone adds 1 to the strong count; dropping an Rc subtracts 1, and at 0 it drops the value. The allocation itself stays until the weak count also reaches 0, so a Weak's upgrade() can still look at the strong count and safely answer None. Internally all the strong keys together hold one hidden extra weak count; Rc::weak_count leaves it out, which is why panel 27 printed weak 1. The counters are plain numbers changed without any coordination between threads, which is why Rc isn't Send. Arc (Chapter 26) does the same with atomic operations.
            
      
            RefCell's sign-out sheet
            
      
            A RefCell stores the value plus one number, the borrow flag: 0 means nobody is signed in, a positive number counts the readers, and a negative number means a writer. borrow() checks and increases it; the returned Ref decreases it in its Drop. That's the "pass" from panel 19, and why a pass kept in a variable keeps you signed in. The check costs a comparison and an add each time: small, but not free. Cell has no flag at all; it only ever copies values in and out.
            
      
            Deref coercion, precisely
            
      
            When the types don't match, the Compiler may insert deref calls: &T becomes &U if T: Deref<Target = U>, &mut T becomes &mut U with DerefMut, and &mut T may become &U (giving up the right to write is always allowed). Never the other way round. It repeats as many times as needed, and the method call dot (boxed.len()) does the same search.
            
      
            The vtable
            
      
            For each pair of a concrete type and a trait used as dyn, the Compiler emits one vtable. Today's compiler puts the type's drop code, its size and its alignment first, then one entry per method; the exact layout isn't promised and may change. Box<dyn Shape> uses the drop entry to clean up a value whose type it no longer knows, and the size entry to free the right number of bytes. Since Rust 1.86 a &dyn Sub can also be turned into a &dyn Super when Sub has Super as a supertrait ("trait upcasting"), so a vtable also knows how to reach its supertraits' tables.
            
      
            A surprising error: &Box<dyn Shape> isn't a &dyn Shape
            
      
            Panel 31 wrote describe(s.as_ref()). Here is the real run of the same program with just describe(s), saved as dyn_box_ref.rs:
            
      
            
      
            When the target type is a &dyn Shape, the Compiler tries to turn the Box itself into a trait object, which would need Box<dyn Shape>: Shape: that's the note: required for the cast from `&Box<dyn Shape>` to `&dyn Shape`. It doesn't fall back to following the key. Fixes: s.as_ref(), &**s, or (in your own crate) impl<T: Shape + ?Sized> Shape for Box<T>.
            
    
            
  
            

  
            
    In real programs: where these keys, counters and remotes turn up
    
            
      
              
        
            • You've used smart pointers since Chapter 7. String and Vec<T> own heap memory, implement Deref (to str and [T]) and free it in Drop. So does PathBuf (Chapter 25).
              • 
        
            • Recursive data: compilers and interpreters store programs as trees of enums with Box children, such as an expression Add(Box<Expr>, Box<Expr>). JSON and XML libraries do the same for nested documents.
              • 
        
            • Trait objects you've met: Box<dyn Error> (Chapters 13 and 21) and Box<dyn Fn> callbacks (Chapter 20). Logging, plugin and GUI libraries keep lists of Box<dyn Trait>; &mut dyn std::io::Write lets one function write to a file, the terminal or a String buffer.
              • 
        
            • Drop guards: a File closes itself, a MutexGuard unlocks (Chapter 26), and a temporary directory deletes itself, all through RAII.
              • 
        
            • Rc<RefCell<T>> appears in single-threaded GUI code, game prototypes and tree structures. Many experienced Rust programmers prefer to store nodes in a Vec and link them by index instead, which avoids run-time borrow panics and cycles entirely.
              • 
        
            • Rc<str> and Arc<str> are a common way to share one immutable string among many owners without copying it.
              • 
        
            • Clippy (Chapter 15) has lints for this chapter, such as clippy::borrowed_box, which suggests taking &T instead of &Box<T> in a function's parameters.
              • 
      
            
    
            
  
            

  
            
    Common wrong ideas
    
            
      
              
        
            • "Box makes values faster." It adds a step (follow the key) and a heap allocation. It helps with size problems, not speed.
              • 
        
            • "Rc::clone copies the data." It only adds 1 to a counter (panel 16). (*rc).clone() is the deep copy.
              • 
        
            • "RefCell turns off the borrow checker." The rules still apply; they're checked while running, and breaking them panics (panel 22).
              • 
        
            • "Safe Rust can't leak memory." Rc cycles leak (panel 26), and so do std::mem::forget and Box::leak, all in safe code. Rust promises no reading of freed memory, not no leaks.
              • 
        
            • "A Weak keeps the value alive." Only strong keys do. A Weak can always come back None.
              • 
        
            • "dyn is slow." A dyn call is one table lookup and an indirect jump. It matters in very hot loops; elsewhere, it rarely shows.
              • 
        
            • "dyn Shape is a type I can store in a variable." It has no fixed size. It always lives behind a pointer: &dyn, Box<dyn>, Rc<dyn>.
              • 
        
            • "No inheritance means no code reuse." Default methods, generics, composition and trait objects cover what inheritance is usually used for.
              • 
        
            • "Object safe" and "dyn compatible" are different rules. Same rule; the name changed in 2024 because "object safety" had nothing to do with memory safety.

    Words from this chapter
    
            
      
            
        
            smart pointer
            A value that points at something, owns it, and does an extra job (freeing, counting, checking) through Deref and Drop.
            
        
            Box<T>
            One owner of a value on the heap: the storage-unit key.
            
        
            recursive type
            A type that contains itself; needs a pointer (indirection) in the loop, or E0072.
            
        
            indirection
            Pointing to a value instead of holding it.
            
        
            Deref / deref coercion
            The trait behind *x; the Compiler's automatic deref calls that turn &Box<String> into &str.
            
        
            coercion
            A type conversion the Compiler makes by itself.
            
        
            Drop / RAII
            Code run automatically when an owner leaves; the pattern of tying cleanup to ownership.
            
        
            Rc<T>
            Reference-counted pointer: several owners of one value, read-only, one thread.
            
        
            strong count
            How many Rc keys keep the value alive (Rc::strong_count).
            
        
            Weak<T>
            A key that doesn't keep the value alive; upgrade() gives Option<Rc<T>>. Made with Rc::downgrade.
            
        
            reference cycle
            Strong keys pointing at each other in a loop; their counts never reach 0, so they leak.
            
        
            memory leak
            Memory that's never given back while the program runs.
            
        
            interior mutability
            Changing something through a shared &, made safe by a run-time check (RefCell) or by copying (Cell).
            
        
            RefCell<T>
            The whiteboard: borrow() (a Ref) and borrow_mut() (a RefMut), with the lending rules checked while running.
            
        
            Cell<T>
            Interior mutability for Copy values with get and set; never lends.
            
        
            Send
            The badge for types that can be handed to another thread. Rc doesn't have it.
            
        
            trait object / dyn Trait
            A value of some type that implements a trait, used behind a pointer, with the type decided while running.
            
        
            fat pointer
            A two-address pointer: data plus vtable (for dyn) or data plus length (for slices).
            
        
            vtable
            The table of a type's method addresses for one trait, used to find the right code at run time.
            
        
            static / dynamic dispatch
            Choosing the method at compile time (generics, one copy per type) / at run time (dyn, through the vtable).
            
        
            dyn compatible
            A trait whose methods can all go in a vtable (formerly "object safe").
            
        
            where Self: Sized
            Marks a method as only for concrete types, leaving it out of the vtable.
            
        
            composition
            Building a type out of other types it holds, instead of inheriting from them.
            
        
            state pattern
            Each stage of a process is its own type that decides the next stage.
            
        
            E0072 / E0614 / E0596
            Recursive type has infinite size; a type that can't be dereferenced; cannot borrow data in an Rc as mutable.
            
        
            E0038 / E0746 / E0782 / E0599
            Trait not dyn compatible; returning a trait object without a pointer; a trait used where a type belongs (missing dyn); no such method (on a trait object, the trait's methods only).

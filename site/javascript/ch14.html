    PART 2 · ADDRESSES ON THE ORDER SLIPDefault exports, and writing addresses Node can find
    

  
    
    8
    
    Some shops are famous for one thing. The bakery's bake is marked export default: the shop's main product. A file can have at most one.
    
    any_name.js
    
    
    
    
    
      
      
    1. No braces for a default import. And you choose the name: bake on line 1, makeBread on line 2. Both mean "whatever this shop's main product is".
      2. 
      
    2. Line 6 prints true: both names point at the same function, from one visit. Bakery: ovens on appears once.
      3. 
    
    
    
    
      
    
        
    NAMEDexport function withTax…
    
        
    Any number per shop. Order with braces and the exact name: import { withTax } from …
    
      
    
      
    
        
    DEFAULTexport default function bake…
    
        
    At most one per shop. Order without braces, under any name you like: import bake from …
    
      
    
    
    
    
    
      
      
    The Professor says: Many teams prefer named exports everywhere: the name is the same in every file, so searching for it finds every use. You'll meet both in real code. Chapter 26 shows the other forms, such as renaming on the slip.
    
    
    
  
    

  
    
  

  
    
    9
    
    The text after from is the shop's address (programmers call it the module specifier). Node reads its first few characters to decide where to look.
    
    
    
      
    Address starts with…Node looks…
    
      
        
    "./shops/prices.js"On your street: a file, starting from the folder of the file doing the ordering. ./ means "this folder".
    
        
    "../prices.js"One street back: ../ means "the folder above this one".
    
        
    "node:fs"On Node's own shelf: a built-in module that comes with Node. Nothing to install.
    
        
    "shout-lib"In the storeroom: just a name means a package, installed into a folder called node_modules (Part 3).
    
        
    "./shops/prices"✗ Missing .js. In Node's modern modules, a file address must be complete. Node won't guess the ending.
    
        
    "shops/prices.js"✗ Missing ./. Without it, shops looks like a package name, so Node searches the storeroom instead of your folder.
    
          
    
    
    
    
      
      
    Kit says: Two habits fix almost every address: start your own files with ./, and always write the .js.
    
    
    
    
    DOT-SLASH AT THE FRONT. DOT-JS AT THE END.

    PART 3 · THE WHOLESALE MARKETnpm, package.json, node_modules and scripts
    

  
    
    13
    
    Kit's shops are all home-made. But millions of shops already exist, written by other people and shared for free. A shop you download is a package, and the market they come from is npm.
    
    
    
    
    
      
    npmthe market, and the tool
    The registry is a huge online catalogue of packages. The npm command, which comes with Node, shops there for you.
    
      
    package.jsonthe shopping list
    A file describing your project: its name, its scripts, and the packages it needs (its dependencies).
    
      
    node_modulesthe storeroom
    The folder where installed packages actually live. npm fills it; you never edit it by hand.
    
      
    package-lock.jsonthe receipt
    Records exactly which version of every package was installed, so the next npm install gets the same ones.
    
    
    
  
    

  
    
    14
    
    Kit opens a new project, corner-shop. Its one file, index.js, imports from Node's shelf. Then Kit writes the shopping list with npm init -y (-y means "yes to every question").
    
    corner-shop/index.js
    
    
    
    
    
      
      
    1. npm init -y writes package.json and prints it. Look at the last field: "type": "commonjs".
      2. 
      
    2. So node index.js crashes: SyntaxError: Cannot use import statement outside a module. "commonjs" means "treat .js files as the old kind of module", the kind that doesn't understand import (Part 4). Node's warning above it even names the fix. (The (node:1) is the program's process number; yours will differ, see the note below.)
      3. 
      
    3. npm pkg set type=module changes that one field to "module": "my .js files are modern modules". It prints nothing, and now node index.js works.
      4. 
    
    
    
    How this run was really made: the npm init -y step first deleted the package.json left by the previous capture (rm -f package.json), so npm writes a fresh one. The first node index.js ran as the first process of its own small process space (unshare -p -f --mount-proc node index.js), which is why its process number is always 1. On your computer, Node shows its real, changing process number there.
    
    
    
      
      
    The Professor says: Every folder in this book has a package.json with "type": "module" for exactly this reason. Newer versions of npm write "commonjs" into new projects, so this is the first thing to change. The notebook's version notes show what older npm and Node do instead.
    
    
    
    
    NEW PROJECT? SET "TYPE": "MODULE".

    Two rules about the storeroom that every team follows.
    
    
    
      
    
        
    ✓ KEEP AND SHAREpackage.json, package-lock.json
    
        
    Small text files that describe what the project needs. Anyone who gets your project runs npm install once, and npm rebuilds node_modules from them.
    
      
    
      
    
        
    ✗ NEVER SHAREnode_modules
    
        
    It can hold thousands of files and can always be rebuilt. When you save your project with Git (a tool that keeps the history of your files), list it in a file called .gitignore so Git skips it:
    
        popcorn-cart/.gitignore

      2.

    PART 4 · THE OLD STREETCommonJS: require and module.exports
    

  
    
    18
    
    Before import existed, Node had its own module system, called CommonJS. Millions of files still use it, so you'll meet it in tutorials and packages. Files ending in .cjs are always CommonJS.
    
    
    
      
    old/prices.cjs
    
      
    old_street.cjs
    
    
    
    
    
    
    
      
    
        
    MODERN: ES MODULES.js with "type": "module", or .mjs
    
        
    export function withTax…
    import { withTax } from "./prices.js";
    Order slips at the top, all checked before anything runs.
    
      
    
      
    
        
    OLD: COMMONJS.cjs, or .js with "type": "commonjs"
    
        
    module.exports = { withTax };
    const { withTax } = require("./prices.cjs");
    require is an ordinary function call that runs when its line is reached.
    
      
    
    
    
    
    This book writes modern modules. The two systems can work together, but the rules for mixing them are a Chapter 26 topic. For now, learn to tell them apart, and to read the errors you get when they're mixed up by accident.
    
  
    

  
    
    19
    
    
    Mix-up 1: copying a require line from an old tutorial into a modern file.
    
    require_in_esm.js
    
    
    
    
    
    
      
      
    The Bouncer says: require? Not on this street's list. A ReferenceError, like any unknown name: require is not defined in ES module scope, you can use import instead. And Node explains why this file counts as modern: .js plus "type": "module".
    
    
    
  
    

  
    
    20

    module_in_esm.js
    
    
    
    
    
      
      
    1. Same family: ReferenceError: module is not defined in ES module scope. Old modules get a hidden module variable; modern ones don't.
      2. 
      
    2. The fix: delete line 5 and write export in front of function on line 1. Or, if the file really must stay old-style, rename it to .cjs, as Node suggests.
      3. 
    
    
  
    

  
    
    21
    
    Mix-up 3, the other way round: an import line in a .cjs file. (Panel 14 hit the same wall because "type": "commonjs" made index.js old-style.)
    
    import_in_cjs.cjs
    
    
    
    
    
    
      
      
    The Proofreader says: In an old-style file, import isn't even grammar. SyntaxError: Cannot use import statement outside a module, with my six carets under the word. The warning above is Node trying to help: use .mjs, or set "type": "module". For a .cjs file, the real fix is to use require, or rename it.

    GIVEN THIS, EXPECT THAT.
    
  
    

  
    
    24
    
    Kit's cart functions now live in their own shop, shops/cart.js, which is exactly what makes them testable. Here's a test file for total, and the referee's report.
    
    first.test.js
    
    
    
    
    
      
      
    1. Lines 1–2 order the referee's tools from Node's shelf: test from node:test, and assert (the default export) from node:assert/strict. Nothing to install. Line 3 orders the code being tested.
      2. 
      
    2. test("name", () => { … }) registers one rule: a name that reads like a sentence, and an arrow function the referee will call.
      3. 
      
    3. assert.equal(actual, expected) is the comparison. Actual first (what your code returned), expected second (what the rule says). It does nothing if they're equal with ===, and throws an error if not.
      4. 
      
    4. node --test first.test.js runs the file. Each rule gets a line: ✔ passed, ✖ failed. Then the summary: 2 tests, 2 pass, 0 fail, and exit code 0.
      5. 
      
    5. Why the long command? Times vary on every run, so this book pipes the report through sed, a text-replacing tool, which turns each time into (…ms) and duration_ms …. --test-reporter=spec asks for this ✔/✖ report even when the output goes into a pipe. And set -o pipefail makes the shell report the exit code of node, not of sed, so a red card still ends with exit code 1. On your own computer, plain node --test first.test.js gives the same report with real times. Every test run in this chapter is made this way.
      6. 
    
    
    
    
      
      
    The Professor says: Always import from node:assert/strict, not plain node:assert. In strict mode, equal uses ===. In the older, non-strict mode it uses ==, and "5" would equal 5: Chapter 5's translator, back to cause trouble.
    
    
    
  
    

  
    
    25

    Under the hood: how Node loads a module graph
    
    
      
    Three phases: find, link, run
    
      
    When you run node street.js, Node first parses the file and collects its import lines. For each address it resolves the specifier to a URL (panel 11's map), loads that file, parses it, and collects its imports, and so on until it has the whole module graph: every file reachable from the entry file. Then it links: every imported name is connected to the matching export, and a missing export is a SyntaxError (panel 6) before anything has run. Only then does it evaluate: each module's top-level code runs once, dependencies before the modules that import them. That's why Bakery: ovens on always comes first.
    
      
    One instance per address
    
      
    Node keeps a cache keyed by the resolved URL (for example file:///home/you/javascript-ch14/shops/bakery.js). A second import of the same URL, from any file, gets the same module, already evaluated. Panel 8's true comes from this. Imported names are not copies: they are connections to the exporting module's own variables. (Chapter 26 shows what happens when the exporter changes one later, so-called live bindings.)
    
      
    Modules are strict and private
    
      
    Every ES module runs in strict mode automatically, has its own top-level scope (a const at the top of one file is invisible in another), and its top-level this is undefined. That privacy is the back room from panel 3.
    
      
    How Node decides which kind a file is
    
      
    .mjs is always an ES module and .cjs always CommonJS. For .js, Node reads the nearest package.json going up the folders: "type": "module" means ES module, "type": "commonjs" means CommonJS. With no "type" at all, Node 22.7 and later guess from the syntax: a file with import or export is re-parsed as a module (with the warning shown in the version notes). Writing "type" explicitly avoids the guesswork.
    
      
    How a bare name is found
    
      
    For "shout-lib", Node looks for node_modules/shout-lib in the importing file's folder, then in its parent, then the parent's parent, up to the root of the disk. Inside the package it reads package.json: an "exports" field if there is one, otherwise "main", says which file is the entry. The NODE_PATH environment variable, which older CommonJS code used for extra search folders, is ignored by ES modules.
    
      
    What the test runner does
    
      
    node --test with no file names searches the folder for files matching patterns such as **/*.test.js, **/*-test.js, **/*_test.js, **/test-*.js, **/test.js and anything inside a test folder (skipping node_modules), and runs each file in its own child process. Each test call registers a test; a test passes if its function finishes without throwing. An assertion is just a function that throws an AssertionError when its check fails. The report format is called a reporter; spec (shown in this book) is the default in Node 23 and later, and --test-reporter=tap or dot choose others.
    
    
    
  
    

  
    
    In real programs
    
    
      
      
        
    • Folders of small modules. Real projects have hundreds of files, often grouped by feature (cart/, tickets/) with a test file next to each one: cart.js beside cart.test.js.
      • 
        
    • Packages everywhere. A typical web project lists a handful of dependencies, but each of those has its own, so node_modules often holds hundreds of packages. That's why the lock file matters: it pins every one of them.
      • 
        
    • Continuous integration (CI). Services such as GitHub Actions run npm ci (a strict, clean install from the lock file) and npm test on every change pushed to a shared project. A red card blocks the change from being merged.
      • 
        
    • Other test runners. Many projects use Jest, Vitest or Mocha instead of node:test. Their describe, it and expect(actual).toBe(expected) look a little different, but the idea is identical: given this, expect that.
      • 
        
    • Scripts as the front door. Open-source projects document their scripts so newcomers can type npm install, then npm test, and have a working setup in a minute.
      • 
        
    • Supply-chain care. Installing a package runs other people's code on your computer. Teams check a package's popularity and maintainers, keep the lock file, and run npm audit to look for known security problems (the audited line in panel 15).
      • 
      
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "Importing copies the code into my file." It connects names to the other module's values. The module runs once and is shared.
      • 
        
    • "I can import anything defined in another file." Only what it exports.
      • 
        
    • "Node will figure out ./prices means ./prices.js." Not for ES modules. Bundlers and TypeScript setups sometimes allow it, which is why you'll see it in tutorials.
      • 
        
    • "shops/prices.js and ./shops/prices.js mean the same." The first is read as a package called shops.
      • 
        
    • "A default import must use the exported function's name." You choose the name. Named imports, though, must match exactly.
      • 
        
    • "npm is part of JavaScript." npm is a tool and a registry that come with Node. Browsers don't use package.json at all.
      • 
        
    • "node_modules should go in Git so others don't need to install." Never: it's huge, it can contain files built for your operating system only, and npm can always rebuild it.
      • 
        
    • "package-lock.json is junk to delete." It's the receipt that makes installs repeatable. Commit it.
      • 
        
    • "require and import are interchangeable." They belong to two different module systems with different rules.
      • 
        
    • "Passing tests prove the code is correct." They prove it follows the rules you wrote. Missing rules (edges!) mean missing checks.
      • 
        
    • "assert.equal([1], [1]) should pass." In strict mode it compares objects with ===. Use deepEqual.
      • 
        
    • "assert.throws(f()) checks that f throws." It calls f first. Write assert.throws(() => f()).
      • 
        
    • "Seeing the right output printed means the function works." The referee checks returned values; prints are invisible to callers.
      •

    Words from this chapter
    
    
      
    
        
    module
    A file that keeps its names private and shares some of them through export. The comic's shop.
    
        
    export
    Puts a function, constant or class in the module's window, so other files can import it.
    
        
    named export
    export function withTax…: imported with braces, by its exact name. A module may have many.
    
        
    default export
    export default …: the module's main product, imported without braces under any name. At most one per module.
    
        
    import
    An order slip: which names, from which module. Goes at the top of the file.
    
        
    module specifier
    The address string after from, such as "./shops/prices.js".
    
        
    relative path
    An address starting with ./ (this folder) or ../ (the folder above).
    
        
    built-in module
    A module that comes with Node, such as node:fs, node:path, node:test.
    
        
    node: prefix
    Marks an address as a built-in module. Required for some, such as node:test.
    
        
    ES module (ESM)
    The modern, standard module system with import and export. .mjs files, or .js with "type": "module".
    
        
    CommonJS (CJS)
    Node's older module system with require and module.exports. .cjs files, or .js without "type": "module".
    
        
    package
    A folder of code with its own package.json, usually shared on npm.
    
        
    npm
    The package registry (the market) and the command-line tool that installs packages and runs scripts.
    
        
    package.json
    A project's description: name, version, "type", scripts and dependencies. The shopping list.
    
        
    dependency
    A package your program needs to run. Listed under "dependencies".
    
        
    devDependency
    A package only needed while developing, such as a formatter. Installed with --save-dev.
    
        
    node_modules
    The folder where installed packages live. Never edited by hand or committed.
    
        
    package-lock.json
    The receipt: the exact version of every installed package. Commit it.
    
        
    npm script
    A named command in package.json's "scripts", run with npm run name (or npm start / npm test).
    
        
    npx
    Runs a command provided by a package, from node_modules or downloaded for one run.
    
        
    .gitignore
    A file listing what Git should not save, such as node_modules/.
    
        
    error code
    A fixed label in square brackets on some errors, such as ERR_MODULE_NOT_FOUND.
    
        
    test
    Code that calls your code with a given input and checks the output against an expected value.
    
        
    assertion
    A check that throws an AssertionError if it fails, such as assert.equal(actual, expected).
    
        
    test runner
    The program that finds, runs and reports tests: node --test.
    
        
    suite
    A named group of tests, made with describe.
    
        
    diff
    A side-by-side list of differences: + actual, - expected.
    
        
    edge case
    An input at a border: empty, zero, negative, exactly on the limit, the wrong kind.
    
        
    red, green, refactor
    Write a failing test, make it pass, then tidy the code with the tests as a safety net.
    
        
    arrange, act, assert
    The three steps inside a tidy test: set up the input, call the code, compare.

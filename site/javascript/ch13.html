CHAPTER 13

PLAN IT, PACK IT

Picture: Kit, the stage manager in a pink hoodie and headset, points at a tilted plan card with four steps (in and out, examples, steps, small first) and at a flat cardboard box labelled with the text {"title": "Hamlet"}.

Two habits that every working programmer leans on. First: plan before you type, the way a cook plans the whole meal before lighting the stove, and write code that other humans can read. Second: pack your data flat for the road. The show is going on tour, and everything has to travel as plain text called JSON, then be put back together at the next theatre. About 110 minutes, with 24 hands-on checks.

  1. Plan before you type
  2. Code for humans
  3. Flat-pack: JSON.stringify
  4. Unpack: JSON.parse
  5. The tour report: plan it, pack it
  6. Boss level and recap

    CODE IS READ FAR MORE OFTEN THAN IT IS WRITTEN.
    
    
    "Ninja code" is the nickname for code that shows off: squeezed into one line, single-letter names, tricks the reader has to puzzle out. The computer doesn't care either way. The next human, often you in three weeks, cares a lot.
    
  
    

  
    
    12
    
    Two programs, same numbers, same answer. Which one tells you what 315 means?
    
    
    
      
    
        
    ✗ MYSTERY LETTERS
    
        bad_names.js
        
    
        
    
      
    
      
    
        
    ✓ NAMES THAT EXPLAIN
    
        good_names.js
        
    
        
    
      
    
    
    
    
      
      
    1. Values get nouns that say what they hold: seatsPerShow, unsoldSeats. Now line 4 reads as a sentence: seats per show, times shows, minus the unsold ones. That's the number of tickets sold.
      2. 
      
    2. Functions get verbs that say what they do: countWords, toWords, formatReport.
      3. 
      
    3. Yes-or-no values read as a question: isSoldOut, hasTickets.
      4. 
      
    4. Avoid vague names (data, temp, thing), puzzling abbreviations (nmSts) and names that lie (seats holding a price). Single letters are fine only in tiny, obvious places, like i in a short counting loop.
      5. 
    
    
  
    

  
    
  

  
    
    13
    
    A comment (// to the end of the line) is a note for humans; JavaScript skips it. Both programs print the same number. Only one set of comments is worth reading.
    
    
    
      
    
        
    ✗ SAYS WHATrepeats the code
    
        what_comments.js
        
    
        
    
      
    
      
    
        
    ✓ SAYS WHYwhat the code can't
    
        why_comments.js
        
    
        
    
      
    
    
    
    
      
      
    1. Says what: every comment repeats its line. "Subtract 2 from seats" tells you nothing that seats - 2 didn't. Worse, when someone changes the code and forgets the comment, it starts to lie.
      2. 
      
    2. Says why: one comment, and it answers the question a reader would really ask: why 2? Two seats are behind a pillar. That fact lives nowhere else in the code.
      3. 
      
    3. Rule of thumb: if a comment explains what the code does, try a better name or a small function instead. Save comments for why: reasons, warnings, surprises and decisions.
      4. 
    
    
  
    

  
    
  

  
    
    14
    
    A magic number is a bare number in the code whose meaning you have to guess. Give it a name once, at the top, and use the name everywhere.
    
    
    
      
    
        
    ✗ MAGIC NUMBERSwhat are 12 and 2?
    
        magic.js
        
    
        
    
      
    
      
    
        
    ✓ NAMED CONSTANTS
    
        constants.js
        
    
        
    
      
    
    
    
    
      
      
    1. Lines 1–2 of constants.js name the numbers. UPPER_SNAKE_CASE (capitals joined by underscores) is the usual style for settings that never change while the program runs.
      2. 
      
    2. One place to change. When the ticket price goes up, you edit line 1 and every calculation follows. In magic.js, you'd hunt for every 12, and hope none of them meant something else, like 12 rows.
      3. 
      
    3. Not every number is magic: 0 to start a sum and 1 to count up are clear on their own.
      4. 
    
    
  
    

  
    
  

  
    
    15
    
    DRY stands for "Don't Repeat Yourself": every fact should live in one place. It's a great rule, until it's taken too far.
    
    
    
      
    
        
    ✓ DRY IT UPthe same job, three times
    
        
    You've pasted the same five lines in three places, or the same number appears again and again. Make one function or one constant, and give it a good name. Many programmers wait for the third copy before they do it: by then you know what really repeats.
    
      
    
      
    
        
    ✗ TOO DRYdifferent jobs, squashed together
    
        
    Two pieces of code look alike today but mean different things: the price of a ticket and the size of a row are both 12. Forcing them into one function or one name with lots of options makes the code harder to read, and changing one breaks the other.
    
      
    
    
    
    
    
      
      
    The Professor says: Ask: "If this changes, should the other copy change too?" If yes, they're one fact: share it. If no, they only look alike: keep them apart. Clear beats short, every time.
    
    
    
  
    

  
    
    16
    
    JavaScript doesn't care about layout, so both of these run and print the same three lines. Your eyes care a lot.
    
    
    
      
    
        
    ✗ MIXED STYLES
    
        messy.js
        
    
        
    
      
    
      
    
        
    ✓ ONE STYLE
    
        tidy.js
        
    
        
    
      
    
    
    
    
      
      
    1. messy.js mixes three kinds of quotes, indents at random, puts a brace on its own line and leaves out every semicolon. Your eyes can't find where the loop starts and ends.
      2. 
      
    2. tidy.js picks one way and sticks to it: double quotes, two-space indents, braces on the same line, a semicolon after each statement. Which style you choose matters much less than using one style everywhere.
      3. 
    
    
    
    
      
    
        
        
    A FORMATTERfor example Prettier
    
        
    Rewrites your file's layout (spaces, quotes, line breaks) into one consistent style every time you save. It never changes what the program does. No more arguing about tabs.
    
      
    
      
    
        
        
    A LINTERfor example ESLint
    
        
    Reads your code without running it and points at likely mistakes: a variable that's never used, a name that was never declared, == where you meant ===. Like a friend proofreading over your shoulder.

    20
    
    JSON (JavaScript Object Notation, said "jay-son") is a way of writing data as plain text. JSON.stringify takes an object apart into a flat box of text. JSON.parse reads the text and builds a brand-new object from it. Anything too lively to flatten, like a function, is left on the floor.
    
    
    
      
      
    
    
    
    The real flat box, from pack.js in the next panel: 
    
    
    
    JSON IS TEXT, NOT AN OBJECT.
    
  
    

  
    
    21
    
    Pack the show object and look at what comes out. Compare lines 1 and 2 of the screen closely.
    
    pack.js
    
    
    
    
    
      
      
    1. Screen line 1 is Node showing you an object: names without quotes, strings in single quotes, spaces for reading.
      2. 
      
    2. Screen line 2 is a string: one long run of characters. Every key now wears double quotes, and there are no spaces. This is JSON.
      3. 
      
    3. Line 5: typeof proves it: object string. Line 6: the text is 57 characters long, and text.title is undefined, because a string has no title drawer. To read the title again, you'd have to unpack it with JSON.parse (Part 4).
      4. 
      
    4. To serialize is the general word for turning data into text (or bytes) that can be stored or sent. JSON.stringify serializes; JSON.parse does the reverse.
      5. 
    
    
  
    

  
    
    22
    
    JSON looks like a JavaScript object literal, but it is much stricter. Here is a valid piece of JSON, held in a string and unpacked.
    
    rules.js
    
    
    
    
    
      
      
    • ✓Allowed values: strings, numbers, true, false, null, arrays [ ] and objects { }, nested as deep as you like. That's the whole list.
      • 
      
    • ✗Double quotes only. Every key and every string: {"title": "Hamlet"}. Not {'title': 'Hamlet'}, and not {title: "Hamlet"}.
      • 
      
    • ✗No trailing commas. [1, 2, 3,] and {"a": 1,} are errors.
      • 
      
    • ✗No comments. Neither // nor /* */.
      • 
      
    • ✗No functions, no undefined, no NaN or Infinity, and no Dates: a date has to travel as a string.
      • 
    
    
    
    
      
      
    The Professor says: Why so strict? Because JSON is a shared language. Python, Go, Rust, C++, phones, databases and web servers can all read it. A small set of rules is easy for every one of them to get exactly right.
    
    
    
  
    

  
    
  

  
    
    23
    
    One long line is perfect for a computer and painful for a human. JSON.stringify takes a third argument: how many spaces to indent.
    
    pretty.js
    
    
    
    
    
      
      
    1. Line 3: JSON.stringify(show, null, 2). The middle argument is for advanced filtering (Chapter 28); null means "no filter". The 2 means "indent each level by two spaces".
      2. 
      
    2. Both outputs are the same data. The spaces and line breaks between values are ignored when the text is parsed. People call the indented version pretty-printed.
      3. 
      
    3. Use the indent for files people will read and edit. Leave it out for data sent over a network, where every character costs a little time.
      4.

    30
    
    
      Two values the packing machine refuses outright. These are TypeErrors from JSON.stringify: the wrong kind of thing to pack.
      
    circular.js
    
      
    
      
    
        
      
      1. A circle: Ada's partner is Bo, and Bo's partner is Ada. Packing Ada means packing Bo, which means packing Ada again, forever. JSON is a tree: each box can only contain boxes, never point back up.
        2. 
      
      2. V8's message even draws the loop: --> starting at object…, then property 'partner', then --- property 'partner' closes the circle. The fix: store something that names the other person instead, such as partner: "Bo".
        3. 
    
      
    bigint.js
    
      
    
      
    
      
      
      
      The TypeError critter says: Wrong kind of thing! A BigInt is a whole number of any size, written with an n on the end (more in Chapter 23). Written as a plain JSON number, it would be read back by JSON.parse on the other end as an ordinary number, and rounded (the notebook shows it), so I refuse instead. Pack it as text: pennies: boxOffice.pennies.toString().
      
    
      
  
      

  
      
  

  
      
    31
    
      Text from outside your program (a file, a form, the network) can be broken in ways you don't control. So JSON.parse of outside text gets the trapeze net from Chapter 12: try/catch.
      
    safe_parse.js
    
      
    
      
    
        
      
      1. Lines 2–3: try to parse. If it works, return hands the object back straight away and catch is skipped: { seats: 400 }.
        2. 
      
      2. Lines 4–6: if JSON.parse throws, the net catches it. We log error.message, so the problem isn't hidden, then hand back the fallback the caller chose.
        3. 
      
      3. The program never crashed: two bad texts, two messages, and every call got a usable value back.
        4. 
      
      4. Keep the try small: wrap only the risky call. A net around the whole program would also catch your own bugs and hide them (Boss 6).

      What you learned in Chapter 13
      
    
        
      
      • WRITE THE PLAN BEFORE YOU COOKUnderstand the input and the output, work out examples (with edge cases) by hand, write pseudocode, split it into small functions that each do one job, build a smaller version first, and test with a trace table.
        • 
      
      • CODE IS READ FAR MORE OFTEN THAN IT IS WRITTENNouns for values, verbs for functions, is/has for yes-or-no. Comments say why, not what. Magic numbers become named constants. Don't repeat a fact, but don't squash different jobs together. One consistent style; a formatter and a linter help.
        • 
      
      • JSON IS TEXT, NOT AN OBJECTJSON.stringify packs, JSON.parse unpacks into a brand-new object. Double quotes only, no trailing commas, no comments. Only strings, numbers, booleans, null, arrays and objects travel.

    Under the hood: what JSON really is, and what the two functions do
    
      
      
      A tiny grammar, written down twice
      
      
      JSON's whole grammar fits on one page. It is standardised as ECMA-404 and, for the internet, as RFC 8259. A JSON text is one value; a value is an object, an array, a string, a number, true, false or null. Spaces, tabs and line breaks are allowed between tokens and mean nothing. Strings must use double quotes, and a few characters inside them must be escaped with a backslash: \", \\, and control characters such as a line break, written \n. Any other character can appear as itself, or as \u followed by four hex digits.
      
      
      Numbers have no limits in JSON, but JavaScript does
      
      
      The grammar allows a number of any length, but JSON.parse turns every number into an ordinary JavaScript number, a 64-bit float (Chapter 3). A very long whole number, such as an ID with 19 digits, can come back slightly changed. Here the box office's 20-digit penny count from Panel 30 arrives as JSON text and is parsed:
      
      big_parse.js
      
      
      
      
      
      The last three digits came back as zeros: the nearest 64-bit float is all JSON.parse can build. That's one reason systems often send big IDs as strings, and why JSON.stringify refuses BigInts instead of quietly rounding them.
      
      
      What JSON.stringify does, step by step
      
      
      For each value it meets: strings are wrapped in double quotes and escaped; finite numbers are written as digits, while NaN and Infinity become null; booleans and null are written as words. If an object has a method called toJSON, that method is called first and its result is packed instead: Dates have one, which is why they become ISO strings (Chapter 28 writes your own). For objects, it walks the own, enumerable string keys in the normal key order (Chapter 10), skipping keys whose values are undefined, functions or symbols. In arrays, those become null. A Map or Set has no enumerable keys of its own, so it packs as {}: another silent loss. While packing, it keeps a list of the objects it's inside; meeting one of them again is the circular TypeError.
      
      
      What JSON.parse does
      
      
      It first turns its argument into a string (which is why undefined becomes the text "undefined"), then reads it from left to right with a strict parser. The moment a character breaks the grammar, it throws a SyntaxError with the position of that character, counted from 0 in UTF-16 code units, the same units as string indexes. Because it reads left to right, it reports the first place where the text can no longer be valid, which is often just after the real mistake. The result is always made of fresh plain objects and arrays, never shared with anything else.
      
      
      Pseudocode and trace tables are old tools
      
      
      Neither has an official format. Pseudocode is whatever plain language makes the steps clear to you and your team. Trace tables (also called desk checking) were how programmers tested programs on paper before computer time was cheap, and they're still the fastest way to see what a loop really does.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • package.json is JSON. Every Node project has one (Chapter 14), and so do many tools' settings files. A trailing comma in it stops npm with a parse error, exactly like the machine jams in Panel 29.
        • 
        
      • Web services talk JSON. When a web page asks a server for data, the answer is very often JSON text, and fetch has a helper that parses it for you (Chapter 28). Always treat it as outside text: it can be missing, broken or shaped differently than you expect.
        • 
        
      • Saving in the browser. localStorage only stores strings, so apps save with JSON.stringify and load with JSON.parse, wrapped in try/catch in case the saved text was damaged.
        • 
        
      • Relatives with comments. Some tools accept "JSON with comments" in their own settings files, and a separate format called JSON5 allows single quotes and trailing commas. Neither is JSON: JSON.parse rejects both.
        • 
        
      • Deep copies. JSON.parse(JSON.stringify(x)) was the classic way to deep-copy plain data. structuredClone (Chapter 10) is better: it keeps Dates, Maps and Sets, and handles circles.
        • 
        
      • Style guides. Teams write down their style choices, or adopt a published guide, then let tools enforce them. Prettier's default style uses two-space indents, double quotes, semicolons and lines up to 80 characters, close to what this book uses.
        • 
        
      • Code review. In most teams, nobody's code goes in until a teammate has read it. Clear names and "why" comments are what make that review quick.
        • 
        
      • Planning at work. Bigger problems get bigger plans: a short written plan (often called a design doc or spec) that names inputs, outputs, examples and edge cases before anyone writes code.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "Planning is slower than just coding." For anything bigger than a few lines, fixing a wrong program costs more than thinking first, as Panel 2 showed.
        • 
        
      • "More comments are always better." Comments that repeat the code waste time and drift out of date. Write fewer, better ones.
        • 
        
      • "Short code is better code." Clear code is better code. A one-liner that takes five minutes to decode is slower than five lines you read at once.
        • 
        
      • "JSON is a JavaScript object." JSON is text. It describes objects, but until you parse it, it's a string.
        • 
        
      • "Any JavaScript object literal is valid JSON." Unquoted keys, single quotes, trailing commas, comments, undefined and functions are all fine in JavaScript and forbidden in JSON. (The other way round does hold: valid JSON is a valid JavaScript expression.)
        • 
        
      • "JSON.stringify warns you when it drops something." It drops undefined, functions and symbols silently, and turns NaN into null silently.
        • 
        
      • "Parsing gives my Date back." It gives back a string. Turn it into a Date yourself if you need one.
        • 
        
      • "The error position is where the mistake is." It's where the parser noticed. Look just before it, too.
        • 
        
      • "Wrap everything in try/catch to be safe." Wrap the risky outside input. A huge net hides your own bugs.

    Words from this chapter
    
      
      
      
        
      input / output
      What a program or function is given, and what it hands back.
      
        
      example (test case)
      An input with the output you expect, worked out by hand before coding.
      
        
      edge case
      An unusual input at the limit of what's allowed: empty text, zero, a tie.
      
        
      pseudocode
      The steps of a solution written in plain language, for humans.
      
        
      decompose
      Split a big problem into small functions that each do one job.
      
        
      trace table
      A table with a column per value and a row per step, filled in by hand to test code.
      
        
      ninja code
      Nickname for code that shows off with tricks and tiny names at the cost of clarity.
      
        
      comment
      A note for humans that JavaScript skips: // to the end of the line, or /* … */.
      
        
      magic number
      A bare number in code whose meaning you have to guess.
      
        
      named constant
      A const with a clear name for a fixed value, often in UPPER_SNAKE_CASE.
      
        
      DRY
      "Don't Repeat Yourself": keep each fact in one place.
      
        
      formatter
      A tool that rewrites code layout into one consistent style (for example Prettier).
      
        
      linter
      A tool that reads code without running it and warns about likely mistakes (for example ESLint).
      
        
      JSON
      JavaScript Object Notation: a strict text format for data that almost every language can read and write.
      
        
      serialize
      Turn data into text (or bytes) that can be saved or sent. JSON.stringify serializes.
      
        
      parse
      Read text and build the structure it describes. JSON.parse parses JSON.
      
        
      JSON.stringify(value, null, indent)
      Packs a value into JSON text; the optional indent pretty-prints it.
      
        
      JSON.parse(text)
      Unpacks JSON text into new objects, arrays and values; throws a SyntaxError on invalid text.
      
        
      pretty-print
      Write data with line breaks and indentation so people can read it.
      
        
      round trip
      Packing data into text and unpacking it again.
      
        
      ISO date string
      A date written like 2026-11-08T19:30:00.000Z; the Z means UTC.
      
        
      circular structure
      Objects that refer back to each other in a loop; they can't be written as JSON.
      
        
      BigInt
      A whole number of any size, written with n at the end, such as 10n; JSON can't hold it.
      
        
      fallback
      A safe value to use instead when the real one can't be had.

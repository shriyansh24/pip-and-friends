CHAPTER 10

DRAWERS AND ADDRESSES

Picture: Kit, the stage manager in a pink hoodie and headset, points at a blue filing cabinet with three drawers labelled name, role and lines, holding "Ada", "Juliet" and 42. Next to it, a little house with the address #A1 on its wall, and a yellow sticky note above it that has only the address #A1 written on it.

An object is a filing cabinet: one thing with many labelled drawers. Today you build cabinets, open their drawers two different ways, and meet the three crashes every JavaScript programmer knows by heart. Then the big surprise: a variable never holds the cabinet itself, only its address. That one fact explains why changing a "copy" can change the original. About 110 minutes, with 24 hands-on checks.

  1. The filing cabinet: objects, properties and methods
  2. Dot or sticky note: brackets, keys and their order
  3. Records, and the three classic crashes
  4. Houses with addresses: references
  5. Photocopies: shallow, deep and the garbage truck
  6. Boss level and recap

In which order do the drawers come out? Mostly in the order you added them, with one twist.

    order.js
    

    

    
    
      
  1. The rule: labels that look like whole numbers (0, 1, 2, … written plainly) come first, smallest to largest. All other text labels follow, in the order they were added.
    2. 
      
  2. Line 2: so { b, 2, a, 1 } lists as [ '1', '2', 'b', 'a' ]. Node prints those number labels in quotes (line 3's output) to remind you they're strings.
    3. 
      
  3. Line 5: "9" and "10" count as numbers and are sorted as numbers (9 before 10). "-1" and "01" don't count (no minus signs, no leading zeros), so they stay in insertion order after them.
    4. 
    

    

      
      
Kit says: Practical advice: don't write code that depends on the order of a cabinet's drawers. If order matters, keep an array.

          What you learned in Chapter 10
          
    
            
      
          • ONE THING, MANY LABELLED DRAWERSAn object { key: value } groups facts under labels. Read with obj.key; add or change with =; remove with delete. A missing drawer reads as undefined. Methods are functions in drawers; call them with ().
            • 
      
          • DOT FOR LABELS YOU KNOW, BRACKETS FOR LABELS ON A NOTEobj[key] when the label is in a variable or has a dash. Keys are strings; Object.hasOwn asks about this cabinet's own drawers; Object.keys, values and entries list them, number-like keys first.
            • 
      
          • READ, WRITE, CALL: THE GHOST HAS NO DRAWERSCannot read properties of undefined (reading 'x'), Cannot set properties of undefined (setting 'x') and o.go is not a function all mean one step of the chain was undefined (or, in the same messages with null, was null).
            • 
      
          • COPY A NOTE, COPY THE ADDRESS, NOT THE HOUSEPrimitives are copied by value; objects and arrays are shared by reference. === compares addresses. A function given an object can change it. const glues the note, not the house.
            •

    Under the hood: references, the order rule and the garbage collector
    
          
      
          What a variable really stores
          
      
          Every JavaScript value is either a primitive (number, string, boolean, undefined, null, bigint, symbol) or an object (plain objects, arrays, functions, dates and everything else). A variable holding an object holds a reference to it: in the comic's words, an address. The specification never says how an engine stores that reference, and you never see the address as a number; the "O1" labels in the tracers are just names for the picture.
          
      
          "Pass by reference"? Not quite
          
      
          JavaScript always passes arguments by value. For an object, the value that gets copied is the reference. That's why a function can change your object (it has the address) but can't make your variable point somewhere else (it only has a copy of the note): panels 29 and 30. Some people call this call by sharing. Languages with true pass-by-reference, such as C++ with & parameters, can move the caller's note; JavaScript can't.
          
      
          The order rule, exactly
          
      
          For an ordinary object, the specification's OrdinaryOwnPropertyKeys lists own keys in three groups: first every key that is an array index (a canonical whole-number string from "0" up to 4,294,967,294), in ascending numeric order; then the remaining string keys in the order they were created; then symbol keys in the order they were created. Object.keys, Object.entries, for...in, spread and JSON.stringify all follow this order (Object.keys leaves out symbols). "01", "-1" and "1.5" aren't canonical array indexes, so they keep insertion order.
          
      
          Why [Object]?
          
      
          console.log in Node uses util.inspect, which by default prints nested objects only two levels below the top, and replaces deeper ones with [Object] (or [Array]). Ask for more with console.dir(x, { depth: null }), or print the data as text with JSON.stringify (Chapter 13):
          
      nested_full.js
      
          
      
          
      
          How shallow is spread?
          
      
          { ...o } and Object.assign({}, o) copy each of o's own, enumerable properties (string and symbol keys) into the new object, one level deep, reading each value once. Getters on the source are run and their results stored. Inherited drawers aren't copied. Arrays spread with [...a] walk the array's items instead.
          
      
          What structuredClone can copy
          
      
          It uses the structured clone algorithm, the same one browsers use to send data between workers. It copies primitives (except symbols), plain objects, arrays, Date, RegExp, Map, Set, typed arrays, Error objects and more, nested in any way, and it even keeps loops intact (an object that contains itself is cloned as a clone that contains itself). It throws DataCloneError for functions, symbols as values, DOM nodes and a few others. It also drops things that aren't plain data: the copy of a class instance (Chapter 18) is a plain object without its methods, and getters become ordinary values.
          
      
          The garbage collector
          
      
          Engines find garbage by reachability: starting from the roots (the variables in scope right now, the global object, the current call stack), they follow every reference, and anything never reached is garbage. That's why a ring of objects pointing only at each other is still collected once nothing outside reaches the ring. V8, the engine inside Node and Chrome, uses a generational collector: most objects die young, so it checks new objects often and old ones rarely. You can't trigger it or predict when it runs, and you don't need to.
          
    
          
  
          

  
          
    In real programs
    
          
      
            
        
          • Arrays of records are everywhere. A list of users from a server, rows from a database or songs in a playlist arrive as arrays of objects, and most code filters, maps and sorts them (Chapter 9's belt, applied to cabinets).
            • 
        
          • Configuration objects. Many functions take one "options" object instead of many arguments: console.dir(x, { depth: null }) is one, and so is almost every library call you'll make. Labels beat argument positions: { depth: null } explains itself.
            • 
        
          • Immutable updates. Front-end frameworks such as React decide what to redraw by checking whether an object is a new house (!==), not by comparing contents. So the style there is never to change state in place, but to build a new object with spread: { ...user, name: "Bo" }. Panel 30's spot_mutate.js bug is the classic way to break that rule.
            • 
        
          • Linters help. ESLint's dot-notation rule suggests obj.key over obj["key"] when a dot works, and no-param-reassign (with its props option) flags functions that change the objects passed to them.
            • 
        
          • Defensive copies. A function that keeps an object it was given, such as a cache or a settings store, often stores structuredClone(input), so the caller can't change the stored copy later by accident.
            • 
        
          • Deep equality. Since === compares addresses, test frameworks provide content comparisons: Node's built-in assert.deepStrictEqual, which the testing chapters use.

    Common wrong ideas
    
          
      
            
        
          • "b = a copies the object." It copies the address. One house, two notes.
            • 
        
          • "const objects can't change." const stops the note being moved. The house can still be rearranged.
            • 
        
          • "Two objects with the same contents are equal." Not to === or ==. They compare identity.
            • 
        
          • "obj.key uses the variable key." The dot uses the literal label key. Use obj[key].
            • 
        
          • "Setting a property to undefined deletes it." The drawer stays, empty; in and Object.hasOwn still say true. Use delete.
            • 
        
          • "Object keys can be numbers." They're stored as strings (or symbols). obj[1] and obj["1"] are the same drawer.
            • 
        
          • "Objects remember insertion order." Mostly, except that number-like keys jump to the front in ascending order.
            • 
        
          • "Spread makes a full copy." Only the top level. Inner objects are shared.
            • 
        
          • "structuredClone copies anything." Not functions, and class instances lose their methods.
            • 
        
          • "Reading a missing property crashes." Reading one gives undefined. Reading through one (a.missing.x) crashes.
            • 
        
          • "delete frees memory." It removes a drawer. Memory is freed by the garbage collector when an object becomes unreachable.
            • 
        
          • "A function can't change my variables." It can't move your notes, but it can change any object you hand it.

    Words from this chapter
    
          
      
          
        
          object
          A collection of labelled values. Pictured as a filing cabinet.
          
        
          property
          One drawer: a key and its value.
          
        
          key
          A drawer's label. Always a string (or a symbol).
          
        
          value
          What's in a drawer. Any kind of value, including another object or a function.
          
        
          object literal
          An object written out directly with { key: value, … }.
          
        
          dot notation
          obj.key: open the drawer whose label is written right there.
          
        
          bracket notation
          obj[expr]: work out the label first, then open that drawer.
          
        
          shorthand property
          { name }, meaning { name: name }.
          
        
          computed key
          { [expr]: value }: a label worked out while building the object.
          
        
          method
          A function stored in a property. Called with obj.method().
          
        
          nested object
          An object stored inside another object's property.
          
        
          record
          One object describing one thing, usually one of many with the same keys.
          
        
          delete
          The operator that removes a property.
          
        
          in
          "key" in obj: is there such a property, own or inherited?
          
        
          Object.hasOwn
          Is there such a property in this object itself?
          
        
          inherited property
          A property an object gets from a shared parent object, such as toString (Chapter 18).
          
        
          Object.keys / values / entries
          Arrays of an object's own keys, values, or [key, value] pairs.
          
        
          for...in
          A loop over an object's keys (including inherited enumerable ones).
          
        
          primitive
          A simple value: number, string, boolean, undefined, null, bigint or symbol. Copied by value.
          
        
          reference
          What a variable holds for an object: the "address" of the house.
          
        
          alias
          A second name for the same object.
          
        
          mutate
          To change an object in place (its drawers), rather than making a new one.
          
        
          identity
          Which object something is. === on objects compares identity.
          
        
          spread
          ... inside { } or [ ]: copy the drawers or items of another object or array into this one.
          
        
          Object.assign
          Copies the properties of one or more objects into a target object, and returns the target.
          
        
          shallow copy
          A new top-level object whose inner objects are shared with the original.
          
        
          deep copy
          A copy in which every nested object is copied too.
          
        
          structuredClone
          The built-in deep copy. Throws DataCloneError for functions.
          
        
          DOMException
          An error type from the web platform; DataCloneError is one of its names.
          
        
          garbage collector
          The part of the engine that reclaims the memory of objects nothing can reach any more.
          
        
          unreachable
          No variable, and no reachable object, leads to it.

A thread is one line of work a computer follows, one step after another. JavaScript gives your code one thread, so it can only do one thing at a time. The call stack is the list of functions running right now, each one waiting for the one it called (Chapter 7).

PART 3 · TICKETS THAT ARRIVE ONE BY ONEasync generators, for await...of, Array.fromAsync and top-level await


  

    15
    
Sometimes results don't arrive all at once: they trickle in, like orders from a ticket printer that prints one ticket whenever the next dish is ready.

    

      
GENERATORfunction* (Chapter 20)
Hands out values one at a time with yield, and a for...of loop collects them. Each value is ready at once.

      
ASYNC GENERATORasync function*
Also hands out values with yield, but may await before each one. A for await...of loop waits for every value.

    

    

      
      
Kit says: Long job? I'll call you back when it's done. A long list of jobs? I'll call you back once for each one.

    

  


  

    16
    
An async generator (line 1, async function*) and a loop that waits for each ticket (line 9, for await).

    ticket_printer.js
    

    

    
    
      
  1. The printer is lazy. It doesn't start the next dish until the loop asks for the next ticket. So the pie (10 ms) comes after the soup (30 ms), and everything takes 30 + 10 + 20 ms: this is one by one.
    2. 
      
  2. Each round: for await asks for a ticket, the generator runs until its next yield (waiting on line 3 on the way), and the loop body runs with that dish.
    3. 
      
  3. That laziness is the point: a stream of messages, the pages of a long search result, or the lines of a huge file, handled one at a time as they arrive, without waiting for them all.

PART 4 · THE TWO SPIKESThe call stack, the VIP spike for microtasks and the normal spike for timers


  

    20
    
Now the rule that decides which ticket the chef takes next. It's the heart of the chapter, so it gets its own panel.

    

      
      
The chef says: My rule never changes. Learn it and you can predict any kitchen.

    

    
    
      
  • Finish the stove. Whatever is cooking (the script, or one callback) runs to the end. Nobody interrupts it.
    • 
      
  • Empty the VIP spike, completely. Every microtask, oldest first, including new VIP tickets added while emptying it.
    • 
      
  • Take ONE ticket from the normal spike (a due timer) and cook it. Then go back to step 2.
    • 
    

    
A microtask is a small job that must happen as soon as the current code finishes: promise callbacks (.then, .catch, .finally), the rest of an async function after its await, and functions passed to queueMicrotask. A task (sometimes called a macrotask) is a bigger unit of work, such as a timer callback. The event loop is the chef walking this circuit for as long as there are tickets or ovens running.

    37
    
        What you learned in Chapter 25
        
    
          
      
        • ASYNC ALWAYS HANDS YOU A PAGERAn async function runs now, up to its first await, and returns a promise: return fulfils it, throw rejects it. await unwraps a promise or throws its error, so try/catch/finally work around it. Inside a try, write return await.
          • 
      
        • START THEM ALL, THEN AWAIT THEM ALLawait in a loop is one by one (the delays add up). Starting jobs first and using Promise.all is parallel (the slowest decides). Await in sequence only when a step needs the previous answer. forEach never waits: use for...of or Promise.all(arr.map(…)). Don't mix .then and await in one statement.
          • 
      
        • ONE TICKET AT A TIMEasync function* yields values that arrive over time; for await...of waits for each, and Array.fromAsync collects them. Top-level await works only in ES modules.
          • 
      
        • EMPTY THE VIP SPIKE, THEN ONE NORMAL TICKETThe stove (call stack) finishes, then every microtask (promise callbacks, the rest after await, queueMicrotask), then one timer, and the VIP spike again. await puts the rest of the function at the back of the VIP spike. A 0 ms timer still waits.
          • 
      
        • STOVE, NOTE, VIP, TIMERS, CHECKNode adds process.nextTick (before the VIP spike in scripts; after it at an ES module's top level) and setImmediate (the check phase). Phases: timers, pending, poll, check, close. setTimeout(0) versus setImmediate varies in the main script, but inside an I/O callback the immediate always wins.
          • 
      
        • NOTHING INTERRUPTS THE STOVECPU-heavy work blocks every timer and callback: chunk it with setImmediate (or use a worker). Cancel waiting jobs with AbortController and AbortSignal.timeout.
          •

    Under the hood: what await really does, and Node's loop in detail
    
        
      
        await, unfolded
        
      
        When an async function reaches await x, the engine turns x into a promise (if it isn't one already), subscribes to it, saves the function's paused state (its local variables and where it stopped), and returns to whoever called it. When that promise settles, a job goes on the microtask queue; running that job puts the function back on the call stack exactly where it stopped, with the value (or the error, thrown at the await). That's why every await, even await null, costs at least one trip through the microtask queue, and why the rest of the function lands behind tickets already waiting (trace_spikes.js). Modern engines take a shortcut when x is already a native promise, so await uses fewer microtask turns than it did before 2019; code shouldn't depend on the exact count.
        
      
        Why return await matters only inside try
        
      
        Returning a promise from an async function makes the function's own promise follow it. The function itself has already finished, so its try/catch no longer exists by the time the inner promise rejects. return await p keeps the function paused inside the try until p settles. Outside a try, both forms give the caller the same result. Stack traces also tend to be more complete with await, because V8's "async stack traces" follow awaited calls.
        
      
        The loop is libuv
        
      
        Node's event loop is provided by a C library called libuv. Each round runs the phases in order: timers (due setTimeout/setInterval callbacks), pending callbacks (some system callbacks deferred from the previous round, such as certain network errors), idle/prepare (internal), poll (wait for, and run, I/O callbacks; how long it waits depends on the nearest timer and on whether immediates are queued), check (setImmediate) and close callbacks (for example a socket's 'close' after destroy()). After every single callback, Node drains the process.nextTick queue and then the microtask queue, repeating until both are empty. When no timers, handles or requests remain, the loop ends and the process exits.
        
      
        Timers are "at least", never "exactly"
        
      
        setTimeout(fn, ms) means "not before ms milliseconds". Node turns 0 (and anything below 1) into 1. While writing this chapter, an early version of Boss 1 printed music and eat salad in either order on different runs, though their due times looked 15 ms apart. That run wasn't kept, so this page can't show it, and the cause is unproven. Our best guess: Node measures timers from a loop clock that is only refreshed at certain moments, so timers set at slightly different moments can drift. Whatever the cause, don't rely on near-ties: keep timers well apart, or don't depend on their order at all.
        
      
        Browsers
        
      
        Browsers follow the HTML standard's event loop: one task (a timer, a click, a network event), then all microtasks, then possibly a rendering step (style, layout, paint, requestAnimationFrame callbacks), then the next task. There's no process.nextTick and no standard setImmediate. Nested timers deeper than five levels are clamped to at least 4 ms. A long task or a never-ending microtask chain freezes rendering, which is why chunking and workers matter so much in pages.
        
      
        Why nextTick exists at all
        
      
        process.nextTick is older than promises in Node. Node's guide gives its uses: letting a caller attach event listeners before an event fires, or reporting an error asynchronously but before anything else happens. Recursive nextTick calls can starve I/O just like the endless VIP spike in panel 23, and the guide recommends setImmediate as "easier to reason about".
        
    
        
  
        

  
        
    In real programs
    
        
      
          
        
        • Parallel requests. A web page loading a user, their orders and their settings uses Promise.all over three fetch calls; a server does the same with database queries. Many sequential awaits in a row are one of the most common reasons an app feels slow.
          • 
        
        • Too much parallelism. Starting 10,000 requests at once can overwhelm a server or hit rate limits. Real programs often process a big list in batches of, say, 10 at a time, with a loop around Promise.all or a small library that limits how many run together.
          • 
        
        • Async iteration everywhere. Node streams can be read with for await (const chunk of stream); readline gives the lines of a file the same way; many APIs page through results with async generators. Chapter 27 uses streams.
          • 
        
        • Linters catch the classics. ESLint's built-in no-await-in-loop rule flags await inside loops (to make you ask "could these run in parallel?"), and TypeScript-ESLint's no-misused-promises and no-floating-promises catch async callbacks passed to forEach and pagers nobody awaits.
          • 
        
        • Cancellation. fetch(url, { signal }), fs.readFile(path, { signal }), timers/promises, event listeners (addEventListener(type, fn, { signal }) removes the listener on abort) and test runners all accept signals. AbortSignal.any([a, b]) combines several.
          • 
        
        • Keeping servers responsive. Node's guide "Don't Block the Event Loop" lists the usual culprits: huge JSON parsing, slow regular expressions, synchronous file APIs (readFileSync) inside request handlers, and heavy crypto. The fixes are chunking, the asynchronous versions of APIs, and worker threads.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "An async function runs in the background." It runs on the same thread, right away, until its first await.
          • 
        
        • "await blocks the whole program." It pauses only its own function; the chef cooks other tickets meanwhile.
          • 
        
        • "Making a function async makes it faster." Only the waiting can overlap. CPU work takes as long as ever, and blocks just the same.
          • 
        
        • "Promise.all runs the jobs in parallel." The jobs started when you called them; all only waits for them together.
          • 
        
        • "forEach waits for async callbacks." Never. Neither do filter, some or reduce with async callbacks; they see pending promises.
          • 
        
        • "setTimeout(f, 0) runs before Promise.then." Microtasks always go first.
          • 
        
        • "0 ms means immediately." At least 1 ms in Node, and only after the stove and the VIP spike.
          • 
        
        • "setImmediate runs immediately, and nextTick on the next round." Back to front: nextTick is sooner.
          • 
        
        • "setTimeout(0) always beats setImmediate." Not guaranteed in the main script, and always the other way round inside I/O callbacks.
          • 
        
        • "nextTick always runs before promises." Not at the top level of an ES module (panel 27).
          • 
        
        • "Aborting stops the work." It rejects the waiting and lets well-behaved APIs stop. A function that ignores its signal keeps going.
          • 
        
        • "return p and return await p are the same." Not inside try.

    Words from this chapter
    
        
      
        
        
        thread
        One line of work a computer follows, step by step. JavaScript runs your code on one.
        
        
        call stack
        The functions running right now, each waiting for the one it called. The comic's stove.
        
        
        async function
        A function that always returns a promise; it may use await inside.
        
        
        await
        Pauses the async function until a promise settles; gives its value, or throws its error.
        
        
        return await
        Waiting for a promise before returning it, so a surrounding try can catch its rejection.
        
        
        sequential
        One after another: each job starts when the previous one is done.
        
        
        parallel (waiting)
        Several jobs started together, so their waiting overlaps.
        
        
        async generator
        async function*: yields values that may take time to arrive.
        
        
        for await...of
        A loop that awaits each value from an async iterable (or an array of promises).
        
        
        async iterable
        Something for await can loop over, such as an async generator or a stream.
        
        
        Symbol.asyncIterator
        The key of the method for await looks for: the async twin of Symbol.iterator.
        
        
        Array.fromAsync
        Collects every value of an async iterable into an array, one by one.
        
        
        top-level await
        await outside any function, allowed only in ES modules.
        
        
        event loop
        The chef's round: run what's on the stove, then the queues, again and again.
        
        
        microtask
        A small follow-up job: promise callbacks, the rest after await, queueMicrotask. The VIP spike.
        
        
        microtask queue
        The queue of microtasks, emptied completely after each piece of code.
        
        
        task (macrotask)
        A larger unit of work, such as a timer callback. The normal spike.
        
        
        queueMicrotask(fn)
        Puts fn on the microtask queue directly.
        
        
        process.nextTick(fn)
        Node only: runs fn as soon as the current operation finishes. The sticky note.
        
        
        setImmediate(fn)
        Node only: runs fn in the check phase, right after poll. The check window.
        
        
        phase
        One stop in Node's loop: timers, pending callbacks, poll, check, close callbacks.
        
        
        poll phase
        Where Node waits for and runs file and network callbacks.
        
        
        libuv
        The C library that provides Node's event loop and talks to the operating system.
        
        
        starving the loop
        Endless microtasks or sticky notes that never let timers and I/O run.
        
        
        CPU-bound
        Work that keeps the processor busy, rather than waiting.
        
        
        blocking
        Keeping the stove busy so long that nothing else can run.
        
        
        chunking
        Splitting long work into pieces, letting other callbacks run in between.
        
        
        worker
        A second thread that can run JavaScript alongside the main one.
        
        
        AbortController
        A remote control with abort(); its signal is passed to jobs that can be cancelled.
        
        
        AbortSignal
        The receiver: aborted, reason, and an "abort" event.
        
        
        AbortSignal.timeout(ms)
        A signal that aborts itself after ms, with a TimeoutError.
        
        
        AbortError
        The error name for an operation that was cancelled.

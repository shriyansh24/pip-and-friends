SIMULATORS AND ROBOT ARMS

Pilots learn in a flight simulator, where crashing costs nothing and the reset button is always there. Tests are your simulator: today you learn to crash your code on purpose, safely, a hundred times a day, with hooks, sharper checks, stopwatches for async code and stunt doubles for things you can't control. Then you meet the workshop robot, Node itself: its name badge (process), its filing arm (fs), its telephone (http) and its hose (streams). About 150 minutes, with 28 hands-on checks.

Before every lesson the simulator is reset to a fresh plane; after it, someone tidies up. Test hooks do this for you, so each test starts from the same clean state.

    

      
beforebefore(fn)
Once, before the first test of the group. Power on the simulator: open a database, start a server.

      
beforeEachbeforeEach(fn)
Before every test. A fresh plane: new objects, an empty folder.

      
afterEachafterEach(fn)
After every test, even a failed one. Tidy the cockpit: delete temp files, restore mocks.

    11
    
Juno's rulebook for tests worth keeping.

    
    
      
  1. One reason to fail. A test named "spots low fuel" should fail only when low-fuel spotting breaks.
    2. 
      
  2. Independent. Tests must pass in any order, alone or together. Shared state between them is the most common cause of mystery failures (the boss level has one).
    3. 
      
  3. Repeatable. Same code, same result, every run, on every machine: no real clock, no real randomness, no internet (Part 3 shows how).
    4. 
      
  4. Fast. A whole file should run in well under a second, so you run it all the time.
    5. 
      
  5. Checks behaviour, not insides. Test what the function returns or does, not which helper it happens to call, so you can rewrite the insides freely.
    6. 
      
  6. Sees red at least once. Break the code on purpose and watch the test fail. A test you've never seen fail might not be checking anything (Chapter 14's never-failing test).

    14
    
Films use stunt doubles for the dangerous scenes. Tests use test doubles: stand-ins for the parts you can't control or don't want to really run (the radio, the clock, the dice, the network).

    

      
SPYmock.fn()
Records every call: how many, with which arguments, what it returned. "Did the radio get called with Puffin?"

      
STUBmock.fn(() => 0.1)
Gives a fixed answer. "The dice always roll low."

      
MOCKED METHODt.mock.method(obj, 'name', fn)
Swaps a method on a real object for a double, and puts the real one back after the test.

      
FAKE TIMEt.mock.timers
A pretend clock: one minute passes the moment you say tick(60_000).

    

    
People say "mock" for all of these. The Node docs call the whole toolbox mock, and so do we.

    
Four cards: spy, records every call; stub, gives a fixed answer; mocked method, swaps a method on a real object and restores it; fake time, a pretend clock you move forward.

    Node's built-in runner is one referee among several. Most projects you'll read use one of these, with the same ideas and slightly different words.
    
    
    
      
    Jestnpm package
    Long the most common choice. describe, it and beforeEach work like ours; checks read expect(x).toBe(3) and toEqual (deep). Mocks are jest.fn().
    
      
    Vitestnpm package
    Very close to Jest's style, built for projects that use the Vite bundler (Chapter 26). Mocks are vi.fn(); fake time is vi.useFakeTimers().

    A pretend browser page inside Node, so tests for DOM code (Chapter 15) can run without a real browser. Jest and Vitest can switch it on for you.

    28
    
    Every program gets two output pipes. Standard output (stdout, console.log) is for the results. Standard error (stderr, console.error) is for warnings and problems. On screen they look alike. The difference shows when you redirect.
    
    streams_out.js
    
    
    
    
    
    The shell's > sends stdout into a file. The warning still appears on screen, because it travels on the other pipe, and the file holds only the results. That's why a tool's error messages go to console.error: someone saving your output to a file still sees the warnings, and the file stays clean. (This page draws stderr lines in the error style.)

    readFile loads the whole file into memory at once. Fine for a config file; a disaster for a 20 GB log. A stream is the robot's hose: data flows through in chunks, and only one chunk needs to fit in memory at a time.
    
    big_count.js
    
    
    
    
    
    The program writes a 1.1 MB log, then reads it two ways. createReadStream delivers it in 17 chunks of at most 64 KiB (65,536 bytes: 16 full ones and a smaller last one), and for await (Chapter 25) takes them one by one. Wrapped in readline, the same stream comes out as lines. Neither loop ever holds the whole file, so the same code would count the lines of a file far bigger than the computer's memory.
    
  
    

  
    
  

  
    
    36
    
    Chunks are Buffers: fixed-size boxes of bytes, each a number from 0 to 255. Text is just one way to read them.
    
    buffer_basics.js
    
    
    
    
    
    Four characters, six bytes: in UTF-8 the plane ✈ takes three bytes (e2 9c 88), while H, i and the space take one each (Chapter 22's emoji library). Spreading the Buffer shows the bytes as ordinary numbers. Base64 spells any bytes using only safe letters, digits, + and /, which is how images and keys travel inside text.

    Streams connect like hoses: a readable stream (data comes out), a transform (data goes in, changed data comes out), a writable stream (data goes in). pipeline joins them and tells you when the water stops.
    
    
    
    
    Picture: the robot with a dashed ring around the hose marked stream at its feet.
    
    pipeline.js

    Under the hood: how node --test runs, how mocks swap, and what fs really does
    
      
      
      One process per file
      
      
      Given file names, node --test runs exactly those. Given none, it searches the current folder (skipping node_modules) for files whose names match patterns such as *.test.js, *-test.js, *_test.js, test.js, and anything inside a folder called test. Each test file runs in its own child process, so a crash or a leaked global in one file can't break another. The children report back to the parent in a structured format, and the parent's reporter turns that into the spec tree, dots or TAP. That's also why a test's console.log lines appear before the report under --test: the parent collects the child's output as it comes and prints the summary at the end.
      
      
      When is a test finished?
      
      
      A test function is finished when it returns, or, if it returns a promise, when that promise settles. That's the whole rule behind panel 13: a non-async function that starts a promise and returns nothing is finished at once. Afterwards, Node watches for errors and unhandled rejections that it can trace back to a test that already ended, and reports them as "asynchronous activity after the test ended". A test function can also accept a second parameter, done, a callback style from older libraries; don't mix it with promises.
      
      
      What mock.method does
      
      
      t.mock.method(obj, 'name', impl) remembers obj.name, replaces it with a spy that calls impl, and registers a clean-up step. When the test ends, the test's mock tracker restores every method it swapped. The top-level mock object is a tracker too, but it belongs to no test, so nothing restores it until you call mock.restoreAll() (or mock.reset()). The panel 17 tracer is literally this: one property of the Math object pointing at a different function for a while.
      
      
      Mock timers
      
      
      mock.timers.enable({ apis: [...] }) replaces setTimeout, setInterval, setImmediate and/or Date with versions driven by an internal counter. tick(ms) moves the counter forward and runs, in order, every callback that became due. runAll() runs everything pending. Node 22 still printed an ExperimentalWarning for this API; Node 26 doesn't.
      
      
      fs, libuv and the thread pool
      
      
      Your JavaScript runs on one thread, but readFile doesn't block it: Node's C library libuv (Chapter 25) hands file operations to a small pool of helper threads (four by default) and queues a callback when each finishes. The fs/promises functions wrap that callback in a promise. The …Sync versions skip all of that and wait on the main thread. Errors from the system come back as codes such as ENOENT (no such entry), EACCES (permission denied), EISDIR (that's a folder) and EEXIST (already exists).
      
      
      Streams and backpressure, briefly
      
      
      A readable file stream reads 64 KiB at a time by default (its highWaterMark). If the writable end is slower than the readable end, chunks would pile up in memory; pipeline (and .pipe) handle this backpressure by pausing the reader until the writer catches up. That's beyond this book, but it's why you should connect streams with pipeline rather than copying chunks by hand.
      
    
      
  
      

  
      
    In real programs: test scripts, CI, CLIs and config
    
      
      
        
        
      • npm test. Projects put the test command in package.json, for example "scripts": { "test": "node --test" }, so everyone (and every build server) runs the same thing with npm test or node --run test (Chapter 26).
        • 
        
      • Continuous integration (CI). Services such as GitHub Actions run the tests on every push and look only at the exit code: 0 lets the change in, anything else blocks it. That's why a test runner must exit non-zero on failure, and why your own tools should too.
        • 
        
      • Watch mode. node --test --watch re-runs the tests whenever a file changes; the TDD loop at full speed.
        • 
        
      • Argument parsing. Real tools rarely hand-split argv. Node has parseArgs in node:util for flags like --seat 14C and -v; npm packages such as commander and yargs add help screens.
        • 
        
      • Config. A common pattern: defaults in code, overridden by a JSON config file, overridden by environment variables, overridden by command-line flags. The fleet tool (panel 42) is the first step of that.
        • 
        
      • Logging. Servers write logs to stdout or stderr, one line per event (often as JSON), and let the hosting system collect them. Never log passwords, tokens or full card numbers.
        • 
        
      • Shebang. A first line #!/usr/bin/env node lets macOS and Linux run a script as ./boarding.js once it's marked executable (chmod +x). npm uses this for the commands packages install.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "A green tick means the code works." It means the asserts that ran didn't fail. An un-awaited assert, a test with no assert, or a check of the wrong thing all give ticks.
        • 
        
      • "assert.equal compares arrays." In strict mode it's ===: two separate arrays are never equal. Use deepEqual.
        • 
        
      • "assert.throws(fn(), …) is fine." That calls fn before throws starts. Pass a function: () => fn().
        • 
        
      • "before and beforeEach are the same." before runs once; state it creates is shared by every test in the group (Boss 2).
        • 
        
      • "100% coverage means no bugs." It means every line ran, not that its result was checked.
        • 
        
      • "Relative paths are relative to the script." They're relative to the current working directory. Only import specifiers like './lib/plane.js' are relative to the file.
        • 
        
      • "process.argv[0] is my first word." Index 0 is node, index 1 is the script; your words start at 2.
        • 
        
      • "Numbers on the command line or in env vars are numbers." They are always strings. Convert with Number() and check for NaN.
        • 
        
      • "process.exit() is the normal way to finish." It can cut off output that hasn't been written yet. Set process.exitCode and let the program end.
        • 
        
      • "emit is asynchronous, like a browser click." Listeners run right inside emit, before the next line.
        • 
        
      • "Putting the API key in the code is fine, the repo is private." Private repos get shared, forked and leaked. Keep secrets in the environment and out of git.

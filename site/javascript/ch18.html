CHAPTER 18

PARENTS AND COOKIE CUTTERS

Picture: Kit, the stage manager in a pink hoodie and headset, points at two drawings. First, a chain of three boxes joined by dashed arrows: ada, then actor, then Object.prototype, with the words "ask my parent!". Second, a star-shaped cookie cutter labelled class above two star-shaped cookies, with the words "one cutter, many cookies".

Every object in JavaScript has a hidden parent. When an object doesn't know something, it asks its parent, who asks theirs, all the way up a chain. Today you meet that chain, the machinery behind new, and then the tidy way everyone writes it now: the class, a cookie cutter that stamps out objects with private fillings sealed inside. You'll also meet the error messages that come with them. About 120 minutes, with 30 hands-on checks.

  1. Ask my parent: the prototype chain
  2. One recipe card for everyone: constructors and new
  3. The cookie cutter: class
  4. Sealed fillings: private fields, getters and setters
  5. Cutters from cutters: extends and super
  6. Building a good cast: mixins and composition
  7. Boss level and recap

      PART 4 · SEALED FILLINGSPrivate fields and methods, getters and setters
      

  
      
    32
    
      The box office keeps money in a BankAccount object. If any code anywhere can write acct.balance = 1000000, the money isn't safe. Kit wants a filling sealed inside the cookie.
      
    
    
      
      
      THE ICINGpublic
      Ordinary properties like owner. Anyone can read or change them.
      
      
      THE FILLING#private, sealed
      Fields like #balance. Only the class's own methods can reach them.
      
    
      
    
      
      
      
      Kit says: Put a # in front of a field's name and it becomes private: only code written inside the class's curly brackets can read or write it. Everyone else has to ask nicely, through the methods the class offers. Hiding the inside and offering a few safe buttons is called encapsulation.

    Under the hood: lookups, classes, super and private names
    
        
      
        The two halves of a property access
        
      
        The specification describes reading a property as the internal operation [[Get]]: look for an own property with that key; if there is none, repeat on the object's [[Prototype]]; if the prototype is null, the answer is undefined. Writing is [[Set]], and it is not a mirror image. It also walks the chain, but only to see whether an inherited property gets in the way: if it finds an inherited setter, it calls it (that's how panel 37's d.level = 80 reached the setter on Dimmer.prototype); if it finds an inherited property that is read-only, the write fails (silently in sloppy code, with a TypeError in strict code, as in panel 38). Otherwise it creates or updates an own property on the object you wrote to. That's the precise version of "writing stays home".
        
      
        __proto__ is an accessor, not a drawer
        
      
        obj.__proto__ works because Object.prototype has a getter and setter called __proto__ that call Object.getPrototypeOf and Object.setPrototypeOf. It's listed in Annex B of the specification, the part kept for compatibility with old web pages. An Object.create(null) object never reaches Object.prototype, so on it __proto__ is just an ordinary key, one more reason such objects make safe dictionaries. The { __proto__: p } form in an object literal is separate, standard syntax.
        
      
        What a class really builds
        
      
        class Actor { constructor(n) { … } bow() { … } } creates a function Actor (the constructor's body), an object Actor.prototype whose constructor points back, and a method bow on that object. The differences from a hand-written constructor function are real: the function is marked as a class constructor, so calling it without new throws; class methods are created non-enumerable; the whole body is strict; and the binding Actor is in the temporal dead zone until the class has been evaluated.
        
      
        class Star extends Actor makes two links: Star.prototype's parent is Actor.prototype (for instances), and Star's own parent is Actor (so static methods are inherited too: Star.fromCode would find Actor.fromCode). In a derived class, new doesn't make the object itself: the object is made by the base constructor when super() reaches it. That's the reason behind panel 44's rule and panel 46's order.
        
      
        How super finds the parent
        
      
        A method defined in a class (or with the method shorthand in an object literal) remembers the object it was defined on, an internal slot called [[HomeObject]]. super.bow() means "look up bow starting from the parent of my home object, and call it with the current this". Because it uses the home object rather than this, a three-level chain like panel 46's exercise works: Spotlight's super.price() reaches Lamp's, whose super.price() reaches Prop's. Methods written as key: function () {} have no home object and can't use super.
        
      
        Fields are defined, not assigned
        
      
        A field like seat = "unassigned" creates the property as if with Object.defineProperty (Chapter 19), not with =. One consequence: a child class's field does not trigger a setter of the same name on the parent class; it simply creates an own property that shadows it.
        
      
        Private names are not properties
        
      
        Each #name is a unique, hidden key that exists only inside the class body's text. Each object made by the class carries its own private slots, keyed by that hidden name, but they never appear in any list of properties, aren't inherited through the prototype chain and can't be reached by any reflection tool. A useful mental model: a private field behaves like a WeakMap (Chapter 20) owned by the class, from objects to values. Two classes that both declare #id have two unrelated names.
        
      
        Why Node writes the class name
        
      
        console.log uses util.inspect, which looks up the object's constructor.name through its prototype and prints it in front of the braces: Actor { name: 'Ada' }. That label is Node's choice. Objects with no prototype get [Object: null prototype]; arrays made by a subclass get CueList(2) [ … ]. Browsers show something similar in their consoles, but differently laid out.
        
      
        Why changing a parent is slow
        
      
        Engines such as V8 make property lookups fast by remembering, for each place in your code, the "shape" of objects seen there and where a property was found along the chain. Changing an object's prototype after it's built throws that knowledge away, which is why MDN warns that Object.setPrototypeOf is slow. Building objects with their parent from the start (Object.create, new, class) keeps them fast.
        
    
        
  
        

  
        
    In real programs
    
        
      
          
        
        • Your own error types. Libraries define error classes so callers can tell failures apart with instanceof: a database library might throw a ConnectionError and a QueryError, both extending Error. Chapter 24 builds a family of them.
          • 
        
        • Node's own classes. Many of Node's built-in tools are classes you can extend. A common pattern is class Show extends EventEmitter (from node:events), which gives your objects on and emit for events.
          • 
        
        • Browser components. A custom HTML element is a class: class TicketCard extends HTMLElement { … }, registered with customElements.define("ticket-card", TicketCard).
          • 
        
        • TypeScript's private versus #. TypeScript, a typed version of JavaScript, has a private keyword that is only checked while compiling; at run time it's an ordinary property anyone can read. A #field is enforced by the JavaScript engine itself.
          • 
        
        • Dictionaries. Object.create(null) was the classic way to build a safe lookup table. Modern code often uses a Map instead (Chapter 20), which has no inherited keys at all and allows any value as a key.
          • 
        
        • Polyfills. A polyfill adds a missing standard method to an old engine, for example defining Array.prototype.at where it doesn't exist yet. That's the one accepted reason to touch a native prototype, and careful polyfills first check that the method is missing and add it as non-enumerable.
          • 
        
        • Linters help. ESLint's no-extend-native rule flags changes to built-in prototypes, no-prototype-builtins flags obj.hasOwnProperty(…) calls (prefer Object.hasOwn), and prefer-object-has-own suggests the modern form.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "Object.create copies the parent's properties." Nothing is copied. The child asks the parent at read time, so later changes to the parent show through (panel 7's exercise).
          • 
        
        • "obj.prototype is the object's parent." Only functions have a prototype property, and it's the parent of objects the function builds. An object's own parent is Object.getPrototypeOf(obj).
          • 
        
        • "Writing to an inherited property changes the parent." It creates an own property on the child (unless an inherited setter catches it).
          • 
        
        • "console.log shows everything an object can do." It shows own properties. Inherited methods are there but not printed.
          • 
        
        • "Classes are a completely new kind of object system." They build constructor functions and prototypes, the same chain as Part 2, with stricter rules.
          • 
        
        • "instanceof means the object was made by that constructor." It means the constructor's prototype is on the chain (panel 21's fake).
          • 
        
        • "A child class can read the parent's #private fields." No. Only code written inside the declaring class can, even though the child's objects do carry the field.
          • 
        
        • "acct.balance = 5 changes #balance." They're different names. It makes a new public property (or calls a setter, if there is one).
          • 
        
        • "Methods remember their object." this depends on the call. Pass obj.method alone and it's lost, class or not.
          • 
        
        • "The child's constructor runs first, so child fields are ready in the parent's constructor." The parent's part completes first; child fields arrive after super() returns.
          • 
        
        • "Every derived class must write a constructor." Leave it out and you get one that passes all arguments to super (panel 45).
          • 
        
        • "Adding helpers to Array.prototype is a neat trick." It changes every array in every library, and can block future language features.

        A function meant to be called with new, which fills in this.
        
        
        new
        Makes an object, links it to F.prototype, runs F with this = it, and returns it.
        
        
        F.prototype
        A function's property holding the object that becomes the parent of everything new F builds.
        
        
        constructor (property)
        A property of F.prototype pointing back at F.
        
        
        instanceof
        x instanceof F: is F.prototype on x's chain?
        
        
        class
        A cookie cutter: a constructor and its prototype methods written as one block.
        
        
        instance
        An object made by a class or constructor.
        
        
        field
        A property every instance gets, declared in the class body.
        
        
        static
        A field or method that belongs to the class itself, not to instances.
        
        
        static initialization block
        static { … }: code that runs once when the class is defined.
        
        
        private field / method
        A #name member usable only inside its class.
        
        
        brand check
        #name in obj: does obj carry this class's private field?
        
        
        getter / setter
        Methods that run when a property is read (get) or written (set).
        
        
        encapsulation
        Hiding an object's inside and offering a few safe ways to use it.
        
        
        extends
        Makes a class a child of another class.
        
        
        parent class / child class
        Also called superclass / subclass, or base / derived class.
        
        
        super(…)
        In a child constructor: run the parent's constructor. Required before this.
        
        
        super.method()
        Call the parent class's version of a method.
        
        
        overriding
        A child class defining a method with the same name as its parent's.
        
        
        mixin
        A bag of methods copied onto a class's prototype.
        
        
        composition
        Building an object out of other objects kept in its fields ("has a").
        
        
        inheritance
        Getting behaviour from a parent through the chain ("is a").
        
        
        single responsibility
        The design rule that each class should have one clear job.
        
        
        temporal dead zone
        The time before a let, const or class line has run, when using the name throws.
        
        
        polyfill
        Code that adds a missing standard feature to an older engine.

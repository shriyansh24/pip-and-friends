2

Cuetown has two kinds of shop. They sell the same things, but you order from them in very different ways.

ES MODULESimport / export · "ESM"

The modern kind, part of the JavaScript language itself. Every shop prints its catalog in advance: before a single line runs, Node reads every import and export in every file, connects the orders to the catalogs, and stops if anything doesn't match. That's called static: decided by reading, not by running.

COMMONJSrequire / module.exports · "CJS"

Node's older kind (Chapter 14). require(…) is an ordinary function call. It runs when your code reaches it: you knock, the shop runs, and you get whatever is in its box. Nobody checked beforehand. That's called dynamic: decided while running.

ESM PRINTS A CATALOG. COMMONJS HANDS YOU A BOX.

      PART 3 · ON DEMANDOrdering while the program runs, knowing where you are, and JSON shops
      

  
      
    15
    
      Sometimes you don't know which shop you need until the program is running, such as a language chosen by the visitor. For that, ES modules have import(…) with parentheses: a dynamic import. It returns a promise (Chapter 24's pager) of the shop's namespace object.
      
    dynamic.js
    
      
    lang/fr.js
    
      
    
      
    
        
      
      1. Line 3: the address is built at run time with a template string. A static import can't do that: its address must be a plain string, so it can be read before running.
        2. 
      
      2. await: loading a file takes time, so you wait for the pager. Top-level await works in ES modules (Chapter 25); inside a function, the function must be async.
        3. 
      
      3. Line 4: you get the namespace object, so the default is shop.default, and named exports are properties.
        4. 
      
      4. Lines 5 and 6: there's no lang/xx.js, so the promise rejects with an error whose code is ERR_MODULE_NOT_FOUND. With a dynamic import, a missing shop is a normal error you can catch, not a crash before the start.
        5. 
    
      
    
      Dynamic import() works in CommonJS files too. It's the one way for an old shop to order from an ES module that uses top-level await (Part 5).
      
  
      

  
      
  

  
      
  

  
      
    16
    
      Every ES module carries an address card about itself: import.meta.
      
    where.js
    
      
    
      
    
        
      
      1. import.meta.url is the module's address as a file URL, the kind with file:///. ES modules are identified by URLs, in Node and in browsers alike.
        2. 
      
      2. import.meta.filename and import.meta.dirname (not in browsers, which have no file paths) are the plain file path and its folder.
        3. 
      
      3. import.meta.resolve(…) answers "if I imported this address, which file would I get?" without loading it.
        4.

    dirname_esm.js

      PART 4 · ESM OR COMMONJS?How Node decides which kind of shop a file is, for six real files
      

  
      
    19
    
      Node must decide, for every file, "catalog or box?" before it can run it. It asks at most four questions, in this order, and stops at the first answer.
      
    
        
      
      1. Does the name end in .mjs? Then it's an ES module. Always.
        2. 
      
      2. Does it end in .cjs? Then it's CommonJS. Always.
        3. 
      
      3. It ends in .js: find the nearest package.json, starting in the file's own folder and walking up. If it says "type": "module", ES module; if "type": "commonjs", CommonJS.
        4. 
      
      4. That package.json has no "type" at all? Node tries to read the file as CommonJS. If it finds ES-only grammar, such as import or export lines, it switches to ES module. This is syntax detection, on by default since Node 22.7. It costs a little time, so Node prints a warning.
        5. 
    
      
    
      
      
      
      The Professor says: Every folder in this book has a package.json that says "type": "module", so all our .js files are ES modules. Inside it, I made a folder called combo with three smaller folders, each with its own package.json, so we can test all six cases for real.

    30
    
      Behind the theatre is Kit's workshop. On the wall hangs every tool a JavaScript project uses besides Node itself. Each one has a job you could do by hand, slowly and badly.
      
    
      
    
      
      
      BUY AND TRACKthis part
      Version numbers say how much a package changed. Ranges say which versions you accept. The lockfile is the receipt that says exactly which one you got, so every machine gets the same.

    Under the hood: how a module graph loads
    
      
      
      Three phases
      
      
      An ES module graph is loaded in three phases. Construction: starting from the entry file, the loader finds each file, reads it, and parses it into a module record that lists its imports and exports. It doesn't run anything; it only follows the import addresses, so every file in the graph is known before anything runs. Linking: every import is connected to the matching export. A name that no export provides fails here, which is why panel 6's error came before line 1. The exported variables are created, but uninitialised (in their temporal dead zone). Evaluation: each module's body runs once, dependencies first (a depth-first, post-order walk), which gives panel 14's order.
      
      
      Why live bindings work
      
      
      Linking doesn't copy values. The importer's name and the exporter's variable are the same storage slot, seen through a read-only view. That's why imports update (panel 10), why you can't assign to them (panel 11), and why reading one too early in a circle hits the temporal dead zone (panel 26). export default <expression> is the exception worth knowing: it evaluates the expression once into a hidden binding, so export default count; exports the value count had at that moment, while export { count as default } stays live.
      
      
      Top-level await
      
      
      A module that uses await at its top level makes evaluation asynchronous for itself and everything that imports it: they wait for it to finish. Sibling modules that don't depend on it can still run. require must return immediately, so it refuses any graph that contains a top-level await (ERR_REQUIRE_ASYNC_MODULE).
      
      
      The CommonJS wrapper
      
      
      Node runs each CommonJS file inside a function, roughly function (exports, require, module, __filename, __dirname) { … }, called with this set to module.exports. That explains every CommonJS-only name in panel 13, and why exports = … only changes a parameter. require caches by resolved file name in require.cache; a circular require gets the half-filled module.exports of the shop that's still running, instead of a TDZ error.
      
      
      How importing CommonJS from ESM finds named exports
      
      
      CommonJS exports are only known after running the file, but linking happens before. Node bridges the gap by reading the CommonJS source with a small, fast analyser (cjs-module-lexer) that spots patterns like module.exports = { a, b } and exports.c = …. Names it can spot become named exports; the whole box is always available as the default.
      
      
      Module identity
      
      
      A module is identified by its resolved URL. Two different addresses that resolve to the same file share one instance; the same file reached by a different URL (for example with a ?v=2 query on the end) would be a second instance with its own variables.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • Barrel files, with care. Libraries often have one index.js that re-exports everything. It's convenient, but importing one small thing from a big barrel can make tools load the whole tree; many teams import from the specific file instead.
        • 
        
      • Dual packages. Packages that must work for both ESM and CommonJS users list two entry points under "exports" with the conditions "import" and "require". With require(esm) now built in, more packages ship ESM only.
        • 
        
      • Lazy loading. Web apps load rarely used screens with import() when a visitor first opens them; bundlers split each dynamic import into its own file ("code splitting").
        • 
        
      • Lockfiles everywhere. Every serious project commits its lockfile, and its build servers run npm ci. Bots such as Dependabot or Renovate open a pull request for each update, so the tests run before the new version is accepted.
        • 
        
      • Scripts as documentation. A package.json with dev, build, test, lint and format scripts tells a newcomer how the project works without reading anything else.
        • 
        
      • TypeScript in the editor. Even in plain JavaScript projects, editors such as VS Code run the TypeScript checker in the background, which is where many of those squiggly underlines and JSDoc hints come from.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "Imports run where they are written." Static imports are hoisted: all of them happen before the module's first line.
        • 
        
      • "Importing a module twice runs it twice." Once per program, then it comes from the cache.
        • 
        
      • "An import is a copy." It's a live, read-only view. CommonJS unpacking is the one that copies.
        • 
        
      • "export * re-exports everything." Everything except the default.
        • 
        
      • "import { x } gets a default export if the names match." Braces always mean named exports; the default needs no braces.
        • 
        
      • ".js files are ES modules." Only under a "type": "module" package.json, or when detection finds ES grammar. .mjs is the only sure sign.
        • 
        
      • "The package.json at the top of my project decides." The nearest one decides, even if it has no "type".
        • 
        
      • "require can't load ES modules." It can since Node 22.12, unless they use top-level await.
        • 
        
      • "exports and module.exports are the same thing." Only until you assign to one of them.
        • 
        
      • "^1.2.3 means version 1.2.3." It means 1.2.3 up to, but not including, 2.0.0.
        • 
        
      • "npm install gives everyone the same versions." Only with a lockfile; npm ci guarantees it.
        • 
        
      • "Node checks my TypeScript types." It strips them unread. Run tsc.
        • 
        
      • "A transpiler makes old browsers support new functions." It translates grammar; missing functions need polyfills.
        •

      re-export
      Listing another shop's goods in your catalog: export … from.
      
        
      barrel
      A file (often index.js) that only re-exports other modules.
      
        
      namespace object
      The object of a module's whole catalog, from import * as x, import() or require(esm).
      
        
      side-effect import
      import "./file.js": run that file, take nothing.
      
        
      live binding
      An imported name that is a read-only view of the exporter's variable.
      
        
      module scope
      The private top-level names of one module.
      
        
      strict mode
      JavaScript's stricter rule set; automatic in modules (and classes).
      
        
      hoisting (imports)
      Static imports are handled before any other line of the module.
      
        
      module cache
      Node's memory of modules already loaded, so each runs once.
      
        
      dynamic import
      import(address): load a module while running; returns a promise.
      
        
      import.meta
      Facts about the current module: url, dirname, filename, resolve().
      
        
      file URL
      An address like file:///home/you/x.js for a file on disk.
      
        
      import attribute
      Extra information on an import, such as with { type: "json" }.
      
        
      syntax detection
      Node reading a type-less .js file to decide whether it's an ES module.
      
        
      require(esm)
      Loading a synchronous ES module with require.
      
        
      module.exports / exports
      A CommonJS module's box / a second name for the same box.
      
        
      circular import
      Modules that import each other, directly or through others.
      
        
      "exports" field
      A package's list of addresses others may import.
      
        
      import map
      A JSON list on a web page saying where bare module names live.
      
        
      semver
      Semantic versioning: MAJOR.MINOR.PATCH, each with a meaning.
      
        
      range
      A rule for acceptable versions: ^1.4.2, ~1.4.2, 1.4.2, >=1.4.2.
      
        
      registry
      The online catalogue npm downloads packages from.
      
        
      lockfile
      package-lock.json, the receipt of exact installed versions.
      
        
      npm ci
      Clean install exactly from the lockfile.
      
        
      npm outdated / npm update
      Compare Current, Wanted and Latest / move to Wanted.
      
        
      devDependency
      A package needed only while building and checking.
      
        
      npx
      Runs a command provided by a package, local ones first.
      
        
      version manager
      A tool that installs and switches between Node versions (nvm, fnm).
      
        
      node --run
      Runs a package.json script without npm.
      
        
      node --check
      Checks a file's grammar without running it.
      
        
      static checker
      A tool that finds problems by reading code, not running it.
      
        
      linter
      A static checker with rules you choose (ESLint).
      
        
      formatter
      A tool that rewrites layout in one consistent style (Prettier).
      
        
      bundler
      A tool that packs a module graph into a few files (esbuild, Vite, Webpack).
      
        
      tree shaking
      Leaving unused code out of a bundle.
      
        
      minify
      Shrinking code: short names, no spaces or comments.
      
        
      transpiler
      A tool that rewrites newer grammar as older grammar (Babel, esbuild).
      
        
      polyfill
      Code that adds a missing built-in function.
      
        
      TypeScript
      JavaScript plus type annotations, checked by tsc.
      
        
      type stripping
      Node removing annotations from a .ts file without checking them.
      
        
      JSDoc
      Comments like /** @param {number} seat */ that describe types in plain JavaScript.

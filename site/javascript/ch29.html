Two ways to answer "is this plate already on the pass?"

The left way compares pairs: with n plates there are about n × n ÷ 2 of them. The right way uses a labelled rack, which is what a Set or a Map from Chapter 20 is: you go straight to the right hook.

COUNT THE STEPS, NOT THE SECONDS

  


  

  

  

    5
    
Big-O is a nickname for the shape of the work: how the number of steps grows as the input size n grows. It ignores small details (×2, +3) and keeps the shape. The kitchen's speed board, fastest first:

    
    
      
  • O(1)constant: grab the soup from its hook. arr[3], set.has(x), map.get(k), push, pop.
    • 
      
  • O(log n)logarithmic: halve the pile each look. Binary search (Part 5): a million items in 20 looks.
    • 
      
  • O(n)linear: walk the whole line once. includes, indexOf, reduce, one for loop, shift.
    • 
      
  • O(n log n)"n log n": the speed of good sorting. Merge sort and the built-in sort (Part 6).
    • 
      
  • O(n²)quadratic (slow!): every item against every item. A loop in a loop, or includes inside a loop.
    • 
    

    
Here are the shapes as numbers. These are formulas worked out by a program, not timings:

    growth.js
    

    

    
At a million items, O(log n) is 20 steps and O(n²) is a trillion. No faster laptop rescues O(n²) on big inputs; only a better shape does. Big-O usually describes the worst case: the dish you search for is at the far end, or not there at all.

    
The speed board lists O(1) constant, O(log n) logarithmic, O(n) linear, O(n log n), and O(n²) quadratic, which is marked slow with a dashed border.

The classic slow pattern in real code: includes inside a loop. For every order, check the sold-out list. Feed the step-counting machine bigger and bigger nights. On each night, none of the n orders is sold out, so every search walks the whole list (the worst case). The Set version builds its rack once, then grabs. The inner for loop in countArray does by hand what includes does inside: look at each item until a match. Counting a Set lookup as one step is fair: the language rules require Set and Map lookups to be faster than walking the list, and engines use hash tables (lockers, Part 5) so a lookup takes about the same time whatever the size.

    8
    
The chef's rules for a faster kitchen. Rule 1 beats all the others put together.

    
    
      
  1. Pick the right shape first. A Set instead of includes in a loop, a Map instead of searching an array of pairs: these turn O(n²) into O(n). Nothing else comes close.
    2. 
      
  2. Measure, don't guess. Most programs spend most of their time in a few hot spots. Find them before you change anything.
    3. 
      
  3. Skip micro-tricks. Rewriting for...of as an old for (let i…) loop, or caching arr.length, saves almost nothing in today's engines, and it makes code harder to read. That's premature optimization: polishing before you know what's slow.
    4. 
      
  4. Use the profilers. In the browser, the DevTools Performance panel records what ran and for how long, and the Memory panel shows what's taking up memory (Part 2). In Node, node --cpu-prof app.js writes a .cpuprofile file that DevTools can open as a chart of where the time went.
    5. 
      
  5. Small n? Relax. For 20 items, O(n²) is 400 steps: nothing. Shapes matter when n can grow: user lists, logs, files, anything from the network.
    6. 
    

    

      
      
The chef says: Don't sharpen the knives while the oven is on fire.

    

  


  
  
PART 2 · DIRTY DISHESReachability, garbage collection, the four classic leaks, and WeakMap


  

    9
    
    

      
      
The Professor says: Every object you make takes up memory, like a plate on a counter. You never wash plates yourself in JavaScript: a night crew called the garbage collector does it. Its rule is simple. A plate stays if someone can still reach it; every other plate gets washed.

    

    
"Reach" means: starting from the roots (global variables, and the variables of every function that is running right now), can you follow names and drawers (properties, array slots, closures' backpacks) to the object? If yes, it's reachable and it stays. If no road leads there, it's garbage, and its memory is reused. The crew works by itself, whenever it decides to; you can't call it (Node has a flag, --expose-gc, for experiments, but real programs never need it).

    
Picture: the Professor explains garbage collection. A burst says CLATTER.

    So how can JavaScript leak memory at all? A leak is memory you don't need any more but that is still reachable, so the crew must keep it. Dirty dishes nobody is responsible for. The commonest one: a cache that only grows.
    
    leak_cache.js
    
    
    
    
    
    Two users, yet 6 entries after three rounds, and it would be 6,000 after three thousand. Line 4 makes a new key object on every call, and Map keys compare by reference: two objects with the same insides are still two different tickets (Chapter 20). The cache never finds an old entry, and the global cache keeps every one reachable forever. A server running this for a week runs out of memory.
    
    cache_fixed.js
    
    
    
    
    
    Keyed by the id, a value, the same user finds the same entry. Real caches also set a limit (say, the newest 500 entries) and throw out the oldest, so they can't grow forever.
    
  
    

  
    
  

  
    
    12
    
    Sometimes you want to attach extra information to an object you don't own: a note about a guest, the size of a DOM element. Store it in a normal Map and the Map keeps the guest reachable forever. A WeakMap (Chapter 20) holds its keys weakly: it doesn't count as a road. When nothing else can reach the key, the entry goes out with it.
    
    
    
      
      
    The WeakMap coat check says: When the guest walks out the exit, her coat goes with her. I don't hold anyone back.
    
    
    
    weak_notes.js
    
    
    
    
    
    size is undefined: a WeakMap can't be counted or looped over, because its contents could change at any moment the crew runs. You can only ask about a key you're holding. And keys must be things that can be collected: objects, or symbols made with Symbol(). Strings and numbers can't be weak keys, and neither can a symbol from Symbol.for(), because that one is kept in a global list for ever:
    
    weak_key_error.js
    
    
    
    
    
    Read it like a detective (Chapter 1's name, place, caret): the name and message first, TypeError: Invalid value used as weak map key. Then the place, weak_key_error.js:2:7: line 2, the set call. A string like 'Ada' can't be a weak key.

    14
    
    The four classic leaks. Each one is a road nobody remembered to close.
    
    
    
      
    GROWING CACHESMap / object / array
    Entries go in, nothing comes out. Fix: key by value, cap the size, or use a WeakMap for notes about objects.
    
      
    FORGOTTEN LISTENERSon / addEventListener
    Every subscribe needs an unsubscribe: off, removeEventListener, or an AbortController signal.
    
      
    TIMERS LEFT RUNNINGsetInterval
    An interval runs forever, and its callback's backpack stays reachable. Keep the id and call clearInterval.
    
      
    BIG BACKPACKSclosures
    A long-lived function that mentions a huge array keeps all of it. Copy out only the small part it needs.
    
    
    
    timer_fixed.js
    
    
    
    
    
    Without line 6, this program would print ticks forever: an interval is a job still waiting, so Node won't exit (that's why we don't capture that version). To find leaks in a real app, the DevTools Memory panel takes heap snapshots, photos of every object in memory; take one, use the app for a while, take another, and look for things that keep multiplying.
    
  
    

  
    
  

  
  
    PART 3 · KEEP THE PASS MOVINGDon't block the one cook: chunks, helpers, debounce, throttle and lazy loading
    

  
    
    15
    
    
    
      
      
    Kit says: Remember Chapter 25? JavaScript has one cook. While the cook stirs a long pot, nobody answers the doorbell. One cue at a time.
    
    
    
    block.js
    
    
    
    
    
    The doorbell timer was due after 0 ms, but it rang last: the 100-million-step loop held the only thread the whole time. In a browser, that's a frozen page: no clicks, no scrolling, no animations. In a server, every other visitor waits. That's called blocking the event loop.
    
    
    Picture: Kit points at the program. A burst says DING DONG.
    
  
    

  
    
    16
    
    Fix 1: chunking (Node's guide calls it partitioning). Do a slice of the work, then step aside with setTimeout(…, 0) so anything waiting gets a turn, then do the next slice.
    
    chunked.js
    
    
    
    
    
    Same total, same one cook, but the doorbell got answered after the first slice instead of after the whole job. The job takes about as long; the kitchen just never freezes for long. The doorbell's timer was due first (it was set before chunk 1 ran), so it goes ahead of chunk 2's timer: timers due at the same delay run in the order they became due.
    
  
    

  
    
  

  
    
    17
    
    Fix 2, as a preview: hire a helper cook with a stove of their own. A worker runs JavaScript on a separate thread, with its own memory and its own event loop. Node has worker_threads; browsers have Web Workers (new Worker('file.js')). They can't share variables: they talk by posting messages.
    
    worker.js
    
    
    
    
    
    The same file runs twice: on the main thread (isMainThread is true) it hires the helper; on the helper's thread it does the counting and posts the total back. While the helper counted, the main thread was free to answer the doorbell. The main thread awaits the one message, so the output order is the same every run. Workers cost something to start and to send data to, so they pay off only for big jobs. More than this preview is beyond this book.
    
  
    

  
    
    18
    
    Some jobs aren't big, they're just too frequent. A search box that searches on every key press does 3 searches for "pie", and 2 of them are for words nobody wanted. Debounce: wait until the keys stop for a moment, then run once. (Chapter 21 gave a preview; here's the real thing, on Chapter 27's pretend clock so every run is identical.)
    
    debounce.js
    
    
    
    
    
    Every call clears the waiting timer (line 7) and starts a fresh 300 ms one. Keys 100 ms apart keep cancelling each other; only when the typing pauses does the last timer survive and search for "pie". The closure's backpack (Chapter 17) keeps timer between calls. (On Node 22 this prints the same, plus a warning that mock timers were still experimental there.)
    
  
    

  
    
    19
    
    Throttle is debounce's cousin: run at most once per time window, no matter how often you're asked. Good for scrolling and resizing, where you want steady updates while it's happening, not just one at the end.
    
    throttle.js
    
    
    
    
    
    Eleven scroll events, three redraws: at 0 ms, then the first event at least 100 ms later (120 ms), then 240 ms. The pretend clock (apis: ['Date']) makes Date.now() start at 0 and move only when we tick.
    
    
    
      
    DEBOUNCEwait for the quiet
    Runs once, after the calls stop for wait ms. Search boxes, auto-save, "resize finished".
    
      
    THROTTLEone per beat
    Runs at most once every wait ms while calls keep coming. Scroll position, drag, game input.
    
    
    
  
    

  
    
  

  
    
    20
    
    Last kitchen trick: don't prepare dishes nobody ordered. A normal import at the top loads its module before anything runs. await import('./file.js') loads it when that line runs, so rarely used code (a report, a chart library, a settings page) costs nothing until someone needs it. This is lazy loading.
    
    lazy.js
    
    
    lib/report.js
    
    
    
    
    
    The menu was ready before report.js even ran: its top-level line printed only when import() asked for it. import() returns a promise (a pager, Chapter 16) for the module's exports, and a module runs only once, however many times it's imported (Chapter 26). In browsers, bundlers use exactly this to split an app into smaller files that load on demand.

    linked_list.js

      PART 5 · NUMBERED LOCKERS AND FAMILY TREESA hash map from scratch, keys by reference, binary search and its bugs, search trees
      

  
      
    28
    
      How can a Map find a key without walking? The locker room trick, called hashing:
      
    
        
      
      1. A hash recipe turns any key into a big number, always the same number for the same key. Ours adds up the letters' codes, mixing as it goes.
        2. 
      
      2. Remainder: that number % the number of lockers gives a locker, from 0 to lockers − 1. Go straight there.
        3. 
      
      3. Collisions: two keys can land in the same locker. So each locker holds a short list (a bucket), and we check the few keys in it.
        4. 
      
      4. Growing: when the lockers fill up (more than 3 keys per 4 lockers here), double the lockers and move every key to its new locker. Buckets stay short, so lookups stay O(1) on average.
        5. 
    
      
    
      
  
      

  
      
    29
    
      Here it is, built with nothing but arrays. (Never use this instead of Map; it's here so you know what Map does for you.)
      
    hashmap.js
    
      
    
      
    
        
      
      1. The first picture: Bo and Lu collide in locker 1, so that bucket holds two entries. A lookup for Lu checks only those two, not all three.
        2. 
      
      2. Adding Hal makes 4 keys in 4 lockers, more than 0.75 per locker, so grow doubles to 8 and re-files everyone. With 8 lockers, Bo and Lu land in different ones. Growing costs O(n) once in a while, but doubling makes it rare, so each set is still O(1) on average.
        3. 
      
      3. Line 14: keys are compared with ===, like a real Map. That matters next.
        4.

    binary_search.js

The catch: the crate must be sorted, and sorting costs O(n log n). That pays off when you search the same crate many times.
      
    
      HALF THE CRATE EACH LOOK
      
  
      

  
      
  

  
      
    32
    
    
      Binary search is short, and famously easy to get slightly wrong. Bug 1, the off-by-one: < instead of <=.
      
    bs_off_by_one.js
    
      
    
      
    
      15 and 3 are found, but 57 says -1 although it's right there. When the search narrows to a single slot, lo equals hi, and while (lo < hi) stops before looking at it.       PART 6 · SORTING DAYBubble, selection, insertion, merge and quick sort, then the built-in sort
      

  
      
    35
    
      The returned books come back in a jumble, and the crate must be in order again. Librarians have invented many ways. Five classics, slowest first:
      
    
      
      
      BUBBLE SORTO(n²) · slow
      Walk the crate comparing neighbours; swap any pair in the wrong order. After each pass, the biggest unsorted book has bubbled to the end. Stop after a pass with no swaps.
      
      
      SELECTION SORTO(n²) · slow
      Find the smallest book in the unsorted part and swap it into the next seat. Repeat for each seat.
      
      
      INSERTION SORTO(n²), fast on nearly sorted
      Like sorting cards in your hand: pick up the next card and slide it left past the bigger ones into its place.
      
      
      MERGE SORTO(n log n)
      Split the heap in half, sort each half (the same way), then merge the two sorted halves by taking the smaller front book each time.
      
      
      QUICK SORTO(n log n) usually
      Pick a pivot book. Put the smaller ones left of it and the bigger ones right, then sort each side the same way.
      
      
      BUILT-IN SORTarr.sort / arr.toSorted
      What you should actually use. In Node and Chrome it's TimSort, a merge sort that's clever about runs already in order.

    Under the hood: what Big-O ignores, how V8 collects garbage, how Map really finds keys
    
      
      
      What Big-O leaves out
      
      
      Big-O keeps only the fastest-growing part and drops constant factors: 3n² + 5n + 7 is O(n²). That's why predict_steps.js's "each pair once" (n(n − 1)/2) has the same shape as "every pair twice" (n²). It also means a faster-growing algorithm with small constants can beat a slower-growing one on small inputs: that's why TimSort uses insertion sort (O(n²)) instead of merging for short runs. Big-O usually means the worst case; sometimes people quote the average case (quick sort: O(n log n) on average, O(n²) at worst) or the amortized cost (a growing hash map or array: an occasional O(n) resize spread over many O(1) operations). Memory has a Big-O too: merge sort as written here uses O(n) extra memory for its piles, while an in-place quick sort uses O(log n) for its recursion.
      
      
      The garbage collector in V8
      
      
      The collector finds garbage by marking: start from the roots, follow every reference, mark what you reach; whatever is unmarked is free to reuse ("mark and sweep"). Objects that point at each other but that no root reaches, an "island", are collected together. V8 (the engine inside Node and Chrome) is generational: most objects die young, so new objects live in a small area that is cleaned very often and cheaply, and survivors are moved to an older area that is cleaned less often. Much of the marking happens incrementally and on helper threads, so your program pauses only briefly. You can't predict when a particular object goes; that's why WeakRef and FinalizationRegistry exist but are beyond this book.
      
      
      How Map and Set find a key
      
      
      The language rules only say that Map and Set must give access times that are, on average, better than walking the whole list. V8 uses hash tables, like our lockers, with two twists: the table also remembers insertion order (so for...of gives entries in the order you added them), and for an object key it uses a hash number stored with the object when it was first needed, which is why lookup is by identity, never by contents. Plain objects with string keys use a different trick ("hidden classes" with fixed slots) when their shape stays the same, and fall back to a hash table when you add and delete many keys: one reason to prefer Map for collections that change a lot.
      
      
      Arrays, shift and holes
      
      
      V8 stores an array of small whole numbers, an array of doubles and an array of mixed values in different, compact ways, and moves an array to a slower "dictionary" form if you make huge holes in it (arr[1_000_000] = 1 on an empty array). shift is O(n) by the language rules; V8 can sometimes avoid moving the items by sliding the start of the array's storage, but it can't always, so the safe plan is the head-index queue from panel 24.
      
    
      
  
      

  
      
    In real programs: where these structures and tricks live
    
      
      
        
        
      • Map and Set everywhere. Removing duplicates ([...new Set(list)]), counting (Boss 4), indexing a list by id (new Map(users.map((u) => [u.id, u]))) so later lookups are O(1). This one habit fixes most slow JavaScript.
        • 
        
      • Caches. Memoized functions, HTTP caches and "least recently used" (LRU) caches, which cap their size and evict the entry used longest ago. A Map's insertion order makes a simple LRU possible: delete and re-add an entry to move it to the end.
        • 
        
      • Debounce and throttle sit behind most search boxes, auto-save drafts, infinite-scroll lists and window-resize handlers. Libraries such as Lodash ship tested versions.
        • 
        
      • Workers. Image filters, spreadsheet recalculation, parsing huge files and syntax highlighting in code editors often run in Web Workers so the page never freezes.
        • 
        
      • Lazy loading. Bundlers split apps at every import(), so the first screen downloads quickly and the rest loads when the user goes there.
        • 
        
      • Trees. The DOM is a tree (Chapter 15), and so is JSON (Chapter 13), your folders, and the syntax tree tools like Prettier and ESLint build from your code (Chapter 26). Databases keep their indexes in B-trees, very bushy search trees.
        • 
        
      • Graphs. Maps and route planners, "people you may know", the module graph Node builds from your imports, and npm's dependency tree (which is really a graph). Shortest routes with different travel times use Dijkstra's algorithm, a BFS with a priority queue.
        • 
        
      • Sorting. Almost always the built-in sort/toSorted, with localeCompare or Intl.Collator for human text (Chapter 22). Sorting by several keys relies on stability.
        • 
        
      • Binary search hides inside databases, Git's git bisect (which finds the commit that introduced a bug by halving the history), and any "find the first day when…" question over sorted data.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "Faster computers make Big-O irrelevant." A computer twice as fast handles an O(n²) job only about 1.4 times bigger in the same time. A better shape can be millions of times faster.
        • 
        
      • "I timed it once, so I know it's faster." Timings wobble on every run (panel 7). Repeat, use realistic inputs, and look at the shape.
        • 
        
      • "includes is fast because it's built in." Built in, yes; still a walk through the array, O(n). Inside a loop, it's O(n²).
        • 
        
      • "JavaScript has a garbage collector, so it can't leak." It can't free what's still reachable. Caches, listeners and timers keep things reachable.
        • 
        
      • "Setting a variable to null frees the object." It removes one road. The object goes only when no road at all is left (panel 10).
        • 
        
      • "A WeakMap is a faster Map." It's a different tool: object keys only, no size, no looping, entries that leave with their keys.
        • 
        
      • "setTimeout(fn, 0) runs right away." It runs after the current code and all promise jobs, and only when the thread is free (panel 15).
        • 
        
      • "Async functions run on another thread." async/await only waits politely; the work still runs on the one thread. Only workers add threads.
        • 
        
      • "Binary search works on any array." Only on a sorted one, sorted the same way you compare.
        • 
        
      • ".sort() sorts numbers." It sorts their text: [10, 9, 1, 100].sort() gave [ 1, 10, 100, 9 ] (panel 39). Bring a comparator.
        • 
        
      • "Recursion is always slower or always more elegant." Neither. It's natural for bushy trees; for deep data, loop with your own stack.
        • 
        
      • "I need to write my own sort / hash map / linked list for real work." Almost never. Learn how they work, then use sort, Map, Set and arrays.

      5. Profile. Run node --cpu-prof timing.js. It writes a file named like CPU.….cpuprofile in the folder. In Chrome, open DevTools (F12), choose the Performance panel, and load the file to see where the time went. In the browser, the Performance panel's record button does the same for a page.
        6. 
        
      6. Watch memory. Run node --inspect leak_cache.js with a much bigger loop, open chrome://inspect in Chrome, click "inspect", and take two heap snapshots in the Memory panel. Compare them and look for what grew.
        7. 
        
      7. The stack limit. Run node deep_tree.js, then change 100,000 to 5,000 and run it again: no crash. Node accepts --stack-size to change the limit, but setting it too high can crash Node itself instead of throwing a tidy RangeError; the loop with your own stack is the real fix.
        8. 
        
      8. Paths and shells. Commands are the same in Windows PowerShell, Command Prompt, macOS Terminal and Linux shells. On Windows, chrome://inspect and DevTools work the same; the profile file lands in the current folder.

    Words from this chapter
    
      
      
      
        
      performance
      How much time and memory a program uses.
      
        
      Big-O
      The shape of how work grows with input size: O(1), O(log n), O(n), O(n log n), O(n²).
      
        
      constant / linear / quadratic
      O(1): the same work at any size / O(n): grows with n / O(n²): grows with n × n.
      
        
      logarithmic
      O(log n): the work grows by one step each time the input doubles.
      
        
      worst case
      The input that makes an algorithm do the most work.
      
        
      benchmark
      A timing test. Its numbers vary from run to run.
      
        
      performance.now()
      A precise clock reading in milliseconds.
      
        
      profiler
      A tool that records where a program spends its time (or memory).
      
        
      premature optimization
      Making code harder to read for speed before measuring what's slow.
      
        
      garbage collector
      The part of the engine that frees memory no road leads to.
      
        
      root
      A starting point the collector always keeps: globals and running functions' variables.
      
        
      reachable
      Can be found by following references from a root.
      
        
      memory leak
      Memory you no longer need that stays reachable.
      
        
      heap snapshot
      A photo of every object in memory, taken in the DevTools Memory panel.
      
        
      WeakMap
      A Map whose object keys don't keep their objects alive.
      
        
      blocking
      Holding the one thread so nothing else can run.
      
        
      chunking (partitioning)
      Splitting a long job into slices with breaks between.
      
        
      worker
      JavaScript running on another thread, talking by messages.
      
        
      debounce
      Run once, after the calls stop for a while.
      
        
      throttle
      Run at most once per time window.
      
        
      lazy loading
      Loading code only when it's first needed, with import().
      
        
      data structure
      A shape for data, chosen so common jobs are cheap.
      
        
      algorithm
      A step-by-step recipe for a job, such as searching or sorting.
      
        
      stack (LIFO)
      Last in, first out: push and pop.
      
        
      queue (FIFO)
      First in, first out: join at the back, leave at the front.
      
        
      linked list
      A chain of nodes, each pointing at the next.
      
        
      node
      One item in a list, tree or graph, with links to others.
      
        
      head
      The first node of a linked list.
      
        
      hash map / hash table
      Keys turned into locker numbers by a hash function.
      
        
      hash function
      A recipe that turns a key into a number, always the same for the same key.
      
        
      bucket
      The short list in one locker.
      
        
      collision
      Two keys landing in the same locker.
      
        
      load factor
      Keys per locker; too high means it's time to grow.
      
        
      binary search
      Searching a sorted list by halving it each look.
      
        
      off-by-one error
      A loop or index that goes one too far or stops one too early.
      
        
      tree / root / leaf
      Nodes in a family shape / the top node / a node with no children.
      
        
      binary search tree
      A tree where left is smaller and right is bigger.
      
        
      height
      The number of levels in a tree.
      
        
      balanced
      A bushy tree whose height stays about log n.
      
        
      traversal
      Visiting every node: in-order, pre-order, and so on.
      
        
      stable sort
      A sort that keeps equal items in their original order.
      
        
      comparator
      The compare function given to sort.
      
        
      pivot
      The value quick sort splits around.
      
        
      divide and conquer
      Split a problem, solve the halves, combine the answers.
      
        
      graph / edge / directed
      Nodes joined by edges / one connection / edges that go one way.
      
        
      adjacency list / matrix
      Each node's neighbour list / a grid of 0s and 1s.
      
        
      BFS
      Breadth-first search: ring by ring, with a queue.
      
        
      DFS
      Depth-first search: go deep, then back up, with a stack.
      
        
      dynamic programming
      Building answers from smaller overlapping answers, each computed once.
      
        
      memoization
      Remembering a function's answers so repeat calls are instant.

CHAPTER 16

THE RESTAURANT PAGER

Picture: Kit, the stage manager in a pink hoodie and headset, waves hello. On one side stands the chef in a tall white hat. On the other, a square restaurant pager with a ring of lit-up lights buzzes; its screen says BUZZ! and its tag says #16.

Kit runs the show one cue at a time. So what happens when a cue takes a long time, like popcorn from the kitchen, or an order from a restaurant across town? Kit can't freeze the whole theatre and wait. Today you meet code that runs later: timers, callbacks, and the promise, which works exactly like the buzzing pager a restaurant hands you when you order. Then async and await let you write "wait for the soup" in plain top-to-bottom style, fetch orders data from a web server, and a real-run puzzle settles who goes first. About 120 minutes, with 25 hands-on checks.

  1. One cue at a time: now and later
  2. The restaurant pager: promises
  3. Standing at the counter: async and await
  4. When the kitchen says no
  5. Ordering from across town: fetch

  7. Boss level and recap

PART 1 · ONE CUE AT A TIMECode that runs now, and code that runs later

1

Every program in this book so far has been synchronous: one line, then the next, then the next, each one finished before the next one starts. Kit likes it that way.

Kit says: One cue at a time. Lights up. Curtain. Music. I never start a cue until the last one is done.

Kit says: But the popcorn takes three minutes in the kitchen. If I stand by the microwave for three minutes, the whole show freezes. Nobody moves the curtain, nobody starts the music.

Kit says: So I'll do what every stage manager does: ask for a reminder, and carry on with the show.

That reminder is setTimeout, which you met in Chapter 7: "run this function after so many milliseconds". A millisecond (ms) is a thousandth of a second, so 200 ms is a fifth of a second. Read the code top to bottom, then look at the order of the output.

later.js

    PART 2 · THE RESTAURANT PAGERA promise: a placeholder for a value that isn't ready yet
    

  
    
    10
    
    After the show, Kit and Ada go to a busy restaurant. You've probably seen this: you order at the counter, and instead of food you get a pager.
    
    
    
      
    ORDER
    Kit orders soup. The chef starts cooking.
    
      
    PAGER
    Kit gets a pager right away. It isn't soup. It's a promise of soup.
    
      
    CHAT
    Kit sits down and keeps talking. The kitchen works on its own.
    
      
    BUZZ!
    The pager buzzes. Now the soup is ready to collect.
    
    
    
    
    Picture in four boxes. 1, Order: Kit points at the chef, who starts cooking. 2, Pager: a pager on its own, lights off, its screen says WAIT. 3, Chat: Kit waves and chats beside the waiting pager. 4, Buzz: the pager's lights are lit, its screen says BUZZ!, and Kit cheers in surprise.
    
    
    In JavaScript the pager is called a promise: an object that stands in for a value that isn't ready yet. You get it immediately; the value arrives later.
    
    
    A PROMISE IS A PAGER, NOT THE SOUP
    
  
    

  
    
    11

    kitchen.js
    
    
    
      
      
    1. cook(dish, ms): starts cooking and returns a promise at once. After ms milliseconds the promise is ready, holding the dish. (Inside, it's our old friend setTimeout.)
      2. 
      
    2. cookOrRefuse(dish, ms): the same, except that for lobster the promise comes back with bad news, an Error. Part 4 orders it.
      3. 
      
    3. lostOrder(): a pager that never buzzes. Also Part 4.
      4. 
    
    
  
    

  
    
    12
    
    Kit orders soup and prints what comes back. Then Kit tells the pager what to do when it buzzes.
    
    pager.js
    
    
    
    
    
      
      
    1. Line 3: cook returns immediately, and what it returns is the pager. Line 4 shows it: Promise { <pending> }. Pending means "still cooking: no value yet". This is how Node prints a promise.
      2. 
      
    2. Line 7: pager.then(callback) means "when this pager buzzes, call this function with what it holds". then doesn't wait either: it registers the callback and returns.
      3. 
      
    3. 200 ms later the soup is ready, the promise is fulfilled (it now holds "soup"), and the callback gets dish = "soup".
      4. 
    
    
  
    

  
    
  

  
    
  

  
    
    13
    
    Two ways to be told "it's ready". Both are everywhere in real code.
    
    
    
      
    CALLBACKorderFood(dish, callMeBack)

    PROMISEconst pager = cook(dish, ms)

      PART 4 · WHEN THE KITCHEN SAYS NORejected promises, try/catch, crashes and the pager that never buzzes
      

  
      
    23
    
    
      
      
      
      The chef says: Table seven, I'm sorry! We're out of lobster!
      
    
      
    
      
      
      
    
      
    
      A pager can buzz with bad news. The promise is then rejected: instead of a value, it holds an error. When you await a rejected promise, the error is thrown right there, at the await line, just like a throw in Chapter 12.
      
    
      Picture: the chef shouts an apology. Below, a pager with a dashed rim and crossed eyes says SORRY, next to a worried Kit. A burst says SORRY!
      
  
      

  
      
    24
    
      So the safety net from Chapter 12 works here too: put the await inside try, and handle the bad news in catch.
      
    try_await.js
    
      
    
      
    
        
      
      1. Pasta: line 5's pager buzzes with "pasta", line 6 runs, and catch is skipped.
        2. 
      
      2. Lobster: line 5's pager buzzes with an error. The await throws it, line 6 is skipped, and catch (error) receives the Error object. Its message is the text the kitchen wrote.
        3. 
      
      3. Because the error was caught, order("lobster") finishes normally, and The show goes on.
        4. 
    
      
    
      WRAP THE WAIT IN A SAFETY NET
      
  
      

  
      
    25
    
      And with no safety net? Kit orders lobster at the top level of a module, with nothing to catch the bad news.
      
    crash_reject.js
    
      
    
      
    
        
      
      1. The message: Error: we are out of lobster. Node stops the program, prints the error with its stack, and exits with code 1.
        2. 
      
      2. Where: the top lines point into kitchen.js:14, where the error was created, and the stack starts at Timeout._onTimeout: the kitchen's timer. Your file isn't in the stack at all!         4. 
    
      
  
      

  
      
    26

      PART 5 · ORDERING FROM ACROSS TOWNfetch, and the second pager from res.json()
      

  
      
    28
    
      The slowest jobs of all happen on other computers. A web server is a kitchen across town: you send it a request, and some time later a response comes back. fetch(url) places the order and, of course, hands you a pager.
      
    
      
      
      1 · ORDERawait fetch(url)
      Sends the request. Its pager buzzes as soon as the response starts arriving, and gives you a Response object: the delivery bag, still sealed.
      
      
      2 · UNPACKawait res.json()
      Reading the rest of the bag and decoding the JSON (Chapter 13) takes time too, so res.json() hands you a second pager.
      
      
      3 · EATorder.dish
      After both waits you have an ordinary object with ordinary properties.
      
    
      
    
      A real fetch goes over the internet, but this book's runs must be the same every time and work offline. So local_kitchen.js starts a tiny pretend restaurant on the same computer, for the length of one program, and closes it at the end. You don't need to understand it yet (it's Chapter 28's territory); read it only if you're curious.
      
    
      Show local_kitchen.jslocal_kitchen.js

        2.

        3.

      PART 6 · WHO GOES FIRST?The script, then promise callbacks, then timers
      

  
      
    32
    
      One last question. When a timer and a pager are both ready, which callback runs first? Kit has a fixed rule, with three lanes.
      
    
      
      
      1
      THE SCRIPTsynchronous code
      Every ordinary line, top to bottom, to the very end. Nothing interrupts it.
      
      
      2
      THE PAGER DESKpromise callbacks
      Callbacks from .then, and functions resuming after await. When the script is done, all of them run, including any new ones they add.
      
      
      3
      THE TIMER SHELFtimer callbacks
      Due setTimeout and setInterval callbacks, one at a time. After each one, Kit checks the pager desk again.
      
    
      
    
      
      
      
      Kit says: A buzzing pager is a guest who's already waited, so they go before anyone at the timer shelf. Programmers call the pager desk the microtask queue and the timer shelf a task queue. My clipboard of cues from Chapter 6 (and panel 4) turns out to be these two queues. The loop that keeps checking them is the event loop.
      
    
      
    
      Picture: three boxes. Lane 1, the script: synchronous code. Lane 2, the pager desk: promise callbacks. Lane 3, drawn with a dashed border, the timer shelf: timer callbacks. Kit points at them.

      What you learned in Chapter 16
      
    
        
      
      • "LATER" MEANS AFTER EVERYTHING ELSEJavaScript runs one piece of code at a time. setTimeout(callback, ms) runs a callback once, at least ms later, and only after the current code has finished (even with 0 ms). setInterval repeats until clearInterval(id); a forgotten interval keeps the program alive forever.
        • 
      
      • A PROMISE IS A PAGER, NOT THE SOUPA promise stands in for a value that isn't ready yet. Node prints it as Promise { <pending> } or, when ready, Promise { value }. pager.then(callback) runs the callback with the value when it arrives.
        • 
      
      • ASYNC ALWAYS HANDS YOU A PAGERAn async function always returns a promise. await unwraps one. Forgetting await gives a promise where you expected a value, and undefined for its properties. await outside an async function is a SyntaxError: Unexpected reserved word in a module, await is only valid in async functions and the top level bodies of modules in CommonJS.
        • 
      
      • AWAIT PAUSES ITS OWN FUNCTION. EVERYONE ELSE KEEPS TALKING.The caller of a paused async function carries on. Top-level await in a module pauses the module.
        • 
      
      • WRAP THE WAIT IN A SAFETY NETA rejected promise throws at its await; catch it with try/catch. Unhandled, it crashes Node with exit code 1, and the stack may not mention your file. A top-level await that can never settle ends with a warning and exit code 13. fetch(url) and res.json() are two pagers: await both.

      • THE SCRIPT, THEN THE PAGERS, THEN THE TIMERSSynchronous code first, then every promise callback (the microtask queue, emptied completely), then timer callbacks one at a time, with the promise callbacks checked again after each.

    Under the hood: the event loop, queues and what await really does
    
      
      
      One thread, one call stack
      
      
      A JavaScript engine (V8, inside Node and Chrome) runs your code on a single thread: one sequence of instructions at a time. The functions currently running are stacked on the call stack (Chapter 12's footprints). While anything is on the stack, nothing else can run. That's Kit's "one cue at a time", and it's why the busy loop in panel 5 held the timer back.
      
      
      Who does the waiting?
      
      
      Timers, network requests and file reads don't wait on that thread. Node hands them to a library called libuv, which uses the operating system to watch clocks and network sockets. When one finishes, its callback is put in a queue. Browsers do the same with their own machinery. So "the kitchen works on its own" is literally true: the waiting happens outside JavaScript.
      
      
      The event loop
      
      
      When the call stack is empty, the event loop picks the next thing to run. The microtask queue (the comic's pager desk) holds promise reactions: .then callbacks and the continuations of async functions after await. It is emptied completely, including microtasks added while emptying it, every time the stack becomes empty. Timers, I/O callbacks and similar work are tasks (sometimes called macrotasks); the loop runs one, then empties the microtasks again. Node does this after every single timer callback; puzzle_nested.js shows it on both Node versions this book used. Chapter 25 opens up Node's loop phases (timers, poll, check), setImmediate and process.nextTick.
      
      
      What await becomes
      
      
      Roughly, const x = await p; rest… means "subscribe to p; when it settles, resume this function with its value (or throw its error) and run rest…; meanwhile, return to whoever called me". The function's local variables are kept alive in the meantime: that's the paused frame in panel 19. An async function wraps everything in a promise: a return v fulfils it with v, a throw rejects it. And await on a value that isn't a promise (like await 5) still pauses until the microtask queue gets to it.
      
      
      Timer details
      
      
      In Node, a delay below 1 ms (or not a number) is treated as 1 ms; browsers also make deeply nested timers wait at least 4 ms. The delay is a minimum: a timer runs at the first chance after it's due. Timers that fall due together run in order of due time, then in the order they were created. In Node, setTimeout returns a Timeout object; in browsers it returns a number. Both work with clearTimeout.
      
      
      Why a promise prints as Promise { … }
      
      
      console.log in Node formats objects with util.inspect, which can see a promise's internal state: <pending>, the value when fulfilled, or <rejected> followed by the error. Browser consoles show the same information in their own style. Your code can't read that state directly: the only way to get the value is to wait for it.
      
      
      Exit codes 1 and 13
      
      
      An unhandled rejection is treated like an uncaught exception: printed, then exit code 1. Node's process documentation (checked 2026-11-08) gives throw as the default of the --unhandled-rejections option, which can change this; the default is the safe one. Exit code 13 is listed in Node's documentation as "Unsettled Top-Level Await": the event loop ran out of work while the main module was still waiting at a top-level await.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • Almost all input and output is async. Reading files (import { readFile } from "node:fs/promises"), talking to databases, calling web APIs, waiting for a user's click: they all hand you a promise or take a callback, so the program stays responsive while it waits.
        • 
        
      • Servers live on this. A Node web server handles thousands of visitors on one thread because, while one request waits for its database, the event loop serves others.
        • 
        
      • Web pages too. A page that loads data uses fetch plus await res.json(), then updates the DOM (Chapter 15). A page that froze during every request would be unusable.
        • 
        
      • Three generations of style. Old code passes callbacks (often (error, result) => …, Node's "error-first" style). Code from around 2015 chains .then().catch(). Modern code uses async/await with try/catch. You'll read all three; Chapter 24 shows how they convert into each other.
        • 
        
      • Timers for real jobs: polling a server every few seconds with setInterval, giving up on a slow job with a timeout, debouncing a search box (wait until the user stops typing), or retrying after a short pause.
        • 
        
      • Linters catch forgotten awaits. Tools like ESLint and TypeScript have rules (such as "no floating promises") that warn when a promise is created and then ignored, the sneak from panel 20.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "setTimeout(f, 0) runs f immediately." It runs after the current code has finished, and after every waiting promise callback.
        • 
        
      • "setTimeout(f, 1000) runs f exactly one second later." At least one second later, as soon as Kit is free.
        • 
        
      • "Async code runs in parallel, on another thread." Your JavaScript still runs one piece at a time. Only the waiting happens elsewhere.
        • 
        
      • "await freezes the whole program." It pauses only its own async function (or the module, for top-level await). Everything else carries on.
        • 
        
      • "A promise is the value." It's a pager for the value. You need await or .then to get the value out.
        • 
        
      • "An async function returns what its return says." It returns a promise of that.
        • 
        
      • "try/catch around an async call catches its errors." Only if you await it inside the try (Boss 6).
        • 
        
      • "If a promise fails and I don't handle it, nothing happens." In Node the whole program crashes with exit code 1.
        • 
        
      • "fetch gives me the data." It gives a pager for the response; res.json() gives a second pager for the data.
        • 
        
      • "fetch rejects when the server says 404." It only rejects when no response arrives at all (Chapter 28).
        • 
        
      • "Promises run before timers because they're faster." It's a fixed rule about queues, not speed.
        • 
        
      • "I can use await inside forEach." The callback is its own function; it needs async, and even then forEach won't wait for it. Use for…of.

    Words from this chapter
    
      
      
      
        
      synchronous
      Running one step after another, each finished before the next starts.
      
        
      asynchronous (async)
      Part of the work happens later, while the program does other things.
      
        
      millisecond (ms)
      A thousandth of a second. Timer delays are in milliseconds.
      
        
      callback
      A function handed to other code to be called later: "call me back".
      
        
      setTimeout(callback, ms)
      Runs the callback once, at least ms later, after the current code has finished. Returns a timer id.
      
        
      setInterval(callback, ms)
      Runs the callback every ms milliseconds until stopped. Returns a timer id.
      
        
      clearInterval(id) / clearTimeout(id)
      Stops a repeating timer, or cancels a reminder that hasn't rung yet.
      
        
      timer id
      The value a timer function returns, used to stop that timer.
      
        
      promise
      An object standing in for a value that isn't ready yet. The comic's pager.
      
        
      pending
      A promise that has no value yet. Printed Promise { <pending> }.
      
        
      fulfilled
      A promise that has its value. Printed Promise { value }.
      
        
      rejected
      A promise that came back with an error instead of a value.
      
        
      settled
      Fulfilled or rejected: no longer pending. Final.
      
        
      .then(callback)
      Registers a callback to run with the promise's value when it is fulfilled.
      
        
      Promise.resolve(value)
      Makes a promise that is already fulfilled with value: a pager that's already buzzing.
      
        
      async function
      A function marked with async. It always returns a promise and may use await.
      
        
      await
      Pauses the current async function (or module) until a promise settles, then gives its value or throws its error.
      
        
      top-level await
      await outside any function, allowed in ES modules. It pauses the module.
      
        
      reserved word
      A word the language keeps for a special job, such as await, class or return.
      
        
      unhandled rejection
      A rejected promise that no code ever handles. Node crashes with exit code 1.
      
        
      exit code 13
      Node's code for a top-level await that could never settle.
      
        
      fetch(url)
      Sends a request to a web server and returns a promise for the Response.
      
        
      Response
      What fetch gives you: status, headers and a body still to be read.
      
        
      res.json()
      Reads the response body and decodes it as JSON. Returns a promise.
      
        
      web server
      A program that answers requests over a network. The kitchen across town.
      
        
      thread
      One sequence of instructions running at a time. JavaScript runs your code on one.
      
        
      event loop
      The loop that runs callbacks from the queues whenever the call stack is empty.
      
        
      microtask queue
      The queue of promise callbacks (the pager desk). Emptied completely before any timer runs.
      
        
      task queue
      Where timer and other callbacks wait (the timer shelf). One runs at a time.

BRICKS AND TRAY STACKS

Picture: Kit, the stage manager in a pink hoodie and headset, waves hello. On one side is a yellow building brick with four studs on top. Its side says price(2, 5), and a tag under it says arrow 35. Functions have been machines since Chapter 7. Today you learn two ways to build big things out of them. First, bricks: functions that always give the same answer for the same input and never mess with anything else. Bricks like that click together into pipelines, rows of machines on a belt. You'll meet the copy-making array methods that keep you from changing someone else's data by accident. Then, trays: a function that calls itself, stacking one tray per call, until it reaches the bottom of the problem. About 140 minutes, with 27 hands-on checks.

A pure function is a brick that follows two rules. Break either rule and the brick gets odd: it might click today and wobble tomorrow.

    

      
Rule 1same in, same out
Give it the same arguments and it gives back the same answer. Every time, no matter what happened before. Its answer depends only on what you hand it.

      
Rule 2no side effects
It doesn't change anything outside itself. A side effect is anything a function does besides handing back its answer: changing an outside variable, changing an object or array it was given, printing, saving a file.

    

    

      
      
      
    

    
Picture: three building bricks. A mint brick says price(2, 5) with a tag saying 35. A sky-blue brick says Math.max(3, 9) with a tag saying 9. A pink brick in a dashed frame says price(2) with a tag saying 35? 30? 25?

    

      
      
Kit says: "Pure" doesn't mean clean or good. It's a technical word: same in, same out, and hands off everything else.

    COPY, DON'T CHANGE
    
  
    

  
    
  


  
    
    11
    
    ES2023 gave four old array methods a careful twin. The old one changes the array it's called on. The twin, whose name starts with to or is with, makes a changed copy.
    
    
    
      
    JobChanges the originalMakes a copy
    
      
        
    put in ordera.sort(fn)✗ changes a, hands back aa.toSorted(fn)✓ new array
    
        
    flipa.reverse()✗ changes a, hands back aa.toReversed()✓ new array
    
        
    cut out / put ina.splice(start, count, …items)✗ changes a, hands back the removed itemsa.toSpliced(start, count, …items)✓ new array with the change
    
        
    replace one itema[i] = value✗ changes aa.with(i, value)✓ new array with one item swapped
    
          
    
    
    
    Some methods never change the original and always did: map, filter, slice, concat, flat, flatMap. Others always change it: push, pop, shift, unshift, fill, copyWithin. When you're unsure, check the docs, or run it and print the original afterwards.

    PART 3 · THE BUCKET ON THE BELTreduce patterns: count, index, group, and the empty-array crash
    


  
    
    18
    
    Chapter 9's reduce walks the belt with a bucket, the accumulator: the running result. At each item, your function gets the bucket and the item and hands back the bucket for the next step. The second argument to reduce is the empty bucket it starts with. Change the starting bucket and you get a different tool.
    
    
    
      
    A NUMBER
    start: 0
    Add each item in: totals, sums, the longest, the biggest.
    
      
    AN OBJECT OF COUNTS
    start: {}
    One drawer per kind of item, holding how many: a tally.
    
      
    AN OBJECT OF LISTS
    start: {}
    One drawer per group, holding a list: grouping. Or one drawer per id: an index.
    
    
    
    
    
      
      
    Kit says: Is changing the bucket inside reduce a side effect? Only inside. The bucket is a brand-new {} that reduce made for this one job, and nobody else holds it. The original array is never touched, so the whole reduce is still a brick.

    debounce.js

        3.

          What you learned in Chapter 21
          
    
            
      
          • SAME IN, SAME OUTA pure function's answer depends only on its arguments, and it has no side effects: no changing outside variables or its arguments, no printing. Pure functions are bricks: easy to test, reuse, combine and memoize. Higher-order functions take or hand back functions; Array.from({ length: n }, fn) builds an array from a recipe.
            • 
      
          • COPY, DON'T CHANGEsort, reverse, splice and a[i] = v change the original, even a caller's array. Their twins toSorted, toReversed, toSpliced and with make copies. with past the end gives RangeError: Invalid index : 3. reduce buckets count, index and group; without a starting bucket, an empty list gives TypeError: Reduce of empty array with no initial value.
            • 
      
          • ONE MACHINE, ONE JOBA pipeline lines up one-input bricks: pipe left to right with reduce, compose right to left with reduceRight. Currying and partial application turn many-input functions into one-input machines. Debounce is a function that hands back a function. Name the steps instead of writing clever chains, and follow the footprints to your line when a belt jams (fn is not a function).
            • 
      
          • A FLOOR AND A SMALLER STEPRecursion is a function calling itself. It needs a base case that answers without calling, and a recursive case that moves closer to it. Without both: RangeError: Maximum call stack size exceeded, from a missing floor, a floor that can be stepped over, or the same input again. Recursion fits nested data best: deep flatten, trees, JSON; loops fit flat data and big inputs.
            • 
      
          • ONLY THE TOP TRAY RUNSEach call gets its own frame on the call stack, a tray with its own variables. Calls pile up on the way in and leave last in, first out, each handing its answer to the tray below. Memoization saves answers so repeated calls are skipped. Node doesn't reuse trays for tail calls.
            • 
      
          • RETURN IT, OR LOSE ITA recursive case that works out an answer without return hands back undefined, and the trays below get nothing, or NaN.

    Under the hood: frames, the stack limit and the copying methods
    
          
      
          What a tray really is
          
      
          Each call creates an execution context: the standard's name for the record of one call in progress. It holds the call's own variables (its environment), its this, and where to carry on when it finishes. The engine keeps these on the execution context stack, which everyone calls the call stack. The running context is always the top one. Returning pops it, and the one underneath resumes exactly where it paused, in the middle of its expression.
          
      
          Why the limit isn't a number of calls
          
      
          V8 reserves a fixed amount of memory for the stack, and each frame takes up space according to how many arguments and local variables it has. So the number of trays that fit depends on the function: a frame with many locals uses more room. That's why this book never prints "how deep can I go?": the answer changes from function to function and between Node versions. Node has a --stack-size option, but raising it far can crash the process outright instead of throwing a catchable RangeError, so don't treat it as a fix.
          
      
          Why exactly ten footprints
          
      
          V8 records at most Error.stackTraceLimit frames in an error's stack, and the default is 10. A runaway recursion therefore shows ten identical at … lines, however deep it went. You can set Error.stackTraceLimit = 50 at the top of a program while debugging.
          
      
          The copying methods, precisely
          
      
            
        
          • toSorted, toReversed, toSpliced and with came from the ES2023 "change array by copy" proposal. They always return a brand-new ordinary array.
            • 
        
          • They treat holes in sparse arrays (Chapter 9) as undefined, so the copy has no holes.
            • 
        
          • with(i, v) accepts -length up to length - 1, and anything outside that range throws a RangeError. It never grows the array.
            • 
        
          • Typed arrays (such as Uint8Array) have toSorted, toReversed and with, but not toSpliced, because a typed array's length can't change.
            • 
        
          • Since ES2019, sort and toSorted must be stable: items that compare as equal keep their original order.
            • 
      
          
      
          reduce, exactly
          
      
          With a starting value, the callback runs once per item. Without one, the first item becomes the bucket and the callback runs from the second item, so a one-item list returns that item without calling the callback, and an empty list throws the TypeError. The callback also receives the index and the whole array as third and fourth arguments. reduceRight is the same, walking from the last item.
          
      
          Spreading into a call
          
      
          out.push(...flatten(item)) passes every item as a separate argument. For extremely large arrays (hundreds of thousands of items) that can itself throw a RangeError, because arguments live on the stack too. For huge data, push in a loop or use concat.
          
      
          Tail calls in the standard
          
      
          ES2015 specifies "proper tail calls": in strict-mode code, a call in tail position (return f(…) with nothing left to do) must not grow the stack. V8, the engine in Node, doesn't do it, as tail.js shows; this book didn't run other engines. One cost of reusing trays: the reused frames would vanish from stack traces. In practice, write deep repetition as a loop.
          
    
          
  
          

  
          
    In real programs
    
          
      
            
        
          • User-interface state: React and Redux-style code expects state to be updated by copy, with spreading, map, filter, toSorted and friends, never in place. The framework compares the old and new arrays with === to decide what to redraw, so a sort in place can leave the screen stale.
            • 
        
          • Functional libraries: Lodash (lodash/fp) and Ramda provide pipe, compose, curry, memoize, debounce and throttle. A pipeline operator, value |> f, has been a proposal for JavaScript for years; until it lands, pipe helpers and method chains do the job.
            • 
        
          • Debounce and throttle are everywhere on the web: search-as-you-type, saving drafts, resizing and scroll handlers. Chapter 25 explains the timers, and Chapter 29 builds both.
            • 
        
          • Recursion walks every tree a program meets: the DOM (Chapter 15's tree of elements), JSON from APIs, nested comments and menus, folders on disk (Node's fs.readdir even has a recursive option), syntax trees in compilers, linters and formatters, and the built-in structuredClone, which deep-copies nested data.
            • 
        
          • Memoization shows up as caches: React's useMemo, the "dynamic programming" technique in algorithms (Chapter 29), and HTTP caching, all with the same rule: only cache what is pure.
            • 
        
          • Tests love pure functions. A pure function needs no setup and no clean-up: one input, one expected output (Chapter 27).
            • 
      
          
    
          
  
          

  
          
    Common wrong ideas
    
          
      
            
        
          • "A function can't change my array; it only gets a copy." It gets an arrow to the same array (panel 9). Primitives like numbers are safe; objects and arrays are not.
            • 
        
          • "const stops sort changing the array." const glues the name; sort rearranges the array behind it. Freeze it, or use toSorted.
            • 
        
          • "reverse() returns a reversed copy." It reverses in place and returns the same array (predict_copy.js).
            • 
        
          • "splice and toSpliced return the same thing." splice returns the removed items; toSpliced returns the new array.
            • 
        
          • "Spreading makes a deep copy." One layer only. Inner arrays and objects are shared (update.js, line 8).
            • 
        
          • "Pure means no variables change." Local variables inside the function may change freely. Pure is about what the outside world can see.
            • 
        
          • "Pure code can't print." Programs need side effects. Keep them in a few named places at the edges.
            • 
        
          • "Shorter chains are better code." Clearer code is better code (panel 22).
            • 
        
          • "Recursion is slow / always better / only for experts." It's a tool for self-similar problems. Plain recursion like fib can redo work; memoization fixes that.
            • 
        
          • "The base case has to be the first line." It has to be reachable on every path. It can be implicit, like a loop over an empty list.
            • 
        
          • "A RangeError means my numbers were too big." In recursion it almost always means the floor was missed or the step didn't shrink.
            • 
        
          • "Recursive calls share the same n." Each call has its own frame with its own variables (panel 35).

    Words from this chapter
    
          
      
          
        
          pure function
          A function whose answer depends only on its arguments and which has no side effects. Same in, same out.
          
        
          side effect
          Anything a function does besides handing back its answer: changing an outside variable or an argument, printing, saving.
          
        
          higher-order function
          A function that takes a function as an argument, hands one back, or both: map, twice, pipe, debounce.
          
        
          first-class functions
          Functions treated as values: stored in variables, passed along and handed back.
          
        
          mutate, mutation
          To change an existing object or array in place.
          
        
          immutable, immutable update
          Never changed after it's made; an update done by making a changed copy.
          
        
          hidden mutation
          A function changing data its caller still uses, without saying so.
          
        
          toSorted, toReversed, toSpliced, with
          The copy-making twins of sort, reverse, splice and index assignment.
          
        
          flat, flatMap
          Unpack nested arrays by some number of layers; map, then unpack one layer.
          
        
          accumulator
          The running result (the bucket) that reduce carries from item to item.
          
        
          tally, index, grouping
          Three bucket shapes: counts per kind, one item per id, lists per group.
          
        
          pipeline
          A row of functions where each one's output is the next one's input.
          
        
          pipe, compose
          Helpers that join functions into one: left to right, or right to left.
          
        
          currying
          Writing a function to take its arguments one at a time, each call handing back a function for the next.
          
        
          partial application
          Fixing some of a function's arguments in advance, making a function that needs fewer.
          
        
          debounce, throttle
          Wrappers that squash rapid calls into one after a quiet moment, or let at most one through per time window.
          
        
          declarative, imperative
          Code that says what it wants (filter, map) versus code that spells out each step (loops and pushes).
          
        
          recursion, recursive function
          A function that calls itself on a smaller version of the problem.
          
        
          base case
          The input small enough to answer without another call: the floor.
          
        
          recursive case
          The part that does a little work and calls the function again, closer to the base case.
          
        
          call stack, frame
          The pile of calls in progress, newest on top; each call's own record of variables (one tray).
          
        
          stack overflow
          Running out of stack space: RangeError: Maximum call stack size exceeded.
          
        
          factorial
          The product of the whole numbers from 1 to n, written n!. 4! = 24.
          
        
          tree, node, children, leaf
          Nested data where each node may contain child nodes; a node with no children is a leaf.
          
        
          palindrome
          A word that reads the same backwards, like "level".
          
        
          Fibonacci numbers
          0, 1, then each number is the sum of the two before.
          
        
          memoization
          Saving each answer so a repeat call with the same input is answered from the notebook.
          
        
          tail call
          A call that is the very last thing a function does. Not optimized in V8.

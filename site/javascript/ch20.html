CHAPTER 20

COAT CHECKS AND DISPENSERS

Picture: Kit, the stage manager in a pink hoodie and headset, waves hello. On one side is a coat-check counter labelled new Map(), with two coats on hooks: a scarf whose ticket says 'Ada', and a hat whose ticket is an object, drawn as curly braces. On the other side is a candy dispenser labelled next(), its head tipped back, popping out a candy that says 'red', with a tag that says done: false.

Arrays keep things in a row; objects keep them in labelled drawers. Today you meet four new containers and a new way of handing things out. A Map is a coat check that accepts any ticket, even an object. A Set is a guest list where each name appears once. A WeakMap is a coat check that quietly forgets. Then the machinery behind every for...of loop: a candy dispenser that pops out one value per press, and the storyteller, a function that can pause in the middle of a sentence and carry on later. About 140 minutes, with 28 hands-on checks.

  1. The coat check: Map
  2. The guest list: Set
  3. The coat check that forgets: WeakMap and WeakSet
  4. The candy dispenser: iterators
  5. The storyteller: generators
  6. Boss level and recap

What Kit needs is a coat check. You hand over a coat and get a ticket; later you show the ticket and get your coat back. JavaScript's coat check is called a Map. Its superpower: anything can be the ticket. Text, a number, true, NaN, even an object or a function. The ticket is called the key; the coat is the value; a key with its value is an entry.

    PART 3 · THE COAT CHECK THAT FORGETSWeakMap and WeakSet
    

  
    
    19
    
    An ordinary coat check keeps a coat for as long as the coat check exists, even if its owner left hours ago and nobody will ever ask for it. A WeakMap is a coat check with a different rule: once the owner has left the building, the coat can be thrown away. The ticket must be an object (the owner), and the WeakMap never stops that object from being cleaned up.
    
    
    
      
    
    
    
    Picture: a coat-check booth drawn with a dashed outline, with a WEAK plate and the label new WeakMap(). Two notes hang on hooks: no feathers, ticket ada; a chair, ticket bo. At the right is a door marked EXIT, with an arrow pointing out through it.
    
    
    
      
      
    Professor says: JavaScript cleans up memory by itself. When no variable, object or list can reach an object any more, it is garbage, and the garbage collector may reclaim its memory, at a time of its own choosing. "Weak" means: this coat check doesn't count as a way of reaching the ticket.
    
    
    
  
    

  
    
    20
    
    Kit keeps private notes about actors without writing on the actor objects themselves.
    
    weak_cache.js
    
    
    
    
    
      
      
    1. Lines 3 to 5: set, get and has work as on a Map. Object tickets are compared by identity, so the look-alike gets false.
      2. 
      
    2. Line 6: there is no size (undefined). Line 7: Node can't even show the contents: WeakMap { <items unknown> }. A WeakMap can't be counted, listed or looped over, because an entry might disappear at any moment; any count would already be out of date.
      3. 
      
    3. Line 8: the last arrow to Ada's object is gone. Now nothing can reach her, so her note may be cleaned up: later, or never if the program ends first. No JavaScript code can watch it happen, which is the whole point. This book never prints garbage-collector timing, because it changes from run to run.
      4. 
    
    
  
    

  
    
    21

    22
    
    A WeakSet answers just one question: "have I seen this object before?" without keeping the object alive.
    
    weakset.js
    
    
    
    
    
    Line 8 greets Ada and adds her object to seen. Line 9 passes the same object: Ada again!. Line 10's look-alike is a new object, so it's welcomed as a stranger. If Ada's object is ever thrown away, so is its place in seen.
    
    
    You may also meet WeakRef: a single weak arrow to an object, which you can ask "is it still there?" Because the answer depends on when the garbage collector last ran, its behaviour differs from run to run, and experts advise using it rarely. It isn't used in this book.

    PART 4 · THE CANDY DISPENSERThe iteration protocol: next(), value and done
    

  
    
    24
    
    
    Arrays, strings, Maps and Sets all work with for...of and with [...]. Objects don't. Kit wants to know what the loop is really doing.
    
    
    
      
      
      
    
    
    
    Picture: three candy dispensers in a row. The first pops out a candy saying value: 'red' with a tag done: false. The second pops out value: 'lime' with done: false. The third is empty, with a dashed candy saying undefined and a tag done: true.
    
    
    
      
      
    Kit says: It's a candy dispenser! Every collection can hand you a dispenser. Each press gives one candy, plus a tag that says whether that was the end. One candy at a time, like one cue at a time.
    
    
    
  
    

  
    
    25
    
    The dispenser is called an iterator, and pressing it is calling its next() method. You ask a collection for one with its [Symbol.iterator]() method, the well-known symbol from Chapter 19.
    
    next_by_hand.js
    
    
    
    
    
      
      
    1. Line 2: candies[Symbol.iterator]() gives a brand-new dispenser loaded with the array's items.
      2. 
      
    2. Lines 3 and 4: each next() returns a small object with two drawers: value, the candy, and done, which is false while candies are still coming.
      3. 
      
    3. Lines 5 and 6: once it's empty, next() returns { value: undefined, done: true }, and keeps returning it however often you press.
      4. 
    
    
    
    That's the whole iteration protocol, a promise between two pieces of code: "I have a [Symbol.iterator]() method that returns an object with a next() method that returns { value, done }." Anything that keeps that promise is iterable.

    Under the hood: hash tables, SameValueZero, the iteration protocol and generator states
    
      
      
      How a Map finds a key so fast
      
      
      The standard only requires that Map and Set lookups take, on average, less time than looking through every entry ("sublinear"). Engines use hash tables: the key is turned into a number (its hash) that says roughly where to look, so get, set, has and delete take about the same time whether the Map holds ten entries or ten million. V8 uses an ordered hash table that also keeps entries in a list, which is how insertion order is remembered. An object's identity is hashed, never its contents, which is why a look-alike object can't find an entry.
      
      
      SameValueZero, SameValue and ===
      
      
      The standard has several equality rules. IsStrictlyEqual (===) says NaN is not equal to itself and 0 equals -0. SameValue (Object.is) says NaN equals NaN and 0 does not equal -0. SameValueZero takes the friendly half of each: NaN equals NaN and 0 equals -0. Map keys, Set members, Array.prototype.includes and the Set methods all use SameValueZero. (A Map stores a key of -0 as +0.)
      
      
      Set-like objects
      
      
      The ES2025 Set methods don't demand a real Set as their argument. They read three things from it, through the abstract operation GetSetRecord: a size that converts to a number (otherwise The .size property is NaN), a has method and a keys method. A Map passes, so set.intersection(map) compares members with the Map's keys. An array fails on size. Results always come back as a new Set; the order of members in some results depends on which Set is smaller, so don't rely on it for intersection.
      
      
      The iteration protocol, exactly
      
      
      The standard's GetIterator calls obj[Symbol.iterator]() and checks the result is an object (Result of the Symbol.iterator method is not an object otherwise). IteratorStep calls next() and reads done and value. When a consumer stops early (break, return, an error, destructuring that needs fewer values), IteratorClose calls the iterator's return() method if it has one. Built-in iterators such as array iterators inherit from %IteratorPrototype%, whose [Symbol.iterator]() returns this: that's why it[Symbol.iterator]() === it. Since ES2025 that prototype is reachable as Iterator.prototype, and it's where the helpers live; Iterator.from(obj) wraps any object with a next() so it gets the helpers too.
      
      
      Generator states
      
      
      The standard tracks a generator's [[GeneratorState]]: suspended-start (created), executing (running), suspended-yield (paused) and completed (done), the four boxes of panel 34. Pausing works by saving the function's whole execution context (its local variables and the spot it stopped at) and restoring it on the next next(). Calling next() on a generator that is currently executing (from inside itself) throws Generator is already running. next(x) also sends a value in: x becomes the result of the paused yield expression (the first next's argument is ignored, since no yield is waiting). gen.throw(err) makes the paused yield throw. Chapter 25's async generators build on all of this.
      
      
      Iterator helpers are lazy and single-use
      
      
      Each helper (map, filter, take, drop, flatMap) returns a new "Iterator Helper" object wrapping the old iterator, and does no work until pulled. take calls the underlying iterator's return() after its last value, which is why the infinite naturals() in lazy_log.js never makes number 3. toArray, reduce, forEach, some, every and find consume. Like all iterators, a helper can be used up only once.
      
      
      Weak collections
      
      
      A WeakMap entry behaves like an ephemeron: the value is kept alive only as long as the key is reachable from somewhere else. That's why WeakMaps make good caches of extra data about objects. The standard deliberately gives no way to observe collection, so programs behave the same whatever the garbage collector does. WeakRef and FinalizationRegistry (ES2021) are the exceptions that let you observe it, and the standard warns that their timing is unpredictable.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • Caches: a Map from an input to a slow result ("memoising") is everywhere: cache.getOrInsertComputed(url, fetchAndParse). When the input is an object you don't own, a WeakMap stops the cache from leaking memory.
        • 
        
      • Extra data about DOM elements: front-end code keeps a WeakMap from page elements to their state (which tooltip belongs to which button), so removed elements don't linger. Frameworks use the same trick internally.
        • 
        
      • Counting and grouping: word counts, log lines per level, orders per customer. Map.groupBy (Chapter 19) and getOrInsert(key, []).push(item) are the modern ways.
        • 
        
      • Sets for membership: "has this user already voted?", "which tags are in use?", deduplicating search results, finding new or removed items between two lists with difference, permissions checks with isSubsetOf.
        • 
        
      • Graph and search algorithms keep a visited Set so they never process the same node twice (Chapter 29).
        • 
        
      • Generators produce IDs (nextId()), walk tree structures, page through results from a server one page at a time, and power the for await...of loops over streams you'll meet in Chapter 25. Some libraries (for example, the redux-saga library for React apps) are built entirely around generator functions.
        • 
        
      • Lazy pipelines with iterator helpers process huge files line by line, or endless event streams, without loading everything into memory at once.

    Common wrong ideas
    
      
      
        
        
      • "map[key] = value adds an entry." It adds an ordinary property; get, has and size can't see it (panel 7).
        • 
        
      • "Two objects with the same contents are the same key." Object keys and members match only the very same object (panels 4, 5 and 15).
        • 
        
      • "A Map is just an object with a different syntax." Keys keep their types, nothing is inherited, it has size, and its order is always insertion order.
        • 
        
      • "JSON.stringify saves my Map." It writes {} without complaint. Convert with Object.fromEntries or [...map] first.
        • 
        
      • "new Set(5) makes room for five." The argument is an iterable to read members from.
        • 
        
      • "A Set is sorted." It keeps insertion order. Sort with [...set].sort() (or toSorted, Chapter 21).
        • 
        
      • "I can count or list a WeakMap." No size, no looping, no keys(). That's the price of forgetting.
        • 
        
      • "Every object works with for...of." Only iterables. Plain objects need Object.entries (or for...in).
        • 
        
      • "An iterator can be looped over again." Iterators, including generator objects and map.keys(), are single-use. Iterables like arrays hand out a new iterator each time.
        • 
        
      • "Calling a generator function runs it." It only creates the generator object. The body starts at the first next().
        • 
        
      • "for...of sees the generator's return value." It stops at done: true and drops that value.
        • 
        
      • "Infinite generators freeze the program." Only if you try to collect all of their values. Pulled lazily, they're perfectly safe.
        • 
        
      • "Iterator helpers are just array methods." They're lazy and single-use, and toArray() must still be called to get an array.

    Under the hood: exceptions are objects with a family tree
    
        
      
        An exception is an ordinary Python object. raise creates one and throws it. Python then leaves the current function, then the one that called it, and so on up the call stack, until an except clause matches it. If none does, the program stops and prints the traceback. Leaving functions on the way up is called propagating, or unwinding the stack.
        
      
        The family tree
        
      
        Every exception kind is a class, and classes have parents. An except clause catches its own kind and all its children. Here's the part of the tree you've met (★ = in this chapter's gallery):
        
      
        
        
      
        
      
        Don't take the drawing's word for it. This program asks Python for each kind's line of parents (its __mro__):
        
      
        
      
        Catching a parent catches its children
        
      
        LookupError is the parent of both IndexError and KeyError, so one net catches both:
        
      
        
      
        Why a bare except is worse than it looks
        
      
        SystemExit (raised by sys.exit()) and KeyboardInterrupt (raised when you press Ctrl+C) sit outside Exception, so except Exception: lets them through. A bare except: catches everything, including them. Here it swallows a real request to quit:
        
      
        
      
        Those ~~~^^^ marks
        
      
        Modern Python underlines the exact part of a line that failed: ~ for the surrounding expression and ^ for the operation or value that broke. This arrived in Python 3.11. Both versions used for this comic print them.
        
    
        
  
        

  
        
    Version notes: where 3.15 and 3.13 really differ
    
        
      
        Every program in this chapter was run on two Pythons. These are the only two that printed something different.
        
      
        1. A friendlier AttributeError
        
      
        
        
        
        
        
      
        
      
        The newer build suggests the method you probably meant. Same error, same fix; the older one just doesn't hint.
        
      
        2. Several kinds in one except, without brackets
        
      except_no_parens.py
        
      
        
        
        
        
        
      
        
      
        Python 3.14 started allowing except ValueError, TypeError: (PEP 758). Older versions need brackets: except (ValueError, TypeError):. The bracket form works everywhere, so use it.
        
    
        
  
        

  
        
    In real programs
    
        
      
        Ask forgiveness, or look before you leap?
        
      
        Python people have names for the two styles. Look before you leap checks first: if item in prices:. Easier to ask forgiveness than permission just tries, and catches the failure: try: prices[item] / except KeyError:. Both are fine. Python code often uses the second, especially when the check would repeat the work or the situation could change between check and use (files are the classic case).
        
      
        Keep the try small
        
      
        Put only the risky line in the try. Everything that should run only on success goes in else. A big try block catches errors from lines you never meant to protect, which is the bare-except trap in disguise.
        
      
        Cleaning up
        
      
        finally is how programs make sure something always happens: close a file, release a connection, save a log. In Chapter 10 you'll meet with open(...), which closes the file for you even when an error happens.
        
      
        Users never see tracebacks
        
      
        Real apps catch errors near the top, show the user a friendly message, and write the full traceback to a log file (Python's logging module) for the programmers.
        
      
        assert is for programmers, not for users
        
      
        Python skips assert statements entirely when run with the -O (optimize) option. So use assert to check your own assumptions and in tests, but use if plus raise to check what users type.
        
      
        Testing tools
        
      
        The tiny test_double function is exactly how the popular pytest tool works: functions whose names start with test_, full of plain asserts. Python also ships its own unittest module.
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "The line in the error is the line to fix." It's where Python noticed. The bad value may come from much earlier (Panel 18).
          • 
        
        • "No error means my program is right." Sneak says hi. Logic bugs make no noise (Panel 19).
          • 
        
        • "try/except fixes bugs." It handles problems you expect, like bad typing. Wrapping buggy code in try/except just hides the bug.
          • 
        
        • "A bare except: is the safest choice." It hides typos and even swallows Ctrl+C and sys.exit().
          • 
        
        • "Two tracebacks means two separate crashes." When an error happens inside an except block, Python prints both, joined by a "During handling" line. Fix the last one first; the first is the background story:
          
          • 
        
        • "finally catches errors." It doesn't catch anything. It runs, and a loose error carries on afterwards.
          • 
        
        • "else runs when the except runs." The opposite: else runs only when the try had no error.
          • 
        
        • "assert is a good way to check input." Asserts can be switched off with -O. Use if and raise.
          • 
        
        • "SyntaxError can be caught with try/except in the same file." No: the Proofreader rejects the whole file before any line, including your try, gets to run.

    Words from this chapter
    
        
      
        
        
        exception
        An error raised while the program runs. It's an object with a kind (its class) and a message.
        
        
        raise
        Create an exception and throw it. Python raises them; so can you: raise ValueError("why").
        
        
        traceback
        The report printed when an exception isn't caught. Read it bottom to top.
        
        
        call stack
        The pile of function calls that haven't finished yet, one frame each.
        
        
        frame
        The workspace for one function call: its own names and values.
        
        
        propagate
        An uncaught exception leaves each function in turn, climbing the call stack.
        
        
        try / except
        Run risky code; if a named exception happens, run the except block instead of crashing.
        
        
        bare except
        except: with no kind named. Catches everything. Avoid.
        
        
        else (on try)
        Runs only if the try block raised nothing.
        
        
        finally
        Runs on every road: no error, handled error, or crash.
        
        
        logic bug
        The program runs without errors but gives the wrong result.
        
        
        debugging
        Finding and fixing bugs.
        
        
        rubber duck
        Explaining code line by line, out loud, to find the gap in your thinking.
        
        
        halving
        A debugging trick: check the middle, then search only the half where things go wrong.
        
        
        minimal reproduction
        The smallest program that still shows the bug.
        
        
        assert
        assert condition, "message": raises AssertionError if the condition is false.
        
        
        test
        Code that checks your code against answers you already know.
        
        
        attribute
        A tool or value reached with a dot, like .append or .upper.

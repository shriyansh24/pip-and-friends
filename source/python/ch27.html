Part 1 · The busy cafémost programs spend their time waiting, and waiting can be shared

1

Every morning Pip phones three suppliers for today's prices: flour, milk and eggs. Each call means a second on hold. Meanwhile the café fills up.

Pip says: I call the mill and wait. Then I call the dairy and wait. Then the farm, and wait. I'm not doing anything while I wait! Couldn't somebody else make the next call?

The Professor says: That's the question of this chapter's first half: how a program can deal with several jobs at once. Think of a restaurant. One waiter who stands at each table until the food comes is slow. A good restaurant hires waiters, opens more kitchens, or trains one waiter never to stand still.

2

This last chapter leans on a lot of earlier ones. If one feels shaky, its chapter has the full story.

  1. Functions are values (Chapter 17): you can hand a function to another function without calling it. That's how you give a waiter a job.
  2. Key cards (Chapter 22): a with block takes something and always gives it back. A lock works exactly like that. Chapter 22 also showed exception groups, which come back in Part 4.
  3. The __name__ guard and a first look at sys.argv (Chapter 13).
  4. Files, CSV and JSON (Chapters 10 and 12), paths with pathlib, and exceptions (Chapters 9 and 22).
  5. Tests with pytest (Chapters 14 and 26), and timing with time.perf_counter() (Chapter 18; Chapter 24 measured with timeit).

Pip says: So the question to ask about any slow job: is it waiting or working? A job that mostly waits (for the network, a disk, a person) is I/O-bound: I/O means input and output. A job that mostly calculates is CPU-bound. My rule: WAITING CAN BE SHARED. WORKING NEEDS MORE HANDS.

The operating system's scheduler decides which thread runs next, and it can switch at almost any moment. So programs that use threads should never rely on the order things happen in, unless they arrange that order themselves: by joining before printing, as Panel 7 did.

Picture: a kitchen door with a turnstile and a sign saying one at a time, and Ben carrying a tray through it.

    

      
The Professor says: Here is the catch. In the standard Python build, only one thread at a time may run Python code. The rule is called the GIL, the Global Interpreter Lock: the kitchen door. A waiter on hold steps out of the kitchen, so waiting threads overlap beautifully. But two waiters who both want to chop (calculate) just take turns at the door, and threads make CPU-bound work no faster.

      
    

    

      gil_check.py

      

    

    
Since Python 3.14 there is also an officially supported free-threaded build with no GIL, installed as a separate program, python3.15t (the t is for threads). There, threads can calculate in parallel on several cores. It is optional, the standard build keeps its GIL, and the races in the next panels become much more likely without one. (No free-threaded Python was installed where this page's programs ran, so the page describes it rather than running it.)

    The Professor says: Locks are fiddly. Often it's simpler not to share at all, and to pass work along instead. A queue.Queue is a ticket rail: a first-in, first-out line that any number of threads can use safely, because it does its own locking inside. get() even waits politely until a ticket arrives.
    
      
    
    
    
    The main program is the waiter, clipping tickets. A cook thread takes them off and cooks, until it meets the special None ticket that means "kitchen closed". This pattern has a name: producer and consumer.
    
    
    
      ticket_rail.py
    
      
    
    
    
    
      
      
    1. The only thread that prints while cooking is the cook, and the main program prints only after join(). So the output order is fixed, even with two threads.
      2. 
      
    2. A stop marker like None is called a sentinel. Without it, the cook would wait at get() forever and join() would never return.
      3.

    Hiring, starting and joining waiters by hand gets repetitive. concurrent.futures has an agency: a pool of ready waiters. pool.map(f, items) works like the built-in map (Chapter 17), but hands the calls out to the pool's threads.
    
    
    
      pool_map.py

      2. 
      
    2. pool.map gives the results back in the order of the inputs, whichever thread finished first. That makes it easy to zip them with the items (Chapter 12).

    The Professor says: For CPU-bound work, open more kitchens. A process is a whole separate running program, with its own memory and its own GIL. Processes really do calculate in parallel on different cores. The costs: starting one is slower than starting a thread, and everything sent to it or back must be packed up and copied, using pickle (Part 6), since kitchens share nothing.

      2. 
      
    2. count_primes is defined at the top level of the file, so each new kitchen can find it by name. The jobs and the counts travel between processes packed by pickle.
      3.

      4.

    Pip forgets the guard. A new kitchen starts by loading your file to find square. Unguarded, that would run the pool code again, which would open another kitchen, which would load the file again… Python stops it at the first step. The real error output is about a hundred lines long, so the command below keeps only the two lines that matter, using grep, a standard tool on macOS and Linux that prints matching lines (2>&1 sends the error stream into it as well; Part 5 explains streams).
    
    
    
      no_guard.py

    The Professor says: Why did 3.13 get away with it? Kitchens can be opened in different ways. Linux used to fork: copy the running program, which needs no reload.     Part 4 · One waiter who never waitsasyncio: one thread, many jobs, and a promise to come back
    

  
    
    19
    
    
    
      
      
    Cy says: Soup for table one? Order's in, I'll be back when it's ready. Toast for table two? In. Tea? In. Oh, the toast is up! Never stand still, never stand in line.
    
    
    
    
    
      
    The Professor says: That's asyncio: one thread, and one waiter called the event loop, who juggles many jobs. A job marks each place where it would wait with await, which means "I'll wait for this; go and serve someone else meanwhile". Nobody is interrupted at a random moment, so there are far fewer races. The jobs take turns politely.
    
      
    
    
  
    

  
    
    20
    
    Three new words. async def makes a coroutine function: a function that can pause. await pauses it until something is ready. asyncio.run(main()) hires the waiter, runs main() to the end, and sends the waiter home.

    1. await asyncio.sleep(seconds) is the polite version of time.sleep: it tells the waiter "wake me in this many seconds", and frees the waiter meanwhile.
      2. 
      
    2. But this main waits for the soup to finish before ordering the toast. Polite pausing only helps when there's another job to switch to. Three seconds, the same as before.
      3.

    Under the hood: switching threads, starting processes, and what the event loop really does
    
    
      
      
    When does a thread get its turn?
    
      
    On the standard build, a thread holding the GIL is asked to let go every switch interval, 5 milliseconds by default, and it always lets go while it waits for input or output (a sleep, a download, a file). Between those moments it can be stopped after almost any bytecode instruction: the small steps Python compiles your code into. count += 1 is several such steps (load the value, add one, store it), so another thread can slip in between them. Whether it actually does is a matter of timing. This four-thread counter printed the right total on the run captured for this page, which proves nothing. It is one possible run:
    
      
    
      
    A program that is right only when the timing is lucky is wrong. On the free-threaded build, threads really run at once, and races like this one show up far more often. The fix is the same everywhere: a lock, a queue, or not sharing.
    
      
    Three ways to open a kitchen
    
      
    
      
    CPython 3.13.18, same Linux computer:
    
      
    
      
      
        
    • fork (the Linux default up to 3.13): copy the running process. Fast, needs no reload, but copying a program that has threads running can copy a lock while another thread holds it, which can freeze the new process. That's why the default changed.
      • 
        
    • spawn (the default on Windows, and on macOS since 3.8): start a fresh Python, which imports your main file to find your functions. Hence the guard.
      • 
        
    • forkserver (the Linux default since 3.14): a clean helper process is started early and forks the workers, so they start from a known, thread-free state. It also imports your main file.
      • 
      
    
      
    What the event loop does
    
      
    The event loop keeps two lists: tasks that are ready to run, and timers and network sockets it's waiting on. Its round is: run each ready task until it reaches an await on something not ready; then ask the operating system "wake me when one of these sockets has data, or when the next timer is due"; then put whatever woke up back on the ready list. A coroutine is a function that can pause in the middle and be resumed later, keeping its local variables, much like the generators of Chapter 16, which is how they began. That's all "one waiter who never waits" means.
    
    
    
  
    

  
    
    More tools: check=True, timeouts, and requests
    
    
      
    Make a failing command raise
    
      
    With check=True, subprocess.run raises CalledProcessError when the other program's exit code isn't 0, so a failure can't slip past unnoticed:
    
      
    
      
    Give up on slow jobs
    
      
    asyncio.timeout(seconds) (Python 3.11+) cancels whatever is inside the block if it takes too long, and raises TimeoutError. Every program that waits on the outside world needs a limit somewhere.
    
      
    
      
    The same web request with requests
    
      
    requests isn't part of Python: install it with python3 -m pip install requests, ideally inside a virtual environment (Chapter 13). response.json() decodes the body, and raise_for_status() turns error codes such as 404 into exceptions.

    • threading.Event (one thread signals another), threading.Semaphore (at most N at a time), and threading.local (a separate value per thread).
      • 
        
    • asyncio.Queue, the ticket rail for asyncio tasks; asyncio.to_thread(f) runs a blocking function in a thread without freezing the waiter.
      • 
        
    • multiprocessing.Pool, the older cousin of ProcessPoolExecutor.
      • 
        
    • shlex.split("ls -l") turns a command string into the right list for subprocess.run.
      • 
        
    • shutil copies and moves files and whole folders; tempfile makes scratch files (Chapter 22).

    In real programs: where waiters and doors show up
    
    
      
      
        
    • Web servers. A server handles many visitors at once. Frameworks such as FastAPI run on asyncio; others use a pool of threads or processes. Each request is one table in the restaurant.
      • 
        
    • Downloaders and scrapers. Fetching hundreds of pages is pure waiting: a thread pool or asyncio makes it many times faster. Be polite: limit how many requests you make at once and how often.
      • 
        
    • Data crunching. Big calculations are split into chunks for a process pool, or handed to libraries such as NumPy, whose C code releases the GIL while it works.
      • 
        
    • Graphical apps and games. A window must keep responding while a file downloads, so slow work goes to a background thread, or the app runs an event loop of its own.
      • 
        
    • Command-line tools. git, pip and pytest are all programs with arguments, streams and exit codes, exactly like tip.py. Continuous-integration services decide pass or fail from nothing but the exit code.
      • 
        
    • Glue scripts. A huge amount of real Python reads a folder of exports, calls another program or a web API, stores results in SQLite or another database, and runs every night from a scheduler.
      • 
        
    • SQLite everywhere. SQLite is built into phones, web browsers and countless apps. Python's sqlite3 is the same engine. Bigger systems use database servers such as PostgreSQL, but the SQL, the placeholders and the commits work the same way.
      • 
      
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "Threads make everything faster." They speed up waiting. On the standard build they don't speed up calculating at all, and they always add complexity (Panel 9).
      • 
        
    • "My threaded program printed the right answer, so it has no race." Races depend on timing. One good run proves nothing (the counter in "Under the hood").
      • 
        
    • "count += 1 is one step." It's a read, an add and a write, and another thread can get in between.
      • 
        
    • "asyncio runs things in parallel." One thread, one waiter. It overlaps waiting, never calculating. A CPU-heavy coroutine freezes everything else (Panel 26).
      • 
        
    • "Calling an async def function runs it." It builds a coroutine object. Nothing happens until it's awaited (Panel 22).
      • 
        
    • "The GIL makes my code thread-safe." It only protects Python's own insides. Your three-step updates still need a lock (Panels 10 to 13).
      • 
        
    • "print() is for messages, so errors go there too." Errors go to stderr, so they reach the screen even when the output is saved to a file (Panel 29).
      • 
        
    • "Exit codes don't matter." Schedulers, scripts and test services read nothing else. Ring the right bell.
      • 
        
    • "An f-string is fine for SQL if I'm careful." Placeholders are the only safe way. Being careful is how injection bugs get written (Panel 41).
      • 
        
    • "Closing the connection saves my changes." Only commit() saves them (Panel 40).
      • 
        
    • "pickle is just a faster JSON." Loading a pickle can run code. Use it only for data your own program wrote and nobody else could touch (Panel 43).
      • 
        
    • "A program found the files in alphabetical order, so they always come that way." File-system order isn't guaranteed. Sort (Panel 37).

    1. Check your version: python3 --version on macOS and Linux, py --version on Windows. Everything here works on Python 3.11 or newer, except gil_check.py (3.13 or newer); 3.14 or newer matches this page's start-method behaviour.
      2. 
        
    2. Save threads_calls.py and async_gather.py and run them: python3 threads_calls.py (Windows: py threads_calls.py). Change the sleep lengths and predict the new "took about" line before running.
      3. 
        
    3. Run tally_race.py five times. Then delete the time.sleep(0.01) line and run it five more times: the race becomes rare, which is worse, because now it hides.
      4. 
        
    4. Redirection and exit codes. macOS and Linux: exactly as Panel 29. Windows PowerShell: Get-Content orders.txt | py counter.py (PowerShell has no <), py counter.py 2> complaints.txt works as shown, and the exit code is in $LASTEXITCODE. Windows Command Prompt: py counter.py < orders.txt > receipt.txt works, and the exit code is echo %ERRORLEVEL%.
      5. 
        
    5. Environment variables. macOS and Linux: PIP_GREETING=howdy python3 env_demo.py. PowerShell: $env:PIP_GREETING="howdy"; py env_demo.py. Command Prompt: set PIP_GREETING=howdy, then py env_demo.py.
      6. 
        
    6. subprocess on Windows. ls and wc are macOS and Linux tools. On Windows, try subprocess.run([sys.executable, "--version"], capture_output=True, text=True), which asks your own Python its version and works on every system. Built-in shell commands such as dir aren't programs, so they need ["cmd", "/c", "dir"].
      7. 
        
    7. A real web API. On your own computer, with internet, urllib.request.urlopen("https://api.github.com", timeout=5) returns JSON describing GitHub's API. Install requests with python3 -m pip install requests (Windows: py -m pip install requests).
      8. 
        
    8. pipshop. Save pipshop.py, test_pipshop.py and a folder of CSV files. Run python3 pipshop.py yourfolder, then python3 pipshop.py yourfolder --db week.db: the database file stays after the program ends. Run it twice with --db and the totals double. Fix that as an exercise: delete the old rows first, or skip files you've already loaded. Run the tests with python3 -m pytest -q.
      9. 
        
    9. The free-threaded build (optional). The python.org installers for Windows and macOS offer it as an extra; with uv, uv python install 3.15t. Run counter_luck.py with it and watch the races appear.

    Words from this chapter
    
    
      
    
        
    concurrency
    Several jobs in progress at once, taking turns.
    
        
    parallelism
    Several jobs running at the same instant, on different CPU cores.
    
        
    CPU core
    The part of a processor that actually runs instructions. Most computers have several.
    
        
    I/O-bound / CPU-bound
    Slow because of waiting for input and output / slow because of calculating.
    
        
    thread
    A separate line of work inside one program, sharing its memory. A waiter.
    
        
    start / join
    Send a thread off / wait until it has finished.
    
        
    scheduler
    The part of the operating system that decides which thread runs next (also: a tool that runs programs at set times).
    
        
    GIL
    The Global Interpreter Lock: on the standard build, only one thread runs Python code at a time. The kitchen door.
    
        
    free-threaded build
    An optional Python build without the GIL, such as python3.15t.
    
        
    race condition
    A bug where the result depends on which thread gets somewhere first. A lost update is one kind.
    
        
    lock
    An object only one thread can hold at a time: threading.Lock(), used with with. The key card.
    
        
    queue
    A thread-safe first-in, first-out line: queue.Queue. The ticket rail.
    
        
    producer / consumer
    One part of a program makes work, another takes it, with a queue between them.
    
        
    sentinel
    A special value that means "stop", such as None on the rail.
    
        
    pool / executor
    A group of ready workers that runs jobs you hand in: ThreadPoolExecutor, ProcessPoolExecutor.
    
        
    future
    A claim ticket for a result that isn't ready yet; .result() waits for it, and re-raises the job's exception.
    
        
    process
    A whole running program with its own memory. A separate kitchen.
    
        
    start method
    How a new process begins: fork, spawn or forkserver.
    
        
    asyncio
    Python's library for running many waiting jobs in one thread.
    
        
    coroutine
    What calling an async def function gives you: a job that can pause at each await.
    
        
    await
    Pause here until this is ready, and let other tasks run meanwhile.
    
        
    event loop
    The waiter: runs whichever task is ready, and sleeps when none is.
    
        
    task
    A coroutine handed to the event loop to run alongside others.
    
        
    TaskGroup
    An async with block that waits for all its tasks and cancels the rest if one fails.
    
        
    blocking
    A call that freezes its whole thread while it waits, such as time.sleep.
    
        
    command-line argument
    A word typed after the program's name. Positional ones are required by position; options start with --.
    
        
    argparse / namespace
    The standard library's argument parser / the object it returns, with one attribute per argument.
    
        
    stdin, stdout, stderr
    Standard input, output and error: the front counter, the receipt printer and the complaints desk.
    
        
    redirection
    Sending a stream to or from a file in the shell: <, >, 2>.
    
        
    shell
    The program that reads the commands you type in a terminal.
    
        
    exit code
    The number a program ends with: 0 for success, anything else for a problem. The bell.
    
        
    environment variable
    A named setting a program inherits from the shell: os.environ.
    
        
    subprocess
    Another program started by yours.
    
        
    wildcard
    * in a pattern such as *.csv: any characters.
    
        
    XML / element / attribute
    Text with tags in angle brackets / one tagged piece / a name="value" setting inside a tag.
    
        
    database / table / SQL
    Organised stored data / a grid of rows and columns / the language for asking a database questions.
    
        
    connection, transaction, commit
    Your line to the database / a batch of changes saved all at once / saving that batch.
    
        
    placeholder
    A ? in SQL, filled in separately with a value.
    
        
    SQL injection
    An attack where text pasted into SQL becomes part of the command.
    
        
    web API, HTTP, status code
    A web address that answers programs / the web's language / the number saying how a request went (200 OK, 404 not found).
    
        
    pickle
    Python's format for turning objects into bytes. Never load one from a stranger.
    
        
    cron / Task Scheduler
    The tools that run programs at set times on macOS and Linux / on Windows.

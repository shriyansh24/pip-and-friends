CHAPTER 24

DOLLS AND STOPWATCHES

Picture: four nesting dolls in a row, from big to small. The three bigger ones are open, their tops lifted. The smallest one is solid and has a star above it. Beside them, a smiling stopwatch whose display reads 0.03 s.

A function that calls itself sounds like a magic trick. It's really a set of nesting dolls: open each one until you reach the solid one in the middle, then close them back up. Then Pip picks up a stopwatch and learns why some programs crawl while others fly. About 90 minutes, with 29 hands-on checks.

Part 1 · The nesting dollsa function that calls itself, a base case, and the frames in between

1

The Professor puts a round wooden doll on Pip's desk. "There's a note for you inside," she says. Pip opens it. Inside is a smaller doll. And inside that one…

Picture: a big red nesting doll with its top lifted off, and a smaller blue doll, still shut, waiting inside it.

Pip says: Another doll! How do I even describe what I'm doing? "Open the doll. If there's a doll inside, do the same thing to that one."

The Professor says: You just described recursion: solving a problem by doing the same job on a smaller piece of it. In code, it's a function that calls itself. That's a recursive function.

2

Recursion needs no new syntax at all. It's built from three things you already have. If one feels shaky, its chapter has the full story.

  1. Every call gets its own frame (Chapter 6). A frame is the little workspace a call gets for its parameters and local names. When the call returns, the frame is thrown away.
  2. A traceback lists the frames (Chapter 9), outermost first. Read it from the bottom: the last line names the error, the line above says where.
  3. @cache remembers answers (Chapter 18). You'll see why it matters so much here.

Pip says: So when a function calls itself, Python just opens another frame for the same function? Each with its own copy of the names?

3

Exactly. Here's the whole idea in one picture. Every recursive call is a doll you open. You keep opening until you reach the solid doll, the one that doesn't open. Then you close them back up, from the inside out, and each one carries its answer outward.

→ →

Then back out: doll 3 hands its answer to doll 2, doll 2 finishes and hands its answer to doll 1, and doll 1 gives the final answer.

Picture: three dolls getting smaller from left to right, with arrows between them. The first two are open and labelled "open, waiting". The third, smallest, is solid with a star and labelled "solid, answer known".

The Professor says: The solid doll is called the base case: the small problem you can answer straight away, without calling again. Every other doll is the recursive case: it calls the function on something smaller.

Every recursive function you'll ever write has these two parts. Learn to spot them first, every time.

    

      

        
Base case

        
        
A small input you can answer directly. No calls. Usually an if near the top with a return.

        
if n == 0: … return

      

      

        
Recursive case

        
        
Does a little work, then calls the same function on a smaller input, one step closer to the base case.

        
countdown(n - 1)

      

    

    
Two cards. Base case, with a solid doll: a small input answered directly, usually an if with a return. Recursive case, with an open doll: does a little work, then calls the same function on a smaller input.

    

      
      
Pip says: My rule: EVERY DOLL SET HAS A SOLID ONE IN THE MIDDLE. And every call must get closer to it. Smaller number, shorter string, shorter list.

    Part 4 · When the dolls never endRecursionError, the 1000-frame limit, and the missing return
    

  
    
    19
    
    
    Pip forgets the solid doll. total(n) always calls total(n - 1), and nothing ever stops it: 4, 3, 2, 1, 0, −1, −2…
    
    
    
      no_base.py
    
      
    
    
    
    
    Read it like a detective, bottom line first:
    
    
      
      
    1. RecursionError: maximum recursion depth exceeded
      Too many frames piled up. Python has a safety limit, and this run hit it.
      2. 
      
    2. [Previous line repeated 996 more times]
      Instead of printing the same two lines a thousand times, Python squashes them into one line with a count. The same line, over and over, is the fingerprint of runaway recursion.
      3. 
      
    3. line 2, in total
      The call that keeps happening. That's where a base case is missing, or never reached.
      4. 
    
    
    
    
      
      
    Pip says: Dolls all the way down, forever. A doll set with no solid doll isn't a puzzle, it's a trap. The exact count ("996") can differ between Python versions and programs, so don't learn it by heart.
    
    
    
  
    

  
    
    20
    
    Why does Python stop at all? Every frame takes memory, and an endless pile would eventually crash the whole program. So Python counts the frames, and gives up at the recursion limit. You can ask for it, and catch the error like any other (Chapter 9):
    
    
    
      limit.py
    
      
    
    
    
    
    
      
    The Professor says: The limit counts every frame, including the main program's, which is why dive got one less than the limit. sys.setrecursionlimit() can raise it, but that's rarely the right fix. If your data is so deep that a thousand frames isn't enough, use a loop. The notebook has the details.

    Part 7 · How the party queue growsBig-O, list versus set, join, deque and memory
    

  
    
    35
    
    Times change from computer to computer. What doesn't change is how the work grows when the input grows. Picture a party: when twice as many guests arrive, what happens to the host's work? Computer scientists write the answer in Big-O notation, where n is the number of guests.
    
    
    
      
    ConstantO(1)
    same work, any size
    Ringing the doorbell. One ring whether 10 or 10,000 guests are coming. Looking something up in a set or dict is like this.
    
      
    LogarithmicO(log n)
    double the guests: one more step
    Finding a name in the sorted guest book by halving (binary search). A thousand names take about 10 looks, a million about 20.
    
      
    LinearO(n)
    double the guests: double the work
    Greeting every guest once. Checking x in a_list walks the list like this, guest by guest.
    
      
    QuadraticO(n²)
    double the guests: four times the work
    Everyone shakes hands with everyone. A loop inside a loop over the same guests. Fine for 10, painful for 10,000.
    
    
    
    
    
      
      
    Pip says: So Big-O isn't seconds. It's the shape of the growth. DOUBLE THE GUESTS, THEN ASK: HOW MUCH MORE WORK?

      What you learned in Chapter 24
      
    
        
      
      • EVERY DOLL SET HAS A SOLID ONE IN THE MIDDLE.A recursive function has a base case, answered directly, and a recursive case that calls itself on something smaller. Each call gets its own frame on the call stack.
        • 
      
      • WORK BEFORE THE CALL HAPPENS ON THE WAY DOWN. WORK AFTER IT HAPPENS ON THE WAY UP.A call tree shows every call, in order; fib asks the same questions again and again.
        • 
      
      • WHEN THE DATA NESTS, THE CODE RECURSES.Strings, lists, nested lists, folder trees. For a straight line of steps, a loop is simpler and has no depth limit.
        •

        •

        • 
      
      • MEASURE FIRST, THEN FIX. DOUBLE THE GUESTS, THEN ASK: HOW MUCH MORE WORK?timeit (best of many runs), cProfile and profiling; O(1), O(log n), O(n), O(n²); sets for lookups, join for strings, deque for queues, generators for memory.

    Under the hood: frames, the limit, and why Python has no tail calls
    
      
      
      
      You can count the frames yourself
      
      
      The inspect module can list the frames on the call stack. Each recursive call adds one; the first one is the main program's frame:
      
      
      
      
      What the recursion limit really protects
      
      
      CPython checks how deep the Python calls are nested and raises RecursionError when the depth goes past sys.getrecursionlimit() (1000 by default). The check exists to stop runaway recursion with a clean, catchable error instead of crashing the whole process. You may raise the limit with sys.setrecursionlimit():
      
      
      
      
      The official documentation warns that setting it too high can crash Python, because the real stack the operating system gives a program is limited too. Treat a higher limit as a quick experiment, not a fix. For truly deep data, rewrite the function with a loop and your own list used as a stack.
      
      
      No tail-call optimisation
      
      
      Some languages notice when the recursive call is the very last thing a function does (a tail call) and reuse the frame instead of adding a new one. CPython deliberately doesn't, so tracebacks always show every call. Writing the function in "tail" form gains nothing in Python:
      
      
      
      
      How a set finds things in one step
      
      
      A set or dict keeps a table of slots. To store or find x, Python computes hash(x), a number, and uses it to pick a slot directly. Only if two different objects land on the same slot does it need to compare more than once. That's why lookups are O(1) on average, why the items must be hashable (their hash must never change), and why Panel 37's set needed a __hash__ method.
      
      
      Why log n is so small
      
      
      log₂ n asks: how many times can you halve n before you get to 1? 1,000 halves to 1 in about 10 steps, 1,000,000 in about 20, and 1,000,000,000 in about 30. Every doubling adds only one step, which is why the binary line in Panel 36 is nearly flat.
      
    
      
  
      

  
      
    In real programs: where recursion and performance show up
    
      
      
      Recursion you already use
      
      
        
        
      • Walking folders. os.walk() and pathlib.Path.rglob() visit every folder inside a folder, at any depth.
        • 
        
      • JSON and nested data. json.loads() turns nested text into nested lists and dicts, and copy.deepcopy() copies a structure all the way down. Both follow the data's nesting.
        • 
        
      • Python reading Python. The ast module turns code into a tree, and tools such as linters walk it recursively.
        • 
        
      • Sorting. Python's sorted() uses a hybrid merge sort known as Timsort (since Python 3.11 its merge rules follow the "powersort" strategy). Like Panel 29, it merges sorted runs; unlike Panel 29, it first finds runs that are already in order, so nearly sorted data is very fast.
        • 
        
      • Web pages. An HTML page is a tree of tags inside tags, and every browser walks it.
        • 
      
      
      
      Performance habits of real projects
      
      
        
        
      • Profile in production-like conditions. A sampling profiler such as profiling.sampling (3.15) can attach to a running program and draw a flame graph: a picture where the widest bars are the functions that took the most time.
        • 
        
      • Benchmarks in the test suite. Projects keep small timing tests (for example with timeit or the third-party pytest-benchmark) so a slowdown is noticed when it's introduced.
        • 
        
      • Caches everywhere. functools.cache and lru_cache for pure functions; web apps cache whole pages.
        • 
        
      • The right container. Most real speed-ups are Panel 37's kind: a set or dict instead of a list scan, not clever tricks.
        • 
        
      • NumPy and friends. Data science code hands big arrays of numbers to NumPy, pandas or similar libraries, whose inner loops run as compiled code.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "A recursive function shares one n between all its calls." Every call has its own frame with its own local names (Panel 8). Changing n in one call doesn't touch the others.
        • 
        
      • "The recursive call finishes the function." The caller pauses, waits for the answer, then carries on with the rest of its own line and the lines after it (Panel 11).
        • 
        
      • "If I call the function, its answer is returned automatically." Only return passes an answer back. Without it, the caller gets None (Panel 22).
        • 
        
      • "Having a base case is enough." Every call must also move towards it (Panels 9 and 21).
        • 
        
      • "Recursion is faster than a loop." In CPython it's usually a little slower, because each call costs a new frame. Choose it because it fits the problem.
        • 
        
      • "RecursionError means my computer ran out of memory." It means the depth counter passed the limit, a deliberate safety stop.
        • 
        
      • "One timing tells me which version is faster." One run is noise. Repeat, take the best, and compare on the same computer (Panel 32).
        • 
        
      • "Big-O tells me how many seconds it takes." It tells you how the work grows. An O(n²) method can beat an O(n) one on tiny inputs.
        • 
        
      • "Optimise everything." Measure first. Usually one spot is slow and the rest doesn't matter.
        • 
        
      • "x in my_list is as fast as x in my_set; it's the same keyword." Same keyword, different machinery: a walk versus a jump (Panel 37).
        • 
      
      
    
      
  
      

  
      
    Version notes: what is new, and since when
    
      
      
        
        
      • The profiling package, with profiling.tracing (the tracing profiler also known as cProfile) and profiling.sampling (Tachyon): new in Python 3.15. On 3.13.18, python3 -m profiling.tracing fails with "No module named profiling" (Panel 34). cProfile still works in both.
        • 
        
      • The profile module (the slow pure-Python profiler) is deprecated in 3.15 and scheduled for removal in 3.17. Importing it prints a DeprecationWarning on 3.15.2 and nothing on 3.13.18 (Panel 34).
        • 
        
      • sys.getsizeof of a generator: 216 bytes on 3.15.2, 200 on 3.13.18 (Panel 39). Object sizes are implementation details and change between versions.
        • 
        
      • The recursion limit is 1000 on both versions here, and both stopped Panel 20's dive at the same depth. Since CPython 3.12 the limit counts only Python code; built-in functions are protected by a separate mechanism (What's New in Python 3.12), so older tutorials may describe slightly different behaviour.
        • 
        
      • functools.cache exists since 3.9; before that, people wrote @lru_cache(maxsize=None).
        • 
        
      • Timing programs (timeit_demo.py, noise.py, timeit_cli.py, join_vs_plus.py, queue_timing.py, profile_slow.py, tracing_slow.py) print different numbers on every run and on both versions. That's not a version difference, just the stopwatch.
        • 
      
      
      
      All 67 programs in this chapter were run with both Python 3.15.2 and 3.13.18, and 9 of them printed differently. Seven are the timing programs listed above, whose numbers change on every run anyway; one of those, tracing_slow.py, also differs for a real reason (no profiling package on 3.13). The other two are profile_warn.py and memory.py, as described above.     Words from this chapter
    
      
      
      
        
      recursion
      Solving a problem by solving smaller copies of the same problem. In code: a function that calls itself.
      
        
      recursive function
      A function that calls itself, directly or through another function.
      
        
      base case
      An input small enough to answer directly, without another recursive call. The solid doll.
      
        
      recursive case
      The part of the function that calls itself on a smaller input.
      
        
      frame
      The workspace a single call gets for its parameters and local names (Chapter 6).
      
        
      call stack
      The pile of frames for calls that have started but not finished. The newest is on top.
      
        
      return value
      The value a call hands back to whoever called it.
      
        
      call tree
      A drawing of every call a program makes, joined to the calls each one made.
      
        
      tree (data)
      Nested data shaped like an upside-down tree: a root, branches, and leaves at the ends. Folders are one.
      
        
      RecursionError
      The error raised when the call stack gets deeper than the recursion limit.
      
        
      recursion limit
      The maximum depth Python allows, 1000 by default. sys.getrecursionlimit() reads it.
      
        
      memoization
      Remembering the answers of a function so the same question is never worked out twice.
      
        
      memo
      The dict (or cache) where those answers are kept.
      
        
      divide and conquer
      Splitting a problem into halves, solving them the same way, and combining the results.
      
        
      binary search
      Finding an item in a sorted list by looking in the middle and throwing away half each time.
      
        
      merge sort
      Sorting by splitting the list in half, sorting each half, and merging the sorted halves.
      
        
      off-by-one error
      A bug where a count or a position is one too big or one too small.
      
        
      timeit
      The standard-library module for timing small pieces of code over many repeats.
      
        
      noise (timing)
      Random differences between measurements caused by everything else the computer is doing.
      
        
      profiler
      A tool that watches a program run and reports where the time goes. A tracing profiler records every call; a sampling profiler takes frequent snapshots.
      
        
      deprecated
      Still available, but on its way out: a future version will remove it.
      
        
      Big-O notation
      A way to describe how the work grows with the input size n: O(1), O(log n), O(n), O(n log n), O(n²).
      
        
      worst case
      The input that makes an algorithm do the most work, such as searching for the last item.
      
        
      hash
      A number worked out from a value, used by sets and dicts to find its slot in one step.
      
        
      NumPy
      A popular third-party package for fast maths on large arrays of numbers.

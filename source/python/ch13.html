    Under the hood: what import really does
    
    
      
    When Python meets import helpers, it does three things:
    
      
      
        
    1. Check the cache. Python keeps every module it has already loaded in a dictionary called sys.modules. If "helpers" is there, it skips straight to step 3.
      2. 
        
    2. Find and run. Otherwise it searches (below), creates a fresh, empty module object, and runs the file top to bottom inside it. Every def and every assignment at the top level of the file becomes a name in that module.
      3. 
        
    3. Bind a name. It puts a tag in your file: helpers for import helpers, h for import helpers as h, or just the tools you named for from helpers import shout.
      4. 
      
    
      
    A module is an ordinary object, with a type of its own:
    
      
    
      
    Imported once, per run
    
      
    Because of the cache, a second import of the same module does nothing at all:
    
      
    
      
    That's also why, in the interactive prompt, editing a module and importing it again shows the old version. Restart Python. (importlib.reload exists, but restarting is simpler and safer.)
    
      
    The search, in full
    
      
    Before any folder, Python checks the modules compiled right into the interpreter, listed in sys.builtin_module_names. They can't be hidden by a file of the same name. On the builds used here, sys and math are built in, but random is an ordinary random.py in the standard library, which is why a local random.py can hide it:
    
      
    
      
    Then it walks sys.path in order: the script's folder (or the current folder in the interactive prompt), any folders in the PYTHONPATH environment variable, the standard library's folders, and finally site-packages. Which built-ins exist varies between builds and systems, so never rely on a clash being "safe".
    
      
    __pycache__ and .pyc files
    
      
    The first time a module is imported, Python saves a pre-digested copy (compiled bytecode) in a __pycache__ folder next to it, named like helpers.cpython-315.pyc. Next time, if the source hasn't changed, it loads the copy, which is a little quicker to load, not to run. The file you run directly is never cached. The runs in this comic switched caching off, so no __pycache__ folders appear.
    
      
    What a venv really is
    
      
    A folder with a small settings file, pyvenv.cfg, which says which Python it came from; a bin folder (Scripts on Windows) holding a python3 that points back at that Python plus the activate scripts; and its own lib/…/site-packages, holding only pip at first (Panel 36). When that python3 starts, it notices pyvenv.cfg and uses the venv's site-packages instead of the system's. That's the whole trick: no copy of Python, and no magic in "activate", which only changes your terminal's PATH.

    In real programs
    
    
      
    Imports go at the top, in three groups
    
      
    Python's style guide (PEP 8) puts all imports at the top of the file, one module per line, grouped with a blank line between: the standard library first, then third-party packages, then your own modules. fancy_dice.py follows that order.
    
      
    Favourite boxes from the standard library
    
      
      
        
    • pathlib, json and csv for files (Chapter 12).
      • 
        
    • itertools: Chapter 16. collections (Counter, defaultdict), decimal and zoneinfo: Chapter 23.
      • 
        
    • argparse for real command-line programs: Chapter 27.
      • 
        
    • secrets instead of random for passwords and tokens: random is predictable on purpose (that's what a seed is), so never use it for security.
      • 
      
    
      
    Checking a package before installing it
    
      
    Anyone can publish to PyPI, and some bad actors upload packages whose names are one typo away from popular ones. Check the spelling, look at the project's page on pypi.org (who makes it, when it was last updated), and install only what you need.
    
      
    Pinning, and keeping the pantry out of git
    
      
    Pinned versions (pyfiglet==1.0.4) mean everyone gets the same code, so "works on my machine" works on theirs too. The .venv folder is never shared or saved in version control: add it to .gitignore and share requirements.txt instead.
    
      
    Tools you run, rather than import
    
      
    Some packages are programs rather than toolboxes. pipx and uv tool install each such program into a hidden pantry of its own, so it can't clash with your projects.
    
      
    pyproject.toml and lock files
    
      
    Bigger projects describe themselves in pyproject.toml (name, version, dependencies). uv also writes a uv.lock file that records the exact version of every package, including the packages your packages need. Chapter 23 lists the command that writes one, uv lock.
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "random.shuffle gives me the shuffled list." It shuffles the list you pass in and returns None. Assigning its result throws your list away:
          
      • 
        
    • "I type pip install inside my program." pip is a terminal command, not Python code. In a .py file (or at the >>> prompt) the Proofreader rejects it:
          
      • 
        
    • "sys.argv always has my words." Only if you type them. Run greet.py with nothing after the name and item 1 doesn't exist (Tumble, Chapter 9):
          
      • 
        
    • "import helpers.py." Never include .py in an import. The module's name is helpers.
      • 
        
    • "Importing a module twice runs it twice." Once per run; after that Python reuses it (see "Under the hood").
      • 
        
    • "from math import sqrt also gives me math." It gives you only sqrt.
      • 
        
    • "A venv contains a copy of Python." It points back to the Python that made it. If you delete or upgrade that Python, rebuild the venv.
      • 
        
    • "I must activate, or the venv doesn't work." Activating is a convenience. .venv/bin/python3 banner.py (Windows: .venv\Scripts\python banner.py) uses the pantry directly.
      • 
        
    • "I can move or rename the .venv folder." Its scripts remember the full path where it was made. Delete it and build a new one from requirements.txt instead.
      • 
        
    • "sudo pip install fixes the externally-managed error." It risks breaking your system's own tools. Use a venv.

    Words from this chapter
    
    
      
    
        
    module
    A file of Python code whose tools you can borrow with import. Every .py file is one.
    
        
    import
    Load a module (once per run) and put a name for it in your file.
    
        
    standard library
    The modules that come with Python: math, random, datetime, statistics, sys, os, json and many more.
    
        
    alias
    A nickname given with as: import statistics as st.
    
        
    star import
    from x import *: takes every public name. Avoid it; names appear from nowhere and can overwrite yours.
    
        
    pseudo-random
    Numbers from a recipe that only look random.
    
        
    seed
    Where the recipe starts. Same seed, same numbers.
    
        
    current working directory
    The folder your terminal (and your program) is in: os.getcwd().
    
        
    sys.argv
    The list of words typed on the command line; item 0 is the file name.
    
        
    __name__
    A name every module has: "__main__" for the file you run, the module's own name when imported.
    
        
    main guard
    if __name__ == "__main__":, so code runs only when the file is run directly.
    
        
    module search path
    Where Python looks for a module, in order: built-ins, then the folders in sys.path (script's folder first, then the standard library, then site-packages).
    
        
    shadowing
    Your file or name hiding another with the same name, like random.py hiding the real random.
    
        
    third-party package
    A toolbox made by someone outside the Python core team, usually installed from PyPI.
    
        
    PyPI
    The Python Package Index, pypi.org: the public warehouse of packages.
    
        
    pip
    Python's package installer. Run it as python3 -m pip.
    
        
    wheel
    A ready-to-install package file ending in .whl.
    
        
    site-packages
    The folder where pip installs packages for one Python (or one venv).
    
        
    virtual environment (venv)
    A project's own pantry: a folder with its own python3 and site-packages.
    
        
    activate / deactivate
    Step into / out of a venv in this terminal. The prompt shows (.venv) while you're inside.
    
        
    externally managed environment
    A system Python that refuses pip installs to protect the operating system (PEP 668).
    
        
    requirements.txt
    A list of packages, one per line, for pip install -r.
    
        
    pin
    Fix an exact version with ==, like pyfiglet==1.0.4.
    
        
    uv
    A fast, separate tool that manages venvs, packages and runs in one.
    
        
    pyproject.toml
    A project's description file, with its dependencies. Chapter 23.
    
        
    lazy import
    New in 3.15: lazy import x loads x only when first used.

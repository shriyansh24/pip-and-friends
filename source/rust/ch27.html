PART 1 · ONE WAITERprograms that mostly wait; async fn and .await; a future is an order slip that does nothing until someone hands it in; the unused-Future warning

1

The library has opened a café in the reading room. Forty little tables. Mabel remembers last chapter's kitchen, where every job got its own cook.

Mabel says: Forty tables means forty waiters? They'd spend all day standing at the kitchen hatch, waiting for food. And each one needs a uniform, a locker, a salary…

The Professor says: Most of a waiter's day is waiting. One good waiter can serve every table, as long as they never stand still while the kitchen cooks. First catchphrase: waiting isn't working.

Picture: Mabel shrugs, worried. The Professor answers from the right.

2

Two ways to wait for the soup.

Blockingthe frozen waiter

Bob takes table 1's order and stands at the kitchen hatch until the soup is ready. Tables 2 to 40 wave at him. He can't move: he's blocked.

Asyncthe busy waiter

Tokio hands the order to the kitchen and says "ring the bell when it's ready". Meanwhile he takes table 2's order, then table 3's. When a bell rings, he goes back to that table.

Picture: in the Blocking card, a waiter labelled BOB stands stiff with his arms down, frost marks around him. In the Async card, a waiter labelled TOKIO hurries with a tray, speed lines behind him.

Nobody cooks faster. The soup still takes as long as it takes. What changes is that the waiting overlaps: while one table waits, the waiter is busy somewhere else. Doing several jobs in overlapping stretches of time is called concurrency.

3

Programs wait far more than you'd think. A computer can do billions of steps per second, but asking another computer for a web page, reading from a disk or waiting for a timer takes thousands or millions of those steps. Waiting on input and output is called waiting on I/O.

a threadChapter 26: one cook

The operating system runs it. Each one gets its own stack (a Rust thread's default is 2 MiB on the major platforms), and switching between thousands of them gets expensive.

a taskone table on the waiter's list

The async runtime runs it, not the operating system. Tokio's docs call tasks "light weight": tens of thousands are fine on a few threads.

a futurean order slip

A value that stands for work that will finish later. Every async fn hands one back. Nothing happens until someone hands it in.

Mabel says: So async is for jobs that mostly wait, like a server talking to thousands of slow phones. For jobs that mostly think, like resizing photos, the cooks from Chapter 26 are still the right tool.

    9
    
    An async runtime is the waiter plus the restaurant's bell board. Tokio provides three parts.
    
    
    
      
    the executorthe waiter
    Keeps the list of tasks. Runs each one until it reaches an .await that isn't ready, then moves on to the next task that is ready.
    
      
    the timers and I/Othe bell board
    Watches every timer, network socket and file the tasks are waiting for. When one is ready, it rings that task's bell (the task is woken).
    
      
    the threadshow many waiters
    #[tokio::main] starts one worker thread per CPU core, by default. flavor = "current_thread" asks for exactly one waiter, on main's own thread.
    
    
    
    
    
      
      
    The waiter says: I never interrupt a table. I only switch at an .await. That's called cooperative scheduling: every table has to let go of me now and then.

    27
    
    You've used macros since Chapter 1: println!. The ! is how you tell a stamp from a machine (a function, Chapter 4).
    
    
    
      
    
        
    
        
    A functiona machine
    
        
    Runs while the program runs. Takes values, a fixed number of them, each of a fixed type. Can be written anywhere in the file, even below the code that calls it.
    
      
    
      
    
        
    
        
    A macroa stamp
    
        
    Works before the program is compiled. Takes code, in any amount and shape it was built to accept, and prints code back. Called with !. Must be defined above where it's used in the file.
    
      
    
    
    
    
    That's how println! can take one argument or ten, and how it checks your {} placeholders against the arguments at compile time. No function could do either. The price: macros are harder to read and write, so reach for a function first.

    What you learned in Chapter 27
    
    
      
      
    • WAITING ISN'T WORKINGAsync lets the waits of many jobs overlap on a few threads: perfect for programs that mostly wait on I/O (servers, network clients, timers), no help for programs that mostly think. async fn may pause; .await pauses until a value is ready and lets the waiter serve others meanwhile.
      • 
      
    • A FUTURE IS AN ORDER SLIP: NOTHING COOKS UNTIL SOMEONE HANDS IT INCalling an async fn only makes a future. It runs when it's .awaited or spawned. Forgetting gives warning: unused implementer of `Future` that must be used, and the work silently never happens. A dropped future never runs again.
      • 
      
    • NO WAITER, NO SERVICERust has no built-in runtime. async fn main alone is E0752; #[tokio::main] builds a Tokio runtime and calls block_on for you; .await in a non-async function is E0728. flavor = "current_thread" means exactly one waiter.
      • 
      
    • TAKE ALL THE ORDERS, THEN WAITjoin! runs several futures together and waits for all (results in written order); tokio::spawn makes a task and a JoinHandle to .await (tasks still running when main ends are dropped); select! takes the first and drops the rest (biased; for a fixed order); tokio::sync::mpsc is the async rail. On many threads, output order varies.
      • 
      
    • NEVER FREEZE THE WAITERstd::thread::sleep or long calculations inside async code block every task on that thread, silently. Use tokio::time::sleep(...).await, async libraries, and spawn_blocking for work that must block. Async closures: async |x| { ... }. Streams: values over time, while let Some(x) = s.next().await.
      • 
      
    • A MACRO IS A STAMP: IT PRINTS CODE BEFORE THE COMPILER READS ITCall with ! (without it: E0423, or a parse error). Standard stamps: vec!, format!, write!, assert!, assert_eq!, matches!, dbg!, todo!, unreachable!, include_str!. Derive and attribute macros write whole impls and rewrite items. macro_rules!: $x:expr, $n:ident, $( ... ),*; define it above its first use; an argument used twice runs twice.

    Under the hood: poll, Pending, wakers, state machines, and how stamps are pressed
    
    
      
    
        
        
    The Professor says: Let's open the order slip and look at the machinery.
    
      
    
      
    A future is something you can poll
    
      
    Every future implements the Future trait, which has one method, poll. The runtime calls poll to say "make as much progress as you can". The future answers Poll::Ready(value) when it's finished, or Poll::Pending when it's stuck waiting. Before answering Pending, it hands a waker to whatever it's waiting for (a timer, a socket). When that thing is ready, it calls the waker, and the runtime knows to poll that task again. That's the bell in the comic. Nobody polls a future that hasn't been handed in, which is why futures are lazy.
    
      
    async fn becomes a state machine
    
      
    The Compiler turns each async fn into an enum-like state machine: one state per .await, holding the local variables that must survive across that pause. Polling runs from the current state to the next .await. That's why futures are values you can store, pass around and drop, and why no extra thread is needed. It's also why some futures must not move in memory once started (they may point into themselves); the Pin type handles that. You rarely see Pin unless you write futures by hand, which is beyond this book.
    
      
    Why main can't be async
    
      
    An async main would only return a future, and something must poll it. The operating system knows nothing about futures. So a runtime must start first: #[tokio::main] keeps your code in an async block and wraps it in an ordinary fn main that builds the runtime and calls block_on, as Panel 34's real expansion shows.
    
      
    How many waiters?
    
      
    Tokio's default (multi-thread) runtime starts one worker thread per CPU core and lets idle workers steal tasks from busy ones. current_thread runs everything on the thread that called block_on. spawn_blocking uses a separate pool of threads that grows when needed. Because tasks may move between workers at an .await, a spawned task must be Send; holding an Rc or a std::sync::MutexGuard across an .await makes it not Send, and the Compiler refuses the spawn.
    
      
    How a stamp is pressed
    
      
    The Compiler first splits your source into tokens (names, numbers, symbols, brackets). When it meets name!(...), it hands the tokens inside the brackets to the macro, which matches them against its rules and produces new tokens. Those are parsed as if you had typed them, and expansion repeats until no macro calls are left; only then are types checked. macro_rules! macros are also hygienic for local variables: a let map inside the stamp can't clash with a map in your own code. And an expr fragment is pasted as a single unit, which is why square!(2 + 3) is 25.
    
      
    The three kinds of procedural macro
    
      
    Derive macros (#[derive(Serialize)]), attribute macros (#[tokio::main], #[test]) and function-like ones (sqlx::query!) are written as Rust functions that take tokens and return tokens. They live in a special crate type (proc-macro = true) and usually use the syn and quote crates. Tokio's macros come from a companion crate, tokio-macros, which the macros feature switches on.
    
    
    
  
    

  
    
    In real programs: where you'll meet waiters and stamps
    
    
      
      
        
    • Web servers and clients: axum, hyper and reqwest are built on Tokio. A handler is an async fn; every incoming connection becomes a task. Chapter 29's server builds a small version of this idea.
      • 
        
    • Timeouts everywhere: real network code wraps every request in tokio::time::timeout(duration, future) (a ready-made select! against a timer), so one slow partner can't hang the program.
      • 
        
    • Graceful shutdown: servers often select! between "the next connection" and "Ctrl+C was pressed" (tokio::signal::ctrl_c()), then let running tasks finish.
      • 
        
    • Async in tests: #[tokio::test] is the attribute macro for tests that are async fn.
      • 
        
    • Derive macros you'll use constantly: serde's #[derive(Serialize, Deserialize)] (Chapter 28), clap's #[derive(Parser)] (Chapter 25), thiserror's #[derive(Error)] (Chapter 21).
      • 
        
    • Function-like macros in crates: anyhow! and bail! for errors, tracing::info! for logs, serde_json::json! to write JSON inline.
      • 
        
    • macro_rules! in the wild: mostly to remove repetition, such as implementing the same trait for ten number types, or writing many similar test cases.
      • 
      
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "Calling an async function starts it." It only makes a future. .await it or spawn it.
      • 
        
    • "async makes my code faster." It lets waiting overlap. A single job takes just as long, and code that never waits gains nothing.
      • 
        
    • "async means parallel." With current_thread everything runs on one thread, yet waits still overlap: that's concurrency. Parallelism (several things at the same instant) needs several threads.
      • 
        
    • ".await blocks the thread." It pauses this task and frees the thread for other tasks. std::thread::sleep is the one that blocks the thread.
      • 
        
    • "A spawned task always finishes." If main returns first, the runtime shuts down and drops it.
      • 
        
    • "select! lets the losers finish quietly." It drops them at their current .await; their remaining code never runs.
      • 
        
    • "Rust comes with an async runtime." It provides the async/.await syntax and the Future trait. The runtime is a crate you choose.
      • 
        
    • "Macros are just functions with a !." They work on code, before compiling, and can take any number of arguments or invent names.
      • 
        
    • "I can define a macro_rules! anywhere, like a function." It must come before its first use in the file.
      • 
        
    • "A macro argument is evaluated once, like a function argument." It's pasted wherever the transcriber mentions it, and runs each time.
      • 
        
    • "Writing a macro is the best way to avoid repetition." Try a function, a generic or a trait first. Macros are harder to read, and their error messages are harder to follow.

    concurrency / parallelism
    Several jobs in overlapping stretches of time / several jobs at the very same instant, on several cores.

    Making a whole thread wait, so it can do nothing else meanwhile.
    
        
    async / async fn

    future

    poll, Pending, Ready
    The runtime asks a future to make progress; it answers "not yet" or "done, here's the value".
    
        
    waker
    The bell a future leaves behind, so the runtime knows when to poll it again.
    
        
    runtime / executor
    The library that polls futures, watches timers and I/O, and owns the worker threads. Tokio is one.
    
        
    #[tokio::main]
    An attribute macro that turns async fn main into a normal main that builds a runtime and calls block_on.
    
        
    block_on
    Run one future to completion from ordinary code, blocking the current thread.
    
        
    task / tokio::spawn

    join! / select!
    Wait for all of several futures / for the first, dropping the rest.
    
        
    cancellation
    Stopping a future by dropping it; its remaining code never runs.
    
        
    cooperative scheduling
    Tasks switch only where they choose to (at .await), never in the middle of other code.
    
        
    spawn_blocking
    Run blocking code on a separate pool of threads, so the async workers stay free.
    
        
    async closure

    stream
    An async series of values arriving over time.
    
        
    macro
    Code that writes code before compiling; called with !.
    
        
    expansion
    The code a macro call is replaced with.
    
        
    derive macro / attribute macro
    #[derive(...)] writes trait impls for a type / #[name] rewrites the item under it.
    
        
    macro_rules!

    matcher / transcriber

    fragment ($x:expr, $n:ident…)

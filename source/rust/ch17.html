RUST · CHAPTER 17 · INTERMEDIATE

COOKIE CUTTERS AND BADGES

Picture: Mabel the librarian waves. On her left is a cookie cutter with a wobbly dashed outline and a question mark inside, labelled with angle brackets around T: a cutter shaped like any shape. On her right is a yellow rosette badge with blue ribbons that says SPEAK, with a tick under the word.

You've reached the intermediate part of the book! This chapter gives you two of Rust's biggest ideas. Generics are cookie cutters shaped like "any shape": write a function or a struct once, and the Compiler stamps out a copy for every type you actually use. Traits are badges: a type earns the "Speak" badge by having a speak method, and a function can say "badge-wearers only". Along the way the Compiler will show you ten error codes, four of them new to this book, and you'll read each one like a detective. About 130 minutes, with 26 hands-on checks.

  1. One cutter, many doughs: generic functions
  2. Generic boxes: structs, enums and impl blocks
  3. Badges: defining and implementing traits
  4. Badge-wearers only: trait bounds and impl Trait
  5. The badge office rules: orphans, supertraits, associated types
  6. Boss level and recap

Here's the secret. There is no "any shape" cutter in your finished program. While compiling, the Compiler looks at every call, sees which doughs you actually used, and stamps out a separate, ordinary cutter for each one. This is called monomorphization ("making into one shape").

      Now put the two big ideas together. A generic function with a bound is a door with a sign: "Any type may enter, if it wears this badge." Inside, the function may use every method on the badge, and nothing else.
      
    bound.rs

        3.

    Under the hood: stamping, checking and choosing
    
      
      
      
        
        
      The Professor says: Generics and traits are mostly compile-time machinery. Here's what the Compiler is really doing.
      
      
      
      
      Monomorphization, step by step
      
      
      When the Compiler meets largest(&pages) with pages: Vec<i32>, it fills T with i32 and records that largest::<i32> is needed. After checking the whole crate, it generates machine code for each recorded combination, and only those. Each copy is optimized separately, so largest::<i32> compares with a single whole-number instruction, exactly as the hand-written twin would. The names nm printed in panel 7, like stamps::largest::<i32>, come from how Rust names functions inside a program file (its "symbol mangling"). Both versions used here (1.99.1 and 1.97.0) name them with Rust's own "v0" scheme, which keeps the type parameters, which is why nm -C can show them. The Rust blog's announcement of Rust 1.97.0 says that 1.97 is the release that turned v0 on by default for stable Rust. The older scheme it replaced lost the type parameters and added an opaque hash instead (the Rust blog, "Switching to Rust's own mangling scheme on nightly", November 2025), so every copy showed up under the same readable name, stamps::largest.
      
      
      Checked before stamping, unlike C++ templates
      
      
      Rust checks a generic function's body once, against its bounds, before any copy is made. That's why panel 4 failed even though main only ever used i32, which can do >. C++ templates work the other way round: they're checked after stamping, for each type used, so an error shows up deep inside the template, sometimes pages long. Rust's rule gives shorter errors that point at the bound you forgot, and it means a generic library that compiles will work for every type that meets its bounds.
      
      
      How a method call finds its impl
      
      
      For polly.speak(), the Compiler looks at the type of polly (Parrot), looks for a method speak on Parrot itself, then in the traits Parrot wears that are in scope. For a trait defined in the same file, that's automatic. For a trait from another module or crate, you must use it first, or the method isn't found (E0599, with a help: naming the use line). Since everything is decided while compiling, the call jumps straight to <Parrot as Speak>::speak. This is called static dispatch. Chapter 23's dyn Speak decides while running instead (dynamic dispatch).
      
      
      Fully qualified syntax
      
      
      If two traits a type wears both have a method called speak, x.speak() is ambiguous, and the Compiler asks you to choose. You write Speak::speak(&x), or in full <Parrot as Speak>::speak(&x). You'll see that angle-bracket form in error messages and in the docs.
      
      
      The orphan rule, a little more precisely
      
      
      The rule is called coherence: for any trait and type, there may be at most one impl in the whole program. The orphan rule is how Rust guarantees it without looking at every crate at once. Slightly more precisely than panel 28: impl ForeignTrait<…> for ForeignType is allowed if a local type appears in the right place, so impl From<Book> for String is fine because Book is yours. The E0117 note "impl doesn't have any local type before any uncovered type parameters" is the precise version. The Reference's "Orphan rules" page, linked in Go deeper, has the full rule.

    In real programs: where cutters and badges show up
    
      
      
        
        
      • The standard library is built from them. Vec<T>, HashMap<K, V>, Option<T>, Result<T, E>, Box<T> are generic types. Sorting needs T: Ord; a HashMap key needs K: Eq + Hash. When the docs show impl<T: Ord> …, read it as "this method exists when T wears Ord".
        • 
        
      • Read the badge list on a docs page. Every type's page has a "Trait Implementations" section (Chapter 15), and blanket impls get their own section, "Blanket Implementations". Every trait's page lists its wearers under "Implementors".
        • 
        
      • Library authors take impl Trait arguments so callers can pass many types: fn open(path: impl AsRef<Path>) accepts a &str, a String or a PathBuf. Chapter 18 meets AsRef.
        • 
        
      • Derive is everywhere. Real structs often start with #[derive(Debug, Clone, PartialEq)]. Popular crates add their own derivable badges, such as serde's Serialize and Deserialize (Chapter 28), which turn a struct into JSON and back.
        • 
        
      • Traits make testing easier. A function that takes impl Clock instead of the real system clock can be tested with a fake clock that always says 9:00.
        • 
        
      • Watch compile times. A generic used with dozens of types is stamped dozens of times. Large projects sometimes write a small generic wrapper that calls one non-generic inner function, so most of the code is compiled only once.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "Generics are slower than normal functions." They're stamped into normal functions while compiling. Same speed.
        • 
        
      • "If main only uses numbers, I don't need a bound." The body is checked for every possible T, not just the ones you use (panel 4).
        • 
        
      • "Point<i32> and Point<f64> are the same type." They're two different types made from one recipe. A function that takes a Point<i32> refuses a Point<f64>.
        • 
        
      • "With <T>, each field can be anything." One T is one type everywhere it appears (panel 12). Use <T, U> for two.
        • 
        
      • "impl Point<T> is enough." Without impl<T>, the Compiler looks for a real type named T (E0425).
        • 
        
      • "A trait is like a class from other languages." A trait holds no data; it's a list of abilities. Data lives in structs and enums; abilities are attached with impl, even to types you didn't write.
        • 
        
      • "Implementing half a trait is fine if I only call that half." All required methods, or no badge (E0046).
        • 
        
      • "impl Speak as a return type can be a different type each time." One hidden type per function. For "either one", Chapter 23's Box<dyn Speak>.
        • 
        
      • "I can add Display to Vec if I really want to." Not directly: the orphan rule. Use your own trait or a newtype wrapper.
        • 
        
      • "derive works for any trait." Only for traits that support it, mostly from std (Chapter 18 lists them) or crates that provide a derive.
        • 
        
      • "The single letter T is a keyword." It's just a name. <Item> works too.

    Words from this chapter
    
      
      
      
        
      generic
      Code written once with a blank for a type, which works for many types.
      
        
      type parameter
      The blank itself, declared in angle brackets: the T in fn largest<T>.
      
        
      generic function / struct / enum
      One that declares type parameters: fn f<T>, struct Point<T>, enum Option<T>.
      
        
      impl<T>
      An impl block that declares the blank, so its methods exist for every T.
      
        
      monomorphization
      The Compiler stamping out one ordinary copy of a generic for each concrete type used. Zero run-time cost.
      
        
      concrete type
      A real, filled-in type such as i32 or Point<f64>, as opposed to a blank T.
      
        
      turbofish
      The ::<Type> syntax that says which type to use: "42".parse::<u8>().
      
        
      type inference
      The Compiler working out a type from how a value is used. When it can't: "type annotations needed".
      
        
      const generic
      A blank for a number known while compiling: const N: usize, as in [u32; N].
      
        
      trait
      A named list of methods a type can have: a badge.
      
        
      implement (a trait)
      Write impl Trait for Type { … } with every required method: earn the badge.
      
        
      default method
      A trait method with a body; wearers get it free, or override it.
      
        
      override
      Write your own version of a default method in an impl.
      
        
      derive
      An attribute that makes the Compiler write an impl for you: #[derive(Debug, PartialEq)].
      
        
      trait bound
      A requirement on a type parameter: T: Speak, "T must wear Speak".
      
        
      where clause
      The same bounds, written after the signature: where T: Speak + Debug.
      
        
      impl Trait
      "Some type that wears this trait". As an argument, a shortcut for a bound; as a return type, one hidden type.
      
        
      PartialOrd, PartialEq, Debug, Display
      Standard badges for < and >, for ==, for {:?} and for {}. Chapter 18 tours them.
      
        
      orphan rule (coherence)
      You may implement a trait for a type only if the trait or the type is defined in your crate.
      
        
      newtype
      A one-field wrapper struct, like struct Shelf(Vec<i32>);, made so you own the type.
      
        
      supertrait
      A trait another trait requires: in trait Announcer: Speak, Speak is the supertrait.
      
        
      associated type
      A type blank inside a trait, filled in by each impl: type Item = u32;.
      
        
      Self
      Inside a trait or impl, the type that's wearing it.
      
        
      blanket impl
      One impl for every type that meets a bound: impl<T: Speak> Greet for T.
      
        
      static dispatch
      Deciding while compiling which function a call runs, as generics do.
      
        
      symbol, nm
      A name stored in a program file for each function; nm lists them.
      
        
      E0369 / E0282 / E0283
      An operator used on a T with no bound promising it; type annotations needed (twice: the second also names a required trait).
      
        
      E0308 / E0599 / E0425
      Mismatched types (one T, two types; or two different hidden types); no such method for this stamped type; a type name, like an undeclared T, not found.
      
        
      E0046 / E0053 / E0277 / E0117
      A required trait method missing; an impl's method signature differs from the trait's; a type doesn't wear a required trait; the orphan rule broken.

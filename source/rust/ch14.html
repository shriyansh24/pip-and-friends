PART 1 · ROOMS AND DOORSPackage, crate and module; mod; everything private until you say pub; who may open which door

1

Mabel's late-fee program, her catalogue, her guessing game and her word counter all live in one main.rs. It is 400 lines long, and this morning she spent ten minutes looking for one function.

Mabel says: Imagine a library with no rooms. Every book, every desk, every filing cabinet, all piled in the lobby. You could find things, eventually. Nobody would call it a library.

Mabel says: Rust lets me put up walls. Rooms for the front desk, rooms for the stacks. And every room gets a door that I decide to lock or leave open.

2

Three words people mix up, and one picture to keep them apart.

PACKAGEthe plot of land

What cargo new makes: a folder with a Cargo.toml (the deed: the name, the version, what it depends on). A package holds one or more crates.

CRATEthe building

What the Compiler builds in one go. Its front door is the crate root: src/main.rs for a program you run (a binary crate), or src/lib.rs for code other programs use (a library crate).

MODULEa room

A named room inside a crate, made with mod. Rooms can hold items (functions, structs, enums) and smaller rooms. The crate root itself is the lobby.

Mabel says: Every program you've written so far was a package with one binary crate and no rooms: just a lobby, main.rs. Today we add rooms.

THE PRIVACY RULEone sentence
A private item can be used by code in its own room, and in any room inside that room. Nobody else.

      
THE OTHER WAY ROUNDlooking in
Code outside a room sees only what has pub on it. An inner room can see out; an outer room can't see in. Like a shop: staff can walk into the street, but the street can't walk behind the counter.

PART 2 · ADDRESSES AND SPEED-DIALPaths that start at crate::, super:: or self::; wrong addresses; use, as and { }


  

    9
    
A path is an address. You can start it from the front door of the building, from the room you're standing in, or from the room around you.

    
    
    

      
ABSOLUTE PATHfrom the front door
Starts with crate::, the root of your own crate. It means the same thing from anywhere in the building, like a full street address. (Paths into other crates start with that crate's name: std::cmp::max.)

      
RELATIVE PATHfrom where you stand
Starts with a name in the current room (stacks::tidy from the lobby), with self:: (this room, said out loud), or with super:: (one room out). Like "next door" or "upstairs".

    PART 3 · PUBLIC LABELS, PRIVATE DRAWERSpub struct with private fields, new as the only way in, enums whose variants follow the enum, and the errors E0616 and E0451
    

  
    
    15
    
    A library card has the owner's name printed on the front, where anyone can read it. The PIN is sealed inside, and only the front desk ever sees it.
    
    
    
    
    
      
    pub structthe card may leave the room
    Code outside can name the type, hold a Card and pass it around. But pub on the struct opens only the struct. Every field still has its own door.
    
      
    pub fieldone door per field
    Write pub before each field outsiders may read and change. A field without it is private: only code in the struct's own room (its impl methods, for example) can touch it.

    PART 5 · OTHER PEOPLE'S BUILDINGScrates.io, cargo add, what a version requirement like "0.10.3" allows, and the receipt called Cargo.lock
    

  
    
    26
    
    Your crate is one building in a city. crates.io is the city's public registry: well over a hundred thousand library crates that other people built and share for free. A dependency is a building you use but didn't build.
    
    
    
    
    
      
    Cargo.tomlthe order form
    You write which crates you need and which versions are acceptable: rand = "0.10.3". Cargo downloads them from crates.io and builds them with your code.
    
      
    Cargo.lockthe delivery receipt
    Cargo writes down the exact version of every crate it chose, including the crates they need. Next time, and on every other computer, the same versions are used.
    
    
    
  
    

  
    
    27
    
    Chapter 6 did this once for the guessing game. Now read every line.
    
    
    
    
      
      
    1. cargo add rand asks the crates.io index for the newest version of rand (Updating crates.io index) and writes it into Cargo.toml (Adding rand v0.10.3 to dependencies).
      2. 
      
    2. Features: with + and - lists optional parts of the crate that are switched on or off. The defaults are fine; features are for later (Chapter 24).
      3. 
      
    3. Locking 8 packages: rand needs helpers of its own, so Cargo picked versions for 8 crates in all, and recorded them in Cargo.lock.
      4. 
      
    4. The last two commands look at the results: the new line in Cargo.toml, and rand's entry in Cargo.lock, with its exact version.
      5. 
    
    
    
    The download needs the internet once. After that, Cargo keeps a copy on your computer. (The folder in the prompt is shown as ~: this session ran in a fresh, empty folder.)
    
  
    

  
    
    28
    
    A version number has three parts: major.minor.patch. Crates promise to break things only when the first non-zero part goes up. So "0.10.3" in Cargo.toml doesn't mean "exactly 0.10.3". It means "0.10.3 or any later version that promises to be compatible".
    
    
    
      
    In Cargo.tomlCargo may chooseNever
    
      
        
    rand = "0.10.3"0.10.3, 0.10.4, 0.10.9 …0.10.2, or 0.11.0 (the 10 is the "breaking" number while the first is 0)
    
        
    x = "1.2.3"1.2.3, 1.2.9, 1.3.0, 1.99.0 …1.2.2, or 2.0.0
    
        
    x = "=1.2.3"exactly 1.2.3anything else
    
          
    
    
    
    
      
      
    Mabel says: Cargo.toml says what you'd accept; Cargo.lock says what you got. Keep both with your project. cargo update is the only thing that moves the receipt to newer, still-compatible versions.

        What you learned in Chapter 14
        
    
          
      
        • LOCKED UNLESS YOU SAY PUBA package (Cargo.toml) holds crates; a crate (rooted at main.rs or lib.rs) holds modules made with mod. Every item is private: usable in its own room and rooms inside it. pub opens one door; every door on a path must be open (E0603). pub struct doesn't open its fields (E0616 to read, E0451 to build); pub enum opens all its variants.
          • 
      
        • USE IS A SPEED-DIAL, NOT A KEYPaths start at crate:: (the root), super:: (the room around), self:: (this room), a name here, or another crate's name. use makes a short name in its own room only, with as for nicknames and {a, b} for several. Wrong item: E0425. Wrong room or crate: E0433.
          • 
      
        • NO SIGN, NO ANNEXmod x; loads x.rs (or x/mod.rs), inside the folder of the file that declares it. A file with no mod line is never compiled; a mod line with no file is E0583. Declare each module once; use paths everywhere else.
          • 
      
        • THE TOML IS THE ORDER, THE LOCK IS THE RECEIPTcargo add puts a dependency in Cargo.toml; "0.10.3" means 0.10.3 or a later compatible 0.10. Cargo.lock records the exact versions used. Paths into a dependency start with its name.
          • 
      
        • CHECK SMALL, CHECK OFTEN#[cfg(test)] mod tests with use super::*; (forget it: E0425), #[test] functions, assert!, assert_eq! (left/right), assert_ne!, custom messages, #[should_panic(expected = ...)], and tests returning Result. cargo test runs them in parallel and ends with test result: and exit 0 or 101.

    Under the hood: the module tree, privacy at compile time, and the test harness
    
        
      
        
        
        
        The Professor says: Modules, privacy and use exist only while compiling. By the time the program runs, every path has been turned into a plain jump to the right function, and every door check has already happened.
        
      
        
      
        Every item has a full name
        
      hood.rs
        
      
        module_path!() is a macro that the Compiler replaces with the full path of the room it's written in. The crate's own name comes first: hood, the package name. That's the name other crates use for your library, and the name crate:: stands for inside it.
        
      
        How the Compiler builds the tree
        
      
        It starts at the crate root, reads it, and every time it meets mod x { ... } it adds a room; every time it meets mod x; it opens the file for that room and keeps going. Files it never reaches are never read (panel 22). Then it resolves every path against that tree (E0425, E0433 when that fails), and checks every door: an item is visible from a place if it is pub all the way along, or if that place is inside the item's room (E0603, E0616, E0451). Nothing about privacy is left for run time, so it costs nothing.
        
      
        Warnings about unused things
        
      warn.rs
        
      
        Because the Compiler knows exactly who can reach each private item, it can tell when nobody ever uses one: function `dust` is never used (the dead_code warning) and unused import. These are warnings, so the program still runs. When you split code into rooms, they're a good hint that something became unreachable.
        
      
        What cargo test builds
        
      
        cargo test compiles your crate a second way: with cfg(test) switched on (so mod tests exists) and with a generated main supplied by Rust's built-in test library, the test harness. That harness collects every #[test] function, runs each one in its own thread, catches its panic if it has one, and prints the report. That's why your own main never runs during tests, and why a panicking test doesn't stop the others.
        
    
        
  
        

  
        
    In real programs: how projects are laid out and tested
    
        
      
          
        
        • A short main.rs, a real lib.rs. Most programs keep main.rs to a few lines that read the input and call into the library crate. The library is where the rooms, the logic and most tests live. Chapter 16's search robot is built this way.
          • 
        
        • One topic per module, one module per file once it passes a screen or two. Names are short and lower case with underscores: front_desk, not FrontDesk.
          • 
        
        • Tests live next to the code. Almost every Rust file ends with #[cfg(test)] mod tests. These are called unit tests. Tests that use your library from outside, in a separate tests/ folder, are integration tests (Chapter 24).
          • 
        
        • Test names are sentences: three_days_costs_twenty, empty_shelf_panics. When one fails, the report already tells you what broke.
          • 
        
        • Machines run the tests too. Projects on code-hosting sites usually run cargo test automatically on every change ("continuous integration"), so a failing check is caught before it's shared.
          • 
        
        • Choosing a crate. Before adding a dependency, look at its page on crates.io and its documentation on docs.rs (Chapter 15): how recently it was updated, how widely it's used, its licence, and whether it has good docs and examples. Every dependency is code you trust.
          • 
        
        • A middle door. Besides private and pub, Rust has pub(crate): open to the whole crate, closed to everyone else. Libraries use it a lot. It's in Chapter 24 with re-exports (pub use).
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "Every .rs file is a module automatically." Only if some module declares it with mod name;. Otherwise it's never read (panel 22).
          • 
        
        • "mod is Rust's import, so I write mod helpers; in every file that uses helpers." mod creates a room, so it's written once, in the parent. Elsewhere, use a path or use (the E0583 note in panel 23).
          • 
        
        • "use gives me access." It only shortens a name. Access comes from pub (panel 13).
          • 
        
        • "A use at the top of the file works everywhere in the file." Only in the room where it's written, which isn't inside the file's mod blocks (panel 14).
          • 
        
        • "pub struct makes the fields public." Each field needs its own pub (panel 17). Enum variants are the exception (panel 16).
          • 
        
        • "super:: lets me reach private things." It's only an address. Private items are reachable from inside their room, whatever the path says.
          • 
        
        • "A child room can't see its parent's private items." It can: private means "this room and every room inside it". That's why use super::* in tests sees private functions.
          • 
        
        • "cargo test runs my program." It runs the test harness instead of main.
          • 
        
        • "Tests run top to bottom." They run at the same time, and finish in any order (panel 39).
          • 
        
        • "assert_eq!(expected, actual) is the required order." Rust calls the two sides left and right and doesn't care which is which. Pick one order and stick to it.
          • 
        
        • "#[should_panic] is enough." Without expected, any panic passes, even the wrong one (panel 37).
          • 
        
        • "rand = "0.10.3" means exactly 0.10.3." It means "0.10.3 or a later compatible 0.10". Exact versions live in Cargo.lock (panel 28).

    Words from this chapter
    
        
      
        
        
        package
        What cargo new makes: a folder with Cargo.toml, holding one or more crates (at most one library crate).
        
        
        crate
        What the Compiler builds in one go: a binary crate (a program) or a library crate (code for other programs).
        
        
        crate root
        The file the Compiler starts from: src/main.rs or src/lib.rs. The lobby of the building.
        
        
        module
        A named room inside a crate, made with mod. Holds items and other modules.
        
        
        item
        Anything a module can hold: functions, structs, enums, constants, modules, use lines.
        
        
        pub / private
        Public: usable from outside the room. Private (the default): usable only in its room and rooms inside it.
        
        
        path
        An item's address, with :: between the parts: stacks::fiction::shelve.
        
        
        absolute / relative path
        Absolute starts at crate:: (or another crate's name); relative starts from where you stand.
        
        
        super:: / self::
        The room around this one / this room.
        
        
        use
        Makes a short name for a path, in the room where it's written. as renames; {a, b} takes several; * takes every name (a glob).
        
        
        mod name;
        Declares a module whose contents are in name.rs or name/mod.rs.
        
        
        dependency
        Another crate your package uses, listed under [dependencies] in Cargo.toml.
        
        
        crates.io
        The public registry of shared Rust crates, where cargo add looks.
        
        
        Cargo.lock
        The file where Cargo records the exact versions of every dependency it chose.
        
        
        semantic versioning (semver)
        major.minor.patch, where only the first non-zero number going up may break things.
        
        
        version requirement
        What Cargo.toml says is acceptable: "0.10.3" means 0.10.3 up to (not including) 0.11.0.
        
        
        seed
        A starting number for a random number generator; the same seed gives the same numbers.
        
        
        test
        A function marked #[test] that checks one thing. It passes unless it panics (or returns Err).
        
        
        attribute
        A note to the Compiler in #[...] before an item: #[test], #[cfg(test)], #[should_panic].
        
        
        #[cfg(test)]
        Compile the next item only when testing.
        
        
        assert! / assert_eq! / assert_ne!
        Panic unless a condition is true / two values are equal / two values differ.
        
        
        #[should_panic]
        The test passes only if it panics; expected = "..." also checks the message.
        
        
        test harness
        The program cargo test builds around your tests: it runs them and prints the report.
        
        
        thread
        A lane of work running side by side with others. Tests run in separate threads.
        
        
        unit test / integration test
        A test next to the code, in mod tests / a test in the tests/ folder that uses the crate from outside.
        
        
        E0603 / E0616 / E0451
        A private item, module or struct reached from outside / a private field read / a private field written in a struct expression.
        
        
        E0425 / E0433 / E0583
        A name not found where you looked / a room or crate not found / a mod name; with no file.

Most test runs end with a visible | sed … that rewrites the closing time and a failing test's thread id to … (panel 33 explains why), after set -o pipefail so the real exit code survives. The plain cargo test runs (panels 31, 32 and 39) are single real runs: their timings, fingerprints and line order vary between runs, so each is labelled one possible run. cargo add fetched the crates.io index on 8 November 2026. All 57 programs (and the 11 extra project files they show) printed the same output with both versions except the four described on the "Version notes" page.

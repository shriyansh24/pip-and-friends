PART 1 · THE MAPthe standard library documentation: how a page is laid out, where methods live, and how to read a signature before you call it

1

The Professor says: Nobody memorizes it, not even the people who wrote it. Every Rust programmer keeps the documentation open in a browser tab, all day. It's the map of the standard library. Today you learn to read the map.

Picture: Mabel shrugs, overwhelmed. The Professor answers from the right.

2

This is a drawing of the page for Vec at doc.rust-lang.org/std (shortened; the real page is very long). Every type, every function and every macro in the standard library has a page laid out the same way.

  1. Search. Type a name, like dedup or HashMap. Results appear as you type. Press S or / anywhere on a docs page to jump into the box, and ? to see more search tricks.
  2. The sidebar lists everything on the page. Methods are the type's own. Methods from Deref are borrowed from a close relative (next panel). Trait Implementations are the skills the type has, like Clone and Debug.
  3. The path and the title. std::vec is the module (the room) where it lives; Struct says what kind of item it is. The same path goes in a use line, as in Chapter 13's use std::collections::HashMap;.
  4. Version and Source. "1.0.0" is the Rust version that added it. Source opens the real code of the standard library. Curious, not required!
  5. The description, almost always with small examples you can copy.
  6. Implementations: one entry per method. Each starts with its signature, the first line of the function, then a one-line summary. Click it for the full story and examples. The signature is the most useful line on the page (panel 4).
3

The standard library is one big crate (Chapter 14's word for a building), called std. Inside are modules, rooms with names like std::collections, std::fs and std::io. Inside the rooms are the items.

TYPESstruct, enum

Things you make values of: Vec, String, HashMap are structs; Option and Result are enums. Their pages list their methods.

TRAITSskills

Named abilities a type can have: Debug, Clone, Hash. A trait's page lists every type that has it. (Traits get their own chapters, 17 and 18.)

FUNCTIONS, MACROSand constants

Free-standing tools: std::fs::read_to_string, the println! and dbg! macros, the constant std::f64::consts::PI.

The Professor says: One thing trips up everybody. Some of Vec's most useful methods, like first, contains and sort, aren't in its own list. A Vec can act as a slice, [T] (Chapter 9), so it borrows every slice method. The docs put those under Methods from Deref<Target = [T]>. If you can't find a method, keep scrolling!

4

A signature tells you, before you write a single line, what goes in and what comes out. Tap each part of the one for pop.

Mabel says: The part I'll read first, every time: what's after the arrow. Does it hand me the thing itself, a gift box (Option), or a parcel (Result)? Catchphrase: read the arrow before you call.

The standard library isn't the only map. Here are the four you'll use, and how to open each one. (These open a browser, so this page can't show a captured run of them; the lab in the Professor's notebook walks you through it.)

    

      
doc.rust-lang.org/stdthe standard library
Everything that comes with Rust: Vec, String, Option, std::fs. Put a version in the address, like doc.rust-lang.org/1.99.1/std, to read the docs for exactly your Rust.

      
docs.rsevery crate on crates.io
Chapter 14's rand and every other published crate get pages in exactly the same layout, built automatically. Search for the crate name, then read it the same way.

      
cargo doc --openyour own project
Builds pages for your code and every dependency you use, at the versions in your Cargo.lock, and opens them in your browser.

      
rustup docoffline, on your computer
The docs were installed with Rust. rustup doc --std opens the standard library and rustup doc --book opens the Rust book. They work with no internet, on a train or a plane.

    14
    
A clippy warning has the same layout as the Compiler's messages, so you already know how to read it. Take the first one, top to bottom.

    
    
      
  1. warning: unneeded `return` statement
    What: "warning", not "error", so nothing stops you. This is advice.
    2. 
      
  2. --> src/main.rs:6:5 and the ^^^^ line
    Where: line 6, column 5, underlined.
    3. 
      
  3. = note: `#[warn(clippy::needless_return)]` on by default
    The lint's name: needless_return. Names are made of plain words joined with underscores, so most of them explain themselves.
    4. 
      
  4. = help: for further information visit https://rust-lang.github.io/rust-clippy/…#needless_return
    Every lint has its own page saying what it checks, why it's bad and an example. That's the lint's map page.
    5. 
      
  5. help: remove `return` with lines marked - and +
    The fix: remove the line marked -, write the line marked +. Chapter 4 explained why: the last expression of a function is its answer, so return isn't needed there.
    6. 
    

    

      
LintThe shortcutBefore → after

      
        
needless_returnThe last expression is the answer.return x; → x

        
ptr_argAsk for a slice: it accepts a Vec, an array or part of either (Chapter 9).&Vec<i32> → &[i32]

        
needless_range_loopLoop over the items, not over numbers you then use to index.for i in 0..v.len() → for x in &v

        
assign_op_patternThere's an operator for "add to".t = t + x → t += x

        
len_zeroSay what you mean.v.len() == 0 → v.is_empty()

        
bool_comparisonA bool is already true or false.if b == true → if b

Lints come in groups, and each group has a level: allow (silent), warn (a warning) or deny (an error). Plain cargo clippy uses the levels below.

    

      
GroupWhat it catchesLevel

      
        
correctnessCode that is outright wrong or useless, like panel 16's loop.DENY

        
suspiciousCode that is most likely wrong.WARN

        
styleCode that could be written the usual Rust way (most of panel 13).WARN

        
complexitySomething simple done in a complicated way.WARN

        
perfCode that could run faster.WARN

        
pedantic, restriction, nursery, cargoStricter, specialised or still-experimental lints. Teams switch on the ones they want, one by one.ALLOW

      
    

    
    
      
  • Can I switch one off? Yes, for one item: put #[allow(clippy::needless_range_loop)] on the line above the function. Do it rarely, and write a comment saying why. If you don't know why, the Trail Guide is probably right.
    • 
      
  • Can it fix them for me? Many suggestions can be applied automatically with cargo clippy --fix. It edits your files, so save your work somewhere first (the notebook's lab shows how).
    • 
      
  • (Not run for this page: #[allow] and --fix are described from the Clippy book, linked in the notebook.)
    • 
      
  • Is it the Compiler? Clippy runs the Compiler's checks first, then adds its own lints. So cargo clippy also reports every ordinary error and warning, in the same format.

Probes mean editing and re-running. A debugger is the other tool: it plays your program like a film, and hands you a remote control. You can pause on any line, look at every variable, and go forward one line at a time.

    
    
    
    
      
  • Breakpoint: a marker on a line (in VS Code, click left of the line number and a red dot appears). The program runs at full speed until it reaches that line, then pauses before running it.
    • 
      
  • Step over runs the current line and pauses on the next. Step into follows a function call inside. Step out runs to the end of the current function. Continue runs to the next breakpoint.
    • 
      
  • Variables shows every name and its value right now. Call stack is a live backtrace: the functions in progress, newest at the top.
    • 
    

    
A debugger session is interactive, so this page can't show a captured one. The next two panels are models of what you'd see, checked against the real runs; the notebook's lab sets up a real debugger on Windows, macOS and Linux (VS Code with CodeLLDB, or rust-gdb and rust-lldb).

    Under the hood: how the clues are made
    
      
      
      
        
        
      The Professor says: Every tool in this chapter is ordinary code you could read. Here's what each one is really doing.
      
      
      
      
      What dbg! writes for you
      
      
      dbg!(expr) is a macro, so it writes code before the Compiler checks your program. Roughly: evaluate expr once, take the value, print it to stderr with the file, line and column (from the macros file!, line! and column!), the expression's own text, and its {:#?} pretty Debug form (which is why Some("Ben") spread over three lines in Boss 1), then hand the value back. Taking the value is why dbg!(title) moved the String, and why dbg!(&title) doesn't. Two surprises: dbg! works exactly the same in a --release build (it is not removed for you), and the value must implement Debug, which is why Chapter 10 told you to derive it on almost everything.
      
      
      How a backtrace is made
      
      
      When a panic starts, the panic handler prints the message. If RUST_BACKTRACE is set, it then walks up the stack: each frame records where its function will continue when the call it made returns. Turning those raw addresses into names and file:line needs debug information, which cargo build and cargo run include by default (the "debuginfo" in cargo's [unoptimized + debuginfo] line). Release builds have less of it, so their backtraces show fewer details. The short form (=1) hides the frames before Rust starts your main and after the panic machinery begins; =full shows everything, including each frame's memory address:
      
      
      The full backtrace of panel 19's program (long)
        
      
        
      Made like panel 20's run, with RUST_BACKTRACE=full.
      
      
      
      
      The long hex numbers in std[68c81ae915296b05] tell apart different builds of the same crate. The path /rustc/58cf8f9c35b…/library/ names the exact compiler build: the std docs for this version show the same commit, std 1.99.1 (58cf8f9c3 2026-10-13), at the top of every page. On your machine those paths point to source files you may not have, and the addresses will differ (this page's runs were made with address randomisation off). Rust 1.97.0 printed different line numbers inside std for some frames: that code moved between versions.
      
      
      Why unwrap points at your line
      
      
      Functions like Option::unwrap, Result::expect and slice indexing carry the attribute #[track_caller]. It makes the function receive its caller's location as a hidden argument, and its panic message reports that location instead of its own. You can put #[track_caller] on your own functions too, for helpers whose panics are really the caller's fault.
      
      
      What clippy is
      
      
      cargo clippy runs the same compiler as cargo check, but through a driver called clippy-driver that registers several hundred extra lint passes. A lint pass looks at your program after it has been parsed and type-checked, so it knows, for example, that days_late is a u32 and that u32 starts at 0. That's how it can say "always false" when the Compiler's checks only warned. Clippy releases with Rust every six weeks; the help links in its messages include the version (rust-1.99.0 here), and Rust 1.97's clippy printed its own version instead.
      
      
      Why cargo check is fast
      
      
      Compiling has two big halves: checking (parsing, names, types, borrowing) and generating machine code. cargo check stops after the first half and writes no program, which is often several times faster. Your editor's red squiggles come from rust-analyzer running the same checks continuously.
      
      
      Why the test thread has a different id
      
      
      The test harness runs each test on a separate thread, named after the test, so that one panicking test can't stop the others. That's why panel 34's panic says thread 'tests::on_time_is_free', with a different id from a main thread. Without --test-threads=1, several tests run at once and their ok lines can arrive in any order.
      
    
      
  
      

  
      
    In real programs: how teams use the tool belt
    
      
      
        
        
      • Build servers check every change. A typical setup runs cargo fmt --check, then cargo clippy -- -D warnings (the -D warnings turns every warning into an error, so advice can't pile up unread), then cargo test. A change that fails any step isn't merged.
        • 
        
      • Lint settings live in Cargo.toml. Since Rust 1.74 a project can set lint levels in a [lints] table, for example [lints.clippy] with dbg_macro = "warn" to catch forgotten probes, so the whole team shares the same Trail Guide.
        • 
        
      • Allowing a lint, with a reason. #[allow(clippy::too_many_arguments, reason = "mirrors the C library's API")] keeps the explanation next to the exception. #[expect(…)] (Rust 1.81+) is like allow, but warns you if the lint stops firing, so stale exceptions get cleaned up.
        • 
        
      • Long-running programs log instead of probing. Servers use logging crates such as log or tracing: messages with levels (error, warn, info, debug) that can be switched on and off without changing code. They still write to stderr or a log file, never into the real output.
        • 
        
      • Before adding a dependency, people read its docs.rs page: is there an example, are the important functions documented, does the signature return a Result where failure is possible? Good docs are a sign of a well-kept crate.
        • 
        
      • Every bug gets a test. Many teams have the rule from panel 34: a bug fix isn't accepted without a test that failed before the fix and passes after. Over the years, these "regression tests" become a record of everything that ever went wrong.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "Good programmers know the whole standard library." They know how to find things in it quickly. The docs tab stays open.
        • 
        
      • "If a method isn't in the Methods list, the type can't do it." Look under Methods from Deref and the trait implementations too.
        • 
        
      • "v.first() gives me the first item." It gives an Option<&T>. Read the arrow.
        • 
        
      • "It compiles, so it's correct." Panel 16's loop compiled perfectly. The Compiler checks Rust's rules, not your intentions.
        • 
        
      • "Clippy warnings are just opinions; I can ignore them." Most are well-tested advice, and the deny-level ones are almost always real bugs. Read the lint's page before deciding.
        • 
        
      • "The bug is in the top frame of the backtrace." The top frames are std raising the alarm. Start at the first frame that's yours.
        • 
        
      • "The thread id in the panic message is an error code." It's just the thread's number, and it differs on every computer.
        • 
        
      • "Debugging with println! is fine." It works, but it mixes probes into the real output (panel 25). Use eprintln! or dbg!, and remove them afterwards.
        • 
        
      • "dbg! disappears in release builds." It doesn't. Remove it yourself, or let the dbg_macro lint remind you.
        • 
        
      • "Debuggers are for experts." Breakpoint, step over, look at Variables: three ideas. The first session takes ten minutes to set up (see the lab).
        • 
        
      • "Write the fix first, then a test." Write the failing test first. Then you know the test can catch the bug, and you know when the fix works.
        • 
        
      • "I'll just change things until it works." Random changes can hide a bug instead of fixing it. One hypothesis, one change, one run.

C++ · CHAPTER 10

MENUS AND PAUSE BUTTONS

Picture: Wren, the mechanic in orange coveralls, waves hello next to her red toolbox.

Wren's workshop has opened a little diner, and its program has grown too big for one file. First you'll split it the way real C++ programs are split: a menu that promises dishes (a header file), a kitchen that cooks them (a source file), and a waiter, the Linker, who checks every order has a cook. Then you'll learn to hunt bugs: a strategy, debug prints, the line that vanished, and a debugger with a pause button, so you can freeze a running program and look inside. About 100 minutes, with 25 hands-on checks.

  1. The menu and the kitchen: headers, sources, #include, building in steps
  2. The waiter's complaints: linker errors, header guards, one recipe per dish
  3. House rules for headers, and the map of a build
  4. Detective work: a strategy, debug prints, the vanishing line
  5. The pause button: gdb, breakpoints, stepping, the call stack
  6. Boss level and recap

PART 1 · THE MENU AND THE KITCHENOne program, several files

1

Wren's diner sells two things: soup (item 1, $4) and pie (item 2, $3). Her program knows the prices and adds up a table's bill. So far it all lives in one file.

diner_one.cpp 

      

    

    

      
      
Wren says: It works. But real programs have thousands of functions. One giant file is slow to rebuild, hard to find things in, and two people can't comfortably work in it at once. I want the prices in one place and the dining room in another.

    

    
Picture: Wren shrugs at a long single file.

  


  

    2
    
Big idea: think of a restaurant. The menu lists dishes: it promises them, but there is no food on it. The kitchen actually cooks each dish. Customers order from the menu without ever seeing the kitchen. And a waiter makes sure every order reaches a cook.

    
    

      
Wren says: In C++ the menu is a header file (.h): it holds declarations, the promises you met in Chapter 7. The kitchen is a source file (.cpp): it holds the definitions, the actual recipes. Today's motto: the menu promises, the kitchen cooks.

      
    

  


  

    3
    
The same program, split three ways. Read them in this order: the menu, the kitchen, the dining room.

    menu.h
    

    kitchen.cpp
    

    main.cpp
    

    
Build them together: list every .cpp file in one command. Headers are never listed; they ride along inside the .cpp files that include them.

    

    

      
      
Wren says: Same screen as panel 1. Lines 2 and 3 of menu.h are just signatures with semicolons: promises. Both .cpp files say #include "menu.h", so both know the promises. main.cpp can call price_of(1) without ever seeing how it's cooked.

    

    

  


  

  

  

    4
    
What does #include actually do? Something wonderfully simple. Before the Compiler reads a .cpp file, a helper called the preprocessor handles every line that starts with #. For #include, it finds that file and pastes its text in, right there.

    
    
You can watch it happen. g++ -E stops after the preprocessor and prints the pasted result; -P leaves out its bookkeeping lines. (Comments are removed too.)

    shout.h
    

    main.cpp
    

    

    

      
      
Wren says: The #include line is gone, and the promise from shout.h sits in its place. That's all a header is: text that gets pasted into every file that asks for it. An include is a paste.

    

  


  

  

  

    5
    
    
Two spellings. #include "menu.h", with quotes, looks next to the file being compiled first, then in the system folders. #include <iostream>, with angle brackets, looks only in the system folders (and folders you add with -I). Wren tries angle brackets for her own menu.

    main.cpp
    

    

    

      
      
The Compiler says: I searched the system folders, as the angle brackets asked, and I found a menu.h there! It just isn't yours. It belongs to a library for drawing menus in a terminal. It promises nothing called price_of.

    

    
A surprise from a real run: this machine has a system menu.h (from the ncurses library), so the include "worked" and the errors appear later. On a machine without that library, or with a name nobody else uses, you get the plain message:

    

    
    
      
  1. "not declared in this scope" although you did include a menu? Check which file the include really found. Wrong brackets can find a stranger's file.
    2. 
      
  2. "fatal error: ... No such file or directory" means the search found nothing. "Fatal" means the Compiler stopped at once: "compilation terminated."
    3. 
      
  3. The rule: quotes for your own headers, angle brackets for the standard library and installed libraries.
    4. 
    

  


  

  

  

    6
    
Under the hood, one g++ command did two jobs, as in Chapter 1. Now we split them. -c means "compile only": each .cpp file becomes an object file (.o), machine code with a list of what it needs and what it provides. Then a separate command links the object files into one program. This is how every build tool works, and it's how we'll build from now on.

    a terminal in ~/cpp-ch10/diner
    

    

      
STEP 1 · COMPILEg++ -c main.cpp
The Compiler reads one .cpp file at a time, with its headers pasted in. It checks every call against the promises it can see, and writes a .o. It never looks at other .cpp files.

      
STEP 2 · LINKg++ main.o kitchen.o -o diner
The Linker (ld) takes every .o, matches each call to the one definition that provides it, and writes the program. It never looks at source code.

    

    

      
      
The Linker says: You know me from Chapter 1: I pack the trays into one box. Tonight I'm the waiter. main.o hands me orders for price_of and bill_for; kitchen.o says "I cook both". Every order has a cook. Program served!

    

    
The bonus: change only kitchen.cpp, and you recompile only kitchen.cpp, then link again. In a project with a thousand files, that's the difference between seconds and an hour.

  


  

  

  
  
PART 2 · THE WAITER'S COMPLAINTSLink errors, pasting twice, and one recipe per dish


  

    7
    
    
Mistake one, the classic. Wren compiles the dining room and links it, but forgets the kitchen.

    

    

      
      
The Linker says: Table orders on line 6 and line 7, and I've checked every tray I was given. Nobody cooks price_of(int), nobody cooks bill_for(int, int). It's on the menu, so the Compiler was happy, but I can't serve a promise.

    

    
    
      
  1. Who's talking: /usr/bin/ld, the Linker. Step 1 printed nothing, so compiling was fine. That alone tells you: the problem is a missing definition, not a typo.
    2. 
      
  2. Where the order came from: main.o: in function `main', then main.cpp:6. The (.text+0x2f) is a position inside the machine code; you can ignore it.
    3. 
      
  3. What's missing: undefined reference to `price_of(int)'. The parameter types are in the name, which matters in a minute.
    4. 
      
  4. The last line: collect2: error: ld returned 1 exit status just means "linking failed". collect2 is the g++ helper that runs ld. The real news is always above it.
    5. 
    

  


  

    8
    
With clang++ the Linker is the same ld, so the complaints are word for word the same. Only the very last line changes: clang++ reports the failure in its own words.

    

    

      
      
Wren says: "linker command failed with exit code 1" is clang's version of collect2's line. The fix is the same: give the waiter the kitchen. g++ -c kitchen.cpp, then link main.o kitchen.o. If you build in one command, list both: g++ main.cpp kitchen.cpp -o diner. (Built that way, the message names a temporary file such as /tmp/cc plus random letters instead of main.o, different every time.)

    

  


  

    9
    
The Linker as a machine: object files go in, and either a program comes out or it jams with a complaint. Every result below is a real link run from this chapter. Try them all, including two you haven't met yet.

    

    
  


  

    10
    
    
Mistake two is sneakier. Here the kitchen is in the build. The menu promises tip_for(int). The kitchen cooks tip_for(double).

    tips.h
    

    main.cpp
    

    kitchen.cpp
    

    

    

      
      
The Linker says: Remember overloading from Chapter 7? To me, tip_for(int) and tip_for(double) are two different dishes with different names inside the object files. The kitchen cooked the double one. The order was for the int one.

    

    
Why didn't the Compiler notice? When it compiled kitchen.cpp, a new tip_for(double) looked like a perfectly legal second overload. Each file was fine on its own. Only the Linker sees all the files together. The cure: copy the signature from the header into the source file exactly, and always #include your own header in its .cpp file.

  


  

  

  

  

  

    11
    
    
Mistake three. Wren adds a struct (Chapter 9's forms) for an order. table.h needs it, so it includes order.h. main.cpp needs it too, so it includes order.h as well as table.h.

    order.h
    

    table.h
    

    main.cpp
    

    

    

      
      
The Compiler says: Line 3 of main.cpp pasted struct Order in. Line 4 pasted table.h, which pasted order.h again. Now I'm reading the same form twice in one file. A type may only be defined once per file.

    

    
    
      
  1. Follow the trail upward: "In file included from table.h:2, from main.cpp:4": the second paste came in through table.h.
    2. 
      
  2. The accusation: order.h:2:8: error: redefinition of 'struct Order'.
    3. 
      
  3. The witness: the note: shows the previous definition, pasted by main.cpp:3.
    4. 
    

  


  

    12
    
The fix is a header guard: three preprocessor lines that make a header paste itself only once per .cpp file, however many times it's included.

    
    

      
THE CLASSIC GUARDworks everywhere
order.h

      
THE SHORT GUARD#pragma once
order.h

    

    
Read the classic guard as a sentence. Line 1: "if the name ORDER_H is not defined yet..." Line 2: "...define it now, and keep everything down to #endif." The second time the header is pasted into the same file, ORDER_H already exists, so everything up to line 8's #endif is skipped. #pragma once says the same in one line. It isn't in the C++ standard, but g++, clang++ and Microsoft's compiler all support it (it can be fooled if the same header exists as two copies in different folders). Both builds now work:

    

    

      
      
Wren says: The guard's name just has to be unique in your project: the file name in capitals, with _H, is the custom. My rule: every header gets a guard, starting today, even if you think it's only included once.

    

  


  

  

  

  

  

  

  

    13
    
    
Mistake four: a recipe on the menu. specials.h holds a whole function, body and all. It's guarded, and two source files include it.

    specials.h
    

    main.cpp
    

    kitchen.cpp
    

    

    

      
      
The Linker says: main.o brought a cooked todays_special(). kitchen.o brought another one. Two cooks claim the same dish, and I refuse to guess which one to serve.

    

    
    
      
  1. The accusation: multiple definition of `todays_special()'.
    2. 
      
  2. The two suspects: the copy inside kitchen.o, and "first defined here", the copy inside main.o. The Linker names the .cpp file each object was compiled from; the :4 is line 4 of specials.h, where the pasted recipe came from.
    3. 
      
  3. The tell-tale sign: a header with a { body } for an ordinary function.
    4. 
    

  


  

    14
    
This is C++'s one-definition rule (the ODR), in plain words: a function may be declared as often as you like, but defined exactly once in the whole program. Promises can be printed on every menu; the recipe lives in one kitchen.

    

      
PROBLEMWHO SAYS SOFIX

Here's the fixed specials: the header keeps only the promise, and a new specials.cpp holds the one and only recipe.

    specials.h
    

    specials.cpp
    

    

    

      
      
The Professor says: Struct definitions like Order are allowed in headers, one per file, because they describe a shape and produce no machine code. The keyword inline also lets a function's body live in a header; we'll meet it properly in Chapter 28. Until then: bodies go in .cpp files.

    

  


  
  
PART 3 · HOUSE RULES FOR HEADERSSelf-contained, polite, and the map of a whole build


  

    15
    
    
Rule: a header must include what it uses. This menu.h mentions std::string, but leaves #include <string> to whoever includes it. main.cpp happens to include menu.h first.

    menu.h
    

    main.cpp
    

    

    

      
      
The Compiler says: I read the pasted menu.h before <string> was pasted, so I didn't know std::string yet. My note even shows the fix-it line, marked with +. The second error is just a knock-on: the declaration failed, so dish_name was never declared.

    

    
With the includes in another order, it would compile, and the bug would hide until someone else included menu.h first. Make each header self-contained: add #include <string> to menu.h itself. A good habit: in each .cpp file, include its own header first, so a missing include shows up at once.

  


  

    16
    
    
Rule: never put using namespace in a header. In Chapter 7 it was risky in your own file. In a header, it's poured into every file that includes it, whether they like it or not.

    tools.h
    

    main.cpp
    

    

    

      
      
The Compiler says: You wrote count. Thanks to the header's using namespace std;, I can also see the standard library's std::count function from <algorithm>, in two versions. Three candidates, one name: ambiguous.

    

    
The author of main.cpp did nothing wrong: they never asked for std's names. Don't skim the long notes: the useful parts are the first error line, and the candidate at the bottom, 'int count', which is yours. Fix: delete line 5 of tools.h and write std::vector in the header.

  


  

    17
    
The house rules, from the C++ Core Guidelines' section on source files (the SF rules). Pin them above your desk.

    
    
      
  1. Promises in .h, recipes in .cpp. Declarations in headers, function bodies in source files. (SF.1, SF.2)
    2. 
      
  2. A guard in every header. #ifndef, #define, #endif, or #pragma once. (SF.8)
    3. 
      
  3. Each .cpp includes its own header, so the Compiler can compare promise and recipe. (SF.5)
    4. 
      
  4. A header includes what it uses, so it works no matter who includes it first. (SF.11)
    5. 
      
  5. No using namespace in a header. (SF.7)
    6. 
      
  6. Never #include a .cpp file. List .cpp files in the build instead.
    7. 
      
  7. Quotes for yours, angle brackets for libraries. "menu.h", <vector>.
    8. 
    

    

      
      
Wren says: And a handy trick when a header only mentions a type, say in const Order&: it can say struct Order; instead of including order.h. That's a forward declaration of a type: "this form exists; you'll see its fields later." Fewer includes, faster builds.

PART 4 · DETECTIVE WORKA strategy, debug prints, and the line that vanished


  

    19
    
    
So far every mistake was caught by a tool. Some aren't. The diner's tip jar holds $4, $6, $9 and $5, which is $24. The program says otherwise, and builds without a single warning.

    tips_bug.cpp
    

      

      

    

    

      
      
Sneak says: Heh. I'm a logic error, also called a semantic error. The grammar is perfect, every type matches, and the program does exactly what you wrote. Just not what you meant.

    

    

      
SYNTAX ERRORSand type errors
Broken grammar or mismatched types: a missing ;, an undeclared name. The Compiler refuses to build. Annoying, but it tells you the line.

      
LOGIC ERRORSsemantic errors
It builds, it runs, it prints something wrong (or crashes). No tool points at a line. That's what debugging is for.

    

    
Picture: Sneak, a grey sneaky critter, grins. It stands for a logic bug.

  


  

    20
    
Staring at the code and changing things at random rarely works. Detectives have a method. So do programmers.

    
    
    
      
  1. Reproduce. Find input that fails every time. Here: just run it, $20 instead of $24.
    2. 
      
  2. Shrink. Narrow down where it goes wrong: the sum is wrong, so the loop is the suspect.
    3. 
      
  3. Guess. Make a precise guess: "$20 is $24 minus $4, the first tip. Maybe the loop skips index 0."
    4. 
      
  4. Test. Check the guess with evidence, not hope: a debug print, or the debugger in Part 5. Wrong guess? Back to shrinking.
    5. 
    

    

      
      
Wren says: My motto: reproduce, shrink, guess, test. And change one thing at a time, so you know which change mattered.

    

  


  

    21
    
The quickest test: make the program tell you what it's doing. Wren adds one debug print inside the loop. She sends it to std::cerr, the error stream, instead of std::cout.

    tips_debug.cpp
    

      

      

    

    

      
      
Wren says: Guess confirmed! The first debug line says i=1: the loop never visits index 0, the $4 tip. Line 7 should say int i = 0. The evidence pointed straight at it.

    

    

      
WHY std::cerr?the error stream
It's a separate stream from std::cout: debug lines stay apart from the real output, and the terminal shows them in error style. And it's unbuffered: each line goes out immediately. Panels 22 and 23 show why that matters.

      
LABEL EVERYTHINGDEBUG i=1 tip=6
A bare 6 tells you nothing. Print the names with the values, and a tag like DEBUG, so the lines are easy to find and to delete afterwards.

    

  


  

  

  

  

  

    22
    
    
A spooky one. The program prints two messages, then hits trouble and stops dead with std::abort() from <cstdlib>, which ends a program on the spot, as a failed safety check would.

    lost.cpp
    

      

      

    

    

      
      
Wren says: Where's Saving order 2...? Line 6 definitely ran, because line 7 came after it! If I were print-debugging, I'd think the program died before line 6. That's a lie the screen just told me.

    

    
Aborted is the shell telling you the program was killed by its abort signal; exit code 134 is how it reports that (128 + 6, the signal's number).

  


  

    23
    
The answer is buffering. Writing to the screen is slow, so std::cout collects text in a bucket (a buffer) and empties it in one go. It empties when the bucket is full, when you flush it (std::endl or std::flush), when the program ends normally, and, on a terminal, at the end of each line. std::abort() is not a normal ending: the bucket is thrown away.

    
    lost_fixed.cpp
    

      

      

    

    

      
      
Wren says: Sent to std::cerr, the message survives the crash, and the shell's Aborted lands right after it on the same line. Memory hook: cout waits for a full bucket; cerr shouts right away. Debug prints near a crash belong in cerr.

    

  


  

  

  

    24
    
When you have no idea where a bug lives, cut the search in half. Put one debug print in the middle. Is the value already wrong there? Then the bug is in the first half; otherwise in the second. Halve again. Sixteen suspect lines need only four checks. The same trick works by commenting out half of a long block with /* ... */ (or //): does the problem go away?

    
    

      
      
The rubber duck says nothing. Caption: And when you're truly stuck, explain the code, line by line, out loud, to a rubber duck (or a patient friend). Saying "and here i starts at 1, because..." is very often the moment you hear the bug yourself. Programmers really do this; it's called rubber-duck debugging.

PART 5 · THE PAUSE BUTTONgdb: freeze the program and look inside


  

    25
    
Debug prints mean editing, rebuilding and rerunning for every question. A debugger lets you ask questions while the program runs. Think of a film on a remote control: you can mark a scene, pause there, go forward one frame at a time, zoom into a scene, and ask what anything looks like right now. The debugger for g++ is called gdb, the GNU debugger.

    
    

      
      
Wren says: A breakpoint is a bookmark: "pause when the program gets here". While it's paused, nothing happens until you press a button. My new motto: don't guess. Pause and look.

    

  


  

    26
    
Two things before you start. Build with -g, which packs a map from machine code back to your lines and names, and -O0, "no optimising", so the machine code follows your lines one by one. Then, to record a real session for this page, the commands are kept in a file and gdb reads them with -x. At your keyboard you would type the same commands after gdb's (gdb) prompt.

    bill.cpp
    

    first.gdb (the commands, typed for you)
    

    

    
    
      
  1. The + lines are the commands gdb read from the file (that's what set trace-commands on does). Everything else is gdb's answer.
    2. 
      
  2. break total_bill sets a bookmark on the first line of the function: line 9. run starts the program, and it stops there: Breakpoint 1, total_bill (soup=12, pie=8), with the arguments shown. The two "libthread_db" lines are gdb noting it found a helper for the system's C library; ignore them.
    3. 
      
  3. The line gdb shows is the line about to run, not one that already ran. Paused at line 9, food doesn't have its value yet. One next later, line 9 has run, and print food says $1 = 20. ($1 is gdb's name for that answer, so you can reuse it.)
    4. 
      
  4. next again runs all of line 10, including the whole call to tip_for. info locals lists every local in the function. continue plays to the end: the program prints its bill, and gdb reports that it exited normally. (The process number differs on your machine.)

    34
    
      Read the crash like a detective. A backtrace from a crash starts inside the system's own code, so read down until you reach a file you wrote.
      
    
        
      
      1. What happened: Program received signal SIGABRT, Aborted. SIGABRT is the abort signal, number 6.
        2. 
      
      2. Frames #0 to #4 are inside the C library (pthread_kill.c, raise.c, abort.c): how abort() does its job. gdb has no source for them on this machine, hence "No such file or directory". Not your bug.
        3. 
      
      3. Frame #5 is the first one in your code: check_plates (plates=-2) at crash_gdb.cpp:7, the std::abort() line. The arguments already show the bad value: -2.
        4. 
      
      4. Frames #6 and #7 say how we got there: serve (plates=4, tables=3) at line 13, called from main at line 19, the second order.
        5. 
      
      5. Then question the witness: frame 6 jumps to serve, and print left gives -2: 4 plates minus 3 tables × 2. The guilty input is 4 plates for 3 tables.
        6.

    Under the hood: translation units, symbols and debug information
    
      
      
      Translation units
      
      
      The standard's name for "one .cpp file after all its includes are pasted in" is a translation unit. The Compiler only ever sees one translation unit at a time. That's the whole reason headers exist: they're how one translation unit learns about functions defined in another.
      
      
      What's inside an object file
      
      
      An object file holds machine code plus a symbol table: the names it defines and the names it needs. On Linux, nm -C main.o lists them: a T marks a function defined here ("text", the code section) and a U marks one that is undefined here and must come from elsewhere. The Linker's whole job is matching every U to exactly one T. Function names carry their parameter types (name mangling, Chapter 7's notebook), which is why tip_for(int) and tip_for(double) never match.
      
      
      Who adds the standard library?
      
      
      Your program also calls std::cout's machinery, which you never compiled. g++ quietly hands the Linker the C++ standard library (libstdc++) and the C library, which provide those symbols. That's one reason to link with g++ rather than calling ld yourself. Chapter 28 covers libraries in depth.
      
      
      What -g adds
      
      
      -g stores debug information (in a format called DWARF) inside the program: which machine-code addresses belong to which source lines, where each variable lives, and the types of everything. It makes the file larger but doesn't change what the program does. gdb reads it to translate between machine code and your source. Without it, gdb only has function names from the symbol table, which is exactly what panel 31 showed.
      
      
      Why breakpoints on line numbers can move
      
      
      gdb places a breakpoint on the first machine instruction of a line. Some lines produce no instructions (a lone {, a declaration with no initialiser), so gdb moves the breakpoint to the next line that does. With optimisation on, lines can be reordered, merged or removed entirely, which is why -O0 is the debugging setting.
      
      
      How a breakpoint works
      
      
      On x86 processors, gdb temporarily replaces the first byte of the instruction with a special one-byte "trap" instruction. When the processor reaches it, the operating system stops the program and tells gdb, which puts the original byte back so the program can continue. Watchpoints use the processor's debug registers instead: the hardware itself reports a write to the watched address.
      
      
      Buffering, precisely
      
      
      By default std::cout is synchronised with C's stdout, which is line-buffered when connected to a terminal (flushed at each newline) and fully buffered when sent to a file or a pipe (flushed only when the buffer fills). This page captured its runs through pipes, so a line ending in '\n' could also be lost there; the examples avoid that difference by using text without a newline, which is lost either way. std::cerr is unbuffered, and it is tied to std::cout: before cerr writes, cout is flushed. That's why panel 33 shows Left:  before the error message.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • Header and source pairs. Real projects are hundreds of name.h/name.cpp pairs, one per idea (Chapter 12 does it for classes). Some projects use .hpp and .cc or .cxx instead; the compiler doesn't care about the extension.
        • 
        
      • Build systems. Nobody types g++ -c for a thousand files. Tools such as CMake (Chapter 17), Make and Ninja track which .cpp files changed, or include a header that changed, and recompile only those. That's panel 6's bonus, automated.
        • 
        
      • Header-only libraries. Some libraries ship as headers alone. They make every function inline or a template, both of which are allowed to be defined in headers, so they never cause multiple definition.
        • 
        
      • Modules. C++20 added modules (import), which replace copy-and-paste includes with compiled interfaces. Support in compilers and build tools is still settling, so headers remain the everyday tool; Chapter 28 previews modules.
        • 
        
      • Logging instead of prints. Large programs keep their debug prints permanently, as log messages with levels (debug, info, warning, error) that can be switched on when needed.
        • 
        
      • Debuggers in editors. VS Code, CLion, Visual Studio and Xcode all wrap a debugger (gdb, lldb or Microsoft's) behind buttons: a red dot in the margin is a breakpoint, and the same next/step/finish/continue appear as icons, with locals and the call stack in side panels. The commands you learned are what those buttons send.
        • 
        
      • Crash reports. When a program crashes on a user's computer, crash reporters collect the backtrace, exactly like panel 34's, and send it to the developers.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "You compile header files." You compile .cpp files. Headers are pasted into them; never list a .h in the build command.
        • 
        
      • "Header guards prevent multiple definition errors." They stop a second paste into the same file. Two .cpp files each get their own paste. Panel 13.
        • 
        
      • "If it compiles, the Linker will be fine." The Compiler only checks promises; the Linker checks that every promise is kept, once.
        • 
        
      • "#include \"kitchen.cpp\" is a shortcut." It pastes the recipes into the including file; include it from two places and you get multiple definition. List .cpp files in the build.
        • 
        
      • "collect2: error is the error." It's only the summary. Read the ld lines above it.
        • 
        
      • "Quotes and angle brackets are interchangeable." They search different places, and angle brackets can find a stranger's file of the same name (panel 5).
        • 
        
      • "If a debug print didn't appear, the line didn't run." With std::cout, the text may be sitting in the buffer. Use std::cerr.
        • 
        
      • "The line gdb shows has just run." It's the line about to run.
        • 
        
      • "next skips the function." It runs the whole call; it just doesn't stop inside it.
        • 
        
      • "A debugger is only for crashes." It's just as good for wrong answers: pause, look, compare with what you expected.
        • 
        
      • "Optimised builds debug the same." Variables and whole functions can be optimised away. Debug at -O0.

    Lab: run it yourself (Windows, macOS, Linux)
    
      
      
      1. Build a multi-file program
      
      
      Make a folder diner with menu.h, kitchen.cpp and main.cpp from panel 3. Then either build in one command, g++ -std=c++23 -Wall -Wextra -g main.cpp kitchen.cpp -o diner, or in steps: g++ -std=c++23 -Wall -Wextra -g -c main.cpp, g++ -std=c++23 -Wall -Wextra -g -c kitchen.cpp, g++ main.o kitchen.o -o diner. Run with ./diner (Windows PowerShell: .\diner.exe). With Microsoft's compiler: cl /std:c++20 /W4 /EHsc main.cpp kitchen.cpp; its link errors say LNK2019: unresolved external symbol and LNK2005: already defined.       3. Install a debugger
      
      
        
        
      • Linux: sudo apt install gdb (Debian, Ubuntu) or sudo dnf install gdb (Fedora). Then gdb ./bill, and type commands after (gdb). quit leaves. Pressing Enter on an empty line repeats the last command, handy for many nexts.
        • 
        
      • macOS: gdb is awkward on Apple computers; use lldb, which comes with Xcode's command-line tools (xcode-select --install). The commands are close cousins: b total_bill, run, next, step, finish, p food, frame variable (for locals), bt, up, c.
        • 
        
      • Windows: with MSYS2's MinGW g++, install gdb with pacman -S mingw-w64-ucrt-x86_64-gdb; or use WSL and follow the Linux notes; or use Visual Studio's debugger (F9 breakpoint, F10 next, F11 step, Shift+F11 finish, F5 continue).

      4. Handy gdb extras
      
      
      gdb -tui ./bill shows the source in a window above the prompt. list shows lines around the current one. info breakpoints lists bookmarks; delete 1 removes one. break kitchen.cpp:5 sets a bookmark in a particular file. display food prints food after every step. run < input.txt feeds the program a file as keyboard input.
      
      
      5. No install?
      
      
      Compiler Explorer (godbolt.org) can build multi-file projects in "tree" mode. For stepping in the browser, Python Tutor's C++ mode (pythontutor.com/cpp.html) shows frames and values line by line for small single-file programs.
      
    
      
  
      

  
      
    Words from this chapter
    
      
      
      
        
      header file
      A file (.h) of declarations that other files include: the menu.
      
        
      source file
      A file (.cpp) of definitions that is compiled: the kitchen.
      
        
      declaration
      A promise that a name exists, with its type or signature, ending in ;.
      
        
      definition
      The actual recipe: a function with its body, or a type with its fields.
      
        
      preprocessor
      The step before compiling that handles # lines such as #include, #define and #ifndef.
      
        
      #include
      Paste the named file's text here. "..." looks next to the current file first; <...> looks in system and -I folders.
      
        
      translation unit
      One .cpp file with all its includes pasted in: what the Compiler sees at once.
      
        
      object file
      A .o file: one translation unit's machine code, plus the names it defines and needs.
      
        
      separate compilation
      Compiling each .cpp on its own (-c), then linking.
      
        
      linker
      The tool (ld) that joins object files and libraries into a program, matching each needed name to its definition.
      
        
      undefined reference
      The Linker's error for a name that is used but defined nowhere it was given.
      
        
      multiple definition
      The Linker's error for a function defined in more than one object file.
      
        
      one-definition rule (ODR)
      Declare as often as you like; define each function exactly once in the program, and each type at most once per translation unit.
      
        
      header guard
      #ifndef NAME_H / #define NAME_H / #endif: makes a header paste only once per file.
      
        
      #pragma once
      A one-line header guard supported by all major compilers (not part of the standard).
      
        
      forward declaration
      Declaring something before its definition: a function's signature, or a type's name (struct Order;).
      
        
      self-contained header
      A header that includes everything it uses, so it works whatever is included before it.
      
        
      syntax error
      Code that breaks the language's grammar; the Compiler refuses it.
      
        
      logic (semantic) error
      Code that builds and runs but does the wrong thing.
      
        
      debugging
      Finding and fixing the cause of wrong behaviour.
      
        
      debug print
      A temporary output line showing a value, usually sent to std::cerr.
      
        
      std::cerr
      The standard error stream: unbuffered, and tied to std::cout.
      
        
      buffer
      A holding area where output collects before being written in one go.
      
        
      flush
      Empty a buffer now: std::flush, or std::endl (newline plus flush).
      
        
      std::abort()
      Ends the program immediately, without normal clean-up; buffered output is lost. Exit code 134.
      
        
      rubber-duck debugging
      Explaining code out loud, line by line, until you hear the bug.
      
        
      debugger
      A program that runs another program under control: pause, step, inspect.
      
        
      gdb
      The GNU debugger, used with g++ (and clang++) on Linux.
      
        
      debug information
      The map from machine code to source lines and variables, added by -g.
      
        
      breakpoint
      A bookmark where the program pauses: break total_bill, break 9.
      
        
      next / step / finish
      Run one line (calls as one line) / one line, entering calls / until the current function returns.
      
        
      continue
      Run until the next breakpoint, watchpoint, or the end.
      
        
      watchpoint
      Pause whenever a variable's value changes: watch total.
      
        
      backtrace (bt)
      The list of unfinished calls, newest first: the call stack written out.
      
        
      frame
      One call on the stack; up, down and frame N choose which one gdb looks at.
      
        
      inlining
      An optimisation that pastes a function's body where it is called, so the call disappears.
      
        
      SIGABRT
      The abort signal (number 6), sent by std::abort().

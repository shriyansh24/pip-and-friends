# Go: beginner and intermediate curriculum map

Research as of 2026-11-07. Current Go: **go1.27.3** (released 2026-10-19); the language spec reads "Language version go1.27 (May 26, 2026)". Every compiler, vet, runtime and test message quoted below in backticks was produced by actually running go1.27.3 linux/amd64 in a scratch module (`go 1.27` in go.mod unless noted). Paths shown as `./main.go:L:C` are what the go command prints.

Legend for the "Covered by" columns: **TOUR** A Tour of Go; **GBE** Go by Example; **EG** Effective Go; **GD** go.dev docs/tutorials; **BOOT** boot.dev Learn Go (BOOT-H = its HTTP Clients/Servers courses); **LGWT** Learn Go with Tests; **EXM** Exercism Go track; **RM** roadmap.sh/golang; **GPH** Gophercises; **GOPL** The Go Programming Language; **ARD** Ardan Labs Ultimate Go; **UPN** UPenn CIS 193; **100M** 100 Go Mistakes; **CIG** Concurrency in Go; **GPG** Get Programming with Go; **LG2** Learning Go, 2nd ed.

**How deep the best treatments go.** The official Tour, which most people start with, has **zero slides dedicated to strings or runes**, **one slide on pointers** (plus five on receivers and indirection), ten slides plus one exercise on slices, and two content slides on generics. Go by Example gives strings three examples (runes, string functions, formatting), while Exercism splits them into five concepts (strings, strings-package, runes, string-formatting, strings-builder) and Learning Go gives pointers a whole chapter of ten sections. At the intermediate layer, 100 Go Mistakes spends seven mistakes on slice length/capacity/aliasing alone. **Almost every curriculum skips** the things a true beginner needs first: what a terminal and compiler are, how to set up an editor, how to *read* a compile error or panic stack trace, how to use a debugger (Delve appears in none of the tables of contents I opened; roadmap.sh has one "Stack Traces & Debugging" node), how to read keyboard input, and how to break a problem down. Most also assume prior programming outright (boot.dev FAQ, Ardan's prerequisites, UPenn's CIS 120 requirement). Our book therefore has to add roughly six "tooling and thinking" modules that no single source provides, spend 2–3 modules on slices and strings, where the free sources spend one or none, and flag version gates (1.18, 1.22, 1.23, 1.26, 1.27) that GOPL and Effective Go predate.

**Where curricula disagree, and the choice made here:**
- **Functions before or after collections.** TOUR teaches functions in its first module; GBE puts functions after arrays, slices and maps; BOOT puts functions 4th. Chosen: functions first (B15), because decomposing problems (B17) and testing (B29) need them, and slices are easier to explain when `append` can be shown as "a function that returns a new slice header".
- **Errors early or late.** TOUR teaches errors inside its methods/interfaces module; BOOT puts errors right after interfaces (chapter 7); GBE after generics; EXM requires interfaces before errors. Chosen: split. B16 teaches the *habit* (`n, err := strconv.Atoi(s); if err != nil`) as soon as input is read, because a beginner meets errors the moment they read text. B26 later explains that `error` is an interface, and I6 handles design.
- **Pointers.** TOUR introduces pointers before structs; GBE after closures and recursion; BOOT at chapter 11 after maps; EXM requires structs, slices and maps first. Chosen: after structs (B24), because "change the player's score from inside a function" is the motivating picture and that needs a struct.
- **Structs before loops.** BOOT teaches structs, interfaces and errors before loops and slices. Nobody else does. Rejected: control flow is more foundational for someone who has never programmed.
- **Strings.** TOUR never gives strings their own slide; GOPL puts strings in "Basic Data Types" before composite types; EXM requires slices, maps and range before runes. Chosen: plain strings in B5, the bytes/runes/UTF-8 story in B21 after slices, because "a string is a read-only slice of bytes" is the key picture.
- **Testing.** LGWT starts testing at Hello World; GOPL, LG2 and GBE put it near the end; EXM declares it out of scope. Chosen: B29 at the end of the beginner track, with "predict the output" exercises from B3 onward acting as informal tests. A comic for absolute beginners can't afford test syntax on page 5.
- **Concurrency placement.** BOOT and TOUR put goroutines and channels inside the beginner course; GPG makes it the final unit. Chosen: intermediate (I14–I18). Captured output is nondeterministic (see section 6), so it needs the debugging and testing modules first.
- **Generics placement.** TOUR, BOOT and GBE place generics late; LG2 makes it chapter 8 right after interfaces. Chosen: right after interfaces II (I7), since constraints *are* interfaces.
- **defer.** TOUR teaches defer in flow control, before any resource exists. Chosen: B27, with files, so the reason for defer (cleanup) is visible.

## 6. Facts for a "real runs only" course

**Current version and toolchain (verified 2026-11-07).**
- go.dev/dl lists exactly two supported releases: **go1.27.3** and **go1.26.10**, both released 2026-10-19. go1.27.0 came out 2026-08-19 and go1.26.0 on 2026-02-10. The spec header reads "Language version go1.27 (May 26, 2026)".
- Commands every page will use:
  - `go version` prints `go version go1.27.3 linux/amd64`.
  - `go mod init example/hello` prints `go: creating new go.mod: module example/hello`.
  - Run with `go run .`; build with `go build`. A successful build prints nothing.
  - `go test`, `go test -v`, `go test ./...`, `go test -bench=. -run=^$`.
  - `go vet .`, `gofmt -l .`, `gofmt -d file.go`, `go doc strings.CutLast`.
  - Dependencies: `go mod tidy`, `go get mod@version`.
  - Race detection needs cgo and a C compiler on Linux: `go run -race .`.
- **go.mod line surprise:** go1.27.3's `go mod init` wrote `go 1.27.3`. That contradicts the Go 1.26 release notes, which say a 1.N toolchain writes `go 1.(N-1).0`. The 1.27.3 source writes the local toolchain version (`gover.Local()`). Capture go.mod from the real tool; don't copy it from the notes.
- **Pin the toolchain.** The default is `GOTOOLCHAIN=auto`, so a go.mod asking for a newer Go makes the go command try to download that toolchain. Set `GOTOOLCHAIN=local` when capturing output, and record the exact version on each page.
- **First-run download noise.** On the first `go mod tidy`, the go command prints extra lines: `go: finding module for package rsc.io/quote`, then `go: downloading rsc.io/quote v1.5.2`, `go: found rsc.io/quote in rsc.io/quote v1.5.2`, plus download lines for indirect dependencies. The "downloading" lines are missing when the module cache is warm, so expected output differs between machines.

**Sources of nondeterminism (all observed except where marked).**
- **Map iteration order** is unspecified. The spec says "The iteration order over maps is not specified and is not guaranteed to be the same from one iteration to the next", and the runtime does randomise it: the same 6-key map ranged three times in one run gave three different orders. **However, `fmt.Println(m)` prints maps sorted by key** (`map[apple:2 mango:3 zebra:1]`), so printing a whole map is deterministic. Use `slices.Sorted(maps.Keys(m))` for ordered loops.
- **`select` with several ready cases** picks one "via a uniform pseudo-random selection" (spec). Observed: `abbabbaaba`.
- **Goroutine scheduling order.** Four runs of five goroutines produced four different orders. A program whose main returns before its goroutines finish prints nothing, or only part of the output.
- **Data races and `fatal error: concurrent map writes`** may or may not appear on a given run. The race detector exits with status 66, and its report contains memory addresses (`0x00c000114028`) that change.
- **Panic traces vary:**
  - absolute source paths (use `go run -trimpath .` to get `example/index_oob/main.go:8` instead);
  - `+0x9` offsets and `pc=0x499df6` values, which change with compiler version and code edits;
  - argument values like `sync.(*WaitGroup).Add(0x1f7a97806000, ...)`, which change every run because 64-bit heap base randomisation has been on by default since 1.26;
  - goroutine numbers (`goroutine 54`, `goroutine 19`).
  - Recommendation: show traces from a `-trimpath` run, label the volatile parts in the art, or crop to the `panic:` line plus `main.main()` and the file:line.
- **Timing:**
  - `go test` prints elapsed time (`ok  	example.com/calc	0.003s`), and it changes every run.
  - Benchmarks print the CPU model, a `-N` GOMAXPROCS suffix, iteration counts and ns/op.
  - `time.Now()`, `time.Since` and anything involving sleeps are nondeterministic.
  - `go test` with no package argument never caches, while `go test ./...` prints `(cached)` on repeat runs.
- **Randomness:** the top-level `math/rand/v2` functions are randomly seeded (two runs gave `94 38` and `52 35`). `rand.New(rand.NewPCG(1, 2))` repeats exactly (`76 61` both times). `crypto/rand` and `uuid.New()` are always random.
- **Pointer addresses** (`%p`, printing `&x`) change between runs.
- **Interactive input isn't echoed in captured output.** A Scanln program fed "Ada Lovelace" from a file printed `Name: Hello, Ada` on one line. Comic panels must draw the user's typing separately.
- **Floating point** printing is deterministic. `0.1 + 0.2` on float64 variables prints `0.30000000000000004`; as untyped constants it prints `0.3`.
- **Integer overflow** wraps silently at run time (two's complement). There is no undefined behaviour like in C.

**How errors look (shapes to teach once and reuse).**
- **Compile errors** go to stderr. The go command prints a header line with the package path, then one line per error in the form `./main.go:LINE:COL: message`, and exits with status 1. Some errors add tab-indented detail lines (`have (number)` / `want (int, error)`; `previous case`). Lines marked "syntax error:" come from the parser. A missing package clause comes from the go command itself, without `./` (`main.go:1:1: expected 'package', found 'import'`).
- **go vet** messages use `main.go:7:14: ...` without the header line.
- **Runtime panics:**
  - `panic: <message>` (runtime errors read `panic: runtime error: ...`), a blank line, `goroutine 1 [running]:`, then function/file:line pairs.
  - `go run` then prints `exit status 2`, while the `go run` process itself exits 1.
  - Nil dereferences add a `[signal SIGSEGV: segmentation violation ...]` line.
  - Deadlocks and some sync misuse show `fatal error:` instead of `panic:` and can't be recovered.
  - A panic inside a test shows `[recovered, repanicked]`.
- **Version-gate errors** all follow one template: `<feature> requires go1.NN or later (-lang was set to go1.MM; check go.mod)`. The go.mod `go` line, not the installed toolchain, decides which language features compile.

**Version-specific facts a beginner page must flag.**
- **Go 1.18:** generics (`[T any]`, `any`, `comparable`).
- **Go 1.21:** a go.mod line of 1.22+ is refused by 1.21 toolchains; toolchain directive and GOTOOLCHAIN.
- **Go 1.22:** each loop iteration gets its own variable. It's gated by the go.mod `go` line; the same closure program prints `3 3 3` under `go 1.21` and `0 1 2` under `go 1.27`. Also from 1.22: `for i := range 10`, `math/rand/v2`, and ServeMux method/wildcard patterns. 100M mistake #32 is obsolete from 1.22, and GOPL/Effective Go loop-capture advice predates it.
- **Go 1.23:** range over function iterators, the `iter` package, iterator functions in `slices` and `maps`.
- **Go 1.24:** `testing.B.Loop` (confirmed via the toolchain's api/go1.24.txt).
- **Go 1.25:** `sync.WaitGroup.Go` (api/go1.25.txt).
- **Go 1.26:** `new(expr)` (for example `new(42)`), self-referential generic constraints, `errors.AsType`, `slog.NewMultiHandler`, `go fix` rewritten as modernizers, Green Tea GC on by default, `cmd/doc` removed in favour of `go doc`.
- **Go 1.27:** generic methods (methods with their own type parameters; still not allowed in interfaces), struct literal keys may be any field selector, new std packages `uuid` and `encoding/json/v2` (and `encoding/json` is now implemented on v2 with the same API), `strings.CutLast`/`bytes.CutLast`, `go test` runs the `stdversion` vet check, a vet printf check for `%w` with pointer-to-error types, the goroutine leak profile is generally available, and time channels are always unbuffered (`asynctimerchan` removed).
- **Outdated material:** Effective Go states it predates generics and modules, and GOPL (2015) predates modules, generics, iterators and the loop change. Any pattern borrowed from them must be re-run on go1.27.3.

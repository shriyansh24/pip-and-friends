CHAPTER 16 · CAPSTONE

THE HEIST PLAN

Picture: Scoot, the bike courier in a red cap and green jacket, cheers with both arms up.

Fifteen chapters of tools: values, loops, functions, errors, slices, maps, structs, interfaces, files, packages and tests. Now Scoot puts them all in one real program: a command-line tool that reads a loot log, checks every line, adds up the scores and prints a neat table, or stops with a clear message when the input is wrong. The secret is the plan: a big job cut into small cards, each card a function with its own test. About 120 minutes, with 26 hands-on checks.

  1. The plan board: five small cards
  2. Casing the joint: the ways in
  3. Cracking each line: errors, not panics
  4. Splitting the loot: totals and a tidy report
  5. The answer keys: tests light up the board
  6. The getaway: build, exit codes, stderr
  7. Boss level and recap

PART 2 · CASING THE JOINTTwo ways in: command-line arguments and standard input


  

    8
    
Before a heist, the crew "cases the joint": they study every way in. A command-line program has two front doors.

    

      
      

        
Scoot says: Door one: arguments. Words typed after the program's name, like go run args.go Scoot crown. Good for short settings.

        
Scoot says: Door two: standard input. A stream of lines, typed live or poured in from a file. Good for lots of data, like our loot log.

      

    

    
Picture: Scoot, focused, points to the two doors.

  


  

    9
    
Door one. The words after the program name arrive in os.Args, a []string.

    args.go
    

    

    

    
    
      
  1. os.Args[0]
    The program's own name comes first. With go run it's the path of a temporary file Go builds and later deletes, so it changes from run to run: this program never prints it.
    2. 
      
  2. os.Args[1], os.Args[2]
    The words you typed, in order. len(os.Args)-1 counts them: 2.
    3. 
      
  3. if len(os.Args) != 3 (line 9)
    Check before you grab. With no words, os.Args[1] would crash with "index out of range". Instead the program prints how to use it, a usage line, on standard error and exits with 1. go run adds exit status 1.
    4. 
    

  


  

  

  

    10
    
Door two. Every program starts with three streams already connected, like pipes. One comes in; two go out.

    

    
    
      
  • standard input · os.Stdin
    Comes in. Typed, or poured from a file with <.
    • 
      
  • standard output · os.Stdout
    The results. fmt.Println writes here. > can send it to a file.
    • 
      
  • standard error · os.Stderr
    Messages about problems. Stays on the screen even when results go to a file.
    • 
    

    

      
      
Scoot says: Typing straight into a program works too: type your lines, then press Ctrl+D on macOS or Linux (Ctrl+Z then Enter on Windows) to say "that's all".

  1. panic: strconv.Atoi: parsing "lots": invalid syntax

      Picture: Scoot, happy, explains.
      
  
      

  
      
    33
    
      One real terminal session in the loot folder. (These steps run in one shell, as in a real terminal, so cd and $? carry from line to line. The rm -f step deletes any binary left from an earlier run, so go build really builds.)
      
    
      
    
        
      
      1. go build
        Prints nothing when it works. Silence is success. It names the binary after the module (example/loot), so the file is called loot (loot.exe on Windows).
        2. 
      
      2. ls
        There it is, next to the source files.
        3. 
      
      3. ./loot < haul.txt
        ./ means "the program in this folder". Same table as go run, but nothing is compiled this time.
        4. 
      
      4. ./loot < bad.txt
        The message from line 11 of main.go, starting with the program's name so users know who's talking. No exit status 1 line: that was go run reporting on the program it ran.
        5. 
      
      5. echo $?
        $? is the shell's memory of the last program's exit code: 1, from os.Exit(1). 0 means success; anything else means "something went wrong".
        6. 
    
      
  
      

  
      
    34
    
      Why bother with two output streams? Send the results into a file with > and see what happens to each.
      
    
      
    
        
      
      1. ./loot < haul.txt > scores.txt
        Nothing on the screen: standard output went into scores.txt. cat shows it there.
        2. 
      
      2. ./loot < bad.txt > scores.txt
        The error still appears on the screen, because standard error isn't redirected. If it had gone to standard output, it would have been hidden in the file.
        3. 
      
      3. The last cat scores.txt prints nothing
        > empties the file before the program starts, and the program printed no results. A script can check $? to know not to trust it.
        4. 
    
      
    
      
      
      
      Scoot says: Catchphrase: results to stdout, trouble to stderr, and an honest exit code.

    Under the hood: streams, exit codes, binaries and scanners
    
      
      
      
        
        
      The Professor says: Panel 10's three pipes are real. The operating system sets them up before your first line of Go runs.
      
      
      
      
      Three numbered streams
      
      
      Every process starts with three open file descriptors: 0 is standard input, 1 is standard output and 2 is standard error. Go's os.Stdin, os.Stdout and os.Stderr are *os.File values wrapping those numbers, which is why they fit the io.Reader and io.Writer sockets. The shell, not Go, handles < and >: before starting the program it connects descriptor 0 to the input file, or descriptor 1 to the output file. The program never knows whether it's talking to a keyboard, a file or another program. 2> errors.txt redirects standard error, and a | b connects one program's standard output to the next one's standard input.
      
      
      Exit codes
      
      
      When a process ends, it hands the operating system a small number. On Linux and macOS only the lowest 8 bits survive, so codes run from 0 to 255. Returning from main means 0. os.Exit(n) ends the process at once with n, skipping deferred calls (the os documentation says so explicitly). An unrecovered panic exits with 2. go run builds, runs the program as a child, and if the child's code isn't 0 it prints exit status N and itself exits with 1. That's why panel 33's binary run has no such line, and why scripts should run the built binary, not go run. Some tools go further and use 1 for "it failed" and 2 for "you used me wrongly".
      
      
      What go build produces
      
      
      A pure-Go program like loot is statically linked: the runtime, the garbage collector and every package you imported are inside the one file, so it runs on another computer with the same operating system and processor type without Go installed. (Programs that use cgo, for example through the net or os/user packages on Linux when a C compiler is installed, may depend on the system C library.) Build for a different system by setting two variables, for example GOOS=windows GOARCH=amd64 go build, which writes loot.exe. go build -o name chooses the file name. go install builds and copies the binary into $HOME/go/bin (or $GOBIN), so you can run it from anywhere once that folder is on your PATH.
      
      
      How bufio.Scanner reads
      
      
      The scanner asks the reader for a block of bytes at a time (4096 to start), finds line endings inside its buffer, and hands out one line per Scan. It removes a trailing \r as well as \n, so logs written on Windows read correctly. By default it refuses lines longer than 64 KiB: Scan returns false and Err returns bufio.ErrTooLong, which is exactly the case readHauls's sc.Err() check catches. Call sc.Buffer to allow longer lines.
      
      
      Why byWho[k].Items++ is refused
      
      
      A map stores its values inside an internal table that moves them around as it grows. The spec only lets you assign to things that are addressable, and map elements aren't, so a field of a struct stored in a map can't be the target of an assignment. Two ways out: copy out, change, store back (this chapter), or store pointers, map[string]*Total, so that byWho[k].Items++ changes the struct the pointer points at. The pointer version must create each Total before using it, or it dereferences nil and panics.
      
    
      
  
      

  
      
    In real programs: how Go command-line tools are organised
    
      
      
        
        
      • Thin main, fat packages. Real Go tools keep main tiny. A common shape: func main() { if err := run(os.Args, os.Stdin, os.Stdout); err != nil { fmt.Fprintln(os.Stderr, err); os.Exit(1) } }. Everything inside run is testable with fake input and output.
        • 
        
      • cmd/ folders. A module that ships several programs puts each main package in its own folder such as cmd/loot, and shared code in ordinary packages.
        • 
        
      • Flags. Options like -min 10 are parsed with the standard flag package rather than reading os.Args by hand, and it writes the usage message for you (chapter 21).
        • 
        
      • Files as well as standard input. Many Unix tools read the files named on the command line, or standard input when none are given. os.Open gives an *os.File, which is an io.Reader, so readHauls would work unchanged.
        • 
        
      • Golden files. For big outputs, tests often compare against an expected-output file stored in a testdata folder instead of a long string in the table (chapter 23).
        • 
        
      • Real-world examples. The Go toolchain itself (go, gofmt), Docker's CLI, Kubernetes' kubectl, Hugo and the GitHub CLI gh are all Go command-line programs built from exactly these pieces.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "If it works on my example, it works." One happy run tests one road. Try a bad line and an empty input too, and write them down as test rows.
        • 
        
      • "Panicking on bad input is fine, the user will see what's wrong." They'll see a stack trace meant for programmers, and exit code 2. Return an error with a clear sentence.
        • 
        
      • "_ is a safe way to silence the unused-variable error." It silences the Compiler, and hides the failure. Only use _ when you've decided the value really doesn't matter.
        • 
        
      • "os.Args[1] is always there." Only if the user typed something. Check len(os.Args) first.
        • 
        
      • "Command-line arguments are numbers if they look like numbers." They're always strings. Convert with strconv.Atoi.
        • 
        
      • "byWho[name].Items++ should work." Struct fields inside a map can't be assigned. Take the value out, change it, put it back.
        • 
        
      • "Ranging over a map gives the keys in insertion order." Go randomises it. Sort the keys.
        • 
        
      • "%8s cuts long names to 8 letters." A width is a minimum; long values are printed in full.
        • 
        
      • "Errors should be printed with fmt.Println." Print them to os.Stderr, so they're seen even when results are redirected.
        • 
        
      • "os.Exit runs my deferred clean-up first." It doesn't. Exit from main only, after everything is tidied.
        • 
        
      • "Exit code 0 means the program printed something useful." It means the program says it succeeded. Choose codes that tell the truth.
        • 
        
      • "A long main is simpler: everything's in one place." Simpler to write once; much harder to read, test and fix.

    Words from this chapter
    
      
      
      
        
      capstone
      A final project that uses everything learned so far.
      
        
      command-line program (CLI)
      A program used by typing commands in a terminal, reading arguments and input and printing results.
      
        
      decomposition
      Breaking a big problem into small jobs, each solved by its own function.
      
        
      command-line arguments, os.Args
      The words typed after a program's name. os.Args[0] is the program itself.
      
        
      usage message
      A short line telling the user how to run the program, printed when they get it wrong.
      
        
      standard input, os.Stdin
      The stream a program reads from: the keyboard, or a file poured in with <.
      
        
      standard output, os.Stdout
      Where results go. fmt.Println writes here; > can send it to a file.
      
        
      standard error, os.Stderr
      Where messages about problems go, kept separate from results.
      
        
      redirection
      The shell connecting a stream to a file: < in.txt, > out.txt.
      
        
      parse
      Turn text into structured values, such as a line into a Haul.
      
        
      validate
      Check that values make sense (three words, a whole number, more than 0), and report clearly when they don't.
      
        
      wrap (an error)
      Make a new error that adds context and keeps the original inside, with fmt.Errorf("...: %w", err).
      
        
      aggregate, tally
      Combine many items into totals, such as points per crew member.
      
        
      field width
      The minimum number of characters a Printf verb fills: %8s pads on the left, %-8s on the right.
      
        
      off-by-one error
      A loop or index that goes one step too far or stops one step too early.
      
        
      table-driven test
      A test with a slice of cases (input and expected result) checked by one loop.
      
        
      anonymous struct
      A struct type written in place without a name, as in []struct{ line string; want Haul }.
      
        
      binary, executable
      A program file made by go build that runs without Go installed.
      
        
      exit code, exit status
      The number a program hands back when it ends: 0 for success, other values for failure. $? shows it in a shell.
      
        
      os.Exit
      Ends the program at once with a given exit code, without running deferred calls.

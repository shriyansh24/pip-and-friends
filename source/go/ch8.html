CHAPTER 8

RECEIPTS AND FOOTPRINTS

Picture: Scoot, the bike courier in a red cap and green jacket, waves. Next to Scoot stands Inspector Pell, a detective in a brown hat and a tan trench coat, holding up a magnifying glass.

Things go wrong. Text isn't a number, a file isn't there, a box is empty. In Go, a function that can fail hands you a receipt with every result: an error value. Learn the Go habit of reading it first, and write receipts of your own. Then, when a program crashes or lies, follow its footprints like a detective, and learn the five-step loop that fixes any bug. About 90 minutes, with 25 hands-on checks.

  1. Every delivery has a receipt: errors as values
  2. Unread receipts: the classic mistakes
  3. Write your own receipts: errors.New, fmt.Errorf, and what to do with them
  4. Three kinds of bug
  5. Footprints: reading a panic like a detective
  6. The detective's method: debugging step by step
  7. Boss level and recap

    19
    
    You've read the receipt, and it isn't blank. Now what? There are three good answers. Pick by asking "who can actually do something about this?"
    
    
    
      
    PASS IT UPreturn 0, err
    Inside a helper function like weigh. It doesn't know whether the caller wants to skip, retry or stop, so it hands the receipt back and lets the caller decide.
    
      
    SKIP AND CARRY ONprint, then continue
    In a loop over many items, when one bad item shouldn't spoil the rest: say which one was skipped, and do the others.
    
      
    SAY SO AND STOPprint, then exit
    In main, when nothing useful can happen without this value. Explain the problem and end the program.
    
    
    
    
    
      
      
    Scoot says: What's never a good answer: ignoring it (panel 1), or crashing because of it (panel 21). Bad input is normal. People type "twelve". Files go missing. A good program expects that.

            Three more tools for the detective's kit.
            
    
            
      
            
        
        
            THE RUBBER DUCK
            
        
            Explain your code out loud, line by line, to a rubber duck (or a patient friend). Saying "and then this line…" makes you notice what the line really does. It works embarrassingly often.
            
      
            
      
            
        
        
            SMALLER STEPS
            
        
            Big jobs hide bugs. Split the problem into steps, one function each (chapter 7), and check each step on its own. A bug in a 5-line function has nowhere to hide.
            
      
            
      
            
        
        
            A DEBUGGER
            
        
            A debugger pauses a running program at a line you choose (a breakpoint), so you can look inside every box and step one line at a time. The debugger most Go programmers use is Delve (dlv), a free tool you install once. The Professor's lab below shows how.

            What you learned in Chapter 8
            
    
              
      
            • READ THE RECEIPT BEFORE YOU OPEN THE BOXA function that can fail returns (value, error), error last. nil means no problem. When err isn't nil, the value is a junk zero value.
              • 
      
            • CHECK RIGHT AWAY. LEAVE EARLY.if err != nil { … return } straight after the call. The happy path runs down the left edge; problems take an exit ramp.
              • 
      
            • NEVER DROP A RECEIPT_ and calls like os.Remove(…) with nothing caught hide errors. Give bad input an error value, not a panic.
              • 
      
            • WRITE RECEIPTS PEOPLE CAN READerrors.New("…") for a fixed message, fmt.Errorf("…%d…", x) with values, fmt.Errorf("order %d: %v", n, err) to add a note. Small letter, no full stop. Then pass it up, skip and carry on, or say so and stop.
              •

    Under the hood: what an error value is, and what a panic report really shows
    
            
      
            An error is an ordinary value
            
      
            Go has no special machinery for errors that can fail. An error is a value like an int: you can put it in a box, pass it to a function, return it, compare it with nil and print it. Strictly, error is an interface: any value that can describe itself in words with an Error() string method counts as an error. Println calls that method to get the text it prints. Interfaces are chapter 14's subject; for now, "a receipt with a message on it" is exactly right.
            
      
            What errors.New and fmt.Errorf build
            
      
            errors.New("x") makes a tiny hidden value holding the text "x" and hands you a receipt pointing at it. Two calls with the same text make two different receipts, which is why programs don't compare errors by their text. fmt.Errorf formats the message first, exactly like fmt.Sprintf, then does the same. With %w instead of %v it also remembers the receipt it wrapped (chapter 19).
            
      
            Why Go chose receipts
            
      
            Many languages report problems with exceptions: the failing code "throws", and the program jumps to some handler that may be far away. Go's designers chose to make errors visible in every function's signature instead: if a function can fail, you see error in its results and decide on the spot. The cost is many if err != nil lines. The benefit is that you can read a function from top to bottom and see every way it can go wrong. Go does have panic, but it's meant for bugs ("this should never happen"), not for bad input.
            
      
            The panic report, part by part
            
      
              
        
            • panic: runtime error: …: the reason. "runtime error" means a check built into Go fired, such as the index check and the integer-division check whose reports you read on this page. Not every panic says it.
              • 
        
            • A blank line, then goroutine 1 [running]:: the goroutine that crashed and what it was doing. With many goroutines (chapter 24), the report can list them all.
              • 
        
            • Pairs of lines, newest call first: a function name (package.function), then a tab and the file path with its line number. A function called from another function appears above its caller.
              • 
        
            • (...) after a name: the function was inlined, so its argument values aren't available. Hex values in brackets: the arguments in raw form; a trailing ? means the value may be out of date.
              • 
        
            • +0x65: how far into the function's machine code the crash happened. Useful to tools, not to you.
              • 
        
            • exit status 2: printed by go run, not by your program. A panicking Go program exits with code 2. go run then exits with 1 itself. If you build a program first (go build) and run it directly, there is no exit status line; the shell just sees code 2.
              • 
      
            
      
            The file paths in this book's reports are the real paths of the capture folder, /home/you/go-ch8/. On your computer they will be your own folder. Building with -trimpath replaces those paths with short module paths, which is how many real programs are shipped.
            
      
            Exit codes and the two output streams
            
      
            Every program ends with an exit code: 0 for success, anything else for failure. os.Exit(1) picks the code yourself. Every program also has two streams to the terminal: standard output and standard error. A shell can send them to different places, for example go run batch.go > load.txt puts the results in a file while the complaints still appear on your screen. Note that os.Exit ends the program immediately, without running any deferred clean-up (chapter 14).
            
    
            
  
            

  
            
    In real programs: where you'll see these every day
    
            
      
              
        
            • if err != nil is everywhere: opening files, reading from the network, talking to databases, parsing text. In the Go standard library, almost every function that touches the outside world returns an error last.
              • 
        
            • Command-line tools follow panel 20's pattern: print toolname: what went wrong to standard error, and os.Exit(1). Go's log package has a shortcut, log.Fatal(err), which prints the error with a timestamp and exits with code 1.
              • 
        
            • Adding context as receipts travel up (panel 17) is how real error messages end up reading like load config: open settings.json: no such file or directory: each layer adds what it was doing.
              • 
        
            • Servers mostly "skip and carry on": one bad request gets an error reply, and the server keeps serving everyone else.
              • 
        
            • Panics in real code are bugs, reported with exactly the layout you learned. Crash reporters and logs show the same trail, often with many more frames: read it the same way, first line first, then the first frame in your code.
              • 
        
            • Debuggers: VS Code's Go extension and GoLand both use Delve underneath, so clicking in the margin to set a breakpoint is the same break command as in the lab.
              • 
      
            
    
            
  
            

  
            
    Common wrong ideas
    
            
      
              
        
            • "If there's an error, the value will be something sensible." By custom it's the zero value (0, ""), and you mustn't use it. Some functions document a useful partial value, but don't rely on it unless the docs say so.
              • 
        
            • "nil means zero." nil means "no value here" for things like errors. An int can never be nil (panel 18).
              • 
        
            • "Printing the error is handling it." Printing and then carrying on with the junk value (panel 8, scan_err.go) still uses junk. Handling means choosing a road: pass up, skip, or stop.
              • 
        
            • "_ makes errors go away." It only stops you seeing them.
              • 
        
            • "Bad input should panic so I notice." Bad input is normal. Return an error; save panics for impossible situations.
              • 
        
            • "Error messages should look like sentences: Too heavy!" Go style is small letter, no full stop, because messages get chained: order 7: too heavy.
              • 
        
            • "The last line of the report is the important one." In Go it's exit status 2. Read the first line first.
              • 
        
            • "The line in the top frame is where the bug is." It's where the program crashed. The wrong value may come from a footprint further down (panel 26).
              • 
        
            • "If it compiles, it works." The Compiler checks types and names, not your intentions. Panics and wrong answers both compile.
              • 
        
            • "Change several things at once to save time." If it starts working, you won't know which change fixed it, and the others may have added new bugs.
              • 
        
            • "Debug prints are unprofessional." Professionals use them all the time. Just delete them when you're done.

The steps were checked by hand with Delve 1.27.2 and Go 1.27.3.
            
      
            dlv debug              start the program under Delve, paused before main
(dlv) break main.go:16   a breakpoint on the line that calls label(shelf, 5)
(dlv) continue           run until the breakpoint (short form: c); "parcel: kite" prints first

    Words from this chapter
    
            
      
            
        
            error
            Go's type for "something went wrong" values: the receipt. Returned as a function's last result.
            
        
            err
            The name Go programmers give a box holding an error.
            
        
            nil
            "No value here". An error that is nil means no problem. Prints as <nil>.
            
        
            if err != nil
            "If there is a problem". The check that goes straight after any call that can fail.
            
        
            early return
            Leaving a function as soon as there's a problem, so the rest only runs on the happy path.
            
        
            happy path
            The way through the code when nothing goes wrong. In Go it runs down the left edge, not indented.
            
        
            errors.New
            Makes a new error value with a fixed message.
            
        
            fmt.Errorf
            Makes a new error value from a format, like Sprintf, so the message can include values.
            
        
            context (in an error)
            Extra words added in front of a receipt as it's passed up, like order 7:.
            
        
            standard output / standard error
            A program's two streams to the terminal: os.Stdout for results, os.Stderr for complaints.
            
        
            os.Exit(code)
            Ends the program at once with that exit code. 1 is the usual "it failed" code.
            
        
            exit code
            A number a program hands back when it ends: 0 for success, anything else for failure. A panic gives 2.
            
        
            bug
            A mistake in a program. Three kinds: compile error, panic, wrong output.
            
        
            compile error
            A problem the Compiler finds before the program runs. Nothing runs.
            
        
            panic
            A crash while the program is running, with a report and exit code 2.
            
        
            logic bug
            The program runs and ends normally but does the wrong thing. No message at all.
            
        
            panic report / stack trace
            What Go prints when it panics: the reason, then the functions that were running, newest first, with file and line.
            
        
            stack frame (frame)
            One function call that is still running. Each pair of lines in the trace is one frame: one footprint.
            
        
            goroutine
            One line of work running in a Go program. Every program starts with goroutine 1.
            
        
            inlined
            A small function whose body the Compiler copied into its caller. Shown as (...) in a trace.
            
        
            runtime error
            A problem caught by Go's own checks while running, like an index out of range.
            
        
            debugging
            Finding and fixing bugs. The loop: reproduce, read, hypothesise, change one thing, re-run.
            
        
            hypothesis
            A guess about the cause that you can test.
            
        
            tiny reproduction
            The smallest program that still shows the bug.
            
        
            print debugging
            Adding temporary print lines to see what's in your boxes while the program runs.
            
        
            %#v
            Prints a value the way you'd write it in Go code: strings in quotes, arrays with their type.
            
        
            go vet
            A checker that reports code which compiles but is probably wrong.
            
        
            rubber duck debugging
            Explaining your code out loud, line by line, to find the bug yourself.
            
        
            debugger / Delve
            A tool that pauses a running program so you can look inside it. Delve (dlv) is the one most Go programmers use; it's a separate free tool you install.
            
        
            breakpoint
            A line where the debugger pauses the program.
            
        
            exception
            Other languages' way of reporting errors by jumping to a handler. Go uses error values instead.

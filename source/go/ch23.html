PART 1 · THE RACK OF TEST TUBESTable-driven tests, t.Run subtests, -v and -run

1

Scoot's fee calculator decides how many coins each parcel costs. One wrong number, and every customer that day pays the wrong price. So every morning, before the first delivery, Scoot takes the calculator to the Professor's lab.

Scoot says: I wrote my first tests in chapter 15. Now I have twenty cases, a function that sleeps, a clock that changes every second, and a bug that only shows up on Tuesdays.

The Professor says: Then you need a proper lab. Racks for many cases, safety rules, and a few clever instruments. Go has all of them built in: one package, testing, and one command, go test.

Picture: Scoot shrugs, worried. The Professor, in a lab coat, answers calmly.

2

A chemist doesn't test one sample and go home. She fills a rack of tubes, writes a label on each, notes what should happen, and checks them one by one. A Go table-driven test is that rack.

  1. 1The label: the name you give the case. It is the name field, and go test prints it.
  2. 2The sample: the input, here the parcel's weight in kilograms.
  3. 3The line on the glass: the answer you want.
  4. 4The stamp: PASS or FAIL, printed for every tube separately.

The Professor says: Catchphrase: one tube, one label, one answer. Each case gets a name, and each name gets its own verdict.

3

Two honest notes before we go on, because every terminal on this page is a real run.

    

      

        
THE …s

        
go test ends with the time the whole package took, such as 0.003s. It changes on every run, so this page pipes the output through sed, a tool that edits text as it flows past: sed 's/\t[0-9.]*s\b/\t…s/' swaps a tab and a time for a tab and …s. The command is shown in full each time. On your computer you'll see real numbers.

      

      

        
THE FOLDERS

        
Each example is a tiny module of its own, made with go mod init example.com/parcel, in a folder such as ~/go-ch23/tubes. Each terminal starts in ~/go-ch23 and walks into the example's folder with cd, then the prompt shows the new folder. go test with no arguments tests the package in the folder you are standing in.

    7
    
The real terminal. Read it like a detective: last line first, then work upwards.

    

    
    
      
  1. set -o pipefail (before the test)
    A shell setting. Without it, a line like go test -v | sed … ends with sed's exit code, which is 0 even when tests fail. With it, the line's exit code is go test's own. The road map in panel 21 reads that exit code.
    2. 
      
  2. FAIL	example.com/parcel	…s (last line)
    The verdict for the whole package. Something in here failed.
    3. 
      
  3. exit status 1 and FAIL
    The test program that go test built ended with exit code 1: "some test failed". go test itself then exits with 1 too, which is how scripts and build servers notice.
    4. 
      
  4. --- FAIL: TestFee (0.00s)
    A parent fails as soon as any of its subtests fails. Below it, every tube has its own stamp: three PASS, two FAIL.
    5. 
      
  5.     fee_test.go:21: Fee(8) = 16, want 11
    Each message appears straight under the === RUN line of the tube that wrote it. fee_test.go:21 is the t.Errorf line in the test, not the bug in fee.go. The test tells you which tube and what went wrong; finding why is your job.
    6. 
      
  6. The message itself
    The house style for test messages is got, want: the call, what it returned, what it should have returned. Fee(8) = 16, want 11 needs no explaining.

    9
    
When one tube cracks, you'll fix the code and re-run just that tube, many times. -run picks tests by name.

    

    
    
      
  1. -run 'TestFee/bowling'
    -run takes a pattern (a regular expression, a small language for matching text). A slash splits it into levels: TestFee must match the top-level test's name, bowling the subtest's name.
    2. 
      
  2. TestFee/bowling_ball
    A pattern only needs to match part of a name, so bowling finds bowling_ball. Add ^ and $ to insist on the whole name: -run '^TestFee$'.
    3. 
      
  3. The quotes
    Single quotes keep the shell from changing anything in the pattern. They matter as soon as your pattern has characters like $, * or a space.
    4. 
      
  4. The parent still runs
    === RUN   TestFee appears, because the subtest lives inside it, but only one child is started.

PART 2 · LAB SAFETYt.Error vs t.Fatal in subtests, t.Helper, t.Cleanup, testdata and golden files


  

    10
    
The lab has two ways to report trouble. Chapter 15 met them in one test; inside a rack they behave in a way worth seeing.

    

      

        
        
t.Error / t.Errorf

        
Write a note on the clipboard: "this tube is wrong". Then carry on with the rest of this tube's checks. The test is marked failed at the end.

      

      

        
        
t.Fatal / t.Fatalf

        
Write the note, then put this tube down and walk away from it. Nothing after the Fatal line runs in this function.

      

    

    

      
      
Scoot says: So if one tube calls Fatal... does the whole rack stop?

    

  


  

    11
    
Let's find out. Two tubes hold weights that make no sense, and the test refuses them with t.Fatalf.

    fatal_sub/fee_test.go
    

    

    
    
      
  1. fee_test.go:18: Fee(-2): a parcel must weigh something
    Line 18's t.Fatalf ran for the negative tube. Its t.Logf on line 23 never printed: Fatal stopped that function on the spot.
    2. 
      
  2. fee_test.go:23: Fee(3) checked
    The shoebox tube still ran, all the way to the end. t.Logf writes a note that is shown with -v or when the test fails; it never changes the verdict.

    4.

    15
    
    The t you get in every test has more tools that tidy up after themselves. You don't need them today; know that they exist.
    
    
    
      
    t.TempDir()
    Makes a brand-new empty folder for this test and returns its path. It is deleted automatically when the test ends, through t.Cleanup. Perfect for tests that write files.
    
      
    t.Setenv(k, v)
    Sets an environment variable for this test only, and puts the old value back afterwards.
    
      
    t.Chdir(dir)
    Moves the test into another folder, and moves it back at the end (Go 1.24).
    
      
    t.Context()
    A context that is cancelled just before the cleanups run (Go 1.24). Chapter 26 explains contexts.

    golden/receipt.go

      go test runs each package's tests inside that package's folder, so a path relative to the folder always works, whoever runs the test and from wherever.

    2. Why the name testdata?

    PART 3 · EXAMPLES, COVERAGE AND THE ROAD MAPExample functions as documentation, -cover, and every road go test can take
    

  
    
    17
    
    Chapter 15 showed that an Example function with an // Output: comment is run and checked. Here's why people write them: they are documentation that can't go out of date.
    
    example/example_test.go
    
    
    
    
    
      
      
    1. package parcel_test (line 1)
      A test file may belong to a second package whose name ends in _test. It sits in the same folder but sees parcel from the outside, exactly like a user: it must import it and write parcel.Fee, and it can't touch lowercase names. That makes the example honest.
      2. 
      
    2. func ExampleFee() (line 9)
      The name says what it documents: ExampleFee is shown next to Fee in the package's documentation on pkg.go.dev, together with its output. Example alone documents the whole package; ExampleFee_heavy adds a second example with a suffix.
      3. 
      
    3. // Output: (lines 12 to 14)
      go test runs the example and compares everything it printed with these lines. If the output can come in any order, write // Unordered output: instead. With no output comment at all, the example is compiled but not run.
      4. 
    
    
  
    

  
    
    18
    
    The lab has three kinds of experiment, and each has its own name pattern in a _test.go file. (A fourth, the benchmark, measures speed rather than checking answers: part 5.)
    
    
    
      
    
        
        
    TestXxx
    
        
    Unit test, func TestXxx(t *testing.T). You know the inputs and the answers. A rack of tubes, each one checked. Most tests are these.
    
      
    
      
    
        
        
    ExampleXxx
    
        
    Example, func ExampleXxx(). A recipe card in the documentation that is also checked, so it can never lie. Shows a reader how to call your code.
    
      
    
      
    
        
        
    FuzzXxx
    
        
    Fuzz test, func FuzzXxx(f *testing.F). You don't know every input, but you know a rule that must always hold. A machine throws thousands of strange inputs at the code to break the rule.

    23
    
      Some code waits on purpose: "ride to each stop, one second each". A test for it has to wait too... or does it?
      
    
      
      
      
        
        
      REAL TIME
      
        
      The test really waits. Two seconds here, five there: a few hundred tests and the whole suite takes minutes. Worse, a test that checks "it took about two seconds" can fail on a busy computer. Tests like that are called flaky: sometimes pass, sometimes fail, same code.
      
      
      
      
      
        
        
      A BUBBLE CLOCK
      
        
      Put the test inside a bubble with its own fake clock. When the code sleeps and nothing else in the bubble can happen, the clock simply jumps forward. Two "seconds" pass in no time at all, and always exactly two.
      
      
      
    
      
  
      

  
      
    24
    
      First the slow way. Deliver sleeps one second per stop.
      
    sleepy/deliver.go
    
      
    sleepy/deliver_test.go
    
      
    
      One possible run. These times are real and different every time, so there's no sed here.
      
    
      
    
        
      
      1. The time on the --- PASS: TestDeliver line
        The test passed, after really waiting about two seconds.
        2. 
      
      2. took …s of real time
        Never exactly 2 seconds: Sleep waits at least as long as asked, and there's always a little extra. That's why you can't write if took != 2*time.Second against a real clock.
        3. 
      
      3. Sleeping in tests has a second, worse form
        Sleeping "long enough" to wait for something else to finish, such as a goroutine (chapter 24). It's the classic source of flaky tests: 100 Go Mistakes lists it as mistake #86.
        4. 
    
      
  
      

  
      
    25
    
      The same Deliver, unchanged. The test wraps its body in synctest.Test, from the testing/synctest package (Go 1.25).
      
    bubble/deliver_test.go
    
      
    
      
    
        
      
      1. synctest.Test(t, func(t *testing.T) { ... }) (line 10)
        Runs the function in a bubble. Inside, time.Now, time.Sleep and the other time functions use the bubble's fake clock.
        2. 
      
      2. bubble clock started at 2000-01-01 00:00:00 +0000 UTC
        Every bubble's clock starts at midnight on 1 January 2000, UTC. Always the same, so tests are repeatable.
        3. 
      
      3. took 2s of bubble time and (0.00s)
        Exactly two seconds of fake time, so line 17 can compare with !=, in less than a hundredth of a second of real time. When Deliver sleeps and nothing else in the bubble can run, the fake clock jumps straight to the moment the sleep ends.
        4. 
      
      4. Version gate
        synctest.Test arrived in Go 1.25. On Go 1.24 this test fails to build (see the version notes in the notebook).
        5. 
    
      
    
      
      
      
      Scoot says: Catchphrase: in the bubble, waiting is free. Two seconds, two hours, two days: the test still finishes at once.

      PART 5 · THE STOPWATCH RACE AND THE FUZZ MACHINEBenchmarks with b.Loop, fuzzing, -race and test caching
      

  
      
    30
    
      How long does one call to Fee(8) take? Far too little for any stopwatch to see. So the lab runs a stopwatch race: do it once and time it, then many more times, each round sized from the one before, until the whole race lasts at least a second. Then divide the time by the number of laps.
      
    
      
  
      

  
      
    31
    
      A benchmark is a function called BenchmarkXxx that takes a *testing.B. The code to time goes inside for b.Loop() { ... } (Go 1.24).
      
    bench/fee_test.go
    
      
    
      One possible run. Benchmark numbers change on every run and on every computer, so nothing on this page uses them as an answer.
      
    
      
    
        
      
      1. go test -bench=.
        Benchmarks only run when you ask. -bench takes a pattern like -run; . matches every name. (Ordinary tests run first; this package has none.)
        2. 
      
      2. goos, goarch, pkg, cpu
        Which system, processor and package. Numbers are only comparable on the same machine.
        3. 
      
      3. BenchmarkFee-2, then the laps, then ns/op
        -2 is GOMAXPROCS: how many processor cores Go may use (this machine has 2). Then how many times the loop ran, and the average time per run in nanoseconds (billionths of a second).
        4. 
      
      4. In this run, BenchmarkFeeOldStyle looks faster. It isn't.
        The old way, for i := 0; i < b.N; i++, never uses Fee's result, so the Compiler may quietly throw part of the work away, and the stopwatch times an almost empty loop. b.Loop keeps the calls inside it from being optimised away, and also starts the stopwatch only when the loop begins, so setup before it isn't timed. 100 Go Mistakes #89 is all about benchmarks that measure the wrong thing.
        5. 
    
      
    
      
      
      
      The Professor says: Catchphrase: a stopwatch race, run until the time is steady. And never trust one race: run it several times (-count=10) and compare. Chapter 28 makes speed work its main topic.

    Under the hood: what go test really builds and runs
    
      
      
      
        
        
      The Professor says: go test is a builder, a runner and a reporter in one command. Knowing which part speaks helps you read its output.
      
      
      
      
      A test binary
      
      
      For each package, go test compiles the package together with its _test.go files, plus a generated main function that knows every Test, Benchmark, Fuzz and Example function it found. That program is the test binary. go test runs it and relays what it prints; the exit status 1 line is the test binary's own exit, and the final ok or FAIL line is go test's summary. go test -c keeps the binary as parcel.test, and you can run it yourself with flags such as ./parcel.test -test.v.
      
      
      vet runs first
      
      
      Before running, go test runs a small, high-confidence subset of go vet checks (such as wrong Printf verbs). A problem there stops the run with [build failed], as chapter 15 showed. Compile errors do the same.
      
      
      How a subtest runs
      
      
      Each t.Run starts its function on a new goroutine and waits for it to finish. That is why t.Fatal only ends one subtest: it calls runtime.Goexit, which ends the current goroutine (running its deferred calls), and the parent carries on. It is also why t.Fatal must be called from the test's own goroutine, never from a goroutine the test started. A panic is different: it is caught just long enough to record the failure, then re-raised, and an unrecovered panic in any goroutine ends the whole program.
      
      
      Output streaming
      
      
      With -v, log lines appear as they happen, under the === RUN line of their test, and the --- PASS/FAIL verdicts are printed when each test completes, parents after their children have finished. Without -v, only failing tests show their logs.
      
      
      t.Parallel()
      
      
      A test or subtest that calls t.Parallel() pauses until its parent's function has returned, then runs at the same time as the other parallel tests. It can make big suites faster. It also means cleanups registered by the parent run after the parallel children finish. Since Go 1.22 every loop iteration has its own tc, so the old trick of writing tc := tc before t.Run is no longer needed.
      
      
      How b.Loop chooses N
      
      
      The ramp-up in panel 30 follows predictN in Go's testing package: aim for the goal time plus 20%, grow at most 100× per round, always at least one more lap than last time, and never more than a billion. The default goal is one second; change it with -benchtime=3s or a fixed count like -benchtime=100x. Add -benchmem to see memory use per lap (chapter 28).
      
      
      How fuzzing finds things
      
      
      The fuzzer is coverage-guided: it builds the package with extra counters (that's why the first -fuzz run takes a while to compile), mutates inputs, and keeps any input that reaches code no earlier input reached. Interesting inputs are cached in Go's build cache; failing ones are minimised and written to testdata/fuzz/FuzzXxx/. Fuzzing runs only one fuzz test at a time and only in one package.
      
      
      Inside a synctest bubble
      
      
      Time in a bubble advances only when every goroutine in it is durably blocked: sleeping, or waiting on a channel or lock that only another goroutine in the same bubble can release. Real input and output, such as network calls, never counts as durably blocked. synctest.Wait() waits until every other goroutine in the bubble is blocked, which is how tests of concurrent code avoid sleeping. synctest.Test also waits for all goroutines in the bubble to finish, and reports a deadlock if they can't.
      
    
      
  
      

  
      
    In real programs: how Go projects test
    
      
      
        
        
      • Table-driven tests everywhere. The Go standard library and most Go projects use the table-and-t.Run shape from panel 3. A common variation stores cases in a map[string]struct{...}, so the names are the keys; maps have no order (chapter 12), so the tubes then run in a random order, which can catch tests that secretly depend on each other.
        • 
        
      • Golden files with an -update flag. A test declares var update = flag.Bool("update", false, "rewrite golden files"); when you run go test -update, it writes the current output into testdata instead of comparing. Review the diff before committing.
        • 
        
      • Fakes, stubs and mocks. A stub returns fixed answers (panel 28). A fake is a small working version, like an in-memory database. A mock also records how it was called, so the test can check the calls. Go programmers usually write small hand-made stand-ins behind small interfaces rather than using a mocking library.
        • 
        
      • testing/fstest, iotest, httptest. The standard library ships stand-ins for file systems, readers that fail on purpose, and web servers and clients.
        • 
        
      • Continuous integration. Build servers run go vet ./... and go test -race ./... on every change; the exit code decides whether a change may be merged. Long fuzzing runs happen separately, for example in OSS-Fuzz for open-source projects.
        • 
        
      • -short and t.Skip. Slow tests check testing.Short() and skip themselves when you run go test -short, so the quick loop stays quick.
        • 
        
      • -failfast, -shuffle=on, -timeout. Stop after the first failure; run tests in a random order to find hidden dependencies; and kill the test binary if it runs longer than a limit (10 minutes by default), printing every goroutine's stack.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "t.Fatal stops all the tests." It stops the function it is called in: one test or one subtest (panel 11, Boss 1).
        • 
        
      • "t.Error stops the test." It marks the test failed and carries on. Use t.Fatal only when continuing makes no sense.
        • 
        
      • "A panic in a test is just a failed test." It crashes the whole test binary, and later tests in that package never run (panel 22).
        • 
        
      • "The file and line in a failure point at the bug." They point at the check that noticed. Without t.Helper they may even point inside your helper.
        • 
        
      • "100% coverage means no bugs." It means every statement ran at least once. Wrong want values, missing cases and wrong rules all survive 100% coverage.
        • 
        
      • "A short time.Sleep in a test is harmless." It's slow, and if it waits for something to happen, it's flaky. Use synctest, a stub clock, or wait on the event itself.
        • 
        
      • "(cached) means the test ran quickly." It means it didn't run.
        • 
        
      • "A benchmark number is the speed of my code." It's one measurement on one machine with one Go version. Repeat it, compare with benchstat, and make sure the loop body really does the work.
        • 
        
      • "Fuzzing is just random testing." It is guided by coverage, keeps interesting inputs, and turns every failure into a permanent regression test.
        • 
        
      • "Example functions are only for show." With an // Output: comment they are run and checked by go test.
        • 
        
      • "The test package can't see unexported names." A test file in package parcel can; one in package parcel_test can't. Both may live in the same folder.

CHAPTER 15

LIBRARIES AND ANSWER KEYS

Picture: Scoot, the bike courier in a red cap and green jacket, waves hello.

So far every program has lived in one file, in one room called package main. Real programs are bigger. This chapter turns your code into a library building: rooms called packages, a front door called go.mod, and one simple rule about which books may leave a room. Then a teacher shows up with an answer key: tests that check your code for you, every time you ask. About 120 minutes, with 24 hands-on checks.

  1. The library building: packages you already use
  2. Your own building: modules, go.mod and capital letters
  3. House rules: one package per folder, no circles
  4. Borrowing from other libraries, and reading the docs
  5. The answer key: your first test
  6. Tables, examples and traps
  7. Boss level and recap

Here's the picture to keep in your head for the whole chapter. A package is a room: one folder of Go files. A module is the whole building: a set of rooms with one name plate on the front door, the file go.mod.

  1. 1The building is a module: one project, with one name.
  2. 2The plaque on the door is go.mod. It holds the module's name, example/market.
  3. 3Each room is a package: one folder of .go files.
  4. 4Books with a capital letter on the spine may leave the room: they are exported.
  5. 5A small letter means "staff only": unexported. Only code in the same room can use it.

Scoot says: Catchphrase: capital on the spine? It may leave the room.

    14
    
    Why not just make everything exported? Think of a shop's front desk and its back office.
    
    
    
      
    FRONT DESK · EXPORTED
    • A promise to every customer: "this will keep working".
    • Keep it small and clear.
    • Give each exported name a comment starting with its name, like // Add puts....
    
      
    BACK OFFICE · UNEXPORTED
    • Free to rename, split or rewrite at any time: no other package can depend on it.
    • Protects the rules: nobody sets total to −100.
    • No comment required, though it helps.
    
    
    
    
    
      
      
    Scoot says: Start small: export only what another room really needs. Making a name exported later is easy. Taking it back breaks everyone who used it.

    a/a.go

    main.go

    Scoot says: Think of imports as stairs that only go down. main is at the top floor; every import leads one floor lower. No staircase leads back up.
    
    
    
  
    

  
    
    17
    
    The house rules of every Go building, in one list.
    
    
      
      
    • One folder, one package. Every .go file in a folder has the same package line (test files get a small exception you'll meet in the notebook).
      • 
      
    • Package name = folder name. A convention, kept almost everywhere. Short, lowercase, one word: shop, strings, not shopHelpers.
      • 
      
    • package main is the entrance. It holds func main, and it's the only package you can run. Other packages are libraries.
      • 
      
    • Import path = module path + folder. Same path from every file, no ./.
      • 
      
    • Capital = exported. For every name: function, type, field, method, variable, constant.
      • 
      
    • No circles. Imports go one way only.
      • 
      
    • Every import must be used. An unused import is a compile error, like an unused variable: "strings" imported and not used.
      •

    main.go
    
    
    
    
    
      
      
    1. no required module provides package rsc.io/quote; to add it: go get rsc.io/quote
      The first go run . fails: go.mod doesn't list any module that contains this package. Go even suggests a fix.
      2. 
      
    2. go mod tidy
      The tidy-up command. It reads every import in the module, finds the module for each missing one (found rsc.io/quote in rsc.io/quote v1.5.2), downloads it plus whatever it needs, and writes everything down. It also removes lines for modules nothing uses any more.
      3. 
      
    3. require rsc.io/quote v1.5.2
      go.mod now lists the dependency and its version. The second require block lists modules that rsc.io/quote needs, marked // indirect because your code doesn't import them itself.
      4. 
      
    4. cat go.sum
      A new file: one fingerprint line per download. More on this in panel 20.
      5. 
      
    5. The last go run . works and prints a Go proverb.
      6. 
    
    
    
    The go: downloading lines appear only the first time a module comes to your computer. After that, Go keeps a copy in its module cache and stays quiet. How this run was really made: in ~/go-ch15/quote, before the first command, go.mod was reset to its starting version (only the module and go lines), go.sum was deleted, the module cache was emptied, and Go was pointed at a local copy of the module proxy (GOPROXY=file://…, GOSUMDB=off), so the downloads print the same way on every capture; on your computer they come from proxy.golang.org. Every command shown then ran in one terminal, in that order. go get rsc.io/quote also works: it adds one dependency by name.
    
  
    

  
    
    20
    
    Two files, two jobs.
    
    
    
      
    
        
        go.mod · THE LIST
        
    Which building you are (module), which Go you need (go), and which other modules you borrow, at which version (require). You may read and even edit it; go mod tidy keeps it right.
    
      
    
      
    
        
        go.sum · THE FINGERPRINTS
        
    A cryptographic fingerprint (the h1: part) of every module version downloaded. Next time, on any computer, Go checks the download matches, so nobody can slip in a changed copy. Never edit it by hand.
    
      
    
    
    
    
    
      
      
    Scoot says: Catchphrase: go.mod says what you borrow. go.sum proves it's the same book. Keep both with your code in version control (chapter 21 shows git), so everyone builds exactly the same thing.

    One test, two checks, the minus bug again. The only difference: Errorf or Fatalf.
    
    
    
      
    t.Errorf: mark and keep going

    Under the hood: how Go builds packages, the module cache, and what go test really does
    
        
      
        Each package is compiled on its own
        
      
        Go compiles a package once, then saves a compact summary of it, its export data: the exported names with their types, plus whatever the Compiler needs to copy small functions into the packages that call them (inlining). When main imports shop, the Compiler reads that summary, not cart.go. That's why package builds are fast and cached, and why imports must form a one-way staircase: a package's summary must exist before anyone can read it.
        
      
        Why the lowercase message changes its wording
        
      
        In panel 12, Total is tiny and calls bagFee, so the Compiler can copy Total's body into callers, and bagFee ends up named in the summary. Finding it there, the Compiler can say name bagFee not exported by package shop. In Boss 6, plants.Grow isn't copied that way, water isn't in the summary, and the message is undefined: plants.water. We checked this: marking Total with //go:noinline turns panel 12's message into undefined: shop.bagFee. Same rule, different wording.
        
      
        Where downloaded modules go
        
      
        Downloads land in the module cache, by default $HOME/go/pkg/mod (see go env GOMODCACHE). Each version is stored once and shared by all your projects. Go makes those files read-only so nothing edits a dependency by accident. go clean -modcache empties it. By default, Go downloads through the module proxy proxy.golang.org and checks each download's fingerprint against the public checksum database sum.golang.org before writing it to go.sum. (go env GOPROXY GOSUMDB shows both.)
        
      
        Versions
        
      
        Module versions look like v1.5.2: major, minor and patch numbers (semantic versioning). Something like v0.0.0-20170915032832-14c0d48ead0c is a pseudo-version: a commit that never got a release tag, named by its date and commit id. When two dependencies need different versions of the same module, Go picks the lowest version that satisfies everyone (Minimal Version Selection), so builds don't change just because someone published something new. Chapter 21 covers versions, /v2 and more.
        
      
        What go test does, step by step
        
      
          
        
        1. Collects the package's files plus its _test.go files.
          2. 
        
        2. Runs a short list of go vet checks (atomic, bools, buildtag, directive, errorsas, ifaceassert, nilfunc, printf, stdversion, stringintconv and tests). Any problem: [build failed], nothing runs.
          3. 
        
        3. Generates a hidden main that calls every TestXxx and ExampleXxx, builds a test binary, and runs it.
          4. 
        
        4. Prints the results. Everything goes to standard output, even what a test printed to standard error.
          5. 
      
        
      
        Run with no package arguments (local directory mode), results are never cached. With arguments such as ./... (package list mode), passing results are cached and shown as (cached) until something changes. -count=1 forces a fresh run.
        
      
        t.Fatal stops only one test
        
      
        t.Fatal calls t.FailNow, which ends the goroutine running that test (the test function returns early). Other tests, and other subtests of the same parent, still run. Deferred calls in the test still run too, so chapter 14's defer f.Close() still happens.
        
      
        Examples: the fine print
        
      
        The comparison ignores spaces at the start and end of the output. // Unordered output: accepts the lines in any order (handy for map loops). An example named Example documents the package; ExampleCart_Total documents the method Total of type Cart.
        
      
        Test files may use a second package name
        
      
        The one exception to "one folder, one package": a _test.go file may say package calc_test. It then sits outside the room and sees only exported names, exactly like a real user. That's called black-box testing; this chapter's tests use package calc (white-box) and can see everything.
        
    
        
  
        

  
        
    In real programs: how packages and tests are organised
    
        
      
          
        
        • Module path = repository URL. Shared modules use paths like github.com/name/project, so go get knows where to fetch them. For code that stays on your computer, example/... or any name works.
          • 
        
        • Small, focused packages. Names like http, json, bufio: short nouns that say what's inside. Avoid grab-bags called util or common; their names say nothing.
          • 
        
        • Constructors. Packages with hidden fields usually export NewCart(owner string) *Cart, so users can only build a cart that starts out valid.
          • 
        
        • Tests next to code. Every package in the standard library has its tests beside it: strings/strings.go and strings/strings_test.go. You can read them at go env GOROOT/src.
          • 
        
        • Continuous integration. Teams run go vet ./... and go test ./... automatically on every change, so a red mark appears before the code is merged.
          • 
        
        • Doc comments everywhere. Every exported name gets a comment starting with its name. pkg.go.dev builds its pages straight from them.
          • 
        
        • Few dependencies. Go programmers check the standard library first. Every dependency is code you trust and must keep up to date; go mod tidy keeps the list honest.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "A package is a file." A package is a folder; it can have many files, which all see each other's names without importing.
          • 
        
        • "Capital letters are just style, like in other languages." In Go they decide visibility. It's the only visibility rule there is: no public or private keywords.
          • 
        
        • "Lowercase means private to the file." It means private to the package. Every file in the same folder can use it.
          • 
        
        • "The import path is the package name." The path is the address ("example/market/shop"); the name is what you type before the dot (shop). Usually the name is the last part of the path, but the package line decides.
          • 
        
        • "go.mod lists my packages." It lists the module itself and the other modules you depend on. Your own packages are just folders.
          • 
        
        • "go.sum is a lock file I can delete." It's the fingerprint record. Keep it in version control.
          • 
        
        • "go run downloads missing modules automatically." Not since Go 1.16: you get no required module provides package until you go get or go mod tidy.
          • 
        
        • "A passing test means the code is correct." It means the code is correct for those cases. Panel 26's return 5 passed.
          • 
        
        • "t.Fatal stops all the tests." Only the current test (or subtest).
          • 
        
        • "Printing in a test is how you check things." Printing shows information; only t.Error, t.Fatal and friends mark failures. (In Examples, printing is the check, because // Output: compares it.)
          • 
        
        • "Test files end up in my program." go build and go run ignore every _test.go file.

    Words from this chapter
    
        
      
        
        
        package
        A folder of Go files compiled together, all starting with the same package line. A room in the library.
        
        
        module
        A set of packages with one go.mod at the top. The library building.
        
        
        module path
        The module's name from go.mod's module line, e.g. example/market. The start of every import path in the module.
        
        
        import path
        A package's address: module path plus folder, e.g. "example/market/shop". Standard library paths are short, like "strings".
        
        
        package name
        The word in the package line, typed before the dot: shop.Welcome.
        
        
        exported / unexported
        A name starting with a capital letter can be used from other packages (exported). A small letter keeps it inside its package (unexported).
        
        
        standard library
        The packages that come with Go: fmt, strings, os, testing and hundreds more.
        
        
        go.mod
        The module's file: module line, go line, and require lines for dependencies.
        
        
        go line
        The minimum Go version a module needs, e.g. go 1.27.3.
        
        
        dependency
        Another module your code uses.
        
        
        indirect dependency
        A module needed by your dependencies but not imported by your code; marked // indirect.
        
        
        go.sum
        Fingerprints (checksums) of every module version downloaded, used to check that downloads never change.
        
        
        go mod tidy
        Adds missing requirements for your imports and removes unused ones, updating go.mod and go.sum.
        
        
        module cache
        The folder where downloaded modules are kept, shared by all your projects.
        
        
        module proxy
        A server that hands out module downloads; by default proxy.golang.org.
        
        
        import cycle
        Packages that import each other in a circle. Not allowed.
        
        
        go doc / pkg.go.dev
        Documentation from doc comments, in the terminal or the browser.
        
        
        signature
        A function's name, inputs with types, and result types: func Repeat(s string, count int) string.
        
        
        test
        A function func TestXxx(t *testing.T) in a _test.go file that checks code against an answer key.
        
        
        got / want
        What the code gave, and what the answer key says it should give.
        
        
        t.Errorf / t.Fatalf
        Mark a test failed with a message; Errorf carries on, Fatalf stops the current test.
        
        
        table-driven test
        A test with a slice of cases and one loop that checks them all.
        
        
        subtest
        A named test inside a test, started with t.Run(name, func(t *testing.T) {…}).
        
        
        example function
        func ExampleXxx() whose printed output is checked against an // Output: comment, and shown in the docs.
        
        
        edge case
        An input at the edge of what's normal: zero, negative, empty, the biggest value. Bugs gather there.
        
        
        Arrange, Act, Assert
        The three parts of a clear test: set up, do the thing, check the result.
        
        
        local directory mode / package list mode
        go test with no package arguments (never cached) versus with arguments like ./... (passing results cached).
        
        
        ./...
        A pattern meaning this folder's package and every package below it.

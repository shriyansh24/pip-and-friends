PART 1 · TWO HANDS, ONE BOARDWhat a data race is, and the detector that catches it

1

Scoot's depot has a tally board on the wall. Every time a helper sorts a parcel, they add 1 to it. Ten helpers, a hundred parcels each. The board should say 1000.

Scoot says: The board says way less than 1000?! Everyone worked hard. Nobody skipped a parcel. Where did the missing parcels go?

Picture: four numbered kitchen helpers stir their pots busily. Scoot stares at the tally board and shrugs, worried.

2

Here's the depot as a program. Each helper is a goroutine (chapter 24), and all ten change the same variable, count. To make the trouble easy to see, each helper reads the board, pauses for a moment with runtime.Gosched() ("let another goroutine run now"), then writes the new number.

race_count.go 

    
One possible run. This program is marked as varying from run to run, and it is never used as an answer.

    

    
    
      
  1. Far fewer than 1000, every try
    The pause lets several helpers read the same number before any of them writes. When all ten read the same number, ten adds become one add: that's how a try can end at 100.
    2. 
      
  2. Different numbers on different tries
    Run it yourself and you'll see other numbers, changing from try to try. That's what makes this bug so nasty: it depends on timing.
    3. 
      
  3. Without the pause?
    With a plain count++ the mistake is rarer, because each step is quicker. Rarer is worse: a program can pass every test and still lose parcels on a busy day. Panel 5 shows the tool that finds it anyway.
    4. 
    

  


  

    3
    
The secret: count++ looks like one step, but the computer does it as three moves.

    

      
1 · READn := countLook at the board and remember the number.

      
2 · ADDn = n + 1Work out the new number on your own note.

      
3 · WRITEcount = nRub out the board and write your number.

    

    

    

      
      
Scoot says: B read the board after A read it but before A wrote. So B's 8 rubbed out A's 8. This is called a lost update.

    

  


  

  

  

    4
    
This kind of bug has a name: a data race. A program has one when all three of these are true:

    
    
      
  • Two or more goroutines use the same variable,
    • 
      
  • at least one of them writes to it (only reading is fine),
    • 
      
  • and nothing makes them take turns: no lock, no channel handoff, no wg.Wait() in between.
    • 
    

    

      
      
Scoot says: Catchphrase: two hands, one board, no turns: trouble. The Go memory model warns that a racy program can see stale or half-written values, and that races on bigger values like strings and slices can even corrupt memory. Wrong numbers are the friendly outcome.

    

    
Taking turns is called synchronisation. Chapter 24 already had some: a channel handoff makes the sender and the receiver meet, and wg.Wait() makes main wait until the helpers are done. That's why reading count on line 23 of panel 2, after wg.Wait(), is not part of the race. This chapter adds a few more ways to take turns.

  


  

  

  

    5
    
Timing bugs hide. So Go ships a detective: the race detector. Add -race to go run, go build or go test, and Go builds a version of your program that watches every memory access while it runs. Here it is on a tiny program with a plain count++.

    race.go
    

    
The race detector needs cgo (Go's bridge to C), and on Linux and Windows a C compiler too (on macOS it doesn't, the Go docs say). This book's machine switches cgo off, so the command turns it on with CGO_ENABLED=1. On most computers it's on already, and plain go run -race race.go works (the notebook's lab explains). One possible run:

    

    
    
      
  1. WARNING: DATA RACE
    The headline. Everything between the two lines of = signs is one report.
    2. 
      
  2. Read at 0x… by goroutine 9: … race.go:13
    Who touched the variable, and where: goroutine 9 read it on line 13, the count++. The hex number is the variable's address in memory; it changes from run to run.
    3. 
      
  3. Previous write at 0x… by goroutine 8: … race.go:13
    Same address, so the same variable. Goroutine 8 wrote it on the same line, and nothing made the two take turns.
    4. 
      
  4. Goroutine 9 (running) created at: sync.(*WaitGroup).Go()
    Where each goroutine was born: the two wg.Go calls.
    5. 
      
  5. count = 2
    The answer came out right this time! The detector doesn't need the numbers to go wrong. It sees that the two accesses could collide.
    6. 
      
  6. Found 1 data race(s), exit status 66
    A program built with -race exits with status 66 when it found a race, so scripts and tests notice. The last line is go run's own exit code, 1, as with every failed run.
    7. 
    

    

      
      
Scoot says: Two things to remember. It only finds races that actually happen while it watches, so run your tests with -race. And it's slow: the Go docs say memory can grow 5 to 10 times and run time 2 to 20 times. Use it in testing, not in the shipped program.

    

  


  

  

  
  
PART 2 · ONE KEY ON A HOOKsync.Mutex, defer Unlock, and the mistakes it invites


  

    6
    
Down the corridor sits Ida, the Key Keeper. The board room has one door, and next to it, one key on one hook.

    

      
Ida says: The rule is simple. Want to change the board? Take the key. Key not on the hook? Wait in line. Done? Hang it back. Only the one holding the key may go in.

      
    

    

      
      
Scoot says: So read, add and write all happen with the key in your hand. Nobody can sneak in between them!

    

    
In Go the key is a sync.Mutex, short for mutual exclusion: "only one at a time". mu.Lock() takes the key, waiting if someone else has it. mu.Unlock() hangs it back. Its zero value is ready to use: var mu sync.Mutex is an unlocked key on its hook.

    
Picture: Ida, the Key Keeper, in teal overalls with round glasses and a grey bun, holds up a big gold key. Scoot points, amazed.

  


  

    7
    
The program from panel 2, with one change: the read-pause-write now happens inside add, which holds the key the whole time. Same pause, same ten helpers.

    mutex_count.go
    

    

    
    
      
  1. mu.Lock() (line 15)
    Take the key. If another helper has it, this line simply waits until it's back on the hook.
    2. 
      
  2. defer mu.Unlock() (line 16)
    Hang it back when add returns, whichever way it returns (defer, chapter 14). Writing it on the very next line means you can't forget.
    3. 
      
  3. runtime.Gosched() (line 18)
    Other helpers may run now, but they all stop at mu.Lock(). Nobody can read the board in the middle of someone else's add.
    4. 
      
  4. count = 1000, five times
    Exact, every try, on every computer. The lock is the turn-taking that panel 4 asked for. This program is deterministic, so it can be an answer.
    5. 
    

    

      
      
Ida says: Catchphrase: take the key, then defer hanging it back. mu.Lock() and defer mu.Unlock(), one line after the other, every time.

In real programs the key lives inside a struct, next to the data it guards, and the struct's methods take it. Callers can't forget to lock, because they never see the lock at all.

    safe_counter.go
    

    

    
    
      
  1. mu sync.Mutex right above counts (lines 10 and 11)
    A common Go habit: the mutex sits just above the fields it protects, so readers know what it guards.
    2. 
      
  2. func (t *Tally) Add (line 14)
    A pointer receiver (chapter 13). Every caller uses the one real Tally and its one real key. Panel 12 shows what goes wrong without the *.
    3. 
      
  3. Get locks too (lines 21 and 22)
    Reading needs the key as well, if a writer could be busy at the same moment.
    4. 
      
  4. Oslo: 100 Rome: 200
    300 goroutines; every third one is Oslo. Maps are not safe for writes from several goroutines (panel 15), but with the key, they take turns.

    10
    
    
Mistake one: hanging back a key that's already on the hook.

    unlock_twice.go
    

    
One possible run (the hex numbers in brackets change every time):

    

    
    
      
  1. fatal error: sync: unlock of unlocked mutex
    The last good line was key back on the hook, then line 14 tried to Unlock again.
    2. 
      
  2. fatal error, not panic
    A panic can be caught with recover (chapter 19). A fatal error can't: the whole program stops.
    3.

    Skip the internal/sync lines: they're inside Go's own code. Your line is the first one in main.
    4.

    11
    
    
Mistake two, much more common: taking the key and never hanging it back.

    forgot_unlock.go
    

    
One possible run:

    

    
    
      
  1. first add done: 1
    The first call took the key and kept it.
    2. 
      
  2. fatal error: all goroutines are asleep - deadlock!
    The second call waits for the key forever, and nobody else is left to hang it back. You met this message in chapter 24, waiting on a channel.
    3. 
      
  3. goroutine 1 [sync.Mutex.Lock]:
    The word in brackets says what it was waiting for: a mutex, this time, not [chan send].
    4. 
      
  4. main.add(...) forgot_unlock.go:12, called from line 20
    The Lock that never returned, and the call that led there.
    5. 
    

    

      
      
Scoot says: Here Go noticed because every goroutine was stuck. In a big program with other goroutines still busy, there's no message: the waiting helpers just hang there. defer mu.Unlock() also hangs the key back when a function returns early or panics.

    Ida has a second kind of key for boards that are read often and changed rarely, like a price list: sync.RWMutex. Many readers may look at the same time, each with a reading pass. A writer needs the one writing key, and gets it only when nobody is reading.
    
    
    
      
    
        READING PASS
        mu.RLock()
defer mu.RUnlock()
        
    Many at oncefor code that only reads
    
        
    Readers don't block each other. They only wait while a writer is inside.
    
      
    
      
    
        WRITING KEY
        mu.Lock()
defer mu.Unlock()
        
    One, alonefor code that changes the data
    
        
    The writer waits for every reader to leave, and nobody enters while it writes.
    
      
    
    
    
    rwmutex.go
    
    
    
    
    
    
      
      
    Ida says: Start with a plain Mutex. Switch to RWMutex only when reads vastly outnumber writes and measuring shows the lock is a bottleneck. It does more bookkeeping, so for short reads it can even be slower.
    
    
    
  
    

  
    
  

  
    
    15
    
    
    Maps (chapter 12) get special treatment. Go's map does some checking of its own, and when it catches two goroutines writing at once, it stops the whole program.
    
    map_writes.go
    
    
    
    One possible run:
    
    
    
    
      
      
    1. fatal error: concurrent map writes
      Another fatal error: no recover, no second chance.
      2. 
      
    2. main.main.func1() … map_writes.go:14
      func1 is the first function literal inside main: the goroutine's body. Line 14 is the map write.
      3. 
      
    3. Not guaranteed
      The check is a cheap spot check, not a detector. On another run, or another computer, the program may finish and print a wrong count, or crash. Never rely on it; use -race in tests.
      4.

    Scoot says: Many goroutines may read a map at once, as long as nobody writes. The standard library also has sync.Map, for a few special cases; a plain map with a mutex is the usual choice.
    
    
    
  
    

  
  
    PART 3 · ONCE, ATOMICS, AND CHOOSINGsync.Once, sync/atomic, and channel or mutex
    

  
    
    16
    
    Some jobs must happen exactly once, however many helpers ask: loading the route map, opening a connection, reading settings. sync.Once is a "done" stamp on the job. once.Do(f) runs f the first time; every later call does nothing, and waits if the first call is still running.
    
    once.go
    
    
    
    
    
      
      
    1. loading the route map... printed once (line 14)
      Five goroutines called loadOnce.Do(loadRoutes). Only one ran it. Which one won varies, but it never runs twice.
      2. 
      
    2. routes: [Oslo Rome Lima]
      Every caller of Do returns only after the job is finished, so anyone who called it can safely use routes.
      3. 
    
    
    
    
      
      
    Ida says: Since Go 1.21 there are handy cousins: sync.OnceValue(f) gives you a function that runs f once and hands back its result on every call, and sync.OnceFunc(f) wraps a plain function the same way.
    
    
    
  
    

  
    
  

  
    
    17
    
    For a single number, there's an even smaller tool. A turnstile clicker adds 1 in one click: there's no moment in the middle when someone else could sneak in. The sync/atomic package gives you number types whose operations work like that click. Atomic means "can't be split".
    
    atomic_count.go
    
    
    
    
    
      
      
    1. var count atomic.Int64 (line 10)
      A typed atomic. Its zero value is 0, ready to use.
      2. 
      
    2. count.Add(1) (line 14)
      Read, add and write as one unsplittable step, done by the processor itself. No key, no waiting in line.
      3. 
      
    3. count.Load() (line 18)
      Read it with Load. Every use goes through a method: that's how Go stops you from touching it the unsafe way (panel 19).
      4. 
    
    
  
    

  
    
    18
    
    The typed atomics are atomic.Int32, Int64, Uint32, Uint64, Uintptr, Bool, Pointer[T] and Value. Here are the moves they share.
    
    atomic_more.go
    
    
    
    
    
      
      
    1. Store and Load (lines 12 and 15)
      Write and read. Add(-2) subtracts: true 3.
      2. 
      
    2. old := parcels.Swap(10) (line 17)
      Put in a new value and get the old one back, in one step: swap: 3 10.
      3. 
      
    3. CompareAndSwap(10, 11) (line 20)
      "If it's still 10, make it 11." It was 10, so it worked: true 11. On line 22 it's no longer 10, so nothing changes: false 11. This "CAS" move is what other lock-free tools are built from.
      4. 
    
    
    
    
      
      
    Scoot says: Atomics are for one number or flag on its own. If two values must change together (a balance and a history list), each atomic step is safe but someone could look in between them. That's a job for the key.
    
    
    
  
    

  
    
  

  
    
    19
    
    
    What if you forget, and write count++ out of habit?
    
    atomic_err.go
    
    
    
    
    
    
      
      
    The Compiler says: Line 10, column 2: count++ needs a number, and "sync/atomic".Int64 is a struct, a "non-numeric type". Use count.Add(1). Nothing runs until everything checks out.
    
    
    
    
    That's the point of the typed atomics, added in Go 1.19. The older style, atomic.AddInt64(&n, 1) on a plain int64, still works, but nothing stops another line from writing n++ by mistake. With atomic.Int64, the Compiler does.

    PART 4 · THE FACTORY FLOORGenerators, pipelines, and who closes the belt
    

  
    
    21
    
    Business is booming, and Scoot's depot becomes a little factory. Each station does one job and passes its work along a conveyor belt to the next.
    
    
    
    
    
      
      
    Scoot says: In Go, a station is a goroutine and a belt is a channel. A row of stations is called a pipeline. Each station only ever touches the item in its own hands, so there's no shared board and no key needed!
    
    
    
  
    

  
    
    22
    
    The first station is a generator: a function that hands back a channel and fills it from its own goroutine.
    
    gen.go
    
    
    
    
    
      
      
    1. func count(n int) <-chan int (line 7)
      It returns a receive-only channel (chapter 24): callers can take items off this belt but can't put anything on it.
      2. 
      
    2. defer close(out) (line 10)
      When the goroutine runs out of numbers, it closes the belt. "That's all, folks."
      3. 
      
    3. for v := range count(4) (line 19)
      main takes items until the belt is closed, then the loop ends and belt empty prints.
      4. 
    
    
    
    
      
      
    Scoot says: Catchphrase: whoever loads the belt closes the belt. The sender closes, never the receiver: only the sender knows when there's nothing more coming.
    
    
    
  
    

  
    
  

  
    
    23
    
    Now join three stations. Each takes the belt from the one before and hands back its own.
    
    pipeline.go
    
    
    
    
    
      
      
    1. box(square(source(2, 3, 4))) (line 42)
      Read it from the inside out: source makes a belt, square takes it and makes the next, box takes that one. Each call starts its goroutine and returns at once.
      2. 
      
    2. for n := range in (lines 22 and 34)
      Every station works the same way: take items until the belt before it closes, then close its own. Closing ripples down the line.
      3. 
      
    3. In the same order as they went in
      One goroutine per station, so items can't overtake each other. This program prints the same three lines every time.
      4.

    PART 5 · MORE HANDSWorker pools, fan-out and fan-in, limits, errgroup and tickers
    

  
    
    25
    
    One station is slow: the squaring takes ages. Ida's advice: don't build a new line, put more workers at that station. They all take jobs from the same belt.
    
    
    
      
      
      
    
    
    
    
      
      
    Scoot says: Many workers taking from one belt is called fan-out. A fixed team of them, waiting for jobs, is a worker pool. And joining several belts into one is fan-in.
    
    
    
    
    Picture: three kitchen helpers with aprons W1, W2 and W3 all stir pots side by side.
    
  
    

  
    
    26
    
    A worker pool needs three goroutines' worth of thinking: who hands out jobs, who does them, and who announces that the results are all in.
    
    workers.go
    
    
    
    
    
      
      
    1. worker(jobs <-chan int, results chan<- int) (line 9)
      Directional channel types: a worker may only take jobs and only send results. The Compiler holds it to that.
      2. 
      
    2. close(jobs) (line 28)
      The dispatcher loaded the jobs belt, so the dispatcher closes it. Each worker's range jobs then ends.
      3. 
      
    3. wg.Wait(); close(results) (lines 32 and 33)
      Three workers send results, so no single one of them may close it. A separate goroutine waits for all three, then closes. That ends main's range results.
      4. 
      
    4. slices.Sort(got) (line 40)
      Which worker finishes first changes from run to run, so results arrive in any order. Sorting makes the output the same every time: [1 4 9 16 25 36].
      5. 
    
    
  
    

  
    
  

  
    
  

  
    
    27
    
    The pool as a machine: town names go in on the jobs belt, three workers shout each one, and the results come out. Every result is a real line printed by pool_m.go; the last chip jams it with pool_err.go.
    
    
    
    
    pool_m.go
    
    
  
    

  
    
    28
    
    Fan-in goes the other way: several belts feed one. merge starts one little forwarder per belt, and a closer that waits for all of them, the same trick as the pool's results.
    
    fanin.go
    
    
    
    
    
      
      
    1. merge(belts ...<-chan string) (line 21)
      The ... makes it variadic: it takes any number of belts.
      2. 
      
    2. One forwarder per belt (lines 24 to 30)
      Each copies its belt onto out. Three forwarders send on one belt, so none of them may close it.
      3. 
      
    3. The closer (lines 31 to 34)
      Waits until every forwarder has finished, then closes out. Then main's loop ends.
      4. 
      
    4. 7 items: [a1 a2 a3 b1 b2 c1 c2]
      Items from the three belts arrive mixed in any order; sorted, they're the same every time.
      5. 
    
    
  
    

  
    
    29
    
    Sometimes you have plenty of work but must not do it all at once: a website may block you if you download 1000 pages in the same second. The depot has six trucks and only two loading bays. A buffered channel with two slots makes a perfect bay counter. This is called a semaphore.
    
    semaphore.go
    
    
    
    
    
      
      
    1. sem := make(chan struct{}, 2) (line 10)
      Two slots. struct{} is an empty struct: it holds nothing and takes no room. We only care how many tokens are in.
      2. 
      
    2. sem <- struct{}{} (line 17)
      Put a token in to take a bay. If both slots are full, the send waits: that truck queues.
      3. 
      
    3. defer func() { <-sem }() (line 18)
      Take the token back out when done, freeing the bay for the next truck.
      4. 
      
    4. never more than 2 at once: true
      The program counts trucks in bays with a mutex and keeps the biggest number it saw. It prints a true-or-false check, not the number, because how many were in at the same moment depends on timing.
      5. 
    
    
  
    

  
    
  

  
    
    30
    
    A WaitGroup waits, but it can't tell you if something went wrong. The errgroup package can. It isn't in the standard library: it lives in golang.org/x/sync, maintained by the Go team. Add it to a module with go get golang.org/x/sync@v0.24.0 (chapter 21). This program is its own module, in the folder errg:
    
    errg/go.mod

    Under the hood: happens-before, how a mutex waits, how -race watches, and how leaks are found
    
    
      
    The memory model in one paragraph
    
      
    The Go memory model (go.dev/ref/mem) defines when one goroutine is guaranteed to see another's write. The key idea is happens before: an Unlock happens before the next Lock of the same mutex returns; a send on a channel happens before the matching receive completes; closing a channel happens before a receive that sees it closed; wg.Done happens before the wg.Wait it releases; the function in once.Do finishes before any Do returns. If a write and a read of the same variable are not ordered by a chain of these, they race. The memory model also says what a racy program may still do: on a single machine word, a read sees some value that was actually written, but races on bigger values such as strings, slices and interfaces can produce mixed-up values and even memory corruption. Its advice for programs: don't be clever; synchronise.
    
      
    Why count++ isn't safe even on one line
    
      
    The processor executes count++ as a load, an add and a store, and modern processors and compilers also reorder and cache memory operations as long as a single goroutine can't tell. Synchronisation operations (mutexes, channels, atomics) are where those reorderings are forbidden from crossing. That's why "it's only one line" is never an argument, and why runtime.Gosched() in panel 2 only made a real problem easier to see.
    
      
    How sync.Mutex waits
    
      
    A sync.Mutex is two small integers. Lock first tries a single atomic compare-and-swap; if the key is free, that's all. Otherwise it may spin briefly, then parks the goroutine on a queue inside the runtime, so a waiting goroutine uses no processor time. The mutex has two modes: in normal mode a woken waiter competes with newly arriving goroutines (which often win, because they're already running); if a waiter has waited more than 1 ms, the mutex switches to starvation mode and hands the key directly to the waiter at the front of the queue. That's why panel 8 says Go doesn't promise an order. A Mutex is not tied to a goroutine: one goroutine may Lock and another Unlock, but code that does so is hard to follow. Go mutexes are not re-entrant: a goroutine that calls Lock twice without Unlock waits for itself forever.
    
      
    How the race detector watches
    
      
    -race builds your program with ThreadSanitizer, a C/C++ library from the LLVM project, which is why it needs cgo. Every memory access is instrumented, and the runtime keeps "shadow" information about recent accesses to each 8-byte word, plus vector clocks that track what happened before what. When two accesses to the same word aren't ordered and at least one is a write, it prints the report you saw. It doesn't guess: every report is a pair of accesses that really happened in that run without an order between them. The GORACE environment variable tunes it, for example GORACE="halt_on_error=1" to stop at the first report, or exitcode=… to change the 66.
    
      
    How atomics work
    
      
    Typed atomics compile to single processor instructions such as x86's LOCK XADD and LOCK CMPXCHG, which the hardware guarantees can't be interrupted or interleaved with other cores' writes to the same location. In the Go memory model, atomic operations behave like sequentially consistent operations: they also order the ordinary reads and writes around them. atomic.Int64 is also guaranteed to be 8-byte aligned, which the older atomic.AddInt64(&x, 1) on a plain int64 field is not on 32-bit platforms.
    
      
    Why maps crash instead of racing quietly
    
      
    Go's map keeps a "writing" flag in its header. A write sets it, and any access that finds it set from somewhere else calls fatal("concurrent map writes"). It's a cheap spot check that catches some, not all, overlapping writes, which is why panel 15 couldn't promise the crash. It is a fatal error rather than a panic so that nobody can recover and carry on with a map whose insides may already be broken.
    
      
    How the goroutineleak profile finds leaks
    
      
    A goroutine blocked on a channel, mutex or WaitGroup that no running goroutine can reach any more can never wake up. When the profile is requested, the runtime runs a special garbage collection that treats blocked goroutines as unreachable unless something live points at what they're waiting on; those left over are reported as leaked. It finds goroutines stuck on objects nothing else can reach; a goroutine blocked on a channel that a global variable still refers to is not reported, even if nobody will ever use it.
    
    
    
  
    

  
    
    In real programs: where keys and belts show up
    
    
      
      
        
    • Caches. An in-memory cache in a web server is usually a map with a sync.RWMutex, or a sync.Map when keys are written once and read many times.
      • 
        
    • Metrics. Request counters and "currently open connections" gauges are atomics. Monitoring libraries are built on atomic.Int64-style counters.
      • 
        
    • Lazy setup. Database connections, compiled regular expressions and parsed templates are often created with sync.Once or sync.OnceValue the first time they're needed.
      • 
        
    • Crawlers and downloaders. A semaphore channel or errgroup.SetLimit caps how many pages are fetched at once, and a ticker (or golang.org/x/time/rate) caps how many per second.
      • 
        
    • Batch processing. Image resizing, log parsing and data imports use worker pools sized to the number of processors (runtime.GOMAXPROCS(0)).
      • 
        
    • Servers. Go's HTTP server runs each request in its own goroutine (chapter 26), so any shared state in a handler needs a key, and any goroutine a handler starts needs a way home.
      • 
        
    • CI. Many teams run go test -race ./... on every change, because races found in testing are cheap and races found in production are not.
      • 
      
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "count++ is one step." It's read, add, write.
      • 
        
    • "My program gave the right answer, so it has no race." Panel 5's race gave count = 2. Run -race.
      • 
        
    • "Races only matter on computers with many cores." The memory model doesn't care how many cores you have, and the compiler may reorder code anyway.
      • 
        
    • "Only writers need the lock." Readers need it too whenever a writer could be active at the same time.
      • 
        
    • "A mutex protects a variable." It protects nothing by itself. It only works if every access to the data takes the same key.
      • 
        
    • "Copying a struct copies its lock safely." You get a second, unrelated key. Use pointers; go vet checks.
      • 
        
    • "I can lock again inside a method that already holds the lock." Go mutexes aren't re-entrant: that's a deadlock.
      • 
        
    • "concurrent map writes will always catch my bug." It's a spot check. Use a mutex and -race.
      • 
        
    • "Atomics make a whole struct safe." Each atomic operation is safe on its own; several of them together aren't one step.
      • 
        
    • "The receiver should close the channel." The sender closes. With many senders, a closer goroutine waits for them all.
      • 
        
    • "Goroutines are cheap, so leaking a few is fine." A leak per request adds up until the server runs out of memory.
      • 
        
    • "The garbage collector stops stuck goroutines." It never stops a goroutine. A blocked one stays blocked.
      • 
        
    • "More workers is always faster." Past the number of cores, or the limit of the disk, network or remote server, more workers just wait in line.

    Words from this chapter
    
    
      
    
        
    data race
    Two or more goroutines access the same variable, at least one writes, and nothing orders the accesses.
    
        
    lost update
    One goroutine's write rubs out another's because both read the old value first.
    
        
    synchronisation
    Anything that makes goroutines take turns or wait for each other: mutexes, channels, WaitGroups, atomics, Once.
    
        
    race detector
    The -race build flag: watches memory accesses at run time and reports races. Needs cgo.
    
        
    cgo
    Go's way of calling C code; turned on with CGO_ENABLED=1 and needs a C compiler.
    
        
    mutex, sync.Mutex
    Mutual exclusion: a lock only one goroutine can hold. Lock waits for it; Unlock releases it.
    
        
    sync.RWMutex
    A lock with many-at-once reading passes (RLock/RUnlock) and one writing key (Lock/Unlock).
    
        
    critical section
    The code between Lock and Unlock, which only one goroutine runs at a time.
    
        
    deadlock
    Goroutines waiting for each other (or for a key) so that none can ever continue.
    
        
    fatal error
    A runtime failure that, unlike a panic, can't be recovered: the program stops.
    
        
    sync.Once
    Runs a function exactly once, however many goroutines call Do.
    
        
    atomic
    An operation that can't be split or interrupted. sync/atomic has Int64, Bool and friends.
    
        
    compare-and-swap (CAS)
    "If the value is still X, make it Y", done as one atomic step; reports whether it worked.
    
        
    generator
    A function that returns a channel and fills it from its own goroutine.
    
        
    pipeline, stage
    A chain of goroutines (stages, or stations) joined by channels, each doing one job.
    
        
    worker pool
    A fixed number of goroutines taking jobs from one channel.
    
        
    fan-out, fan-in
    Several goroutines reading one channel; several channels merged into one.
    
        
    semaphore
    A counter of free slots that limits how many things run at once; in Go, often a buffered channel.
    
        
    errgroup
    golang.org/x/sync/errgroup: run goroutines, wait for all, get the first error, optionally limit how many run.
    
        
    rate limiting
    Allowing at most a certain number of actions per unit of time.
    
        
    goroutine leak
    A goroutine that never finishes, usually stuck on a channel nobody will use again.
    
        
    done channel
    A channel closed to tell goroutines to stop.
    
        
    goroutineleak profile
    Go 1.27's runtime/pprof profile listing leaked goroutines and where they're stuck.
    
        
    happens before
    The memory model's ordering between events in different goroutines; without it, accesses race.

Programs without wg.Go, such as gen.go, pipeline.go, atomic_more.go, done.go and the leak programs, gave identical output.
    
  
    The key-hook and conveyor-belt steppers, the tracer, the machine and the map are teaching models. Each checks itself against the real runs and shows a badge: the screens must match the captured output line by line, the key-hook board may only grow by one while a helper holds the key and must end at the printed total, and each line main prints in the belt stepper must arrive on the last belt. The order of turns in the key hook and the timing in the belt stepper are one possible order; Go doesn't promise either.

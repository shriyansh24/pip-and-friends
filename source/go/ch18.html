CHAPTER 18 · INTERMEDIATE

MEASURING CUPS AND SANDWICHES

Picture: Scoot, the bike courier in a red cap and green jacket, waves hello.

Last chapter, functions learned to carry backpacks. This chapter is about making your own types. First, measuring cups: a Celsius and a Fahrenheit are both just numbers inside, but Go keeps them in differently shaped cups so they can never be mixed by accident. Then numbered tickets (iota), nicknames (aliases), and finally sandwiches: building a big type out of smaller ones with embedding. About 120 minutes, with 24 hands-on checks.

  1. Measuring cups: named types and conversions
  2. The ticket machine: enums with iota
  3. A new cup or a nickname? Aliases and unexported types
  4. The sandwich: struct embedding
  5. Who answers the call? Shadowing, and why embedding is not inheritance
  6. What leaks out of the sandwich: embed or named field?
  7. Boss level and recap

PART 1 · MEASURING CUPSNamed types, the underlying type, conversions and methods

1

Scoot drops a recipe card at the corner bakery. An hour later, a smell of smoke. The card said 350. The oven dial counts in Celsius. The card meant Fahrenheit.

  • THE CARD350, meaning °F: a nice warm oven
  • THE DIAL350, read as °C: a furnace

Scoot says: Same number, different meaning. Both are just a float64, so nothing stopped the baker pouring one into the other.

Scoot says: If only the two numbers came in differently shaped cups that refuse to pour into each other...

Picture: two jelly creatures, the float creature, both labelled 350; the second one looks shocked. Scoot shrugs, worried.

2

Go lets you make exactly those cups. type Celsius float64 makes a brand-new type called Celsius. Inside, it holds a float64, but Go treats it as a different type from float64 and from any other cup.

  1. 1The cup's shape is the named type: Celsius or Fahrenheit.
  2. 2What the cup is made of is the underlying type: here float64 for both.
  3. 3Pouring straight across is refused by the Compiler: mismatched types.
  4. 4The funnel is a conversion. You write it on purpose, and you say how.

Scoot says: Catchphrase: same stuff, different cup. The numbers are the same kind of thing, but the cups won't mix unless you use the funnel.

    13
    
    Sometimes several choices can be on at the same time: a file can be readable and writable. For that, give each choice its own switch in a row of switches. In binary (counting with only 0 and 1), each switch is one digit, called a bit.
    
    
    
      
      
    • Read Perm = 1 << iota gives 1, 2, 4, 8...: each constant is a single switch.
      • 
      
    • a | b ("or") turns on every switch that's on in either: combining choices.
      • 
      
    • a & b ("and") keeps only switches on in both. mine&Write != 0 asks "is the Write switch on?"
      •

    PART 3 · A NEW CUP OR A NICKNAME?Type aliases, what a new type keeps and loses, and unexported types
    

  
    
    18
    
    One tiny character changes everything. Without = you make a new cup. With = you only stick a nickname label on a cup that already exists. That's a type alias.
    
    
    
      
    
        
    NEW TYPE
    
        
        
    A NEW CUPtype Celsius float64
    
        
      
          
    • A different type from float64. Mixing them needs a conversion.
      • 
          
    • You can give it methods.
      • 
          
    • It does not keep the methods of the type it's built from.
      • 
          
    • %T prints main.Celsius.
      • 
        
    
      
    
      
    
        
    ALIAS
    
        
        
    A NICKNAMEtype Temp = float64
    
        
      
          
    • Exactly the same type as float64, under a second name.
      • 
          
    • Mixes freely with float64: no conversion needed.
      • 
          
    • Has exactly the original's methods; you can't add methods to float64 through it (panel 21).
      • 
          
    • %T prints float64.
      • 
        
    
      
    
    
    
    
    
      
      
    Scoot says: Catchphrase: no equals, new cup. Equals, nickname.

    Under the hood: named types, constants, iota and embedding
    
      
      
      
        
        
      The Professor says: The cups cost nothing at run time. All of this chapter's checking happens in the Compiler.
      
      
      
      
      Named types are free
      
      
      A Celsius is stored exactly like a float64: eight bytes, no tag saying "Celsius". The type exists only while the Compiler checks the program. A conversion between two types with the same underlying type, such as Fahrenheit(c), produces no machine instructions at all: the bits stay as they are, and only the Compiler's idea of the type changes. That is why it can't do any maths. (Conversions between different underlying types, such as int to float64, do change the bits.)
      
      
      Assignability, in the spec's words
      
      
      The spec allows a value to be assigned to a variable of another type only in a few cases. The two that matter here: the types are identical (which is true for an alias and its original), or one of them is not a named type and both have the same underlying type. That second rule is why a plain []string literal can be assigned to a Shelf without a conversion, while a Celsius can never be assigned to a Fahrenheit: both are named. An untyped constant is assignable to any type that can represent its value, which is how plan(42) slipped through in panel 17.
      
      
      iota, exactly
      
      
      The spec defines iota as the index of the current constant specification (roughly: line) in a const block, starting at 0. It counts specs, not names: in const ( a, b = iota, iota*10; c, d ), a and b share ticket 0, c and d share ticket 1. A spec with no type and no expression repeats the previous spec's type and expressions, which is what makes bare names work. Everything is worked out at compile time, with arbitrary precision: a constant like 1 << 100 is allowed, as long as it fits wherever you finally use it.
      
      
      An embedded field is a real field
      
      
      Embedding doesn't copy methods into the outer type. The outer struct simply has a field whose name is the type's name (Engine), stored inline, and the Compiler rewrites v.Start() to v.Engine.Start(). The method set rules from chapter 14 then apply: if S embeds T, both S and *S get T's value-receiver methods, and *S also gets *T's pointer-receiver methods. If S embeds *T, both get all of them. So in panel 27, Turnstile (a value) does not fit an interface that needs Inc, because Inc has a pointer receiver, but &Turnstile{} does.
      
      
      Depth and ambiguity
      
      
      The spec gives every promoted name a depth: the number of embedded fields you pass through to reach it. A name at a shallower depth hides deeper ones. If the shallowest depth has two or more matches, the selector is illegal, but only when used, which is why panel 31's struct compiled until s.Name appeared. Effective Go points out why that rule is useful: an embedded type from another package can gain a new field later without breaking your code, unless you actually use the clashing name.
      
      
      Why a String method can recurse forever
      
      
      Inside func (c Celsius) String() string, writing fmt.Sprintf("%v", c) would ask fmt to print a Celsius, which calls String, which calls Sprintf... until the goroutine's stack runs out and the program dies with a stack-overflow fatal error. Converting first, float64(c), gives fmt a value with no String method. Using a number verb like %f or %d on c directly would also be safe, because number verbs don't call String (panel 16), but the conversion makes the intent obvious.
      
    
      
  
      

  
      
    In real programs: where named types, enums and embedding show up
    
      
      
        
        
      • time.Duration is type Duration int64, counting nanoseconds, with methods like Minutes() and a String() that prints 1m30s. time.Month and time.Weekday are iota enums with String methods (chapter 22).
        • 
        
      • os.FileMode and fs.FileMode are bit flags; 0644 from chapter 14 is three groups of read/write/execute switches written in octal.
        • 
        
      • http.HandlerFunc is a named function type with a method, so a plain function can satisfy the http.Handler interface (chapter 26).
        • 
        
      • sort.StringSlice is a named []string with methods, much like panel 7's Shelf.
        • 
        
      • Embedded interfaces: io.ReadWriter, io.ReadCloser and friends are built exactly like panel 28 (chapter 19).
        • 
        
      • Embedded structs: bufio.ReadWriter embeds a *bufio.Reader and a *bufio.Writer. Test helpers often embed an interface in a struct to "pretend" to implement it, overriding only the methods a test needs.
        • 
        
      • Generated String methods: the official stringer tool (golang.org/x/tools/cmd/stringer) writes the String method of an iota enum for you, usually run through go generate.
        • 
        
      • Aliases during big moves: type aliases were added in Go 1.9 mainly so a type could move from one package to another without breaking callers: the old name becomes an alias of the new one.

    Common wrong ideas
    
      
      
        
        
      • "type Celsius float64 just gives float64 another name." That's an alias, type Celsius = float64. Without = it's a separate type.
        • 
        
      • "A conversion between two temperature types converts the temperature." It only changes the type; the number stays the same.
        • 
        
      • "Methods only belong on structs." Any named type declared in your package can have methods: numbers, slices, maps, even functions.
        • 
        
      • "A new type built from another keeps its methods." It keeps the underlying type, not the methods. An alias keeps everything.
        • 
        
      • "Go enums can only hold the listed values." Any value of the underlying type can be converted in, and an untyped constant can be passed straight in.
        • 
        
      • "iota counts names." It counts lines (constant specs) in the block, including _ lines, and restarts at 0 in every block.
        • 
        
      • "Embedding is inheritance." The outer type isn't a subtype, can't be used as the inner type, and the inner type's methods never call the outer type's methods.
        • 
        
      • "An outer method with the same name overrides the inner one everywhere." It only shadows it for calls made on the outer type.
        • 
        
      • "Two embedded types with the same field name won't compile." They compile until you use the clashing name without saying which.
        • 
        
      • "Embedding is just a shortcut, so it's always harmless." Every exported method of the part becomes part of the whole's public face.

    Words from this chapter
    
      
      
      
        
      named type, defined type
      A type made with type Name Underlying. It is different from every other type, including its underlying type.
      
        
      underlying type
      The type a named type is built from: what the cup is made of. It decides which operators work.
      
        
      type definition
      The declaration type Celsius float64, with no =.
      
        
      conversion
      T(x): the same value as type T. Between types with the same underlying type, it changes only the type.
      
        
      non-local type
      A type declared in another package (or built into Go). You can't add methods to it.
      
        
      enum, enumeration
      A fixed list of named choices. In Go: a named integer type plus a block of constants.
      
        
      iota
      Inside a const block, the number of the current line (constant spec), from 0.
      
        
      blank identifier _
      A name that throws its value away; in a const block it skips a number.
      
        
      bit, bit flag
      A bit is one binary digit, 0 or 1. Bit flags give each choice one bit, so several can be on at once.
      
        
      <<, |, &
      Shift left; bitwise or (switch on); bitwise and (keep only switches on in both).
      
        
      type alias
      type A = B: a second name for the very same type.
      
        
      unexported type
      A type whose name starts with a small letter; other packages can't write its name.
      
        
      embedding, embedded field
      Putting a type in a struct (or an interface in an interface) with no field name. The field's name is the type's name.
      
        
      promoted field, promoted method
      A field or method of an embedded part that can be used directly on the outer value.
      
        
      selector
      The .Name after a value: v.HP, v.Start.
      
        
      shadowing
      A name on a closer layer hiding the same name on a deeper one.
      
        
      ambiguous selector
      A selector that matches two names at the same depth; a compile error when used.
      
        
      inheritance
      In some other languages, a class taking over another's methods so that the parent's code can call the child's versions. Go doesn't have it.
      
        
      composition
      Building a type from smaller parts and connecting behaviour through interfaces.

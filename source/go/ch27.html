Go's standard library has a simple logbook: the log package. log.Println and log.Printf work like their fmt cousins, with two differences.

    log_default.go
    

    
One possible run. The date and time are the moment the program ran, so they are different every time.

    

    
    
      
  1. A time stamp
    Every log line starts with the date and time, to the second. On your computer you'll see your own clock.
    2. 
      
  2. The error stream
    The log lines are drawn in error style: they went to standard error, while dock opens went to standard output. You can send the two streams to different places, for example go run log_default.go 2> night.log keeps the screen for answers and fills a file with the log.
    3. 
      
  3. A newline for free
    log.Printf adds a newline at the end if your format doesn't have one.
    4. 
    

  


  

    4
    
You can choose what goes at the start of each line. log.SetFlags(0) turns the time stamp off, and log.SetPrefix adds a label. This book uses SetFlags(0) so that every run prints exactly the same thing and can be checked.

    log_flags.go
    

    

    
    
      
  1. log.SetFlags(0) (line 9)
    A flag here is an on/off switch. 0 means all switches off: no date, no time. Others include log.Ldate, log.Ltime, log.Lmicroseconds, log.Lshortfile (the file and line that logged) and log.LUTC. Combine them with |, for example log.SetFlags(log.Ltime | log.Lshortfile).
    2. 
      
  2. The order on screen
    Both streams arrive at the same terminal, in the order they were written. That's why the log lines sit between the two fmt lines.
    3.

    PART 2 · STRUCTURED LOGSlog/slog: key-value pairs, text and JSON handlers, levels, With, groups, NewMultiHandler
    

  
    
    8
    
    The harbour master doesn't write sentences in the logbook. Every line has the same boxes: how serious, what happened, then labelled details. That's a structured log: a program can read it as easily as a person.
    
    
    
    
      
      
    1. 1The level: how serious. DEBUG, INFO, WARN or ERROR.
      2. 
      
    2. 2The message: a short, fixed sentence. Same event, same words, every time.
      3. 
      
    3. 3An attribute: a key and a value, such as crane=2.
      4. 
      
    4. 4Another attribute. Want every line about crane 2? Search for crane=2.
      5. 
    
    
  
    

  
    
    9
    
    Since Go 1.21 the standard library has a structured logger: log/slog ("s" for structured). You give it a message, then pairs: a key, then its value, a key, then its value.
    
    slog_default.go
    
    
    
    One possible run: the time stamp is the moment it ran.
    
    
    
    
      
      
    1. "id", 42, "to", "Lisbon"
      Read them two at a time: key id, value 42; key to, value "Lisbon". They come out as id=42 to=Lisbon.
      2. 
      
    2. INFO, WARN
      The level comes from which function you called: slog.Info, slog.Warn, slog.Error, slog.Debug.
      3. 
      
    3. Where's the Debug line?
      The default logger only shows INFO and above. Debug messages are for when you're hunting a problem; you switch them on when you need them (panel 13).
      4. 
      
    4. Same look as log
      Out of the box, slog writes through the log package: same time stamp, same standard error.
      5. 
    
    
  
    

  
    
    10
    
    The part of slog that decides what a line looks like and where it goes is called a handler. Make a logger with slog.New(handler). Here are the two built-in handlers. The programs differ only on line 10: NewTextHandler or NewJSONHandler.
    
    slog_text.go
    
    
    
    
    slog_json.go (the same file with line 10 changed)
    
    Show all of slog_json.go
    
    
    
    
      
      
    1. slog.NewTextHandler(os.Stdout, opts)
      key=value pairs, with quotes only where a value has a space: msg="parcel shipped". Easy for people, easy to search.
      2. 
      
    2. slog.NewJSONHandler(os.Stdout, opts)
      One JSON object per line (chapter 22). Numbers stay numbers (42, 12.5), true stays a boolean. Log-collecting services read this without guessing.
      3. 
      
    3. ReplaceAttr: noTime (lines 9 and 16 to 22)
      A hook that sees every attribute before it's written and may change or drop it. Returning an empty slog.Attr{} drops the time, so this book's runs repeat exactly. Real programs keep the time!
      4. 
      
    4. os.Stdout
      So the exercises can check the lines. In a real program, logs usually go to os.Stderr or a file.
      5. 
    
    
  
    

  
    
    11
    
    The handler as a machine: a logging call goes in, one line comes out. Try each call. The last one jams in a sneaky way.
    
    
    
    
  
    

  
    
  

  
    
  

  
    
    12
    
    Levels are really just numbers: Debug is −4, Info 0, Warn 4, Error 8. A handler has a minimum level; anything below it is skipped before any work is done. The gaps leave room for your own levels in between.
    
    slog_levels.go
    
    
    
      
      
    1. &slog.HandlerOptions{Level: slog.LevelInfo} (line 11)
      The minimum level. Set slog.LevelDebug while you hunt a bug, slog.LevelWarn when you only want trouble.
      2. 
      
    2. h.Enabled(ctx, lv) (line 14)
      Asks the handler: "would you write a line at this level?" Every logging call asks this first.
      3. 
      
    3. slog.LevelWarn + 2
      A level of your own, between Warn and Error. It prints as WARN+2.
      4. 
    
    
  
    

  
    
  

  
    
    13

    slog_with.go
    
    
    
    The run is hidden this time: it's the answer to the next check.
    
    
      
      
    1. scoot := base.With("courier", "Scoot") (line 11)
      A new logger. Every line it writes starts its attributes with courier=Scoot, before the call's own pairs. base itself is unchanged.
      2. 
      
    2. Level: slog.LevelDebug (line 9)
      This handler's minimum level is Debug, the lowest of the four.
      3. 
      
    3. slog.Group("route", "from", "dock", "to", "Lisbon") (line 13)
      Two attributes under the name route. The text handler writes each key with the group name and a dot in front; the JSON handler nests them inside an object named route.

The first word picks the booth, a subcommand; the flags after it fill in that booth's form.

    Sometimes your tool needs another tool: ring a bell, call git, run a script. The os/exec package starts another program and collects what it prints.
    
    exec_echo.go
    
    
    
    
    
      
      
    1. exec.Command("echo", "ring", "the", "dock", "bell")
      The program's name, then each argument separately. No shell is involved, so spaces, * and quotes in an argument are passed on exactly as they are. That's safer than gluing a command line together.
      2. 
      
    2. .Output()
      Runs it, waits, and returns everything it wrote to standard output as bytes: "ring the dock bell\n", newline included.
      3. 
      
    3. exec: "teleport": executable file not found in $PATH
      No program by that name in any folder on the PATH (chapter 1). An ordinary error value: check it like any other.
      4. 
    
    
  
    

  
    
    19
    
    When you press Ctrl+C in a terminal, the system sends the program a signal called SIGINT ("interrupt"). Normally that kills the program on the spot, deferred calls and all. signal.NotifyContext turns the signal into a cancelled context (chapter 26) instead, so the program can close up properly.
    
    signal_self.go
    
    
    
    
    
      
      
    1. signal.NotifyContext(context.Background(), os.Interrupt) (line 12)
      A context that is cancelled when an interrupt arrives. Add syscall.SIGTERM too for the polite "please stop" that servers and containers receive.
      2. 
      
    2. Line 17
      Nobody can press Ctrl+C during this book's captured run, so the program sends the signal to itself. That's the same signal your keyboard would send.
      3. 
      
    3. <-ctx.Done() (line 19)
      Waits until the context is cancelled. A real server would do its work meanwhile, and check ctx.Done() in its loops.
      4. 
      
    4. interrupt signal received
      Since Go 1.26, the context's cause names the signal. Go 1.24 says only context canceled (the version notes show both).
      5. 
      
    5. defer stop() (line 13)
      Hands the signal back to the default when main returns. Until then, every further Ctrl+C is still caught and does nothing. To let a second Ctrl+C force-quit while closing up, call stop() right after <-ctx.Done() as well (the os/signal documentation advises calling it as soon as you no longer need the signal).

    20
    
    So far every program ran with go run: the go command compiled it into a temporary file, ran it, and threw the file away. Shipping means packing the program into a crate that runs on its own, with no Go installed: an executable, or binary. And each crate gets a destination label: which operating system, and which kind of processor.
    
    
    
    
      
      
    1. 1The source code: text only you and the Compiler read.
      2. 
      
    2. 2go build: compiles everything into one file. Go puts the whole program, the parts of the standard library it uses and the runtime into that file, so the target computer needs nothing else.
      3. 
      
    3. 3The destination label: GOOS (Go's name for the operating system: linux, windows, darwin for macOS) and GOARCH (the processor: amd64 for most PCs, arm64 for newer Macs, phones and a Raspberry Pi).
      4.

    1. go env GOOS GOARCH
      This computer's own label: linux, amd64. It's what go build uses when you don't say.
      2.

    A customer says "dock is broken". Which dock? Every crate should carry a version number. Two tools: -ldflags "-X ..." stamps a value into a string variable while building, and every Go binary already carries build info that you can read from outside or from inside.

    28
    
    go vet is really a crew of its own: dozens of small checkers called analyzers, each looking for one kind of mistake that compiles but is almost certainly wrong. Here's one file that trips six of them.
    
    vet_many.go
    
    
    
    
    
    vet runs its analyzers at the same time, so the order of its messages can change from run to run. The command pipes them through sort -t: -k2,2n, which sorts by the number after the first colon: the line. A pipeline's exit code normally comes from its last command, here sort, which is happy; the first step, set -o pipefail, is a bash setting that makes the pipeline fail when any command in it fails, so the exit code below is vet's.
    
    
      
      
    1. passes lock by value and copies lock value (lines 14 and 19)
      The copylocks analyzer. A sync.Mutex (chapter 25) must never be copied: a copy is a second, separate lock, and the protection silently disappears. Pass *Dock.
      2. 
      
    2. format %d has arg "twelve" of wrong type string (line 18)
      The printf analyzer, from chapter 2.
      3. 
      
    3. result of fmt.Sprintf call not used (line 19)
      unusedresult. Sprintf builds a string and returns it; it prints nothing. Throwing the result away means the line does nothing at all.
      4. 
      
    4. call to slog.Info missing a final value (line 20)
      The slog analyzer, from panel 11.
      5. 
      
    5. self-assignment of d.crates (line 21)
      assign. Setting something to itself is a typo for something else, every time.
      6. 
      
    6. No header, exit code 1
      vet's messages have no # package line, unlike the Compiler's (chapter 2). vet exits with 1 when it found something (passed on here thanks to pipefail), so build scripts can stop.

    Under the hood: handlers, binaries, analyzers
    
      
      
      
        
        
      The Professor says: Four machines from this chapter, opened up.
      
      
      
      
      How slog is put together
      
      
      A *slog.Logger is a thin front end. Each call such as logger.Info(msg, args...) first asks the handler Enabled(ctx, level); if the answer is no, it returns at once, before turning arguments into attributes. Otherwise it builds a slog.Record (time, level, message, attributes) and passes it to the handler's Handle method. slog.Handler is an interface (chapter 14) with four methods, Enabled, Handle, WithAttrs and WithGroup, so anyone can write a handler: one that sends lines to a log service, one that colours the terminal, one that filters. NewMultiHandler is just a handler that calls several others. logger.With(...) calls WithAttrs, so a handler can format those attributes once instead of on every line.
      
      
      The loose "key", value style is convenient but unchecked. The typed style, logger.LogAttrs(ctx, slog.LevelInfo, "shipped", slog.Int("id", 42), slog.String("to", "Lisbon")), can't produce !BADKEY and allocates less memory, which matters in code that logs very often.
      
      
      What the log package's flags do
      
      
      log keeps one default logger that writes to os.Stderr. log.SetOutput(w) sends it anywhere that has a Write method, such as a file. log.New(w, prefix, flags) makes extra loggers. log.Fatal, log.Fatalf and log.Fatalln print, then call os.Exit(1); log.Panic prints, then panics, which does run deferred calls. slog.SetDefault(logger) also redirects the old log functions through your slog handler.
      
      
      Why cross-compiling is so easy in Go
      
      
      The Go compiler can produce machine code for every supported processor, and the standard library is written in Go (with small pieces of assembly per platform), so it can be compiled for any target on any computer. By default Go programs are statically linked: everything the program needs is inside the one file, so the target computer needs no Go and no extra libraries. The exception is cgo, Go's bridge to C code: with cgo on, you also need a C compiler for the target. This book's captures run with CGO_ENABLED=0, and plain Go programs like dock don't need cgo at all.
      
      
      Where build info lives
      
      
      go build writes a small block of text into the binary: the Go version, the main module path and version, every dependency module with its version and checksum, and the build settings (-trimpath, CGO_ENABLED, GOOS, GOARCH, GOAMD64, and version-control details such as the commit when you build inside a git repository). go version -m reads that block from the file; debug.ReadBuildInfo reads it from memory. govulncheck can scan a binary the same way: govulncheck -mode=binary ./dock.
      
      
      How vet, go fix and staticcheck read your code
      
      
      They all parse your source into a tree, type-check it exactly as the Compiler does, then walk the tree looking for patterns. vet and go fix share one framework, golang.org/x/tools/go/analysis: each analyzer is a small program that reports diagnostics, and some diagnostics carry a suggested fix, a precise text edit. go vet prints diagnostics; go fix applies fixes. staticcheck and most golangci-lint linters use the same framework, which is why they can be mixed. Because these tools must understand the newest syntax, a tool built with an older Go may fail on newer code, as panel 34 showed.
      
      
      How govulncheck decides "your code is affected"
      
      
      It loads your module's packages, builds a call graph (who calls whom), and looks up each dependency's version in the Go vulnerability database, which records the affected versions and the affected functions. Only vulnerabilities whose functions your code can reach are listed under symbol results. The database also covers the standard library, so an old Go installation shows up too: the fix is then to update Go.
      
    
      
  
      

  
      
    In real programs: logs, tools and releases
    
      
      
        
        
      • JSON logs in production, text on your laptop. Services usually log JSON to standard error and let the platform collect it. A command-line option or environment variable picks the handler and the level, so you can switch on Debug lines without changing code.
        • 
        
      • Context-aware handlers. Every slog method has a ...Context twin, such as logger.InfoContext(ctx, ...). A custom handler can pull a request ID out of the context (chapter 26) and add it to every line, so one request can be followed through the whole log.
        • 
        
      • Never log secrets. Passwords, tokens and personal data end up in log files that many people can read. Give such types a LogValue() method (the slog.LogValuer interface) that returns a masked value.
        • 
        
      • Command-line libraries. Many larger Go tools use third-party packages such as Cobra for nested subcommands, shell completion and generated help. Under the hood it's the same idea as panel 16: pick a booth, parse its form.
        • 
        
      • Release builds. Projects usually build every platform in a build server, with -trimpath and a version from git tags, and publish one archive per GOOS/GOARCH. Tools such as GoReleaser automate this. -ldflags="-s -w" leaves out debugging information to make files smaller, at the price of less helpful crash reports.
        • 
        
      • Graceful shutdown. Servers combine signal.NotifyContext with http.Server.Shutdown(ctx) (chapter 26): stop accepting new requests, finish the ones in flight, then exit.
        • 
        
      • The crew on every change. A typical project's build server runs gofmt -l (fails if any file is listed), go vet ./..., a linter, go test -race ./... and govulncheck ./.... Editors run gopls, which shows vet and staticcheck findings as you type.
        • 
        
      • Delve, the debugger. go install github.com/go-delve/delve/cmd/dlv@latest, then dlv debug in a package folder starts your program paused. break main.go:20 sets a breakpoint; condition 1 crates == 0 makes breakpoint 1 stop only when that's true (a conditional breakpoint); continue, next, step and print lang move and look around; goroutines lists every goroutine and goroutine 7 switches to one, which helps with chapter 24's helpers. Editors with the Go extension use Delve behind their debug buttons. Delve isn't installed on this book's capture machine, so no Delve output is shown here.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "log.Fatal is a fancy log.Println." It exits the program, skipping every deferred call (panel 5, Boss 2).
        • 
        
      • "Logs and output are the same thing." Output is the program's answer, on standard output. Logs describe what happened, on standard error or in a file.
        • 
        
      • "slog will complain if I forget a value." It quietly writes !BADKEY. vet complains; slog doesn't.
        • 
        
      • "Debug lines cost nothing when they're switched off." The call is skipped cheaply, but its arguments are still evaluated first. Don't compute something expensive just to pass it to Debug.
        • 
        
      • "Flags can go anywhere." The flag package stops at the first word that isn't a flag (panel 17's predict, Boss 5).
        • 
        
      • "Naming the file dock.exe makes it a Windows program." Only GOOS=windows does (Boss 6).
        • 
        
      • "A binary built on my Mac runs on any Mac." darwin/arm64 and darwin/amd64 are different crates. An arm64 crate won't run on an Intel Mac; an amd64 crate runs on Apple silicon only through Apple's Rosetta translator.
        • 
        
      • "go build printed nothing, so it didn't work." Silence is success.
        • 
        
      • "If it compiles, the linters have nothing to say." Panels 28 and 29: every one of those programs compiled.
        • 
        
      • "The go line in go.mod picks which Go runs my code." It's the minimum version you promise to support (and the language features you may use). With GOTOOLCHAIN=auto a newer go line can make the go command download a newer toolchain, but it never makes an old one pretend.
        • 
        
      • "govulncheck found nothing, so my program is secure." It only knows published vulnerabilities in Go modules and the standard library. Your own bugs are your tests' job.
        • 
        
      • "Turning a linter off fixes the warnings." It hides them (panel 34).

      The first word after a tool's name that picks what it should do, like build in go build.
      
        
      FlagSet
      A separate set of flags, one per subcommand.
      
        
      usage message
      The help text a tool prints when it's used wrongly or asked with -h.
      
        
      exit code 2
      By custom, "the command was used wrongly".
      
        
      signal, SIGINT, SIGTERM
      A message from the system to a running program; Ctrl+C sends SIGINT, a polite stop request is SIGTERM.
      
        
      binary, executable
      A file of machine code that runs on its own.
      
        
      GOOS, GOARCH
      The target operating system and processor for a build: the destination label.
      
        
      cross-compiling
      Building a program on one kind of computer for another kind.
      
        
      GOBIN
      The folder go install puts programs in; $HOME/go/bin when it's not set.
      
        
      -trimpath
      A build flag that removes your computer's folder names from the binary.
      
        
      linker, -ldflags, -X
      The linker joins compiled pieces into one binary; -ldflags passes it options; -X sets a string variable.
      
        
      build info
      The Go version, modules and settings recorded inside every Go binary.
      
        
      static linking
      Putting everything a program needs into its one file.
      
        
      analyzer
      One small checker inside vet, go fix or a linter, looking for one kind of problem.
      
        
      linter
      A tool that checks code for likely mistakes without running it.
      
        
      modernizer
      A go fix analyzer that rewrites code into a newer idiom without changing what it does.
      
        
      diff
      A listing of changes between two versions of a file: - lines removed, + lines added.
      
        
      vulnerability
      A known security problem in some versions of a piece of software.
      
        
      call graph
      A map of which functions call which; govulncheck uses it to see if you reach a vulnerable function.
      
        
      tool directive
      A tool line in go.mod that pins a program, run with go tool name (Go 1.24).
      
        
      stdversion
      The vet analyzer that flags standard library names newer than the module's go line.
      
        
      debugger, breakpoint
      A program (Delve) that pauses yours so you can look inside; a breakpoint is where it pauses.

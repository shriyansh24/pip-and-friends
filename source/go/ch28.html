2

A benchmark is a stopwatch race for code: Go runs the same job many times and reports averages. You met it in chapter 23. Today we read two of its numbers, and they behave very differently.

WOBBLES

ns/opnanoseconds per run of the job

The time. It changes every run: your laptop is also playing music, the fan speeds up, other programs wake. This book never uses it as an answer; on this page it's always replaced by ….

STEADY

allocs/optrips to the storage unit per run

How many times the job asked for new memory on the heap. For the same code and the same Go version, it's the same on every run and every computer. Fewer trips usually means faster.

Scoot says: Catchphrase: don't guess, time it. And when the time wobbles, count the trips.

PART 3 · PLATES, STORAGE UNIT, JANITORstack and heap, escape analysis, the garbage collector, and pprof


  

    13
    
Where do “trips” go? Go keeps a program's values in two places. The first is the pile of plates from chapter 7's notebook: every function call gets a plate on top of the pile.

    

    

      
THE PLATES
the stackquick, tidy, private
Each function call gets a plate for its variables, on top of the pile. When the function returns, its plate comes off in one go, with everything on it. Nothing to clean up, and no trip anywhere.

      
THE STORAGE UNIT
the heapfor things that must outlive a call
A value that's still needed after its function returns goes here, and you keep an address slip (a pointer, chapter 13) to it. Renting a unit is a trip (an allocation), and someone has to clear it out later: the janitor.

    

    

      
      
Scoot says: Catchphrase: a plate if you can, a storage unit if you must. You never choose in Go: the Compiler decides for you, and it can tell you what it decided.

    16
    
    The janitor is Go's garbage collector (GC). Every so often it walks the building: starting from every address slip on every plate, it marks each unit it can reach, following slips inside units too. Then it clears every unit nobody marked. It does most of this while your program keeps running, using part of the CPU, with only very short pauses.
    
    
    
    Key: ticked = reachable, kept · dashed = nobody's, cleared · free = ready for the next trip.
    
    
    
      
    WHY TRIPS COST TWICE
    Every allocation is work now (finding a free unit) and work later (the janitor marking and sweeping). Fewer, bigger trips mean the janitor comes round less often. That's why allocs/op is such a good clue.
    
      
    GREEN TEA
    Since Go 1.26 the janitor uses a design called Green Tea by default: instead of hopping from object to object all over the building, it works through memory a block at a time, which suits how today's processors read memory. Your code doesn't change at all; it was an experiment in Go 1.25.
    
    
    
  
    

  
    
    17
    
    A benchmark says how slow. A profiler says where. Go's is pprof: add -cpuprofile=cpu.out (or -memprofile=mem.out) to go test -bench, then open the file with go tool pprof. While the program runs, the profiler peeks about a hundred times a second and notes which function is running, and who called it.
    
    
    
    
    That picture is a flame graph, drawn by hand here as a teaching model. Each bar is a function; bars stand on the function that called them; width is time. Look for the widest bars near the top. Since Go 1.26, go tool pprof -http=:8080 cpu.out opens the flame graph first in your browser. The Professor's notebook (“Lab”) has a real profile of this code, with its text report.

        PART 6 · BOSS LEVEL AND THE END OF THE BOOKrefactor in order, six harder checks, the recap, and a party
        

  
        
    35
    
        Thursday. Time to act on the comments. Changing code's shape without changing what it does is called refactoring, and the order matters more than the cleverness.
        
    
          
      
        1. Tests green first. Run go test before touching anything. No tests for this code? Write a few now (chapter 23). They're your safety net.
          2. 
      
        2. One change at a time. Flatten the nesting, run the tests. Fix the shadowed err, run the tests. Small steps make a mistake easy to find.
          3.

          4.

          5. 
      
        5. Speed last, and only with a stopwatch. Benchmark before and after, on the same machine; keep the change only if the numbers say so.
          6. 
      
        6. Ask for another review. Fresh eyes on the new version, then merge.

    Under the hood: how allocations are counted, what escapes, and how the janitor works
    
        
      
        Counting trips
        
      
        The runtime keeps running totals of every heap allocation: how many (Mallocs) and how many bytes (TotalAlloc), readable with runtime.ReadMemStats. -benchmem reads them before and after the timed loop and divides by the number of laps; testing.AllocsPerRun does the same around your function (after one warm-up call) and returns the average. Both count only the heap: space on a plate (the stack) is free and never counted. That's why a function can create values and still report zero.
        
      
        How b.Loop helps
        
      
        The old style, for i := 0; i < b.N; i++, let the Compiler notice that a result was never used and throw the work away, so benchmarks measured empty loops (100 Go Mistakes #89). Inside for b.Loop(), arguments and results are kept alive on purpose. Since Go 1.26 b.Loop also no longer stops the Compiler from inlining calls in the loop body, so the old and new styles measure the same code. In ordinary programs like allocs.go, storing the result in a package-level variable does the same job.
        
      
        Escape analysis
        
      
        While compiling, Go works out for each value whether any reference to it can outlive the function: returned pointers, values stored in global variables or in other heap objects, values captured by a closure that outlives the call, values put into an interface that escapes, and values too big or of unknown size for the stack. Anything that might escape goes to the heap; the rest stays in the function's stack frame. The analysis is careful, so “might” is enough to escape. Small inlined functions often stop escaping once the Compiler can see the caller. Two recent releases let more slices start on the stack. Go 1.25 gave a small slice that never leaves its function a 32-byte starter array on the stack: that's the cap 4 you saw in panel 9. Go 1.26 extended this to slices that do escape at the end, for example by being returned or stored: they start on the stack, and are copied to the heap once, when they leave. That's why append 1000, no cap in allocs_m.go, whose slice escapes into keepInt, counts 9 trips on this book's Go and 12 on Go 1.24.7.
        
      
        Stacks that grow
        
      
        Each goroutine has its own stack, which starts small (a few kilobytes) and grows by copying itself to a bigger one when needed. That's how Go can run hundreds of thousands of goroutines. When a stack is copied, pointers into it are updated, which is one reason Go never lets you keep a pointer to a stack slot that might move without the runtime knowing.
        
      
        The garbage collector
        
      
        Go's GC is a concurrent mark-and-sweep collector. It starts a cycle when the heap has grown by a set fraction since the last one (the GOGC setting, default 100, meaning “when the heap doubles”), or when a soft memory limit (GOMEMLIMIT) is near. Marking happens alongside your goroutines, using about a quarter of the CPU plus a little help from goroutines that allocate a lot; two very short stop-the-world pauses bracket the cycle. Sweeping returns unmarked memory for reuse. Green Tea, the default since Go 1.26, changes how marking walks memory: it scans small objects page by page rather than chasing one pointer at a time, which keeps the processor's caches busy with nearby memory. The Go team reported that many programs spend noticeably less CPU time on garbage collection with it; your code needs no change.
        
    
        
  
        

  
        
    In real programs: performance work and code review at real companies
    
        
      
          
        
        • Benchmarks in pull requests. A change that claims to be faster comes with before-and-after numbers. Teams run go test -bench=. -count=10 on both versions and compare them with benchstat (from golang.org/x/perf), which says whether a difference is real or noise.
          • 
        
        • Profiles from live servers. Importing net/http/pprof adds /debug/pprof/ pages to a server, so you can take a 30-second CPU profile of the real thing. Keep those pages private.
          • 
        
        • Profile-guided optimisation (PGO). Save a CPU profile from production as default.pgo next to main, and go build uses it to inline the hot paths more boldly.
          • 
        
        • Allocation budgets. Libraries that sit in hot paths (JSON encoders, loggers, routers) often test that a call makes zero allocations with testing.AllocsPerRun, so a future change can't quietly add one.
          • 
        
        • Review culture. Large Go projects review every change. Go's own project keeps a page of common review comments (“Go Code Review Comments”), and many teams start from it. Linters such as staticcheck (chapter 27) catch more of the gallery automatically.
          • 
        
        • Style is mostly settled. Because gofmt decides layout, Go reviews spend their time on behaviour, naming and design, not on where braces go.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • “I can tell which part is slow by reading it.” Experienced programmers guess wrong all the time. Measure.
          • 
        
        • “One benchmark run tells me the speed.” Times wobble. Repeat runs, compare with benchstat, and trust allocation counts for steady comparisons.
          • 
        
        • “+= is always wrong.” For a handful of pieces it's clear and fine. It's a loop over many pieces that hurts.
          • 
        
        • “new() and &T{} put things on the heap.” Not necessarily. Escape analysis decides; a pointer that never leaves the function can point into the stack.
          • 
        
        • “The garbage collector stops my program for a long time.” Go's pauses are usually well under a millisecond; most of the work runs alongside your code.
          • 
        
        • “Pointers are always faster than copying.” A pointer can make a value escape, which costs a trip and janitor work. Small structs are often cheaper to copy.
          • 
        
        • “If it compiles, the review is just style.” Every bug in part 5 compiles.
          • 
        
        • “A nil slice is an error waiting to happen.” It's a perfectly good empty slice for len, range and append. It only differs for == nil and JSON.
          • 
        
        • “Shadowing is always a mistake.” if err := f(); err != nil shadows on purpose and is idiomatic. It's shadowing by accident that bites.

    Words from this chapter
    
        
      
        
        
        benchmark
        A function BenchmarkXxx(b *testing.B) that runs code many times to measure its cost.
        
        
        -benchmem
        The go test flag that adds B/op and allocs/op to benchmark results.
        
        
        ns/op, B/op, allocs/op
        Average nanoseconds, heap bytes and heap allocations per run of the benchmark loop.
        
        
        allocation (a trip)
        Asking for new memory on the heap.
        
        
        testing.AllocsPerRun
        Calls a function many times and returns the average number of allocations per call.
        
        
        strings.Builder
        A type that builds a string piece by piece in one growing buffer; Grow reserves room in advance.
        
        
        preallocate
        Reserve room before filling: make([]T, 0, n), make(map[K]V, n), b.Grow(n).
        
        
        stack (the pile of plates)
        Memory for each function call's variables: one plate per call, taken off automatically when the call returns.
        
        
        heap (the storage unit)
        Memory for values that must outlive the function that made them; cleared by the garbage collector.
        
        
        escape analysis
        The Compiler's check of which values can outlive their function and must go on the heap.
        
        
        garbage collector (GC, the janitor)
        The part of the Go runtime that finds heap memory nothing refers to any more and frees it.
        
        
        Green Tea
        The garbage collector design used by default since Go 1.26.
        
        
        profiler, pprof
        A tool that samples a running program to show where its time or memory goes.
        
        
        flame graph
        A picture of a profile: stacked bars, one per function, with width showing time.
        
        
        flat, cum
        In a pprof table: time in a function's own code, and time including everything it called.
        
        
        pull request
        A proposed set of changes that teammates review before it's merged into the main code.
        
        
        code review
        Reading someone's changes to find bugs and suggest clearer code.
        
        
        refactoring
        Changing code's structure without changing what it does.
        
        
        early return, guard clause
        Checking a problem first and returning straight away, so the main path isn't nested.
        
        
        idiomatic
        Written the way experienced Go programmers expect.
        
        
        doc comment
        A comment directly before an exported name, starting with that name; shown by go doc.
        
        
        shadowing
        Declaring a new variable with the same name as one in an outer block, hiding the outer one.
        
        
        range copy
        The loop variable in for _, v := range s is a copy of each element.
        
        
        zero value, useful zero value
        The value a variable holds before you set it; a type whose zero value is ready to use needs no constructor.
        
        
        receiver (value, pointer)
        The value a method is called on: a copy, or the original through a pointer.

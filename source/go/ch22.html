2

JSON (say "JAY-son", short for JavaScript Object Notation) is plain text with a few simple rules. Websites, phone apps and config files use it to pass data between programs written in different languages.

IN GO Parcel{ ID: 7, To: "Ana", Kg: 2.5, Fragile: true, }

A struct valuelives in your program's memory

Only Go understands it. It has a type, Parcel, with typed fields.

AS JSON {"ID":7,"To":"Ana", "Kg":2.5,"Fragile":true}

JSON textjust characters, ready to send

Any language can read it. Keys are always in double quotes; values are written in a few simple forms.

The IN GO card: a Go struct value Parcel with ID 7, To "Ana", Kg 2.5 and Fragile true. The AS JSON card: the same data as JSON text, an object with keys "ID", "To", "Kg" and "Fragile".

JSON formLooks likeUsually becomes, in Go
object{"to": "Ana"}a struct, or a map with string keys
array[1, 2, 3]a slice (or an array)
string"Ana"string
number2.5int, float64 and friends
true / falsetruebool
nullnullnil (a nil slice, map, pointer or interface)

Scoot says: Turning a Go value into JSON text is called encoding, or marshalling. Turning JSON back into a Go value is decoding, or unmarshalling. Go's package for it is encoding/json.

But the officer wants lowercase keys like "to", and some boxes left out when empty. You write those instructions in a struct tag: a little string in backquotes after a field's type. It's the translation printed next to each line of the form.

    

      

        
Go field and its tagOn the customs form

        
          
ID int `json:"id"`declared as "id"

          
Kg float64 `json:"weight_kg"`declared as "weight_kg": any name you like

          
Note string `json:"note,omitempty"`declared as "note", but left off the form when it is empty: "", 0, false, nil, or an empty slice or map. (A struct is never "empty"; the notebook shows the omitzero option for that.)

          
Secret string `json:"-"`never declared: the dash means "skip this field"

          
pin string (lowercase)never declared: a private pocket. The officer can't see unexported fields at all

        
      

    

    

      
      
Officer Ines says: Catchphrase: tags are the translations. The Go name stays in your program; the tag says what to write on my form. The format is exact: json:"name,option", no spaces.

    Under the hood: how the desk reads your struct, what a time.Time holds, and where random numbers come from
    
    
      
    Reflection and struct tags
    
      
    json.Marshal takes an any, so it doesn't know your type when it's compiled. At run time it uses the reflect package to list the struct's fields, their types and their tags. A tag is just a string stored with the field; reflect.StructTag.Get("json") parses the key:"value" convention. That's why a malformed tag (panel 7) is silently ignored by Marshal, and only go vet notices. reflect can see unexported fields, but another package can't take their values out as interfaces or set them, so encoding/json skips them. The work of looking up a type's fields is done once per type and cached.
    
      
    omitempty, omitzero and structs
    
      
    omitempty leaves a field off only when it is empty: false, 0, a nil pointer or interface, or an array, slice, map or string of length zero. A struct is never empty, so a zero time.Time (the year 1, written 0001-01-01T00:00:00Z) is still declared. The omitzero option (added in Go 1.24) leaves a field off when it holds its type's zero value, structs included; a type with an IsZero() method, like time.Time, is asked directly. The package documentation now suggests omitzero instead of omitempty for bools, numbers, pointers and interfaces.
    
      omit_struct.go
      
    
      
    
      
    Why Unmarshal needs a pointer
    
      
    Go passes arguments by value (chapter 7). Unmarshal(data, p) would receive a copy of the struct inside an any, and anything it wrote would vanish. With &p, it receives an address and writes through it. Rather than silently doing nothing, Unmarshal returns an *json.InvalidUnmarshalError, which prints as json: Unmarshal(non-pointer main.Parcel).
    
      
    Custom forms: MarshalJSON and friends
    
      
    A type can write its own form by having a MarshalJSON() ([]byte, error) method (and read it back with UnmarshalJSON). That's how time.Time becomes an RFC 3339 string. Types with MarshalText, like uuid.UUID, are written as JSON strings. Careful: if you embed a time.Time in your struct (chapter 18), its MarshalJSON is promoted and replaces your whole struct's form, one of the JSON mistakes in 100 Go Mistakes (#77).
    
      
    Numbers, escapes and errors
    
      
      
        
    • Into an any, numbers become float64, which holds whole numbers exactly only up to 253. For big IDs, call dec.UseNumber() on a Decoder to get json.Number strings instead.
      • 
        
    • By default Marshal escapes <, > and & inside strings as \u003c, \u003e and \u0026, so JSON can be pasted safely into a web page. A JSON reader turns them back into the same characters. A json.Encoder can turn this off with SetEscapeHTML(false).
          html_escape.go
          
      
          
      
        
      • 
        
    • A syntax error is a *json.SyntaxError with an Offset field: how many bytes were read before the problem. A wrong kind is a *json.UnmarshalTypeError with Field, Value and Type. Get them with errors.As (chapter 19).
      • 
        
    • Since Go 1.27, encoding/json is implemented on top of the v2 code. The release notes say marshalling and unmarshalling behave as before, unmarshalling is significantly faster, and the exact text of error messages may differ. (Every error message on this page was identical under Go 1.24.7.) Building with GOEXPERIMENT=nojsonv2 switches back to the old implementation for now.
      • 
      
    
      
    encoding/json/v2's stricter defaults
    
      
    Besides exact name matching and refusing duplicate names (panel 18), v2 rejects invalid UTF-8 in strings, writes nil slices as [] and nil maps as {}, and has no default form for time.Duration (v1 writes the raw nanosecond count, which surprises readers; v2 asks you to choose with an option). Its functions take options, such as json.MatchCaseInsensitiveNames(true), and the lower-level encoding/json/jsontext package reads and writes JSON tokens. The v1 package's API isn't going away.
    
      
    What a time.Time holds
    
      
    A time.Time holds a wall-clock reading (seconds and nanoseconds), sometimes a monotonic clock reading (the m=+… in panel 32), and a pointer to a *time.Location. That pointer is why == can say false for the same moment in two zones: use Equal. time.Now() includes the monotonic reading, which Sub and Since prefer; Round(0), In, UTC and a JSON round trip drop it. A time.Duration is an int64 count of nanoseconds, so it can span about 292 years either way.
    
      
    How Format reads a layout
    
      
    Format scans the layout from left to right. At each position it checks whether one of the reference pieces starts there (January before Jan, 2006 before 2, 15 before 1). If so, it writes that part of your time; if not, it copies the character. That's why YYYY is copied, and also why a word like "Monday" in your own text gets replaced. There are a few more pieces than the builder shows: .000 for milliseconds, Z07:00 (writes Z for UTC), 002 for the day of the year.
    
      
    Where the random numbers come from
    
      
    The top-level math/rand/v2 functions draw from a generator the runtime seeds randomly at start-up, safe to call from many goroutines. rand.NewPCG and rand.NewChaCha8 make sources you seed yourself; the package documentation calls ChaCha8 "resistant to prediction" and PCG "faster but unfit for security-relevant purposes", and it warns that the package's outputs "might be easily predictable regardless of how it's seeded". Go 1.27 also gives *rand.Rand a generic N method, so r.N(10*time.Second) picks a random Duration. crypto/rand reads from the operating system's secure random source (on Linux, the getrandom system call). The old math/rand (no /v2) still exists; v2 arrived in Go 1.22 with clearer names like IntN.
    
    
    
  
    

  
    
    In real programs: where forms and clocks show up
    
    
      
      
        
    • Web APIs. Nearly every web service speaks JSON. A Go server decodes requests with json.NewDecoder(r.Body) and replies with json.NewEncoder(w) (chapter 26).
      • 
        
    • Config and data files. JSON settings files, CSV exports from spreadsheets and banks, and XML in older systems and office documents.
      • 
        
    • Logs. Structured logs are often written as one JSON object per line ("JSON Lines"), exactly the stream a Decoder reads. Go's log/slog can write them (chapter 27).
      • 
        
    • Timestamps. APIs and databases usually store RFC 3339 times in UTC. Durations in settings are often strings like "30s", read with time.ParseDuration or flag.Duration.
      • 
        
    • Timeouts everywhere. HTTP clients, database calls and contexts all take time.Durations, so the "bare number" mistake has real costs (chapters 24 to 26).
      • 
        
    • IDs. UUIDs name orders, users and uploads. Version 7 is popular for database keys because new IDs sort last.
      • 
        
    • Randomness. Shuffles, sampling, test data and retry "jitter" use math/rand/v2; session tokens, reset codes and keys use crypto/rand.
      • 
      
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "Marshal reports fields it can't write." Unexported fields are skipped silently. Run go vet.
      • 
        
    • "A tag makes a lowercase field visible." No: the field must be exported. The tag only renames it.
      • 
        
    • "omitempty hides a field." Only when it is empty ("", 0, false, nil, or an empty slice or map), and a struct such as a zero time.Time never counts as empty: use omitzero for that (see "Under the hood"). Use json:"-" to always hide a field.
      • 
        
    • "Unmarshal clears the struct first." It writes only the keys present (panel 12's exercise).
      • 
        
    • "Unmarshal complains about unknown keys." It ignores them, unless you use a Decoder with DisallowUnknownFields().
      • 
        
    • "JSON numbers in an any are ints." They're float64s.
      • 
        
    • "Trailing commas are fine." In Go code, yes; in JSON, they're a syntax error.
      • 
        
    • "YYYY-MM-DD is a Go layout." It prints itself. Show the magic photo.
      • 
        
    • "01 is the first minute." 01 is the month; minutes are 04.
      • 
        
    • "== compares moments." Use t.Equal(u).
      • 
        
    • "time.Sleep(5) waits five seconds." Five nanoseconds. Say the unit.
      • 
        
    • "Random numbers are random enough for passwords." Only crypto/rand's are.
      • 
        
    • "Seeding with the time makes math/rand secure." No seed makes it secure; the v2 top-level functions are already seeded for you.

The listed differences: uuid_parse.go, secrets.go and v2.go don't build there, because uuid and encoding/json/v2 are new in Go 1.27 (panel 18 shows that run); for vet_tag.go, Go 1.24.7's go vet prints two header lines (# command-line-arguments and # [command-line-arguments]) and writes ./vet_tag.go before each of the same two findings; and now.go and dice.go differ because they read the clock and fresh randomness. All JSON, CSV, time and Duration outputs and error messages were identical.

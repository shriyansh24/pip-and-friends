CHAPTER 17 · INTERMEDIATE

BACKPACKS AND BUFFETS

Picture: Scoot, the bike courier in a red cap and green jacket, cheers with both arms up.

Welcome to the intermediate part of the book. Until now, you handed functions numbers, strings and slices. Today you hand them other functions. A function made inside another one carries a backpack of the variables it saw, and keeps them. You'll sort people with your own rule, meet a function that calls itself, and fill a buffet plate that takes any number of items. Then everything joins up in one famous Go pattern: options as stickers on a default order. About 120 minutes, with 27 hands-on checks.

  1. Machines in boxes: function values
  2. The backpack: closures
  3. The loop-variable trap (Go 1.22)
  4. Plug-in rules: sorting
  5. Parcels inside parcels: recursion
  6. The buffet plate: variadics and options
  7. Boss level and recap

PART 1 · MACHINES IN BOXESA function is a value, like 5 or "hi"

1

Scoot's courier company has a new dispatcher. Every morning she hands Scoot a list of parcels, and also a rule: "double the stamps today", or "square them".

Scoot says: I can carry a number in a box. I can carry a slice. Can I carry a rule?

Scoot says: A rule is a machine: something goes in, something comes out. So the question is: can a machine go in a box too?

Three things that all start with func. Learn to tell them apart:

    

      

        func double(n int) int {…}
        
DECLARATIONbuilds a named machine

        
A name, parameter names, and a body. This is what you've written since chapter 7.

      

      

        func(int) int
        
FUNCTION TYPEthe shape of the plug

        
No name, no body, parameter names optional. It only says what goes in and what comes out. Any machine with that shape fits.

      

      

        f := double
        
FUNCTION VALUEthe machine in a box

        
The machine itself, ready to be stored, handed over, or called later with f(…).

    PART 3 · THE LOOP-VARIABLE TRAPOne box for the whole loop, or a fresh box every lap?
    

  
    
    16
    
    Scoot finds the Professor reading old Go code, frowning.
    
    
    
      
      
    
        
    The Professor says: Closures in a loop have a history. From Go 1.0 in 2012 until 2024, a loop like for i := 0; i < 3; i++ had one box i for the whole loop. Every lap reused it.
    
        
    The Professor says: So three closures made in three laps all packed the same box. People expected 0, 1, 2 and got something else. The Go team called it one of the most common Go mistakes, and in Go 1.22 (February 2024) they changed the rules: each lap gets its own fresh box.
    
      
    
    
    
    
    
      
    Scoot says: But then old programs would suddenly behave differently!
    
      
    
    
    
    Picture: the Professor, with glasses and a notebook, explains; Scoot looks worried.
    
  
    

  
    
    17
    
    Not quite. The new rule only applies to modules whose go.mod says go 1.22 or later (chapter 15's go line). Proof: the same program, copied into two modules, built by the same Go 1.27.3. (Each module was made with go mod init; then go mod edit -go=1.21, or -go=1.27, set its go line, as cat go.mod shows.)
    
    
    
    main.go · the same in old121 and new127
    
    
    
    
      
    
        
    MODULE SAYS go 1.21
    
        
    
      
    
      
    
        
    MODULE SAYS go 1.27
    
        
    
      
    
    
    
    
      
      
    1. 3 3 3 (go 1.21)
      Under the old rules there is one i. When the closures finally run (lines 10 to 12), the loop has finished and that one box holds 3, the value that made i < 3 false.
      2. 
      
    2. 0 1 2 (go 1.27)
      Under the new rules each lap has its own i, and each closure packed a different box.
      3.

    PART 5 · PARCELS INSIDE PARCELSRecursion: a function that calls itself
    

  
    
    26
    
    A prank delivery: Scoot opens a parcel and finds a smaller parcel inside, and inside that another, until the smallest one holds the answer. Then the answers travel back out, one layer at a time.
    
    
    
    
    
      
      
    Scoot says: A function that calls itself is recursive. Every recursive function needs a smallest parcel it can answer straight away: the base case. Catchphrase: every trip down needs a floor.
    
    
    
  
    

  
    
    27
    
    The factorial of a number multiplies every whole number from 1 up to it: 3 factorial is 3 × 2 × 1. Notice that it's also 3 × (2 factorial). A problem that contains a smaller copy of itself is a perfect fit for recursion.
    
    factorial.go
    
    
    
    
    
      
      
    1. if n == 0 { return 1 } (lines 6 to 8)
      The base case. No more calls: the trip down stops here. (By definition, 0 factorial is 1.)
      2. 
      
    2. return n * fact(n-1) (line 9)
      The recursive case: answer a slightly smaller problem, then use it. Each call moves one step closer to 0.
      3. 
      
    3. 6, 120, 3628800 (lines 13 to 15)

    30
    
    
      What if you forget the base case? func down(n int) int { return down(n-1) + 1 } calls itself forever: 5, 4, 3, … 0, -1, -2, … No parcel is ever small enough.
      
    
    
    
      Every call adds a frame and none ever finishes. Go lets a goroutine's stack (chapter 24 explains goroutines; main runs in one) grow up to 1 GB on a 64-bit computer. When the tower hits that ceiling, the program dies with a fatal error, not an ordinary panic. This page has no captured run of it: on the book's machine it took about 20 seconds to fill the stack, the report is many screens long, and its addresses change every time. In one uncaptured run with Go 1.27.3, made while checking this page, the report's first line was runtime: goroutine stack exceeds 1000000000-byte limit and the third was fatal error: stack overflow. Try it yourself in the lab (Professor's notebook).
      
    
      
      
      
      Scoot says: The Compiler can't catch this one: calling yourself is allowed. If you ever see stack overflow, check two things: is there a base case, and does every call really move closer to it?

    Under the hood: what a closure really is, where its backpack lives, and why the stack can grow
    
          
      
          A function value is a pointer
          
      
          A plain function's code lives in the program file and never moves. A function value is a small pointer to a closure record: the address of the code, followed by the captured variables (or pointers to them). For a function with nothing to capture, like double, the record holds only the code address. Calling f(5) reads the code address out of the record and jumps there, with the record handy so the body can reach its backpack. That's why the zero value is nil, and why calling it is a nil pointer dereference.
          
      
          Where the backpack lives
          
      
          In panel 12, n outlives makeCounter. The Compiler notices that a closure captures n and might outlive the call, so n "escapes": it is placed in longer-lived memory (the heap) instead of the function's own frame, and the garbage collector frees it when the last closure that refers to it is gone. When a captured variable is never changed after capture and is small, the Compiler may store a copy in the record instead of a pointer; you can't tell the difference, because nobody changes it. You can watch these decisions with go build -gcflags=-m (chapter 28).
          
      
          Capture by reference
          
      
          Go closures capture variables, not values. That's why panel 10 printed Yo Bo and why the old loop rule bit so hard. Some languages copy values into closures, or let you choose; Go always shares. If you want a snapshot, copy into a new variable first, which is exactly what i := i did.
          
      
          How Go 1.22 loops work
          
      
          The specification now says that in a three-part for loop "each iteration has its own separate declared variable". The first lap's variable is set by the init statement; each later lap's variable starts as a copy of the previous one's final value, and then the post statement (i++) runs on it. If no closure or pointer captures the variable, the Compiler keeps using one machine register and there's no cost. The rule is chosen per file from the module's go line, and a //go:build go1.22 line can opt a single file in. The Go team's blog post "Fixing For Loops in Go 1.22" tells the story, including that Google forced the new rule in its own builds for months before release without production problems.
          
      
          Method values copy the receiver early
          
      
          ring := b.Ring evaluates b right then. With a value receiver, the method value stores a copy; with a pointer receiver, it stores &b. A method expression, Bell.Ring, is different: it's an ordinary function whose first parameter is the receiver, func(Bell).
          
      
          Variadic parameters are slices
          
      
          func sum(nums ...int) has type func(...int) int, and inside it nums is a []int. Loose arguments are packed into a new slice (sometimes on the stack, when it can't escape). sum(s...) passes s unchanged, with no copy: same pointer, length and capacity, which is why panel 35's double could change a. If s is nil, nums is nil too; with no arguments at all, nums is also nil (length 0 either way).
          
      
          Why the stack can grow so big
          
      
          Each goroutine starts with a small stack, a few kilobytes. When a call needs more room, the runtime allocates a bigger stack, twice the size, and copies the frames across (this is why Go never lets you keep the address of a stack slot outside Go's control). The maximum is 1 GB on 64-bit systems, which is what the stack exceeds 1000000000-byte limit line reports. Go does not promise to turn recursive calls in tail position into loops ("tail-call optimisation"), so very deep recursion uses real memory. For depths in the millions, write a loop.
          
      
          Functions can't be compared
          
      
          Function values may only be compared with nil. f == g is a compile error, so functions can't be map keys either (chapter 12's rule: keys must be comparable).
          
      
          A closure that calls itself
          
      
          A function literal can't use its own name in its body while the name is still being declared. Declare the variable first, then assign: var fib func(int) int on one line, then fib = func(n int) int { if n < 2 { return n }; return fib(n-1) + fib(n-2) }. The closure captures the variable fib, which holds the closure by the time it runs.
          
    
          
  
          

  
          
    In real programs: where function values, closures and variadics show up
    
          
      
            
        
          • The standard library's "Func" family. slices.SortFunc, slices.IndexFunc, slices.ContainsFunc, slices.DeleteFunc, strings.FieldsFunc, strings.Map and strings.IndexFunc all take a rule as an argument. A name ending in Func means "bring your own rule".
            • 
        
          • Older sorting code. Before the slices package (Go 1.21), people wrote sort.Slice(s, func(i, j int) bool { return s[i].Age < s[j].Age }): indexes and a "less than?" answer. You'll see both; new code uses slices.SortFunc.
            • 
        
          • Web servers (chapter 26). http.HandleFunc("/hello", func(w http.ResponseWriter, r *http.Request) { … }) hands the server a machine to run for each request. "Middleware" are functions that take a handler and return a new handler wrapped around it, closures all the way down.
            • 
        
          • Tests (chapter 23). t.Run("empty input", func(t *testing.T) { … }) runs a function literal as a sub-test; table-driven tests often loop over cases and capture each one, which is safe since Go 1.22.
            • 
        
          • Walking folders. filepath.WalkDir(root, fn) calls your function once for every file and folder.
            • 
        
          • Do this once, later. defer func() { … }() (chapter 14), sync.Once.Do(f) and goroutines started with go func() { … }() (chapter 24) all take function literals.
            • 
        
          • Functional options are everywhere in Go libraries for servers, clients and database drivers, often with names like WithTimeout or WithLogger. Some return error from the option so a bad setting can be reported.
            • 
        
          • Variadic APIs. fmt.Println, fmt.Printf(format string, a ...any), append(s, items...), errors.Join(errs ...error), slices.Concat(slices ...S), filepath.Join(elem ...string) and log/slog's key-value arguments.
            • 
        
          • Recursion is the natural tool for anything shaped like a tree: folders inside folders, JSON inside JSON, menus with sub-menus, and many search and sorting algorithms.
            • 
      
          
    
          
  
          

  
          
    Common wrong ideas
    
          
      
            
        
          • "apply(nums, double()) passes double." The brackets run it. Pass the machine itself: double.
            • 
        
          • "A closure copies the variables it uses." It shares them. A change made after the closure was built is visible inside it, and a change made inside it is visible outside.
            • 
        
          • "When a function returns, all its variables are gone." Not if a closure captured them: panel 12's n lived on.
            • 
        
          • "Two closures from the same maker share a backpack." Only if they were made in the same call (panel 13). Each call makes fresh variables (panel 11).
            • 
        
          • "The loop-variable bug still exists." Not in modules that say go 1.22 or later. It does still exist in older modules, and old tutorials (and some books) still warn about it.
            • 
        
          • "I installed a new Go, so I get the new loop rules." The go.mod go line decides, not the installed version.
            • 
        
          • "A comparison function returns true or false." In sort.Slice, yes. In slices.SortFunc, it returns an int: negative, zero or positive.
            • 
        
          • "SortFunc keeps equal elements in their original order." It doesn't promise to. Use slices.SortStableFunc, or break ties with cmp.Or.
            • 
        
          • "Recursion is slow and should always be avoided." For tree-shaped problems it's often the clearest code, and a call is cheap. Avoid it when the depth could be huge.
            • 
        
          • "A variadic function copies my slice." Not with s...: it gets your slice. It does build a new one for loose arguments.
            • 
        
          • "I can mix loose values and a spread slice." sum(1, s...) doesn't compile. The spread slice must be the whole plate.
            • 
        
          • "A variadic parameter can go anywhere." Only the last parameter can be variadic, and there can be only one.
            • 
        
          • "Functional options are always better than an options struct." They're more flexible, but an options struct is simpler and perfectly fine when zero values make good "not set" markers.

    Words from this chapter
    
          
      
          
        
          function value
          A function used as a value: stored in a variable, passed, returned. double without brackets.
          
        
          function type
          The shape of a function, what goes in and what comes out: func(int) int.
          
        
          anonymous function (function literal)
          A function written as an expression, with no name: func(n int) int { return n + 10 }.
          
        
          higher-order function
          A function that takes or returns other functions, like apply or slices.SortFunc.
          
        
          closure
          A function value together with the variables it captured from the code around it: a machine with a backpack.
          
        
          capture
          When a function literal uses a variable from outside it. Go captures the variable itself, so changes are shared.
          
        
          generator
          A function that hands out the next value each time it's called, like a closure counter.
          
        
          method value
          x.M without brackets: a function with the receiver already bound.
          
        
          method expression
          T.M: the method as an ordinary function whose first parameter is the receiver.
          
        
          instantiation
          Picking the type for a generic function: Id[int]. Needed before it can be stored or passed.
          
        
          per-iteration loop variable
          Since Go 1.22 (by go line), each lap of a for loop gets its own fresh variable.
          
        
          comparison function
          A function func(a, b T) int returning negative, zero or positive to say which of a and b goes first.
          
        
          cmp.Compare, cmp.Or
          Compare two ordered values (-1, 0, +1); return the first non-zero of several values.
          
        
          stable sort
          A sort that keeps equal elements in their original order: slices.SortStableFunc.
          
        
          recursion
          A function calling itself on a smaller version of the problem.
          
        
          base case
          The smallest case, answered without another recursive call: the floor.
          
        
          recursive case
          The step that calls the function again on a smaller problem.
          
        
          call stack
          The pile of frames for calls that haven't finished yet; the newest is on top.
          
        
          stack overflow
          The stack hit its size limit, usually because recursion never reached a base case. A fatal error in Go.
          
        
          variadic function
          A function whose last parameter, ...T, takes any number of values, received as a []T.
          
        
          spread (s...)
          Passing an existing slice as a variadic parameter's whole plate. No copy is made.
          
        
          options struct
          One struct parameter with a field per setting; empty fields get defaults.
          
        
          functional options
          Settings passed as closures (WithSize("large")) that change a default value, taken by a variadic parameter.

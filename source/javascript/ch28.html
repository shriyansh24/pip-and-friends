Kit says: In Chapter 15 we put on our first show: a page, some search parties, a few doorbells. Tonight I'm giving you the backstage tour: how the set is built, how cues really travel, what's in the cupboard, and how letters come and go.

The whole chapter on one map. Keep it in your head: every new word today belongs to one of these four rooms.

  • Stage set = the DOM. The tree of element objects the browser builds from the HTML. Part 1 walks around it, reads its labels and measures it.
  • Cues = events. A click, a key, a form being sent. Part 2 shows that a cue travels down the tree to the actor and then back up, and how to send your own cues.
  • Props cupboard = storage. localStorage survives closing the browser; it only holds strings. Part 4.
  • Mail room = data on the wire. Only text travels between computers, so objects are written as JSON letters (Part 5) and carried by fetch (Part 6).

Each element wears two sets of labels. Attributes are what the HTML said, as text. Properties are keys on the live JavaScript object. Often they mirror each other; sometimes they really don't. The test script typed Ada into the box, ticked VIP and clicked Show.

    attrs.html
    

    

    
    
      
  1. href: the attribute is exactly what was written, tickets.html. The property is the full address the browser would really visit, worked out from the page's own address: http://theater.test/tickets.html.
    2. 
      
  2. value: the attribute is the starting value from the HTML (guest), and it never follows the typing. The property is what's in the box now (Ada). Even setAttribute("value", …) later doesn't change what the visitor typed.
    3. 
      
  3. checked: the attribute was never written, so getAttribute gives null; the property is the live tick, a real boolean true.
    4. 
      
  4. Rule of thumb: to read or change what's happening now, use the property. Use attributes for things that only exist as attributes: aria-*, data-* (next panel) and custom ones.

Which colour is this seat, really? element.style only knows the styles written on the element itself, in its style="…" attribute. To ask what the browser actually uses, after every stylesheet has had its say, ask for the computed style.

    computed.html
    

    

    
    
      
  1. seat.style.color is the empty string "": the red comes from the <style> sheet, not from the element's own style attribute. The gold background was written on the element, so style.backgroundColor knows it.

  2. getComputedStyle(seat) gives the final answer, in the browser's own units: colours as rgb(…), even the named colour gold, and sizes in px.
    3. 
      
  3. The computed-style object is live: after the class gone was added, the same look object reports display now: none.

The browser window here is 800 by 600 pixels; the curtain sits 900 pixels down a tall page.

PART 2 · CUES GO DOWN, THEN UPCapture and bubble, stopPropagation, delegation with closest, custom cues, keys and pointers


  

    8
    
Chapter 15 said a click "bubbles up" from the clicked element. That was the second half of the journey. Every cue first travels down from the top of the theatre to the actor (the capture phase), lands on the actor (the target phase), and then travels back up (the bubble phase).

    

    
    
      
  • Ordinary listeners (addEventListener("click", fn)) hear the cue on its way up. That's all of Chapter 15.
    • 
      
  • Capturing listeners (addEventListener("click", fn, { capture: true })) hear it on its way down, before the target does.
    • 
      
  • event.eventPhase says where the cue is: 1 capturing, 2 at the target, 3 bubbling.

Chapter 15's delegation asked e.target.matches("li"). Real buttons often have an icon or a bold word inside, and then the target is the icon, not the button. The lighting desk has one listener; each button names its cue in a data-cue label. The test script clicked the Lights icon, the middle of the Curtain button, and the Thunder icon.

    delegate_closest.html

    2. 
      
  2. e.target.closest("button[data-cue]") climbs from wherever the click landed to the button that holds it. It works for the icon, the words, or anything you add inside later. If the click landed outside every button, it gives null and line 18 returns.

The browser fires clicks and key presses. You can fire your own cues too, with your own names and your own details: "a seat was taken". Other parts of the page listen for them like any other event, without knowing who sent them. The test script clicked "Take F7", then "Take F8 quietly".

    custom.html
    

    

    
    
      
  1. new CustomEvent(name, options) makes the cue. detail carries any data you like; listeners read it as e.detail.
    2. 
      
  2. element.dispatchEvent(cue) sends it, starting at that element. With bubbles: true it travels up exactly like a click, so the chart heard it.
    3. 
      
  3. It's synchronous: look at the order. chart heard printed between "before" and "after". dispatchEvent runs every listener right away and only then returns. One cue at a time, no waiting.
    4. 
      
  4. Custom events don't bubble unless you ask. The quiet F8 cue was dispatched on the button without bubbles: true, so the chart above it heard nothing.

    13
    
Two more kinds of cue. Keyboard events tell you which key; pointer events cover mouse, pen and touch with one set of names. The test script pressed a, Shift+A and Enter in the box, then clicked Go.

    keys.html
    

    

    
    
      
  1. e.key is the character the key makes: "a", and "A" with Shift held. Special keys have names: "Shift", "Enter", "Escape", "ArrowLeft".
    2. 
      
  2. e.code is the physical key, whatever it types: both presses were KeyA. On a French keyboard the key in that spot types "q" but is still KeyA. Use key for text and shortcuts like "press Escape", code for game controls like WASD.
    3. 
      
  3. Holding Shift fires its own keydown first ("Shift", ShiftLeft), and e.shiftKey is true for every key pressed while it's down.
    4. 
      
  4. One mouse click is five cues, in this order: pointerdown, mousedown, pointerup, mouseup, click. In current Chromium, click itself is a PointerEvent. For "the user activated this", listen for click: keyboards fire it too (Chapter 15). Use pointer events for drawing and dragging.

    2.

HTML can check a form before it's sent: required, type="email", min, max and pattern. This is constraint validation, and JavaScript can listen in. The test script typed ada as the email and clicked Book; then filled the form in properly and clicked Book again.

    validate.html
    

    

    
    
      
  1. The first click sent nothing. The browser checked each field, fired an invalid event on every one that failed, and never fired submit. A visitor would also see a little message bubble next to the first bad field.
    2. 
      
  2. validationMessage is that message. The wording is Chromium's (in English, because the browser's language was set to en-US). Firefox and Safari word it differently, so never compare it to a fixed string.

  3. The second click passed, so submit fired, and form.checkValidity() (run the checks, answer true or false) said true. Each field also has a validity object with one flag per rule, such as valueMissing, typeMismatch and rangeOverflow.

  4. Browser checks are a convenience, not security. Anyone can switch them off or send data without your page. The server must check everything again.

    17
    
A screen redraws itself many times a second, usually 60. Each redraw is a frame. requestAnimationFrame(fn) means "call fn just before you draw the next frame". Call it again inside fn, and you get one small step per frame: an animation.

    raf.html
    

    

    
    
      
  1. The first line printed first: requestAnimationFrame only books a call, like a timer. The script finishes, then the browser calls step before each of the next four frames.
    2. 
      
  2. Why not setInterval? rAF lines your changes up with the screen's own rhythm, so movement is smooth, and it pauses automatically in a hidden tab, saving battery.
    3. 
      
  3. Real animations use the time, not the frame count. rAF hands step a timestamp; moving "25% per 100 ms" instead of "25% per frame" gives the same speed on a 60-frame and a 120-frame screen. This example counts frames only so that its output is the same on every run.
    4. 
    

  


  

    18
    
    
Same job, two ways: make each of 1,000 rows one pixel taller. One way reads a size and writes a size, a thousand times over. The other reads all the sizes first, then writes them all. This is one possible run: the times change on every run and every computer, but the gap is always huge.

    thrash.html
    

    

    
    
      
  1. After you change a style, the browser doesn't recalculate where everything goes straight away; it waits, so it can do it once. That recalculation is called layout.
    2. 
      
  2. But reading a size (offsetHeight, getBoundingClientRect(), getComputedStyle) needs an up-to-date answer, so after a change the browser must do layout right now. Read, write, read, write: a full layout for every row. That's layout thrashing.
    3. 
      
  3. The fix: batch the reads, then batch the writes. Both versions give the same final page (2 px rows), but only one makes the browser redo layout a thousand times.
    4. 
    

    

      
      
Kit says: It's like moving one chair, then re-measuring the whole stage, then moving the next chair. Measure everything first, then move all the chairs.

PART 4 · THE PROPS CUPBOARDlocalStorage and sessionStorage, strings only, a to-do list that survives a reload, and keeping strangers out


  

    20
    
When the visitor reloads the page, every variable is gone: the script starts from line 1 again. Things you want to keep between shows go in the props cupboard backstage: localStorage.

    

    
    
      
  • localStorage.setItem(key, value) puts a value in a labelled box; getItem(key) takes it out (or null if there's no such box); removeItem(key) and clear() empty boxes; length counts them.
    • 
      
  • It survives reloads, closing the tab and restarting the browser, until the visitor or your code clears it.
    • 
      
  • One cupboard per website (per origin: the scheme, host and port, such as http://theater.test). Another site can't open yours.
    • 
      
  • Strings only. Anything else is turned into a string on the way in. The next panel shows what that does to an object.
    •

Anything in the cupboard can be read by any script running on your page. That's why Chapter 15's warning about innerHTML matters even more now. The reviews page stores a login token, then shows two reviews written by visitors. One visitor is not friendly.

The attack: Mallory's "review" contains an image tag pointing at a picture that doesn't exist, with an onerror attribute. innerHTML builds a real <img> from it; the browser tries to load it (the red 404 line), fails, and runs the onerror code. That code read the token: stolen: SECRET-LOGIN-123. A real attacker would send it to their own server. This is cross-site scripting (XSS).

PART 5 · LETTERS IN ENVELOPESJSON in depth: indent, replacer, toJSON, reviver, dates, deep copies, big numbers and base64


  

    25
    
Now the mail room. Between two computers (or between your page and the cupboard) only text can travel: no objects, no functions, no dates. So you write the object down as a letter, send the letter, and the other side rebuilds an object from it. That letter-writing language is JSON (JavaScript Object Notation).

    

    
    
      
  • JSON looks like JavaScript but is stricter: keys always in double quotes, strings in double quotes, no trailing commas, no comments, no undefined, no functions.
    • 
      
  • It holds six kinds of thing: objects, arrays, strings, numbers, true/false and null. Anything else must be changed into one of these on the way out, and changed back on the way in.
    • 
    

  


  

    26
    
From here on, the programs run in Node again, in a terminal. JSON.stringify(value, replacer, indent) has two optional extra arguments that most people never meet.

    stringify.js

    Under the hood: an event's path, rendering frames, storage and the fetch body
    
      
      
      How the browser plans an event's journey
      
      
      When you click, the browser finds the deepest element under the pointer (the target) and, before any listener runs, works out the path from window down to it. That path is fixed for this event: if a listener removes an element from the page halfway through, the event still visits the rest of the planned path. It then walks the path down, calling capturing listeners (phase 1), calls the target's listeners (phase 2), and walks back up calling bubbling listeners (phase 3). At the target, current browsers run capturing listeners before non-capturing ones (in Part 2's trace the aisle's capturing listener was also added first, so both rules agree there). event.composedPath() returns the planned path as an array if you want to see it.
      
      
      stopPropagation() sets a flag that stops the walk after the current element; stopImmediatePropagation() also skips the remaining listeners on the current element. Neither cancels the browser's default action: that's preventDefault(). A few events don't bubble at all (focus, blur, mouseenter, load on elements); their bubbling cousins focusin and focusout exist for delegation.
      
      
      Custom events and dispatchEvent
      
      
      dispatchEvent is an ordinary synchronous function call that happens to run listeners: it returns only after every listener on the path has run, and its return value is false if a listener called preventDefault() on a cue created with cancelable: true. A custom cue's name can be any string; using a dash (seat-taken) keeps it from ever clashing with a future built-in event.
      
      
      One frame in the browser
      
      
      Between two screen refreshes, the browser roughly does this: run tasks (such as an event handler or a timer), run microtasks (promise callbacks), run requestAnimationFrame callbacks, recalculate styles, do layout (work out every box's size and position), then paint. Changing a style only marks the layout as out of date. Reading a size such as offsetHeight forces the browser to bring it up to date immediately, which is called a forced synchronous layout. Panel 18's slow version forced one per row. DevTools' Performance panel shows them as purple "Layout" bars with a warning triangle.
      
      
      Where storage lives
      
      
      localStorage is kept on disk by the browser, separately for each origin (scheme + host + port, so http://theater.test and https://theater.test have different cupboards). Reads and writes are synchronous: the page waits while they happen, which is fine for small values and bad for big ones. When another tab of the same site changes localStorage, your page receives a storage event, which lets two open tabs keep in sync. Storing too much throws a QuotaExceededError. For large or structured data, browsers offer IndexedDB, which is asynchronous (beyond this book).
      
      
      Why a body can only be read once
      
      
      A response's body is a stream: the bytes arrive in chunks, and they are handed to whoever reads them, then let go so a huge download doesn't fill your memory. res.json(), res.text(), res.blob() and res.arrayBuffer() each read the whole stream to its end. After that, bodyUsed is true and there's nothing left to read. res.clone() splits the stream into two before reading. In Node, fetch is built on a library called undici, which is why its name appears in the stack traces of Part 6.
      
      
      CORS in a little more detail
      
      
      For "simple" requests (a GET, or a POST with a form-style body), the browser sends the request with an Origin header and then checks the answer for Access-Control-Allow-Origin. For anything else, such as a POST with Content-Type: application/json or a custom header, the browser first sends a preflight: an OPTIONS request asking "may I?". Only if the server says yes does the real request go. That's why adding headers can suddenly make a working request fail with a CORS error.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • closest is everywhere. Delegated handlers in large apps almost always start with const item = e.target.closest("[data-id]"), then read item.dataset.id.
        • 
        
      • Custom events are how web components and many libraries announce things ("value-changed", "dialog-closed") without knowing who's listening.
        • 
        
      • "Click outside to close" menus, dialogs and dropdowns all listen on document. Analytics tools do too. That's why teams treat stopPropagation with suspicion in code review.
        • 
        
      • Forms are usually checked twice: with HTML attributes and a little JavaScript for quick feedback in the browser, and again on the server, which is the only check that counts.
        • 
        
      • Saved state: drafts, shopping carts, "dark mode" and dismissed banners usually live in localStorage as JSON. Logins usually use cookies that page scripts can't read (marked HttpOnly), precisely because of XSS.
        • 
        
      • API clients: most apps wrap fetch in one helper like Panel 38's getJSON, adding the base address, a timeout, the stamp check, retries for 5xx, and logging. Libraries such as ky and axios are ready-made versions of that helper.
        • 
        
      • Big ids (from databases, payment systems and social networks) are often sent as JSON strings precisely because of the precision problem in Panel 33. Reading the source text is the newer, exact alternative.
        • 
        
      • Animations are mostly done with CSS transitions today; requestAnimationFrame is used for games, canvas drawing, and anything that has to follow the pointer.

    Common wrong ideas
    
      
      
        
        
      • "Events only bubble up." They go down first. Capturing listeners hear that half (Panel 9).
        • 
        
      • "stopPropagation only affects my own code." It hides the event from every listener higher up, including menus and analytics (Panel 10).
        • 
        
      • "closest only looks at ancestors." It checks the element itself first.
        • 
        
      • "getAttribute("value") is what the visitor typed." It's the starting value. Use .value.
        • 
        
      • "element.style.color tells me the colour." Only colours written on the element itself. Use getComputedStyle.
        • 
        
      • "dispatchEvent is asynchronous, like a timer." It runs every listener before returning.
        • 
        
      • "Custom events bubble like clicks." Only with bubbles: true.
        • 
        
      • "A form with required is safe." Browser checks can be skipped. Check on the server.
        • 
        
      • "async is the modern defer." They differ: async runs in arrival order, defer in page order after parsing.
        • 
        
      • "localStorage can store objects." Strings only. Objects become "[object Object]".
        • 
        
      • "localStorage is private." Every script on your page can read it, including injected ones.
        • 
        
      • "JSON is JavaScript." It's a stricter text format: double quotes only, no trailing commas, no comments, no undefined.
        • 
        
      • "JSON.parse(JSON.stringify(x)) is a perfect copy." Dates become strings, undefined and functions vanish, Maps become {}. Use structuredClone.
        • 
        
      • "fetch throws on a 404." It fulfills. Only a network failure rejects (Panel 36).
        • 
        
      • "I can read the body again later." Once read, it's used up.
        • 
        
      • "A CORS error means my code is wrong." It means the other server didn't give permission. Only that server can fix it.
        • 
        
      • "fetch turns my object into JSON." You must JSON.stringify it yourself, and add the content-type header.

    Version notes: Chromium, Node 26 and Node 22
    
      
      
      Browsers. All browser pages ran in one engine, Chromium 153, so the console wording is Chromium's: the CORS message, Failed to fetch and the form validation messages.     Words from this chapter
    
      
      
      
        
      parentElement, children, nextElementSibling
      An element's parent, its element children, and its next element sibling.
      
        
      closest(selector)
      The nearest element, starting with itself and going up, that matches the selector; or null.
      
        
      attribute / property
      What the HTML says, as text / a key on the live element object.
      
        
      dataset
      An element's data-* attributes, as string properties in camelCase.
      
        
      computed style
      The final value of every CSS property after all stylesheets apply, from getComputedStyle.
      
        
      viewport
      The visible part of the page in the window.
      
        
      getBoundingClientRect()
      An element's box (top, left, width, height…) in pixels, measured from the viewport's top-left corner.
      
        
      capture / target / bubble phase
      The event travelling down to the target, at the target, and back up. eventPhase is 1, 2 or 3.
      
        
      stopPropagation()
      Stops the event visiting any further elements.
      
        
      custom event
      An event you create with new CustomEvent(name, { detail, bubbles }) and send with dispatchEvent.
      
        
      key / code
      The character or name a key produces / the physical key's position.
      
        
      pointer events
      pointerdown, pointerup, pointermove…: one set of events for mouse, pen and touch.
      
        
      FormData
      All of a form's named fields as key/value entries; can be sent with fetch.
      
        
      constraint validation
      The browser's built-in form checks (required, type, min, pattern), with checkValidity(), validity and the invalid event.
      
        
      defer / async
      Run after the page is read, in order / run as soon as downloaded, in any order.
      
        
      DOMContentLoaded / load
      The page is read and deferred scripts have run / everything, images included, has finished.
      
        
      frame
      One redraw of the screen, usually 60 per second.
      
        
      requestAnimationFrame
      Asks the browser to call a function just before the next frame.
      
        
      layout / layout thrashing
      Working out where every box goes / forcing it over and over by mixing reads and writes.
      
        
      screen reader
      Software that reads the page aloud or in braille.
      
        
      aria-expanded
      Tells assistive technology whether the thing a button controls is open ("true") or closed ("false").
      
        
      focus management
      Moving keyboard focus deliberately, into a dialog when it opens and back when it closes.
      
        
      localStorage / sessionStorage
      String storage for one website that survives restarts / for one tab, emptied when it closes.
      
        
      origin
      Scheme, host and port of an address, like http://theater.test. Storage and CORS work per origin.
      
        
      XSS (cross-site scripting)
      A stranger's text running as code on your page, for example through innerHTML.
      
        
      JSON
      JavaScript Object Notation: a strict text format for objects, arrays, strings, numbers, booleans and null.
      
        
      replacer / reviver
      A function (or allow-list) that shapes what JSON.stringify writes / a function that transforms each value JSON.parse reads.
      
        
      toJSON()
      A method that decides how its object is written as JSON.
      
        
      structuredClone
      A built-in deep copy that keeps dates, Maps and Sets but refuses functions.
      
        
      source text access / JSON.rawJSON
      A reviver's context.source (the original text of a value) / a way to write raw JSON text, for exact big numbers. ES2026.
      
        
      base64
      A way to write any bytes with 64 safe characters. toBase64 / fromBase64 on Uint8Array, ES2026.
      
        
      Response
      The envelope fetch gives you: status, statusText, ok, headers and a body you read once.
      
        
      status code
      The number on the envelope: 2xx success, 3xx redirect, 4xx your request was wrong (404 not found), 5xx the server had a problem.
      
        
      header
      A label on a request or response, such as content-type: application/json.
      
        
      method
      What a request wants: GET to fetch, POST to send, and others.
      
        
      URL / URLSearchParams
      Objects that build, encode and read web addresses and their ?key=value parts.
      
        
      AbortController / AbortSignal.timeout
      A way to cancel a fetch by hand / a signal that cancels it after a time.
      
        
      retry with backoff
      Trying again after a failure, waiting longer each time, up to a limit.
      
        
      CORS
      Cross-Origin Resource Sharing: the browser lets a page read another origin's answer only if that answer carries permission headers.

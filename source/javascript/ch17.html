CHAPTER 17 · INTERMEDIATE

BACKPACKS AND VENTRILOQUISTS

Picture: Kit, the stage manager in a pink hoodie and headset, waves hello. On one side sits a yellow backpack with a tag that says tickets, and a label sticking out of its top that says count = 0. On the other side, a ventriloquist's puppet in a blue jacket and red bow tie holds up a placard that says me = ?

Two mysteries are left over from earlier chapters. How does a callback still know the names from where it was written, long after that code has finished? And who exactly is this? Today you solve both. Every function carries a backpack of the variables around the place it was born, and that one idea explains counters, private data, the famous 3 3 3 loop, caches and modules. Then a ventriloquist shows the five rules that decide who "me" is, and the tools call, apply and bind that put words in a function's mouth. About 130 minutes, with 28 hands-on checks.

PART 1 · EVERY FUNCTION CARRIES A BACKPACKFunctions remember where they were born

1

At the end of Chapter 16, Kit noticed something odd. An interval callback kept reading count every 100 ms, long after the script that made count had finished.

Kit says: In Chapter 8 we learned that a function's variables live in its own room, and the room is cleared when the function ends.

Kit says: So how can a little function, made inside a bigger one, still use the bigger one's variables after the bigger one has finished? Where does it keep them?

Picture: Kit shrugs, puzzled. A burst says HMM?

2

Here is the puzzle in its smallest form. You saw this kind of greeter machine in Chapter 7. Now we open it up.

backpack.js 

    

    
    
      
  1. Line 8 calls makeGreeter("Hello"). Inside, greeting is "Hello" and mark is "!". Line 3 makes a new little function and hands it back. Then makeGreeter ends.
    2. 
      
  2. Line 10 calls that little function, now called hello, with "Ada". Line 4 needs greeting and mark. Neither is hello's own variable, and the call that made them is over. Yet the output is Hello, Ada!.
    3. 
      
  3. Lines 11 and 12: howdy remembers "Howdy", and hello still remembers "Hello". Each little function remembers its own call of makeGreeter.
    4. 
    

  


  

    3
    
The answer: when a function is born, it packs a backpack. The backpack holds the room it was born in, with every variable in that room and in the rooms around it. Wherever the function goes, the backpack goes too.

    

      
      
      
    

    
Picture: three boxes. First, a function machine labelled hello. Second, a backpack tagged hello with two labels sticking out: greeting = "Hello" and mark = "!". Third, a backpack tagged howdy with greeting = "Howdy" and mark = "!".

    
Programmers call a function together with its backpack a closure: the function "closes over" the variables around it. The backpack itself is called the function's lexical environment. "Lexical" means "decided by where it is written in the text". In JavaScript, every function carries one.

    

      
      
Kit says: So the room isn't cleared when makeGreeter ends, as long as somebody still carries it in a backpack. My callback in Chapter 16 had count in its backpack all along!

        ✗ VAR: ONE ROOMfor (var i …)
        var ignores the loop's braces and lives in the room around the loop. Every closure made in the loop packs that same room, and reads i later, when it has its final value.

        A backpack can be heavy. JavaScript frees memory automatically with a garbage collector: a cleaner that throws away anything no living code can reach any more. A room is reachable as long as some reachable function carries it.
        
    big.js
    
        
    
        
    
        
      
      
    
        
    
        Picture: first, a yellow backpack tagged countSeats, with a label seats: a million. Second, the same backpack drawn grey and dashed, its tag saying NO OWNER.
        
    
        A long-lived closure, such as a handler or interval nobody removes, keeps its whole room alive, including big things it may not even need. That's a memory leak. Exactly when the cleaner runs is up to the engine and can't be seen from ordinary code, so this book describes it rather than printing it.

        PART 5 · THE VENTRILOQUISTWho is "me"? The rules for this, and call, apply and bind
        

  
        
    24
    
    
        Chapter 11 taught one rule for this, the word "me": whoever is before the dot. Tonight a ventriloquist is in the show. A ventriloquist works a puppet and speaks for it, and decides who the puppet is.
        
    
        
      
      
        
        
        Kit says: A function using this is a puppet. It says "my name is this.name", but it has no idea who "me" is until somebody works it.
        
        
        Kit says: Backpacks are packed where a function is born. this is the opposite: it's chosen fresh at every call, by whoever makes the call.
        
      
        
    
        
    
        
      
      
      
    
        
    
        Picture: Kit points, excited. Below, three copies of the same puppet. The first holds a placard saying me = ?, with its mouth shut. The second says me = Ada, mouth open. The third says me = Bo, mouth open. A burst says WHO, ME?
        
    
        BACKPACKS AT BIRTH, "ME" AT EVERY CALL
        
  
        

  
        
    25
    
        Five rules decide this. Check them in this order and stop at the first that fits.
        
    
        
      
        1
        ARROW
        () => this
        An arrow has no this of its own. It borrows the this of the place it was born, like a backpack. Nothing can change it.
        
      
        2
        NEW
        new Puppet()
        A brand-new empty object is made, and this is that object.
        
      
        3
        EXPLICIT
        f.call(x) f.apply(x) f.bind(x)
        The ventriloquist names "me" outright: this is x.
        
      
        4
        IMPLICIT
        obj.f()
        The object before the dot (Chapter 11).
        
      
        5
        DEFAULT
        f()
        Nobody: undefined in strict code, which includes every module. In old "sloppy" code, the global object.
        
    
        
    
        The names "default", "implicit" (implied by the dot), "explicit" (stated outright) and "new" binding are what you'll see in books and talks. To bind this means to decide what it refers to.
        
  
        

  
        
    26
    
        Rule 5 first, because it has two versions. You have met strict mode in earlier chapters: the modern, safer rules that every module follows automatically. Older code without it is nicknamed sloppy mode. A .cjs file is CommonJS, which is sloppy unless it says "use strict".
        
    
        
      
        default_strict.js
        
      
        default_sloppy.cjs
        
    
        
    
          
      
        1. Strict (the module): a plain call has nobody before the dot, so this is undefined. Line 6 shows the module's own top-level this is undefined too.
          2. 
      
        2. Sloppy (the .cjs file): JavaScript quietly swaps in the global object, the object that holds built-ins like setTimeout. Its standard name everywhere is globalThis (in browsers it's also called window). Line 9 proves it: true.
          3. 
      
        3. Line 5 of the .cjs file turns strict mode on for just that function, and the swap stops: undefined.
          4. 
    
        
  
        

  
        
    27
    
        Why does strict mode refuse to swap in the global object? Watch what sloppy mode lets slip through. The same three lines, run both ways:
        
    
        
      
        sloppy_leak.cjs
        
      
        strict_leak.js
        
    
        
    
          
      
        1. Sloppy: setName("Ada") has no object, so this becomes the global object, and line 2 quietly writes a global variable called name. No error, a hidden mess.
          2. 
      
        2. Strict: this is undefined, and you can't put a drawer on undefined: TypeError: Cannot set properties of undefined (setting 'name'), at line 2, called from line 5. A loud error at the right line beats a silent leak.
          3. 
    
        
    
        
      
      
        Kit says: Whenever you see "Cannot read" or "Cannot set properties of undefined" inside a function that uses this, suspect a call with nobody before the dot.
        
    
        
  
        

  
        
  

  
        
    28
    
        Rule 3: the ventriloquist chooses "me" directly. Every function has three built-in methods for this.
        
    
        
      
        CALL
        intro.call(ada, "Hi", "!")
        Call it now, with this = ada, then the arguments one by one, in a list.
        
      
        APPLY
        intro.apply(ada, ["Hi", "!"])
        The same, but the arguments come in an array. Apply, array.
        
      
        BIND
        const f = intro.bind(ada)
        Doesn't call it. Makes a new function whose "me" is glued to ada for good. Call it later.
        
    
        
    
        Picture: three boxes, each with the puppet holding a placard that says me = ada. In the call and apply boxes the puppet is talking; in the bind box it waits with its mouth shut.

        What you learned in Chapter 17
        
    
          
      
        • EVERY FUNCTION CARRIES A BACKPACKA function remembers the room it was born in, with all its variables, even after the code that made them has finished. A function plus its backpack is a closure. The backpack holds the live variables, not copies, and a room lives as long as some reachable function carries it (then the garbage collector may free it).
          • 
      
        • WHERE IT WAS BORN, NOT WHERE IT IS CALLEDNames are looked up in the function's own room, then outward through the rooms where it was written (lexical scope). A caller's variables are never visible. Outsiders get ReferenceError: … is not defined.
          • 
      
        • LET GIVES EVERY LAP ITS OWN ROOMvar loops share one variable, so closures made in them all see its final value (3 3 3); let loops make a room per lap. Stale closures read a different variable from the one you changed.
          • 
      
        • BACKPACKS AT BIRTH, "ME" AT EVERY CALLClosures give factories, private state, partial application, memo caches, once and the IIFE module pattern. this is chosen at each call: arrow (borrowed), new (fresh object), explicit (call, apply, bind, or a host such as Node's timer with its Timeout), the object before the dot, or nobody (undefined in strict code, globalThis in sloppy code).
          • 
      
        • BIND GLUES "ME" FOR GOOD. THE FIRST GLUE WINS.call takes a list, apply an array, and both call now; bind returns a new function whose this can't be changed again, and can glue arguments too. A detached method crashes with Cannot read properties of undefined (reading 'name'): fix it with an arrow wrapper, bind, or an arrow class field. Arrows ignore call/bind and can't be used with new.

    Under the hood: environments, contexts and how this is set
    
        
      
        Environment records
        
      
        The language standard (ECMAScript) describes scope with environment records: the comic's rooms. Every call of a function, every block with let or const, every module and the global scope gets one. Each record has a link to its outer record, and name lookup follows those links outward until it finds the name, or reaches the end and throws a ReferenceError.
        
      
        [[Environment]]: the backpack
        
      
        When a function object is created, the engine stores the current environment record in a hidden internal slot the standard calls [[Environment]]. When the function is later called, its new record's outer link is set to that stored record, not to the caller's. That single rule is lexical scope, and it is why every JavaScript function is a closure (the only exception is a function made with new Function("…"), whose outer link is always the global scope).
        
      
        What V8 actually keeps
        
      
        Engines don't really keep every variable of every room. V8, the engine in Node and Chrome, works out ahead of time which variables any inner function uses, and keeps only those in a heap-allocated context; variables nobody captures stay on the fast stack and vanish when the call ends. All closures created in the same room share one context, so if one closure uses a big array, every sibling closure keeps it alive too. A debugger paused inside a closure may therefore show an outer variable as unavailable: it was optimised away because the closure never used it.
        
      
        Per-iteration bindings
        
      
        For for (let i = …; …; …), the standard copies the loop variables into a fresh environment record before each lap's update step ("CreatePerIterationEnvironment"). Closures made in a lap therefore keep that lap's record. for…of and for…in with let or const also get a fresh binding every lap. var lives in the function's (or module's) record, so there's only one.
        
      
        How this is decided
        
      
        Every regular function call passes a thisArgument. obj.f() passes obj (the standard calls the obj.f part a Reference, which remembers its base object; that's what's lost when you copy obj.f into a variable). A plain f() passes undefined. call/apply pass their first argument. A bound function is a special "exotic" object that stores a target function, a bound this and bound arguments, and always calls the target with them, which is why rebinding can't change it. new creates the object first and passes it. In sloppy functions, the engine then replaces undefined or null with globalThis and wraps primitives (so this for f.call(7) is a Number object); strict functions get the value as-is. Arrow functions have no this binding at all, so this inside them is looked up through the environment, exactly like a variable from the backpack.
        
      
        new beats bind
        
      
        One more ranking detail the comic skips: calling a bound function with new ignores the bound this (the new object wins) but keeps the bound arguments. That's why new sits above explicit binding on the map.
        
    
        
  
        

  
        
    In real programs
    
        
      
          
        
        • Event handlers and callbacks are closures in almost every program: a click handler that remembers which item it belongs to, a fetch callback that remembers which request it was for, an interval that remembers its counter.
          • 
        
        • Private state with factories is a popular alternative to classes: createStore(), createLogger() and similar functions return objects whose methods share hidden variables. Classes now have their own private #fields too (Chapter 18).
          • 
        
        • Memoization speeds up expensive pure functions, and UI frameworks offer it built in (for example React's useMemo and memo). Real caches also need a size limit, or they become memory leaks.
          • 
        
        • once, debounce and throttle are closure wrappers found in utility libraries such as Lodash. Debounce waits until calls stop for a moment (search boxes); throttle allows at most one call per time window (scroll handlers). Both keep a timer id in their backpack.
          • 
        
        • Stale closures are among the most-asked questions about React hooks: an effect or handler created during one render keeps reading that render's values. The tools for fixing them (dependency lists, functional updates, refs) all come down to "which variable is in the backpack?"
          • 
        
        • bind in older code: before arrow functions (2015) and class fields (2022), code was full of this.handleClick = this.handleClick.bind(this) and var self = this; (saving this in an ordinary variable, so a nested function could find it in its backpack).
          • 
        
        • Memory leaks in long-running servers and single-page apps often come from closures that are never released: listeners that are never removed, intervals never cleared, caches that only grow. Browser DevTools' Memory panel and Node's --inspect heap snapshots show what keeps an object alive.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "A closure is a special kind of function you create on purpose." Every function closes over the room where it was born. "Closure" usually describes a function that is used outside that room.
          • 
        
        • "A closure takes a snapshot of the variables." It keeps the live variables (panel 6). It only looks like a snapshot when nobody changes them, or when a value was copied into a parameter (panel 16).
          • 
        
        • "Each call of the inner function gets a new copy of the outer variables." No: all calls of one closure share its backpack (the counter). Each call of the outer function makes a new room.
          • 
        
        • "The 3 3 3 bug is caused by setTimeout." It's caused by var sharing one variable; closures stored in an array show the same thing (exercise after panel 14).
          • 
        
        • "Closures always leak memory." A closure keeps its room only as long as the closure itself is reachable. Most are short-lived and are freed normally.
          • 
        
        • "this is the function itself" or "this is the object the function was written in." It's chosen at each call by the rules; where a regular function was written doesn't matter.
          • 
        
        • "Arrow functions have this bound to the object they're defined in." They have no this; they use the surrounding function's (or module's). An arrow written as an object property sees the code outside the object.
          • 
        
        • "bind changes the original function." It returns a new one; the original is untouched (false on line 15 of bind.js).
          • 
        
        • "I can rebind a bound function." The first binding wins forever.
          • 
        
        • "call and apply are different things." They do the same job; only the way you pass the arguments differs.
          • 
        
        • "In a callback, this is always undefined." It's whatever the caller chooses: undefined for forEach without a second argument, a Timeout for Node timers, the element for DOM listeners.

    Words from this chapter
    
        
      
        
        
        closure
        A function together with the variables from where it was born, which it can still use later, anywhere. Every JavaScript function is one.
        
        
        backpack
        The comic's picture of what a closure carries: the room it was born in, and the rooms around it.
        
        
        lexical environment
        The technical name for the backpack: the variables in scope where the function was written.
        
        
        lexical scope
        Names are found by where code is written, not where it is called.
        
        
        factory
        A function that builds and returns new objects or functions, such as makeCounter.
        
        
        private state
        Data only certain functions can reach, kept in their shared backpack.
        
        
        stale closure
        A closure that keeps reading an old value, because its backpack holds a different variable from the one being updated.
        
        
        garbage collector
        The part of the engine that frees memory no running code can reach any more.
        
        
        memory leak
        Memory kept alive by mistake, for example by a closure that is never released.
        
        
        partial application
        Filling in some of a function's arguments now and the rest later.
        
        
        memoization, cache
        Saving the answers of a function so repeated questions are answered from the cache instead of worked out again.
        
        
        once
        A wrapper that lets a function run only the first time.
        
        
        IIFE
        Immediately Invoked Function Expression: (function () { … })(), called the moment it's written.
        
        
        module pattern
        An IIFE that returns a public object while its variables stay private.
        
        
        this
        The word "me" inside a regular function, chosen at each call.
        
        
        binding (of this)
        Deciding what this refers to: default, implicit, explicit, new, or borrowed by an arrow.
        
        
        strict mode / sloppy mode
        Modern safer rules (all modules, "use strict") versus the older loose rules (plain scripts, CommonJS files).
        
        
        globalThis
        The global object, holding the built-ins, under one standard name in every host (window in browsers).
        
        
        call, apply
        Call a function now with a chosen this; call takes the arguments as a list, apply as an array.
        
        
        bind, bound function
        bind returns a new function whose this (and any leading arguments) are fixed for good.
        
        
        constructor
        A function meant to be called with new, which makes a fresh object as its this.
        
        
        arguments
        An array-like object holding every argument of a regular function call. Arrows don't have one.
        
        
        function borrowing
        Using one object's method on another object with call or apply.
        
        
        class field
        A property written directly in a class body, set on every new object (Chapter 18).
        
        
        host
        The environment running JavaScript, such as Node or a browser, which supplies extras like timers.

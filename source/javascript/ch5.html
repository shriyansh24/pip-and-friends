Yes or no, the same or not the same, and what happens when JavaScript quietly changes one kind of value into another. Meet the Doorkeeper, who decides which values count as "yes", and the Translator, who turns text into numbers (sometimes when you didn't ask). About 90 minutes, with 25 hands-on checks.

    25
    
    How Number() reads text. It is a strict reader: all or nothing.
    
    
      
      
    • THE WHOLE TEXT must be a number. One stray letter anywhere, and the answer is NaN: "08px", "px12", "ten".
      • 
      
    • SPACES AT THE ENDS are trimmed away first, so " 12 " is fine.
      • 
      
    • EMPTY TEXT IS 0. "" (or only spaces) becomes 0, not NaN. A blank form box turns into zero without a word!
      • 
      
    • NOT TEXT? true → 1, false → 0, null → 0, but undefined → NaN. (The empty frame is zero; the ghost is "no idea".)
      •

    PART 5 · BEHIND YOUR BACKImplicit conversion (coercion) with + - * /
    

  
    
    31
    
    When an operator gets two different kinds of value, it calls the Translator by itself. But the operators don't agree on which way to translate.
    
    
    
      
    
        
    
        
    PLUS PREFERS WORDS+
    
        
    If either side is a string, + turns the other side into text too, and glues. Only two numbers get added.

    Under the hood: the four algorithms behind this chapter
    
      
      
      The ECMAScript specification, the rulebook every JavaScript engine follows, defines each idea in this chapter as a small named algorithm. Knowing their names helps when you read the spec or MDN.
      
      
        
        
      • ToBoolean is the Doorkeeper. Its table returns false for exactly: the boolean false; the numbers +0, -0 and NaN; the bigint 0n; the empty string; undefined; null. Everything else, every object included, returns true. (There is one historical oddity in browsers: document.all, an old web object, pretends to be falsy. You will probably never meet it.)
        • 
        
      • ToNumber is the Translator heading for numbers. For strings it uses a grammar called StringToNumber: trim white space from both ends, then the rest must be a complete number literal (decimal, or 0x/0o/0b hex, octal or binary, or Infinity), or empty, which gives 0. Anything else is NaN. That's why Number("0x1A") is 26 but Number("12px") is NaN (lines 1 and 2 of hood.js below). parseInt and parseFloat are separate, more forgiving functions that read a prefix.
        • 
        
      • IsStrictlyEqual is ===: different types give false; numbers compare by value, with NaN unequal to everything and +0 equal to -0; strings compare character by character; objects compare by identity.
        • 
        
      • IsLooselyEqual is ==: same type means strict comparison. null and undefined are equal to each other only. Number and string: the string goes through ToNumber. A boolean is first turned into a number. An object meeting a primitive is first turned into a primitive (Chapter 19). A bigint and a number compare their mathematical values. Anything left over gives false.
        • 
      
      
      
      Why NaN isn't equal to itself
      
      
      JavaScript numbers follow IEEE 754, the international standard for floating-point arithmetic used by almost every processor. That standard says NaN compares unequal to everything, itself included, on purpose: two failed calculations (say 0/0 and Number("abc")) aren't "the same answer", so calling them equal would be misleading. That's also why x !== x is an old trick for "x is NaN"; today Number.isNaN(x) says it clearly. (The older global isNaN(x) converts first, so isNaN("abc") is true even though "abc" is a string. Prefer Number.isNaN.)
      
      hood.js
      
      
      
      
      
      Line 5 is the isNaN difference; line 7 shows x !== x being true for NaN; line 8 prints a negative zero, from the next section.
      
      
      Negative zero
      
      
      The same standard has two zeros, +0 and -0, so that tiny results can remember which side of zero they came from: -1 / Infinity is -0. === treats them as equal, String(-0) writes "0", and Object.is is the tool that tells them apart. You will rarely need to care.
      
      
      Why >= and == disagree about null
      
      
      <, >, <= and >= use a different algorithm (IsLessThan): it turns both sides into primitives and, unless both are strings, into numbers. null becomes 0 there. == never turns null into a number; it has its own null rule. Two algorithms, two answers.
      
    
      
  
      

  
      
    In real programs: forms, linters and type checkers
    
      
      
        
        
      • Everything typed is text. In a web page, input.value is always a string, even for <input type="number"> (which also offers input.valueAsNumber). In Node, process.argv (command-line arguments) and anything read from a file or a terminal are strings too. The "1020" bug starts exactly there.
        • 
        
      • Linters catch ==. ESLint's eqeqeq rule warns on every == and !=; many teams set it to allow only x == null. The use-isnan rule flags x === NaN. Both are on in many popular style guides.
        • 
        
      • Type checkers prevent mix-ups. TypeScript (Chapter 26) checks the kinds of values before a program runs, and is designed to report mix-ups like "5" - 3 or a string compared with a number. This chapter doesn't run it, so no checker output is shown here.
        • 
        
      • Validating numbers. A careful form handler checks, in order: is the text empty (text.trim() === "")? Then convert with Number(text). Then Number.isNaN? Then range checks (>= 0). Only then use it. Number.isInteger(n) checks for whole numbers.
        • 
        
      • parseInt's radix. Always pass 10. Without it, text starting with 0x is read as hexadecimal: parseInt("0x10") is 16 (line 3 of hood.js in the notebook's first page). A leading 0 is not special: parseInt("077") is 77 (line 4).
        • 
        
      • Comparing lists by contents. Since === checks identity, real programs compare item by item, or use a library's "deep equal". Node has util.isDeepStrictEqual(a, b), and its test runner offers assert.deepStrictEqual.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • ""false" is false." It's a five-letter string: truthy. Compare it: text === "true".
        • 
        
      • ""0" is falsy, like 0." Only the number 0 is on the list. The text "0" is truthy.
        • 
        
      • "An empty list is falsy." [] and {} are objects, and every object is truthy. To test for an empty list, check its length (Chapter 9).
        • 
        
      • "x === NaN checks for NaN." Always false. Use Number.isNaN(x).
        • 
        
      • "Two lists with the same items are ===." Only if they are the same list object.
        • 
        
      • "Number("") is NaN." It's 0. parseInt("", 10) is the one that gives NaN.
        • 
        
      • "parseInt rounds." It cuts: parseInt("3.99", 10) is 3.
        • 
        
      • "+ always adds." With a string on either side, it glues.
        • 
        
      • "null == 0, because null is basically zero." It's false: == has a special null rule. (But null >= 0 is true. Different rulebook.)
        • 
        
      • "== is fine if you know what you're doing." Even experts write ===, so readers don't need the rulebook to understand the code.
        • 
        
      • "Truthy means equal to true." No: "0" is truthy but "0" == true is false (true becomes 1, "0" becomes 0). Truthiness is the Doorkeeper's question; == is the rulebook's.

    Words from this chapter
    
      
      
      
        
      boolean
      The type with exactly two values, true and false.
      
        
      comparison operator
      < > <= >=: asks how two values compare and answers with a boolean.
      
        
      strict equality
      ===: true only for the same type and the same value, with no conversion. !== is its opposite.
      
        
      loose equality
      ==: converts by a rulebook first, then compares. != is its opposite.
      
        
      assignment
      Putting a value on a name with one =.
      
        
      left-hand side
      What stands left of =; it must be something a value can be put on, like a name.
      
        
      identity
      Being the very same object. === compares objects and lists by identity, not by contents.
      
        
      truthy
      A value that counts as "yes" when a boolean is needed. Every value not on the falsy list.
      
        
      falsy
      One of the eight values that count as "no": false, 0, -0, 0n, "", null, undefined, NaN.
      
        
      ! (not)
      Gives the opposite of a value's truthiness. !!x is the same as Boolean(x).
      
        
      type conversion
      Turning a value of one type into another type.
      
        
      explicit conversion
      Conversion you ask for by name: Number(x), String(x), Boolean(x).
      
        
      implicit conversion (coercion)
      Conversion JavaScript does by itself, for example when - meets a string.
      
        
      parse
      Here: to read a number out of text. parseInt reads a whole number, parseFloat a decimal one.
      
        
      integer
      A whole number, with no decimal part.
      
        
      radix
      The counting system (base) of a number written as text: 10 for everyday numbers, 2 for binary, 16 for hexadecimal.
      
        
      unary plus
      A + with one value, on its right: +x converts x to a number.
      
        
      concatenate
      To glue strings end to end, as + does with text.
      
        
      NaN
      "Not a Number": a number value meaning a calculation failed. Not equal to itself.
      
        
      Number.isNaN
      The reliable test for NaN.
      
        
      Object.is
      A "same value" test like ===, except that NaN is NaN and 0 is not -0.
      
        
      negative zero
      -0, a second zero kept by the number standard. Falsy, and === 0.
      
        
      bigint
      A type for whole numbers of any size, written with an n. Never mixed with ordinary numbers automatically.
      
        
      symbol
      A type for one-of-a-kind labels. Never glued into text automatically.
      
        
      transitive
      A rule where A = B and B = C always means A = C. == isn't.

Every layer of a program that meets an error has the same three choices.

Picture: a triage desk with a bell and a yellow TRIAGE sign. An arrow leads left to a bed with a tick, labelled TREAT: catch it here. Another arrow leads right to a staircase going up, labelled REFER UP: throw, with cause. At the far right is an exit door, and under the floor it says DISCHARGE: finally, tidy up.

TREATcatch (err) { … }

You know this error and what to do about it: show a friendly message, use a default, try again. Then carry on.

REFER UPthrow err

Not yours to fix. Pass it to the caller, the next layer up. If you add a note, keep the original attached (Part 2).

DISCHARGEfinally { … }

Treated or referred, some tidying always happens: close the file, switch off the lights, call the next patient.

    15
    
The big design question for every error: keep going, or stop?

    

      
FAIL FASTstop, loudly
For bugs and impossible states: a TypeError, a missing config file, a broken promise to yourself. Carrying on would only spread wrong data. Let it crash (or catch it at the edge, log it, exit with code 1).

      
RECOVERtreat it, carry on
For problems you expected: a user typed a bad seat, a server was busy, a file was empty. Show a message, use a default, retry. Treat only the kinds you named.

    

    
    
      
  • Catch what you can treat. Rethrow the rest, unchanged or wrapped with { cause }.
    • 
      
  • One safety net at each edge: the program's top, each request, each click.
    • 
      
  • Never an empty catch, never a catch that logs only "error".
    • 
      
  • Throw Error objects, never strings, and give your classes a name.
    • 
      
  • Put cleanup in finally (or using, panel 18).
    •

PART 3 · BUILDING A PAGERnew Promise, the three states, and settled is final


  

    20
    
Chapter 16 used pagers the kitchen made. Now Kit goes behind the counter. Every pager is in exactly one of three states.

    

      
      
→resolve(value)

      
      OR
      
→reject(error)

      
    

    
Picture: a pager saying WAIT is pending, with no value yet. An arrow labelled resolve(value) leads to a pager saying BUZZ!, fulfilled, holding a value. Or an arrow labelled reject(error) leads to a dashed pager saying SORRY, rejected, holding an error.

    
A pager that has buzzed, either way, is settled. And here's the rule that makes promises trustworthy: once settled, it never changes again. It can't buzz twice, it can't change its mind, and it can't go back to waiting.

    
SETTLED IS FINAL

  


  

    21

    3.

      PART 5 · MANY PAGERS AT ONCEPromise.all, allSettled, race and any
      

  
      
    32
    
      Kit's friends order at three stalls at once. Each gets a pager. There are four ways to wait for the whole table, and each one hands you one new pager for the group.
      
    
      
      
      ALLPromise.all(pagers)
      Waits for every pager and gives all the values, in the order you listed them. If one says SORRY, it gives up at once with that error.
      
      
      ALL SETTLEDPromise.allSettled(pagers)
      Waits for every pager, good news or bad, and gives a report for each one. Never rejects.
      
      
      RACEPromise.race(pagers)
      Settles like the first pager to settle, whether that's good news or bad.
      
      
      ANYPromise.any(pagers)
      The first good news wins; failures are ignored. Only if every pager fails does it reject, with an AggregateError.
      
    
      
    
      Picture: four cards. All: three buzzing pagers. All settled: buzzing, sorry, buzzing. Race: waiting, buzzing, waiting. Any: sorry, buzzing, waiting.

      What you learned in Chapter 24
      
    
        
      
      • TREAT IT, REFER IT UP, OR DISCHARGEGive each kind of problem a class (class ValidationError extends Error, super(message), then this.name), in a small family tree. Each layer catches only what it can treat (instanceof covers children; Error.isError works across realms), rethrows the rest, and cleans up in finally or with using / DisposableStack.
        • 
      
      • WRAP IT, DON'T LOSE IT: { cause }new Error("summary", { cause: err }) keeps the original error; Node prints it under [cause].
        • 
      
      • NEVER SWALLOW. LOG WHO, WHAT AND WHY.No empty catches, no "error" alone, no thrown strings. Catch at the edges, use process.exitCode = 1, and choose fail-fast for bugs, recovery (or result objects) for expected problems. AggregateError carries many errors at once.
        • 
      
      • SETTLED IS FINALA promise is pending, then fulfilled or rejected, once and for good. new Promise(executor) runs the executor now; a throw inside it rejects. Forget resolve, and the program just ends (or exits with code 13 under top-level await). withResolvers and Promise.try are newer helpers.
        • 
      
      • THEN HANDS YOU A NEW PAGERA callback's returned value (or the inside of a returned promise) fulfils the next pager. No return, no value. A throw skips the thens down to the next catch; catch at the end of the chain. all needs every result, allSettled reports each, race takes the first to settle, any the first success.
        • 
      
      • EVERY PAGER NEEDS A LISTENERUnhandled rejections crash Node with exit code 1. util.promisify and a one-line sleep turn callbacks into pagers: callbacks, then chains, then async/await.

    Under the hood: errors, stacks and how a promise really works
    
      
      
      What an Error object holds
      
      
      An Error has an own property message, an optional own cause (only when you passed { cause }; it can be any value), and in V8 an own stack string. name usually comes from the prototype: Error.prototype.name is "Error", TypeError.prototype.name is "TypeError", and so on. That's why a subclass that never sets name introduces itself as Error (panel 4). In V8 the stack is captured when the error is constructed, not when it's thrown, and its first line is formatted from name and message the first time something reads it, which is why setting this.name right after super shows up in crash reports.
      
      
      Why super must come first
      
      
      In a derived class (extends), the object is created by the parent's constructor. Until super(…) returns, there is no this to write to; touching it throws the ReferenceError from Boss 2. Error's constructor is also what installs the internal marker that Error.isError checks, so an object merely made with Object.create(Error.prototype) passes instanceof Error but fails Error.isError.
      
      
      Realms
      
      
      A realm is a complete set of built-ins (Object, Array, Error, …) plus a global object. An iframe, a vm context and a worker each have their own. instanceof compares prototype chains, so values crossing realms fail it. Array.isArray was the first "brand check" built to work across realms; Error.isError does the same for errors.
      
      
      A promise inside
      
      
      A promise keeps a state (pending, fulfilled, rejected), a result, and two lists of reactions (callbacks registered by then). resolve and reject are a pair of functions that share one "already resolved" flag, so only the first call counts (panel 23's ignored buttons). When the promise settles, each reaction becomes a job on the microtask queue (Chapter 16's pager desk). then creates the next promise and its own resolve/reject pair; whatever the callback returns is passed to that resolve, and a thrown error goes to its reject. If the returned value is itself a promise (or any object with a then method, a thenable), the next promise follows it instead of holding it, which is why the chain waits in panel 28 and why you can never get a promise of a promise.
      
      
      catch and finally are then in disguise
      
      
      p.catch(f) is p.then(undefined, f). p.finally(f) calls f with no argument on either road, then passes the original value or error on unchanged, unless f itself throws or returns a rejected promise. A then with no failure handler passes a rejection straight to its own new promise, which is how an error "skips" steps (panel 30).
      
      
      Unhandled rejections
      
      
      The engine tells the host when a promise is rejected with no handler attached. Node waits until the current batch of microtasks is done (in case a handler is attached a moment later), then, by default since Node 15 (see the version notes), treats it like an uncaught exception: print, exit code 1. Browsers fire an unhandledrejection event and log Uncaught (in promise), but the page keeps running.
      
      
      using and disposal order
      
      
      Each using declaration pushes its value's [Symbol.dispose] method onto the block's hidden disposal stack; at the end of the block they run last-in, first-out. If disposal itself throws while another error is already flying, both are kept in a SuppressedError (with error and suppressed properties), so neither is silently lost. await using and AsyncDisposableStack do the same for asynchronous cleanup, with Symbol.asyncDispose.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • Error families are everywhere. Web frameworks map classes to HTTP status codes: a ValidationError becomes "400 Bad Request", a NotFoundError "404 Not Found", and anything unexpected "500 Internal Server Error", logged in full. That's the triage desk at the edge of every request.
        • 
        
      • Node's own errors carry a code. Errors from Node have a stable err.code such as ENOENT (file not found) or ERR_INVALID_ARG_TYPE. Checking err.code is often more reliable than reading the message, which may change between versions.
        • 
        
      • Causes in logs. Logging libraries and error-tracking services print the whole cause chain, so wrapping with { cause } pays off the first time something breaks at 3 a.m.
        • 
        
      • Promise.all for parallel work. Loading a user, their orders and their settings at once, and failing the page if any is missing. allSettled for batch jobs: send 100 emails and report which failed. race for timeouts. any for trying several mirror servers.
        • 
        
      • Promisified Node. Most Node modules now have promise versions built in: node:fs/promises, node:timers/promises, node:dns/promises, node:stream/promises. You'll rarely call promisify on Node's own functions, but you'll still meet it for older libraries.
        • 
        
      • Linters guard the chain. ESLint's promise/always-return and promise/catch-or-return rules (from a popular plugin) and TypeScript-ESLint's no-floating-promises flag the forgotten return and the chain with no catch.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "A class that extends Error names itself." Not unless you set this.name; otherwise it says Error.
        • 
        
      • "Catching everything is the safe choice." A catch-all that hides bugs is the opposite of safe. Catch what you can treat.
        • 
        
      • "Wrapping an error replaces it." Only if you forget { cause }.
        • 
        
      • "err.message always exists in a catch." Anything can be thrown; a string has no message.
        • 
        
      • "instanceof Error is always reliable." Not across realms (iframes, vm, some test runners).
        • 
        
      • "The executor runs later." It runs at once, inside new Promise.
        • 
        
      • "Calling reject after resolve throws an error." It's silently ignored.
        • 
        
      • "A throw inside a setTimeout inside an executor rejects the promise." No: by then the executor has finished, so that throw is an ordinary uncaught exception. Call reject instead.
        • 
        
      • "then changes the promise it was called on." It returns a new one; the original never changes.
        • 
        
      • "A .catch anywhere in the chain protects all of it." Only the steps above it.
        • 
        
      • "After a .catch, the chain stops." It continues on the happy road with whatever the catch returned.
        • 
        
      • "Promise.all runs the jobs." The jobs already started when you called cook(…); all only waits. It also doesn't cancel the others when one fails.
        • 
        
      • "Promise.race picks the first success." It picks the first to settle, success or failure. That's any's job.
        • 
        
      • "A promise that never settles makes Node hang." Usually the program just ends; only a top-level await on it gives exit code 13.
        •

    Words from this chapter
    
      
      
      
        
      triage
      Sorting problems by who should handle them. The comic's desk: treat, refer up, discharge.
      
        
      custom error class
      Your own kind of error: class X extends Error, calling super(message) and setting this.name.
      
        
      validation error
      An error meaning "the input has the wrong shape or value".
      
        
      error hierarchy
      A family tree of error classes; checking for a parent also matches its children.
      
        
      name
      The error's kind, printed before the colon. Inherited as "Error" unless you set it.
      
        
      rethrow
      Throwing again an error you caught, because this layer can't treat it.
      
        
      wrap
      Throwing a new, clearer error with the original kept as its cause.
      
        
      cause
      The option { cause: err } on any error constructor; read back as err.cause.
      
        
      swallowing an error
      Catching it and hiding it, so nobody can learn what went wrong.
      
        
      edge (of a program)
      The outermost layer: the top of the script, one request, one click. Where errors are finally reported.
      
        
      stderr
      The error output stream. console.error writes there.
      
        
      process.exitCode
      The exit code Node will use when the program ends; 1 means failure.
      
        
      fail fast
      Stop loudly as soon as something impossible happens, rather than carry on with bad data.
      
        
      AggregateError
      One error that carries a list of errors in errors.
      
        
      result object
      A returned { ok, value } or { ok, error } instead of a thrown error.
      
        
      realm
      A separate JavaScript world with its own built-ins (an iframe, a vm context).
      
        
      Error.isError(value)
      True if the value is a real error from any realm.
      
        
      using
      A declaration that disposes its value automatically when the block ends.
      
        
      Symbol.dispose
      The well-known symbol naming an object's cleanup method.
      
        
      DisposableStack
      A list of cleanup jobs (defer, use), run newest first by dispose().
      
        
      executor
      The function passed to new Promise. It runs at once and gets resolve and reject.
      
        
      resolve / reject
      The two buttons that settle a promise, with a value or an error. Only the first press counts.
      
        
      settled
      Fulfilled or rejected. Final.
      
        
      promise chain
      Promises linked by then, catch and finally, each returning a new promise.
      
        
      .catch(f)
      Handles a rejection from any step above it; the same as .then(undefined, f).
      
        
      .finally(f)
      Runs on both roads and passes the value or error on.
      
        
      thenable
      Any object with a then method; promises follow thenables returned to them.
      
        
      Promise.all / allSettled / race / any
      Wait for every result / a report on each / the first to settle / the first success.
      
        
      fail fast (Promise.all)
      Rejecting as soon as one input rejects.
      
        
      Promise.withResolvers()
      Returns { promise, resolve, reject } together.
      
        
      Promise.try(fn, …args)
      Calls fn and always returns a promise, turning a quick throw into a rejection.
      
        
      error-first callback
      A callback called as (err, result); Node's old style.
      
        
      callback hell
      Callbacks nested inside callbacks, drifting to the right.
      
        
      util.promisify(fn)
      Turns an error-first-callback function into one that returns a promise.
      
        
      sleep(ms)
      A promise that fulfils after ms milliseconds, built from setTimeout.
      
        
      unhandled rejection
      A rejected promise nobody handles. Node crashes with exit code 1.

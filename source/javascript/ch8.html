CHAPTER 8

ROOMS WITH WINDOWS

Picture: Kit, the stage manager in a pink hoodie and headset, points at a drawing of three rooms nested inside each other: a lobby, a dressing room inside it, and a cupboard inside that. An eye in the cupboard looks out through a window in each wall, all the way to the lobby.

Every name in a program lives in a room. From inside a room you can look out through the windows and see the names in the rooms around you, but nobody outside can see in.     Under the hood: environments, the walk-through and per-lap bindings
    
          
      
          Rooms are "environments"
          
      
          The specification calls each room an environment record: a table of names and their values, plus a link to the room around it (its outer environment). Looking a name up means checking the current table, then following the outer link, again and again, until the link runs out. The rooms are decided by where the code is written, not by who calls it. That is called lexical scope ("lexical" means "about the text"). A function called from the lobby still looks out into the room where it was written, a fact Chapter 17 (closures) builds on.
          
      
          The walk-through is real
          
      
          Before a room's code runs, the engine creates all of that room's bindings (the spec's word for a name-and-value slot). Function declarations are created and filled with their function object at once. var bindings are created and filled with undefined. let, const and class bindings are created but left uninitialized; any read or write of an uninitialized binding throws a ReferenceError. That uninitialized stretch is the temporal dead zone. The SyntaxError for two lets of one name is found in an even earlier phase, when the file is parsed, which is why nothing in redeclare.js ran.
          
      
          Why typeof throws in the dead zone
          
      
          typeof name has a special case for names that cannot be found anywhere (it returns "undefined" instead of throwing). A name in its dead zone is found: it has a binding, but the binding is uninitialized, so reading it throws as usual.
          
      
          A fresh i every lap
          
      
          For a for (let i = …; …; …) loop, the specification says that at the end of each lap the loop copies the current i into a brand-new environment, and the i++ then runs in that new one. A function created in a lap (like the arrow inside setTimeout) remembers that lap's environment. With var there is only the function's (or the file's) one environment, so every arrow remembers the same i.
          
      
          How old code fixed the loop
          
      
          Before 2015, programmers made a new function room per lap on purpose, with an IIFE (an immediately invoked function expression): (function (j) { setTimeout(() => console.log(j), 0); })(i);. Each call gets its own j. You'll see IIFEs in old code for that reason, and to keep vars out of the global object. let made both uses unnecessary.
          
    
          
  
          

  
          
    In real programs
    
          
      
            
        
          • Linters enforce the house rule. ESLint's no-var rule reports every var, and prefer-const reports a let that is never changed. Many projects turn both on.
            • 
        
          • Accidental shadowing (panel 14) is caught by ESLint's no-shadow rule, which some teams enable and others find too noisy. no-use-before-define flags reads in the dead zone before the code even runs.
            • 
        
          • Modules are the real fix for the crowded lobby. Each module file has its own top-level room, so two files can both have a total without colliding. Chapter 14 is about modules.
            • 
        
          • Old code and old answers. Code written before about 2016, many jQuery-era tutorials, and a lot of highly voted Stack Overflow answers use var throughout. Read it with the three habits in mind; when you copy it, switch to const/let and check for reads before the declaration.
            • 
        
          • Top-level let and const in classic browser scripts are shared between all the classic scripts on a page (they live in one global room), even though they don't become window properties. Two scripts that both say let total at the top give a SyntaxError in the second script, which then doesn't run at all. A real run in headless Chromium:
          let_twice.html
          
            
          
            • 
        
          • TypeScript (Chapter 26) checks names before the program runs, so many dead-zone and lookup mistakes are reported while you type instead of at run time.

    Common wrong ideas
    
          
      
            
        
          • "Only functions create scope." True for var. For let and const, every block does.
            • 
        
          • "An inner function can't see the outer variables." It can: windows look out. It's the outer code that can't see in.
            • 
        
          • "Shadowing changes the outer variable." It hides it. The outer one keeps its value.
            • 
        
          • "let and const are not hoisted." They are: their seat exists from the start of the room, which is exactly why tdz_block.js can't see the lobby's seat. They're hoisted but uninitialized.
            • 
        
          • "The dead zone is the lines above the declaration." It's a stretch of time. A function written above can use the name if it's called after the declaration has run (panel 23).
            • 
        
          • "typeof can never throw." It throws for a name in its dead zone.
            • 
        
          • "let x; without a value is still in the dead zone." Once the line has run, x is undefined and usable (card 8 of the verdict board).
            • 
        
          • "var is just an old spelling of let." It behaves differently in five ways (panel 35).
            • 
        
          • "Forgetting let creates a global." Only outside strict mode. In modules it is a ReferenceError (panel 31).
            • 
        
          • "The 3-3-3 loop is a setTimeout bug." setTimeout works fine. The loop shares one i.

    Words from this chapter
    
          
      
          
        
          scope
          The part of a program where a name can be seen. Pictured as a room.
          
        
          global scope
          The outermost room: names made outside every function and block. In a module file it's the module's own top level (module scope).
          
        
          function scope
          The room made by a function's body; parameters and local variables live there.
          
        
          block scope
          The room made by any pair of braces { }, such as an if or a loop. let and const respect it; var doesn't.
          
        
          local variable
          A variable made inside a function or block, visible only there.
          
        
          lookup
          Finding a name: the line's own room first, then outward room by room.
          
        
          lexical scope
          Rooms are decided by where code is written, not by where it's called from.
          
        
          shadowing
          An inner room making a name that an outer room already has, hiding the outer one from inside.
          
        
          narrowest scope
          The habit of making each name in the smallest room that needs it.
          
        
          ReferenceError
          The Bouncer's error: a name that can't be found from here (x is not defined) or is still reserved (Cannot access 'x' before initialization).
          
        
          hoisting
          The walk-through before a room runs, which sets out a seat for every name declared in it.
          
        
          initialization
          Giving a name its first value. For let/const, when its declaration line runs.
          
        
          temporal dead zone (TDZ)
          The time between the start of a room and a let/const line running, when the name is reserved and can't be touched.
          
        
          identifier
          The official word for a name in code.
          
        
          redeclaration
          Declaring the same name again in the same room: a SyntaxError for let/const, allowed for var.
          
        
          var
          The pre-2015 way to make a variable: function-scoped, hoisted as undefined, redeclarable.
          
        
          global object
          window in browsers (globalThis everywhere): top-level vars in classic scripts become its properties.
          
        
          classic script
          A browser <script> without type="module".
          
        
          strict mode
          A stricter set of rules, always on in modules: for example, assigning to an undeclared name is an error.
          
        
          binding
          A name and its slot for a value, inside one room.
          
        
          environment record
          The specification's name for a room: its table of bindings plus a link to the outer room.
          
        
          IIFE
          An immediately invoked function expression; old code used it to make a private room.

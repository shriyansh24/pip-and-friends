CHAPTER 12

FOOTPRINTS AND SAFETY NETS

Picture: Kit, the stage manager in a pink hoodie and headset, points at a trail of footprints leading up to a big magnifying glass that reads "at line 2" and "CLUE!". Below, a safety net is stretched out.

Every programmer's code crashes, every day. The difference between a beginner and a pro is what happens next. Today you learn to read an error like a detective's note, follow its footprints back to the real culprit, hunt bugs that leave no note at all, and then string up a safety net so your program can fall without the show ending. About 120 minutes, with 26 hands-on checks.

  1. The detective's note: what an error says
  2. Footprints: following the stack trace
  3. The detective's toolkit: debugging
  4. The trapeze net: try, catch and throw
  5. The clean-up crew: finally, and the classic traps
  6. Boss level and recap

Four names cover almost every crash a beginner meets. Each has a character you've met before.

    

      

        
        
SyntaxError"I can't even read this."

        
A typo in the grammar: a missing bracket, quote or comma. Found before anything runs, so nothing runs at all. (syntax_typo.js)

      

      

        
        
ReferenceError"That name's not on my list."

        
A name that was never declared, usually a typo like sodl for sold. Message: sodl is not defined. (name_typo.js)

      

      

        
        
TypeError"Wrong kind of piece."

        
The value is the wrong kind for the job: reading a drawer of undefined, calling something that isn't a function. (crash_ticket.js)

      

      

        
        
RangeError"Right kind, bad amount."

        
A number is the right kind but outside what's allowed: an array can't have -2 slots. (range_seats.js)

      

    

    

      
      
Kit says: Learn the four names and you already know half the story before you read a single word of the message. There are a few more (a plain Error, and some rare ones), but these four are the regulars.

So there are two moments when things can go wrong.

    

      

        
1 · READING (parsing)before the show

        
The engine reads the whole file and checks its grammar. A SyntaxError here means the show never starts: zero lines run.

      

      

        
2 · RUNNINGduring the show

        
Line by line, top to bottom. A runtime error (TypeError, ReferenceError, RangeError…) stops the show at that line. Every line before it has already run.

      

    

    before_crash.js
    

    

    
    
      
  1. Lines 2 and 3 ran and printed. Line 4 asked for cast[2], a carriage that doesn't exist, so it got undefined and then tried to open its toUpperCase drawer: crash. Line 5 never ran.
    2. 
      
  2. The trail has just one footprint in your file, before_crash.js:4:21: no function was involved, so it's the top level of the file. Line 4, column 21, exactly where the caret is.
    3.

    Two tools that cost nothing.
    
    
    
      
    
        
        
    RUBBER-DUCK DEBUGGINGexplain it out loud
    
        
    Explain your code, line by line, to a rubber duck (or a patient friend, or a houseplant). Saying "and then this line adds the score…" out loud forces you to notice what the line really does. Surprisingly often, you find the bug halfway through the sentence.
    
      
    
      
    
        
    MINIMAL REPRODUCTIONshrink the crime scene
    
        
    Copy the code into a new file. Delete everything that isn't needed to make the bug happen, a piece at a time, running after each cut. What's left, often three or four lines, makes the bug obvious. And it's exactly what to show someone when you ask for help.
    
      
    
    
    
    
    
      
      
    The Professor says: When you do ask for help, bring three things: the smallest code that shows the bug, the complete error text (copied, not retyped), and what you expected to happen instead.

    35
    
      Trap: the clean-up crew is so determined to come out that it even interrupts a return. What if the crew returns something too? Predict it below before reading on.
      
    
      
      
      
        
      ✓ FINALLY FOR TIDYINGno return inside
      
        
      Use finally to turn off lights, close files and reset flags. Then the try's or catch's return value goes through untouched.
      
      
      
      
      
        
      ✗ NEVER RETURN FROM FINALLYit overrides everything
      
        
      A return in finally replaces any value the try returned, and even swallows an error that was falling. Linters flag it as unsafe.

    37
    
      So when should you check input and throw? A stage manager's rules.
      
    
        
      
      1. Check at the doors. Anything from outside your code can be wrong: what a user types, a file, saved settings, data from the internet. Check it as soon as it comes in.
        2. 
      
      2. Fail early and loudly. A clear RangeError: volume must be 0 to 10, got 11 at the door beats a mysterious NaN three functions later.
        3. 
      
      3. Pick the right kind. Wrong kind of value: TypeError. Right kind, outside the limits: RangeError. Anything else: Error. Always with a message that says what was expected and what arrived.
        4. 
      
      4. Catch where you can do something useful, such as use defaults, ask again, or show a friendly message. If you can't, let it fall.
        5. 
      
      5. Don't wrap everything in try. A bug in your own code should crash loudly with its footprints, so you can fix it.
        6. 
    
      
    
      
      
      
      Kit says: Nets are for falls you expect. They are not for hiding bugs.

    Under the hood: parsing, the call stack and error objects
    
      
      
      Two phases: parse, then run
      
      
      Before running a file, the engine (V8, inside Node and Chrome) parses it: it turns the text into a tree of statements and checks the grammar. An ES module (every .js file in this book, thanks to "type": "module") is parsed completely before any of it runs, which is why a single SyntaxError anywhere stops every line. These "early errors" also include things like declaring the same let twice in one scope, or using a reserved word as a name.
      
      
      Why SyntaxErrors can point late
      
      
      The parser reads left to right and only reports a problem when what it has read can no longer be valid. A missing } leaves everything after it looking like part of the block, perfectly legal, until the file ends. A missing ) is noticed at the first thing that can't be inside an argument list. So the report is the place where the parser gave up, never earlier than the real typo, and sometimes much later.
      
      
      The call stack and the trace
      
      
      Each call pushes an execution context (the comic's frame) holding that call's parameters and local variables; returning pops it. When an error object is created, V8 records the frames on the stack at that moment and formats them into err.stack. That's why an error object points at the line where it was created, even if it's caught and rethrown elsewhere (panel 30's third road: created on line 5, rethrown on line 8, reported at line 5), and why a thrown string has no trail at all: nothing captured one.
      
      
      Only ten footprints
      
      
      V8 keeps the newest Error.stackTraceLimit frames, which is 10 by default in both Node versions used here. That's why the recursion trace in panel 14 shows exactly ten copies. You can raise it (Error.stackTraceLimit = 50;) or run node --stack-trace-limit=50 file.js. The stack's own size limit, which causes the RangeError, is a separate setting measured in memory, not frames.
      
      
      Exit codes and stderr
      
      
      An uncaught error makes Node print the report to stderr (standard error, the second output stream of every program) and exit with code 1. Scripts and tools check that number: 0 means success, anything else failure. In a terminal, echo $? (macOS, Linux) or $LASTEXITCODE (PowerShell) shows the last exit code.
      
      
      The error object
      
      
      Built-in errors have name and message. stack is not part of the language standard, but every major engine provides it, and its format differs: Firefox and Safari write functionName@file:line:column instead of V8's at functionName (file:line:column). The error types are a small family: Error is the parent, and TypeError, RangeError, ReferenceError, SyntaxError, EvalError, URIError and AggregateError (Chapter 24) are its children. Chapter 24 shows how to make your own kinds.
      
      
      What finally really does
      
      
      A try statement remembers how its block ended: normally, by return, by break or continue, or by a throw. After finally runs, that ending resumes, unless finally itself ends abruptly (with its own return or throw), in which case the new ending wins. That rule is panel 35's trap, and it also means a return in finally silently cancels an error that was falling.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • Error monitoring. Websites and servers send uncaught errors, with their stack traces, to monitoring services, so developers see crashes from real users. The trace is what makes those reports useful, which is one more reason to throw error objects, never strings.
        • 
        
      • Source maps. Code shipped to browsers is usually squashed into one long line. A source map file lets DevTools and monitoring tools translate the footprints back to your original files and line numbers.
        • 
        
      • Validation at the edges. Servers check every incoming request before using it, and answer with a clear message (an HTTP "400 Bad Request") instead of crashing. That's panel 37's "check at the doors" rule at scale.
        • 
        
      • Clean-up with finally. Real uses: closing a file or a database connection, releasing a lock, hiding a loading spinner, stopping a timer. Chapter 24 shows a newer tool for this, using.
        • 
        
      • Linters catch traps. ESLint's no-empty rule flags an empty catch {}, no-unsafe-finally flags a return in finally, no-throw-literal flags throw "oops", and no-debugger flags a forgotten debugger;.
        • 
        
      • Logging levels. Besides console.log, there are console.error and console.warn (which write to stderr in Node), console.info and console.debug. Real programs use these levels to filter what they keep.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "Errors mean I'm bad at this." Every programmer sees errors constantly. Reading them quickly is the skill.
        • 
        
      • "The last line of the report is the important one." In Node it's the version footer. The Name: message line is in the middle.
        • 
        
      • "The bug is always on the line the caret points at." That's where it was noticed. A bad value may have come from a caller, and a SyntaxError may be reported after the typo.
        • 
        
      • "The first at line is my code." It may be a built-in (<anonymous>) or Node itself. Open the first one in your own file.
        • 
        
      • "A SyntaxError only stops the broken line." It stops the whole file before anything runs.
        • 
        
      • "try/catch catches every error." Not SyntaxErrors in the same file, and not errors in callbacks that run after the try has ended.
        • 
        
      • "Wrapping everything in try makes code safer." It hides bugs. Catch only where you can do something useful.
        • 
        
      • "finally runs only when there was an error." It runs every time: no error, caught error, rethrown error, even after a return.
        • 
        
      • "A variable declared with let inside try is available in catch." Each block has its own scope. Declare it before the try (panel 23).
        • 
        
      • "Throwing a string is the same as throwing an error." A string has no name, no stack and no footprints.
        • 
        
      • "debugger; stops every program." Only when a debugger is attached; otherwise it does nothing.
        • 
        
      • "Exit code 0 means my program is correct." It only means nothing crashed. The average of 4427.5 exited with 0.

    Words from this chapter
    
      
      
      
        
      error message
      The report printed when something goes wrong: name, message, location and stack trace.
      
        
      error name
      The kind of error, before the colon: TypeError, RangeError…
      
        
      caret
      The ^ under the copied line, marking the spot where the error was noticed.
      
        
      stack trace
      The list of at … lines: every call that was in progress, newest first. The comic's footprints.
      
        
      frame
      One function call's box of parameters and local variables. One line of the stack trace.
      
        
      call stack
      The pile of frames for calls that haven't finished yet.
      
        
      stderr
      "Standard error", the output stream where programs write problems. Shown in red in this book.
      
        
      exit code
      A number a program reports when it ends: 0 for success, anything else (1 for an uncaught error) for failure.
      
        
      parse
      To read source text and check its grammar before running it.
      
        
      SyntaxError
      The code (or text given to JSON.parse) breaks the grammar rules and can't be read.
      
        
      ReferenceError
      A name was used that was never declared (or used before its line, Chapter 8).
      
        
      TypeError
      A value is the wrong kind for the operation.
      
        
      RangeError
      A value is the right kind but outside the allowed range.
      
        
      runtime error
      An error that happens while the program is running, as opposed to while it's being parsed.
      
        
      logic bug
      Code that runs without errors but does the wrong thing.
      
        
      debugging
      Finding and fixing the cause of a bug.
      
        
      debugger
      A tool that pauses a running program so you can inspect it; also the JavaScript statement debugger; that asks it to pause.
      
        
      breakpoint
      A line where the debugger pauses the program.
      
        
      console.table
      Prints an array (or object) as a table of rows and columns.
      
        
      rubber-duck debugging
      Explaining your code out loud, line by line, to find the bug.
      
        
      minimal reproduction
      The smallest program that still shows the bug.
      
        
      recursion
      A function calling itself. Without a stopping point it causes Maximum call stack size exceeded.
      
        
      Baseline
      A label on reference pages saying a feature works in all the major browsers; "widely available" means for at least 30 months.
      
        
      throw
      The statement that raises an error on purpose and starts the fall.
      
        
      error object
      An object made with new Error(…) (or a built-in error type) with name, message and stack.
      
        
      try / catch
      Run a block; if anything in it throws, jump to the catch block instead of stopping the program.
      
        
      finally
      A block that runs after the try (and catch), whatever happened.
      
        
      optional catch binding
      catch { … } without (err), when the error itself isn't needed.
      
        
      rethrow
      To throw a caught error again because this catch can't handle it.
      
        
      uncaught error
      An error no catch stopped. The program prints the report and exits with code 1.
      
        
      validation
      Checking input before using it, and refusing bad input clearly.

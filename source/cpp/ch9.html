FORMS AND MAP LEGENDS

Picture: Wren, the mechanic in orange coveralls, waves hello next to her red toolbox.

Wren's workshop is drowning in loose scraps of paper. Time to make forms. A struct lets you design your own type: a form with labelled fields that you fill in, copy, pass to machines, stack in a vector and tear into slips. Then the Professor opens the library and teaches you to read the map of any C++ documentation page: which header, which standard, what goes in and what comes out.     uninit.cpp

    Picture: Wren points at the two terminals, worried. One compiler warned and the other said nothing.
    
  
    

  
    
  

  
    
    8
    
    The cure: write a default for each field right in the design, with =. These are default member initialisers. Any field you don't fill in gets its default, so no field is ever blank.
    
    defaults.cpp
    
    
    
    
    
    
      
    NO BRACESSettings a;
    Every field takes its default: 5, 70, light.
    
      
    SOME VALUESSettings b{8};
    Braces fill fields from the front: volume becomes 8. The rest keep their defaults.
    
      
    ALL VALUESSettings c{8, 30, "dark"};
    Every field filled, in declaration order. The defaults are not used.
    
    
    
    
    
      
      
    The Professor says: The C++ Core Guidelines prefer defaults written right on the members (C.48). My own rule is shorter: never leave a field blank. Even empty braces, Pet p{};, fill every field that has no default with zero. (The const Settings& on line 10 is Chapter 8's visitor badge: show may look at the form, not change it.)

    Wren says: Line 16 reads like a filled-in form: brightness 20, theme dark. Anyone can see which number goes where, with no counting. One rule, though: the labels must come in the same order as the design. Watch what happens if they don't.

        PART 4 · TEARING THE FORM INTO SLIPSStructured bindings, and std::pair: a ready-made two-field form
        

  
        
    16
    
        Sometimes you want the fields as plain separate names. auto [h, m, s] = split_time(3725); takes the returned form and tears it along the dotted lines into labelled slips. This is a structured binding (C++17). The first name gets the first field, the second name the second, and so on.
        
    
        
    
        
      
      
        Wren says: The slip names are brand new names you choose. They don't have to match the field names, and C++ doesn't even look at the field names. Slips go by position. Count them, and keep them in order.
        
    
        
  
        

  
        
    17
    
        Two places where slips shine: catching a returned form (line 21), and a loop over a vector of forms (line 25), where each lap tears the current form into bike and price.
        
    bindings.cpp
    
        
      
        
      
        
    
        
    
        
      
      
        Wren says: The word is always auto: the Compiler works out each slip's type from the form. In the loop, const auto& means the slips are look-only nicknames for the fields in the carton, so nothing is copied. Plain auto [h, m, s] on line 21 makes its own copy of the form first.

        What you learned in Chapter 9
        
    
          
      
        • ONE FORM, MANY FIELDSA struct designs a new type; each object is one filled-in form. Read and change fields with a dot. The design ends with };. Copying a struct copies every field.
          • 
      
        • NEVER LEAVE A FIELD BLANKA field with no value is uninitialised, and reading it is undefined behaviour. Give every member a default (C.48), or use {}. Braces fill fields in declaration order; designated labels (C++20) must follow that order too.
          • 
      
        • LOOK WITH const&, CHANGE WITH &Pass forms to machines by const&, or by & to change them. Return a struct to send back several results (F.21). std::vector<Job> holds many forms; loop with auto& to change them, not a copy.
          • 
      
        • SLIPS GO BY POSITIONauto [a, b] = form; tears a form into new names, matched by position, never by name, and the count must match. std::pair is a ready-made form with first and second.
          • 
      
        • READ THE LEGEND FIRSTEvery reference page: address (header), opening hours (version badge vs your -std), shop sign (signature, defaults, size_type), warning labels, photo. And your library must actually have the tool.
          • 
    
        
    
        
      
      
        Wren says: No more loose scraps: forms for everything, and a map for every tool in the box. Measure twice, compile once!

    Under the hood: how a form sits in memory, and language versus library
    
        
      
        Fields in a row
        
      
        A struct object is one block of memory with its members laid out in declaration order, the first member at the start. Between members the compiler may leave small gaps, called padding, so that each member starts at an address its type likes (an int usually wants a multiple of 4, a double a multiple of 8). That's why sizeof a struct can be bigger than the sizes of its members added up, and why listing members from biggest to smallest sometimes makes a struct smaller. A std::string member is itself a small object holding its letters elsewhere; copying the struct copies the string properly, letters and all.
        
      
        Aggregates and braces
        
      
        A struct with only public data members, no constructors (Chapter 12) and nothing fancier is an aggregate. Braces fill an aggregate member by member, in declaration order. Members you leave out are taken from their default member initialisers, or, if they have none, set to zero (or empty). Braces also refuse narrowing, as you saw with int in earlier chapters: Job a{"Racer", 2.5, 45.5} would not build, because 2.5 doesn't fit the int wheels field.
        
      
        What a structured binding really is
        
      
        auto [h, m, s] = split_time(3725); makes one hidden object, here a copy of the returned form, and h, m and s become names for its fields. With auto& [a, b] = form; the hidden object is a reference to form itself, so the slips name the real fields and writing to a changes form. Slips work on structs whose members are all public, on std::pair and std::tuple, and on plain arrays.
        
      
        Language features versus library features
        
      
        Compilers are often lenient about language features from a newer standard: g++ accepts designated initialisers under -std=c++17 as an extension, and only -Wpedantic points it out. (clang++ 18 did the same with these two commands: silent without the flag, and with it warning: designated initializers are a C++20 extension.) A library member from a newer standard is simply not there. Both builds below are real:
        
      designated17.cpp (same source as designated.cpp)
      
        
      
        
      ssize17.cpp (same source as size_type.cpp)
      
        
      
        
      
        clang++ 18, given the same -std=c++17 builds, used one phrase for both missing names: no member named 'contains' in 'std::map<int, int>' and no member named 'ssize' in namespace 'std'; did you mean 'size'?. For print17.cpp it said fatal error: 'print' file not found.
        
      
        That's why -Wpedantic belongs in a careful build: it turns "works here by accident" into a warning you can see.
        
      
        struct or class?
        
      
        In C++ the keywords struct and class make the same kind of type. The only difference is the default: members of a struct are public (anyone can read them with a dot), members of a class are private. The common habit, which the Core Guidelines describe (C.2, C.8), is: struct for plain bundles of data whose fields can take any values, class when the type has rules to protect. Classes arrive in Chapter 12.
        
    
        
  
        

  
        
    In real programs
    
        
      
          
        
        • Settings and options. Libraries often take one options struct instead of ten parameters. With defaults on every member and designated initialisers, a call reads like a form: Window w{.width = 800, .title = "Paint"};.
          • 
        
        • Several results. Functions that compute a few things together (a minimum and a maximum, a quotient and a remainder) return a small struct. The standard library does it too: std::div returns a struct with quot and rem, and std::minmax returns a pair.
          • 
        
        • Records from files. One line of a spreadsheet, one row of a database, one player in a save file: each becomes a struct, and the whole file a std::vector of them.
          • 
        
        • Talking to C and the operating system. C has structs too, and many system interfaces hand you one, such as std::tm (a broken-down date and time from <ctime>). Designated initialisers came to C++ from C.
          • 
        
        • Maps are full of pairs. Every element of a std::map is a std::pair of key and value, and loops over a map usually tear each one into slips: for (const auto& [key, value] : m) (Chapter 14).
          • 
        
        • Docs all day. Experienced programmers keep a reference open constantly. Editors show signatures as you type (hover over a name), drawn from the same headers the docs describe.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "A struct definition makes an object." It only designs the form. Objects come from Job a{...};.
          • 
        
        • "Fields start at zero." Not without braces or defaults. Pet p; leaves int fields uninitialised (panel 7).
          • 
        
        • "No warning means no problem." clang++ said nothing about the blank field. Defaults protect you; warnings sometimes don't.
          • 
        
        • "Job b = a; makes b another name for a." It photocopies the form. A second name is Job& b = a;.
          • 
        
        • "Designated labels can go in any order." In C, yes; in C++, they must follow declaration order (g++ refuses, clang++ warns).
          • 
        
        • "Slip names pick fields by name." By position only (the door quiz).
          • 
        
        • "for (Job j : jobs) changes the jobs." It changes copies. Use Job&.
          • 
        
        • "A function can't return several values." It returns one struct holding several.
          • 
        
        • "If it's on cppreference, my compiler has it." Check the badge against your -std, and your library's version (<print>).
          • 
        
        • "size() returns an int." It returns an unsigned size_type; size() - 1 on an empty container is huge.
          • 
        
        • "It compiled without the include, so I don't need it." Another header pulled it in by luck. Include what you use.
          • 
        
        • "cppreference is the official standard." It's a careful community wiki. The ISO standard is the official text.

    Words from this chapter
    
        
      
        
        
        struct
        A design for a new type made of named fields: struct Job { ... };.
        
        
        member (field)
        One named, typed part of a struct.
        
        
        object
        One value of a type in memory; for a struct, one filled-in form.
        
        
        member access (the dot)
        a.bike: the bike field of object a.
        
        
        aggregate
        A simple struct with only public data members and no constructors; it can be filled with braces.
        
        
        aggregate initialisation
        Filling a struct's fields in declaration order with braces: Job a{"Racer", 2, 45.5};.
        
        
        uninitialised
        Never given a value. Reading an uninitialised int field is undefined behaviour.
        
        
        default member initialiser
        A default written on a member in the design: int volume = 5;.
        
        
        value initialisation
        Empty braces, Pet p{};: every field gets its default, or zero if it has none.
        
        
        designated initialiser
        Filling fields by label: {.theme = "dark"} (C++20). Labels must follow declaration order.
        
        
        structured binding
        auto [a, b] = x;: new names for the parts of x, matched by position (C++17).
        
        
        std::pair
        A ready-made two-field struct from <utility>, with fields first and second.
        
        
        reference documentation
        Pages describing exactly what each language feature and library tool does, such as cppreference.com.
        
        
        header
        The file you #include to get a library tool: its "street address".
        
        
        signature
        A function's return type, name, parameters and qualifiers such as const, as shown on its page.
        
        
        overload list
        The numbered signatures on a page when one name has several versions.
        
        
        version badge
        A marker such as "(since C++20)" saying which standard added a feature.
        
        
        standard (C++17, C++20, C++23)
        An edition of the official C++ rules, named by year. -std= chooses which one to build with.
        
        
        standard library implementation
        The library that ships with a compiler (libstdc++ for g++, libc++ for Apple clang, MSVC's STL); it may lag behind the standard.
        
        
        size_type / std::size_t
        The unsigned whole-number type sizes and positions use. It never goes negative; 0 − 1 wraps to a huge number.
        
        
        npos
        A special "as many as possible" or "not found" value for strings: the largest size_type.
        
        
        exception
        A signal thrown when a tool can't do its job, such as std::out_of_range. Uncaught, it stops the program (exit 134 here). Catching one: Chapter 15.
        
        
        padding
        Unused bytes a compiler may place between struct members so each starts at a convenient address.

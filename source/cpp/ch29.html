PART 1 · MANY COOKSWhat a thread is, starting one, waiting for it with join(), and std::jthread

1

Lunchtime. Twelve orders are pinned up, and one cook works through them, one at a time, from top to bottom. That's every program in this book so far: one list of steps, followed in order.

Cook 1 says: Soup, then pasta, then cake, then... There's a second stove standing cold over there, and I've only got two hands!

Wren says: Then let's hire a helper. Two cooks, two stoves, two dishes at once. Your computer is the same: it almost certainly has several cores, and a program can put more than one of them to work. But more cooks means new kinds of trouble. Close to the metal. Careful with the wrench.

Picture: a little cook stirs a pot, overwhelmed. Wren points at an empty stove.

2

Three words you'll need all chapter. A running program is a process. Inside it, each separate list of steps being followed is a thread. The chips that actually do the steps are cores.

PROCESS

The whole kitchen: your running program, with its own memory that no other program can touch.

THREAD

One cook following steps. Every program starts with one, the main thread, which runs main. All threads of a process share its memory.

CORE

A stove: hardware that runs one thread at a time. With more threads than cores, the operating system takes turns, many times a second.

Three cards. Process: the whole kitchen, the running program with its own memory. Thread: one cook following steps; the main thread runs main; threads share memory. Core, dashed: a stove, hardware that runs one thread at a time; the operating system takes turns when there are more threads than cores.

Now the real thing: four cooks, 100,000 orders each, all doing ++orders on one plain int. This is a data race: two threads touch the same memory at the same time, at least one of them writes, and nothing orders them. In C++ that is undefined behaviour, so this book won't show it as an ordinary run. Instead it's built with -fsanitize=thread: ThreadSanitizer (TSan), the Sanitizer's thread-watching goggles from Chapter 18.

    race.cpp
    

    race.cpp · built with -fsanitize=thread · one possible run
    

    
    
      
  1. The headline: WARNING: ThreadSanitizer: data race.
    2. 
      
  2. Two accesses: one block starts Read of size 4 (or Write) by thread T…, the next Previous write of size 4 ... by thread T…. The frames inside the standard library are folded to one line per block (the whole report is in the box under the terminal): frame #0 of each block is yours, tally() .../race.cpp:7, the ++orders line.
    3. 
      
  3. The victim: Location is global 'orders' of size 4. An int is 4 bytes.
    4. 
      
  4. The suspects: each Thread T… created by main thread at block points at race.cpp:12, where the cooks were hired.
    5. 
      
  5. The ending: ThreadSanitizer: reported 2 warnings, and TSan makes the program exit with code 66 so a test script notices.
    6. 
    

    

      
      
The Sanitizer says: Notice that this program doesn't even print its total. A data race makes the whole program undefined, so any number it printed would be meaningless: never trustworthy, even when it looks right. Picture: the Sanitizer, in night-vision goggles, looking stern.

  


  

    15
    
"Undefined behaviour" sounds dramatic for a missing order or two. Here is why C++ treats it so seriously.

    

      
      
The Professor says: To make code fast, the compiler and the processor reorder and combine work, on the promise that no other thread is touching your plain variables at the same moment. In a loop like tally, an optimiser is allowed to keep orders in a register and write it back once at the end, or add 100000 in a single step. Each of those is a fine program on one thread. With four threads racing, each turns into a different wrong answer.

    

    

      
The Professor says: So the rule is simple and strict: if two threads touch the same memory and either one writes, something must put them in order. That something is a mutex, an atomic, or a join(), which is why panel 8 was safe. Core Guideline CP.2: avoid data races. CP.9: let tools like TSan check you, because races hide from testing.

In real C++, the pen is a std::mutex (header <mutex>, line 6). You never pick it up and put it down by hand: a std::lock_guard (line 10) locks the mutex when it's made, waiting if another thread holds it, and unlocks it in its destructor at the closing brace on line 12.

    counter_mutex.cpp
    

      

      

    

    

      
      
Wren says: 400000 every single time. Why a guard object instead of pen.lock() and pen.unlock()? Because an early return or an exception between them would leave the pen locked forever, and every other cook would wait forever. RAII hands it back on every way out (Core Guideline CP.20: use RAII, never plain lock and unlock). One pen, one writer.

    

  


  

    18
    
The proof that matters: the very same source, built with ThreadSanitizer. The badge below checks that the two captured files are identical.

    
    counter_mutex_tsan.cpp · built with -fsanitize=thread
    

    

      
      
The Sanitizer says: Not a peep. Every access to orders happens while holding pen, so each ++ is ordered after the one before. Exit code 0. A quiet TSan run is good evidence, though not proof: I only see the paths a run actually takes.

For a plain counter there's a lighter tool. std::atomic<int> (header <atomic>, line 5) is like a hand tally clicker: each ++ is one indivisible step that no other thread can split. Compare with race.cpp: the type of orders is the only real change.

Cook 3 says: Click! No pen to wait for. The processor has special instructions that read, add and write a number as one step. But it only works for one small value at a time. "Take an egg from the fridge and put it in the pantry" is two changes that must happen together, and that still needs a mutex.

    

  


  

  

  

    20
    
Pick the lightest tool that keeps every shared write in order.

Wren says: Keep each locked stretch short: lock, change, unlock. Never call some unknown function, or print a long report, while holding the pen (Core Guideline CP.22): every other cook is standing there waiting.

    

  


  

    21
    
    
A new kind of trouble that only exists with locks. Moving an egg from the fridge to the pantry needs both shelf locks. Cook 1 grabs the fridge lock, then reaches for the pantry. At that very moment, Cook 2, moving an egg the other way, grabs the pantry lock, then reaches for the fridge.

    

    

      
      
Wren says: Each holds one lock and waits for the other's. Neither will ever let go. That's a deadlock: no crash, no message, the program just sits there forever. That's why this one has no terminal: a frozen program has nothing to show, and the capture tool stops any run after 10 seconds. The fix isn't "be quicker". It's to never hold one lock while waiting for another.

    

    
Picture: two cooks, each holding one padlock and reaching for the other's, in a circle of waiting.

  


  

    22
    
C++17's std::scoped_lock (line 12) takes several mutexes in one go, using a deadlock-avoidance method: in this book's library, if it can't get them all, it lets go of the ones it has and tries again, so it never sits holding one while blocking on another. Here two cooks move 1,000 eggs each, in opposite directions, exactly the setup from panel 21.

    transfer.cpp
    

      

      

    

    

      
      
Wren says: Finished, and not one egg lost or doubled: 100 in the kitchen. std::ref again on lines 22 and 23, because move_eggs wants nicknames for the shelves. Core Guideline CP.21: use std::scoped_lock (or std::lock) to take more than one mutex. Grab both tools at once.

    

  


  
  
PART 4 · RING THE BELL, COLLECT THE ORDERA first look at std::condition_variable, then tasks with std::async and std::future


  

    23
    
The kitchen puts finished dishes on a counter, and a courier takes them out to the customers. How does the courier know when there's something to carry? Walking over every second to look would wear out her shoes (and waste a whole core). Instead, she naps until the cook rings the bell.

    

    

      
THE COUNTER
Shared data (a queue of dishes), protected by a mutex, as always.

      
THE BELL
A std::condition_variable. The cook calls notify_one() after putting a dish down.

      
THE CHECK
The courier's wait(lock, condition) sleeps until the condition is true. It always re-checks, because a courier can wake up when nobody rang.

    

    
Three cards. The counter: shared data protected by a mutex. The bell: a condition variable; the cook calls notify_one. The check, dashed: wait with a condition sleeps until the condition is true and always re-checks.

  


  

    24
    
The courier is a thread running courier(); main plays the cook. Only the courier prints, so the output is the same on every run.

    cv_orders.cpp
    

      

      

    

    
    
      
  1. Line 15: a std::unique_lock, not a lock_guard. It's a guard that can be unlocked and relocked, which waiting needs.
    2. 
      
  2. Line 16: wait checks the condition (a lambda). If it's false, it unlocks the mutex and sleeps. On a ding it wakes, relocks, and checks again. It only returns when the condition is true, holding the lock.
    3. 
      
  3. Line 22: unlock before printing, so the cook isn't kept waiting for the counter while the courier talks (panel 20).
    4. 
      
  4. Lines 37 to 41: closing time is also news, so it's written under the lock and announced with a ding too. Without that, the courier would sleep forever.
    5. 
    

    

      
      
Wren says: That's the "first look" this book promised: there's a lot more to condition variables. Always wait with a condition (Core Guideline CP.42), and keep the pattern exactly as here: lock, wait with a check, take, unlock.

    

  


  

  

  

    25
    
Often you don't want to manage a thread at all. You just want a job done in the background and its answer later. That's a task: you hand in the job and get an order ticket back.

    
    

      
      
Cook 4 says: std::async(std::launch::async, job, args...) starts the job on another thread and hands you a std::future<T>: a ticket for a T that doesn't exist yet. Later, .get() trades the ticket for the answer, waiting if it isn't ready. One ticket, one get().

    

  


  

    26
    
Add up 1 to 1,000,000 in two halves: a helper takes the bottom half, 1 to 500,000 (line 13), while main does the top half itself (line 14). No mutex, no join, no shared variable: the answer travels back through the future.

    async_sum.cpp
    

      

      

    

    

      
      
Wren says: Always pass std::launch::async. Without it, the library may decide to run the job later, on your own thread, at the moment you call get(): correct, but not in the background at all. Core Guideline CP.4: think in terms of tasks, rather than threads.

    

  


  

    27
    
What if the job throws? An exception can't jump from one thread's stack to another's. So the future stores it, and get() throws it again, in the thread that asked (line 18).

    async_throw.cpp
    

      

      

    

    

      
      
Ember says: My alarm, carried home on the ticket and rung again in main, where there's a catch for it (Chapter 15). And look closely at that last line: ice cake: caught in main: .... Since C++17 a chain of << runs left to right, so ice cake:  was already printed when bad.get() threw. Get the value into a variable first if you don't want half a sentence.

    

  


  

  

  

  

  

  

  

    28
    
Pin these by the kitchen door. They're the C++ Core Guidelines' concurrency rules, in kitchen words.

    
    
      
  1. Prefer tasks to threads (CP.4). std::async plus a future is often all you need.
    2. 
      
  2. Give each cook their own page (CP.3). Share as little writable data as possible.
    3. 
      
  3. Every shared write is ordered (CP.2): a mutex, an atomic, or a join. No exceptions.
    4. 
      
  4. Locks are objects, never hands (CP.20): lock_guard, unique_lock, scoped_lock.
    5. 
      
  5. Two locks? Take them together (CP.21) with std::scoped_lock.
    6. 
      
  6. No cook left behind (CP.25, CP.26): std::jthread, never detach().
    7. 
      
  7. Run the goggles (CP.9): build your tests with -fsanitize=thread too. (It can't be combined with AddressSanitizer: two separate builds, Chapter 18.)

PART 5 · THE STOPWATCHMeasure first: steady_clock and duration_cast, Debug vs Release, a profiler, and a peek at the assembly


  

    29
    
The kitchen's relay team takes too long to get a dish out: warm-up, the main job, cool-down. Everyone has an opinion about whose leg is slow. Enter Tick, the kitchen's timekeeper.

    

    

      
      
Tick says: Opinions are free, and usually wrong. Programmers are famous for guessing the slow part badly. So: don't guess the slow runner. Time each leg. Only then do we change anything, and then we time it again to prove the change helped (Core Guideline Per.6: don't make claims about performance without measurements).

    

    
Picture: a three-leg relay track with blank stopwatches under each leg, and Tick the timekeeper in a striped shirt and flat cap, holding a stopwatch showing question marks.

C++'s stopwatch lives in <chrono>. std::chrono::steady_clock::now() (lines 14 and 16) reads a clock that only ever moves forward. Subtracting two readings gives a duration, and duration_cast (line 17) turns it into the unit you want to print. This program times the same job three times.

    stopwatch.cpp
    

    one possible run
    

    
    
      
  1. The answer is the same on every lap and every run: that part is the program's logic.
    2. 
      
  2. The times are different on every lap, and different again every time the page's capture ran it. Other programs share the machine, the processor speeds up and slows down, and the first lap often pays for warming things up. Run it yourself and you'll get your own numbers.
    3. 
      
  3. Why steady_clock? system_clock is the wall clock, and it can jump: the computer may correct its time in the middle of your measurement. A stopwatch must never run backwards.
    4.

    34
    
Curious what the optimiser really did? As in Chapter 19, -S asks g++ for assembly, the human-readable form of machine code, instead of a program. -o - prints it to the screen, and grep filters out the bookkeeping lines (the ones starting with a dot, and a few numbered labels). Here is a three-line function at both settings.

    square.cpp
    

    

    
    
      
  1. _Z6squarei is square(int), mangled (Chapter 28). endbr64 is a security landing pad; ignore it.
    2. 
      
  2. At -O0: set up a stack frame (pushq, movq), copy x from its register %edi into memory and back again, multiply (imull), tidy up, return. Every line of C++ is faithfully acted out.
    3. 
      
  3. At -O2: multiply the register by itself, move it into %eax (where a returned int goes), return. Same meaning, less than half the work.
    4. 
    

    
The same two commands with clang++ in place of g++ made slightly different code: no endbr64, retq instead of ret, comment lines starting with # that the grep lets through, and at -O2 the move first, then the multiply (movl %edi, %eax, imull %edi, %eax). Its -O0 version still copies x into memory and reads it back. Two compilers, two ways to write the same meaning.

    

      
      
The Compiler says: You don't need to read assembly to write good C++. But a quick look settles arguments like "is this copy really made?". The website Compiler Explorer (godbolt.org) shows this side by side for any compiler, as you type.

    Why std::vector is usually the fastest container, even where a std::list "should" win. The processor doesn't fetch one number from memory at a time. It fetches a whole cache line, usually 64 bytes, into a small, very fast store called the cache.

    What you learned in Chapter 29
    
    
      
      
    • NO COOK LEFT BEHINDA std::thread runs a function alongside main. Join it before it's destroyed, or terminate called without an active exception, exit 134. std::jthread joins in its destructor, on every way out. Never detach(). Threads copy their arguments: std::ref for a nickname.
      • 
      
    • GIVE EACH COOK THEIR OWN PAGETwo threads touching the same memory, at least one writing, with nothing ordering them, is a data race: undefined behaviour. ++x is read, add, write. Find races with -fsanitize=thread; avoid them by not sharing.
      • 
      
    • ONE PEN, ONE WRITERstd::mutex held by a std::lock_guard for groups of changes; std::atomic<int> for one counter. Keep locked stretches short.
      • 
      
    • GRAB BOTH TOOLS AT ONCEHolding one lock while waiting for another can deadlock. std::scoped_lock takes several together. Wait for news with a condition_variable and a unique_lock, always with a condition.
      • 
      
    • HAND IN THE JOB, KEEP THE TICKETstd::async(std::launch::async, f, args) returns a std::future; get() waits for the answer, or rethrows the job's exception in your thread.
      • 
      
    • DON'T GUESS THE SLOW RUNNER: TIME EACH LEGsteady_clock and duration_cast (which chops), several runs, the -O2 build, a profiler. Then fix the route (O(n²) to O(n)) before the engine: const&, const auto&, reserve, '\n', vectors.

    Under the hood: what a thread is made of, what "happens before" means, how a mutex waits, how a profiler counts
    
    
      
    What a thread owns, and what it shares
    
      
    Each thread gets its own stack (its own plates of local variables, Chapter 13's picture) and its own copy of the processor's registers while it runs. Everything else is shared by the whole process: global variables, the heap, open files, std::cout. That's why a local variable inside tally is always safe, and a global orders is not. On Linux, std::thread is built on the operating system's POSIX threads (pthreads); that's the pthread_create you saw in the TSan report.
    
      
    "Happens before"
    
      
    The C++ standard defines a data race precisely: two accesses to the same memory location from different threads, at least one a write, where neither happens before the other. Things that create happens-before links include: everything a thread did before it finished happens before join() returns; unlocking a mutex happens before the next lock of that mutex; a write to an atomic happens before a read that sees it; setting a future's value happens before get() returns it. ThreadSanitizer tracks exactly these links during a run, which is how it can report a race even when the total happened to come out right.
    
      
    Why TSan only works with g++ here
    
      
    Sanitizers need a run-time library. g++ ships its own (libtsan); clang's sanitizer libraries aren't installed on this machine (Chapter 18), so the TSan builds on this page have no clang comparison (the footer lists every build that had none). TSan slows a program down several times and uses much more memory, so it's for test builds only, and it can't be combined with AddressSanitizer.
    
      
    How a mutex waits
    
      
    Locking a free mutex costs one atomic instruction. If it's taken, the thread may spin for a moment, then asks the operating system to put it to sleep until the holder unlocks (on Linux, a "futex"). That's why holding a lock for a long time wastes so much: every waiting cook is asleep. std::atomic<int>'s ++ uses one special locking instruction instead (lock xadd on x86-64) and never sleeps.
    
      
    Atomics have settings too
    
      
    Every atomic operation takes an optional memory order. The default, std::memory_order_seq_cst, is the simplest to reason about and what this chapter used everywhere. The weaker orders (relaxed, acquire, release) can be faster but are famously easy to get wrong; they belong to the "memory model" topic this book leaves for later.
    
      
    What std::jthread adds besides joining
    
      
    A std::jthread also carries a stop token. If its function takes a std::stop_token as its first parameter, it can ask token.stop_requested() in its loop; request_stop() sets that flag, and the destructor calls request_stop() and then join(). That gives long-running helpers a polite way to be told "kitchen's closing".
    
      
    Two compilers, two ways to say "wrong lock"
    
      
    clang++ 18 rejects cv_bug.cpp too, and its note says the same thing more directly: no known conversion from 'std::lock_guard<std::mutex>' to 'unique_lock<mutex> &'.
    
      
    
      
    And its message for the missing std::ref puts the failed requirement in the first line:
    
      
    
      
    How gprof counts
    
      
    -pg makes every function record each call (that's the exact calls column), and the program is interrupted about 100 times a second to note which function was running (the sampled seconds columns, hence "Each sample counts as 0.01 seconds"). Very short programs get too few samples to say much; that's why find_pairs needed real work to measure.
    
      
    Why -O2 doesn't simply delete benchmark loops
    
      
    An optimiser may remove any work whose result is never used. The benchmarks here all print their totals, which forces the work to happen. A loop whose answer you throw away can be timed at 0 ms at -O2: a classic benchmarking trap.
    
    
    
  
    

  
    
    In real programs
    
    
      
      
        
    • Thread pools. Starting a thread costs time, so servers and game engines start a fixed team of worker threads once (often one per core) and feed them tasks from a queue: Part 4's courier, grown up.
      • 
        
    • The UI thread. Programs with windows keep one thread for drawing and clicks, and move slow jobs (loading, saving, network) to helpers, so the window never freezes. Results come back through futures or message queues.
      • 
        
    • Parallel algorithms. C++17 lets many standard algorithms run in parallel by passing an execution policy, as in std::sort(std::execution::par, v.begin(), v.end()). With libstdc++ this needs Intel's TBB library installed, so this book didn't use it.
      • 
        
    • Benchmark libraries. Real projects measure with tools like Google Benchmark, which repeats each test until the timing settles and reports the spread, doing panel 30's "several laps" properly.
      • 
        
    • Profilers. perf on Linux, Instruments on macOS, the Visual Studio profiler and Intel VTune show where time goes without rebuilding with -pg, often as "flame graphs".
      • 
        
    • Release builds. CMake's Release build type (Chapter 17) means -O3 -DNDEBUG with g++; RelWithDebInfo means -O2 -g -DNDEBUG, a common choice for profiling.
      • 
        
    • Data layout. Games often store each field of many objects in its own vector ("structure of arrays") so a loop over positions touches only positions: panel 39's cache lines, taken seriously.
      • 
      
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "More threads is always faster." Beyond the number of cores, threads just take turns; and locks, sharing and starting threads all cost time. Measure.
      • 
        
    • "My race printed the right answer, so the code is fine." A data race is undefined behaviour whether or not today's run looked right (panel 14's notes).
      • 
        
    • "++x is one step." On a plain int it's read, add, write. Only on a std::atomic is it one indivisible step.
      • 
        
    • "volatile makes a variable thread-safe." It doesn't, in C++. It's for hardware registers. Use std::atomic (Core Guideline CP.8).
      • 
        
    • "join() runs the thread." The thread started when it was made. join() only waits for it to finish.
      • 
        
    • "A thread gets my variable." It gets a copy, unless you pass std::ref or capture by reference.
      • 
        
    • "std::async always makes a new thread." Only with std::launch::async; otherwise the library may run the job later, on the thread that calls get().
      • 
        
    • "A deadlock crashes the program." It freezes it, silently.
      • 
        
    • "Timing the debug build is good enough for comparing." -O0 and -O2 can differ many times over, and not evenly (panel 32).
      • 
        
    • "duration_cast rounds." It chops towards zero: 1500 ms is 1 second.
      • 
        
    • "Lists are faster for everything except indexing." Walking a list is usually far slower than walking a vector, because of the cache (panel 39).
      • 
        
    • "Fewer lines of code means faster." One line can hide a million steps, or a whole copied vector.

    process
    A running program, with its own memory.
    
        
    thread
    One sequence of steps being followed inside a process; all threads of a process share its memory. The main thread runs main.
    
        
    core
    A part of the processor that runs one thread at a time.
    
        
    concurrency
    Several tasks in progress at the same time (taking turns or truly side by side).
    
        
    std::thread
    Starts a new thread running a function; must be joined (or detached) before it's destroyed.
    
        
    join()
    Wait until a thread has finished.
    
        
    joinable
    A thread object that still owns a running or finished-but-unjoined thread; destroying a joinable std::thread calls std::terminate.
    
        
    detach()
    Let a thread run on with no owner; nobody can wait for it afterwards (avoid: CP.26).
    
        
    std::jthread
    C++20 joining thread: its destructor requests a stop and joins.
    
        
    std::ref
    Wraps a variable so a thread (or std::bind) passes a reference instead of a copy.
    
        
    data race
    Two threads access the same memory, at least one writes, and nothing orders them: undefined behaviour.
    
        
    lost update
    One thread's write overwritten by another that read the old value.
    
        
    register
    A tiny, very fast storage spot inside a core.
    
        
    ThreadSanitizer (TSan)
    A g++/clang tool, enabled with -fsanitize=thread, that reports data races seen during a run.
    
        
    mutex
    "Mutual exclusion": a lock that only one thread can hold at a time; std::mutex.
    
        
    std::lock_guard
    Locks a mutex when made, unlocks it when destroyed.
    
        
    std::unique_lock
    A lock guard that can also unlock and relock; needed by condition_variable::wait.
    
        
    std::scoped_lock
    C++17: locks one or more mutexes together, avoiding deadlock.
    
        
    std::atomic
    A value whose operations (like ++) are indivisible, so threads can share it safely.
    
        
    deadlock
    Threads each waiting for a lock another holds, forever.
    
        
    std::condition_variable
    Lets a thread sleep until another notifies it; always wait with a condition.
    
        
    notify_one / notify_all
    Wake one, or every, thread waiting on a condition variable.
    
        
    task
    A piece of work whose result you want, rather than a thread you manage.
    
        
    std::async
    Runs a function as a task (on a new thread with std::launch::async) and returns a future.
    
        
    std::future
    A ticket for a result that may not exist yet; get() waits for it, or rethrows the task's exception.
    
        
    happens before
    The standard's word for "is guaranteed to be finished and visible before"; joins, locks, atomics and futures create it.
    
        
    std::chrono
    The time library: clocks, time points and durations, in <chrono>.
    
        
    steady_clock
    A clock that never goes backwards; the one to time things with.
    
        
    duration / duration_cast
    A length of time with a unit; duration_cast converts units, chopping towards zero.
    
        
    -O0 / -O2
    No optimisation (the default, best for debugging) / the usual optimisation level for released programs.
    
        
    benchmark
    A careful measurement of how long something takes.
    
        
    profiler
    A tool that reports where a program spends its time; gprof (-pg), perf and others.
    
        
    assembly
    Human-readable machine code; g++ -S writes it.
    
        
    O(n), O(n²)
    "Big O": how the work grows as the input grows; linear, or with the square.
    
        
    reserve
    Ask a vector for room for n elements up front, so it doesn't have to move them as it grows.
    
        
    flush
    Push buffered output out now; std::endl does it after every line.
    
        
    cache / cache line
    Small fast memory inside the processor / the 64-byte chunk it fetches from main memory at once.
    
        
    small-string optimisation (SSO)
    Storing short strings inside the std::string object itself, with no heap block.

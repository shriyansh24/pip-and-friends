C++ · CHAPTER 12

THE BANK VAULT

Picture: Wren, the mechanic in orange coveralls, waves hello next to her red toolbox.

Wren's crew keeps its savings on open forms, and anyone can scribble on them. Time to build a bank vault. A class locks the data away (private) and opens a teller's window (public member functions) where every request is checked against the rules. You'll meet constructors that open an account properly, const promises, the hidden this, the order members are really set in, the one rule a class must never break (its invariant), a class split across files, and the destructor that tidies up on its own. About 110 minutes, with 22 hands-on checks.

  1. The open drawer: class, public, private
  2. The teller at work: member functions, this, const
  3. Opening an account: constructors and initialisation order
  4. The rules of the vault: invariants, getters and setters
  5. Behind the counter: header and source, and the destructor
  6. Boss level and recap

Big idea: a class is a struct with a vault. Its data sits behind a locked door marked private: only the class's own code can touch it. The outside world talks to it through a window marked public, where the class's member functions work like a teller, checking every request against the rules.

    

    

      
Tally says: Hi, I'm Tally. Nobody walks into my vault. You ask at the window: deposit, withdraw, what's my balance? I check every request against the rule on the wall before anything moves. Lock the vault, open a window.

Line 16 fails. A class's members are private by default; clang++ even says "implicitly declared private here".

    

    

      
      
The Professor says: Apart from that default, the two keywords make exactly the same kind of type: both can have member functions, constructors and private parts. Programmers use the word to tell readers something.     7
    
The Professor's test: is there a rule that ties the data together? If any combination of field values is fine, it's a plain form: struct. If some values must be forbidden, it needs a teller: class.

Wren says: No rule? Leave the drawer open, a struct is simpler. A rule? Lock it in a class and put a teller at the window.

    PART 3 · OPENING AN ACCOUNTConstructors, member initialiser lists, default and overloaded constructors, and the order members are really set
    

  
    
    14
    
    A real bank doesn't hand you an account with a blank name and a random balance. You fill in the opening form, the teller checks it and stamps it, and only then does the account exist. In C++, that opening ceremony is a constructor: a special member function that runs automatically the moment an object is created.
    
    
    
    
    
      
      
    Tally says: Nobody leaves my counter with a half-filled account. Every account is born valid: complete and following the rules from its very first moment (Core Guideline C.41).

    PART 4 · THE RULES OF THE VAULTInvariants: the promise every public door must keep, and when getters and setters break it
    

  
    
    21
    
    The rule on the vault wall, "balance_ is never below zero", has a name: the class's invariant, something that must be true of every object, always. Since only member functions can touch private data, the plan is simple: every public door checks the rule. The constructor makes it true at birth; every member function keeps it true.
    
    
    
    
    
      
      
    Tally says: Because nobody can reach the vault except through my doors, I only have to check the rule in a few places, and then it's true everywhere, always. That's what private buys you. The teller checks every request.
    
    
    
  
    

  
    
    22
    
    
    Mistake six, and the compiler can't catch this one: it builds, runs, and breaks the rule. withdraw checks carefully. But the constructor on line 6 copies any opening amount straight in.
    
    invariant_bug.cpp
    
    
      
    
      
    
    
    
    
    
      
      
    Wren says: Sneak, the logic-bug critter, came in through the front door: the account was born broken, with −50. Every later check assumes the rule already holds, so a broken birth breaks everything after it. A class with an invariant must check it in every constructor (C.40, C.41).
    
    
    
    
    Picture: a SNEAKY burst, and Sneak, the logic-bug critter, tiptoeing past.
    
  
    

  
    
  

  
    
    23
    
    The fixed account. Line 7 clamps the opening amount: std::max(0, opening) (from <algorithm>) turns anything below zero into 0. Line 12 refuses a bad withdrawal and reports it with false, leaving the balance untouched.
    
    invariant_fixed.cpp
    
    
      
    
      
    
    
    
    
    
      
    CLAMPstd::max(0, opening)
    Quietly fix the value. Fine when there's an obvious safe value; but the caller never hears about it.
    
      
    REFUSEbool withdraw(int)
    Do nothing and return false. Best for ordinary mistakes like "not enough money": the caller can check and react.
    
      
    ASSERTassert(amount <= balance_)
    Stop the program (Chapter 11). Only for programmer mistakes that should be impossible, never for user input.
    
    
    
    
    
      
      
    The Professor says: Professionals have a fourth way: when a constructor can't make a valid object, it throws an exception (C.42), so no broken object ever exists. Exceptions arrive in Chapter 15. Until then, clamp, refuse or assert, and choose on purpose.

    Mistake seven: the "helpful" setter. Many tutorials teach you to write a getter (a member function that returns a private value) and a setter (one that replaces it) for every field. Line 12's setter replaces the balance with anything at all.

    30
    
    One last special member function, for a first look. The destructor is named with a tilde, ~Locker(). It has no parameters and no return type, and C++ calls it automatically when an object's life ends: at the closing brace of the block where it was made. Objects in the same block end in reverse order: last opened, first closed.
    
    
    
    
    
      
      
    Wren says: My motto: every bolt you tighten, you loosen later. The constructor tightens, the destructor loosens, and C++ guarantees the loosening happens, even if you forget. Today the destructors only print. In later chapters they'll close files and give back memory.

    33
    
      What you learned in Chapter 12
      
    
        
      
      • LOCK THE VAULT, OPEN A WINDOWA class keeps its data private and offers public member functions. Outside code that touches private data doesn't build: "is private within this context". struct and class differ only in the default: public versus private. Use class when there's an invariant (C.2).
        • 
      
      • LOOK-ONLY MEANS constA member function marked const promises not to change the object, so it can be called on const objects and through const&. Forget it: "discards qualifiers". Break it: "read-only object". Inside a member function, this points at the object before the dot.
        • 
      
      • BORN VALIDA constructor has the class's name and no return type, and sets members in its member initialiser list (C.49). Default member initialisers fill in the rest. Overloads are picked by the arguments; the free default constructor vanishes once you write any constructor.
        • 
      
      • DECLARATION ORDER WINSMembers are initialised in the order they're declared, never in list order. -Wreorder warns; never build one member from another that comes later (C.47).
        • 
      
      • THE TELLER CHECKS EVERY REQUESTAn invariant must be made true by every constructor and kept true by every member function: clamp, refuse with a bool, or assert for impossible cases (exceptions in Chapter 15). Getters are fine; trivial setters break the vault (C.131).
        • 
      
      • EVERY BOLT YOU TIGHTEN, YOU LOOSEN LATERThe destructor ~Name() runs automatically at the end of an object's scope, newest first. In a header and source split, write Name::member in the .cpp, and keep each const in both files.
        • 
    
      
    
      
      
      
      Wren says: No more open drawers. Every account is born valid, every door checks the rule, and every bolt gets loosened. Measure twice, compile once!

    Under the hood: where member functions live, what private really protects, and the constructors you get for free
    
      
      
      An object holds only its data
      
      
      Each object stores its data members, nothing else. The member functions are compiled once and live in the program's code, shared by every object. When you write acc.deposit(50), the compiler quietly passes the address of acc along, and that hidden argument is this. So a class with one int and three member functions is exactly as big as a struct with one int:
      
      sizes.cpp
      
      
      
      
      
      (sizeof an int is 4 bytes on this machine and on most computers today, but the standard only promises "at least 16 bits".)
      
      
      private is a rule for the compiler, not a lock on memory
      
      
      Access is checked while the program is built. At run time a private member is ordinary memory, at no extra cost: no checks, no slowdown. That's why private protects you from mistakes, not from a determined attacker. Access is also per class, not per object: a member function of Account may read the private data of another Account object, which comes in handy for comparing two accounts.
      
      
      Constructors the compiler writes for you
      
      
      If a class declares no constructor at all, the compiler provides a default constructor that takes no arguments and uses the default member initialisers. Declare any constructor yourself and that one is no longer provided (panel 17); Name() = default; asks for it back. The compiler also writes a copy constructor and a move constructor, which is why g++ listed Account(const Account&) and Account(Account&&) as candidates. They copy or move every member, which is how Meter c = b; worked in Boss 1. Chapters 21 and 22 explain when you must write them yourself.
      
      
      Why mark one-argument constructors explicit (C.46)
      
      
      A constructor that can be called with one argument also acts as a silent conversion. Here a std::string turns into a whole new Account just to be welcomed:
      
      implicit_conv.cpp
      
      
        
      
        
      
      
      
      
      The same program with explicit in front of the constructor (line 7) refuses the quiet conversion, and you must write welcome(Account{name}) if you really mean it:
      
      explicit_conv.cpp
      
      
      
      The order of construction and destruction
      
      
      Building an object happens in a fixed order: first each data member is initialised, in declaration order, using the initialiser list or else the default member initialiser; then the constructor's body runs. Destruction is the mirror image: the destructor's body runs first, then the members are destroyed in reverse declaration order (a std::string member gives back its letters at that moment). Objects in one scope are destroyed in reverse order of creation. That mirror rule is what makes "every bolt you tighten, you loosen later" automatic, and Chapter 22 builds on it (RAII).
      
      
      Member functions defined inside the class
      
      
      A member function whose body is written inside the class definition is automatically inline, so the header can be included by many .cpp files without the "multiple definition" link error from Chapter 10. That's why tiny getters often stay in the header, while longer bodies move to the .cpp file.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • You've been using classes since your first std::string. std::string and std::vector are classes with private data and an invariant (for a vector: the size is never more than the room it has reserved). v.size() is a const member function; v.push_back(x) is a door that keeps the rule, growing the storage when needed.
        • 
        
      • Destructors that clean up. A file stream (std::ofstream, Chapter 15) closes its file in its destructor; a std::vector gives its memory back in its destructor. You never call either one yourself.
        • 
        
      • Naming habits. Projects mark private data members so they can't clash with parameters and getters: a trailing underscore (balance_, used here and in the Google C++ style guide), an m_ prefix (m_balance, used by learncpp.com and many codebases), or nothing at all. Pick one per project and stick to it.
        • 
        
      • One class, two files. Almost every class in a real project has a header (account.h or account.hpp) and a source file (account.cpp). Readers and editors show the header first, because it's the interface: the teller's window.
        • 
        
      • Validation at the edges. Programs check user input once, where it comes in, then pass it to classes whose constructors guarantee their invariants. Inside, code can trust every object it's given.
        • 
        
      • Structs are still everywhere. Settings, coordinates, records read from files: if any combination of values is fine, professionals use a plain struct with public fields and defaults.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "A class and a struct are different kinds of thing." Only the default access differs (public for struct, private for class).
        • 
        
      • "private hides data from hackers." It stops honest mistakes at build time; it adds no run-time protection.
        • 
        
      • "Members are set in the order of the initialiser list." Always in declaration order (panel 19).
        • 
        
      • "Every private field needs a getter and a setter." A trivial setter undoes the vault (C.131). Offer actions instead.
        • 
        
      • "const at the end of a member function is optional decoration." Without it, the function can't be called through const& or on a const object.
        • 
        
      • "The error is where the Compiler points." For a missing const, the call is where it shows; the fix is at the declaration (the note says where).
        • 
        
      • "If my class has a constructor, I still get a free default one." Not once you've written any constructor.
        • 
        
      • "A constructor returns the new object." It has no return type at all; it fills in an object that already has its memory.
        • 
        
      • "I must call the destructor at the end." C++ calls it automatically at the end of the scope. Calling it yourself on an ordinary object would destroy it twice.
        • 
        
      • "points = points; sets the member." When a parameter has the member's name, both sides mean the parameter (Boss 2). Use the initialiser list, this->, or a different name.
        • 
        
      • "A const member function makes the whole class read-only." It only promises that that function won't change the object.
        • 
        
      • "In the .cpp file I can drop the class name." Without Account::, you've written a separate ordinary function (panel 28).

    Words from this chapter
    
      
      
      
        
      class
      A user-defined type whose members are private unless declared otherwise.
      
        
      access specifier
      public:, private: (and protected:, Chapter 24): who may use the members that follow.
      
        
      public
      Usable by any code. The public members form the class's interface.
      
        
      private
      Usable only by the class's own member functions.
      
        
      encapsulation
      Keeping data private and offering only checked operations on it: the vault and the window.
      
        
      data member
      A variable that belongs to each object of a class, such as balance_.
      
        
      member function (method)
      A function declared in a class and called on an object: acc.deposit(50).
      
        
      this
      Inside a member function, a pointer to the object it was called on. this->x means "my x".
      
        
      const member function
      A member function marked const after its parameters; it promises not to change the object.
      
        
      const object
      An object that may not be changed; only const member functions can be called on it.
      
        
      qualifier
      A word like const that adjusts a type. "Discards qualifiers" means a call would ignore a const.
      
        
      invariant
      A rule about an object's data that must always be true, such as "the balance is never below zero".
      
        
      constructor
      A special member function with the class's name and no return type, run automatically when an object is created.
      
        
      member initialiser list
      The : a_{x}, b_{y} part of a constructor, which initialises members before the body runs.
      
        
      default member initialiser
      A value written on the member itself, int balance_ = 0;, used when a constructor doesn't set it.
      
        
      default constructor
      A constructor callable with no arguments: Account a;.
      
        
      overloaded constructors
      Several constructors with different parameter lists; the arguments pick one.
      
        
      = default
      Asks the compiler for its usual version of a special member function.
      
        
      explicit
      Marks a constructor that may not be used for silent conversions.
      
        
      declaration order
      The order members are written in the class; members are always initialised in this order.
      
        
      getter / setter
      Member functions that return or replace one private value. Getters are often fine; trivial setters bypass the invariant.
      
        
      scope resolution operator (::)
      Names something inside a class or namespace: Account::deposit, std::cout.
      
        
      destructor
      The special member function ~Name(), run automatically when an object's lifetime ends.
      
        
      scope
      The region of code, usually between braces, where a name exists. A local object is destroyed at the end of its scope.

C++ · CHAPTER 28

A CITY OF ADDRESSES

Picture: Wren, the mechanic in orange coveralls, waves hello. Beside her stands the Linker in a red cap and apron, holding a taped box marked LINK, and the Compiler, the big checkpoint robot, with its gate up.

A big C++ program is a city. Every .cpp file is a neighbourhood, built on its own by the Compiler. The Linker is the city planner: it joins the neighbourhoods and keeps the city's address book. Some names are local street names that only one neighbourhood uses. Others are city-wide addresses, and there must be exactly one of each. Today Wren learns which is which, how to share signs between neighbourhoods, who gets set up first, how to pack neighbourhoods into libraries, and what the names really look like inside the address book. About 120 minutes, with 25 hands-on checks.

  1. One city, many neighbourhoods: translation units, the address book, external and internal linkage, static and unnamed namespaces
  2. Signs every street can share: headers, inline functions and variables, the one-definition rule, extern
  3. Who arrives first: globals before main, the static initialisation order fiasco, construct on first use
  4. Warehouses and lending libraries: static libraries with ar, shared libraries, LD_LIBRARY_PATH and rpath, the map of a build
  5. Sign painters and name stamps: the preprocessor, macros that leak, #ifdef, name mangling, extern "C", modules
  6. Boss level and recap

PART 1 · ONE CITY, MANY NEIGHBOURHOODSTranslation units, the address book, and two kinds of names

1

Imagine a city with three neighbourhoods: the Harbor, the Market and Main Square. Each one has little lanes that only locals use. Two neighbourhoods may both have a "Mill Lane", and nobody minds, because a local lane is only ever used inside its own neighbourhood. But a city-wide address, the kind a letter from anywhere can reach, must be unique. The city planner keeps the address book.

The Linker says: You've met me as the waiter in Chapter 10. Today I'm the city planner. The Compiler builds each neighbourhood alone. I join them and look up every city-wide name in my book. A name with no entry? undefined reference. A name with two entries? multiple definition. Local lanes never reach my book at all.

2

First, a precise word for "neighbourhood". The Compiler never reads a header by itself. It reads one .cpp file after the preprocessor has pasted in every #include and replaced every macro. That pasted-together text is a translation unit (a TU). g++ -E stops after the pasting and prints the TU; -P leaves out its bookkeeping lines.

    4
    
The grown-up word for "can other files reach this name?" is linkage. A name with external linkage is a city-wide address. A name with internal linkage is a local lane. (Names inside a function, like a loop counter, have no linkage at all: they aren't even on the map.)

    

      
EXTERNAL LINKAGEa city-wide address
The default for functions and for global variables that aren't const. Other files can reach the name with a declaration. There must be exactly one definition in the whole program. nm shows a capital letter.

      
INTERNAL LINKAGEa local lane
Anything marked static at file level, anything inside an unnamed namespace, and global const or constexpr variables. Every TU can have its own, with the same name, and they never meet. nm shows a small letter.

    

    

      
      
Wren says: Here's the rule of thumb for every name you write at the top of a .cpp file: "Does any other file need this?" Yes: put a declaration in the header, leave the definition external. No: make it local. Most little helpers should be local lanes.

Modern C++ prefers a different spelling for "this file only": an unnamed namespace. It's a namespace with no name. Everything inside it gets internal linkage, and you can put many helpers, and even types, in one block. The C++ Core Guidelines recommend it for anything a .cpp file doesn't export (SF.22).

    Chapter 10 promised a word that lets a body live in a header. Here it is: inline (line 5). An inline function may be defined in many TUs, as long as every definition is identical. The Linker keeps one and throws the rest away.
    
    tools.h
    
    
    
    
    
    How this run was really made: in ~/cpp-ch28/hdr_inline, after hdr_inline.cpp was copied in as tools.h and old .o files and the old program were deleted; then the commands shown ran word for word.
    
    
    
      
      
    The Linker says: See the W in my book? It means "weak": "I have a copy of helper(), but I'm one of many identical copies". Two weak copies don't clash. I keep one, and every call goes there.
    
    
    
    
    
      
      
    The Professor says: Old books say inline means "paste the body at every call, for speed". That was the original idea, and compilers still may do that, but they decide for themselves, with or without the word. Today, the meaning that matters is "multiple identical definitions are allowed". Use inline when a function body belongs in a header, not to make code faster.
    
    
    
  
    

  
    
    11
    
    So here is the whole one-definition rule (the ODR): every city-wide function and variable has exactly one definition in the program, unless it's inline: then each TU that uses it has its own definition, and they must all be identical. Some things are inline without the word. Use this table when you decide where a definition goes.
    
    
    
      Which definitions may go in a header included by many files
      
    definitionin a header?why
    
      
        
    int area(int w, int h);✓ yesa declaration: promises are never a problem
    
        
    struct Order { int soups; };✓ yesa type: one per TU is allowed, and it makes no code
    
        
    inline int helper() { ... }✓ yesinline: identical copies are fine
    
        
    constexpr int sq(int x) { ... }✓ yesconstexpr functions are inline automatically
    
        
    member functions written inside the class body✓ yesinline automatically
    
        
    templates (Chapter 26)✓ yeseach stamped copy is inline-like (the W you saw in Chapter 26)
    
        
    inline int next_ticket = 1;✓ yesan inline variable (C++17): one shared variable
    
        
    constexpr int max_lamps = 12;✓ yesconst/constexpr globals are internal: each TU gets its own copy (add inline to share one)
    
        
    int area(int w, int h) { ... }✗ noexternal, not inline: multiple definition (panel 9)
    
        
    int population = 0;✗ noexternal variable definition: multiple definition
    
          
    
    
    
    
      
      
    The Professor says: "Identical" is your job, not the Linker's. If two TUs had different bodies for the same inline function (say, an old header in one folder and a new one in another), the Linker would still keep just one, silently. The standard calls that an ODR violation: the program is broken, but no compiler or linker is required to tell you ("ill-formed, no diagnostic required"). In practice, what it does is unpredictable. One header, included everywhere, keeps them identical.

      PART 4 · WAREHOUSES AND LENDING LIBRARIESStatic libraries, shared libraries, and how a program finds them
      

  
      
    19
    
      Wren's shop code (prices and tax) is used by several programs. Instead of handing everyone a pile of .o files, she packs them into a library. There are two kinds. A static library is like photocopying the recipes you need into your own cookbook when you build it. A shared library is like a lending library: your cookbook just says "see the library", and the program goes there every time it opens.
      
    
      
    
      
      
      
      The Linker says: For a static library, I copy the pieces you need into your program. For a shared one, I only write down "needs libshop.so". Someone else, the loader, has to find that file each time the program starts.

      What you learned in Chapter 28
      
    
        
      
      • ONE .CPP, ONE NEIGHBOURHOODA translation unit is a .cpp plus everything the preprocessor pasted (g++ -E). Each is compiled alone into a .o with a symbol table: nm shows T (city-wide), t (local) and U (needed from elsewhere).
        • 
      
      • LOCAL LANES, CITY-WIDE ADDRESSESFunctions and non-const globals have external linkage by default: one definition in the program, or multiple definition. Helpers only one file uses go in an unnamed namespace (or static): internal linkage, no clashes.
        • 
      
      • IDENTICAL COPIES ARE FINEinline lets a function or variable be defined in a header included everywhere; the Linker keeps one (W). extern int x; promises a variable; int x = 0; in one .cpp defines it. A static variable in a header gives every file its own copy.
        • 
      
      • ASK, DON'T PEEKGlobals are set up before main (top to bottom in one file), but the order between files isn't promised: the static initialisation order fiasco. Use a function with a static local (construct on first use), or constexpr.
        • 
      
      • COPY IT IN, OR LOOK IT UPA static library (ar rcs libx.a) is copied in at link time; objects before -lx. A shared library (-fPIC, -shared) is found by the loader at every start: cannot open shared object file until LD_LIBRARY_PATH or an rpath says where.
        • 
      
      • THE PAINTER DOESN'T READMacros paste text, ignore scopes and leak out of headers (expected unqualified-id before numeric constant). Prefer constexpr; keep macros for #ifdef switches and guards. Names are mangled (_ZN4shop5priceEi, read back with c++filt); extern "C" turns that off for C neighbours.

    Under the hood: object files, weak symbols, start-up code and the loader's search
    
      
      
      What's inside a .o file
      
      
      On Linux, object files, libraries and programs use a format called ELF. An object file holds sections: .text (machine code), .data (globals with a starting value), .bss (globals that start as zero, which take no space in the file), .rodata (constants and string literals), plus debug information from -g. It also holds a symbol table (what nm prints) and relocations: notes like "at offset 0x12 in .text, put the address of price_of(int)". Linking is mostly two jobs: match each undefined symbol to a definition, then patch every relocation with the final address. readelf -s and objdump -dr show all of this; nm's letters are a summary (T/t = .text, D/d = .data, B/b = .bss, R/r = .rodata, W = weak, U = undefined).
      
      
      Why inline copies don't clash
      
      
      g++ puts each inline function, and each template instantiation, in its own little section marked as a group ("COMDAT"), and gives its symbol weak binding (W). When the Linker meets several groups with the same name, it keeps the first and discards the rest. It never compares their contents. That's why two different inline definitions with one name don't produce an error: one of them simply disappears. ASan can catch some such mismatches for global variables (odr-violation), and building with link-time optimisation (-flto) makes g++ warn about some of them (-Wodr).
      
      
      Who runs the global constructors
      
      
      The program's real entry point isn't main. A small piece of start-up code from the C library runs first. Each object file that has globals needing code to set them up contributes a pointer to an .init_array section; the start-up code calls them all, then calls main, then (after main returns, or on std::exit) runs the destructors in reverse. The order of entries in .init_array follows the order the Linker met the object files, which is why panel 17 depended on the link line. That's an implementation detail: the standard leaves the order between TUs unspecified.
      
      
      Zero first, then dynamic
      
      
      The standard splits start-up into static initialisation (zero-filling, plus anything the Compiler can compute, such as int n = 10; or a constexpr value) and dynamic initialisation (anything that runs code, like read_base()). Static initialisation is complete before any dynamic initialisation starts, which is why the early reader in panel 17 saw 0 rather than garbage. constinit (C++20) guarantees a variable is in the first group.
      
      
      Where the loader looks
      
      
      When a program that needs libshop.so starts, the Linux loader (ld.so) searches, in order: the program's RPATH (an older form of runpath, used only if there's no RUNPATH), the LD_LIBRARY_PATH folders, the program's RUNPATH (what g++ writes today, as panel 24 showed), the system cache built by ldconfig from /etc/ld.so.conf, and finally /lib and /usr/lib (the order in the ld.so(8) manual page). ldd ./shop prints where each needed library would be found, or not found. Never run ldd on a program you don't trust: it may run parts of it.

    In real programs
    
      
      
        
        
      • The standard library itself is mostly header-only templates plus one shared library: on this system libstdc++.so.6. Every program in this book needed it at start-up; that's normal, and why system libraries never need an rpath.
        • 
        
      • Header-only libraries rely on inline and templates (panel 11's table) so you can use them with a single #include and no link step.
        • 
        
      • Hiding symbols. Big shared libraries are often built with -fvisibility=hidden, exporting only marked functions. It's the shared-library version of an unnamed namespace: fewer clashes, faster loading.
        • 
        
      • Plug-ins. Programs such as image editors and audio software load extra shared libraries while running, with dlopen (Linux, macOS) or LoadLibrary (Windows), and look up functions by name. Plug-in interfaces are usually extern "C", because unstamped names are easy to look up and don't depend on the compiler.
        • 
        
      • CMake (Chapter 17) builds both kinds: add_library(shop STATIC ...) or add_library(shop SHARED ...), and target_link_libraries puts things in the right order for you.
        • 
        
      • Versioned libraries. System libraries have names like libshop.so.2, so an incompatible new version can live next to the old one. That's beyond this book, but now you know why the names have numbers.
        • 
        
      • Static analysis of linkage. clang-tidy (Chapter 18) has checks aimed at two of this chapter's mistakes: misc-use-anonymous-namespace and misc-definitions-in-headers. Both are in this machine's clang-tidy 18 (clang-tidy --list-checks names them), but they weren't run on this chapter's code.

    Common wrong ideas
    
      
      
        
        
      • "A header guard prevents multiple definitions." Only within one TU. Across TUs, only inline or moving the definition to one .cpp helps (panel 9, Boss 1).
        • 
        
      • "If no header mentions a function, it's private." Functions are external by default (panel 5). Private means an unnamed namespace or static.
        • 
        
      • "static in a header makes one shared variable." It makes one per TU (the 1 1 2 exercise).
        • 
        
      • "inline makes code faster." Today it means "identical definitions in many TUs are allowed". The Compiler decides about speed itself.
        • 
        
      • "Globals are set up in the order the files are listed in my project." Within a file, top to bottom; between files, the order isn't promised (panel 17).
        • 
        
      • "If it linked, it will run." A shared library can still be missing at start-up (panel 23).
        • 
        
      • "Library order on the link line doesn't matter." With GNU ld and static libraries it does: users before suppliers (panel 21).
        • 
        
      • "Macros respect namespaces." The painting happens before namespaces exist (panel 28).
        • 
        
      • "extern \"C\" means the function must be written in C." It only changes the name's stamp (and calling rules) so C can link with it. The body can be any C++.
        • 
      
      
    
      
  
      

  
      
    The Professor's history corner: why C++ builds this way
    
      
      
      C++ kept C's model of separate compilation: each source file compiled alone, joined later by a linker that knows nothing about the language. That made sense on 1970s machines with little memory, and it still makes big builds parallel, but it's why a header must be pasted into every file that uses it, and why the Linker can only compare names, not meanings. Name mangling was C++'s way of fitting overloading and namespaces into linkers built for C, which allowed only one meaning per name.
      
      
      According to Dennis Ritchie's own history of C, the preprocessor arrived around 1972–73, partly at Alan Snyder's urging, inspired by the file-inclusion features of BCPL and PL/I. It began with only included files and simple string replacement, and was at first considered an optional adjunct to the language. Modules (C++20) are the first serious step away from that pasting model, half a century later.

    Words from this chapter
    
      
      
      
        
      translation unit (TU)
      One .cpp file after the preprocessor has pasted its includes and expanded its macros: what the Compiler actually compiles.
      
        
      symbol
      A name in an object file's table: a function or variable it defines or needs.
      
        
      symbol table
      The list of symbols in an object file, shown by nm.
      
        
      linkage
      Whether a name can be reached from other TUs.
      
        
      external linkage
      The name is city-wide: other TUs can use it, and there must be one definition in the program.
      
        
      internal linkage
      The name is local to its TU; other TUs may have their own with the same name.
      
        
      unnamed namespace
      namespace { ... }: gives everything inside internal linkage.
      
        
      one-definition rule (ODR)
      Each city-wide function and variable has exactly one definition in the program, except inline ones, which must be identical in every TU.
      
        
      inline (today)
      "Identical definitions in several TUs are allowed"; lets a function or variable be defined in a header.
      
        
      inline variable
      A variable defined with inline (C++17): one shared object even though its definition is in a header.
      
        
      weak symbol
      A symbol (W in nm) the Linker may meet several times, keeping one.
      
        
      extern
      Makes a variable declaration a promise without memory: extern int x;.
      
        
      static initialisation order fiasco
      A global reading another file's global before it has been set up, because the order between TUs isn't specified.
      
        
      construct on first use
      Replacing a global with a function that returns a static local, made the first time it's called.
      
        
      constinit
      C++20: requires a global to be set up before any code runs, or the build fails.
      
        
      library
      Compiled code packed for reuse by many programs.
      
        
      static library
      An archive of object files (.a, .lib); the pieces needed are copied into the program at link time.
      
        
      ar
      The archiver: makes (rcs) and lists (t) static libraries.
      
        
      shared library
      A library loaded when the program starts (.so, .dylib, .dll); one copy can serve many programs.
      
        
      position-independent code
      Machine code that works at any address (-fPIC); required for shared libraries.
      
        
      loader
      The system part (ld.so on Linux) that finds and loads shared libraries each time a program starts.
      
        
      LD_LIBRARY_PATH
      An environment variable listing extra folders for the Linux loader to search.
      
        
      rpath / runpath
      A folder list written into a program by the Linker (-Wl,-rpath,...) telling the loader where to look; $ORIGIN means the program's own folder.
      
        
      preprocessor
      The text-pasting step before compiling: #include, #define, #ifdef.
      
        
      macro
      A name the preprocessor replaces with text; a function-like macro takes arguments.
      
        
      -D
      Compiler flag that defines a macro from the command line: -DCITY_DEBUG.
      
        
      name mangling
      Stamping namespaces, classes and parameter types into a function's symbol name, so overloads get different addresses.
      
        
      c++filt
      Tool that turns mangled names back into C++.
      
        
      extern "C"
      Gives a C++ declaration C linkage: an unmangled name that C code can link with.
      
        
      module
      C++20: a unit compiled once and imported, exporting only what it chooses and leaking no macros.

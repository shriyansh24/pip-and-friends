C++ · CHAPTER 23

SHARED CUSTODY, OLD MAILBOXES

Picture: Wren, the mechanic in orange coveralls, waves hello. Next to her: a dog with a sign-in sheet of three carers, and a row of five numbered mailboxes bolted to a wall.

Chapter 13 gave every heap object one owner, and that's still the best answer most of the time. Today we design ownership on purpose: handing a unique_ptr into and out of functions and keeping cards in a vector; shared custody with std::shared_ptr, where a sign-in sheet counts the carers; the neighbour, std::weak_ptr, who checks the pet still lives here before visiting; and the leak you get when two pets sign each other's sheets. Then we walk down an old street: C arrays, rows of mailboxes bolted to a wall, plus pointer arithmetic, C strings, argv, new[] and delete[], and std::span, the bridge back to modern code. About 130 minutes, with 25 hands-on checks.

  2. Shared custody: shared_ptr and the sign-in sheet
  3. The neighbour who checks: weak_ptr and cycles
  4. Old mailboxes: C arrays, decay and pointer arithmetic
  5. Hidden zeros and the bridge: C strings, argv, std::span

PART 1 · ONE CARD, HANDED ONunique_ptr into and out of functions, and cards in a vector

1

Back at the library. Mabel, the librarian from Chapter 13, has a question pinned above her desk: "Who brings it back?"

Mabel says: Four ways to hold a thing, and only the first two are owners: someone whose job it is to bring it back. Every pointer in a program should make it obvious which kind it is. When nobody can tell who brings it back, it either never comes back (a leak) or comes back twice (a crash).

Wren says: We start with the card you already know, std::unique_ptr, and ask the everyday question: how do I hand one to a function, or get one back? The type of the parameter is how a function tells you what it plans to do with your card.

    PART 2 · SHARED CUSTODYstd::shared_ptr, make_shared, use_count, and passing shared pets around
    

  
    
    7
    
    Meet Biscuit. Biscuit lives with Mum, but Dad and Gran look after him too. Nobody is "the" owner. On Biscuit's kennel hangs a sign-in sheet: every carer writes their name when they start looking after him and crosses it out when they stop.
    
    
    
    
    
      
      
    Mabel says: The rule on the sheet is simple. A new carer adds a name, a carer who stops crosses theirs out, and whoever crosses out the last name takes Biscuit back to the shelter. Nobody has to know who else is caring for him. They only look after their own line.
    
    
    
    
    
      
    Wren says: That's std::shared_ptr<Pet>, also from <memory>. Copying one adds a name to the sheet. Destroying or resetting one crosses a name out. The number of names is the reference count, and .use_count() reads it. When it drops to zero, the last shared_ptr deletes the pet. Last one out takes the pet home.

    11
    
      The sign-in sheet has to live somewhere every carer can reach, so it lives on the heap too, in a small record the library calls the control block. make_shared asks the heap for one block holding both the sheet and the pet. The older spelling, std::shared_ptr<Pet>{new Pet{...}}, makes the pet first and then a separate block for the sheet: two trips.
      
    
      
      
      
    
      
    
      
      
      
      Wren says: So shared_ptr costs more than a card: a copy is two pointers wide (one to the pet, one to the sheet), and every copy or goodbye updates the count in a way that's safe even if two threads do it at once, which takes a little extra work. On this machine the sheet is 16 bytes; Part 3's leak report will show you a pet and its sheet weighing in together. Say make_shared, the way you say make_unique.
      
    
      
  
      

  
      
    12
    
    
      A trap that catches people who've just learned shared_ptr: using it everywhere, because then you never have to decide who owns what.
      
    
      
      
      SHARED BY HABIT"everyone's a carer"
      Nobody can tell from the code when the pet goes home: it depends on who happens to let go last. Copies sneak in (each one a count update), and a carer that was meant to be temporary quietly keeps the pet alive for ever.
      
      
      UNIQUE BY DEFAULT"one owner, many lookers"
      One card, and functions borrow a Pet&. You can read the lifetime off the code. If real sharing turns up later, a card converts: std::shared_ptr<Pet> s{std::move(card)};. It doesn't convert back.
      
    
      
    
      
      
      
      Mabel says: A book that "belongs to everyone" in practice belongs to no one. Real shared custody does exist: a picture shown by three open windows at once, a cache that several parts of a game read, a message held by several queues. Then the sheet is the honest answer. Otherwise, one card (rule R.21: prefer unique_ptr unless you need to share).

    14
    
      use_count() is wonderful for learning, as you've seen. In real programs, handle it with care.
      
    
        
      
      1. Don't steer a program by the count. "If the count is 1, I'm the only carer, so I can change it freely" is a trap: another thread can sign the sheet a moment after you read it. cppreference calls the value approximate in multithreaded programs; only 0 is exact. (There used to be a unique() for "count is 1". It was deprecated in C++17 and removed in C++20.)
        2. 
      
      2. A shared pet can still be changed by everyone. Sharing the ownership doesn't make the pet read-only. Use std::shared_ptr<const Pet> when carers should only look.
        3. 
      
      3. Hold your own copy while you use it (rule R.37). If you got a Pet& out of a shared_ptr that someone else might reset, for example a global or a member, take a local copy first: auto keep{global_pet};. Your name on the sheet keeps the pet alive until you're done.
        4. 
      
      4. .get() still exists, and gives a plain pointer that doesn't sign the sheet. Never hand it to a second shared_ptr: that would start a second sheet for the same pet, and two sheets means two deletes.
        5.

    18
    
        How do you remember a friend without signing their sheet? Ask the neighbour. The neighbour knows where Biscuit lives and can look over the fence, but doesn't sign. Before visiting, the neighbour checks: is Biscuit still here? If yes, they sign in just for the visit, so Biscuit can't be taken home halfway through. If no, they go home.
        
    
        
    
        
      
      
        Wren says: The neighbour is std::weak_ptr<Pet>. You make one from a shared_ptr, and it doesn't change the count. You can't follow it directly (there's no -> on a weak_ptr). Instead you call .lock(), which hands you a real shared_ptr if the pet is still alive, or an empty one if it's gone. .expired() asks "gone yet?" without visiting. Check before you visit.

    21
    
        Put Parts 1 to 3 together and you get a short recipe for designing ownership. Ask it for every pointer you write.
        
    
          
      
        1. Can it just be a plain object or a vector member? Then do that. No pointer at all.
          2. 
      
        2. Exactly one owner? std::unique_ptr, made with make_unique. This is the usual answer when you need the heap.
          3.

        PART 4 · OLD MAILBOXESC arrays, decay, pointer arithmetic, and new[] with delete[]
        

  
        
    22
    
        Now a walk down an older street. Long before std::vector, C (the language C++ grew out of) had the C array: int boxes[5]; is five int boxes side by side, numbered 0 to 4, like a row of mailboxes bolted to a wall. You'll meet them in old code, in C libraries, and in main's own parameters.
        
    
        
    
        
      
      
        The Professor says: A little history. C was designed in the early 1970s to be small and close to the machine. Its arrays are just memory: no size stored anywhere, no checks, and they can't be copied as a whole. C++ kept them so that it could use C code unchanged. Modern C++ wraps the same idea in safer types (std::array, std::vector, std::span), and this part shows you why.
        
    
        
  
        

  
        
    23

          3.

          4.

          5.

    25
    
        Here is the big surprise of C arrays. Pass one to a function and what arrives is not the row: it's the address of box 0. The parameter int a[] looks like an array, but the compiler quietly reads it as int* a, a pointer. This is called array-to-pointer decay.
        
    decay.cpp
    
        
      
        
      
        
    
        
    
          
      
        1. The warning's first line already gives it away: In function 'void count_boxes(int*)'. You wrote int a[]; g++ lists it as int*.
          2. 
      
        2. The warning: 'sizeof' on array function parameter 'a' will return size of 'int*' [-Wsizeof-array-argument], at line 5, with a note pointing back to where a was declared.
          3. 
      
        3. The proof: 20 in main (the row), 8 inside (a pointer is 8 bytes on this machine, whatever it points at).
          4. 
    
        
    
        
      
      
        Wren says: That's the slip of paper in the picture: "start at box 0". It doesn't say how many boxes there are, so every C function that takes an array also needs the count, passed separately. Get the count wrong and you read someone else's mail. An array passed is just a starting address.
        
    
        
  
        

  
        
  

  
        
    26
    
        If a pointer to box 0 is all you get, how do you reach box 2? Pointer arithmetic: p + 2 is a pointer two boxes further along, not two bytes. The compiler multiplies by the size of an int for you.
        
    ptr_math.cpp

          2.

          3. 
      
        3. Line 11: subtracting two pointers into the same array gives the distance in boxes: 4.
          4. 
      
        4. Line 12: ++p moves the pointer one box along, so *p is now 9. This page never prints the raw addresses: they change from run to run, and only the distances matter.
          5.

    Under the hood: control blocks, weak counts, array cookies and decay
    
        
      
        What is really on the sign-in sheet
        
      
        A shared_ptr holds two pointers: one to the object and one to its control block. The control block holds two counts: the strong count (how many shared_ptrs, what use_count() reports) and the weak count (roughly, how many weak_ptrs are watching). When the strong count reaches zero the object is destroyed. The control block itself stays until the weak count also reaches zero, because every neighbour still needs somewhere to read "gone". That is how expired() can answer safely after the pet has left.
        
      
        The make_shared trade-off
        
      
        Because make_shared puts the object and the control block in one allocation, the object's memory (not the object: its destructor has run) can only be handed back when the control block goes, which is when the last weak_ptr goes. For a huge object watched by long-lived weak_ptrs, the two-block form std::shared_ptr<T>{new T{...}} returns the big block earlier. That is the main reason not to use make_shared, and it's rare.
        
      
        Counting safely
        
      
        The counts are updated with atomic operations, so two threads may copy and destroy shared_ptrs to the same object at once without corrupting the count (Chapter 29 explains threads). That safety covers the counts only, not the object: two threads changing the pet itself still need a lock. Atomic updates are slower than plain ones, which is part of why a shared_ptr copy costs more than a unique_ptr move.
        
      
        lock() can't be split
        
      
        "Check expired(), then make a shared_ptr" would have a gap between the two steps in which another thread could drop the last owner. lock() does both as one atomic step, which is why the comic always writes if (auto p = w.lock()) and never "if not expired, then...".
        
      
        Two more tools you'll see in real code
        
      
          
        
        • std::enable_shared_from_this lets an object that is already owned by a shared_ptr hand out another shared_ptr to itself (shared_from_this()) that signs the same sheet. Writing std::shared_ptr<T>{this} instead would start a second sheet: two deletes.
          • 
        
        • The aliasing constructor makes a shared_ptr that points at a member of an object but signs the whole object's sheet, so the member can't outlive its owner.
          • 
      
        
      
        How delete[] knows how many
        
      
        delete[] p isn't told the count, yet it must run a destructor for every element. For element types with destructors, compilers commonly store the count in a few hidden bytes just before the row (the AddressSanitizer legend in panel 28's full report even has an entry for it: Array cookie). Plain delete knows nothing of those bytes, which is one reason a mismatch is undefined rather than merely wasteful.
        
      
        When an array does not decay
        
      
        Decay happens almost everywhere an array is used as a value, with a few exceptions: sizeof(arr) and &arr see the whole array; a reference to an array keeps its size in the type (void f(int (&a)[5]), which only accepts rows of exactly 5); and an array that is a member of a struct is copied when the struct is copied. std::array is that last trick, packaged.
        
      
        Two compilers, two wordings
        
      
        clang++ 18 says panel 24's error differently: array type 'int[3]' is not assignable.
        
      
        
      
        For the exercise in Part 4, clang++ gives two warnings: the same -Wsizeof-array-argument, plus -Wsizeof-pointer-div, which spots the sizeof(x) / sizeof(x[0]) pattern on a pointer. The program's output, average: 6, is the same.
        
      
        
      
        And its version of panel 6's loop error, which names the deleted constructor and then shows which begin() the loop used:
        
      
        
    
        
  
        

  
        
    In real programs
    
        
      
          
        
        • Trees. Parsers, scene graphs and file-system models often store children as std::vector<std::unique_ptr<Node>>, with a plain Node* parent pointing back up. Deleting the root deletes the whole tree; the parent pointer never owns, so there's no loop.
          • 
        
        • Shared assets. Games and editors share textures, fonts and sounds between many users with shared_ptr, and keep a cache of weak_ptrs so an asset nobody uses can be freed and reloaded later.
          • 
        
        • Observers and callbacks. An event source that holds weak_ptrs to its listeners can skip listeners that have gone away, instead of calling into a destroyed object.
          • 
        
        • Asynchronous work. A task scheduled to run later often captures a shared_ptr to the object it works on, so the object can't vanish before the task runs. Chapter 24 introduces lambdas and what their captures can hold.
          • 
        
        • C libraries everywhere. Operating-system calls, compression, image and database libraries are often C. Real C++ code keeps the data in a std::vector or std::string and lends .data(), .size() and .c_str() at the boundary, and wraps C handles in unique_ptr with a custom deleter (Chapter 22).
          • 
        
        • main(argc, argv) is how every command-line tool reads its options. Real tools hand argv to an argument-parsing library rather than walking it by hand.
          • 
        
        • Static analysis. Tools such as clang-tidy flag C arrays, pointer arithmetic, raw new/delete and smart-pointer parameters that should be references, using the same Core Guidelines rule numbers as this chapter.
          • 
      
        
    
        
  
        

  
        
    Common wrong ideas
    
        
      
          
        
        • "shared_ptr is the safe one, so use it everywhere." It's the costly one, and it hides who owns what. It also leaks in loops, which unique_ptr trees can't (panel 12, panel 17).
          • 
        
        • "A weak_ptr keeps the object alive a little." Not at all. Only lock()'s temporary shared_ptr does, for as long as that variable lives (panel 20).
          • 
        
        • "Moving a shared_ptr changes the count." A move passes the place on the sheet; only copies add names (panel 10).
          • 
        
        • "use_count() == 1 means nobody else can touch it." Not in a program with threads, and not if a weak_ptr can lock() at any moment (panel 14).
          • 
        
        • "Smart pointers mean no leaks." shared_ptr loops leak; LeakSanitizer finds them (panel 17).
          • 
        
        • "An array parameter is an array." It's a pointer; sizeof says 8 (panel 25).
          • 
        
        • "p + 1 is the next byte." It's the next element. The compiler scales by the element's size (panel 26).
          • 
        
        • "delete and delete[] are interchangeable for ints." The rules say undefined, ASan says alloc-dealloc-mismatch, and g++ warns (panel 29).
          • 
        
        • "sizeof of a C string is its length." It counts boxes, including the zero and any unused boxes; strlen counts letters (panel 31).
          • 
        
        • "argv[1] is the first word, so argc is the number of words." argv[0] is the program; argc counts it too (panel 33).
          • 
        
        • "A span owns its numbers." It's a view: the row must outlive it (panel 34).
          • 
      
        
    
        
  
        

  
        
    Reading old code safely: a checklist
    
        
      
        Old C and C++ code isn't wrong because it's old. It's just written without the labels that modern types put on every box. When you read it, add the labels in your head:
        
      
          
        
        1. For every pointer, find the owner. Who calls delete (or free)? Is it called on every path, including early returns and exceptions? If you can't tell, that's the first thing to fix.
          2. 
        
        2. For every array parameter, find the count. Is there a separate length? A hidden zero? A comment promising a size? Check every caller agrees.
          3. 
        
        3. Check each new[] meets a delete[], and each malloc a free.
          4. 
        
        4. Look hard at loops with <= over arrays, and at strcpy, strcat, sprintf and gets.
          5. 
        
        5. Build with warnings on (-Wall -Wextra) and run the tests under the goggles (-fsanitize=address,undefined) before changing anything, so you know what was already broken.
          6. 
        
        6. Modernise in small steps (panel 36), re-running the tests after each one.

        ownership

        sink parameter

        reseat
        Make a pointer (or smart pointer) hold a different object; with a card, the old object is destroyed.
        
        
        std::shared_ptr<T>
        A smart pointer that shares ownership; the object is deleted when the last one lets go.
        
        
        reference count / use_count()
        The number of shared_ptrs sharing an object (the sign-in sheet).
        
        
        std::make_shared<T>(...)
        Builds a T and its control block in one heap block and returns the first shared_ptr.
        
        
        control block
        The heap record holding the strong and weak counts (and the deleter) for a shared object.
        
        
        std::weak_ptr<T>
        A non-owning link to a shared object that can tell whether it still exists.
        
        
        lock()
        Turns a weak_ptr into a shared_ptr: a real one if the object is alive, an empty one if not.
        
        
        expired()
        True when a weak_ptr's object has been destroyed.
        
        
        reference cycle
        Owning pointers that form a loop, so no count reaches zero: a leak.
        
        
        direct / indirect leak
        LeakSanitizer's words: a direct leak is pointed at by nothing; an indirect one only by other leaked blocks.
        
        
        C array
        A fixed-size row of elements, int a[5], inherited from C. Can't be assigned.
        
        
        decay
        An array turning into a pointer to its first element, for example when passed to a function.
        
        
        pointer arithmetic
        p + i, p - q, ++p: moving a pointer by whole elements within an array.
        
        
        one past the end
        The address just after an array's last element: fine to compute and compare, never to follow.
        
        
        new[] / delete[]
        The raw way to borrow and return a row of elements on the heap. Must be paired.
        
        
        heap-buffer-overflow
        ASan's name for reading or writing past the end of a heap block.
        
        
        alloc-dealloc-mismatch
        ASan's name for returning memory with the wrong kind of delete or free.
        
        
        C string
        A row of char ending with a zero, '\0'.
        
        
        null terminator
        The zero character that marks the end of a C string.
        
        
        <cstring>
        The header of C's string functions: strlen, strcpy, strcmp and friends.
        
        
        stack-buffer-overflow
        ASan's name for writing past the end of a local array.
        
        
        argc / argv
        main's argument count and array of argument strings; argv[0] is the program.

        A word typed after the program's name in the terminal.

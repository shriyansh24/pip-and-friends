PART 1 · THE KITCHEN CREWWhy build systems exist, a three-line CMakeLists.txt, configure, build and run

1

Picture: Wren shrugs, worried, beside a very long command. Cam the planner points cheerfully, holding recipe cards.

2

Big idea: a build system is a kitchen. You never shout at the cooks yourself. Follow the order along the arrows.

  1. You write CMakeLists.txt: what to make (a program called hello from main.cpp), never how.
  2. Configure: CMake reads your menu, looks around the computer (which compiler? which version?) and writes recipe cards for one particular kitchen: a Makefile for Make, a build.ninja for Ninja, or a Visual Studio project on Windows. Programs that write these cards are called generators.
  3. Build: the head chef, a build tool (Make or Ninja), reads the cards and calls out each order: compile this file, link those. It remembers what it cooked, so next time it only re-cooks what changed.
  4. The cooks are old friends: the Compiler (g++) and the Linker (ld) from Chapters 1 and 10. They do exactly the work you used to ask for by hand.
  5. Groceries (other people's libraries) arrive by package manager, such as vcpkg or Conan. Part 4 peeks inside the van.

CMakeLists.txt

    

    

      
LINE 1 · WHICH CMAKE
cmake_minimum_required(VERSION 3.28)
"This menu needs CMake 3.28 or newer." It also switches on that version's behaviour. Always the first line.

      
LINE 2 · NAME THE PROJECT
project(hello LANGUAGES CXX)
The project's name, and the languages it uses. CXX is CMake's word for C++ (C is C). This is where CMake goes looking for a compiler.

      
LINE 3 · ONE DISH
add_executable(hello main.cpp)
"Make a program called hello from main.cpp." More files? List them all: add_executable(hello main.cpp menu.cpp). Headers needn't be listed.

      
THE GRAMMAR
command(argument argument ...)
Every line is a command with arguments in brackets, separated by spaces, not commas. Command names don't care about capitals; file names do.

    

    

      
      
Cam says: Notice what's not there: no g++, no -o, no flags. The menu says what you want, and I work out how to make it on whatever computer I find. That's why the same CMakeLists.txt builds on Linux, macOS and Windows.

The menu for a library plus an app. CMake calls each thing it can build a target: here, the library kitchen and the program app. Every target_... command adds something to one target.

    CMakeLists.txt
    

    

      
LINE 4 · A LIBRARY TARGET
add_library(kitchen kitchen.cpp)
Compile kitchen.cpp and pack the result as a library called kitchen (on Linux, the file libkitchen.a). A library has no main; it's a box of ready-cooked parts.

      
LINE 5 · WHICH C++
target_compile_features(kitchen PUBLIC cxx_std_23)
"kitchen needs C++23." PUBLIC means: and so does anyone who uses it. CMake picks the right flag for each compiler.

      
LINES 6, 10 · EXTRA FLAGS
target_compile_options(app PRIVATE -Wall -Wextra)
Flags for this target only. PRIVATE: just for compiling this target, not passed on to users.

      
LINE 9 · CONNECT THEM
target_link_libraries(app PRIVATE kitchen)
"app uses kitchen": link the library into the program, and hand over kitchen's PUBLIC settings, such as C++23.

    

    
PUBLIC or PRIVATE? Think of a dish's label. PRIVATE is a note for the cook ("I used a sharp knife"): it matters while cooking this target only. PUBLIC is a note for everyone who eats it ("contains nuts"): it travels to every target that links this one. A third word, INTERFACE, is "only for the eaters", which Part 6 uses.

STATIC · .aadd_library(kitchen kitchen.cpp)
The default (unless a project sets BUILD_SHARED_LIBS). A packed box of object files. At link time the parts the program uses are copied into the program. The program stands alone; libkitchen.a isn't needed to run it. Change the library, and every program must be relinked.

      
SHARED · .soadd_library(kitchen SHARED kitchen.cpp)
A separate file (.so on Linux, .dylib on macOS, .dll on Windows), loaded when the program starts. Many programs can share one copy, and it can be updated without relinking them. But it must be findable at run time, or the program can't even start.

    

    

      
      
The Linker says: That last error isn't from me, and it isn't from your program: error while loading shared libraries comes from the loader, the part of the system that starts programs. Your main never ran. Exit code 127 is the loader giving up before main. CMake wrote the build folder's path into app so it finds the library there; move the library, and the search fails.

    Under the hood: the cache, the generators, how a build knows what changed, and how test frameworks find tests
    
    
      
    Configure is really three steps
    
      
    CMake's configure step (1) detects the toolchain: it compiles tiny test programs to learn the compiler's name, version and abilities, which is what the Detecting CXX compiler ABI info lines are; (2) runs your CMakeLists.txt like a script, top to bottom, building an in-memory model of targets and their properties (Configuring done); (3) generates the build files from that model (Generating done). Panel 15's typo is found in step 2 ("no such file") and reported again in step 3 ("no sources"), which is why it appears twice.
    
      
    The cache
    
      
    build/CMakeCache.txt is a plain text file of NAME:TYPE=value lines. Everything you pass with -D lands there and is remembered, so later configures of the same folder don't need the option again. Panel 19's grep read its build-type flag entries (four flag strings, each with an -ADVANCED bookkeeping line). To change a setting, configure again with a new -D, or use the interactive editors ccmake (terminal) and cmake-gui. To forget everything, delete the build folder, or use cmake --fresh (CMake 3.24 and later), which throws away the cache but keeps the folder.
    
      
    Targets and properties
    
      
    Modern CMake is all about targets. Each target has properties: its sources, include directories, compile features, compile options, linked libraries. The target_... commands set them, each with a scope: PRIVATE (for building this target), INTERFACE (for those who link it) or PUBLIC (both). target_link_libraries follows the INTERFACE and PUBLIC parts transitively: if app links kitchen and kitchen publicly links fmt::fmt, app gets fmt's include path too. Variables like CMAKE_CXX_STANDARD are only defaults copied into a property (CXX_STANDARD) at the moment each target is created: hence panel 17.
    
      
    How the head chef knows what changed
    
      
    Make compares file timestamps: a rule runs when any of its inputs is newer than its output. CMake's rules list each object file's inputs, including every header it included, which g++ records during compilation (the -MD -MF ....d flags in panel 11 write "dependency files"). Ninja does the same and also keeps a log of the exact command used for each output (build/.ninja_log), so a changed flag triggers a rebuild even when no file changed. Both run commands in parallel when allowed: cmake --build build -j 8, or --parallel. Ninja's default is a little more than the number of CPU cores; ninja --help prints it for your machine.
    
      
    An edited menu counts as a change too. The exercise after panel 13, for real: a copy of the kitchen project in ~/cpp-ch17/cmakeedit, built once, then sed adds -Wshadow to line 10 of CMakeLists.txt, and the build runs again with no configure typed in between. The first three lines of its output are CMake re-planning by itself; then only app's main.cpp.o is recompiled, because only app's flags changed. (The | sed on the last command again only blanks the timings.)
    
      
    
      
    How this run was really made: the menu (cmakeedit.cpp, panel 9's menu letter for letter) was copied in as CMakeLists.txt, and the configure really ran as cmake --fresh ..., so every capture starts from an empty cache.
    
      
    -std=gnu++23 and CMAKE_CXX_EXTENSIONS
    
      
    For g++ and clang++, CMake turns cxx_std_23 into -std=gnu++23, because the property CXX_EXTENSIONS defaults to ON. GNU extensions are mostly harmless additions, but code that leans on them won't compile with Microsoft's compiler. set(CMAKE_CXX_EXTENSIONS OFF) before your targets gives -std=c++23, which is what this book's single-file programs use.
    
      
    How a shared library is found
    
      
    On Linux, the loader (ld.so) searches the program's built-in run path (RPATH or RUNPATH), then LD_LIBRARY_PATH, then the system folders listed in /etc/ld.so.cache. CMake writes the absolute path of the build folder into programs it builds, which is why panel 20's app ran from the build folder and failed once the .so moved. When you install a project (cmake --install build), CMake rewrites that path. macOS uses @rpath, and Windows looks for .dll files next to the .exe and on PATH.
    
      
    How a test framework finds your tests
    
      
    TEST_CASE("...") is a macro. It expands into a function with a made-up unique name (that's why g++ messages inside tests mention names like DOCTEST_ANON_FUNC_20) plus a global object whose constructor registers that function in a list, before main starts. The main that DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN provides walks the list, applies filters, runs each function and catches every exception, and returns 0 only if nothing failed. CHECK(a == b) uses operator tricks to capture a and b separately, which is how it can print values: CHECK( 200 == 300 ). Catch2 and GoogleTest work the same way.
    
      
    Exit codes all the way up
    
      
    doctest returns 1 when anything failed; CTest treats any non-zero exit code (or a crash) as a failed test, and itself exits with 8 when tests failed. Continuous-integration services (GitHub Actions, GitLab CI) mark a whole run red when a command exits non-zero. In panels 32 and 34 the | sed pipe hides CTest's exit code, because a shell pipeline reports the exit code of its last command (sed). Scripts that pipe test output use set -o pipefail to keep the failure.

    In real programs
    
    
      
      
        
    • CMake is the common language. Most open-source C++ projects ship a CMakeLists.txt, and CLion, Visual Studio, VS Code (CMake Tools extension) and Qt Creator open such a folder directly. Other build systems exist (Meson, Bazel, Bazel's cousins Buck2 and Pants, Visual Studio's own MSBuild projects, plain Makefiles), but knowing CMake lets you build almost anything you download.
      • 
        
    • Presets. Instead of remembering -G Ninja -DCMAKE_BUILD_TYPE=Debug ..., teams commit a CMakePresets.json and run cmake --preset debug, then cmake --build --preset debug and ctest --preset debug.
      • 
        
    • Multi-config generators. Visual Studio and Xcode (and "Ninja Multi-Config") hold Debug and Release in one build folder. There you choose at build time: cmake --build build --config Release, and ctest -C Release. CMAKE_BUILD_TYPE is ignored by them.
      • 
        
    • Getting dependencies. find_package for things installed on the system or by a package manager. vcpkg in "manifest mode" reads a vcpkg.json listing your libraries and is plugged in with -DCMAKE_TOOLCHAIN_FILE=.../vcpkg/scripts/buildsystems/vcpkg.cmake. Conan reads a conanfile.txt or conanfile.py and generates files that find_package can use. CMake's own FetchContent module downloads a library's source at configure time and builds it as part of your project, which is how many projects pull in GoogleTest or Catch2.
      • 
        
    • Tests on every push. Continuous integration runs configure, build and ctest --output-on-failure on every change, often on Linux, macOS and Windows at once, with several compilers. That's where "passes on my laptop" tests (panel 36's unordered order) get found out.
      • 
        
    • Test frameworks in the wild. GoogleTest is used by Chromium, LLVM and many companies; it pairs with GoogleMock for fake objects. Catch2 is popular in open source and on Exercism's C++ track, whose every exercise comes with Catch2 tests. doctest is chosen where compile speed matters, since its header is light and tests can even sit beside the code.
      • 
        
    • Coverage. Building with --coverage (g++) and running the tests produces data that tools such as gcov, lcov and gcovr turn into a report of which lines the tests ever ran (Chapter 11's coverage idea).
      • 
      
    
    
    
  
    

  
    
    Common wrong ideas
    
    
      
      
        
    • "CMake compiles my code." It plans. The build tool runs the compiler (panel 2).
      • 
        
    • "I must run cmake -S . -B build before every build." Once per build folder. cmake --build re-plans by itself when the menu changes (the exercise after panel 13).
      • 
        
    • "cmake --build recompiles everything." Only what's older than its inputs (panel 13).
      • 
        
    • "If I saved the file, the program has my change." Not until you build (panel 14).
      • 
        
    • "Building in the source folder is fine." It works, but mixes hundreds of generated files with yours. Use a separate build folder (panel 6); many projects refuse in-source builds outright.
      • 
        
    • "set(CMAKE_CXX_STANDARD 23) works wherever I put it." Only for targets created after it (panel 17).
      • 
        
    • "Without a build type, CMake builds in Debug." With Make and Ninja you get no flags at all: no -g, no -O (panel 11).
      • 
        
    • "Release is just faster." It also defines NDEBUG, so asserts disappear (panel 19).
      • 
        
    • "A shared library is part of the program." It's a separate file that must be found every time the program starts (panel 20).
      • 
        
    • "find_package downloads the library." It only looks on this computer (panel 21).
      • 
        
    • "A passing test proves the code is right." It proves the code agrees with that test, for those inputs. Tests can be wrong (the trace exercise after panel 23) or missing edges (panel 33).
      • 
        
    • "REQUIRE is stricter, so it's always better." It stops the test case and hides later failures. Use it for preconditions (panel 27).
      • 
        
    • "Two doubles that print the same are equal." Printing rounds (panel 28).
      • 
        
    • "Tests run in Release lose their checks, like asserts." Framework checks don't depend on NDEBUG; running tests in Release is common and useful.
      • 
        
    • "ctest rebuilds the tests." It only runs what's there; build first.

    Lab: run it yourself (Windows, macOS, Linux)
    
    
      
    1. Install CMake (and Ninja, if you like)
    
      
      
        
    • Linux: sudo apt install cmake ninja-build g++ (Debian, Ubuntu) or sudo dnf install cmake ninja-build gcc-c++ (Fedora). This page used CMake 3.28.3, Ninja 1.11.1 and GNU Make 4.3. Check yours with cmake --version. If your distribution's CMake is older than 3.28, change line 1 of each menu to your version (3.20 or later is fine for everything here), or install a newer one with pip install cmake or from cmake.org.
      • 
        
    • macOS: xcode-select --install for the compiler (Apple clang), then brew install cmake ninja with Homebrew, or the CMake app from cmake.org (its menu offers to install the command-line tools).
      • 
        
    • Windows: Visual Studio Community with the "Desktop development with C++" workload includes CMake and Ninja; use the "Developer PowerShell for VS". There, cmake -S . -B build generates a Visual Studio solution, and you build with cmake --build build --config Debug; the program lands in build\Debug\hello.exe. MSYS2 users can pacman -S mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja and follow the Linux steps.
      • 
      
    
      
    2. Your first project
    
      
    Make a folder hello with panel 3's two files. Then:
    
      
    cmake -S . -B build
cmake --build build
./build/hello
    
      
    With Windows and Visual Studio, the last command is .\build\Debug\hello.exe. Try cmake -S . -B build-ninja -G Ninja next to it, and cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release (single-config generators only). Open the folder in VS Code with the CMake Tools extension, or in CLion: both run these same steps when you press Build.
    
      
    3. Get a test framework
    
      
      
        
    • doctest: download the single file doctest.h from the doctest GitHub releases (this page used 2.4.12) into third_party/doctest/, as panel 31 does. Nothing to build.
      • 
        
    • Catch2 v3: sudo apt install catch2, brew install catch2 or vcpkg install catch2, then find_package(Catch2 3 REQUIRED) and target_link_libraries(tests PRIVATE Catch2::Catch2WithMain). Its include(Catch) + catch_discover_tests(tests) registers each test case with CTest.
      • 
        
    • GoogleTest: find_package(GTest REQUIRED) and target_link_libraries(tests PRIVATE GTest::gtest_main), then include(GoogleTest) + gtest_discover_tests(tests). Or fetch it with FetchContent, as GoogleTest's own quickstart shows.
      • 
      
    
      
    4. The grocery van, for real
    
      
    With vcpkg: clone it (git clone https://github.com/microsoft/vcpkg), run its bootstrap script, put {"dependencies": ["fmt"]} in a vcpkg.json next to your CMakeLists.txt, and configure with -DCMAKE_TOOLCHAIN_FILE=<vcpkg>/scripts/buildsystems/vcpkg.cmake. Panel 21's menu then finds fmt. With Conan 2: pip install conan, write a conanfile.txt with [requires] fmt/11.0.2 (or whichever version is current) and [generators] CMakeDeps CMakeToolchain, run conan install . --build=missing, and configure with the toolchain file it prints.

    Words from this chapter
    
    
      
    
        
    build system
    Tools that turn a project's source into programs and libraries, knowing which commands to run, in which order, and what to rebuild after a change.
    
        
    CMake
    A build-system generator: reads CMakeLists.txt and writes build files for a build tool.
    
        
    CMakeLists.txt
    The file (exactly this name) in which a project describes its targets and settings for CMake.
    
        
    configure
    CMake's planning step, cmake -S source -B build: detect the compiler, run the menu, write the build files.
    
        
    build (step)
    cmake --build build: run the build tool, which compiles and links what's out of date.
    
        
    generator
    The part of CMake that writes one kind of build file: Unix Makefiles, Ninja, Visual Studio, Xcode. Chosen with -G.
    
        
    build tool (Make, Ninja)
    The program that reads build files and runs the compile and link commands: the head chef.
    
        
    build folder, out-of-source build
    A separate folder (here build) for everything generated, so the source folder stays clean.
    
        
    CMakeCache.txt
    The file in a build folder that remembers what CMake detected and the settings you chose.
    
        
    target
    Something CMake can build: a program (add_executable) or a library (add_library), with its own properties.
    
        
    PRIVATE / PUBLIC / INTERFACE
    Who a target setting applies to: only this target / this target and its users / only its users.
    
        
    build type
    A named set of flags for single-config generators: Debug, Release, RelWithDebInfo, MinSizeRel, chosen with -DCMAKE_BUILD_TYPE.
    
        
    NDEBUG
    A macro that switches assert off; Release-style build types define it.
    
        
    static library (.a, .lib)
    An archive of object files whose needed parts are copied into each program at link time.
    
        
    shared library (.so, .dylib, .dll)
    A separate file loaded when the program starts, which many programs can share.
    
        
    loader
    The part of the operating system that starts a program and finds its shared libraries.
    
        
    find_package
    The CMake command that finds an installed library and gives you its targets, such as fmt::fmt.
    
        
    package manager (vcpkg, Conan)
    A tool that downloads and builds other people's libraries and tells CMake where they are.
    
        
    vendoring
    Copying a third-party library's files into your own project (like third_party/doctest).
    
        
    timestamp
    The time a file was last changed; build tools compare them to decide what to rebuild.
    
        
    unit test
    A small automatic check of one piece of code (a function, a class) against expected behaviour.
    
        
    test framework
    A library that finds, runs and reports tests: doctest, Catch2, GoogleTest.
    
        
    test case
    One named test, TEST_CASE("..."), holding one or more checks.
    
        
    assertion (in a framework)
    One check inside a test case, such as CHECK(a == b).
    
        
    CHECK / REQUIRE
    A check that records a failure and carries on / one that also ends the test case. GoogleTest: EXPECT_ / ASSERT_.
    
        
    Approx
    doctest's "nearly equal" for doubles, allowing a tiny relative difference.
    
        
    SUBCASE / SECTION / fixture
    Ways to share setup between tests; each subcase re-runs the test case from the top.
    
        
    CTest
    CMake's test runner: enable_testing(), add_test(...), then ctest. It judges each test by its exit code.
    
        
    table-driven test
    A test that loops over a table of inputs and expected outputs.
    
        
    edge case
    An input at the boundary of what's allowed: empty, zero, one, the biggest, a leading zero.
    
        
    red-green-refactor
    Write a failing test, make it pass simply, then tidy the code while the tests stay green.
    
        
    regression, regression suite
    Something that used to work and broke / the growing set of tests run after every change to catch that.
    
        
    implementation detail
    How code does its job inside, as opposed to the behaviour it promises; good tests check behaviour.

C++ · CHAPTER 16 · CAPSTONE

THE FLAT-PACK FINALE

Picture: Wren, the mechanic in orange coveralls, throws both arms up in front of a big flat cardboard box.

Fifteen chapters of parts are spread across the workshop floor: variables, strings, loops, functions, vectors, structs, classes, maps, exceptions, files. Today Wren builds something big out of them: a dice game called BUST! Big programs aren't written top to bottom in one go. They're assembled like flat-pack furniture: lay out the parts, read the steps, build one piece at a time, and give it a shake after every bolt. Along the way you'll learn how a computer makes random numbers, and why a good test uses dice that roll the same way every time. About 120 minutes, with 22 hands-on checks.

  4. The finale: BUST!, the whole game, its map, its files and the curtain call

    3
    
Big idea: a program is built like flat-pack furniture. You don't open the box and start screwing pieces together at random. You (1) lay out the parts and check you have them all, (2) read the steps, (3) assemble one module at a time, and (4) give it a shake after every step to check it wobbles less than before.

    

    

      
Wren says: I've built a lot of flat-pack shelves. The ones that fell over were the ones where I skipped the instruction sheet. Programs are the same. Lay out the parts, read the steps, then build.

      
    

    
Picture: Wren points back at the four stages.

  


  

    4
    
Stepwise refinement is the fancy name for splitting a job until every piece is small enough to write. Start with one sentence, "play BUST!". Split it into three steps. Split any step that still feels big. Stop when each box is one small function you could write in a few lines.

    

    

      
      
Wren says: The green boxes at the bottom are tiny: each one is a few lines of C++. The boxes above them are just those tiny pieces called in order. Nothing in the tree is hard on its own. That's the whole trick: no step is big if you split it enough.

    8
    
    There are two directions to build in, and real programmers mix them.
    
    
    
      
    TOP-DOWNstart with main, stub the rest
    Write the top of the tree first, as calls to stubs (panel 6). You see the whole shape at once and the pieces are guaranteed to fit. Then fill the stubs in, one at a time. Risk: the clever bits are left for last.
    
      
    BOTTOM-UPstart with small, tested pieces
    Write a leaf first, like the Die, and test it on its own (Part 3). Then build bigger pieces out of pieces you already trust. Risk: you may build a part that doesn't fit the final shape.
    
    
    
    
    
      
      
    Wren says: I do both. The outline comes top-down, so I know what parts I need. The tricky parts, the dice and the scoring rules, get built bottom-up and tested before anything leans on them. Whichever way you go, you only ever add one piece between runs.

    PART 2 · DICE YOU CAN TRUSTRandom numbers: engines, seeds, distributions, random_device, and the classic mistakes
    

  
    
    10
    
    A game needs dice. But a computer follows exact steps (Chapter 1), so how can it be random? It cheats, cleverly. A random number engine is a number mill: you pour in one starting number, the seed, and it grinds out a very long list of big numbers that look random but are completely fixed by that seed. That's called pseudo-random ("pretend random"). A distribution is a funnel that turns each big number into the range you want, like 1 to 6.
    
    
    
    
    
      
      
    Wren says: The mill is std::mt19937, the "Mersenne Twister", from <random>. Its list is so long it never repeats in practice, and the numbers pass every everyday test for randomness. But it's a list. Give it the same seed and it tells the same story, every single time.
    
    
    
  
    

  
    
    11
    
    The engine on its own. Line 5 makes it with seed 42. Each call gen() takes the next number off its list: whole numbers from 0 up to 4294967295 (the biggest 32-bit unsigned value).
    
    first_engine.cpp
    
    
      
    
      
    
    
    
    
    
      
      
    Wren says: Run it again: the very same three numbers. Run it on your laptop with any compiler, on Windows, macOS or Linux: the very same three numbers. The C++ standard spells out the Mersenne Twister's exact recipe, so every library must produce this list. Useful for games? Not yet. Nobody rolls a 3421126067.
    
    
    
  
    

  
    
    12
    
    Add the funnel. Line 6 makes a std::uniform_int_distribution<int> from 1 to 6. "Uniform" means every face is equally likely. Line 8 hands it the engine, die(gen): the distribution pulls numbers off the engine's list and turns them into a roll.
    
    dice.cpp

Here's the catch, though: these exact rolls are what this library (libstdc++, used by both g++ and clang++ on this machine) makes from seed 42. The standard fixes the engine's list but not the funnel's recipe, so another library may turn the same list into different rolls. Panel 20 has the details.

    So which seed should a program use? It depends on who's watching. Tests and bug hunts want a fixed seed, so every run replays the same game. Real players want a different game each time, so the seed itself should be unpredictable. std::random_device asks the operating system for a truly unpredictable number, perfect for a seed.

    The classic dice mistake. Line 7 makes the engine inside the loop. No error, no warning, no crash.
    
    same_roll.cpp
    
    
      
    
      
    
    
    
    
    
      
      
    Sneak says: Hee hee. Every lap builds a brand-new engine seeded with 42, and every brand-new engine starts at the top of the same list. So you get the first roll, five times: 3 3 3 3 3. A loaded die, and the Compiler can't see it!
    
    
    
    
      
      
    1. Clue 1: the "random" numbers repeat. A repeated value is the fingerprint of an engine that keeps starting over.
      2. 
      
    2. Clue 2: the value is the same as the first roll of dice.cpp (panel 12): this loop never gets past roll 1.
      3. 
      
    3. The fix: move line 7 up, above the loop. Make the engine once; roll it many times.
      4. 
      
    4. The time trap: seeding with the clock inside the loop, std::mt19937 gen(std::time(nullptr));, fails the same way: the clock only ticks once a second, so a fast loop gets the same seed over and over.

    19
    
      Older code and many tutorials roll dice with std::rand() from <cstdlib>, inherited from C: std::srand(42) sets the seed, and std::rand() % 6 + 1 squeezes the result into 1 to 6. It works, sort of.
      
    rand_dice.cpp
    
      
      
      
      
      
    
      
    
      
      
      
      Wren says: Why I keep it in the bottom drawer: the standard doesn't say how rand works, so these rolls are this machine's C library only. RAND_MAX can be as small as 32767 (it is on Windows with Microsoft's library). The % 6 trick makes some faces slightly more likely than others. And there's only one hidden engine for the whole program, which any function can reseed behind your back.

      PART 4 · THE FINALE: BUST!The whole game, a real game, the map of one turn, the saved file, and the curtain call
      

  
      
    25
    
    
      The rules of BUST!, a classic push-your-luck dice game. Two players: you and Bolt, the workshop's dice-playing robot. On your turn you roll one die, again and again, adding up the faces. Stop whenever you like and bank the turn total into your score. But if you roll a 1, you bust: the whole turn total is lost. First to 20 banked points wins.
      
    
      
    
      
      
      
      Wren says: Bolt's strategy is simple and written in one function: keep rolling until the turn is worth 10, or until banking would win. Every turn in this game starts with one roll, so a turn always risks at least one die. It's a small game, but it needs nearly every part from the last fifteen chapters.

      What you learned in Chapter 16
      
    
        
      
      • LAY OUT THE PARTS, READ THE STEPS, THEN BUILDDesign first: split the job by stepwise refinement until every piece is small, write the plan in plain words (pseudocode), and choose the data (structs, classes, containers) before the functions. Build top-down with stubs, bottom-up with tested pieces, or both.
        • 
      
      • ONE JOB, ONE NAMEOne function per task. A job written twice drifts apart (panel 1); a job written once is fixed once. A function whose honest name needs "and" wants splitting. main should read like the plan.
        • 
      
      • SAME SEED, SAME STORYstd::mt19937 gen{seed}; is a fixed list of numbers, the same on every library. std::uniform_int_distribution<int> die{1, 6}; turns it into rolls (both ends included), but its recipe belongs to the library. Fixed seeds for tests and bug hunts; std::random_device seeds for real play. Leave rand() in the bottom drawer.
        • 
      
      • ONE ENGINE, MADE ONCE, PASSED BY REFERENCEAn engine made inside a loop or a function starts over each time; an engine passed by value is copied and never moves. Both give the same roll again and again: 3 3 3.
        • 
      
      • KEEP THE LUCK IN ONE SMALL BOXPut the randomness in one class, and write the rules as plain functions you can test with fixed numbers on any computer. Test facts that are always true, not exact rolls.
        • 
      
      • TIGHTEN ONE BOLT, CHECK THE WOBBLEAdd one piece, build, run, test, under the safety-net build. If it breaks, it's the piece you just added. Keep the tests: they guard every later change.

    Under the hood: how the Twister turns, why rand() % 6 is unfair, and what the Compiler and Linker each check
    
      
      
      Inside std::mt19937
      
      
      The Mersenne Twister keeps 624 numbers of 32 bits as its state. Each call hands out one of them after a "tempering" step that mixes its bits; every 624 calls it "twists" the whole table into a new one using shifts and exclusive-ors. The name comes from its period, the length of its list before it repeats: 219937 − 1, a Mersenne prime with about 6000 digits. The standard lists every constant of the recipe in [rand.predef], and pins it down with a test value: the 10000th call on a default-constructed std::mt19937 returns 4123659995 (tenk.cpp, panel 15). On this machine the object is 5000 bytes (by_ref.cpp, panel 18, prints it), because libstdc++ stores each of the 624 numbers in an 8-byte slot (624 × 8 = 4992, plus the position in the table).
      
      
      One seed is a small key for a big lock
      
      
      A single 32-bit seed can only start about four billion of the Twister's possible lists. For a game, that's plenty. For a scientific simulation, people feed it more starting material with std::seed_seq, for example eight numbers from std::random_device. And random_device is allowed to be a plain pseudo-random engine on systems without a real source of randomness; some old MinGW versions on Windows really did return the same "random" numbers every run. Modern compilers on Windows, macOS and Linux use the operating system's source.
      
      
      Why distributions differ between libraries
      
      
      Turning numbers from 0 to 4294967295 into 1 to 6 fairly needs care: 4294967296 isn't a multiple of 6, so a plain remainder would favour some faces. Libraries solve it with different tricks (scaling with a multiply, rejecting numbers from an incomplete last block and drawing again), and a rejection may use up an extra engine number. So two libraries can give different rolls from the same engine list, and may even use the engine a different number of times. The standard only demands the result: every value equally likely.
      
      
      Why rand() % 6 is slightly unfair
      
      
      Take the smallest allowed RAND_MAX, 32767: that's 32768 possible values. 32768 = 6 × 5461 + 2, so after the remainder, faces 1 and 2 each come from 5462 values and faces 3 to 6 from 5461. A tiny bias, but a real one, and with ranges that aren't small compared to RAND_MAX it grows. A distribution object does the fair version for you.
      
      
      main(int argc, char* argv[])
      
      
      When a program starts, the operating system passes the words typed after its name. argc is how many there are, counting the program's own name as word 0; argv is an array of C-style strings, so argv[1] is the first word after the name. Reading argv[1] when argc is 1 would read past the end, which is why read_seed checks argc < 2 first. A modern habit is to copy them straight into a std::vector<std::string>.
      
      
      Stubs, declarations and the two checkers
      
      
      A declaration such as int play_game(); is enough for the Compiler: it can check every call's name, argument types and return type without seeing a body. Bodies are matched to calls later, by the Linker, which is why panel 7's missing body is a link error and not a compile error. A stub is the cheapest body that satisfies both: right name, right types, a dummy result. That's also why top-down building works in C++ at all: the declarations are the plan, written in a form both checkers understand.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • Seeds in games. Many games build whole worlds from a seed, so players can share a number and explore the same map. "Seeded runs" in speedrunning and daily puzzle challenges work the same way: same seed, same story, for everybody.
        • 
        
      • Replays and bug reports. A game or simulation that logs its seed can replay a crash exactly. Test frameworks that use randomness print the seed they used for the same reason.
        • 
        
      • Simulations. "Monte Carlo" programs estimate answers by running thousands of random trials: weather, traffic, finance, physics. They need good engines, careful seeding, and distributions beyond uniform (normal, Poisson, and more, all in <random>).
        • 
        
      • Not for secrets. std::mt19937 is predictable: after seeing 624 outputs, anyone can work out all the rest. Passwords, keys and tokens need a cryptographic generator from the operating system or a security library, never a Mersenne Twister.
        • 
        
      • Design before code. Professional teams write design documents, sketch the data, and split work into small tasks before coding, for the same reason Wren reads the instruction sheet. The bigger the program, the more the plan pays.
        • 
        
      • Small functions, small changes. Code reviewers push back on long functions that do several jobs. Changes are delivered in small steps, each one built and tested automatically before it's merged: the flat-pack rule, run by a machine.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "Computers can't do random, so <random> is fake." Engines are pseudo-random by design, which is exactly what makes tests reproducible. For an unpredictable start, seed with std::random_device.
        • 
        
      • "Seeding again makes it more random." Reseeding restarts a list. Seed once (panel 16).
        • 
        
      • "A function can make its own engine each time it's called." Then each call replays the first roll (the exercise after panel 16). Make one engine and pass it by reference.
        • 
        
      • "Passing the engine by value is fine; it's just a number." It's 5000 bytes of state on this library (panel 18), and the copy is the one that moves (panel 17).
        • 
        
      • "uniform_int_distribution<int>{1, 6} gives 1 to 5." Both ends are included.
        • 
        
      • "Same seed means same rolls on every computer." Same engine numbers, yes. Same rolls only on the same standard library (panel 20).
        • 
        
      • "rand() % 6 + 1 is fair." Slightly biased, and its algorithm and range depend on the C library.
        • 
        
      • "Planning is slower than just coding." For anything past a few dozen lines, the plan is faster: panel 1's bug took one wrong name to make and a careful hunt to find.
        • 
        
      • "If every piece works, the whole program works." Pieces can still be joined wrongly: that's why each join gets a run too, like the map's roads.
        • 
        
      • "Tests should check the exact rolls." Then they break on another library. Test the rules with plain numbers, and test dice only for facts that are always true.

    Words from this chapter
    
      
      
      
        
      decomposition
      Splitting a big job into smaller jobs, each one simple enough to write and test.
      
        
      stepwise refinement
      Decomposing step by step: split, then split the parts that are still too big, until each part is one small function.
      
        
      pseudocode
      A program's steps written in plain words for people, before (or instead of) real code. No compiler reads it.
      
        
      top-down
      Building from main downwards, with stubs for the parts not written yet.
      
        
      bottom-up
      Building the small parts first, testing each one, then joining them into bigger parts.
      
        
      stub
      A placeholder function with the right name and types and a dummy body, so the program builds and runs before the real code exists.
      
        
      incremental development
      Adding one piece at a time, and building and testing after each one.
      
        
      capstone
      A final project that uses everything learned so far.
      
        
      pseudo-random
      Numbers that look random but come from a fixed recipe, so the same start gives the same sequence.
      
        
      random number engine
      An object that produces a long sequence of pseudo-random numbers, such as std::mt19937, from <random>.
      
        
      std::mt19937
      The 32-bit Mersenne Twister engine. Its exact sequence is fixed by the C++ standard.
      
        
      seed
      The starting number of an engine. Same seed, same sequence.
      
        
      distribution
      An object that turns an engine's numbers into values with a particular shape, such as std::uniform_int_distribution<int>{1, 6}: whole numbers from 1 to 6, all equally likely. Its exact results depend on the standard library.
      
        
      std::random_device
      A source of unpredictable numbers from the operating system, used to pick a seed.
      
        
      reproducible
      Giving the same result every time it's run, which is what a fixed seed makes a test.
      
        
      std::rand / std::srand
      C's old random function and its seed setter, from <cstdlib>. Algorithm and range depend on the library.
      
        
      RAND_MAX
      The largest value rand() can return: at least 32767; 2147483647 on this machine.
      
        
      modulo bias
      The unfairness when a remainder squeezes a range that isn't an exact multiple of the target size.
      
        
      argc / argv
      The parameters of int main(int argc, char* argv[]): how many words were typed to start the program, and those words.
      
        
      command-line argument
      A word typed after the program's name, such as the 105 in ./bust 105.

C++ · CHAPTER 15

FIRE ALARMS AND SCROLLS

Picture: Wren, the mechanic in orange coveralls, waves hello. Next to her: a building with a ringing fire alarm bell, and a half-unrolled scroll covered in writing.

Until now, when something went wrong, your program either printed nonsense or stopped dead with terminate called.... Today you take charge. A throw pulls the fire alarm; everyone leaves the floors in order; a catch is the trained fire marshal who deals with it. Then you learn to keep asking until the keyboard gives you something sensible. And in the second half, files: scrolls you unroll one line at a time, scrolls you write yourself, and the classic trap that makes the last word appear twice. About 120 minutes, with 25 hands-on checks.

  6. Boss level and recap

PART 1 · PULL THE ALARMWhen a function can't do its job: throw, try, catch and what()

1

Every function you've written so far had a job, and it always managed to do it. Real jobs aren't like that. The bolt you asked for isn't in any drawer. The number someone typed is the word twelve. The file you wanted to read isn't there.

Wren says: A function that can't do its job has a problem: it still has to return something. And whatever it returns, the caller will believe. So today's question is: when a job can't be done, how does a function say so, loudly enough that nobody can miss it?

Ember says: That's my department. I'm Ember, fire marshal. When something goes badly wrong in a building, nobody quietly carries on. Somebody pulls the alarm, and people trained for that kind of trouble take over. I only answer the alarms I'm trained for.

Picture: Wren shrugs, looking worried. Ember, a fire marshal in a red helmet and a yellow coat with reflective bands, points ahead.

    3
    
Big idea: an exception is an alarm a function raises when it can't do its job. Three words make it work.

    

      
      
      
    

    
    
      
  1. throw raises the alarm. You throw an object that describes the problem, usually one of the standard library's ready-made kinds, such as std::runtime_error{"no drawer holds size 9"}. The function stops right there. It doesn't return anything.
    2. 
      
  2. try { ... } marks an area where you're ready for alarms: anything thrown while code inside it runs (including code in functions it calls) goes looking for a handler.
    3. 
      
  3. catch (...) is a handler, written right after the try. It says which kind of alarm it's trained for. If the kind matches, it runs, and then the program carries on after the whole try/catch.
    4. 
    

  


  

    4
    
The same search, but line 12 now throws instead of returning -1. main puts the searches inside a try (lines 17 to 22) with a catch for std::runtime_error (lines 23 to 25). You need #include <stdexcept> for the standard exception kinds.

    2. 
      
  2. Size 9: the loop finds nothing, so line 12 throws. find_drawer stops; there is no return value, so b on line 20 is never created.
    3. 
      
  3. Lines 21 and 22 are skipped. No All found!, no drawer -1. The alarm jumps straight to the handler.
    4.

    5.

    6. 
    

  


  

    5
    
Four pieces to recognise. Solid cards are the alarm side; dashed cards are the marshal's side.

    

      
RAISE ITthrow std::runtime_error{"msg"};
Build an exception object with a message and throw it. The function ends here, without returning.

      
WATCH HEREtry { ... }
Code that might lead to a throw, directly or through the functions it calls.

      
HANDLE ONE KINDcatch (const std::runtime_error& e) { ... }
Runs only for that kind (or kinds built from it: Part 2). e names the thrown object.

      
READ THE NOTEe.what()
The message the object was built with. Every standard exception has what().

    

    
Four cards. Solid border: throw builds and throws an exception object; try marks the watched code. Dashed border: catch with a const reference handles one kind; e.what() returns the message.

    

      
      
Ember says: Write the handler exactly like that card: const, the kind, an &, a name. Part 2 shows what goes wrong without the &. And a try on its own isn't allowed: it needs at least one catch straight after it.

PART 2 · EVERYONE OUTStack unwinding, the family of standard exceptions, catching by reference, and alarms nobody answers


  

    7
    
When a function calls a function that calls a function, the calls stack up like the floors of a building: main on the ground, each new call one floor higher. An alarm on the top floor doesn't just stop that floor. Everyone leaves, top floor first, until they reach someone trained to deal with it.

    
    

      
      
Ember says: Leaving a floor means that function is over. Its local variables are tidied away on the way out, exactly as if it had reached its closing }. This is called stack unwinding, and it's why the cleanup you put in destructors (Chapter 12) still happens. Everyone out, top floor first.

    Ember says: The names are advice: a logic error is a mistake the caller could have avoided (asking for item 10 of 3), a runtime error is trouble you only find while running (the pump jammed). For your own alarms, pick the closest standard kind and give it a clear message. Don't throw plain numbers or strings: they aren't std::exceptions, so catch (const std::exception&) won't catch them and they have no what().

    Wren says: Order matters. Handlers are tried top to bottom and the first match wins, so put the most specific kinds first and the parent last. Put catch (const std::exception& e) first and it would grab everything; g++ even warns about it with -Wexceptions (you'll meet that warning in the Boss level). There's also catch (...), with three real dots, which catches anything, even 42, but can't tell you what it caught. If you use it, it goes last.

    catch_value.cpp

"By value" means e is a brand-new std::exception copied from the real alarm. A plain std::exception has no room for the message, so the copy keeps only the parent part.     The fix is one character, plus a const: catch (const std::exception& e). A reference (Chapter 8's nickname) is another name for the real thrown object, so nothing is copied or cut off.

    15

    uncaught.cpp

      2. 
      
    2.   what():  boom: the message. The library prints it for you because the kind is a std::exception.
      3. 
      
    3. Aborted is not from your program. It's the shell (the program that runs your commands) reporting that your program was killed by the abort signal. The exit code is 134: 128 + 6, the abort signal's number.

    17
    
    Ember's rule card, pinned by the door.
    
    
    
      
      
      
        
    1. Throw when a function can't do its job (E.2), with a standard kind and a clear message.
      2. 
        
    2. Throw by value, catch by const& (E.15).
      3. 
        
    3. Specific handlers first, the parent (std::exception) after them, catch (...) last if at all.
      4. 
        
    4. Catch where you can actually do something: report it, retry, skip one item. Not in every function (E.17). Functions in between just let the alarm pass.
      5. 
        
    5. Exceptions are for errors only (E.3): not for ordinary results like "end of list".
      6. 
        
    6. Somebody must answer. A try/catch in main stops any alarm from becoming terminate (panel 26).

    18
    
    
    The most common alarm of all comes from people. This program asks how many bolts to order, and someone types twelve. The terminal shows what they typed, then what happened.

    21
    
    Every input check you write follows the same five-step recipe. Learn it once.
    
    
    
      
      
      
        
    1. Ask: print a prompt that says what's allowed (1-10).
      2. 
        
    2. Read, and stop if the input has ended.
      3.

      4. 
        
    4. Check the range or any other rule.
      5. 
        
    5. Explain and repeat on failure; leave the loop only with a good value.
      6. 
      
    
    
    
    
    
      
      
    Ember says: Notice who catches the alarm: the loop, right where the problem can be fixed (by asking again). That's the right floor for a marshal. Never trust the keyboard.

    cin_bug.cpp

And even if it did read, the letters abc are still sitting at the front of the input. Without line 10's emergency exit, this loop would print forever. (Stuck in one for real?     23
    
    Chapter 4's mail sorter, jammed. Two separate jobs unjam it, and you need both.
    
    
    
      
      
    1. std::cin.clear() lowers the fail flag, so reading works again. On its own, the next >> would just meet abc again and fail again.
      2.

    3. Order matters: clear first. While the flag is up, ignore refuses to work too.
      4.

    The same five-step recipe with >>. Line 8 reads and checks the range in one condition: std::cin >> n counts as true only if the read worked. Lines 11 to 14 stop if the input ended (there's nothing to clear when there's nothing left). Lines 15 and 16 unjam.

    25
    
    So should a function return a special value, or throw? Here's the simple version of a long debate.
    
    
    
      
    RETURN ITbool, a count, an empty result
    When "didn't work" is a normal, expected answer that the very next line will look at: "is this name in the list?", "did the read succeed?". std::cin does this with its flag. Chapter 12's teller returned false for a refused withdrawal. Cheap, and right there.
    
      
    THROW ITstd::runtime_error and family
    When the function can't do the job it promised and the caller can't sensibly carry on as if nothing happened: a constructor given impossible values, a file that must exist, a drawer that must be there (E.2). Someone further up decides what to do. Ignoring it is impossible: it's handled or the program stops.
    
    
    
    
    
      
      
    Ember says: Panel 2's -1 was the worst of both: a failure dressed up as a real answer. If you return, make failure impossible to mistake for success. If you throw, keep it for things that really are errors. I don't come out for a burnt slice of toast. (Later chapters add tools in between, such as std::optional for "maybe there's an answer".)

    PART 4 · SCROLLSReading files: ifstream, checking the open, getline, words and numbers, the eof trap, and where the program looks
    

  
    
    27
    
    A file is text (or other data) kept on the disk with a name, so it's still there after your program ends. Think of it as a scroll. To read one in C++ you make an input file stream, std::ifstream (from <fstream>), which unrolls it for you. std::getline(file, line) pulls out one line per pull, exactly like std::getline(std::cin, line) did with the keyboard.
    
    
    
    The card shows the start of the line; the whole line, without its newline, goes into the string.
    
  
    

  
    
    28
    
    The pattern you'll write a hundred times. Line 6 opens poem.txt. Lines 7 to 10 check that it really opened. Line 13 pulls one line per loop trip, and the loop ends when there's nothing left to pull.
    
    read_lines.cpp
    
    
      
    
      
    
    
    
    
      
      
    1. std::ifstream file{"poem.txt"}; makes the stream and tries to open the file in one go.
      2. 
      
    2. file.is_open() says whether that worked. (if (!file), "if the stream is not OK", is a shorter check you'll also see; both work here.)
      3. 
      
    3. while (std::getline(file, line)): the pull itself is the loop condition. A pull that gets a line counts as true; a pull that finds the end of the scroll counts as false. Read in the condition, and you never use a line you didn't get.
      4. 
      
    4. No close needed. When file is destroyed at main's }, its destructor closes the file (more in Part 5).
      5. 
    
    
  
    

  
    
    29
    
    
    What happens when the file isn't there? First, proof that it really isn't: ls lists files, and it can't find this one. Then a program that opens it without checking.
    
    missing_file.cpp

The loop ran zero times and the program reported lines read: 0 as if the file were empty. (open=0 is how std::cout prints false.) Check the open. Every time.
    
    
    
  
    

  
    
    30
    
    "But the file is there!" The classic puzzle. A name like "poem.txt" is looked up in the program's working directory: the folder the program was started from. Not the folder the .cpp file is in, and not where the executable lives. Here the same program runs twice: once from its own folder, then from one folder up. (One shell again, so cd .. carries over; the prompt shows the folder.)

IDEs often start programs from a build folder, which is why "it works in the terminal but not in my IDE" is so common. Fixes: start the program from the right folder, set the IDE's working directory, or let the user pass the file's full path.

      PART 5 · WRITING SCROLLS, AND STRING STREAMSofstream, files that close themselves, istringstream to split, ostringstream to build, and CSV lines

      Writing is the mirror image. std::ofstream is an output file stream: you send text into it with <<, exactly like std::cout, and it lands in a file.       What you learned in Chapter 15
      
    
        
      
      • DON'T WHISPER: PULL THE ALARMWhen a function can't do its job, throw a standard exception with a clear message instead of returning a fake value like -1. try { } watches; catch handles one kind; e.what() reads the message.
        • 
      
      • EVERYONE OUT, TOP FLOOR FIRSTA throw abandons functions one by one until a matching handler is found, destroying their locals (newest first) on the way. That's stack unwinding, and it's why destructors still clean up.
        • 
      
      • THROW BY VALUE, CATCH BY CONST REFERENCEcatch (const std::exception& e). Without the & the alarm is sliced and what() says std::exception. Specific handlers first, the parent last; the first match wins.
        • 
      
      • NO MARSHAL, NO BUILDINGAn exception nobody catches ends the program: terminate called after throwing an instance of ..., the shell's Aborted, exit 134. A try in main turns it into a message and exit 1.
        • 
      
      • NEVER TRUST THE KEYBOARDAsk, read, convert (catching invalid_argument and out_of_range), check the range, explain and ask again. A failed std::cin >> jams until you clear() and ignore().
        • 
      
      • CHECK THE OPEN, READ IN THE CONDITIONA missing file says nothing (open=0), so check is_open(). Loop with while (std::getline(f, line)) or while (f >> x), never while (!f.eof()). Names are looked up in the working directory. Streams close themselves; istringstream splits, ostringstream builds.

    Under the hood: how a throw finds its catch, what terminate does, and stream flags
    
      
      
      Two passes: search, then unwind
      
      
      With g++ on Linux (and most modern systems), a throw works in two passes. First the runtime searches up the chain of calls, using tables the compiler wrote into the program, for a catch that matches. Only if it finds one does the second pass unwind: it walks back up, running the destructors of every local on the way, until it reaches the handler. If the search finds nothing, std::terminate is called straight away, before any unwinding, which is exactly why panel 15 printed no leave floor. The C++ standard allows this ("it is implementation-defined whether the stack is unwound" when no handler is found).
      
      
      Zero cost until you throw
      
      
      Because the lookup tables sit unused until something is thrown, a try block costs almost nothing when nothing goes wrong. Throwing, on the other hand, is slow: searching tables and unwinding takes far longer than an if. That's one more reason exceptions are for rare errors (E.3), not for ordinary control flow such as ending a loop.
      
      
      Where the exception object lives
      
      
      The thrown object can't live on a plate that's being cleared, so the runtime copies it into separate memory (with g++'s library, normally the heap, with an emergency reserve if memory has run out). It stays alive until the last handler that's using it finishes. Panel 9 shows it in the heap area, away from the plates.
      
      
      What terminate does
      
      
      std::terminate calls a "terminate handler". g++'s default one prints terminate called after throwing an instance of '...' and, for a std::exception, the what(): line, then calls std::abort(). Abort sends the program signal 6 (SIGABRT); the shell reports that as Aborted and sets the exit code to 128 + 6 = 134. clang++ on this machine uses the same library (libstdc++), so its messages are identical:
      
      
      
      
      Other systems word it differently. Microsoft's compiler words it differently again (not run for this page).
      
      
      Two compilers, one slicing warning
      
      
      g++ warns about panel 13's catch by value with -Wall (-Wcatch-value). clang++ 18 with the same flags says nothing, and the message is still lost:
      
      
      
      
      Both compilers warn about the handler order of Boss 2, in their own words. clang++'s version:
      
      
      
      
      Making stoi strict
      
      
      std::stoi has an optional second argument, a pointer to a std::size_t where it stores how many characters it used. std::size_t used{0}; int n{std::stoi(text, &used)}; followed by if (used != text.size()) rejects "12abc", "3.9" and trailing spaces. C++17 also has std::from_chars in <charconv>, which doesn't throw at all and reports problems in its return value; Chapter 18 meets it.
      
      
      Stream state flags
      
      
      Every stream (std::cin, files, string streams) carries three flags: eofbit (a read hit the end), failbit (a read couldn't produce a value) and badbit (something broke underneath, like a disk error). if (stream) and while (stream >> x) are true when neither failbit nor badbit is set. clear() lowers all three. A failed read into a string leaves the string unchanged (panel 33). Streams can be told to throw instead, with f.exceptions(std::ios::failbit), but that also throws at a normal end of file, so most code checks flags. Chapter 27 goes deeper.
      
      
      Lost output when a program aborts
      
      
      std::cout collects text in a buffer and writes it out in batches. When output goes to a terminal it usually writes each line; when it goes to a file or a pipe (as in this course's captures) it waits much longer. abort() skips the normal shutdown, so anything still in the buffer is lost. That's why the uncaught-exception programs end lines with std::endl, and why error messages go to std::cerr, which isn't buffered.
      
    
      
  
      

  
      
    In real programs
    
      
      
        
        
      • Constructors that validate. Standard and real-world classes throw from constructors when given impossible arguments (std::vector throws std::length_error if asked for more elements than it could ever hold). It's the main way a class guarantees its invariant.
        • 
        
      • One safety net at the top. Command-line tools commonly wrap main's work in a try, print error: ... to std::cerr and return a non-zero exit code, so scripts can detect failure. Servers do the same per request, so one bad request doesn't stop the server.
        • 
        
      • Your own exception types. Bigger programs define their own kinds, usually built on std::runtime_error (for example a ConfigError), so callers can catch exactly their problem. That needs inheritance, in Chapter 24; custom hierarchies are part of Chapter 27's error-handling design.
        • 
        
      • Projects without exceptions. Some code bases (many games, some embedded systems, and Google's C++ style guide historically) switch exceptions off (-fno-exceptions) and report errors through return values instead. C++23 added std::expected to make that style tidier (Chapter 27).
        • 
        
      • Config, logs and CSV. Reading settings files, appending to log files (std::ios::app), and importing and exporting CSV are everyday jobs for ifstream, ofstream and string streams. Production CSV readers also handle quoted fields and commas inside quotes, usually through a library.
        • 
        
      • Paths. Real programs build file paths with std::filesystem::path (C++17) and check existence with std::filesystem::exists, often relative to a folder the user chose rather than the working directory.
        • 
      
      
    
      
  
      

  
      
    Common wrong ideas
    
      
      
        
        
      • "An exception means the program crashes." Only if nobody catches it. Caught, it's an ordinary change of route (panel 6).
        • 
        
      • "After the catch, the program goes back to where the throw was." No: it continues after the try/catch. The rest of the try block, and the functions that were abandoned, never resume.
        • 
        
      • "Every function should have a try/catch." Catch only where you can do something useful (E.17). Functions in between should let alarms pass.
        • 
        
      • "catch (std::exception e) is fine, it compiles." It slices (panel 13). Always const&.
        • 
        
      • "Handler order doesn't matter, C++ picks the best match." It picks the first match, top to bottom (Boss 2).
        • 
        
      • "Destructors always run, even if nothing catches." With an uncaught exception they may not (panel 15).
        • 
        
      • "std::stoi checks the whole string." It stops at the first character that doesn't fit: "12abc" gives 12.
        • 
        
      • "std::cin >> n throws when the input is wrong." It sets a flag. No exception, so try won't help; check the stream (panel 24).
        • 
        
      • "clear() removes the bad input." It only lowers the flag; ignore() removes the input.
        • 
        
      • "Opening a missing file gives an error." Silently not (panel 29).
        • 
        
      • "eof() tells me there's nothing left." It tells you a read already hit the end (panels 33 and 34).
        • 
        
      • "File names are relative to my .cpp file." They're relative to the working directory (panel 30).
        • 
        
      • "I must call close()." The destructor does it. You may call close() to close earlier, but you rarely need to.

    Words from this chapter
    
      
      
      
        
      exception
      An object thrown to signal that something went wrong and normal flow can't continue; it travels up the calls until a matching handler catches it.
      
        
      throw
      Raises an exception: throw std::runtime_error{"msg"};. The current function stops at once.
      
        
      try block
      try { ... }: code whose exceptions (including from functions it calls) will be offered to the handlers after it.
      
        
      catch / handler
      catch (const T& e) { ... }: runs when an exception of kind T (or a kind built from T) reaches it.
      
        
      catch (...)
      A handler that matches any exception at all, without naming it.
      
        
      what()
      The member function of every standard exception that returns its message.
      
        
      <stdexcept>
      The header with std::runtime_error, std::logic_error, std::out_of_range, std::invalid_argument and friends.
      
        
      std::exception
      The parent of all standard exceptions; catching it by const& catches them all.
      
        
      std::out_of_range
      Thrown by .at() with a bad position, and by std::stoi for numbers too big for an int.
      
        
      std::invalid_argument
      Thrown by std::stoi when the text doesn't start with a number.
      
        
      std::runtime_error
      The standard kind for problems found while running; a good choice for your own throws.
      
        
      stack unwinding
      Leaving the functions between a throw and its handler, destroying their local objects, newest first.
      
        
      slicing
      Copying an object into a variable of its parent type, which keeps only the parent part (catching by value does it).
      
        
      std::terminate
      The function called when an exception isn't caught; it ends the program (with g++, by calling abort).
      
        
      exit code
      The number a program hands back to whoever started it: 0 for success, small numbers for failures you report, 134 after an abort. echo $? shows it.
      
        
      input validation
      Checking that input is well-formed and sensible before using it, and asking again or rejecting it if not.
      
        
      fail flag (failbit)
      A stream's "the last read failed" flag; while it's up, reads do nothing.
      
        
      clear() / ignore()
      Lower a stream's flags / throw away input characters, up to a given character.
      
        
      file
      Named data stored on the disk that outlives the program.
      
        
      <fstream>, std::ifstream, std::ofstream
      File streams: an ifstream reads a file, an ofstream writes one (creating or emptying it).
      
        
      is_open()
      Says whether a file stream managed to open its file.
      
        
      eof() / end of file
      True once a read has run into the end of the input; not a look-ahead.
      
        
      working directory
      The folder a program was started from; plain file names are looked up there.
      
        
      <sstream>, std::istringstream, std::ostringstream
      String streams: read from a string as if it were input, or write into a string and collect it with .str().
      
        
      CSV
      "Comma-separated values": a text format with one record per line and fields separated by commas.
      
        
      RAII (preview)
      Letting an object release what it holds in its destructor, as file streams close their files; Chapter 22.
